# 创建会话：避开日常开发的那些“坑”

会话是 ZooKeeper 中最核心的概念之一，客户端与服务端的交互操作都离不开会话的相关操作。临时节点、Watch 通知机制等特性都与客户端会话有密不可分的关系：一次会话关闭时，服务端会自动删除该会话所创建的临时节点；客户端会话退出时，通过 Watch 监控机制可以向订阅了该事件的客户端发送相应的通知。本文从会话的应用层使用，到 ZooKeeper 底层的实现原理，梳理会话的相关知识。

## 会话的创建

ZooKeeper 的工作方式一般是通过客户端向服务端发送请求实现的。在一个请求的发送过程中，客户端首先要与服务端进行连接，而一个连接就是一个会话。

在 ZooKeeper 中，一个会话可以看作是一个用于表示客户端与服务器端连接的数据结构 Session。这个数据结构由三个部分组成：会话 ID（sessionID）、会话超时时间（TimeOut）、会话关闭状态（isClosing），如下图所示。

![](/zookeeper-images/09-创建会话_避开日常开发的那些_坑___CgqCHl7XUbeAH4RvAABLmAD-zt0526.png)

三个部分的含义分别如下：

- 会话 ID：会话 ID 作为一个会话的标识符，创建一次会话的时候，ZooKeeper 会自动为其分配一个唯一的 ID 编码。

- 会话超时时间：会话超时时间指一次会话从发起后到被服务器关闭的时长。设置会话超时时间后，服务器会参考设置的超时时间，最终计算一个服务端自己的超时时间，而这个超时时间才是最终真正用于 ZooKeeper 服务端会话管理的超时时间。

- 会话关闭状态：isClosing 状态属性字段表示一个会话是否已经关闭。如果服务器检查到一个会话已经因为超时等原因失效，ZooKeeper 会将该会话的 isClosing 属性值标记为关闭，再之后就不对该会话进行操作了。

## 会话状态

从系统运行的角度分析，一次会话从创建到关闭的生命周期中会经历不同的阶段。

![](/zookeeper-images/09-创建会话_避开日常开发的那些_坑___CgqCHl7XUcSAAoGmAAO6qmEJCC4477.png)

上图来自 ZooKeeper 官网，详细完整地描述了一次会话的完整生命周期。在 ZooKeeper 服务的运行过程中，会话会经历不同的状态变化，这些状态包括：正在连接（CONNECTING）、已经连接（CONNECTED）、会话关闭（CLOSED）等。

当客户端开始创建一个与服务端的会话操作时，它的会话状态就会变成 CONNECTING，之后客户端会根据服务器地址列表中的服务器 IP 地址分别尝试进行连接。如果遇到一个 IP 地址可以连接到服务器，那么客户端会话状态将变为 CONNECTED。

而如果因为网络原因造成已经连接的客户端会话断开，客户端会重新尝试连接服务端，对应的客户端会话状态又变成 CONNECTING，直到该会话连接到服务端最终又变成 CONNECTED。

在 ZooKeeper 服务的整个运行过程中，会话状态经常在 CONNECTING 与 CONNECTED 之间进行切换。最后，当出现超时或者客户端主动退出程序等情况时，客户端会话状态则会变为 CLOSED 状态。

## 会话底层实现

一个会话可以看作是由多种不同的属性字段组成的一种数据结构，在整个 ZooKeeper 服务的运行过程中，会话管理的本质就是围绕这个数据结构进行操作。

ZooKeeper 中会话底层实现的核心类是 SessionTracker，用来实现会话管理和维护等相关操作，可以说在 ZooKeeper 会话的整个生命周期中都离不开 SessionTracker 类的参与。

SessionTracker 是一个接口类型，规定了 ZooKeeper 中会话管理的相关操作行为，具体的实现方式则通过 SessionTrackerImpl 类来完成。

```java
class SessionTrackerImpl implements SessionTracker{
 ConcurrentHashMap<Long, SessionImpl> sessionsById;
 ConcurrentMap<Long, Integer> sessionsWithTimeout;
}

```

如上面的代码所示，SessionTrackerImpl 类实现了 SessionTracker 接口，其中有两个属性字段：

- sessionsById，用于根据会话 ID 来管理具体的会话实体。

- sessionsWithTimeout，根据不同的会话 ID 管理每个会话的超时时间。

SessionTrackerImpl 类初始化的时候，首先会调用 initializeNextSession 方法来生成一个会话 ID，该会话 ID 会作为一个唯一的标识符，在 ZooKeeper 服务之后的运行中用来标记一个特定的会话。

```java
public static long initializeNextSession(long id) {
    long nextSid;
    nextSid = (Time.currentElapsedTime() << 24) >>> 8;
    nextSid =  nextSid | (id << 56);
    return nextSid;
 }

```

生成会话 ID 的过程：首先以毫秒为单位获取系统的当前时间，之后将该值通过位运算方式向左移动 24 位，再向右移动 8 位，最后根据服务器的 SID 进行或运算，得到的最终结果就作为该会话的 ID 编码。

有了会话 ID 和超时时间等信息后，一个会话相关的所有数据就基本具备，也就完成了一个会话的创建工作，接下来就是服务器接收到会话请求后的处理等操作。

## 会话超时的常见"坑"

日常开发中最常遇到和处理的场景是会话超时异常。在 ZooKeeper 中，会话的超时异常包括客户端 readtimeout 异常和服务器端 sessionTimeout 异常，两者的不同之处在于一个发生在客户端，另一个发生在服务端。

对 ZooKeeper 接触不深的开发人员常踩的坑是：虽然设置了超时时间，但在实际服务运行时 ZooKeeper 并没有按照设置的超时时间来管理会话。

::: warning 超时时间由协商决定
ZooKeeper 实际起作用的超时时间是通过客户端和服务端协商决定的。客户端和服务端建立连接的时候，会提交一个客户端设置的会话超时时间，该超时时间会和服务端设置的最大超时时间和最小超时时间进行比对：如果正好在其允许的范围内，则采用客户端的超时时间管理会话；如果大于或者小于服务端设置的超时时间，则采用服务端设置的值管理会话。
:::

## 小结

本文从服务的运行角度分析了一次客户端会话从创建到关闭的整个过程：会话在生命周期中会经历正在连接（CONNECTING）、已经连接（CONNECTED）、关闭（CLOSED）等不同状态的变化；底层由 SessionTracker 接口及 SessionTrackerImpl 实现类承担会话管理。掌握会话的底层实现原理，有助于在会话创建等问题出现时快速排查。

关于会话 ID 生成算法需要补充一点：该算法实现看起来比较复杂，但其实并不完美，最主要的问题在于算法的基础是通过 Java 语言获取系统的当前时间作为基本参数，某些情况下在位运算的过程中会产生负数等问题。这个问题在 3.4.6 版本后得到了解决；在维护旧有系统时需要考虑这个问题。

# 一探究竟：从架构的演变看微服务化架构

## 概念：什么是微服务架构

微服务名词出现的历史并不久远。2011 年 5 月，威尼斯附近的一个软件架构师研讨会上，微服务的概念第一次被提起，但当时并没有给出明确的定义。随着技术的发展，2014 年 3 月，詹姆斯·刘易斯（James Lewis）和马丁·福勒（Martin Fowler）在博客中发表了一篇关于微服务特点的文章，对微服务概念的定义进行了明确。

> 所谓微服务架构风格是一种将单体应用开发为一组小型服务的方法，每个小服务运行在自己的进程中，并以轻量级的机制来进行通信。这些服务围绕着业务能力所建立，并且由完全自动化的部署机制独立部署，这些服务的集中管理只有最低限度，可以用不同的编程语言编写并使用不同的数据库存储技术。

以上是关于微服务的定义。任何架构都不是一蹴而就的，每一种架构都是为了解决以往业务产生的痛点而设计的，理解微服务架构需要从传统分布式架构的问题入手。

## 传统垂直划分的分布式应用存在的问题

在早期构建分布式应用时，多系统间协作是一件比较困难的事情。以一个普惠金融借款业务为例：该业务按照业务职能主要包含 4 部分，分别是**借款人门户网站**、**信审风控系统**、**贷后系统**以及**催收系统**。

具体的业务流程是：

1. 借款人门户负责收集借款人的需求；

2. 将借款人的信息送入信审和风控系统，风控进行评估；

3. 如果满足借款要求，则将这些信息发给贷后系统来进行实际的放款操作；

4. 最后在实际的分期还款过程中，通知借款人定期还款。

这个业务流程被拆解成 4 个子系统，每个子系统有独立的团队维护。因为没有统一的标准，便衍生出一系列后续问题。

**问题一，系统间通信困难。** 假如信审系统需要向贷后系统发送一个调用请求，通过 WebService 来实现，在 WebService 跨进程调用时，需要双方持有相同的传输对象才可以完成数据的交互。但如果服务提供者将接口以及传输对象进行升级后，而客户端没有及时更新，便会因为对象的状态不一致导致传输失败。在互联网机构，接口的升级与扩展可能频繁发生，这类问题一再出现，必然会影响系统的稳定性和团队的协作。

**问题二，系统的内部复杂度对外暴露。** 假如信审系统目前需要访问贷后系统，贷后系统为了高可用的要求，提供了 IP 为 10 和 11 的两个节点，作为信审系统客户端持有了这两个静态的 IP 地址。随着业务的发展，贷后系统的负载越来越大，此时贷后系统集群加入了额外的两个节点 12 和 13。由于原始设计没有动态扩展的机制，只能手动配置信审系统的 IP 列表，并重启应用才可以做到。这就相当于信审系统必须了解贷后系统每一台服务器的实际运行情况，增加了两个系统之间的耦合，提高了项目维护的难度。

**问题三，系统间的调用关系复杂。** 假设有 6 个不同的应用，如果没有提前规划，软件工程师想梳理清系统间的调用关系会非常困难，急需一种技术帮助梳理清系统间的调用关系。

**问题四，过度的重复建设。** 公司进行项目开发时，因为每一个团队负责独立的系统，而这些系统往往需要一些通用的底层设施，例如用户认证与权限控制、黑名单白名单、流量控制与系统异常的处理以及系统参数的配置管理等模块。这些模块在每一个子系统中都要重复开发，费时费力，也不利于数据的集中管理。

**问题五，"大一统"的架构设计。** 所谓大一统架构设计，是指很多公司希望采用一套统一的架构来适应公司各个不同职能的子系统。比如，之前所有的系统将数据统一存放在性能强大的 Oracle 数据库集群中。但这里有一个弊端：借款人门户系统需要对用户开放大量的全文检索，而 Oracle 这种关系型数据库并不擅长全文检索功能，实际应交给 Elasticsearch 全文检索引擎进行处理。

对于借款人门户网站的需求，需要额外引入 Elasticsearch 集群。因为新的集群是借款人门户网站专用的，理应由借款人门户的团队独立管理与维护。此时，Elasticsearch 对于其他的子系统没有意义，但因为大一统的架构设计约束，其他系统也必须要支持 Elasticsearch，这显然是不合理的。

以上的五点弊端，只是传统分布式架构问题的一个缩影。

## 微服务架构如何解决这些问题

微服务的特点有三个：

- 构建基于业务、可重用、职责明确的小型服务；

- 统一的通信标准，轻量级的通信协议，通常这里的通信协议指 RESTful；

- 可独立运行，独立存储，由独立团队进行维护。

引入微服务架构后，将原有的各个子系统中的核心服务进行抽象形成服务层，服务层按照是否与业务相关，分为业务服务层和基础服务层。

业务服务层是原有各个子系统中抽象出来的可以被充分重用的服务模块：原有借款人门户中普惠金融的业务逻辑可以剥离为普惠金融服务，并由专门的团队维护；作为服务，它拥有独立的 Oracle 数据库进行存储。相类似的贷后、催收也都有相应的服务支撑，拥有独立的团队以及独立的数据存储。

基础服务层则抽象出与业务无关的底层基础设施，例如数据同步服务、配置中心服务、全文检索服务，都是面向所有服务对外暴露的。

对应前述五类问题，微服务架构的解决方式分别如下。

**解决通信困难：统一而轻量的进程间通信标准。** 以信审与贷后系统的通信为例，之前采用 WebService 要求客户端和服务端必须持有相同的通信对象；改为 RESTful 通信后，RESTful 基于 HTTP 协议，是轻量级通信方式，并不强制要求客户端持有通信对象，可以使用 Java 中的 HttpClient 或者 OkHttp 组件发起标准的 HTTP 请求完成通信，返回的数据也是标准的 JSON 结构。在实际使用时，如果单纯由服务端进行了响应数据的扩展，后续通信并不强制要求调用端对代码进行升级，服务端与调用端彼此兼容。

**解决复杂度暴露：注册中心屏蔽内部细节。** 假设贷后服务额外增加了两个节点，微服务架构通过注册中心这一关键组件处理，具体执行顺序：

1. 信审服务和贷后服务在启动时，将服务可用的节点的 IP 以及相应状态在注册中心中进行登记。

2. 信审服务向贷后服务发起调用之前，首先从注册中心中获取贷后服务可用的 IP 列表。

3. 信审服务根据某种负载均衡规则，向具体的节点发起 HTTP 请求来完成业务的处理。

因为所有的 IP 地址以及节点的状态都由注册中心维护，信审服务作为使用者不需要了解贷后服务具体有哪些节点，有效降低了分布式应用之间的耦合，提高了程序的可维护性。

**解决调用关系复杂：内建链路跟踪体系。** 在传统的分布式应用中，梳理服务间的调用关系非常烦琐。微服务标准中提供了链路跟踪的技术实现：以 A、B、C 三个服务为例，三者之间的调用顺序以及调用时长一目了然，通过可视化的形式可以直观了解服务间的通信过程以及通信状态。

**解决重复建设：基础能力集中化。** 以用户认证为例，不同系统用户认证的过程都是类似的，将其抽象出一个通用的用户认证中心服务，在前端应用实际发起请求前对用户的身份和权限进行判断。这样做不但可以减少每一个子系统的重复建设，还可以将用户信息进行集中统一存储。

**实现更有弹性的架构设计。** 假如借款人门户需要全文检索的支持，那么与之对应的普惠金融服务中便可以为其专门增加 Elasticsearch，对某一个服务加入新的特性，并不影响其他服务的运行。之后随着业务的不断演化，其他服务假如也需要 Elasticsearch 全文检索，便可以进一步抽象，剥离出"全文检索服务"基础服务，为其他服务提供支撑。因为微服务架构采用统一的标准开发，升级改造工作的难度比较小。

## 小结

微服务架构是目前构建互联网应用的主流解决方案。本文总结了微服务的三大特点：

- 基于业务、可重用的、职责明确的小型服务。

- 统一的通信标准，轻量级的通信协议。

- 可独立运行，独立存储由独立团队进行维护。

与此同时，通过普惠金融借款业务的案例，分析了微服务架构对传统分布式应用五类弊端的解决方式。需要指出的是，《人月神话》一书中反复提到"世界上没有银弹"，任何架构都有自己的缺点，引入微服务架构后同样会产生新的问题，架构选型需要结合业务实际情况权衡。

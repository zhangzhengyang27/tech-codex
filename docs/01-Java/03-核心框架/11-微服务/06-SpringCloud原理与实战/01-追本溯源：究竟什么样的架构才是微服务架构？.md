# 追本溯源：究竟什么样的架构才是微服务架构？

## 概念说明

微服务架构是一种**架构模式**，区别于其他系统架构的构建方式和技术方案，具有其固有特点。微服务架构的提出者 Martin Fowler 在其文章 *Microservices* 中定义了包括服务组件化、去中心化、基础设施自动化在内的多个微服务架构特点。这些特点为使用微服务架构进行系统设计提供了主要切入点。基于这些特点，可以提炼出构建微服务架构的三大要素：**业务建模**、**技术体系**和**研发过程**。

## 微服务架构的第一要素：业务建模

微服务架构设计首要的切入点是服务建模。原因在于微服务架构与传统 SOA 等技术体系有本质区别——服务的粒度以及服务本身的面向业务和组件化特性。针对服务建模，首先需要明确服务的类别以及服务与业务之间的关系，尽可能明确领域的边界。

开展服务建模工作推荐使用领域驱动设计（Domain Driven Design，DDD）方法：通过识别领域中的各个子域、判断这些子域是否独立、考虑子域与子域的交互关系，从而明确各个限界上下文（Bounded Context）之间的边界。

对于领域的划分，业界主流的分类方法认为，系统中的各个子域可以分成三种类型：

- **核心子域**：系统中的核心业务所属的子域。
- **支撑子域**：专注于业务某一方面的子域。
- **通用子域**：可以作为某种基础设施的功能归入的子域。

以一个典型的电商系统为例，其领域划分通常符合这一分类。

另一方面，服务建模本质上是一个为了满足业务需求、并通过技术手段将这些业务需求转换为可实现服务的过程。服务围绕业务能力建模，而业务能力往往体现为一种**分层结构**。按照实践经验，业务体系中的服务通常可以分为**基础服务、通用服务、定制服务**和**其他服务**等几种类型；同样以电商场景为例，业务服务即按这些层次组织。

每个行业、每个公司具有不同的业务体系和产品形态，业务建模的应用场景不必逐一展开。但基于 DDD 设计思想，通过具体案例完成系统业务建模的系统方法，是掌握微服务架构设计的重要途径。

## 微服务架构的第二要素：技术体系

微服务架构的第二大要素是技术体系，这也是学习微服务架构的主体内容。不同的开发技术和框架都会基于自身的设计理念给出各自的技术体系类型及实现方式。微服务架构相关的技术体系比较繁杂，通常可以归纳为以下八大技术体系。

### 1. 服务通信

网络通信是任何分布式系统的基础组件。对微服务架构而言，关注点集中在**网络连接模式**、**I/O 模型**和**服务调用方式**三个方面。

基于 TCP 协议的网络连接有两种基本方式，即**长连接**和**短连接**。长连接和短连接的产生在于客户端和服务器端采取的关闭策略，具体的应用场景采用具体的策略。例如 Dubbo 框架采用长连接，而 Spring Cloud 采用短连接；两者的适用场景可进一步查阅相关资料。

I/O 模型有**阻塞式 I/O 和非阻塞式 I/O** 等多种实现方式。阻塞式 I/O 实现简单，非阻塞式 I/O 性能更好。以服务网关为例，Netflix 的 Zuul 是阻塞式 I/O，而 Spring 自研的 Spring Cloud Gateway 采用非阻塞式 I/O。

调用方式存在同步调用和异步调用两大类实现机制，这两大类机制对开发人员使用开发框架的方式有很大影响。为了简化开发人员的使用过程，框架通常采用**异步转同步**的实现机制：开发人员使用同步方式进行方法调用，而框架本身基于 Future 等机制实现异步的远程处理。

### 2. 服务治理

服务治理是微服务架构中最为关键的技术组件，因为各个微服务需要通过服务治理实现自动化的注册和发现。

服务数量不多时，获取服务的 IP 地址、端口等信息有很多办法，管理也不复杂；但当服务数量达到一定量级时，可能连开发人员自己都不知道系统中到底存在多少个服务，也不知道哪些服务已经变得不可用。这时就需要引入独立的媒介来管理服务的实例，这个媒介一般被称为服务注册中心。

服务注册中心是保存服务调用所需路由信息的存储仓库，也是服务提供者和服务消费者进行交互的媒介，充当服务注册和发现服务器的角色。Dubbo、Spring Cloud 等主流的微服务框架都基于 Zookeeper、Eureka 等分布式系统协调工具构建了服务注册中心。

### 3. 服务路由

通过注册中心构建多服务的集群化环境后，客户端请求到达集群时，需要确定由哪一台服务器进行请求响应，这就是服务路由问题。负载均衡是最常见的一种路由方案，常见的客户端/服务器端负载均衡技术都可以完成服务路由，Spring Cloud 等主流微服务框架也都内置了 Ribbon 等客户端负载均衡组件。

另一方面，负载均衡的出发点更多是提供服务分发而不是解决路由问题，常见的静态、动态负载均衡算法无法实现精细化的路由管理。这时可以采用路由规则。路由规则常见的实现方案是白名单或黑名单，即把需要路由的服务地址信息（如服务 IP）放入可以控制是否可见的路由池中进行路由。路由规则同样是微服务开发框架的一项常见功能。

### 4. 服务容错

分布式环境中的服务在自身失败引发错误的同时，还会因为依赖其他服务而导致失败。除了比较容易想到和实现的超时、重试和异步解耦等手段之外，还需要针对各种场景设计容错机制。

业界存在一批与服务容错相关的技术组件：以失效转移 Failover 为代表的集群容错策略，以线程隔离、进程隔离为代表的服务隔离机制，以滑动窗口、令牌桶算法为代表的服务限流机制，以及服务熔断机制。从技术实现方式上看，Spring Cloud 中这些机制部分包含在服务网关中，另一部分则被提炼成单独的开发框架，例如专门用于实现服务熔断的 Spring Cloud Circuit Breaker 组件。

### 5. 服务网关

服务网关也叫 API 网关，封装了系统内部架构，为每个客户端提供一个定制的 API。在微服务架构中，服务网关的核心要点是：所有的客户端和消费端都通过统一的网关接入微服务，在网关层处理所有的非业务功能。

在功能设计上，服务网关在完成客户端与服务器端报文格式转换的同时，通常还具有身份验证、监控、缓存、请求管理、静态响应处理等功能；也可以在网关层制定灵活的路由策略，针对特定的 API 设置白名单、路由规则等各类限制。Netflix Zuul 和 Spring Cloud Gateway 是两种典型的网关实现。

### 6. 服务配置

考虑到服务数量和配置信息的分散性，微服务架构一般都需要引入配置中心的设计思想和相关工具。与注册中心一样，配置中心也是微服务架构中的基础组件，其目的同样是对服务进行统一管理，区别在于配置中心管理的对象是配置信息而不是服务的实例信息。

配置中心通常需要依赖分布式协调机制，即通过一定的方法确保配置信息在分布式环境中的各个服务中得到实时、一致的管理。可以采用 Zookeeper 等主流的开源分布式协调框架来构建配置中心；Spring Cloud 也提供了专门的配置中心实现工具 Spring Cloud Config。

### 7. 服务安全

服务安全是微服务架构中非常重要但又容易被忽视的内容。一般意义上的访问安全性围绕认证和授权两个核心概念展开：首先确定用户身份，然后确定该用户是否有访问指定资源的权限。站在单个微服务的角度，每次服务访问都应与授权服务器集成以获取访问 Token；站在多个服务交互的角度，需要确保 Token 在各个微服务之间的有效传播；在服务内部，可以使用不同的访问策略限制服务资源的访问。

实现微服务安全访问的通常方案是：使用 OAuth2 协议实现对服务访问的授权机制，使用 JWT 技术构建轻量级的认证体系。Spring 家族提供了 Spring Security 和 Spring Cloud Security 框架来完成这些组件的构建。

### 8. 服务监控

当服务数量达到一定量级时，微服务架构会面临两个核心问题：如何管理服务之间的调用关系？如何跟踪业务流的处理过程和结果？这就需要构建分布式服务跟踪机制。

分布式服务跟踪机制的建立需要完成调用链数据的生成、采集、存储及查询，同时需要对这些调用链数据进行运算和可视化管理。这些工作不是单一工具或框架能全部完成的，因此开发微服务系统时通常会整合多个开发框架进行链路跟踪。例如 Spring Cloud 提供了 Spring Cloud Sleuth 与 Zipkin 的集成方案。

## 微服务架构的第三要素：研发过程

微服务架构的第三个要素是研发过程。过程转变与技术体系建设密切相关。Martin Fowler 在介绍微服务架构时，同样提出了围绕"业务功能"组织团队的研发管理理念。

传统的研发过程通常围绕产品团队、项目管理、大前端和服务器端团队展开，这些团队即通常所说的职能团队。任何一个需求，无论大小，都将导致跨团队协作，从而增加沟通和协作成本。而微服务架构则倾向围绕业务功能的组织来分割服务，而不是面向某项技术能力：团队是跨职能的特征团队，每个服务都围绕业务进行构建，并且能够被独立部署到生产环境。

## 小结

微服务架构是目前构建互联网系统的主流架构体系，需要从业务建模、技术体系和研发过程三个维度入手理解和掌握：

- **业务建模**：以 DDD 为方法论，通过核心子域、支撑子域、通用子域的划分明确限界上下文边界，服务按基础服务、通用服务、定制服务等分层组织。
- **技术体系**：包含服务通信（连接模式、I/O 模型、调用方式）、服务治理（注册中心）、服务路由（负载均衡与路由规则）、服务容错（Failover、隔离、限流、熔断）、服务网关（API 统一入口与非业务功能）、服务配置（配置中心）、服务安全（OAuth2 + JWT）、服务监控（分布式链路跟踪）八大体系。
- **研发过程**：围绕"业务功能"组建跨职能特征团队，服务独立构建与部署。

理解各个技术体系的作用与相互关系，是后续掌握 Spring Cloud 各组件设计原理的基础。

| 组件 | 旧版（本文编写时） | 当前（Spring Cloud 2025.x / Boot 3.5.x） |
|------|-------------------|------------------------------------------|
| 服务注册 | Eureka 1.x（Eureka 2.x 已终止开发） | Nacos 2.x / Consul（Eureka 1.x 仍随 Spring Cloud Netflix 维护） |
| 负载均衡 | Ribbon（已停止维护） | Spring Cloud LoadBalancer |
| 网关 | Zuul 1.x（已停止维护） | Spring Cloud Gateway（基于 WebFlux） |
| 熔断 | Hystrix（已停止维护） | Resilience4j / Sentinel |
| 配置中心 | Spring Cloud Config | Nacos Config / Apollo |
| 版本对应 | Hoxton/2020.x + Boot 2.x + JDK 8 | 2025.x + Boot 3.5.x + JDK 17+ |

> 本文基于 Spring Cloud 旧版（Hoxton/2020.x 时代）编写。Hystrix、Ribbon、Zuul 1.x、Eureka 已停止维护，新项目请使用 Spring Cloud Gateway + LoadBalancer + Resilience4j（或 Alibaba 系 Nacos/Sentinel/Seata），并升级到 Spring Cloud 2025.x + Spring Boot 3.5.x。

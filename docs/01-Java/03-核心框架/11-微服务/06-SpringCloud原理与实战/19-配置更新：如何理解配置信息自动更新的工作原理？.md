# 配置更新：如何理解配置信息自动更新的工作原理？

## 概述

在理解了 Spring Cloud Config 客户端与服务器端的交互流程之后，还剩下一个核心问题：一旦服务器端的配置信息发生变化，客户端如何进行及时更新？

Zookeeper 实现分布式配置中心的方法是在客户端与 Zookeeper 之间建立长连接，然后合理利用 Zookeeper 的临时节点和监听器机制。而 Spring Cloud Config 客户端与服务器端采用的是基于 HTTP 协议的 RESTful API，本质上是一种短连接技术，无法通过类似监听器的方案实现配置信息的自动获取和更新。同时，Spring Cloud Config 也没有采用像 Eureka 中纯粹轮询的方式获取增量数据，而是提供了一套完全不同的解决方案。这套方案在设计和实现方法上具有借鉴价值，下文结合源码深入分析。

## Spring Cloud Config 客户端更新策略

Spring Cloud Config 客户端在启动时，会发送 HTTP 请求到服务器端获取配置信息。而在 Git 等配置仓库中更改了配置信息之后，客户端不会主动再次请求最新配置，而是使用缓存到本地的原有配置信息。实现配置的实时更新有如下三种处理方法：

- **重启客户端。**

客户端在启动时会重新获取服务器端配置，因此重启客户端能实现配置信息的及时更新，但显然这不是一种合理的方法。

- **使用 Spring Boot Actuator。**

Spring Boot 提供了一个专门的组件用来监测和管理系统运行时状态，这个组件就是 Spring Boot Actuator。Actuator 是一种集成化组件，可以获取应用系统的运行时数据和配置信息，并进行统计分析。

当在代码类路径中引入 spring-boot-starter-actuator 依赖并启动 Spring Boot 应用程序时，启动日志里会出现自动添加的 autoconfig、dump、beans、actuator、health、refresh 等众多 HTTP 端点。通过调用 /actuator/refresh 端点就可以刷新客户端的配置信息，从而实现不重启 Spring Boot 应用的配置热更新。从实现原理上，这个操作实际上使用了一个 ContextRefresher 工具类来完成刷新操作，如下所示：

```java
@Endpoint(id = "refresh")
public class RefreshEndpoint {

private ContextRefresher contextRefresher;

public RefreshEndpoint(ContextRefresher contextRefresher) {
        this.contextRefresher = contextRefresher;
    }

    @WriteOperation
    public Collection<String> refresh() {
        Set<String> keys = contextRefresher.refresh();
        return keys;
    }
}
```

这是一种简单有效的处理方式，但不是最好的处理方式：针对每个微服务一般都会存在多个运行时实例，这样就需要把客户端的 /actuator/refresh 端点逐个进行调用，显然不合理。而且，这种方案属于客户端自身行为，与配置服务端没有关系。

- **集成 Spring Cloud Bus。**

Spring Cloud Config 提供的是第三种方法，即集成 Spring Cloud Bus 组件。Spring Cloud Bus 是 Spring Cloud 中用于实现消息总线的专用组件，集成了 RabbitMQ、Kafka 等主流消息中间件。消息通信本身的机制在消息主题中详细阐述，这里只需要知道 Spring Cloud Config 集成 Spring Cloud Bus 的目的是借助它的消息通信能力。

当在 Spring Cloud Config 服务器端工程的类路径中添加 Spring Cloud Bus 的引用并启动应用程序之后，Spring Boot Actuator 就会提供 /actuator/bus-refresh 端点，通过访问该端点就可以达到对客户端所有服务实例的配置进行自动更新的效果。在这种方案中，服务端会主动通知所有客户端进行配置信息的更新：不需要关注各个客户端，只对服务端进行操作即可。

理解整个过程需要搞清楚三大问题：一是 Git 等配置仓库的变更如何自动触发服务器端的 bus-refresh 端点；二是客户端如何得知服务器端的配置信息已经更新；三是客户端如何实时获取更新后的配置内容。以下结合源码逐一展开。

## 问题一：如何自动调用服务器端所暴露的 /actuator/bus-refresh 端点？

在现代软件开发过程中，开放式平台是一种常见的软件服务形态。可以把 Spring Cloud Config Server 所提供的 HTTP 端点视为一种开放式的接口，以供 Git 等第三方工具进行访问和集成。

如前所述，服务器端将 /actuator/bus-refresh 端点对外进行暴露后，第三方工具可以通过这个暴露的端点进行集成。

GitHub 的 Webhook 配置界面（来自 GitHub 官网）

在 Webhook 的 Payload URL 中可以设置 /actuator/bus-refresh 端点地址。所谓的 Webhook，实际上就是一种回调。通过 Webhook，提交代码时 Git 就会自动调用所配置的 HTTP 端点。也就是说，可以根据配置项信息的更新情况自动实现对 /actuator/bus-refresh 端点的访问。基于 GitHub 的配置仓库实现方案，配置变更就能通过 Webhook 自动传导到配置服务器。

现在，配置信息一旦有更新，Spring Cloud Config Server 就能从 Github 中获取最新的配置信息。接下来关注第二个问题，即客户端如何得知服务器端的配置信息已经更新。

## 问题二：客户端如何得知服务器端的配置信息已经更新？

首先需要明确调用 /actuator/bus-refresh 端点之后，系统内部会发生什么。浏览 Spring Cloud Bus 的代码工程可以发现，在 org.springframework.cloud.bus.endpoint 包下存在一个 RefreshBusEndpoint 端点类，如下所示：

```java
@Endpoint(id = "bus-refresh")
public class RefreshBusEndpoint extends AbstractBusEndpoint {

public RefreshBusEndpoint(ApplicationEventPublisher context, String id) {
        super(context, id);
    }

@WriteOperation
    public void busRefreshWithDestination(@Selector String destination) {
        publish(new RefreshRemoteApplicationEvent(this, getInstanceId(), destination));
    }

    @WriteOperation
    public void busRefresh() {
        publish(new RefreshRemoteApplicationEvent(this, getInstanceId(), null));
    }
}
```

RefreshBusEndpoint 类对应于前面访问的 /bus-refresh 端点。可以看到，Spring Cloud Bus 在这里做的事情仅仅只是发布了一个新的 RefreshRemoteApplicationEvent 事件。

发送了事件就需要寻找该事件的监听者。在 Spring Cloud Bus 的 org.springframework.cloud.bus.event 包下存在 RefreshRemoteApplicationEvent 事件的监听者 RefreshListener，如下所示：

```java
public class RefreshListener
        implements ApplicationListener<RefreshRemoteApplicationEvent> {

private static Log log = LogFactory.getLog(RefreshListener.class);

private ContextRefresher contextRefresher;

public RefreshListener(ContextRefresher contextRefresher) {
        this.contextRefresher = contextRefresher;
    }

    @Override
    public void onApplicationEvent(RefreshRemoteApplicationEvent event) {
        Set<String> keys = contextRefresher.refresh();
        log.info("Received remote refresh request. Keys refreshed " + keys);
    }
}
```

从类的定义中可以看到，该监听器用来处理 RefreshRemoteApplicationEvent 事件，其中在 onApplicationEvent 函数中同样调用了前面介绍的 ContextRefresher 中的 refresh() 方法进行配置属性的刷新。

需要注意的是，RefreshRemoteApplicationEvent 是一个远程事件，将通过消息中间件进行发送，并被 Spring Cloud Config 客户端所监听。

最后一个问题——客户端如何获取服务器端所更新的配置信息——需要梳理 Spring Cloud Config Server 与注册中心 Eureka 之间的关系。

## 问题三：客户端如何实时获取服务器端所更新的配置信息？

配置中心作为整个微服务架构运行所需的基础服务，需要确保其可用性。Spring Cloud Config 实现高可用的方式很简单：配置服务本身也是一个独立的微服务，与其他微服务一样，也可以注册到 Eureka 服务器上，让其他服务提供者或消费者通过注册中心进行服务发现和获取。

在这种方式下，基于 Eureka 的服务治理机制同时提供了服务器端的负载均衡和客户端的配置功能，从而间接实现了高可用性。从另一个角度理解：通过 Eureka 可以获取所有 Spring Cloud Config 服务的实例，从而在分布式环境下为获取配置信息提供了一种简便的手段。

Spring Cloud Config 提供一个工具类 ConfigServerInstanceProvider 来完成与 Eureka 之间的交互，如下所示：

```java
public class ConfigServerInstanceProvider {

private static Log logger = LogFactory.getLog(ConfigServerInstanceProvider.class);
    private final DiscoveryClient client;

public ConfigServerInstanceProvider(DiscoveryClient client) {
        this.client = client;
    }

    @Retryable(interceptor = "configServerRetryInterceptor")
    public List<ServiceInstance> getConfigServerInstances(String serviceId) {
        logger.debug("Locating configserver (" + serviceId + ") via discovery");
        List<ServiceInstance> instances = this.client.getInstances(serviceId);
        if (instances.isEmpty()) {
            throw new IllegalStateException(
                    "No instances found of configserver (" + serviceId + ")");
        }
        logger.debug("Located configserver (" + serviceId
                + ") via discovery. No of instances found: " + instances.size());
        return instances;
    }
}
```

这里出现了熟悉的 DiscoveryClient，它通过同样熟悉的 getInstances() 方法从 Eureka 中获取 Spring Cloud Config 服务器实例：

```java
List<ServiceInstance> instances = this.client.getInstances(serviceId);
```

ConfigServerInstanceProvider 的调用者是 DiscoveryClientConfigServiceBootstrapConfiguration。如果系统中生成了 ContextRefreshedEvent 事件就会触发 startup() 方法，而该方法则直接调用了如下所示的 refresh() 方法（部分代码做了裁剪）：

```java
private void refresh() {
        try {
            String serviceId = this.config.getDiscovery().getServiceId();
            List<String> listOfUrls = new ArrayList<>();
            List<ServiceInstance> serviceInstances = this.instanceProvider
                    .getConfigServerInstances(serviceId);

for (int i = 0; i < serviceInstances.size(); i++) {

ServiceInstance server = serviceInstances.get(i);
                String url = getHomePage(server);

if (server.getMetadata().containsKey("password")) {
                    String user = server.getMetadata().get("user");
                    user = user == null ? "user" : user;
                    this.config.setUsername(user);
                    String password = server.getMetadata().get("password");
                    this.config.setPassword(password);
                }

if (server.getMetadata().containsKey("configPath")) {
                    String path = server.getMetadata().get("configPath");
                    if (url.endsWith("/") && path.startsWith("/")) {
                        url = url.substring(0, url.length() - 1);
                    }
                    url = url + path;
                }

listOfUrls.add(url);
            }

String[] uri = new String[listOfUrls.size()];
            uri = listOfUrls.toArray(uri);
            this.config.setUri(uri);

        }
}
```

在上述 refresh() 方法中，系统首先会获取配置文件中配置项 spring.cloud.config.discovery.serviceId 所指定的服务实例 Id，然后根据 serviceId 从 ConfigServerInstanceProvider 中获取注册服务的实例对象集合 serviceInstances，最后循环遍历 serviceInstances 来更新存储在内存中的配置属性值。

这些属性值都保存在 ConfigClientProperties 对象中。在《配置服务：如何基于 Spring Cloud Config 构建配置中心服务器？》中介绍的 ConfigServicePropertySourceLocator 类中，通过分析 getRemoteEnvironment 方法可以发现，正是通过 ConfigClientProperties 对象中的这些属性值来对 Spring Cloud Config Server 进行远程调用。这样整个流程就串联起来了。

## 实践要点

- 配置更新的三种途径：重启客户端（最简单但不可取）、逐实例调用 /actuator/refresh（客户端自身行为，多实例场景不合理）、集成 Spring Cloud Bus（服务端统一触发，生产推荐）。
- /actuator/refresh 与 /actuator/bus-refresh 的底层实现都是 ContextRefresher.refresh()，后者通过 RefreshBusEndpoint 发布 RefreshRemoteApplicationEvent 远程事件。
- RefreshRemoteApplicationEvent 经消息中间件（RabbitMQ/Kafka）广播，各客户端的 RefreshListener 监听该事件并执行 ContextRefresher 刷新。
- Git 仓库侧通过 GitHub Webhook 回调机制自动触发 bus-refresh：在 Payload URL 中配置端点地址，提交代码即自动调用。
- Spring Cloud Config Server 注册到 Eureka 即可获得服务发现与负载均衡能力；客户端通过 ConfigServerInstanceProvider（内含 DiscoveryClient，带 @Retryable 重试）按 serviceId 拉取实例列表，并用实例元数据（user/password/configPath）动态更新 ConfigClientProperties。

## 小结

本文讲解基于 Spring Cloud Config 实现配置信息自动更新的工作原理：围绕三个核心问题——Git 仓库变更如何自动触发服务器端 bus-refresh 端点（Webhook 回调）、客户端如何得知配置已更新（Spring Cloud Bus 发布 RefreshRemoteApplicationEvent 远程事件并由 RefreshListener 监听）、客户端如何实时获取更新后的配置（ConfigServerInstanceProvider 从 Eureka 获取实例并更新 ConfigClientProperties）——基于源码一一解答。当配置服务器中的配置信息发生变更时，客户端保持同步更新的答案是：Webhook 触发 bus-refresh 端点，Spring Cloud Bus 借助消息中间件将刷新事件广播到所有客户端实例。Spring Cloud Config 作为 Spring 自研的配置中心框架，内部大量使用了 Spring 现有的功能特性（事件机制、DiscoveryClient、@Retryable 等），理解其设计与实现需要以 Spring 容器相关知识体系为基础。

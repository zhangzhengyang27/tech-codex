# 服务安全：如何理解微服务访问的安全需求和实现方案？

## 概念说明

微服务架构中的服务访问安全性相关的需求和实现方案是一个重要但又往往被忽略的主题，很多开发人员缺乏对微服务安全访问机制的认识。另一方面，微服务安全性又是一个非常综合的话题，涉及的技术体系也比较复杂。

## 原理与机制：微服务架构中的安全性设计

对于微服务架构而言，安全性设计的最核心考虑点是**认证（Authentication）**和**授权（Authorization）**。

### 认证与授权

在软件系统中，可以把需要访问的内容定义为一种资源（Resource），而安全性设计的核心目标就是对这些资源进行保护，确保对它们的访问是安全受控的。在微服务架构中，一个个的微服务就可以被理解为是资源。对于资源的安全性访问，业界存在一些常见的技术体系。在讲解这些技术体系之前，先理解在安全领域中非常常见但又容易混淆的两个概念：认证和授权。

首先需要明确，所谓认证，解决的是“**你是谁**”这一个问题，也就是说对于每一次访问请求，系统都能判断出访问者是否具有合法的身份标识。

一旦明确“你是谁”之后，下一步就可以判断“你能做什么”，这个步骤就是授权。通用的授权模型通常都是基于权限管理体系的，也就是说是对资源、权限、角色和用户的一种组合处理。

如果将认证和授权结合起来，就构成了对系统中资源进行安全性管理的最常见解决方案：先判断资源访问者的有效身份，然后再来确定其是否有对这个资源进行访问的合法权限。

这是一种通用方案，而不同的应用场景以及技术体系下可以衍生出很多具体的实现策略。微服务架构中的认证和授权模型与之类似，但在具体设计和实现过程中也有其特殊性。

### 微服务架构中的认证与授权

在微服务架构下，服务访问过程中需要考虑的安全性问题如下。因为一个微服务系统中服务之间可以存在相互的调用关系，对于每一个服务而言，一方面需要考虑来自客户端的请求，同时也要考虑可能来自另一个服务的请求。因此，面临着从客户端到服务、从服务到服务的多种认证和授权场景。

针对上述场景下的认证环节，比较容易想到的一种实现方案是**分布式 Session 机制**。Session 本质上是一种服务器端技术，即服务器对请求进行认证，并将已经通过的认证信息的用户信息存储在一个共享存储空间中。这样，每次对于微服务的请求都可以带着 Session ID，服务器根据共享存储空间中的数据检查用户是否认证过。这种方案显然需要消耗服务器端的存储空间，也容易受到攻击。

与服务器端保存认证信息相对应的，另一种思路是将认证信息存储在客户端。可以在客户端生成认证信息并保存在本地，然后在每次请求中，客户端将这个认证信息通过 HTTP 请求传递到服务器端，服务器端再基于这个认证信息执行用户身份验证。显然，这种机制是无状态的，而且有利于减轻服务端存储压力。在这种方案下，通常把认证信息称为一个 Token（令牌），业界也存在诸如 JWT（JSON Web Tokens）这样的实现方案，后文会具体讲到。

看完对认证信息的处理方式，再看微服务架构中的授权。对于某一个特定的微服务而言，面临的第一个问题是如何判断一个 HTTP 请求具备访问自己的权限。更进一步，就算这个请求具备访问该微服务的权限，但并不意味着它能够访问该服务中的所有功能：对于某些核心功能，需要具备较高的权限才能访问，而有些则不需要。这对应的效果即微服务授权效果示意——服务级权限与服务内功能级权限的分层控制。

举个例子，假设某个请求具备访问服务 A 的权限，但不具备访问服务 A 中功能 1 的权限。想要达到这种效果，一般的做法是引入角色体系：对不同的用户设置不同等级的角色，角色等级不同对应的访问权限也不同，而每一个请求都可以绑定到某一个角色，也就具备了访问权限。

接下来，把认证和授权结合起来，梳理出服务访问场景下的安全性实现方案。在这一方案中存在一个授权中心：授权中心首先会获取客户端请求中所带有的身份凭证信息，然后基于这个身份凭证信息生成一个 Token；客户端获取 Token 之后就可以基于这个 Token 发起对微服务的访问；这时候，需要对这个 Token 进行认证，并通过授权中心获取该请求所能访问的特定资源。在微服务系统中，对外的资源表现形式可以理解为就是一个个 HTTP 端点。

关于如何实现上述技术方案，业界也存在一些特定的工具和协议：针对授权，最具代表性的就是 OAuth2 协议；而针对认证，采用 JWT 是目前非常主流的做法。

## 授权：OAuth2 协议

OAuth 是 Open Authorization 的简称，该协议解决的是授权问题而不是认证问题，目前普遍被采用的是 OAuth 2.0 协议。OAuth2 是一个相对复杂的协议，对涉及的角色和授权模式给出了明确的定义，先来看这些基本概念。

OAuth2 协议中把需要访问的接口或服务统称为资源，而每个资源都有一个**拥有者（Resource Owner）**。这些资源拥有者所拥有的资源统一存放在资源服务器（Resource Server）中。同时，协议规定需要有一台授权服务器（Authorization Server），即专门用来处理对访问请求进行授权的服务器，也就是前述方案中的授权中心。

OAuth2 协议的作用就是让客户端程序安全可控地获取用户的授权信息，并与资源服务器进行交互。OAuth2 协议在客户端程序和资源服务器之间设置了一个**授权层**，所以客户端程序不能直接访问资源服务器，而是只能先登录授权层。资源拥有者会首先授权给客户端，客户端获得授权之后，向授权服务器申请一个 Token，Token 中就包含了权限范围和有效期。然后，客户端使用这个申请到的 Token 向资源服务器申请获取资源，资源服务器就根据 Token 的权限范围和有效期向客户端开放拥有者的资源。

对应到微服务系统中，服务提供者所充当的角色就是资源服务器，而服务消费者就是客户端。所以各个服务本身都可以是客户端，也可以作为资源服务器，或者两者兼之。当客户端拿到 Token 之后，该 Token 就能在各个服务之间进行传递，这构成了 OAuth2 协议在服务访问场景中的应用方式。

## 认证：JWT 机制

JWT 是一种表示数据的标准，所有人都可以遵循这种标准来传递数据。在安全领域，通常用它来传递被认证的用户身份信息，以便从资源服务器获取资源。同时，JWT 在结构上也提供了良好的扩展性，开发人员可以根据需求增加一些额外信息用于处理复杂的业务逻辑。需要注意，JWT 默认只是对数据做 Base64 编码与数字签名，并非加密，Payload 可以被任何人解码读取；如需保密，应避免在 Payload 中放置敏感信息，或使用 JWE 等加密方案。

JWT 具有很多优秀的功能特性：它的数据表示方式采用语言无关的 JSON 格式，可以与各个异构系统进行集成；基于 JWT 表示的 Token 简洁紧凑，也便于网络之间的高效传输；最重要的，JWT 中的 Token 不存储在服务端，所以提供了一种无状态性。

同时，也应该注意到，正因为 Token 不存储在服务端，所以要关注它的注销方式。区别于服务器端技术，当用户注销时，无法实时控制 Token 的失效时间。所以一般可以把这个失效时间设置为一个较小的值，从而降低 Token 可用性的风险。

本质上，JWT 和 OAuth2 面向不同的应用场景，本身并没有任何关联，但在很多情况下，在讨论 OAuth2 的实现时，会把 JWT 作为一种认证机制进行使用。

OAuth2 协议和 JWT 机制的实现体系比较复杂，综合应用摘要认证、签名认证、HTTPS 等安全性手段，同时需要开发者进行精细化的权限粒度控制。一般应避免自行实现如此复杂的协议，而是倾向于借助于特定工具以避免重复造轮子。幸好，Spring Cloud 提供了一个专门实现 OAuth2 协议以及整合 JWT 机制的框架，这就是 Spring Cloud Security。Spring Cloud Security 框架基于 Spring 家族中的 Spring Security 框架。本文将采用 Spring Cloud Security 来实现微服务架构下服务之间访问的安全性。

## 实践要点

- 安全性设计的两条主线：认证解决“你是谁”（身份合法性），授权解决“你能做什么”（资源、权限、角色、用户的组合管理），二者结合构成资源安全访问的通用方案。
- 微服务场景下存在客户端到服务、服务到服务两类认证授权链路，方案设计需同时覆盖。
- 认证信息处理两种思路的取舍：分布式 Session 有状态、消耗服务端存储且易受攻击；Token 方案无状态、减轻服务端压力，主流实现为 JWT。
- 服务内功能级权限控制通过角色体系实现：请求绑定角色，角色决定可访问的功能集合。
- OAuth2 三角色模型（资源拥有者/资源服务器/授权服务器）+ 授权层保证客户端不能直接访问资源；微服务中服务提供者即资源服务器，服务消费者即客户端，二者角色可互换。
- JWT 默认只编码不加密，Payload 可被任意解码；注销无法实时失效 Token，应设置较短有效期降低风险。
- 不建议自行实现 OAuth2/JWT 协议细节，推荐使用 Spring Cloud Security（基于 Spring Security）完成落地。

## 小结

微服务安全性领域中，认证和授权仍然是最基本的安全性控制手段。本文系统分析了微服务架构中的认证和授权解决方案：认证信息可由分布式 Session（服务器端）或 Token（客户端）承载，服务内权限通过角色体系精细化控制；在整体方案中引入授权中心签发 Token 并控制资源访问范围，并分别引入 OAuth2 协议（授权）与 JWT 机制（认证）落地这一方案，最终由 Spring Cloud Security 框架提供工程化支持。

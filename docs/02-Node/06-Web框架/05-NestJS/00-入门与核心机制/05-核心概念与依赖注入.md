# 核心概念与依赖注入

## 一、核心概念总览

Nest 是对标 Java 的 Spring 框架的后端框架，概念较多。本节集中梳理核心概念（以理解为主，无需实践）。

### Controller 与路由

后端接口通过不同的 url 访问，不同的 url 对应不同的路由：

```text
/user/create
/user/list
/book/create
/book/list
```

路由在 Controller 里声明：声明一个 `/user/create` 的 post 接口、一个 `/user/list` 的 get 接口，只要在 class 上和方法上分别加上 `@Controller`、`@Post`、`@Get` 的装饰器即可：

```typescript
@Controller('user')
export class UserController {
  @Post('create')
  create() {}

  @Get('list')
  list() {}
}
```

controller 的方法叫做 handler，是处理路由的。

### 请求参数与 DTO

post 的请求体、get 的请求参数都通过装饰器来取：

- `@Param` 取 url 中的参数，比如 `/user/111` 里的 `111`；
- `@Query` 取 url 中的 query 参数，比如 `/user/xx?id=222` 里的 `222`；
- `@Body` 取请求体内容（一般传递 json，如 `{ username: 'xxx', password: 'xxx' }`），会通过 dto（data transfer object）来接收，传递到 handler 的就已经是 dto 对象了。

也就是说，**controller 是处理路由和解析请求参数的**。

### Service 与 Module

请求参数解析出来后，下一步是业务逻辑处理。这部分不写在 controller 里，而是放在 service 里——**service 做业务逻辑的具体实现，比如操作数据库等**。`/book/list`、`/book/create` 接口在另一个 BookController 里，业务逻辑同样在 BookService 里实现。

UserController 和 UserService 是一块的，BookController 和 BookService 是一块的，因此 Nest 有了模块的划分：每个模块里都包含 controller 和 service，通过 `@Module` 声明模块，它包含 controllers 和 providers。

**为什么不是 services 而是 providers？** 因为 Nest 实现了一套依赖注入机制，叫做 IoC（Inverse of Control，反转控制）：只需要声明依赖了什么，不需要手动 new 依赖，Nest 的 IoC 容器会自动创建并注入依赖。比如 UserController 依赖了 JwtService，只需要通过 `@Inject` 声明依赖，然后就可以在方法里使用，运行时会自动查找 JwtService 的实例来注入。

`@Module` 里的 providers 数组就是声明要往 IoC 容器里提供的对象，所以叫 providers。provider 有很多种写法：默认的 `XxxService` 只是一种简化的写法，还可以直接 `useValue` 创建、通过 `useFactory` 创建等。

### 注入的两种方式

IoC 自动从容器中查找实例注入，注入方式有两种：

- **构造器注入**：写在构造器里的依赖；
- **属性注入**：`@Inject` 写在属性上的依赖。

效果一样，只是注入时机不同。

### 模块的组成与启动流程

每个模块都会包含 controller、service、module、dto、entities：

- controller 处理路由、解析请求参数；
- service 处理业务逻辑，比如操作数据库；
- dto 封装请求参数；
- entities 封装对应数据库表的实体。

Nest 应用跑起来后，会从 AppModule 开始解析，初始化 IoC 容器，加载所有 service 到容器里，然后解析 controller 里的路由，之后就可以接收请求了。

这种架构就是 MVC 模式（model、view、controller）：controller 接收请求参数，交给 model 处理（model 即处理 service 业务逻辑、处理 repository 数据库访问），然后返回 view（响应）。

### AOP 面向切面

应用中会有很多 controller、service，跨多个 controller 的通用逻辑怎么办？Nest 提供了 AOP（Aspect Oriented Programming，面向切面编程）机制，具体有五种：Middleware、Guard、Interceptor、Pipe、Exception Filter。它们都是在目标 controller 的 handler 前后额外加一段逻辑。

例如通过 interceptor 实现请求到响应的时间记录——这种逻辑不适合放在 controller 里，通用逻辑应该通过 interceptor 等方式抽离出来，需要用时在 controller 上声明一下。

### 核心概念小结

| 概念 | 含义 |
|------|------|
| **controller** | 控制器，用于处理路由、解析请求参数 |
| **handler** | 控制器里处理路由的方法 |
| **service** | 实现业务逻辑的地方，比如操作数据库等 |
| **dto** | data transfer object，数据传输对象，用于封装请求体里数据的对象 |
| **module** | 模块，包含 controller、service 等，比如用户模块、书籍模块 |
| **entity** | 对应数据库表的实体 |
| **ioc** | Inverse of Control，反转控制或叫依赖注入：只要声明依赖，运行时 Nest 会自动注入依赖的实例 |
| **aop** | Aspect Oriented Programming 面向切面编程：在多个请求响应流程中可复用的逻辑（如日志记录），包含 middleware、interceptor、guard、exception filter、pipe |
| **nest cli** | 创建项目、创建模块、创建 controller、创建 service 等都可以用这个 cli 工具来做 |

## 二、@nestjs/cli 常用命令

项目开发离不开工程化：创建项目、编译构建、开发时 watch 文件变动自动构建等。Nest 在 `@nestjs/cli` 包里提供了 `nest` 命令。

可以直接 npx 执行（npm 会把它下载下来然后执行）：

```
npx @nestjs/cli new 项目名
```

也可以安装到全局再执行，更推荐这种方式：

```
npm install -g @nestjs/cli

nest new 项目名
```

全局安装需要时不时升级版本，否则用它创建的项目版本可能不是最新的：

```
npm update -g @nestjs/cli
```

`nest -h` 可以查看全部命令：有创建新项目的 nest new、生成代码的 nest generate、编译构建的 nest build、开发模式的 nest start 等。

### nest new

nest new 用于创建一个新的 Nest 项目，主要选项：

| 选项 | 说明 |
|------|------|
| `--skip-git` | 跳过 git 的初始化 |
| `--skip-install` | 跳过 npm install |
| `--package-manager` | 指定包管理器（创建项目时会交互式询问，指定后跳过该步骤） |
| `--language` | 指定 typescript 或 javascript，一般用默认的 ts |
| `--strict` | 指定 ts 编译选项是否开启严格模式（5 个编译选项），默认 false，需要时再改 |

### nest generate

nest 命令除了生成整个项目，还可以生成 controller、service、module 等代码。

生成 module：

```
nest generate module aaa
```

它会生成 module 的代码，并自动在 AppModule 里引入。生成 controller、service 同理：

```
nest generate controller aaa
```

同样会更新到 module 的依赖里。

生成一个完整模块不需要逐个生成，可以用：

```
nest generate resource xxx
```

它会交互式选择代码类型（Nest 支持 http、websocket、graphql、tcp 等），选择 http 的 REST 风格 api 后，再选择是否生成 CRUD 代码，随后生成整个模块的 CRUD + REST api 代码，并自动在 AppModule 引入。

这些代码模板的集合在 `@nestjs/schematics` 包里定义，实现原理就是模板引擎填充变量、打印成代码。nest new 时的 `--collection` 选项就是配置这个的，一般不需要配置。模板定义可以在 [@nestjs/schematics](https://github.com/nestjs/schematics/tree/master/src/lib) 里查看。

nest generate 的选项：

| 选项 | 说明 |
|------|------|
| `--flat` / `--no-flat` | 指定是否生成对应目录 |
| `--spec` / `--no-spec` | 指定是否生成测试文件 |
| `--skip-import` | 指定不在 AppModule 里引入 |
| `--project` | 指定生成代码在哪个子项目（用于 monorepo） |

### nest build

nest build 用于构建项目，执行后会在 dist 目录下生成编译后的代码。主要选项：

- `--webpack` 和 `--tsc`：指定用什么编译，默认 tsc，也可以切换成 webpack。tsc 不做打包、webpack 会做打包，两种方式都可以——node 模块本来不需要打包，但打包成单模块能提升加载性能。
- `--watch`：监听文件变动自动 build。默认只监听 ts、js 文件，加上 `--watchAssets` 会连同其他文件（如 md、yml）一同监听变化并输出到 dist 目录。
- `--path`：指定 tsc 配置文件的路径。
- `--config`：指定 nest cli 的配置文件（nest-cli.json）。

### nest-cli.json

上述选项都可以在 nest-cli.json 里配置：

- `compilerOptions` 里设置 webpack 为 true 等价于 `nest build --webpack`；设为 false 就是用 tsc。
- `deleteOutDir` 设置为 true，每次 build 都会清空 dist 目录。
- `assets` 指定 nest build 时把非 js、ts 文件也复制到 dist 目录，可通过 include、exclude 精确匹配，并可单独指定是否 watchAssets。只支持 src 下文件的复制，非 src 下的文件可以自己写脚本复制。
- `generateOptions` 与 nest generate 时的 `--no-spec`、`--no-flat` 效果一样（例如 flat 设为 false、spec 设为 false 后，generate 会生成一层目录且不生成测试文件）。
- `sourceRoot` 指定源码目录；`entryFile` 指定入口文件的名字，默认 main。
- `$schema` 指定 nest-cli.json 的 schema，即可以有哪些属性：[https://json.schemastore.org/nest-cli](https://json.schemastore.org/nest-cli)。这是 json schema 的规范，想全面了解 nest-cli.json 的属性可查看该 schema 定义。

### nest start

nest start 用于启动项目：每次重新 build，并用 node 把 main.js 跑起来。主要选项：

- `--watch`：最常用的选项，改动文件之后自动重新 build；
- `--debug`：启动调试的 websocket 服务，用来 debug；
- `--exec`：指定用什么来跑，默认 node，可切换别的 runtime。

其余选项与 nest build 一致。

### nest info

nest info 用于查看项目信息，包括系统信息、node、npm 和依赖版本。

### CLI 小结

nest 命令的能力覆盖四类：

- 生成项目结构和各种代码
- 编译代码
- 监听文件变动自动编译
- 打印项目依赖信息

对应子命令：

- `nest new` 快速创建项目
- `nest generate` 快速生成各种代码
- `nest build` 使用 tsc 或者 webpack 构建代码
- `nest start` 启动开发服务，支持 watch 和调试
- `nest info` 打印 node、npm、nest 包的依赖版本

很多选项都可以在 nest-cli.json 里配置，比如 generateOptions、compilerOptions 等。学会用 nest cli 是学好 Nest 的重要一步。

## 三、HTTP 数据传输的 5 种方式

对前端而言，后端主要通过 http 接口传输数据，数据传输方式主要有 5 种：

- url param
- query
- form-urlencoded
- form-data
- json

### 传输方式原理

**url param**：参数写在 url 路径中，如 `http://guang.zxg/person/1111` 中的 `1111`，服务端框架或单页应用的路由都支持从 url 中取出参数。

**query**：url 中 `?` 后面用 `&` 分隔的字符串，如 `http://guang.zxg/person?name=guang&age=20` 中的 name 和 age。非英文字符和特殊字符要经过编码，可使用 `encodeURIComponent`：

```javascript
const query = "?name=" + encodeURIComponent('光') + "&age=20"

// ?name=%E5%85%89&age=20
```

或使用封装了一层的 query-string 库：

```javascript
const queryString = require('query-string');

queryString.stringify({
  name: '光',
  age: 20
});

// ?name=%E5%85%89&age=20
```

**form-urlencoded**：form 表单直接提交数据就是这种。与 query 字符串方式的区别只是放在了 body 里，并指定 content-type 为 `application/x-www-form-urlencoded`。内容也是 query 字符串，所以也要用 `encodeURIComponent` 或 query-string 库处理。get 是把数据拼成 query 字符串放在 url 后面，表单的 post 提交就直接用相同的方式把数据放在 body 里。这种方式需要对内容做 url encode，传输大量数据（如上传文件）时不太合适，因为文件 encode 一遍太慢，这时用 form-data。

**form-data**：不再用 `&` 分隔数据，而是用 `----------` + 一串数字作为 boundary 分隔符；不再是 url 的方式，自然不用 url encode。需要指定 content type 为 `multipart/form-data` 并指定 boundary（分割线），body 里就是用 boundary 分隔符分割的内容。适合传输文件，而且可以传输多个文件；但多了用于分隔的 boundary，请求体会增大。

**json**：form-urlencoded 需要 url encode、form-data 需要很长的 boundary，两者都有缺点。只传输 json 数据时直接指定 content type 为 `application/json`，平时传输 json 数据基本用这种。

### Nest 服务端准备

创建一个支持 api 接口、静态页面的 Nest 服务只需几步：

- 安装 @nestjs/cli，用 nest new 创建项目：

```
nest new xxx
```

- 在根目录执行 nest g resource person 快速生成 person 模块的 crud 代码：

```
nest g resource person
```

- nest start --watch 启动 Nest 服务：

```
nest start --watch
```

这样一个带 person crud 接口的服务就跑起来了，控制台会打印可用的接口，可在浏览器测试。

再支持静态资源访问：main.ts 负责启动 Nest 的 IoC 容器，调用 useStaticAssets 支持静态资源请求：

```typescript
import { NestExpressApplication } from '@nestjs/platform-express';

async function bootstrap() {
  const app = await NestFactory.create<NestExpressApplication>(AppModule);
  app.useStaticAssets('public', { prefix: '/static'});
  await app.listen(3000);
}
bootstrap();
```

（注意要给 create 方法传入 NestExpressApplication 的泛型参数才有 useStaticAssets 这些方法。）

指定 prefix 为 static，在静态文件目录 public 下添加一个 html：

```html
<html>
<body>hello</body>
</html>
```

重启服务后浏览器即可访问。api 接口和静态资源都支持后，分别实现 5 种传输方式。

### url param 的实现

url param 在 Nest 里通过 `:参数名` 的方式声明（如下例的 `:id`），然后通过 `@Param(参数名)` 装饰器取出注入到 controller：

```typescript
@Controller('api/person')
export class PersonController {
  @Get(':id')
  urlParam(@Param('id') id: string) {
    return `received: id=${id}`;
  }
}
```

`@Controller('api/person')` 的路由和 `@Get(':id')` 的路由会拼到一起，即只有 `/api/person/xxx` 的 get 请求才会走到这个方法。前端用 axios 发送 get 请求，参数放在 url 里：

```html
<!DOCTYPE html>
<html lang="en">
<head>
    <script src="https://unpkg.com/axios@0.24.0/dist/axios.min.js"></script>
</head>
<body>
    <script>
        async function urlParam() {
            const res = await axios.get('/api/person/1');
            console.log(res);
        }
        urlParam();
   </script>
</body>
```

浏览器控制台会打印服务端返回的消息，证明服务端拿到了通过 url param 传递的数据。

### query 的实现

query 在 Nest 里通过 `@Query` 装饰器来取：

```typescript
@Controller('api/person')
export class PersonController {
  @Get('find')
  query(@Query('name') name: string, @Query('age') age: number) {
    return `received: name=${name},age=${age}`;
  }
}
```

注意：find 的路由要放到 `:id` 的路由前面——Nest 是从上往下匹配的，放在后面会被 `:id` 的路由匹配到。

前端同样通过 axios 发送 get 请求：

```html
<!DOCTYPE html>
<html lang="en">
<head>
    <script src="https://unpkg.com/axios@0.24.0/dist/axios.min.js"></script>
</head>
<body>
    <script>
        async function query() {
            const res = await axios.get('/api/person/find', {
                params: {
                    name: '光',
                    age: 20
                }
            });
            console.log(res);
        }
        query();
   </script>
</body>
</html>
```

参数通过 params 指定，axios 会做 url encode，不需要自己做。

### form urlencoded 的实现

form urlencoded 通过 body 传输数据，本质是把 query 字符串放在 body 里，需要做 url encode。Nest 用 `@Body` 装饰器接收：Nest 会解析请求体，然后注入到 dto 中。dto（data transfer object）就是封装传输数据用的对象：

```typescript
export class CreatePersonDto {
    name: string;
    age: number;
}
```

```typescript
import { CreatePersonDto } from './dto/create-person.dto';

@Controller('api/person')
export class PersonController {
  @Post()
  body(@Body() createPersonDto: CreatePersonDto) {
    return `received: ${JSON.stringify(createPersonDto)}`
  }
}
```

前端使用 post 方式请求，指定 content type 为 `application/x-www-form-urlencoded`，用 qs 做 url encode：

```html
<!DOCTYPE html>
<html lang="en">
<head>
    <script src="https://unpkg.com/axios@0.24.0/dist/axios.min.js"></script>
    <script src="https://unpkg.com/qs@6.10.2/dist/qs.js"></script>
</head>
<body>
    <script>
        async function formUrlEncoded() {
            const res = await axios.post('/api/person', Qs.stringify({
                name: '光',
                age: 20
            }), {
                headers: { 'content-type': 'application/x-www-form-urlencoded' }
            });
            console.log(res);
        }

        formUrlEncoded();
    </script>
</body>
</html>
```

服务端可成功接收到数据。

### json 的实现

json 需要指定 content-type 为 `application/json`，内容以 JSON 方式传输。后端同样用 `@Body` 接收，不需要变动——form urlencoded 和 json 都是从 body 取值，Nest 内部会根据 content type 做区分，使用不同的解析方式：

```typescript
@Controller('api/person')
export class PersonController {
  @Post()
  body(@Body() createPersonDto: CreatePersonDto) {
    return `received: ${JSON.stringify(createPersonDto)}`
  }
}
```

前端用 axios 发送 post 请求，默认传输 json 时会自动指定 content type 为 `application/json`，不需要手动指定：

```html
<!DOCTYPE html>
<html lang="en">
<head>
    <script src="https://unpkg.com/axios@0.24.0/dist/axios.min.js"></script>
</head>
<body>
    <script>
        async function json() {
            const res = await axios.post('/api/person', {
                name: '光',
                age: 20
            });
            console.log(res);
        }
        json();
    </script>
</body>
</html>
```

服务端可成功接收通过 json 传递的数据。

### form data 的实现

json 和 form urlencoded 都不适合传递文件，传输文件要用 form data——用 `----------` 作为 boundary 分隔传输的内容。Nest 解析 form data 使用 AnyFilesInterceptor 拦截器，用 `@UseInterceptors` 装饰器启用；文件内容通过 `@UploadedFiles` 来取，非文件的内容同样通过 `@Body` 来取：

```typescript
import { Body, Controller, Post, UploadedFiles, UseInterceptors } from '@nestjs/common';
import { AnyFilesInterceptor } from '@nestjs/platform-express';
import { CreatePersonDto } from './dto/create-person.dto';

@Controller('api/person')
export class PersonController {
  @Post('file')
  @UseInterceptors(AnyFilesInterceptor({
      dest: 'uploads/'
  }))
  body2(@Body() createPersonDto: CreatePersonDto, @UploadedFiles() files: Array<Express.Multer.File>) {
    console.log(files);
    return `received: ${JSON.stringify(createPersonDto)}`
  }
}
```

这一步需要安装类型声明：

```
npm i -D @types/multer
```

前端使用 axios 发送 post 请求，指定 content type 为 `multipart/form-data`：

```html
<!DOCTYPE html>
<html lang="en">
<head>
    <script src="https://unpkg.com/axios@0.24.0/dist/axios.min.js"></script>
</head>
<body>
    <input id="fileInput" type="file" multiple/>
    <script>
        const fileInput = document.querySelector('#fileInput');

        async function formData() {
            const data = new FormData();
            data.set('name','光');
            data.set('age', 20);
            data.set('file1', fileInput.files[0]);
            data.set('file2', fileInput.files[1]);

            const res = await axios.post('/api/person/file', data, {
                headers: { 'content-type': 'multipart/form-data' }
            });
            console.log(res);
        }

        fileInput.onchange = formData;
    </script>
</body>
</html>
```

file input 指定 multiple 可以选择多个文件。测试后服务端能接收到 name、age（dto）与上传的文件（files）。

### 传输方式小结

用 axios 发送请求、Nest 起后端服务，5 种 http/https 数据传输方式汇总：

url 中的两种：

- **url param**：url 中的参数，Nest 中使用 @Param 来取；
- **query**：url 中 ? 后的字符串，Nest 中使用 @Query 来取。

body 中的三种：

- **form urlencoded**：类似 query 字符串，只不过放在 body 中。Nest 中使用 @Body 来取，axios 中需要指定 content type 为 `application/x-www-form-urlencoded`，并且对数据用 qs 或者 query-string 库做 url encode；
- **json**：json 格式的数据。Nest 中使用 @Body 来取，axios 中不需要单独指定 content type，axios 内部会处理；
- **form data**：通过 `-----` 作为 boundary 分隔的数据，主要用于传输文件。Nest 中要使用 AnyFilesInterceptor（处理单个文件字段则用 FilesInterceptor）处理其中的 binary 字段，用 @UseInterceptors 启用，其余字段用 @Body 来取；axios 中需要指定 content type 为 `multipart/form-data`，并且用 FormData 对象封装传输的内容。

这 5 种方式覆盖了绝大多数开发场景，是全栈开发的基础。

## 四、IoC 依赖注入

### 为什么需要 IoC

后端系统中有很多对象：

- Controller 对象：接收 http 请求，调用 Service，返回响应；
- Service 对象：实现业务逻辑；
- Repository 对象：实现对数据库的增删改查；
- 此外还有数据库连接对象 DataSource、配置对象 Config 等。

这些对象关系错综复杂：Controller 依赖 Service 实现业务逻辑，Service 依赖 Repository 做增删改查，Repository 依赖 DataSource 建立连接，DataSource 又需要从 Config 拿到用户名密码等信息。手动创建对象时需要理清依赖的先后顺序：

```javascript
const config = new Config({ username: 'xxx', password: 'xxx'});

const dataSource = new DataSource(config);

const repository = new Repository(dataSource);

const service = new Service(repository);

const controller = new Controller(service);
```

要经过一系列初始化之后才可以使用 Controller 对象。而且 config、dataSource、repository、service、controller 这些对象不需要每次都 new 一个新的，一直用一个就可以（保持单例）。在应用初始化时理清依赖先后关系、创建并组装一大堆对象、还要保证不重复 new——这就是痛点。

### IoC 与 DI 的概念

解决这个痛点的方式就是 IoC（Inverse of Control）。Java 的 Spring 实现了 IoC，Nest 也同样实现了。

IoC 的实现思路：不在代码里手动 new 依赖对象并组装，而是在 class 上声明依赖了什么，让工具分析声明的依赖关系，根据先后顺序自动创建对象并组装、注入依赖。

它有一个放对象的容器：程序初始化时扫描 class 上声明的依赖关系，把这些 class 都 new 一个实例放到容器里；创建对象时把它们依赖的对象注入进去——自动完成对象的创建和组装。这种依赖注入的方式叫做 Dependency Injection，简称 DI。

"反转控制"的含义：本来是手动 new 依赖对象然后组装起来，现在是声明依赖然后等待被注入——从主动创建依赖到被动等待依赖注入，这就是 Inverse of Control。

在 class 上声明依赖的方式，业界都选择了装饰器（在 Java 里这种语法叫做注解）：声明这个 class 要放到 IoC 容器里、它的依赖是什么，IoC 容器扫描到它就知道怎么创建它的对象了。

### Nest 中使用 IoC

创建 Nest 项目：

```
npx nest new nest-ioc
```

选择 npm 包管理工具后，nest cli 会自动创建项目结构并安装依赖。进入目录执行 `npm run start` 跑起来，浏览器访问 http://localhost:3000 可以看到 Nest 服务返回的 hello world。

代码中对象的创建方式：

- AppService 声明了 `@Injectable`，代表这个 class 可注入，Nest 会把它的对象放到 IoC 容器里；
- AppController 声明了 `@Controller`，代表这个 class 可以被注入，Nest 也会把它放到 IoC 容器里；
- AppController 的构造器参数依赖了 AppService（构造器注入），也可以通过属性的方式声明依赖（属性注入，`@Inject` 写在属性上），两种都可以。

**为什么 Controller 是单独的装饰器？** 因为 Service 既可以被注入也可以注入到别的对象，所以用 `@Injectable` 声明；而 Controller 只需要被注入，所以 Nest 单独给它加了 `@Controller` 装饰器。

然后在 AppModule 里引入：通过 `@Module` 声明模块，其中 controllers 是控制器，只能被注入；providers 里可以被注入、也可以注入别的对象（如 AppService）。入口模块跑起来后，Nest 从 AppModule 开始解析 class 上通过装饰器声明的依赖信息，自动创建和组装对象。AppController 只是声明了对 AppService 的依赖，就可以调用它的方法——Nest 在背后自动做了对象创建和依赖注入的工作。

### 模块机制与跨模块注入

Nest 还提供了模块机制，可以把不同业务的 controller、service 放到不同模块里：

```
nest g module other
```

用 nest cli 的 generate 命令生成一个模块，会在 AppModule 里自动 imports 这个模块。

当 import 别的模块后，那个模块 exports 的 provider 就可以在当前模块注入了。比如再生成 OtherService：

```
nest g service other
```

会生成 Service 的代码并自动添加到 OtherModule 的 providers 中。修改 OtherService 添加一个方法，然后在 OtherModule 里 exports 它。当 AppModule 引用了 OtherModule 之后，就可以注入它 exports 的 OtherService。在 AppService 里注入：

```javascript
import { OtherService } from './other/other.service';
import { Inject, Injectable } from '@nestjs/common';

@Injectable()
export class AppService {

  @Inject(OtherService)
  private otherService:OtherService;

  getHello(): string {
    return 'Hello World!' + this.otherService.xxx();
  }
}

```

跑起来：

```
npm run start:dev
```

浏览器访问即可看到 AppModule 的 AppService 调用 OtherModule 的 OtherService 成功。这就是 Nest 的 IoC 机制。

### IoC 小结

后端系统的对象依赖关系错综复杂，手动创建并组装对象麻烦，因此后端框架一般都提供 IoC 机制：在 class 上标识哪些可以被注入、依赖是什么，从入口开始扫描这些对象和依赖，自动创建和组装对象。

Nest 里通过 `@Controller` 声明只被注入的 controller，通过 `@Injectable` 声明可被注入也可注入别人的 provider，然后在 `@Module` 声明的模块里引入；Module 与 Module 之间可以 import，引入别的模块的 provider 来注入。这套机制看似繁琐，却解决了后端系统对象依赖关系错综复杂的痛点。

## 五、Provider 的四种写法

Nest 的 IoC 容器会从入口模块开始扫描，分析 Module 之间的引用关系、对象之间的依赖关系，自动把 provider 注入到目标对象。provider 有多种写法。

### useClass 与 token

创建项目：

```
nest new custom-provider
```

AppService 是被 `@Injectable` 修饰的 class，在 Module 的 providers 里声明：

```javascript
{
  provide: AppService,
  useClass: AppService
}
```

通过 provide 指定 token，通过 useClass 指定对象的类，Nest 会自动实例化后用来注入。在 AppController 的构造器参数里声明 AppService 的依赖就会自动注入。不想用构造器注入也可以属性注入：

```javascript
@Inject(AppService)
private readonly appService: AppService;
```

通过 `@Inject` 指定注入的 provider 的 token 即可。构造器参数里指定 AppService 依赖时并没有指定 token——那是因为 AppService 这个 class 本身就是 token。

token 也可以是字符串：

```javascript
{
    provide: 'app_service',
    useClass: AppService
}
```

token 是字符串时，注入就要用 `@Inject` 手动指定：

```javascript
@Inject('app_service') private readonly appService: AppService
```

调试验证：点击调试面板的 create launch.json file 创建调试配置文件，添加调试配置：

```json
{
    "type": "node",
    "request": "launch",
    "name": "debug nest",
    "runtimeExecutable": "npm",
    "args": [
        "run",
        "start:dev",
    ],
    "skipFiles": [
        "<node_internals>/**"
    ],
    "console": "integratedTerminal",
}
```

在 getHello 方法打个断点点击调试启动，浏览器访问 http://localhost:3000，代码会在断点处断住，此时 appService 已有值。字符串 token 或 class token 的 provider 都能正确注入；相比之下，class 做 token 可以省去 `@Inject`，更简便。

### useValue

除了指定 class，还可以直接指定一个值让 IoC 容器注入：

```javascript
{
    provide: 'person',
    useValue: {
        name: 'aaa',
        age: 20
    }
}
```

provide 指定 token，useValue 指定值。在对象里注入：

```javascript
@Inject('person') private readonly person: {name: string, age: number}
```

### useFactory

provider 的值可能是动态产生的，Nest 支持 useFactory：

```javascript
{
    provide: 'person2',
    useFactory() {
        return {
            name: 'bbb',
            desc: 'cccc'
        }
    }
}
```

在对象里注入：

```javascript
@Inject('person2') private readonly person2: {name: string, desc: string}
```

类型是 `{name: string, desc: string}`。

useFactory 支持通过参数注入别的 provider：

```javascript
{
  provide: 'person3',
  useFactory(person: { name: string }, appService: AppService) {
    return {
      name: person.name,
      desc: appService.getHello()
    }
  },
  inject: ['person', AppService]
}
```

通过 inject 声明两个 token：一个是字符串 token 的 person，一个是 class token 的 AppService。调用 useFactory 方法时，Nest 会注入这两个对象。

useFactory 还支持异步：

```javascript
{
  provide: 'person5',
  async useFactory() {
    await new Promise((resolve) => {
      setTimeout(resolve, 3000);
    });
    return {
      name: 'bbb',
      desc: 'cccc'
    }
  },
},
```

Nest 会等拿到异步方法的结果之后再注入，这样可以更灵活地创建注入对象。

### useExisting

provider 还可以通过 useExisting 指定别名：

```javascript
{
  provide: 'person4',
  useExisting: 'person2'
}
```

即给 person2 这个 token 的 provider 起一个新 token 叫 person4，之后就可以用新 token 注入。

### 实际应用：@nestjs/typeorm

自定义 provider 的方式里，最常用的是 useClass（一般用简写，直接指定 class）；useClass 由 IoC 容器负责实例化，useValue、useFactory 直接指定对象，useExisting 用于起别名。@nestjs/typeorm 就用到了三种：

- 用 useValue 来[注入一段字符串](https://github.com/nestjs/typeorm/blob/153da09a384fdbf797b66e4500b69a72a7a47b78/lib/typeorm-core.module.ts#L113-L116)；
- 用 useFactory 根据传入的 options [动态创建数据库连接对象](https://github.com/nestjs/typeorm/blob/153da09a384fdbf797b66e4500b69a72a7a47b78/lib/typeorm-core.module.ts#L83-L101)；
- 用 useExisting 给 DataSource 起了一个 Connection 的[别名](https://github.com/nestjs/typeorm/blob/153da09a384fdbf797b66e4500b69a72a7a47b78/lib/typeorm-core.module.ts#L68-L71)——一个版本用 Connection、一个版本用 DataSource，通过 useExisting 起别名即可兼容两者。

另外，构造器注入写起来不方便时可用属性注入，效果一样。

### Provider 小结

- 一般情况下，provider 是通过 `@Injectable` 声明、在 `@Module` 的 providers 数组里注册的 class；默认 token 就是 class，不用 `@Inject` 指定；字符串 token 则注入时要用 `@Inject` 单独指定。
- useClass 指定注入的 class；useValue 直接指定注入的对象。
- useFactory 动态生成对象，其参数也注入 IoC 容器中的对象，支持异步。
- useExisting 给已有的 token 指定一个新 token（别名）。
- 灵活运用这些 provider 类型，可以利用 Nest 的 IoC 容器注入任何对象。

## 六、循环依赖与 forwardRef

Nest 实现了一套模块系统，模块可以通过 imports 声明对其他模块的引用。当 Module 和 Module 相互引用、形成循环依赖时，需要特殊处理。

### Module 之间的循环依赖

创建项目与两个模块：

```
nest new module-test -p npm
```

```
nest g module aaa
nest g module bbb
```

让这两个 Module 相互引用后启动：

```
nest start -w
```

会报错：解析 BbbModule 时它的第一个 imports 是 undefined。报错有两个可能原因：一是值本来就是 undefined，二是形成了循环依赖。因为 Nest 创建 Module 时会递归创建它的依赖，而它的依赖又依赖了这个 Module，所以没法创建成功，拿到的就是 undefined。

**解决方式**：先单独创建这两个 Module，然后再让两者关联起来——即用 forwardRef，两边都在 imports 里用 forwardRef 包裹：

```javascript
import { Module, forwardRef } from '@nestjs/common';
import { BbbModule } from './bbb/bbb.module';

@Module({
  imports: [forwardRef(() => BbbModule)],
})
export class AaaModule {}
```

```javascript
import { Module, forwardRef } from '@nestjs/common';
import { AaaModule } from './aaa/aaa.module';

@Module({
  imports: [forwardRef(() => AaaModule)],
})
export class BbbModule {}
```

由于用 nest start --watch 启动，nest 会自动重启，此时就没有错误了。nest 会单独创建两个 Module，之后再把 Module 的引用转发过去——这就是 forwardRef 的含义。

### Provider 之间的循环依赖

Module 之外，provider 之间也会有循环引用：Service 里可以注入别的 Service，自身也可以用来注入。

生成两个 service（`--no-spec` 不生成测试文件，`--flat` 平铺）：

```
nest g service ccc --no-spec --flat
nest g service ddd --no-spec --flat
```

让两者相互注入：

```javascript
import { Injectable } from '@nestjs/common';
import { CccService } from './ccc.service';

@Injectable()
export class DddService {
    constructor(private cccService: CccService) {}

    ddd() {
        return this.cccService.ccc()  + 'ddd';
    }
}
```

```javascript
import { Injectable } from '@nestjs/common';
import { DddService } from './ddd.service';

@Injectable()
export class CccService {
    constructor(private dddService: DddService) {}

    ccc() {
        return 'ccc';
    }

    eee() {
        return this.dddService.ddd() + 'eee';
    }
}
```

在 AppService 里调用：

```javascript
import { Injectable } from '@nestjs/common';
import { CccService } from './ccc.service';
import { DddService } from './ddd.service';

@Injectable()
export class AppService {
  constructor(private cccService: CccService, private dddService: DddService){}

  getHello(): string {
    return this.dddService.ddd() + this.cccService.eee();
  }
}
```

此时 nest start --watch 会报错：没法解析 DddService 的依赖，同样是循环依赖导致。解决方式同样是 forwardRef：不能用默认的注入方式，通过 `@Inject` 手动指定注入的 token 为 forwardRef 的方式，两个 service 都要改：

```javascript
import { forwardRef, Inject, Injectable } from '@nestjs/common';
import { CccService } from './ccc.service';

@Injectable()
export class DddService {
    constructor(@Inject(forwardRef(() => CccService)) private cccService: CccService) {}

    ddd() {
        return this.cccService.ccc()  + 'ddd';
    }
}
```

```javascript
import { forwardRef, Inject, Injectable } from '@nestjs/common';
import { DddService } from './ddd.service';

@Injectable()
export class CccService {
    constructor(@Inject(forwardRef(() => DddService)) private dddService: DddService) {}

    ccc() {
        return 'ccc';
    }

    eee() {
        return this.dddService.ddd() + 'eee';
    }
}
```

报错消失，浏览器访问后两个 service 的相互调用也成功。

### 循环依赖小结

Module 之间可以相互 imports，Provider 之间可以相互注入，这两者都会形成循环依赖。解决方式是两边都用 forwardRef 包裹：原理是 nest 先创建 Module、Provider，之后再把引用转发到对方（forward ref）。

## 七、整体架构串联

前面分散讲解了 IoC、AOP、全局模块、动态模块、自定义 provider、生命周期等概念，这里整体串联。

### Provider 与 Module 的全景

- provider 是可以注入的对象，都有 token，比如 `@Injectable` 装饰器声明的 class；token 可以是 class 也可以是 string。
- provider 可以用 useClass 指定 class、useValue 指定值、useFactory 动态创建；provider 之间可以相互注入，还可以注入到 controller 里。
- provider、controller 放在一个个 Module 里；module 里 exports 的 provider 在模块被 imports 之后就可以用于别的模块的注入。
- 可以通过 `@Global` 把模块声明为全局的，该 Module 内的 provider 就可以在各处注入。
- Provider 可以通过 useFactory 动态创建，Module 也可以——通过 register、forRoot、forFeature 等方法动态创建。

### 启动与生命周期

在 main.ts 里调用 NestFactory.create 方法，会从 AppModule 开始递归解析 Module，实例化其中的 provider、controller，并依次调用它们的 onModuleInit 生命周期方法；之后再递归调用每个 Module 的 provider、controller 以及 Module 自身的 onApplicationBootstrap 生命周期方法。此后 Nest 就能对外提供服务了。

Nest 销毁时，也会依次调用 Module 的 provider、controller 以及 Module 自己的 onModuleDestroy、beforeApplicationShutdown、onApplicationShutdown 生命周期方法。后两者的区别：beforeApplicationShutdown 可以拿到终止信号。

### 请求到响应的切面流程

Nest 从接收到请求到返回响应的流程中有多个切面，路由最终在 controller 的方法（handler）里处理：

1. **Middleware**：请求首先被 middleware 处理。这一层可以复用 express 的中间件生态，实现 session、static files 等功能；也可以是 Nest 的 class middleware，可以注入 provider。
2. **Guard**：在具体的路由经历 Guard 处理，它可以通过 ExecutionContext 拿到目标 class、handler 的 metadata 等信息，可实现权限验证等功能。
3. **Interceptor**：可以在请求前后做一些处理，同样可以通过 ExecutionContext 拿到 class、handler 的信息。
4. **Pipe**：到达 handler 之前对参数做检验和转换。
5. **Exception Filter**：过程中不管哪一层抛的异常，都会被 Exception Filter 处理，返回给用户友好的响应信息。

通过 AOP 的切面可以把通用逻辑封装起来在各处复用。

### 架构总结

- 通过 IoC 实现了对象的自动创建、依赖的自动组装；
- 通过 AOP 实现了通用逻辑的抽取和复用；
- IoC 内部的 Module 和 Provider 都支持动态创建，灵活度很高。

把这些核心概念（Module、Provider、Controller、动态模块、全局模块、自定义 Provider、生命周期、Middleware、Guard、Pipe、Interceptor、Exception Filter）理解了，对 Nest 就算有比较好的掌握了。

# 会议室项目-部署与优化

## 一、后端部署：Docker Compose

### 部署架构

项目开发完成后要部署到服务器上运行，涉及 mysql、redis、nginx 三个依赖组件，关系如下：

- 前端代码由 nginx 托管，处理静态请求；
- 后端服务经过 nginx 做反向代理，这样可以做多个 Nest 服务的负载均衡；
- Nginx、MySQL、Redis、Nest 服务等都通过 docker 来跑。

不需要一个个跑，通过 Docker Compose 把它们组合成一个整体一起跑。开发完之后，本地把代码 push 到 github、gitlab 等代码仓库，服务器上把代码 pull 下来，然后用 docker compose 跑即可。有了 docker，根本不用考虑 mysql、redis、node 等在 linux 下怎么安装，直接跑 docker 镜像就行。

注意：线上不能开启 typeorm 的 synchronize——代码一改就同步修改表结构，容易导致数据丢失。线上用 migration 迁移来做，详细介绍见《[会议室项目-统计与账号登录](./13-会议室项目-统计与账号登录.md)》。

### docker-compose.yml

在后端项目的根目录添加 docker-compose.yml 文件：

```yml
services:
  nest-app:
    build:
      context: ./
      dockerfile: ./Dockerfile
    depends_on:
      - mysql-container
      - redis-container
    ports:
      - 3005:3005
    networks:
      - common-network
  mysql-container:
    image: mysql
    volumes:
      - /Users/guang/mysql-data:/var/lib/mysql
    environment:
      MYSQL_DATABASE: meeting_room_booking_system
      MYSQL_ROOT_PASSWORD: guang
    networks:
      - common-network
  redis-container:
    image: redis
    volumes:
      - /Users/guang/redis-data:/data
    networks:
      - common-network
networks:
  common-network:
    driver: bridge
```

配置说明：

- 共 3 个 docker 容器：nest-app、mysql-container、redis-container；
- nest-app 通过 Dockerfile 构建，暴露 3005 端口，依赖 redis-container 和 mysql-container；
- mysql-container 指定挂载的 volume 数据卷，以及 MYSQL_DATABASE（自动创建的 database）和 MYSQL_ROOT_PASSWORD（root 用户密码）的环境变量；
- redis-container 指定挂载的 volume 数据卷；
- 三个容器放到同一个桥接网络里。

### Dockerfile

在根目录添加 Dockerfile：

```docker
FROM node:22-alpine3.20 as build-stage

WORKDIR /app

COPY package.json .

RUN npm config set registry https://registry.npmmirror.com/

RUN npm install

COPY . .

RUN npm run build

# production stage
FROM node:22-alpine3.20 as production-stage

COPY --from=build-stage /app/dist /app
COPY --from=build-stage /app/package.json /app/package.json

WORKDIR /app

RUN npm config set registry https://registry.npmmirror.com/

RUN npm install --omit=dev

EXPOSE 3005

CMD ["node", "/app/main.js"]
```

Nest 的 Dockerfile 使用多阶段构建：第一个镜像先复制 package.json、安装依赖，之后执行 npm run build 生成 dist 目录；第二个镜像复制第一个镜像的 dist 目录和 package.json，执行 npm install 并用 node 跑起来。

### 环境变量与 .dockerignore

修改 .env 文件：把 localhost 改为 redis-container 和 mysql-container。

还要修改一处：加载配置文件的目录改成拼接 __dirname 和 .env 的路径：

```javascript
ConfigModule.forRoot({
  isGlobal: true,
  envFilePath: path.join(__dirname, '.env')
}),
```

原因：build 出来的代码没有 src 目录，是直接放在 dist 下的。

添加 .dockerignore（不会被复制到容器内的文件）：

```ignore
node_modules/
.vscode/
.git/
```

### 本地运行

跑起来（最好把本地的 mysql 和 redis 容器停掉再跑）：

```
docker compose up
```

它会首先根据 Dockerfile 生成 nest-app 的镜像，然后分别跑 mysql-container 和 redis-container 容器，最后 nest-app 也跑起来。访问接口验证无误。

如果改了 Dockerfile 或者 docker-compose.yml 想重新跑，需要先把之前的镜像和容器删掉再跑：

```
docker compose down --rmi all
```

## 二、部署到阿里云服务器

### 购买与登录服务器

把本地代码 push 到 gitlab 或 github，然后在服务器上拉下来跑 docker compose up。

购买服务器（示例选的是 1 核 1G、买一周的量，可根据需要购买），注意要勾选公网 ipv4 地址，否则访问不了公网。进入控制台可以看到这台服务器，点击远程连接、点立即登录。用 ssh 密钥的方式登录需要先创建密钥文件：创建完会自动下载密钥文件，然后点击绑定密钥对（用这个密钥登录服务器，这一步会重启服务器）。再次远程连接就可以用密钥文件登录。

### 安装依赖并启动

服务器需要安装 git 和 docker：用 git 下载代码，用 docker compose 跑代码。

安装 git：

```
yum install git -y
```

把 github 的代码下下来：

```
git clone 你自己的git仓库
```

进入项目目录跑 docker compose 就行，和本地跑一样。

安装 docker：直接看[阿里云的文档](https://help.aliyun.com/zh/ecs/use-cases/deploy-and-use-docker-on-alibaba-cloud-linux-2-instances)。docker 安装好后设置开机启动（复制文档命令），然后安装 docker compose（同样直接复制文档命令）。

跑服务：

```
docker compose up
```

会先 pull mysql 和 redis 的镜像，然后 build nest 的镜像，之后服务跑起来。过程中会自动创建一系列的 table——因为现在还没关掉 synchronize。

服务跑在 3005 端口，需要在安全组添加该端口，之后就可以用公网 ip 访问。当然此时初始化数据还没加、创建表也没有用 migration，这些随后继续优化。

## 三、前端部署：Nginx

### 架构与 nginx 配置

后端部署完成后部署前端项目。架构：在之前 docker compose 的基础上加上 nginx 容器。进入 frontend-admin 项目，添加 nginx 配置文件：

```
upstream nest-server {
    server 192.168.31.56:3005;
}

server {
    listen       80;
    listen  [::]:80;
    server_name  localhost;

    location ^~ /api {
        rewrite ^/api/(.*)$ /$1 break;
        proxy_pass http://nest-server;
    }

    location / {
        root   /usr/share/nginx/html;
        index  index.html index.htm;
    }

    error_page   500 502 503 504  /50x.html;
    location = /50x.html {
        root   /usr/share/nginx/html;
    }
}
```

nginx 的两个核心功能就是静态资源托管、反向代理。这里配置了 /api 下的请求走反向代理、转发到 nest 服务；/ 下的静态资源请求返回 index.html。upstream 里的 ip 是宿主机的，实际使用时换成自己的地址。

用 nginx 做了反向代理之后，访问的 url 要改一下：不再直接访问 nest 服务，而是通过 nginx 反向代理到 nest 服务。

### 前端 Dockerfile

```docker
# build stage
FROM node:22 as build-stage

WORKDIR /app

COPY package.json ./

RUN npm config set registry https://registry.npmmirror.com/

RUN npm install

COPY . .

RUN npm run build

# production stage
FROM nginx:stable as production-stage

COPY --from=build-stage /app/dist /usr/share/nginx/html

COPY --from=build-stage /app/nginx.conf /etc/nginx/conf.d/default.conf

EXPOSE 80

CMD ["nginx", "-g", "daemon off;"]
```

同样是多阶段构建：第一个阶段把代码复制到容器、执行 npm run build；第二个阶段把上一阶段的产物和 nginx 配置文件复制过来，把 nginx 服务跑起来。CMD 启动命令参考其他 nginx 镜像的启动命令即可。

添加 .dockerignore：

```
node_modules/
.vscode/
.git/
dist/
```

构建镜像：

```
docker build -t fe-container:first .
```

在 docker desktop 里搜索这个镜像点击 run；进入 backend 项目跑起服务：

```
npm run start:dev
```

浏览器访问：界面正常渲染，访问接口的 url 换成了 nginx 的，接口也正常返回数据——nginx 的反向代理和静态资源托管都成功。

### browser 路由的 404 问题

切换到修改信息界面时会跳到 /login 的 url，此时返回 404。原因：前端用的是 browser 路由（/xxx 方式）而不是 hash 路由（?#/xxx 方式）。需要在 nginx 里支持：

```
location / {
    root   /usr/share/nginx/html;
    index  index.html index.htm;
    try_files $uri $uri/ /index.html;
}
```

加上这条 try_files，访问 /login 时会先匹配 /login、然后 /login/、最后 /index.html——即交给前端页面处理 /login 路由。重新 build，把之前的 container 停止、删除再重新跑，所有路由都能正常访问。

### 并入 docker compose

现在是单独跑 nginx 容器，且反向代理 nest 服务用的是 ip，这不好。希望把它也放进 docker-compose.yml，直接 docker compose up 一起跑。docker compose 跑的多个容器之间可以通过容器名相互访问，所以改一下 nginx 配置，把 ip 换成 nest 服务的容器名，重新 build。然后在 backend 项目的 docker-compose.yml 里配置：

```yml
services:
  fe-app:
    image: fe-container:first
    ports:
      - 80:80
    depends_on:
      - nest-app
    networks:
      - common-network
  nest-app:
    build:
      context: ./
      dockerfile: ./Dockerfile
    depends_on:
      - mysql-container
      - redis-container
    networks:
      - common-network
  mysql-container:
    image: mysql
    volumes:
      - /Users/guang/mysql-data:/var/lib/mysql
    environment:
      MYSQL_DATABASE: meeting_room_booking_system
      MYSQL_ROOT_PASSWORD: guang
    networks:
      - common-network
  redis-container:
    image: redis
    volumes:
      - /Users/guang/redis-data:/data
    networks:
      - common-network
networks:
  common-network:
    driver: bridge
```

把 env 里的 url 改回来，然后跑一下（最好把本地的其他 mysql 和 redis 容器停掉再跑）：

```
docker compose up
```

跑起来后浏览器访问验证。这样就通过 docker compose 一次性跑了 nest、nginx、mysql 和 redis 服务。

## 四、上传镜像到阿里云镜像仓库

fe-container 镜像只存在于本地，在阿里云跑 docker compose 会找不到这个镜像，所以需要把镜像上传到阿里云的镜像仓库。当然，也可以直接在服务器上下载代码然后 build 镜像；这里是为了使用阿里云的镜像仓库。阿里云的[容器镜像服务](https://www.aliyun.com/product/acr)个人用是免费的。

步骤：

1. 进入管理控制台，点击创建镜像仓库（会要求先创建命名空间）。
2. 控制台直接说明了如何登录阿里云镜像仓库和 push 镜像。
3. 在本地 build 镜像。复制服务器的公网 ip，改一下项目里的 baseURL 为服务器 ip，然后构建：

```
docker build -t fe-container:first .
```

4. 分别执行 docker login、docker tag、docker push 把镜像 push 到镜像仓库（直接复制控制台命令即可）。上传之后点击镜像版本可以看到该版本号的镜像。
5. 改一下 backend 项目里的 docker-compose.yml，image 改成阿里云镜像仓库里的。
6. 保存代码 git push 到代码仓库；登录服务器把最新代码 clone 下来（clone 过了只要 git pull），然后跑：

```
docker login --username=用户名 registry.cn-qingdao.aliyuncs.com

docker compose up
```

7. 在安全组添加 80 端口。

### platform 不匹配问题

此时用 ip 访问可能没有返回内容，翻日志可能有报错：docker 镜像的 platform 不匹配——本地是 m1 芯片的 mac，build 出来的镜像在 linux 上跑不了。（不一定遇到这个问题，没遇到可跳过以下步骤。）

遇到时，build 的时候加上 platform：

```
docker build -t fe-container:first --platform linux/amd64 .
```

重新 build 镜像指定目标 platform，然后重新 docker login、docker tag、docker push 上传镜像。上传之后在服务器把之前的镜像删掉重新跑：

```
docker compose down --rmi all

docker login --username=用户名 registry.cn-qingdao.aliyuncs.com

docker compose up
```

这时浏览器就可以看到页面正常渲染，请求的 url 也是对的（只是没有数据，后面加上初始数据即可）。前端部分部署完成。

## 五、后端代码优化

会议室预订系统的后端功能实现得差不多之后，代码层面还有优化空间，集中做一轮优化。

### .env 多环境

.env 文件里保存着 redis、mysql、nodemailer、nest 服务、jwt、minio 的配置。其实 google 登录的 client id 和 client secret 也应该在这里配置：

```
# google 登录配置
google_login_client_id=xxx
google_login_client_secret=xxx
google_login_callback_url=http://localhost:3005/user/callback/google
```

然后 google.strategy.ts 里取出来：

```javascript
constructor(configService: ConfigService) {
    super({
      clientID: configService.get('google_login_client_id'),
      clientSecret: configService.get('google_login_client_secret'),
      callbackURL: configService.get('google_login_callback_url'),
      scope: ['email', 'profile'],
    });
}
```

注意：这个 client id 是测试用的，线上的要另外申请——线上不会是 http://localhost:3005 的域名。也就是说，dev 环境和 prod 环境的 .env 是不同的，需要支持多个环境的 .env 加载。

新建一个 src/.dev.env 配置文件：其他配置都一样，只是把启动端口改为 3006。然后 ConfigModule 的 envFilePath 指定多个 .env 文件：

```javascript
ConfigModule.forRoot({
  isGlobal: true,
  envFilePath: [ path.join(__dirname, '.env'), path.join(__dirname, '.dev.env')]
}),
```

指定多个 .env 文件时配置会做合并，但相同的 key 前面的配置生效——也就是有 .env 时它的配置优先生效。跑起来验证：有 .env 时端口是 3005；删掉 .env 再跑，就跑在 .dev.env 配置的 3006 端口了。

另外，.env 可以不提交到 git 仓库，部署时手动把文件复制过去，就没有泄漏的风险。这样本地测试的配置写在 .dev.env 里，线上生产环境的配置写在 .env 里。

### docker-compose.yml 补充与优化

前面添加了 minio 做 OSS 文件存储，但没把它加到 docker compose 配置文件里，补上：

```yml
minio-container:
  image: bitnami/minio:latest
  ports:
    - 9000:9000
    - 9001:9001
  volumes:
    - /Users/guang/minio:/bitnami/minio/data
  environment:
    MINIO_ROOT_USER: guang
    MINIO_ROOT_PASSWORD: dongdong
  networks:
    - common-network
```

虽然有了桥接网络、多个容器之间可以通过容器名访问，但 minio 还是需要暴露端口出来——管理界面、保存在 minio 的图片都需要直接访问。

把配置文件里的连接配置都改为容器名；注释掉 fe 的容器，并给 nest 容器映射 3005 端口（这里只测试 nest 服务和 minio 服务）。跑之前注意先把本地的 minio 容器停掉，否则 9000、9001 端口被占用：

```
docker compose up
```

nest 和 minio 都跑起来后，浏览器访问 minio 管理页面 http://localhost:9001/ 验证；再访问 minio 预签名接口验证——说明 nest 连接 minio 成功。

进一步优化 docker-compose.yml：

- 可以通过 command 指定容器启动时执行的命令。例如 mysql 容器启动时修改默认字符集为 utf8：

```yml
command: mysqld --character-set-server=utf8mb4 --collation-server=utf8mb4_general_ci # 设置默认字符集
```

- 每个容器都应该加上重启策略：当容器意外停掉时重启。

### dto：mapped-types 复用

可以用 @nestjs/mapped-types 的 PartialType、PickType、OmitType、IntersectionType 灵活创建 dto：

- PickType：从已有 dto 类型中取某个字段；
- OmitType：从已有 dto 类型中去掉某个字段；
- PartialType：把 dto 类型变为可选；
- IntersectionType：组合多个 dto 类型。

用这些方法可以轻松基于已有 dto 创建新的 dto。改造现有 dto：LoginUserDto 的 username 和 password 在 RegisterUserDto 里可以复用，UpdateUserPasswordDto 和 UpdateUserDto 也可以复用 RegisterUserDto 的某些字段。

RegisterUserDto 简化为：

```javascript
import { ApiProperty } from "@nestjs/swagger";
import { IsEmail, IsNotEmpty, MinLength } from "class-validator";
import { LoginUserDto } from "./login-user.dto";
import { PickType } from "@nestjs/mapped-types";

export class RegisterUserDto extends PickType(LoginUserDto, ['username', 'password']){
    @IsNotEmpty({
        message: '昵称不能为空'
    })
    @ApiProperty()
    nickName: string;

    @IsNotEmpty({
        message: '邮箱不能为空'
    })
    @IsEmail({}, {
        message: '不是合法的邮箱格式'
    })
    @ApiProperty()
    email: string;

    @IsNotEmpty({
        message: '验证码不能为空'
    })
    @ApiProperty()
    captcha: string;
}
```

继承 LoginUserDto 里的两个字段。UpdateUserPasswordDto 的字段可以全部从 RegisterUserDto 继承：

```javascript
import { ApiProperty, PickType } from "@nestjs/swagger";
import { IsEmail, IsNotEmpty, MinLength } from "class-validator";
import { LoginUserDto } from "./login-user.dto";
import { RegisterUserDto } from "./register-user.dto";

export class UpdateUserPasswordDto extends PickType(RegisterUserDto, ['email', 'captcha', 'username', 'password']){
}
```

UpdateUserDto 复用 RegisterUserDto 的大部分字段：

```javascript
import { ApiProperty } from "@nestjs/swagger";
import { IsEmail, IsNotEmpty } from "class-validator";
import { RegisterUserDto } from "./register-user.dto";
import { IntersectionType, PartialType, PickType } from "@nestjs/mapped-types";

export class UpdateUserDto extends PickType(RegisterUserDto, ['email', 'captcha']){

    @ApiProperty()
    headPic: string;

    @ApiProperty()
    nickName: string;
}
```

把 frontend_user 跑起来，测试注册、修改密码、登录、修改个人信息，均无问题。

### captcha 一次性使用

现有验证码有个问题：发送了一个邮箱验证码之后，下次修改信息还可以用这个验证码——因为在 redis 里这个验证码会保存 10 分钟。应该用完一次就删掉。

在 RedisService 添加一个 del 方法：

```javascript
async del(key: string) {
    await this.redisClient.del(key);
}
```

更新完信息就调用它删掉验证码：

```javascript
@Post(['update', 'admin/update'])
@RequireLogin()
async update(@UserInfo('userId') userId: number, @Body() updateUserDto: UpdateUserDto) {
    const res = await this.userService.update(userId, updateUserDto);

    this.redisService.del(`update_user_captcha_${updateUserDto.email}`);

    return  res;
}
```

```javascript
@Post(['update_password', 'admin/update_password'])
async updatePassword(@Body() passwordDto: UpdateUserPasswordDto) {
    const res = await this.userService.updatePassword(passwordDto);

    this.redisService.del(`update_password_captcha_${passwordDto.email}`);

    return res;
}
```

测试后一个验证码就只能用一次了。不过提示信息不对——应该在状态码非 20x 的时候展示返回的错误信息：改一下 front_user 项目里 UpdateInfo 组件的 onFinish 处理即可；front_admin 项目里的 InfoModify 组件也要做同样的修改。

## 六、日志：nest-winston

### 为什么要日志框架

现在的日志都直接打印在 console 里，开发时没问题，但线上查日志时在 console 里找很不方便。所以要把日志保存在文件里，或者通过 http 发送到专门的日志服务器——winston 等日志框架就是做这个的。

nest 集成 winston 直接用 [nest-winston](https://www.npmjs.com/package/nest-winston) 这个包，没必要自己写。在 backend 项目里安装依赖：

```
npm install --save nest-winston winston
```

然后在 AppModule 引入：

```javascript
WinstonModule.forRootAsync({
  useFactory: () => ({
    level: 'debug',
    transports: [
      new winston.transports.File({
        filename: `${process.cwd()}/log`,
      }),
      new winston.transports.Console({
        format: winston.format.combine(
          winston.format.timestamp(),
          utilities.format.nestLike(),
        ),
      }),
    ],
  })
}),
```

指定日志输出级别是 debug，输出到的 transport 包括 console 和 file。然后把 winston 的 logger 设置为 Nest 的默认 Logger：

```javascript
app.useLogger(app.get(WINSTON_MODULE_NEST_PROVIDER));
```

跑一下：

```
npm run start:dev
```

除了 console 之外，log 文件中也输出了一份——两个 transport 都生效了。

### 让 typeorm 日志也进入 winston

页面刷新后会发现 typeorm 的日志并没有输出到文件，因为 TypeORM 有自己的 Logger，它也可以自定义。在 src 下新建 CustomTypeOrmLogger.ts：

```javascript
import { WinstonLogger } from 'nest-winston';
import { Logger, QueryRunner } from 'typeorm';

export class CustomTypeOrmLogger implements Logger {

    constructor(private winstonLogger: WinstonLogger) {

    }

    log(level: 'log' | 'info' | 'warn', message: any) {
        this.winstonLogger.log(message);
    }

    logQuery(query: string, parameters?: any[], queryRunner?: QueryRunner) {
        this.winstonLogger.log({
            sql: query,
            parameters
        });
    }

    logQueryError(error: string | Error, query: string, parameters?: any[], queryRunner?: QueryRunner) {
        this.winstonLogger.error({
            sql: query,
            parameters
        });
    }

    logQuerySlow(time: number, query: string, parameters?: any[], queryRunner?: QueryRunner) {
        this.winstonLogger.log({
            sql: query,
            parameters,
            time
        });
    }

    logSchemaBuild(message: string, queryRunner?: QueryRunner) {
        this.winstonLogger.log(message);
    }

    logMigration(message: string, queryRunner?: QueryRunner) {
        this.winstonLogger.log(message);
    }

}
```

实现 typeorm 的 Logger 接口的各方法即可：通过构造器传入 WinstonLogger，分别调用 log、error 等方法打印日志。然后在 TypeOrmModule 里使用它，console 和 file 里就有 typeorm 的日志了。

### 按日期分割日志

现在的日志都保存在单个文件里、不断追加，文件会越来越大，不好维护。改下 transport，换成按照日期分割日志的方案。安装用到的包：

```
npm install --save winston-daily-rotate-file
```

使用：

```javascript
new winston.transports.DailyRotateFile({
  level: 'debug',
  dirname: 'daily-log',
  filename: 'log-%DATE%.log',
  datePattern: 'YYYY-MM-DD',
  maxSize: '10k'
}),
```

指定目录为 daily-log、文件名格式和日期格式、文件最大大小 10k。多刷新几次页面可以看到产生了几个文件，每个都在 10k 左右；最重要的是它会自动按照日期分割——修改本地时间后刷新页面，日志被记录在了新的文件里。也就是说，日志按日期为维度分割，超过 maxSize 也会分割。查日志时找到当天的日期、在日志文件里搜索即可。

### 配置抽到 .env

把 winston 的配置也抽到 .env 里：

```javascript
winston_log_level=debug
winston_log_dirname=daily-log
winston_log_filename=log-%DATE%.log
winston_log_date_pattern=YYYY-MM-DD
winston_log_max_size=1M
```

然后在 WinstonModule 里读取：

```javascript
WinstonModule.forRootAsync({
  useFactory: (configService: ConfigService) => ({
    level: 'debug',
    transports: [
      new winston.transports.DailyRotateFile({
          level: configService.get('winston_log_level'),
          dirname: configService.get('winston_log_dirname'),
          filename: configService.get('winston_log_filename'),
          datePattern: configService.get('winston_log_date_pattern'),
          maxSize: configService.get('winston_log_max_size')
      }),
      new winston.transports.Console({
        format: winston.format.combine(
          winston.format.timestamp(),
          utilities.format.nestLike(),
        ),
      }),
    ],
  }),
  inject: [ConfigService]
}),
```

跑一下验证无问题，winston 集成成功。

## 七、前端优化

### 路由守卫

登录之后会在 localStorage 保存 access_token、refresh_token、user_info 的信息，然后进入会议室列表页。这些页面是登录后才能访问的，但现在没登录访问会议室列表页不会自动跳转登录页——只有点击其他页面时才跳转。原因：这些页面的接口需要登录，没登录访问返回 401，在响应拦截器里做了处理（返回 401 就跳转登录页）。

只在接口返回 401 时处理不够，应该在路由级别也做判断，即路由守卫。分析 frontend_user 的现有路由：需要登录的页面都会渲染 Index 组件，所以在 Index 组件里判断即可。之前有从 localStorage 里取 user_info 设置 headPic 的逻辑，加个 else 分支跳转登录页。测试：没有 user_info（未登录）时就会跳转登录页。

frontend_admin 项目同样修改：

```javascript
useEffect(()=> {
    const userInfo = localStorage.getItem('user_info');
    if(!userInfo) {
        window.location.href = "/login";
    }
}, []);
```

未登录时同样跳转登录页。

### useCallback 与 useMemo 的正确用法

前面代码里加了很多 useMemo 和 useCallback，其实很多是没必要的。创建测试项目验证：

```
npx create-vite test-memo
```

进入项目安装依赖并跑起开发服务：

```
npm install

npm run dev
```

去掉 main.tsx 里的 index.css 和 StrictMode，改 App.tsx：

```javascript
import { useEffect, useState } from 'react'

function Aaa(props: { text: string }) {
  console.log('Aaa render...');

  return <div>{props.text}</div>
}

function App() {
  const [num, setNum] = useState(0);

  useEffect(() => {
    setInterval(() => {
      setNum(num => num + 1);
    }, 1000);
  }, []);

  return <Aaa text="aaa"></Aaa>
}

export default App
```

App 组件里有一个定时器不断修改 state 触发重新渲染。这时 Aaa 每次都会重新渲染——但参数没变，Aaa 不需要重新渲染。这时可以用 memo：

```javascript
import { memo, useEffect, useState } from 'react'

function Aaa(props: { text: string }) {
  console.log('Aaa render...');

  return <div>{props.text}</div>
}

const MemoAaa = memo(Aaa);

function App() {
  const [num, setNum] = useState(0);

  useEffect(() => {
    setInterval(() => {
      setNum(num => num + 1);
    }, 1000);
  }, []);

  return <MemoAaa text="aaa"></MemoAaa>
}

export default App
```

现在 Aaa 只渲染一次：memo 会对比 props 和上次有没有变化，没变就不重新渲染。

如果加一个函数作为参数呢？

```javascript
import { memo, useEffect, useState } from 'react'

function Aaa(props: { text: string, callback: Function }) {
  console.log('Aaa render...');

  return <div>{props.text}</div>
}

const MemoAaa = memo(Aaa);

function App() {
  const [num, setNum] = useState(0);

  useEffect(() => {
    setInterval(() => {
      setNum(num => num + 1);
    }, 1000);
  }, []);

  return <MemoAaa text="aaa" callback={() => { console.log('xxx');}}></MemoAaa>
}

export default App
```

这时每次都会重新渲染：函数每次都变（参数每次都变），加了 memo 也没用。这时用 useCallback 解决——它只有依赖数组变化时才返回新的函数，否则一直返回同一个函数：

```javascript
import { memo, useCallback, useEffect, useState } from 'react'

function Aaa(props: { text: string, callback: Function }) {
  console.log('Aaa render...');

  return <div>{props.text}</div>
}

const MemoAaa = memo(Aaa);

function App() {
  const [num, setNum] = useState(0);

  useEffect(() => {
    setInterval(() => {
      setNum(num => num + 1);
    }, 1000);
  }, []);

  const callback = useCallback(() => {
    console.log('xxx');
  }, []);

  return <MemoAaa text="aaa" callback={callback}></MemoAaa>
}

export default App
```

现在又只渲染一次了。**结论：memo 和 useCallback、useMemo 是配合使用的，单独用 useCallback 没什么意义**，代码里多余的 useCallback 可以去掉。

## 九、项目回顾

### 项目概览

本项目综合运用了 Nest、MySQL、TypeORM、Docker & Docker Compose、Minio、passport 等技术，是一个会议室预订系统，分为用户端和管理端：

- 用户端登录之后可以查看可预订的会议室、预订会议室、查看预订历史等；
- 管理端则是用户、会议室、预订记录等的管理，还有统计分析。

这个实战案例的意义在于把学到的技术综合运用一遍。例如 Nginx——之前可能只知道它可以做反向代理、可以托管静态资源，但不清楚它在整个链路中的位置；通过编写 nginx 配置并部署到阿里云，就对它在请求链路里的角色有了实际的体会，理解更加深入和立体。

为了聚焦 Nest 和后端技术，前端部分尽量简化：界面都是用 antd 写的，没有复杂的样式，交互也比较单调（基本是表格、表单）。实际上，预订会议室的功能一般和日历结合（如 Google Calendar）：可以直观查看哪些时间段没有被预订、然后预订，而不是选一个时间段提交后才发现"该时间段已被预订"。前端交互可以自行完善，本项目的重点在后端部分。

### 开发流程回顾

**第一步：需求分析。** 分析有哪些功能、画原型图，分为用户管理、会议室管理、预订管理、统计 4 个模块——这一步明确"做什么"，最终做出来的系统也符合需求分析和原型图。

**第二步：技术方案与选型。** 设计数据库、分析接口。

**第三步：开发。** 按每个模块先写后端、再写前端的顺序开发（先用户模块后端再前端，再会议室模块后端再前端）：

- 创建后端项目，引入 typeorm 和 redis，实现用户注册；基于 @nestjs/config 包的 ConfigModule 把配置抽离到 .env 文件；
- 实现登录和双 token 的无感刷新；加上登录和权限的 Guard 做鉴权，通过 @RequireLogin、@RequirePermission 的自定义装饰器在 handler 上声明，只有声明的才做鉴权；
- 添加 interceptor 对响应格式做转换（改成 {code、message、data} 格式），并用 interceptor 实现接口访问日志记录；
- 实现修改信息、修改密码接口，userId 通过 @UserInfo 自定义装饰器从 request.user 取；
- 实现冻结用户和用户列表接口；通过自定义 exception filter 捕获 HttpException、返回自定义格式的响应，统一响应格式；加上 swagger 接口文档——用户管理模块后端完成；
- 写用户管理模块前端：React Router 做路由、antd 做 UI 组件库、axios 发请求，实现登录、注册、首页、修改密码、修改个人信息页面，并实现头像上传；
- 写管理端页面；然后分别实现会议室模块、预订模块、统计模块的后端代码和前端页面。

**第四步：部署。**

- 加上 docker-compose.yml 和 Nest 应用的 Dockerfile，部署到阿里云：买一台阿里云服务器，安装 git 下载项目代码，安装 docker compose，在项目目录执行 docker compose up 把服务跑起来——部署成功后服务可以在世界各地访问；
- 加上 nginx 部署前端项目，用它做静态资源托管和 nest 服务的反向代理。通过 Dockerfile 的多阶段构建：第一阶段 npm run build 出产物，第二阶段把产物和 nginx 配置文件复制过去跑 nginx 服务；用 docker build 构建出镜像并上传到阿里云镜像仓库；在 docker compose 配置文件里添加 nginx 容器配置，服务端用 docker compose up 一次性跑起 nginx、nest、mysql、redis 等容器，前后端服务一键启动。

**第五步：生产化与优化。**

- 生产环境关掉 synchronize，用 migration 创建表和初始化数据：加 migration 的 npm scripts，创建若干 migration，服务器上执行 migration:run 就会创建数据库表并插入初始化数据；
- 文件上传从基于 multer 保存在项目目录下，换成基于 minio 实现的 OSS 服务：前端直传 OSS、把文件 url 发给应用服务器，文件都保存在 minio 服务里，便于管理；
- 实现 google 登录：基于 passport 的 passport-google-oauth20 策略，callback 路由里基于 google 返回的信息自动注册（已注册则直接返回登录信息），并重定向到网站首页、通过 cookie 携带 userInfo、accessToken、refreshToken 等信息；前端处理 cookie、同步登录状态；
- 集成 winston 日志框架：日志在 console、file 打印，还可以发送到别的日志服务；
- 对代码做了一轮优化（多环境 .env、mapped-types 复用 dto、验证码一次性使用、路由守卫、memo/useCallback）。

### 结语

项目的具体形态不重要，重要的是把用到的技术融会贯通，理解一个全栈项目从需求分析、开发到部署的完整流程，并在自己的项目里把这些技术真正用起来。

# 中间件与依赖注入进阶

> **本篇做什么**：处理"每个请求都要做的事"——分清中间件（middleware）与依赖注入（Depends）各自的战场，实现 request_id 请求上下文、CORS 等内置中间件、全局异常处理、类依赖与 `BackgroundTasks` 后台任务。
> **产出**：一套带请求追踪、统一错误响应、跨域配置的 App 工厂式骨架，以及"后台任务何时升级到 Celery"的决策依据。
> **前置篇**：[01-FastAPI 入门与路由依赖](/docs/python/01-Web与爬虫/01-Web开发/04-FastAPI/01-FastAPI入门与路由依赖)（Depends 基础）、[04-认证与 JWT](/docs/python/01-Web与爬虫/01-Web开发/04-FastAPI/04-认证与JWT)（依赖链）。

## 先分清：中间件 vs 依赖注入

两者都能做"请求前处理"，但设计意图完全不同：

| 维度 | 中间件 Middleware | 依赖注入 Depends |
|---|---|---|
| 作用范围 | **全局**所有请求 | 精确到**声明了它的路由**（可全局、可路由级） |
| 能否读取路由签名 | 不能，只有原始 Request | 能，FastAPI 按签名解析参数 |
| 能否给路由函数传值 | 不能，只能改 request/response | 能，依赖返回值注入函数参数 |
| 能否短路请求 | 能，不调 `call_next` 直接返回 | 能，依赖抛 HTTPException 即中断 |
| OpenAPI 文档 | 不可见 | 自动进入文档（安全声明等） |
| 典型用途 | CORS、压缩、请求日志、追踪 ID | 鉴权、分页、数据库会话、权限校验 |

一句话原则：**中间件处理"HTTP 层"的事，依赖处理"业务层"的事**。鉴权逻辑写进中间件是常见反模式——中间件看不到路由声明，无法区分"哪些路由需要鉴权"。

```mermaid
flowchart LR
    A["请求"] --> B["中间件（洋葱外层）"]
    B --> C["依赖解析（按签名）"]
    C --> D["路径函数"]
    D --> E["中间件收尾处理"]
    E --> F["响应"]
```

## 自定义中间件与 request_id 上下文

最基本的中间件形态，用装饰器写法实现请求计时：

```python
import time
from fastapi import FastAPI, Request

app = FastAPI()


@app.middleware("http")
async def timing_middleware(request: Request, call_next):
    start = time.perf_counter()
    response = await call_next(request)          # 把请求传给内层
    cost_ms = (time.perf_counter() - start) * 1000
    response.headers["X-Process-Time-Ms"] = f"{cost_ms:.1f}"
    return response
```

### request_id：跨层追踪一个请求

排障时最需要的是"把同一个请求的日志串起来"。用 `contextvars` 存放请求级上下文，业务代码无感读取：

```python
import contextvars
import logging
from uuid import uuid4

request_id_var: contextvars.ContextVar[str] = contextvars.ContextVar("request_id", default="-")


@app.middleware("http")
async def request_id_middleware(request: Request, call_next):
    # 优先复用网关传来的追踪头，便于跨服务串联；否则生成
    rid = request.headers.get("X-Request-ID") or uuid4().hex
    token = request_id_var.set(rid)
    try:
        response = await call_next(request)
    finally:
        request_id_var.reset(token)              # 请求结束必须复位，防止上下文串线程
    response.headers["X-Request-ID"] = rid       # 返回给客户端，便于用户报障时提供
    return response


class RequestIdFilter(logging.Filter):
    """把 request_id 注入每条日志，配合格式化器 %(request_id)s 输出"""
    def filter(self, record: logging.LogRecord) -> bool:
        record.request_id = request_id_var.get()
        return True


logging_config = {
    "version": 1,
    "filters": {"request_id": {"()": RequestIdFilter}},
    "formatters": {
        "standard": {
            "format": "%(asctime)s [%(request_id)s] %(levelname)s %(name)s %(message)s"
        }
    },
    "handlers": {
        "console": {"class": "logging.StreamHandler", "filters": ["request_id"],
                    "formatter": "standard"},
    },
    "root": {"handlers": ["console"], "level": "INFO"},
}
```

日志体系的完整设计（dictConfig 分层、结构化日志、按级别输出）在本站 [01-日志系统](/docs/python/03-工程化与运维/02-运维/01-日志系统)中展开，本篇只负责把 `request_id` 从中间件送到日志层。

## 常用内置中间件

内置中间件通过 `add_middleware` 注册：

```python
from fastapi.middleware.cors import CORSMiddleware
from fastapi.middleware.gzip import GZipMiddleware
from fastapi.middleware.httpsredirect import HTTPSRedirectMiddleware
from fastapi.middleware.trustedhost import TrustedHostMiddleware

# CORS：浏览器跨域的关键配置
app.add_middleware(
    CORSMiddleware,
    allow_origins=["https://app.example.com"],  # 明确列出允许的源
    allow_credentials=True,                     # 允许携带 Cookie
    allow_methods=["GET", "POST", "PUT", "DELETE"],
    allow_headers=["Authorization", "Content-Type"],
    max_age=3600,                               # 预检请求缓存时间
)

# GZip：大响应自动压缩
app.add_middleware(GZipMiddleware, minimum_size=1024)

# 强制 HTTPS：HTTP 请求 307 跳转（生产配反代时通常由 Nginx 承担）
app.add_middleware(HTTPSRedirectMiddleware)

# 主机白名单：防御 Host 头注入
app.add_middleware(TrustedHostMiddleware, allowed_hosts=["example.com", "*.example.com"])
```

::: warning CORS 的两个高频错误
1. `allow_origins=["*"]` 与 `allow_credentials=True` **不能同时生效**——规范规定带凭证的请求必须明确列出来源。开发期想图省事写 `*`，上生产要改成真实域名列表。
2. 生产环境 CORS 应由配置注入（域名列表来自 Settings），而不是硬编码。配置分层见本站 [07-配置管理](/docs/python/03-工程化与运维/01-工程化/07-配置管理)。
:::

## 全局异常处理

业务异常不要散落在每个路由里 try/except，注册全局处理器统一转响应：

```python
from fastapi import FastAPI, Request, status
from fastapi.exceptions import RequestValidationError
from fastapi.responses import JSONResponse

app = FastAPI()


# 1. 自定义业务异常 + 统一错误码
class BizError(Exception):
    def __init__(self, code: str, message: str, http_status: int = 400):
        self.code = code
        self.message = message
        self.http_status = http_status


@app.exception_handler(BizError)
async def biz_error_handler(request: Request, exc: BizError):
    return JSONResponse(
        status_code=exc.http_status,
        content={"code": exc.code, "message": exc.message,
                 "request_id": request_id_var.get()},
    )


# 业务代码里随处可抛，不必关心 HTTP 细节
# raise BizError("ORDER_EXPIRED", "订单已过期，无法支付")


# 2. 改写 422 的默认格式：统一错误结构，方便前端集中处理
@app.exception_handler(RequestValidationError)
async def validation_error_handler(request: Request, exc: RequestValidationError):
    return JSONResponse(
        status_code=status.HTTP_422_UNPROCESSABLE_ENTITY,
        content={"code": "VALIDATION_ERROR",
                 "message": "参数校验失败",
                 "details": exc.errors()},
    )
```

::: tip 兜底 500 也要接管
再注册一个 `Exception` 处理器兜底所有未捕获异常：记录完整堆栈（带 `request_id`），对外只返回"服务器内部错误"。**把堆栈回给客户端等于把实现细节交给攻击者**。
:::

## 依赖注入进阶

### 类依赖

依赖不必是函数，类同样可以——`__init__` 的参数列表就是参数声明：

```python
from dataclasses import dataclass
from typing import Annotated

from fastapi import Depends, Query


@dataclass
class Paginator:
    """类依赖：分页参数收敛成一个可复用对象"""
    skip: int = Query(0, ge=0)
    limit: int = Query(20, le=100)

    @property
    def offset(self) -> int:
        return self.skip


@app.get("/items/")
async def list_items(page: Annotated[Paginator, Depends()]):
    # Depends() 不写参数时自动用类型标注的类
    return {"skip": page.skip, "limit": page.limit}
```

### 依赖缓存与 use_cache

同一请求内，FastAPI 对每个依赖**只求值一次**（默认 `use_cache=True`），这对"查库的依赖"是天然优化：

```python
async def expensive_config() -> dict:
    ...

@app.get("/a/")
async def a(cfg: Annotated[dict, Depends(expensive_config)],
            other: Annotated[dict, Depends(expensive_config)]):
    # expensive_config 只执行一次，两处拿到同一结果
    ...
```

需要"每次都重新执行"的依赖（如随机值、时间戳），声明时关闭缓存：

```python
from fastapi import Depends

def request_nonce() -> str:
    import uuid
    return uuid.uuid4().hex

Nonce = Annotated[str, Depends(request_nonce, use_cache=False)]
```

### 全局依赖与路由组依赖

```python
from fastapi import Depends, FastAPI, APIRouter

# 全局：所有请求都执行（如统计埋点、基础限流）
app = FastAPI(dependencies=[Depends(track_request)])

# 路由组：整组接口统一鉴权，函数体无需重复声明
admin_router = APIRouter(
    prefix="/admin",
    tags=["admin"],
    dependencies=[Depends(get_current_admin)],
)

@admin_router.get("/stats")
async def admin_stats():
    return {...}   # 走到这里必然已通过鉴权
```

`dependencies=[...]` 列表里的依赖只执行、不注入返回值，适合"纯拦截"场景。

### yield 依赖的异常语义

`yield` 依赖中，yield 之前的代码在路由执行**前**运行，之后的代码在响应完成后运行；`try/except` 能捕获路由内抛出的异常：

```python
async def get_session():
    async with SessionLocal() as session:
        try:
            yield session
        except Exception:
            await session.rollback()   # 路由内抛异常时：回滚事务
            raise                      # 继续抛出，交给全局异常处理器
```

::: warning yield 依赖后段拿不到响应体
`yield` 之后的清理代码在响应发送后执行，无法修改响应。要给响应统一加头（如 request_id），用中间件；要保证资源释放（连接、事务），用 yield 依赖。职责不要颠倒。
:::

## 后台任务 BackgroundTasks

响应返回**之后**执行的轻量任务，适合发通知、写审计日志这类"不阻塞响应、丢了也不致命"的工作：

```python
from fastapi import BackgroundTasks, FastAPI
from pydantic import BaseModel, EmailStr

app = FastAPI()


async def send_welcome_email(email: EmailStr) -> None:
    await mailer.send(to=email, subject="欢迎注册", body="...")

async def write_audit_log(user_id: int, action: str) -> None:
    await audit.record(user_id=user_id, action=action)


class SignupIn(BaseModel):
    email: EmailStr
    username: str


@app.post("/signup/", status_code=201)
async def signup(payload: SignupIn, background_tasks: BackgroundTasks):
    user = await create_user(payload)
    background_tasks.add_task(send_welcome_email, payload.email)
    background_tasks.add_task(write_audit_log, user.id, "signup")
    return {"id": user.id}        # 响应立即返回，任务在响应后执行
```

### 何时换 Celery

`BackgroundTasks` 跑在**进程内的事件循环**上，没有持久化、没有重试、没有独立扩缩容。决策依据：

| 特性 | BackgroundTasks | Celery / RQ / Dramatiq |
|---|---|---|
| 执行位置 | 当前进程 | 独立 worker 进程/机器 |
| 进程重启后 | 任务丢失 | 队列持久化，可恢复 |
| 失败重试 | 手动实现 | 内置重试/死信队列 |
| 任务可见性 | 无 | 队列深度、成功率可监控 |
| 适用任务 | 秒级、可丢失：发通知、清缓存 | 分钟级、必须成功：视频转码、对账、批量导入 |

经验法则：**任务失败会让用户投诉的，一律上独立任务队列**；"尽力而为"的才用 BackgroundTasks。

## 常见陷阱

| 陷阱 | 现象 | 正确做法 |
|---|---|---|
| 用中间件做鉴权 | 无法按路由控制，文档不显示鉴权 | 鉴权交给依赖，中间件只管 HTTP 层 |
| CORS 写 `*` + credentials | 浏览器拒绝带凭证跨域请求 | 列出明确域名 |
| 全局异常处理器把堆栈返给客户端 | 泄漏实现细节 | 对外统一文案，堆栈进日志 |
| BackgroundTasks 跑重任务 | 占住 worker，影响所有请求 | 重任务上独立任务队列 |
| 忘记 reset ContextVar | 请求上下文串到下一个请求 | 中间件 finally 中复位 |
| 依赖里开缓存又依赖可变状态 | 同请求内拿到"过期"值 | `use_cache=False` 或拆分依赖 |

## 小结

- 中间件管 HTTP 层（全局、能短路、能给响应加头），依赖管业务层（按签名解析、进文档、可传值）。
- `contextvars` + 中间件是 request_id 追踪的标准实现，日志接入见日志系统篇。
- CORS/HTTPSRedirect/GZip/TrustedHost 用 `add_middleware` 注册，CORS 域名要显式且可配置。
- 全局异常处理器统一错误响应：业务异常转错误码，422 重写格式，兜底 500 不漏堆栈。
- 类依赖、依赖缓存、路由组依赖让横切逻辑可组合；BackgroundTasks 只做"可丢失"的轻任务。

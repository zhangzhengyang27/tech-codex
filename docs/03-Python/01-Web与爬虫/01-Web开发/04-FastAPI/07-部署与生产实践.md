## 运行时：uvicorn 与 gunicorn 的选型

FastAPI 是 ASGI 应用，必须由 ASGI 服务器承载。两种主流组织方式：

```bash
# 方式一：uvicorn 自管多 worker
uvicorn app.main:app --host 0.0.0.0 --port 8000 --workers 4

# 方式二：gunicorn 做进程管理，每个 worker 内跑 uvicorn 事件循环
gunicorn app.main:app -k uvicorn.workers.UvicornWorker -w 4 -b 0.0.0.0:8000
```

选择依据：

- **单容器少量 worker**：`uvicorn --workers` 足够，配置面小，容器场景（1 容器 1 进程组）最常用。
- **需要进程管理能力**：gunicorn 提供 `preload`（共享只读内存）、`--max-requests`（worker 定期重启防内存泄漏）、更成熟的慢速重启容忍。长生命周期大服务的稳妥选择。
- **容器编排环境（K8s）**：更常见的是 **1 容器 1 worker**，副本数交给编排平台水平扩缩——worker 调优从进程层上移到了 Pod 层。

worker 数量公式（CPU 密集与 I/O 密集的权衡）与优雅关闭参数（`--timeout-graceful-shutdown`）的细节讨论见 [部署与运行](/docs/python/03-工程化与运维/02-运维/03-部署与运行)，此处只强调 FastAPI 特有的一条：

::: warning 多 worker 与全局状态
每个 worker 是**独立进程**，内存不共享。进程内的字典缓存、计数器、单例在各 worker 各有一份，且互不可见。需要跨请求/跨 worker 共享的状态放 Redis 或数据库；进程内只放只读配置和连接池。
:::

## lifespan：启动与关闭钩子

连接池、Redis 客户端等"全局资源"的初始化与销毁，现代写法是 `lifespan` 上下文管理器（替代已过时的 `@app.on_event`）：

```python
# app/main.py
from contextlib import asynccontextmanager

from fastapi import FastAPI

from app.database import engine
from app.cache import redis_client


@asynccontextmanager
async def lifespan(app: FastAPI):
    # ---- 启动阶段：在接收第一个请求之前执行 ----
    app.state.ready = False
    await redis_client.ping()          # 提前发现依赖故障，快速失败
    app.state.ready = True
    yield
    # ---- 关闭阶段：收到 SIGTERM、排空请求后执行 ----
    app.state.ready = False
    await engine.dispose()             # 归还并关闭连接池
    await redis_client.aclose()


app = FastAPI(lifespan=lifespan)
```

注意三点：

1. **多 worker 下 lifespan 每个 worker 各执行一次**，连接池等资源本来就是进程级的，正好对齐。
2. 启动阶段失败（如 Redis 连不上）应抛异常让进程退出，交给重启策略处理，不要"带着坏依赖裸奔"。
3. Alembic 迁移在**部署流程**中独立执行（发布前 `alembic upgrade head`），不要放进 lifespan——多 worker 同时迁移必然竞争。

## Docker 多阶段构建

目标是：镜像小、无构建工具残留、非 root 运行、层缓存友好。

```dockerfile
# ---- 构建阶段：装依赖 ----
FROM python:3.12-slim AS builder

WORKDIR /app
ENV PYTHONDONTWRITEBYTECODE=1 \
    PYTHONUNBUFFERED=1

# 先只复制依赖清单再安装，命中层缓存：代码改动不触发重装
COPY pyproject.toml uv.lock ./
RUN pip install --no-cache-dir uv && uv sync --frozen --no-dev

# ---- 运行阶段：只带运行产物 ----
FROM python:3.12-slim

WORKDIR /app
ENV PYTHONDONTWRITEBYTECODE=1 \
    PYTHONUNBUFFERED=1

# 只搬虚拟环境，不带 pip/uv 和编译工具链
COPY --from=builder /app/.venv /app/.venv
COPY app ./app

# 非 root 运行
RUN useradd --create-home appuser && chown -R appuser /app
USER appuser

EXPOSE 8000

HEALTHCHECK --interval=30s --timeout=3s --retries=3 \
  CMD python -c "import urllib.request; urllib.request.urlopen('http://127.0.0.1:8000/healthz')"

CMD ["uvicorn", "app.main:app", "--host", "0.0.0.0", "--port", "8000"]
```

要点：

- 依赖清单先行复制，代码改动不触发依赖重装，构建时间从分钟级回到秒级。
- `--no-dev` / `--frozen` 保证镜像里是锁定的生产依赖集合，锁文件与依赖策略见 [依赖管理](/docs/python/03-工程化与运维/01-工程化/04-依赖管理)。
- 密钥**绝不进镜像**：没有 `COPY .env`，没有 `ENV SECRET_KEY=...`，运行时通过环境注入，见 [配置管理](/docs/python/03-工程化与运维/01-工程化/07-配置管理)。
- 容器内的 worker 数：1 容器 1 worker，副本交给编排；确需多 worker 时容器内存/CPU 配额要按 worker 数倍增。

```bash
docker build -t myapp:latest .
docker run -p 8000:8000 \
  -e DATABASE_URL="postgresql+asyncpg://app:secret@db:5432/app" \
  -e SECRET_KEY="$(openssl rand -hex 32)" \
  myapp:latest
```

## 健康检查：/healthz 与 /readyz

把"进程活着"和"依赖就绪"分成两个端点，编排平台才能正确决策：

```python
from fastapi import APIRouter, Response, status
from sqlalchemy import text

router = APIRouter(tags=["ops"])


@router.get("/healthz")
async def liveness():
    """存活探针：进程能响应即返回 200，不检查任何依赖。
    这里失败 => 容器重启。绝不能查数据库——数据库抖动会导致雪崩式重启。"""
    return {"status": "ok"}


@router.get("/readyz")
async def readiness(response: Response, session: SessionDep):
    """就绪探针：依赖可用才返回 200。
    这里失败 => 从负载均衡摘除流量，但不重启容器。"""
    try:
        await session.execute(text("SELECT 1"))
    except Exception:
        response.status_code = status.HTTP_503_SERVICE_UNAVAILABLE
        return {"status": "db not ready"}
    return {"status": "ready"}
```

| 端点 | 语义 | 探针类型 | 失败后果 |
|---|---|---|---|
| `/healthz` | 进程存活 | liveness | 重启容器 |
| `/readyz` | 依赖就绪 | readiness | 摘除流量 |

配对使用才安全：只有 liveness 时，数据库故障会被误判成"应用挂了"引发重启风暴；只有 readiness 时，死锁进程永远不会被重启。K8s 探针参数（`initialDelaySeconds`、`failureThreshold`）与 Docker Compose 的 `depends_on: condition: service_healthy` 写法见 [部署与运行](/docs/python/03-工程化与运维/02-运维/03-部署与运行)。

## 配置与监控的接入点

### 配置

应用的 Settings 类用 Pydantic Settings 定义，`lifespan` 前实例化即完成启动时校验：

```python
from pydantic_settings import BaseSettings, SettingsConfigDict


class Settings(BaseSettings):
    model_config = SettingsConfigDict(env_file=".env", extra="ignore")

    database_url: str = "postgresql+asyncpg://postgres:secret@localhost:5432/app"
    secret_key: str                     # 必填：缺失即启动失败，问题暴露在最前面
    log_level: str = "INFO"


settings = Settings()
```

环境分层、密钥管理、`.env.example` 约定全部沿用 [07-配置管理](/docs/python/03-工程化与运维/01-工程化/07-配置管理)，本篇不重复。

### 监控

FastAPI 的接入点是中间件——在 HTTP 层统一埋点：

```python
import time
from prometheus_client import Counter, Histogram

REQUEST_COUNT = Counter(
    "http_requests_total", "Total HTTP requests", ["method", "endpoint", "status"]
)
REQUEST_LATENCY = Histogram(
    "http_request_duration_seconds", "HTTP request latency", ["method", "endpoint"]
)


@app.middleware("http")
async def metrics_middleware(request, call_next):
    start = time.perf_counter()
    response = await call_next(request)
    route = request.scope.get("route")
    # 用路由模板而非原始路径，避免高基数标签（每个 /items/123 一个标签会撑爆时序库）
    endpoint = route.path if route else request.url.path
    REQUEST_COUNT.labels(request.method, endpoint, response.status_code).inc()
    REQUEST_LATENCY.labels(request.method, endpoint).observe(time.perf_counter() - start)
    return response
```

指标选型、Grafana 面板、OpenTelemetry 链路追踪与告警信号设计见 [02-监控与可观测性](/docs/python/03-工程化与运维/02-运维/02-监控与可观测性)；日志侧的 request_id 贯通见 [05-中间件与依赖注入进阶](/docs/python/01-Web与爬虫/01-Web开发/04-FastAPI/05-中间件与依赖注入进阶) 与 [01-日志系统](/docs/python/03-工程化与运维/02-运维/01-日志系统)。

## 上线前清单

| 检查项 | 标准 |
|---|---|
| 关闭开发特性 | 无 `--reload`、`echo=False`、文档端点按需限流或关闭 |
| worker 与资源 | worker 数 × 容器配额核算过；内存限制配合 `--max-requests` 防泄漏 |
| 数据库 | 连接池总量 ≤ 数据库上限；迁移在部署流程中独立执行且向后兼容 |
| 密钥 | 全部环境变量/密钥服务注入，镜像与仓库中无明文 |
| 健康检查 | `/healthz` 与 `/readyz` 分离，探针接入编排平台 |
| 可观测性 | 日志带 request_id、指标暴露 /metrics、告警阈值已配置 |
| 回滚预案 | 镜像标签可回退，迁移脚本可 downgrade |
| 压测 | 核心接口经过压测，QPS/P99 有基线数据 |

## 常见陷阱

| 陷阱 | 后果 | 正确做法 |
|---|---|---|
| 生产开 `--reload` | 资源浪费、行为不可预测 | reload 仅限开发 |
| 镜像里打包 .env | 密钥随镜像泄漏 | 环境变量运行时注入 |
| 单容器塞满 worker 又限 1 核 | worker 抢占 CPU，延迟抖动 | worker 数与配额匹配 |
| healthz 里查数据库 | 依赖抖动引发重启风暴 | 存活与就绪探针分离 |
| 迁移放进 lifespan | 多 worker 竞争执行迁移 | 部署流程中独立跑 Alembic |
| 指标标签用原始路径 | 高基数标签拖垮 Prometheus | 用路由模板作为标签 |
| lifespan 里不 dispose 引擎 | 滚动更新时连接堆积 | 关闭阶段显式释放资源 |

## 小结

- 运行时选型：容器场景 `uvicorn --workers` 起步，需要进程管理能力时用 gunicorn + UvicornWorker；K8s 优先 1 容器 1 worker + 水平扩缩。
- 全局资源在 `lifespan` 里初始化与销毁，启动失败快速退出，关闭时 `dispose` 连接池。
- 多阶段 Dockerfile：依赖层缓存、运行层精简、非 root、密钥不进镜像。
- `/healthz` 管"活没活"，`/readyz` 管"能不能用"，分离探针避免重启风暴。
- 配置、监控、日志、进程模型都是站内已有专题，本篇只负责把 FastAPI 的接入点接上去。

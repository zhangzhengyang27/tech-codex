# 分析流程：业务数据分析的通用流程

> 本篇结合"在线教育 App 如何提升 A 课程销量"案例,讲解业务数据分析的通用流程:2W1H 模型(是什么→为什么→怎么办),其中"为什么"细分为分析目的、表面原因、根本原因三层。适合面对复杂业务问题时想抓住分析重点、快速梳理思路的数据分析师。相关主题:[定义问题](10-定义问题：怎么定义问题，打通分析思路？.md)、[拆解问题](11-拆解问题：为什么总是拆解出一堆没用的数据？.md)。

**案例背景**:假设你是一家在线教育 App 的数据分析师,领导让你分析如何提升 A 课程的销量,你会怎么思考及落地?

在给出答案之前,先看解决问题的一般流程。

## 通用的解决问题的流程

几乎所有问题的解决思路都可以用 2W1H 模型,分别是:

- What,是什么;

- Why,为什么;

- How,怎么办。

这个模型之所以通用,是因为只有知道问题是什么,才能分析为什么;也只有分析出了为什么,才能知道该怎么办。

::: tip 通用模型的边界
2W1H 的优点是通用,缺点也是太通用:通用的模型适合大多数情况,所以没有太多细节。要把它具体应用到业务数据分析领域,还需要做一些改造,才能成为数据分析常规流程的专用模型——下文即按改造后的流程展开。
:::

## What：是什么

"是什么"是业务数据分析最基础的问题:**要解决的问题是什么**?领导问"如何提升 A 课程的销量",这个问题可以简单拆分一下。

**首先是"如何提升"。** 这意味着最后分析出的结果应该是一些落地方案。什么是落地方案?方案包括改进的落地措施、负责人、时间等。比如分析完之后建议某渠道的投放资金提高 30%,预计可以带来 10 万的销售额,这就很好地回答了"如何提升"。如果没有具体的落地方案,只说"加大渠道投放",那么这么多渠道,投哪个?投多少?没交代清楚,就不算完整地回答"如何提升"。

**然后是"销量"。** "销量"的定义似乎不清晰:到底是按人算,还是按钱算?问题中的词语必须搞清楚定义,避免歧义一错再错。假设案例里是按钱算,问题就变成了"如何提升 A 课程的销售额"。经过简单梳理,"是什么"这个问题就清楚多了。

在"是什么"这一环节,一定要搞清楚问题是什么。很多分析还没搞清楚问题就草草给领导报几个数,说哪几个数高了、哪几个数低了——这属于答非所问:问的是如何提升,答的却是转化率很低,不被质疑才怪。

"是什么"虽然简单,但非常重要——**认清问题是成功的一半**。如何精准定义问题,见[《定义问题》](10-定义问题：怎么定义问题，打通分析思路？.md)。

## Why：为什么

"为什么"这一环节比较复杂,可以拆分成三个问题:

- 为什么要分析这个问题?

- 问题的表面原因是什么?

- 问题的根本原因是什么?

### 1. 为什么要分析这个问题？

知道了问题是什么——如何提升 A 课程的销售额——还不能急着分析,要先搞清楚:**为什么要分析这个问题**,也就是了解领导希望分析这个问题的目的。

"就是要提升 A 课程的销售额"只是表面目的,还有深层次的目的需要挖掘。比如领导的目的是想短期冲一波业绩,还是希望细细打磨产品?如果是短期冲业绩,而分析却以打磨产品的心态进行,提出一堆效果好但见效慢的建议;或者领导想打磨产品,分析却提出短期见效但有长期隐患的建议——虽然都解决了"如何提升销售额"这个表面问题,但没搞清楚根本问题,分析结果自然不受待见。

这个案例里,假设领导想要的是打磨产品,提升产品自身的转化能力(短期见效的建议相对容易,比如降价促销、活动运营,业务人员凭经验就能完成)。

搞清楚分析的目的还有两个作用:

- **评估分析的价值,调整需求的优先顺序**。数据分析师的精力有限,手上有很多工作,做了 A 课程的销售分析,就没法同时做 B 课程的销售分析、产品留存分析、路径分析等,必须清楚要分析的问题重不重要,是优先做还是等有空再做;

- **搞清楚问题的价值,比用什么分析方法更重要**。如果公司现金流紧张急需变现:一个分析师得出初步结论——变现过程中 A 产品有较大潜力;另一个分析师完成了深度分析,给出提升流失用户召回的 N 种落地方案。前者只是给了一个大概方向,但明显业务价值更大。**有价值的初步结论,远好于没有价值的深入结论。**

### 2. 问题的表面原因是什么？

什么是表面原因,什么是根本原因?肚子疼,医生检查之后确定是胃疼,"胃疼"就是表面原因;知道胃疼还不足以治疗,还要知道为什么胃疼,导致胃疼的病因才是根本原因。

在业务数据分析中,表面原因可以理解为**问题集中在哪个业务环节**。

落实到案例,先看整个用户转化路径。假设 A 课程的用户转化路径如下:

- 用户看到投放的广告;

- 用户进入广告推广落地页;

- 用户在落地页点击购买;

- 用户付费成功。

当然销售额的来源不止这一种途径,比如用户可以直接去 AppStore 下载并购买课程,或者通过老用户转介绍购买。为了便于理解分析思路,假设销售额的来源只有用户看到投放广告购买这一种途径。

找出表面原因最常用的方法是细分:把问题按照不同的维度细分,然后对比找出问题最大的细分项。

- **按并列关系拆分**:比如 A 课程的销售额,可以按渠道、用户类型、时段等不同维度拆分。按渠道拆分时,不同渠道销售额相加之和就是总销售额;

- **按用户购买路径拆分**:把 A 课程的销售额拆分成转化链路——广告曝光、广告点击、进入落地页、点击购买、支付成功,这就是漏斗转化分析,最后支付成功的金额就是总销售额。

一般来说,即使通过并列关系拆分找到了问题点,也要继续按用户转化路径拆分出不同的业务环节:比如发现 C 渠道的销售额最低,还要继续按用户转化路径拆分,看 C 渠道的转化过程中哪一步有问题。

假设通过漏斗分析,发现用户看完落地页后点击购买的转化率比较低,就可以得出结论——销售额低是因为落地页的转化率不高。很多分析到这里就把建议也想好了:"提高落地页的转化率"。

::: warning 表面原因不等于答案
找到表面原因只能缩小问题范围,没法得出落地方案,这种结论很容易被领导评价为"分析不够深入"。想继续深挖却想不出分析方向,通常是因为不懂业务、不懂用户——要分析得深入,必须找到根本原因。
:::

### 3. 问题的根本原因是什么？

业务数据分析中的根本原因,可以理解为**用户想要什么**。这要用到[《懂用户》](08-懂用户：数据分析+用户思维=精细化运营.md)中用户购买决策模型的知识:用户在做出购买决策前,有一连串需要满足的需求——产生兴趣、收集信息、评估价值、做出决策。

上一步梳理出的四个环节只是为了承接用户的一连串需求,并不是需求本身:用户本身并没有"进入落地页"这样一个需求,进入落地页只是为了满足"收集信息"和"评估价值"的需求。

上一步发现落地页转化率偏低,那么用户在这一步想要得到什么?结合业务理解,合理的推断是:用户进入落地页是为了获得更多的课程信息。

那么,用户在获取课程信息时会因为哪些问题放弃购买?可以假设以下情况:

- 落地页的信息和广告里提到的不一样:广告里写着"数据分析培训课",用户进来发现是"财务数据分析",很快就走了;

- 落地页的信息排版很不清楚,有用的信息很难找,用户看了一会儿没看懂,失去兴趣就走了;

- 用户觉得课程还不错,但价格太贵就走了。

这些都是用户需求层面的假设,可以用用户的行为数据定位大概的问题方向。

假设通过行为数据发现,转化率低的根本原因是:用户对课程主题感兴趣,但是课程介绍不适合自己。后续的改版方向也就呼之欲出。

::: tip 如何提出假设
- 站在用户的角度体验一次销售流程,就能提出很多猜想;
- 找同事一起讨论可能的情况——自己本身也是用户,自己的感受很重要;
- 笨办法:把用户在落地页上的行为日志全部拉出来逐个看,看几十上百个用户的行为,基本可以归纳出一些特点,再用所有用户的行为数据验证这些特点是否普遍。
:::

::: warning 数据采集是前提
通过数据分析找到根本原因,对数据采集的要求很高。比如"用户屏幕是否滑动到价格信息"这样的数据,没有提前设计很难办到。如果业务在这块比较缺失,要想着如何完善数据采集,而不是对着现有数据绞尽脑汁——巧妇难为无米之炊,没有行为数据,很难找到根本原因。
:::

## How：怎么办

最后一步是"怎么办",对数据分析师来说,就是给出具体的落地方案。

先汇总案例的分析结论:你是这家在线教育 App 的数据分析师,领导想让你分析"如何提升 A 课程的销售额"。通过分析发现,目前销售额不高主要是由于落地页转化效率不高,而转化效率不高的原因大概率是:用户虽然对课程主题感兴趣,但在落地页没看到感兴趣的课程内容。

找解决方案的方法,可以先看问题解决之后是什么状态:用户在落地页转化率低的根本原因,是用户对课程主题有兴趣但课程介绍无法打动用户;那么问题解决之后的状态应该是——**用户看到了自己感兴趣的内容**。

把优化好之后的状态按"主谓宾"拆分:

- 主语:用户

- 谓语:看到

- 宾语:感兴趣的内容

这样就得到三种建议方向。

**主语"用户"**:之前的结论是课程介绍无法打动用户,那么会不会是用户群体找错了?卖数据分析思维的课程,是不是投放给了想学习数据分析技术的群体?

**谓语"看到"**:用户花了时间阅读落地页的内容最后还是走了,会不会是原本的页面设计太复杂、关键信息找不到?把核心卖点做得更加醒目、更方便用户看到,也是一个办法。

**宾语"感兴趣的内容"**:用户对课程主题有兴趣,但课程内容的介绍似乎不满足需求。优化可以分两类:

- 第一类,在原课程中发掘更多的卖点;

- 第二类,在课程主题下开发新的课程。

至于用户到底想学习哪一个细分知识,可以依靠 A/B 测试,也可以让用户调研人员进行用户访谈,收集用户的真实反馈。

最后整理成"谁,在什么时间,做什么事"结构的解决方案:

给出这样有理有据、条理清晰、能马上落地的建议,领导就不会再说分析"不够深入"。

## 小结

遇到业务问题时,按以下 5 个问题组织分析思路即可:

- 要解决的问题是什么?(What)

- 为什么要分析这个问题?(Why 之一)

- 问题的表面原因是什么?(Why 之二,详见[《拆解问题》](11-拆解问题：为什么总是拆解出一堆没用的数据？.md))

- 问题的根本原因是什么?(Why 之三,详见[《找出原因》](12-找出原因：问题原因那么多，哪条才是最关键.md))

- 要解决问题该怎么办?(How,详见[《提出建议》](13-提出建议：什么才是有价值的建议？.md))

# 拆解问题：为什么总是拆解出一堆没用的数据？

> 本篇讲解分析问题阶段的第一步——拆解问题:明确拆解的目标是找出表面原因,并给出"排除数据错误→缩小问题范围→找出具体环节"的三步拆解方法,回答"拆什么、怎么拆、拆到什么程度"。适合拆解问题总是没有章法、拆出一堆无用数据的数据分析师。相关主题:[指标思维](04-指标思维：如何搞清楚各种不同的指标类型.md)、[系统结构](06-系统结构：跳出问题看问题，让你的分析直击关键.md)。

定义问题解决了"是什么"(见[《定义问题》](10-定义问题：怎么定义问题，打通分析思路？.md)),接下来就要开始分析问题,解决"为什么"。找"为什么"的第一步是找出表面原因,这就需要先拆解问题。

拆解问题看起来很简单:把问题用结构化思维拆解成小问题,发现问题集中在某一个特定的小问题上,就大功告成。这种想法很常见,因为很少有资料细说过拆解问题的核心思路。

许多资料在讲"多维度分析"时,只给出一个现成案例:作者看似随意地选择几个维度拆分问题,分析结果就出现了,非常神奇。轮到自己拆解时,选了 N 种维度却得不到想要的结果。原因在于:案例只演示了"这样拆可以得出分析结果",没解释为什么要这么拆、为什么要选这几个维度。

## 拆解问题的目标究竟是什么

首先,很多分析师不清楚拆解问题要拆到什么程度,拆分时没什么章法:先选几个维度拆分一下,看看有没有什么特点,根据特点思考有没有新的假设,再根据假设拆分一个新的维度。一会儿拆分业务指标,一会儿拆分用户的类型,一会儿拆分行为特点,看起来逻辑有条理,但整个思考过程没有规划,走一步算一步,本质上完全在碰运气。

这是非常普遍的问题,也不能全怪新人:确实很少有资料教这个知识。这些人只知道拿到分析需求之后要拆解问题,就直接开始拆解了,并不了解拆解问题究竟要拆什么、拆到什么程度。

所以在拆解问题之前,一定要搞清楚拆解的目标到底是什么。分析问题的步骤可以拆分成两步:

- 找出表面原因;

- 找出根本原因。

用例子说明两者的区别。

**表面原因**,可以理解成能用指标体系找出的原因。比如销售额下降了,表面原因可以是:

- 某个具体的群体、渠道、产品等维度下的销售额下降;

- 还可以深挖,找出 A 渠道的 B 产品销售额下降,这个表面原因范围更小、更加精准;

- 也可以是 A 渠道的用户人数下降——用户人数是销售额的子指标,依然在指标体系范围之内;

- 甚至是通过过程指标拆分出的 A 渠道的拉新落地页转化率降低,这依然是表面原因。

在找出"A 渠道的拉新落地页转化率降低"这一表面原因之后,会想知道"为什么 A 渠道的拉新落地页转化率会降低?"这个问题的回答就是根本原因。

**根本原因**,是不能用指标体系找出的原因。比如上面那个问题,可能是因为 A 渠道的拉新落地页上某个图片突然不显示了。这种原因在设计指标体系时是想不到的——每一个业务问题最终的根本原因千奇百怪,没办法为这些千奇百怪的原因设定指标。找出根本原因比表面原因更复杂,需要结合实际业务情况提出假设,见[《找出原因》](12-找出原因：问题原因那么多，哪条才是最关键.md)。

::: tip 明确目标,避免乱拆
**拆解问题的目标,就是找出表面原因。** 了解了这个目标,就能避免按奇怪的维度拆解,比如"按用户是否使用过某功能拆解,看使用功能是否会影响转化率"——这种拆解已经属于找根本原因的范畴,在找到表面原因之前,不要急着拆这些非常个性化的维度。
:::

## 具体拆解方法

拆解问题分三步:排除数据错误、缩小问题范围、找出具体环节。

### 第一步 排除数据错误

如果数据和预想的差别很大,或者几个不同指标的数据交叉比对后发现有明显错误,就要怀疑是不是数据本身出了问题。这种情况并不常见,但必须有这个意识,否则做了几天的分析,最后发现原来是数据错了。

**数据的产生是一个相对固定的流程,排除数据错误可以顺着这个流程找原因。** 一般数据通过客户端采集,传输到服务端,服务端清洗后保存在本地数据库,再从数据库清洗入库到数据仓库。流程中可能的问题点有:

- **客户端问题**:排查客户端版本、机型等,排查版本问题、机型适配问题;

- **服务端问题**:排查不同服务端的日志数量,看是否某个服务器出现了问题;

- **数据仓库问题**:排查服务端日志和数据仓库的日志是否能对应上。

经过这样的排查,基本可以确定数据本身是否存在问题。数据没有问题,再进行下一步分析。

### 第二步 缩小问题范围

确定数据正确后,进入第二步——缩小问题的范围。这一步常用的方法是多维度分析,也是新手分析师犯错的重灾区。

常见的错误做法是:对业务还不熟悉,就拼命在数据层面想办法——"不就是拆分维度找原因嘛,我不懂业务,那就多拆几个维度,维度多了之后肯定能找出数据上的差异点,最后把差异大的维度组合起来就是问题的原因了。"于是把数据库里能找到的版本、系统、地域、停留时长之类不管什么类型的维度都拆开看一遍;维度太多看不过来,就按区分度自动排序,找出差异最大的几个维度。

快速跑完所有维度并排序,代码基本功确实不错,但出来的结果一点用都没有。因为按这种方法拆解,最后会发现好多维度都有区别:地域有差异,手机型号有差异,新老用户也有差异。如果把差异大的维度组合起来,5 个维度、每个维度 2 类,组合起来就有 32 种类型;每个维度 3 类,组合起来就是 243 种!复杂度相当恐怖,要配几个业务人员才能搞定?这个人力成本决定了不可能实现这样的精细化运营。

正确的做法分两步。

**首先,选择拆解的维度。** 这是这一步最关键的地方。

- **维度类型**:根据"子指标"和"维度"进行拆分,用到[《指标思维》](04-指标思维：如何搞清楚各种不同的指标类型.md)中指标体系的知识;

- **维度选择**:要符合业务管理模式,也就是公司目前如何运作这个业务。**拆解问题最终拆出一堆没用的数据,基本都是因为没考虑到这一点:拆解的维度离业务太远,最终没法落地。**

举个例子:某些线下企业,业务管理模式是在各地区设置分公司,由分公司管理该地区的整体运作,这种情况下拆分销量问题可以按地域(分公司)拆解,因为地区维度就是这家企业的业务管理模式。而在互联网企业,地域区别不大,业务管理模式是对用户分层——区分新用户、成长用户、忠实用户、流失用户;这种情况下地域不是业务管理的维度,再用地域拆分问题就非常不合适。

核心考虑是让拆分出来的维度更容易落地:就算地域维度的差异真的很大,要更换一种运营模式成本也很大,落地很难,所以最好还是用原有的业务管理模式"用户分层"来拆分。

**然后,多个维度组合进行拆解。** 选好维度后,把这些维度组合起来拆解问题。

::: warning 不建议"逐层递进"式的拆分
有些分析师喜欢先按某一个维度单独拆分,再根据结果中问题较大的部分拆分新的维度。这种做法可能找不到隐蔽的问题。举个例子:某业务的用户来源有 A、B、C 三个渠道,其中 A 渠道人数很少但客单价非常高,某天 A 渠道人数下降了 10%,导致总体销售下降。

如果先按销售额的子指标拆分,会发现:

- 用户数没有明显变化——A 渠道人数很少,减少 10% 在总体上丝毫不明显;

- 转化率也没有明显变化,原因同上;

- 客单价下降很厉害。

然后认为是客单价出了问题,再对客单价按渠道维度拆分,却发现三个渠道的客单价基本都是稳定的——这样拆分,就找不出原因到底在哪。

正确做法是把这些维度一次性放到一个表格里,直接就能清楚找出问题:

:::

拆解问题时不用追求维度"多",而要追求"精":一般控制在三个维度之内。原因有二:

- 业务管理模式本身就那么几种,可选择的范围不多;

- 两维或三维的模型兼顾复杂度和精细化,更容易落地。日常工作中最常见的模型往往不超过三个维度:两维的矩阵、九宫格,三维的 RFM 模型等。

三个维度以内的模型复杂度可接受、容易操作;超过三个维度的模型复杂度太高,要让团队所有人理解非常困难,很容易玩崩。

缩小问题范围的正确做法就是这两步:先找出拆解的维度,再用这些维度组合起来拆解问题。

### 第三步 找出具体环节

缩小了问题范围之后,还可以找出问题出现的具体环节。这一步主要通过拆分过程指标实现,方法在[《指标思维》](04-指标思维：如何搞清楚各种不同的指标类型.md)中已经介绍。

需要说明的是,这一步可以进一步缩小问题范围,但并不是必需的,原因有二:

- **某些问题没有过程指标,或无法获取过程指标。** 比如某些渠道投放只有一个投放金额和最终引流的人数,中间的广告曝光、广告点击等数据都无法获取,就无法拆分过程指标;

- **某些问题的业务流程本身不合理。** 如果流程本身不合理,定位到其中某个环节,最终的分析反而会走进死胡同。[《懂用户》](08-懂用户：数据分析+用户思维=精细化运营.md)中的案例:一个落地页点击购买按钮之后,进入的是另一个落地页,这个流程本身有问题,再怎么优化第二个落地页,效果也不会太好。

所以找出具体环节这一步,根据情况决定是否拆分:业务流程成熟,可以拆分到过程指标;业务流程还在磨合阶段,不一定需要拆解到这一步。

## 小结

新人拆解问题做不好、拆出一堆没用的数据,是因为知道该拆解问题,却不知道按什么维度拆解:看别人一路拆下来非常顺利,自己拆解时就没有思路,完全凭感觉拆解,导致分析结果之间没有关联,对业务也没有参考意义。

其实拆解维度的选择,符合指标体系和业务管理模式就可以了。关键点如下:

- 拆解问题的目标是找到表面原因,表面原因是能用指标体系找出来的原因;

- 拆解问题分三步:排除数据错误、缩小问题范围、找出具体环节;

- 缩小问题范围时,拆解维度从指标体系的子指标和维度中选择;

- 拆解维度必须符合业务管理模式;

- 拆解维度求精不求多,尽量不要超过三个维度。

# 找出原因：问题原因那么多，哪条才是最关键

> 经过指标体系拆解得到的是表面原因，它只能支撑现有业务模式内的优化。本篇说明如何用"假设树 + 数据验证"的方法，从用户属性和需求链路两个方向找出根本原因，从而跳出现有业务框架、带来新的业务增量。前置方法见[《拆解问题》](11-拆解问题：为什么总是拆解出一堆没用的数据？.md)与[《指标思维》](04-指标思维：如何搞清楚各种不同的指标类型.md)。

## 从表面原因到根本原因

通过指标体系的排查，可以找出问题的表面原因。以提升拉新渠道投放 ROI 为例，拆解得到这样几个表面原因：

> 表面原因 1：根据渠道维度的分析，发现 AC 渠道的 ROI 较高，**B 渠道的 ROI 较低。**
>
> 表面原因 2：根据 ROI 的子指标成本和收入，以及渠道维度的交叉组合，发现**B 渠道的人均收入较低**，导致 B 渠道的 ROI 较低，进而拉低了整体 ROI 水平。
>
> 表面原因 3：对 B 渠道的转化进行了过程指标的分析，发现 B 渠道用户的**支付转化率**较低，所以导致 B 渠道用户购买金额低。

现实中，大部分数据分析师找原因到这一步就结束了，因为这些结论已经大大提升了业务人员对业务现状的了解，甚至可以直接拿来用。比如 AC 渠道的 ROI 较高、B 渠道的 ROI 较低，对应的业务动作就是把更多资源投入 AC 渠道、降低 B 渠道的投放，通过渠道结构的调整提升整体 ROI。

这种做法一般来说是有效的，但存在一个问题：**如果 AC 渠道的规模就只有那么大，增加资源投入也无法带来更多的优质用户怎么办？**

如果能知道为什么 AC 相比 B 渠道的 ROI 更高，就可以通过演绎法找到和 AC 渠道类似的优质渠道，带来新的业务增量。所以只有找出根本原因，才能跳出现有业务模式的框架，更好地解决问题。

## 用假设树找出根本原因

根本原因往往千奇百怪，很多原因很难提前想到，无法穷举所有可能性，所以找根本原因不适合用议题树。假设树只需要验证提出的假设是否成立，因此找根本原因一般采用假设树：提出一个假设，然后找出数据验证这个假设。

提出假设这一步和拆解问题一样，看起来简单，做起来难，难点在于究竟应该提出什么样的假设才更合理。比如 ROI 不行，可以假设渠道的文案不行、投放时间段和用户活跃时段不同、产品和用户属性不符等，但这些假设更像灵光一闪的想法，缺少整理假设的套路。

::: tip 提出假设的两个方向
更有条理的假设来自**用户本身**：用户的行为才是真正决定业务数据好坏的根源。用户不做某件事，要么本身没有这个需求，要么在需求链路中出现了问题。因此提出假设的方向有两个——用户的属性、用户的需求链路。
:::

### 用户属性的原因

以 ABC 三个渠道为例，B 渠道的 ROI 最低，AC 渠道的 ROI 较高。从用户属性的角度提出假设：如果能找出 AC 渠道的用户共性，就可以从这个共性出发，到市场上找到符合这个特点的渠道。

用户属性非常多，性别、年龄、地域等维度交叉组合分析的工程量很大，有可能分析了几天终于找到原因，结果业务方一看就说"这还需要分析？我早就知道了"。

::: tip 最高效的路径：直接找业务方沟通
业务人员对业务和用户都比较了解，看到表面问题后，根据业务直觉很容易提出靠谱的假设。比如这款电商 App 卖的大部分是女装和日用品，女生的购买意愿更强，而 B 渠道的量虽然大但男性用户更多，所以 B 渠道质量不行。这类推断中的关键信息早就在业务人员的认知中，不需要用数据验证，很快就能猜个八九不离十。
:::

如果业务人员也没有想法，就从能拿到的用户属性入手分析，把属性控制在三个维度以内，通过数据找出区别度最大的用户属性。用户属性类型很多，拆解要注意优先级，顺序如下：

**首先是用户的基本属性。** 基本信息包括性别、年龄、教育程度、婚姻状况、收入水平、地域、来源等。由于此时对用户还没有真正的了解，这一阶段做的是探索性分析，了解用户到底是一些什么样的人。

**其次是用户画像属性。** 找出一些基本属性特征之后，把这些基础属性组合起来，给不同的用户群体打上"标签"，让用户的形象立体起来，比如小镇青年、一线城市白领、大学生等对应到具体形象的用户类型。如果用户群体和预想的不一样，这就是问题的根本原因。

**最后是用户行为属性。** 根据用户的行为来归纳属性。比如电商产品可以根据用户在产品中的行为归类为冲动型、犹豫型、理性比较型、目标明确型等。这类属性比较难总结，所以放在最后。归纳出不同类型后，看产品的风格是否符合用户的行为特点，也能找出用户属性导致的根本原因。

建议按照上述顺序逐步拆解，每一步搞清楚了再到下一步。跳过基本属性直接用画像分析，只能靠灵光一现提出几种类型，很难考虑全面。这个过程和拆解问题的过程几乎一模一样，区别在于拆解的维度和目标不同，不要和拆解问题混淆。

### 需求链路的原因

需求链路的分析同样优先找业务人员沟通。如果业务场景下的用户需求链路非常清晰，可以直接通过[《懂用户》](08-懂用户：数据分析+用户思维=精细化运营.md)中的用户思维提出假设。

**案例一：促销活动页参与率低。** 运营人员做了某产品的促销活动，用户进入 App 时会弹出活动介绍页面。用户如果对活动感兴趣，本应想看某个具体产品的详细内容，但这个页面只宣传活动，不提供直接跳转的入口，用户必须自己通过搜索等方式找到产品页。

![Drawing 0.png](/data-law-images/i/image2/M01/04/5A/Cip5yF_toIGAZSDJAAGvtyaNkvQ847.png)

据此提出假设：页面跳转的不便导致活动参与率较低。验证方式是选择"进入活动页面后，一分钟内进入具体产品介绍页面的用户比例"作为评判依据——时间太长不能说明用户是看到活动就想看产品页，时间太短用户来不及进入产品页。最终发现接近 30% 的用户在一分钟内进入了产品详情页，说明页面已经激发了参与动机，只是跳转不方便。如果在活动宣传页上增加跳转链接，至少会有 30% 的点击率。

**案例二：B 渠道支付转化率低。** 有些情况下需求链路没有那么明确，需要先用数据还原用户场景，再根据数据反馈的问题提出假设。

在支付页上能得到的用户行为数据有点击率、停留时长等。分析发现 B 渠道用户在这个页面的平均停留时间远超 AC 渠道，而且选择支付渠道的点击率很低。结合支付转化率低的事实还原用户场景：用户进入支付页，看了很久，什么都不点，然后走了。停留久说明用户有支付意愿，不选择支付渠道说明用户遇到了问题。

::: warning 还原场景之后再拆流程
把支付环节拆开——打开支付页 → 理解页面逻辑 → 选择支付渠道 → 点击支付，针对每个小环节提出假设，再用数据验证。这是找出需求链路原因的标准路径。
:::

- **打开支付页**：是不是页面根本没打开，或者打开太慢？比如这个渠道的某类机型占比较大，而这类机型的页面适配没做好。
- **理解页面逻辑**：是不是页面结构或文案太复杂，用户看不懂？比如这个渠道的用户年纪比较大，页面上用了太多新潮词语。
- **选择支付渠道**：是不是缺少用户需要的支付渠道？这个不太容易用数据验证，可能性也不大，如果前两个问题都被排除，可以做用户调研排查。

![Drawing 1.png](/data-law-images/i/image2/M01/04/5A/Cip5yF_toJOALmMeAABonqUbICc654.png)

最后发现 B 渠道用户的手机品牌相对其他渠道较小众、低端，实际测试后发现品牌 1 和品牌 2 的机型存在页面适配差、页面卡顿等情况。

## 找原因的完整流程

## 表面原因与根本原因的区别

找根本原因和找表面原因的过程类似，很容易混淆。区分的关键在于视角：

| 对比维度 | 表面原因 | 根本原因 |
|---|---|---|
| 观察视角 | 站在业务角度看问题 | 站在用户角度看问题 |
| 表现形式 | 某个业务指标的问题 | 用户遇到了什么样的问题 |
| 找出方法 | 指标体系拆解（议题树） | 提出假设、数据验证（假设树） |
| 业务价值 | 在现有业务模式下做优化 | 跳出现有模式，带来新的业务增量 |

![Drawing 6.png](/data-law-images/i/image2/M01/04/5A/Cip5yF_toKiAD55-AADkr1paaiM408.png)

一个问题的原因可以有很多种，对业务人员来说，真正想知道的是基于用户的根本原因。知道表面原因只能在现有的业务模式下做优化，知道根本原因才能打破思维定式，不断创新，带来新的业务增量。

## 小结

- 根本原因相比表面原因能更好地解决问题；
- 找出根本原因的方法是提出假设、验证假设；
- 提出假设的方向一般有用户属性和需求链路两个方面；
- 与业务人员沟通永远是提出有效假设的最高效方法；
- 用户属性拆解的优先顺序：基本属性 → 画像属性 → 行为属性；
- 找需求链路的原因，先用行为数据还原场景，再梳理用户流程，根据流程提出假设。

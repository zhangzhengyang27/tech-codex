# 问题定义和拆解：如何去定义问题、拆解问题？

> 分析师经常面对业务方的诸多需求，第一步是找到业务方的本质需求，然后在此基础上按逻辑树拆解。本篇通过两个完整案例说明问题识别的方法论：先罗列所有问题、按最大概率法则定位破局点，再进行四步拆解。定义与拆解的通用框架可参考[定义问题：怎么定义问题，打通分析思路？](../01-万能的数据分析法则/10-定义问题：怎么定义问题，打通分析思路？.md)与[拆解问题：为什么总是拆解出一堆没用的数据？](../01-万能的数据分析法则/11-拆解问题：为什么总是拆解出一堆没用的数据？.md)。

::: tip 学习方法
把知识点分享给别人，能借助疑问、质疑和新想法加深认知；使用时要结合自己的实际情况，多与同伴交流，督促自己对每个知识点做更深入的理解。
:::

## 案例：问题识别

::: tip 案例背景
小 A 每天都有大量临时提数需求或者杂事，没有时间去做真正的专题分析，感觉自己的能力提升不了，工作越来越没意思。因为力不从心，做事也不认真，老是出错，最近跟同事领导关系变差。年底考核，领导给小 A 的绩效不太好，年终奖也少了很多，跟女朋友也经常吵架，最近事业感情都不太顺，失眠，甚至有点抑郁。
:::

这段描述里有很多问题，如何对问题进行识别和拆解？先说问题识别。

小 A 有很多问题：能力提升不了、做事不认真、跟领导关系变差、跟女朋友吵架、失眠等。然而小 A 真正的问题是：当前工作上有大量临时提数需求，没有时间做专题分析。

针对这个问题，接下来就是拆解问题。首先，为什么会有大量临时提数需求？原因有两个。

### 原因一：需求很多

- **业务繁忙**：如果业务一直持续繁忙，那必须增加人力。
- **业务方需求变来变去**：两个原因。第一，业务方本身也是被动接受任务——向他提任务的那一方变了，他也变了，所以你也跟着变；第二，业务方自己没想明白这件事。这两个原因不一样，对于需求变来变去，最好的做法是对需求进行拆解。

### 原因二：自身效率低

- **对表不熟悉**：那就多去找研发，聊多了，就知道是什么表了。
- **对工具不熟悉**：根据实际应用需求去学一个对应的工具即可。

其中"业务方需求变来变去"是较常见也最花费时间的问题。需求变来变去的真正原因是业务方自己都没想明白这件事，所以小 A 在这个基础之上要理解好业务：业务方没想明白，要帮他想明白，然后把核心指标体系给他。所以在大量临时提数需求这件事上，答案是：一定要理解业务、与业务良好沟通、跟业务方打好关系。

::: tip 问题拆解能力的四个层次
- **Level 1**：对方提了很多需求，问题有没有找到？
- **Level 2**：把问题拆到了第几层——大部分人拆解问题的深度不够。
- **Level 3**：问题拆解到了最后一层，并且去执行了。对性格内向的人，先从找研发沟通这件事做起；做得好不好、效率高不高，又是另外一种能力的培养。
- **Level 4**：掌握了以上所有方法，同时可以在工作中很快发现别人的问题所在。当同事请你给一些指导时，你能很好地用这些方法帮助他人——这代表这些方法已经在脑海里根深蒂固了。
:::

## 问题识别的方法论

首先是二八定理的思考：遇到很多问题，其中必然有一个主要问题，一旦这个问题解决了，其他问题也迎刃而解，所以所有问题一定会有破局点。当业务方说了十个问题，必然有一个是主要问题，而这个主要问题就是要去做专题分析的对象。

怎么找到这个主要问题？第一步，先列出所有问题，自己头脑风暴；第二步，根据最大概率法则，一项一项来试——是否解决一个问题，其他问题都迎刃而解。如果实在不会，就请教 Leader。在问题识别这件事上，一定要心静下来单独思考，动笔画图。

所有的业务问题一定有破局点，怎么做就看问题的拆解。很多书上说拆解要遵循 MECE 原则——不重复不遗漏。这个原则说起来容易，实施起来太难：一是**信息不对称**，业务方想的内容未必都能知道，实施中很难没有遗漏；二是**开始时很难把握是否重复**，而重不重复对结果影响不大。

::: warning 更具实操性的四步拆解
- 第一步：先快速按照自己的理解去做拆解，不要管重复遗漏，能想到多少是多少。
- 第二步：拿着拆解去跟业务方脑子灵活的人对，请教他——这代表业务方在想。
- 第三步：修改第一步的思维导图，做完后请教 Leader——这代表 Leader 在想。
- 第四步：再改一次，汇报给业务方 Leader——这个时候问题不会很大，否则就不是否定你一个人了。
:::

## 案例：问题拆解

::: tip 案例背景
某 App 前期用户量一直在下跌，近期转型（新功能取代第一大功能），转型过了一段时间后，整体用户量大跌。业务负责人压力很大，希望数据部门能派人 100% 投入分析，然而数据方觉得大跌就是因为转型，没什么可分析。于是两个部门就对上了：数据方觉得产品太烂，业务方也不给数据方需求，数据方人员存在感不强，正在考虑是否跳槽。业务进一步下滑，业务方投诉数据部门，决策层在考虑找新的数据部负责人，然而不太好找，各方压力越来越大。
:::

从案例里识别问题，主要有四个：

- 用户量大跌的排查；
- 数据方与业务方关系非常差；
- 数据方存在感不强；
- 找不到新的数据负责人。

其中第一个问题是主要问题，也就是破局点。之所以现在能一眼看到最主要的问题，是因为两点：一是案例本身没有代入感，毕竟当局者迷；二是这里描述得相对简单。真实工作中，在各种复杂因素下不一定很容易找到破局点——比如自己都觉得产品没啥戏了，再加上存在感不强，可能就直接去找工作了。

所以问题的识别就是先罗列，然后按照最大概率法则一项一项排查。用户下跌的原因可以拆解如下。

![用户下跌原因拆解](/data-practice-images/i/image/M00/37/D9/Ciqc1F8avfmAVCOsAAC-CU5862M686.png)

### 原因一：转型影响

- **新功能不好用**：需要做数据分析和用户研究。数据分析是分析新功能的用户留存和 CTR 怎么样，找到异常点分析；用户研究是对用户进行访谈加研究，对客户投诉较多的问题以及用户体验的槽点提出改进意见。
- **新功能不感兴趣**：要看用户的行为路径——是不是当用户跳到这个功能之后立马就切换了，这代表用户压根不感冒。用户行为路径分析可参考[路径分析：用户的使用路径网络分析](./36-路径分析：用户的使用路径网络分析.md)。

### 原因二：非转型影响

- **行业问题**：看整个行业（竞品数据）是不是都不太好，数据可以通过财报、公开数据、第三方公司查看。
- **本身问题**：看版本、用户等各方面数据，分析到后面还会有很多指标可以做。

基于这样一套思维导图，要做的事情就很清晰。把这套逻辑性很强的思维导图给到业务方，对方看完之后可能发现确实是转型影响，或者产品真的没做好，于是大家一起把力往一处使，最终问题也不会太大。在一些时候，数据分析师一定要第一个跳出来，把问题逻辑梳理清楚，最终推动解决问题。

## 方法小结

::: tip 问题拆解的几点感触
- 做问题拆解之前，一定要找到业务方真正关心的点——他们说了很多点，但真正的破局点是什么，要先定位，再对问题拆解。
- 这样做的好处是业务方能清晰理解分析的意思；如果表达能力不好，就请画图。有了具体框架后，业务方会提出具体的建议，这个过程的价值是巨大的。
- 工作多年仍不知如何提升的人，可以主动获得他人的反馈——每次反馈都是对内心的冲击，也只有这样才能真的提升。
:::

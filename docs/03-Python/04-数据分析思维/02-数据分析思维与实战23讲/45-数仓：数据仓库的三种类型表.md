# 数仓：数据仓库的三种类型表

> 本篇介绍数据仓库的基础知识：大数据体系的整体架构、数据研发工程师和数据分析师的关系、App 日志采集中的埋点规范、ODS/DWS/DM 三层数据建模步骤与头条案例，以及数据管理要点。数仓与分析师的日常提数工作直接挂钩，提数方法可参考[数据获取与分析：常见的 SQL 技巧和分析方法](./41-数据获取与分析：常见的 SQL 技巧和分析方法.md)。

## 数据研发工程师和数据分析师的关系

先看整个大数据体系，它包括以下几部分内容：

- 日志的采集和传输；
- 数据建模；
- 数据管理；
- 数据应用。

其中日志采集和传输、数据建模、数据管理属于一般的数据研发岗，也就是广义的数仓。作为分析师，高度要够：一定要熟悉整个大数据体系架构，同时专于其中某个模块。当对大数据团队里每个岗位都有一定理解时，后面跟数据研发沟通时效率会很高。

再看数据研发工程师和数据分析师之间的关系，在大公司和小公司里差异明显：

| 场景 | 特点 | 影响 |
|---|---|---|
| 大公司 | 分工很明确，分析师有点"风险性"，研发工程师相对比较稳 | 日志采集传输、数据建模、数据管理都是对数据本身进行开发，大公司数据需要做底层清洗，要做的事情非常具体，研发工程师的价值很清楚。而分析师的价值大多时候看专题报告的质量和数量、看有哪些报告建议点落地了——这确实是分析师的真正价值，但落地事情很复杂，没把握好的话可能真的在做杂事，稳定性上不如研发工程师 |
| 小公司 | 全部是数据研发工程师（BI 工程师），分析师的活也干了 | 从数据的采集到数据的应用都做，看似什么都懂，但不会很专，特别是在业务分析这一块——因为日志采集、日志传输、数据建模特别耽误时间，过一段时间还可能出现小问题 |

::: tip 结论
**即使作为研发工程师，也要懂业务，否则研发出来的产品真的没人用；即使作为分析师，也要懂研发，否则沟通效率、提数效率会比较低。**
:::

## App 日志采集中的埋点

日志的采集和传输里面具体的技术比较复杂，包括实时传输、批量传输。其中有一个点就是埋点，埋点和分析师关系很大。

**埋点前中期**：数据分析师进入一家公司时，一定要主动参与到埋点的讨论，不要把前后端研发想得多专业。如果埋点出问题了，会非常耽误业务的分析。很多研发纯粹凭感觉埋点，在这过程中一定要把埋点规范建立起来。例如一个 App 营销活动，研发和业务直接对接，研发很多时候按照他们的理解来埋点；但在分析的时候，分析师发现有些点没有埋、或者埋错了，这意味着又要重新埋一次，或者导致这个活动很难分析出什么结论，浪费大家时间。

**埋点后期**：就不要投入太多时间去想新的埋点，文档化即可，这样后面所有的人都可以参照文档。另外日志上报中的公参（所有行为日志一定要有的参数）由分析师来定。

::: warning 埋点的责任划分
**埋点这件事一定是分析师牵头，虽然很烦琐，但非常重要。**
:::

## 数据建模步骤及举例

### 为什么要建模

从分析师的痛点说起：

- **日志量太大，跑数很慢**：一个简单的 Join 都要半个小时才能出结果，而 SQL 又非常容易出错，导致整个分析团队产出效率太低。
- **日志太乱，很多重要的数拿不出来**：想算近一个月新增用户的订单量，如果没有好的数据建模，根本就跑不出来，导致很多重要的思考点无法落地，显得很不专业。

这是业务当中最常见的两个痛点。数据建模可以缓解这些痛点，好处包括：

- 提高整体计算效率，减少重复开发；
- 历史数据追踪，中间表数据可以存储一年；
- 更好适应业务发展，修改影响范围较小；
- 清晰数据结构，分析师更加容易理解。

### 数据建模的三个层次

日常看到的报表，其实都是上层数据的聚合和展示过程。这个过程涉及数据建模（数据仓库），一般是这样一个流程：

- 底层日志每天按照任务调度方式传输到 ODS 层。ODS 可以理解为原始日志的初步加工，经过了明显不合理数据的清洗，比如字段取值过滤。
- ODS 下一层是 DWS，对底层日志进行用户粒度的聚合，怎么聚合非常体现专业力。
- 最后到 DM 常规应用，即上层想看的维度和指标呈现。

三个层次的定义：

- **ODS（Operational Data Store）操作性数据**：作为数据库到数据仓库的一种过渡。ODS 的数据结构一般与数据来源保持一致，便于减少 ETL 的工作复杂性，而且 ODS 的数据周期一般比较短，最终流入 DWS。
- **DWS（Data Warehouse Store）数据仓库**：数据的归宿，保存所有从 ODS 到来的数据并长期保存，这些数据不会被修改。这一层最重要，是数据同学专业力的体现，涉及各种表如何聚合。
- **DM（Data Mart）数据集市**：为了特定的应用目的或应用范围，从数据仓库中独立出来的一部分数据，也可称为部门数据或主题数据，面向应用。

### 数据建模举例——头条

以头条为例，头条做的是信息流的下发。

**第一步：ODS**

- 用户基础属性表：`imei, prov, city, machine`
- 用户文章下发表：`imei, article_id, xiafa_time`
- 用户文章点击表：`imei, article_id, dianji_time`
- 文章属性表：`article_id, category_id, title`

一般一家公司的原始日志都是分为这些：用户基础属性表和文章属性表是维度表，用户文章下发表和用户文章点击表属于 ODS 类型。

**第二步：DWS**

在这一层做用户粒度文章明细表，例如以下两张表：

- 用户文章基础属性表：`imei, prov, city, machine, article_id, category_id, title, xiafa_pv, dianji_pv, xiafa_time, dianji_time`
- 用户分类基础属性表：`imei, prov, city, machine, category_id, xiafa_pv, dianji_pv`

这样就可以通用于每个用户。

**第三步：DM（业务应用表）**

- 省市下发点击 PV 数：`prov, city, xiafa_pv, dianji_pv`
- 分类下发点击 PV 数：`category_id, xiafa_pv, dianji_pv`

在 DWS 中间表的基础之上，看业务想看什么样的数据，针对性聚合就可以了。比如想要各个省市下发的点击 PV，就在上一层表上面聚合省份城市下发 PV、点击 PV；如果要 UV，也可以进行一次聚合；有些时候会涉及多张表 Join 之后的聚合，原理也一样。可以看出 DM 层基本都是确定的：主要和业务方聊，了解业务方想看什么数据，然后在此基础上去设计。

::: warning 数仓建设的实践原则
数仓不要搞得太复杂、太精细，一定要让业务倒逼——先把最核心的数据快速弄出来。有公司要求开发一套类似大数据平台的系统，具体为什么要搞管理层自己都说得不清楚，这很耽误时间。逐步迭代往往比大而全好得多。如果投入大量时间做平台，就没有时间做分析师该做的事情——搞业务；做出来的东西如果业务方不用，也没有意义。有团队在这一块推倒重来、再推倒重来，团队很快解散，对个人成长和公司都没有贡献，所以在这件事情上一定要想好。
:::

### 分析师使用数仓表的注意事项

- **不要过度相信研发的话**：一定要自己动手试一次，比如用表计算一次日活。
- **不要去做研发做的事**：调度异常、表大小、配置错误、UDF 函数、日志传输，这些东西非常耽误时间，对做业务也没好处——可以提建议但不动手。
- **不要去等研发开发表**：数仓对分析师而言最直接的好处就是快，而分析师的最终目的是有数据，目标不要搞错。

## 数据管理

数据管理中的存储、计算等很多时候跟分析师关系不大，重点说以下几块：

- **计算管理**：Join 的时候要注意数据倾斜，选择哪张表很关键，对 MR 内部原理的掌握也很重要。
- **数据存储管理**：核心的表尽量保存久一点（3 个月以上），非核心的表 1 个月内即可。分析师要对表的存储周期有概念，很多时候都要去看历史数据。
- **权限管理**：分析师往往是管理员权限，所以不要随便给其他人开权限。做好了没啥，一旦有问题就是大问题。采用最小可满足原则给权限就行，同时只给读权限。

## 总结

- 埋点的重要性：主动性和文档化；
- 数据建模的三层次：快速迭代；
- 数据的管理：权限管理。

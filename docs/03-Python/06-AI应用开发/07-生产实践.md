# 生产实践

## 概念说明

前面几篇解决了"功能怎么实现"：API 调用、提示、检索、Agent、结构化输出。
本篇解决"上生产还差什么"。LLM 服务与传统 Web 服务在生产化上的差异点集中在四处：

1. **单次调用贵且慢**：一次请求几秒到几十秒、成本按 Token 计费——缓存与并发控制直接决定成本曲线。
2. **质量是概率性的**：同一个提示今天对明天错，没有观测就发现不了静默劣化。
3. **服务商会抖动**：限流、超时、接口变更随时发生，单供应商依赖等于单点故障。
4. **数据敏感**：用户的输入可能含个人信息，流向第三方模型服务前必须过合规闸门。

这些能力全部做在**调用封装层**：业务代码继续只管发消息，缓存、限流、观测、容灾在封装层统一生效（分层结构见 [LLM API 调用与流式输出](01-LLM-API调用与流式输出)）。

::: tip 生产化的检验标准
业务代码零改动的情况下，调用层应当能独立完成：同一请求命中缓存、并发受控、每次调用留下可审计的日志与指标、主模型故障自动切备用。做到这四条，才叫"上得了生产"。
:::

## 核心要点

- **缓存**：对"相同输入必得相同输出"的调用（固定参数、低温）做键值缓存，重复请求零成本零延迟。
- **并发控制**：客户端用信号量限制同时在途的请求数，把限流压力挡在自己这边，而不是撞上服务商 429 再退避。
- **观测**：每次调用记录耗时、Token、成本、错误率四类指标；日志必须脱敏——提示与回复原文默认不落盘。
- **容灾**：维护主备模型清单，按错误类型自动切换，所有降级动作都要留痕可告警。
- **合规**：给第三方模型服务发送数据前过三类问题——必要吗、脱敏了吗、用户同意了吗。
- 缓存键要包含**全部影响输出的参数**：messages、模型名、temperature，漏一项就是错误命中。
- ⚠️ 常见误区：不加并发上限直接 `asyncio.gather` 一批请求。几百个并发同时打到服务端，换来的全是 429 与重试风暴。
- ⚠️ 常见误区：把完整对话原文写进应用日志。日志系统的访问范围远大于业务库，原文落日志等于二次泄漏。
- ⚠️ 常见误区：降级切换静默发生。用户在用备用模型却无人知晓，质量下降找不到归因。

## 请求缓存

### 什么能缓存

LLM 调用是否可缓存，取决于**确定性**：temperature 为 0（或极低）且参数固定的调用，相同输入的输出语义上应当一致，可缓存；高随机性的创作类调用不建议缓存。

| 场景 | 可缓存性 | 说明 |
|---|---|---|
| 结构化抽取（temperature=0） | 高 | 同一工单抽取结果应当相同 |
| 知识库问答（低温 + 固定库版本） | 中 | 知识库更新需失效缓存 |
| RAG 生成（检索结果随库变化） | 中 | 键需包含知识库版本号 |
| 创意生成（高 temperature） | 低 | 缓存反而违背需求 |

### 缓存实现

```python
import hashlib
import json


class ChatCache:
    """请求级缓存：键 = 全部影响输出的参数摘要"""

    def __init__(self, redis_client=None, ttl: int = 3600) -> None:
        self.redis = redis_client   # 传 None 时使用进程内字典
        self.local: dict[str, str] = {}
        self.ttl = ttl

    def make_key(self, *, model: str, messages: list[dict],
                 temperature: float, kb_version: str = "") -> str:
        payload = json.dumps(
            {"model": model, "messages": messages,
             "temperature": temperature, "kb": kb_version},
            ensure_ascii=False, sort_keys=True,
        )
        return "llm:" + hashlib.sha256(payload.encode()).hexdigest()

    def get(self, key: str) -> str | None:
        if self.redis is not None:
            return self.redis.get(key)
        return self.local.get(key)

    def set(self, key: str, value: str) -> None:
        if self.redis is not None:
            self.redis.setex(key, self.ttl, value)
        else:
            self.local[key] = value
```

```python
def cached_chat(messages: list[dict], *, temperature: float = 0.0,
                kb_version: str = "") -> str:
    cache = ChatCache(redis_client=redis_from_env())
    key = cache.make_key(
        model=MODEL, messages=messages,
        temperature=temperature, kb_version=kb_version,
    )
    if (hit := cache.get(key)) is not None:
        metrics.incr("llm.cache.hit")
        return hit

    resp = client.chat.completions.create(
        model=MODEL, messages=messages, temperature=temperature,
    )
    answer = resp.choices[0].message.content or ""
    cache.set(key, answer)
    metrics.incr("llm.cache.miss")
    return answer
```

::: warning 多进程部署用共享缓存
进程内字典缓存只对单实例有效。多副本部署时用 Redis 做共享缓存，缓存命中率才能跨实例累积；Redis 数据模型见 [非关系型数据库](/docs/python/09-进阶核心/03-数据库/02-非关系型数据库)。
:::

## 异步并发调用

批量任务（离线抽取、评测集跑分、批量摘要）的吞吐瓶颈在"同时在途请求数"。用 `asyncio.Semaphore` 划定上限，异步基础见 [asyncio 基础](/docs/python/09-进阶核心/02-异步编程/01-asyncio基础)。

```python
import asyncio
import os

from openai import AsyncOpenAI

aclient = AsyncOpenAI(
    base_url=os.environ["LLM_BASE_URL"],
    api_key=os.environ["LLM_API_KEY"],
)

MAX_CONCURRENCY = 5  # 在途上限：从服务商限流文档的 RPM/TPM 反推，宁低勿高
sem = asyncio.Semaphore(MAX_CONCURRENCY)


async def one_chat(messages: list[dict]) -> str:
    async with sem:                     # 超出的协程在此排队
        resp = await aclient.chat.completions.create(
            model=MODEL, messages=messages,
        )
        return resp.choices[0].message.content or ""


async def batch_chat(questions: list[str]) -> list[str]:
    tasks = [one_chat([{"role": "user", "content": q}]) for q in questions]
    return await asyncio.gather(*tasks)  # 全部受同一个信号量约束


answers = asyncio.run(batch_chat(questions))  # 50 任务、并发 5：服务端始终只看到 5 个在途请求
```

要点：

- **信号量是第一道闸**，指数退避重试（见 [LLM API 调用与流式输出](01-LLM-API调用与流式输出)）是第二道。只做退避不做并发上限，重试风暴会自我放大。
- 上限值从服务商配额（RPM / TPM）反推，留出其他业务共用的余量；不同配额级别的模型分开设信号量。
- 批量任务与在线请求**分池**：离线任务用独立客户端与独立并发池，避免把在线请求挤到限流。
- 失败容忍度高的批量任务可配合 `return_exceptions=True` 收集失败项，逐条重跑而不是整批重来。

## 观测：日志脱敏与指标

### 结构化日志与脱敏

LLM 调用日志要回答三个问题：这次调用是谁发起的、用了哪个模型与提示版本、结果如何。**原文默认不落盘**，日志规范详见 [日志系统](/docs/python/03-工程化与运维/02-运维/01-日志系统)。

```python
import hashlib
import logging
import time

logger = logging.getLogger("llm")


def mask_text(text: str, keep: int = 20) -> str:
    """原文不出日志：保留前缀长度 + 全文摘要指纹，足够对账又不可还原"""
    if not text:
        return ""
    digest = hashlib.sha256(text.encode()).hexdigest()[:12]
    return f"{text[:keep]}...(masked, sha256:{digest}, len={len(text)})"


def logged_chat(messages: list[dict], *, user_id: str = "",
                prompt_version: str = "") -> str:
    start = time.monotonic()
    try:
        resp = client.chat.completions.create(model=MODEL, messages=messages)
        content = resp.choices[0].message.content or ""
        logger.info("llm.call", extra={
            "event": "llm.call",
            "user_id": user_id,                 # 业务侧标识，非个人敏感原文
            "model": resp.model,
            "prompt_version": prompt_version,   # 提示版本，见提示工程篇
            "prompt": mask_text(messages[-1]["content"]),
            "response": mask_text(content),
            "prompt_tokens": resp.usage.prompt_tokens,
            "completion_tokens": resp.usage.completion_tokens,
            "latency_ms": int((time.monotonic() - start) * 1000),
        })
        return content
    except Exception as exc:
        logger.error("llm.call.failed", extra={
            "error_type": type(exc).__name__,   # 记录类型，不记录含原文的报错体
            "latency_ms": int((time.monotonic() - start) * 1000),
        })
        raise
```

### 耗时与成本指标

四类核心指标接入监控系统（指标口径与告警设计见 [监控与可观测性](/docs/python/03-工程化与运维/02-运维/01-监控与可观测性)）：

| 指标 | 口径 | 用途 |
|---|---|---|
| `llm.latency` | 首字延迟 / 总延迟分位数 | 流式看首字，批处理看总量 |
| `llm.tokens` | prompt / completion 分别累计 | 成本核算的原始数据 |
| `llm.cost` | Token × 单价按模型汇总 | 预算与异常消费告警 |
| `llm.error_rate` | 按错误类型分桶 | 容灾切换的触发依据 |

```python
class Metrics:
    """进程内最小指标实现；生产替换为 Prometheus client 等标准方案"""

    def __init__(self) -> None:
        self.counters: dict[str, int] = {}

    def incr(self, name: str, n: int = 1) -> None:
        self.counters[name] = self.counters.get(name, 0) + n


metrics = Metrics()

# 成本告警示例：单用户/单租户当日成本超阈值即上报
def report_cost(user_id: str, cost: float, daily_cap: float) -> None:
    metrics.incr("llm.cost.total_cents", int(cost * 100))
    if cost > daily_cap:
        metrics.incr("llm.cost.budget_exceeded")
        logger.warning("llm.cost.budget_exceeded", extra={"user_id": user_id})
```

::: tip 必须分桶的指标
错误率、延迟、成本都要带维度标签：模型名、功能、提示版本、错误类型。"LLM 平均有 3% 错误"不可行动；"备用模型 B 的超时错误占 40%"才是告警与归因的起点。
:::

## 降级与多模型容灾

### 容灾链设计

维护一份带优先级的模型清单：主模型故障时自动切备用，备用也不可用时走兜底（模板回复 / 拒答 + 告警）。

```python
from dataclasses import dataclass


@dataclass
class ModelRoute:
    name: str          # 模型标识
    base_url: str
    api_key_env: str   # 各服务商密钥独立的环境变量


ROUTES: list[ModelRoute] = [   # 顺序即优先级：主模型在前，备用在后
    ModelRoute(name="primary", base_url=os.environ["LLM_BASE_URL"],
               api_key_env="LLM_API_KEY"),
    ModelRoute(name="backup", base_url=os.environ["BACKUP_BASE_URL"],
               api_key_env="BACKUP_API_KEY"),
]


def make_client(route: ModelRoute):
    return OpenAI(
        base_url=route.base_url,
        api_key=os.environ[route.api_key_env],  # 密钥一律环境变量
        timeout=30.0,
        max_retries=1,   # 单模型内部少重试，把快速失败留给上层切换
    )


def chat_with_failover(messages: list[dict]) -> tuple[str, str]:
    """返回 (回答, 实际使用的模型)，切换动作全部留痕"""
    last_exc: Exception | None = None
    for route in ROUTES:
        try:
            resp = make_client(route).chat.completions.create(model=MODEL, messages=messages)
            metrics.incr(f"llm.route.{route.name}.ok")
            return resp.choices[0].message.content or "", route.name
        except Exception as exc:
            last_exc = exc
            metrics.incr(f"llm.route.{route.name}.fail")
            logger.warning("llm.failover", extra={
                "from_route": route.name,
                "error_type": type(exc).__name__,
            })
    raise RuntimeError("所有模型路由均不可用") from last_exc
```

### 降级策略分层

| 层级 | 动作 | 触发 |
|---|---|---|
| 同模型重试 | 指数退避重试（1~2 次） | 瞬时超时 / 5xx |
| 跨模型切换 | 切到备用服务商 | 限流持续 / 服务不可用 |
| 功能降级 | 缩短回答长度、关闭非核心功能（如改写建议） | 备用模型容量有限 |
| 兜底 | 模板化回复 / "稍后重试" + 告警 | 全部路由失败 |

::: danger 降级要可观测、可回切
每次切换写日志并打指标（`llm.route.*`）；主模型恢复后回切主模型（人工确认或健康探测）。降级动作静默发生是最危险的状态——用户在体验降级服务，团队却在按主模型的质量指标看大盘。
:::

## 隐私合规要点

LLM 调用把用户文本送出组织边界（第三方模型服务），这是与传统 Web 服务最大的合规差异。发送前过三类问题：

### 1. 最小必要：这段文本必须完整发出去吗

- 抽取、分类类任务往往只需要相关字段或片段，不发送完整原文。
- RAG 场景发送的是内部文档片段，注意片段是否含个人信息（员工姓名、手机号）。
- 系统提示不含业务敏感数据；业务数据只出现在 user 消息中，便于按消息级别做过滤。

### 2. 脱敏：发出去之前先抹掉可识别信息

```python
import re

PII_PATTERNS = [
    (re.compile(r"1[3-9]\d{9}"), "<PHONE>"),                       # 手机号
    (re.compile(r"\d{6}(19|20)\d{2}[01]\d[0-3]\d[\dXx]"), "<ID>"),  # 身份证
    (re.compile(r"[\w.+-]+@[\w-]+\.[\w.]+"), "<EMAIL>"),           # 邮箱
]


def sanitize(text: str) -> str:
    """发送给第三方模型服务前的兜底脱敏；模式按业务补充"""
    for pattern, replacement in PII_PATTERNS:
        text = pattern.sub(replacement, text)
    return text
```

脱敏发生在调用封装层，业务代码无感。注意：脱敏可能损伤任务效果（如抽取手机号的任务不能脱手机号），按功能配置脱敏规则，用评测集验证。

### 3. 授权与留痕：用户知道、同意、可追溯

| 要点 | 做法 |
|---|---|
| 用户告知 | 隐私政策与产品交互中明确"输入将由模型服务处理" |
| 数据留存 | 确认服务商的数据留存与训练使用策略，配置不用于训练（如有） |
| 可删除 | 请求日志、缓存中的用户相关内容支持按用户删除（缓存键不含用户标识时可按 TTL 过期） |
| 审计留痕 | 记录"谁、何时、用了哪个模型、数据是否脱敏"的审计日志（不含原文） |
| 敏感功能隔离 | 涉及敏感数据的场景走自部署模型或私有化部署，而非公共 API |

::: danger 合规不是"加了脱敏函数"就完事
脱敏只是技术兜底。法定义务（告知同意、跨境传输评估、数据主体权利响应）按所在法域的个人信息保护要求执行，技术方案要经法务与安全评审后落地。
:::

## 常见陷阱

| 陷阱 | 后果 | 正确做法 |
|---|---|---|
| 缓存键漏掉参数 | temperature 不同却命中同一缓存 | 键覆盖 messages、模型、参数、知识库版本 |
| 无并发上限的批量 gather | 429 风暴 + 重试放大 | 信号量限流 + 独立并发池 |
| 原文写进日志 | 日志系统成为敏感数据重灾区 | 脱敏函数统一处理，默认不落原文 |
| 指标不分桶 | 告警不可归因 | 按模型/功能/错误类型打标签 |
| 单供应商硬依赖 | 服务商故障即全站故障 | 主备路由 + 自动切换 + 可回切 |
| 降级静默发生 | 质量下降无从归因 | 切换留痕、指标分桶、告警联动 |
| 用户原文直发第三方 | 合规风险 | 脱敏 + 最小必要 + 授权留痕 |
| 缓存永不失效 | 知识库更新后答案陈旧 | TTL + 知识库版本进缓存键 |

## 最佳实践

### 1. 调用层是所有横切能力的唯一落点

缓存、限流、日志、指标、容灾、脱敏全部收敛在调用封装层。业务代码只见"发消息、拿结果"，生产能力才能全局一致地生效（参见本系列各篇的封装层示例）。

### 2. 成本预算按租户/功能双维度

Token 累计按用户（租户）与功能两个维度分别上报：租户维度控账单，功能维度控架构（哪个功能的成本收益比恶化了）。

### 3. 容灾清单配置化

主备模型清单（地址、密钥环境变量名、优先级）放配置而非代码。新增备用服务商改配置即可，不改发布。

### 4. 合规规则进评测

脱敏规则、拒答策略、数据发送范围，都写进黄金评测集（见 [结构化输出与评估](06-结构化输出与评估)）的对抗样例中，每次变更回归验证。

## 版本说明

- **AsyncOpenAI**：openai SDK v1.x 提供的异步客户端，配合 `asyncio.Semaphore` 使用；同步场景下用线程池 + 信号量达到同等效果。
- **Redis 缓存**：示例使用 `setex` 的 TTL 语义；共享缓存需多实例可达同一 Redis。
- **指标实现**：文中 `Metrics` 为示意，生产环境建议 Prometheus client 或托管指标服务，口径设计不变。
- **合规**：数据保护义务随法域与业务形态不同，本篇技术要点不构成法律意见。

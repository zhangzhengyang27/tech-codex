# 制作流畅动画的技巧与实践

## 概念说明

动画是一种通过在一系列静止图像(帧)之间快速切换来产生运动效果的视觉技术。观看动画时,人眼实际看到的是迅速连续出现的静止图像,由于视觉暂留效应,大脑会将这些图像解释为运动。单位时间内呈现的图像越多,运动感越平滑。在计算机图形与 Web 开发中,动画通常通过改变图形元素的属性(位置、大小、颜色等),或在图像之间应用变换(平移、缩放、旋转等)来实现;在一定时间内逐渐改变这些属性,即可创建平滑的运动效果。

对 Web 开发者与设计师而言,除了保证动画存在的合理性与趣味性,还需要保证动画的流畅度。性能不佳的 Web 动画会令人感觉笨拙、卡顿,最重要的是显得缓慢。Web 开发往往在减少页面首次加载时间上投入大量精力,却容易忽略后续交互阶段的性能表现。

流畅动画没有灵丹妙药,只能依靠大量测试与优化。但经过多年实践,确实存在一系列可复用的设计原则、代码原则与技术手段,能让动画以接近丝滑的质量运行。以下内容围绕 GPU 渲染、合成层、帧率等核心概念展开,并提供可直接落地的技巧与建议。

## 核心要点

- "流畅"是一种主观感知,其量化指标包括响应时间、帧率、过渡连贯性、卡顿与撕裂控制、硬件加速。
- 流畅动画的目标帧率为 `60fps`;每帧渲染预算约 `16ms`(浏览器自身渲染开销约 `6ms`,实际指导线为每帧 `10ms`)。
- 优先对"动画友好"的 CSS 属性做动画:`transform`、`opacity`、`filter`,它们只触发合成,渲染成本最低。
- 避免对盒模型属性(`width`、`height`、`margin`、`padding`、`top`/`right`/`bottom`/`left` 及对应逻辑属性)做动画,它们触发昂贵的重排。
- 硬件加速将渲染推送到 GPU,可显著提升流畅度,但代价是额外的全层重绘与内存消耗,应按需开启而非随意添加。
- `will-change` 是显式的优化提示,应作为解决既有性能问题的最后手段,而非预防性手段。
- CSS 声明式动画是性能更优的首选;需要精细控制时可选用 Web Animations API 或 `requestAnimationFrame`。
- FLIP 技术与 CSS View Transitions API 通过"先记录终态、再反向播放"的思路降低布局动画的成本。
- `contain` 与 `content-visibility` 让浏览器隔离或跳过部分渲染,是进一步提升动画性能的新手段。
- 使用浏览器开发者工具(性能面板、图层视图)测量 FPS、CPU、布局与绘制,定位动画性能瓶颈。

## 流畅动画的判定标准

"流畅"在视觉与动画语境中是一种主观体验,描述对事物运动、变化和交互的愉悦感。类比舞台表演:舞者动作自然连贯、在音乐节奏下没有突然停顿或不协调转换时,观众会感到表演流畅、赏心悦目。数字产品中的动画同样追求这种连贯性,以确保用户体验愉悦、自然、不被干扰。

流畅的感知建立在帧率、动画连贯性、响应时间等因素之上。当动画在时间与空间上的变化无缝、自然,没有明显的障碍或断裂感时,通常会被判定为流畅。从高层次看,流畅动画有以下主要特点:

- **响应时间(Response Time)**:动画元素对用户输入或触发的响应速度是衡量流畅性的关键因素。从触发动画(点击、轻拍、拖动等)到动画实际开始执行的时间应尽可能短(约 `100` 毫秒),延迟最小化才能让用户感到互动的即时性。
- **帧率(Frame Rate)**:帧率是动画每秒显示的图像帧数。帧率足够高时,肉眼无法察觉单个图像之间的间隔。在大多数情况下,`60` 帧每秒(`60fps`)被认为是创建流畅动画的理想目标;较低的帧率会让动画显得不够流畅,在快速运动或复杂场景中尤其明显。
- **过渡效果(Transitions)**:流畅的过渡效果在状态切换时产生,如元素的平移、缩放、淡入淡出等。过渡应自然、无缝,而非突兀、生硬。
- **卡顿和撕裂(Jank and Tearing)**:卡顿指动画播放时突然停滞或变得不连贯;撕裂指画面出现分裂。两者都会破坏流畅性,应尽量避免。
- **硬件加速(Hardware Acceleration)**:将动画元素放到 GPU(图形处理单元)上处理,可以加速渲染过程,提供更流畅的动画效果。

这些要素看似复杂,但只需掌握若干原则与技巧,即可让动画稳定地以高质量运行。

## 原理:帧率与渲染预算

### 为什么是 60fps

对动画而言,最理想的帧率是 `60fps`,原因如下:

- **屏幕刷新率**:大多数显示屏以每秒 `60` 次的频率刷新,即 `60Hz`。动画以 `60fps` 播放会与屏幕刷新同步,呈现更顺滑的效果。
- **人眼感知**:人眼对动态图像的感知通常能达到 `60fps`。帧率高于该水平时,人眼很难察觉额外的帧,因此 `60fps` 被认为是足够实现流畅动画的帧率。
- **平滑体验**:更高的帧率意味着单位时间内呈现更多帧,创造更自然、流畅的动画效果,这在交互和网络应用、游戏中至关重要。

`60fps` 是一种平衡:既提供良好的视觉效果,又能在各种设备上流畅播放。为实现该目标,每一帧都需要在不到 `16` 毫秒内渲染完成。以一个弹跳并变换的物体为例:左侧以 `60fps` 播放,物体运动平滑;右侧以 `15fps` 播放,运动明显卡顿,甚至能看出构成动画的单个图像——帧的断断续续无法骗过大脑,只会分散对动画本身的注意力。

FPS 指每秒帧数,即一秒内渲染的帧数。FPS 越高,运动感越平滑。对 Web 动画而言,应追求 `60fps`:

- 帧率能够达到 `50 ~ 60fps` 的动画相当流畅,让人倍感舒适
- 帧率在 `30 ~ 50fps` 之间的动画,因各人敏感程度不同,舒适度因人而异
- 帧率在 `30fps` 以下的动画,让人感觉到明显的卡顿和不适感
- 帧率波动很大的动画,亦会使人感觉到卡顿

### Web 动画的帧率是可变的

传统动画的帧速率是固定的,所有帧在播放之前就已创建。Web 动画则由浏览器即时渲染:浏览器尽快计算新帧并更新动画,因此帧率是可变的。假设浏览器完成一个动画帧的计算需要 `0.04s`,接下来一帧用 `0.03s`,将 `1s` 除以计算持续时间即得帧速率:`1 ÷ 0.04 = 25fps`,即第一帧的帧速率是 `25fps`,第二帧为 `33fps`。关键不在于当前帧率是多少,而在于目标帧率是多少——即 `60fps`。

### 每帧渲染预算

每帧的最大预算是 `16ms`(即 `1000ms ÷ 60fps ≈ 16ms`),但浏览器自身需要约 `6ms` 来渲染每一帧,因此业界制定了每帧 `10ms` 的指导方针。

典型设备的刷新率为 `60Hz`,即屏幕每秒刷新 `60` 次。要在不同刷新率下以 `60fps` 运行,一帧的渲染时间非常有限:

- 在 `60Hz` 下:`16.67ms`
- 在 `90Hz` 下:`11.11ms`
- 在 `120Hz` 下:`8.34ms`
- 在 `144Hz` 下:`6.94ms`

在屏幕刷新时创建新帧,就能获得平滑的运动。若动画以 `75fps` 播放,由于显示器刷新不足以呈现这些额外的帧,用户仍然只能看到每秒 `60` 帧。因此,`60fps` 是用户能看到的上限,动画帧的计算时间应保持在 `16ms` 以下。

### 实现 60fps 的两件事

- 第一件事:对"动画友好"的 CSS 属性(如 `transform`、`opacity`)进行动画。这些是经过优化、可快速更改和屏幕更新的属性。
- 第二件事:将工作分派到 GPU(图形卡),在那里动画等视觉操作比 CPU 处理得更好。

掌握这两点的前提是理解动画是如何工作的。

### 渲染流水线的四个阶段

浏览器渲染是一个复杂的过程,包含四个不同的阶段。渲染流水线接受 HTML 和 CSS,并将它们转换为稍后显示在屏幕上的图像。构建流畅动画的关键在于了解这个过程以及每个步骤中发生的事情。

- **样式(Style)**:浏览器解析 CSS,弄清楚应该将哪些规则应用于哪些元素。
- **布局(Layout)**:浏览器计算出每个元素的大小以及放置位置。
- **绘制(Paint)**:浏览器使用样式计算与布局计算的结果,将元素呈现为像素。
- **合成(Composite)**:浏览器将所有元素层叠在一起,形成最终渲染的页面。

在第一阶段(Style),HTML 元素与适用于它们的 CSS 进行匹配,浏览器必须将每个 DOM 元素与适用的规则进行匹配,HTML 和 CSS 越复杂,这个过程就越慢。

> 参考来源：https://developer.chrome.com/blog/inside-browser-part3

随后是布局阶段。对每个 HTML 元素,只应用影响位置和大小的 CSS 属性,比如 `width`、`height`、`border-width`、`margin`、`padding` 和 `font` 等属性。

> 参考来源：https://developer.chrome.com/blog/inside-browser-part3

一旦知道每个元素的位置和大小,浏览器就在绘制阶段应用其余的视觉样式,比如 `color`、`box-shadow`、`background` 和 `border-color` 等属性。

> 参考来源：https://developer.chrome.com/blog/inside-browser-part3

最后,在合成阶段构建完整图像,将所有不同的图层组合在一起。只有少数属性,如 `opacity`、`transform`、`z-index` 或 `filter`,会影响这一阶段。

> 参考来源：https://developer.chrome.com/blog/inside-browser-part3

渲染是复杂的过程。通常一个网站有数百甚至数千个 DOM 节点和同样数量的 CSS 规则,网站越大这个过程越慢,这还没有考虑 JavaScript。做动画的目标是让这个过程每秒至少执行 `60` 次,即每帧不到 `16` 毫秒。

尽管创建 Web 动画的方式有很多种,但从根本上说,除 `canvas` 之外的动画都通过调整布局属性(Layout)、绘制属性(Paint)和合成属性(Composite)之一来工作。浏览器在渲染页面时,并不需要每次都执行每个步骤。

### 渲染路径的三个层级

**渲染时不跳过任何步骤**

> JS / CSS 👉 样式 👉 布局 👉 绘制 👉 合成

更改布局属性(改变元素几何形状的属性,例如宽度、高度,或元素的左侧、顶部位置)时,浏览器必须检查所有其他元素并"重排"页面;任何受影响的区域都需要重新绘制,最终绘制的元素需要重新合成。改变布局属性会同时引起重排和重绘,重排非常昂贵,而且很容易被触发。

**渲染时跳过布局步骤**

> JS / CSS 👉 样式 👉 绘制 👉 合成

更改仅影响绘制的属性(例如背景图片、文本颜色或阴影),即不影响页面布局的属性时,浏览器会跳过布局,但仍会执行绘制。改变绘制属性会引起重绘,它虽没有重排昂贵,但计算同样耗资源。注意:重排必将引起重绘,但重绘不会引起重排。

**渲染时跳过布局和绘制步骤**

> JS / CSS 👉 样式 👉 合成

更改既不影响布局也不影响绘制的属性时,浏览器只执行合成。这是开销最小的渲染路径,对动画这类高负荷渲染,应争取使用这种流程。

从渲染引擎的角度看,编码时应尽可能少地改变布局和绘制相关的属性,从而提高页面性能——即尽可能避免重排和重绘。浏览器渲染一帧时经历的步骤越少,性能越好:动画只依赖绘制阶段的属性(如 `color` 和 `background-color`)时,将跳过布局阶段;仅依赖合成属性(如 `transform` 和 `opacity`)时,将跳过布局和绘制阶段,节省大量计算资源。了解什么类型的更改会触发哪些步骤,就能在创建动画时做出更好的决策。

对影响绘制的属性(如 `color`)做动画,浏览器需要为每次计算重新绘制和合成元素;对影响布局的属性(如 `width`)做动画,浏览器需要重新计算整个页面的布局再重新绘制。浏览器需要计算的越多,处理时间越长,帧速率越低,甚至出现"顿挫"(JANK)。

> 当帧速率降低到足以看到单个帧且运动变得迟缓时,称之为"顿挫"(JANK),这是 Web 动画师的天敌。避免顿挫的关键是限制自己只对不触发布局或绘制计算的属性进行动画。

## 对动画友好的属性

要判断哪些属性对动画友好,需要全面了解哪些属性会触发布局、绘制和合成(可通过 [csstriggers.com](https://csstriggers.com/) 查询)。制作动画时应尽可能避免对布局和绘制相关的属性做动画,因为它们的计算是昂贵的;合成级别的更改最廉价、最有效,因此动画应只改变触发合成的属性。

只触发合成的属性即动画友好的属性,它们是 `transform`、`opacity` 和 `filter`。看似限制很多,实则空间巨大:

- `transform`:允许使用 `translate()` 函数改变元素位置、`scale()` 函数改变大小、`rotate()` 函数旋转元素、`skew()` 函数倾斜元素,CSS 变换能提供几乎无限的组合可能。
- `opacity`:允许调整元素透明度,可用于控制元素显示隐藏及其颜色表现。
- `filter`:允许对元素应用阴影、发光、颜色校正等视觉效果。

### 变换

CSS 变换(`transform`)允许对元素进行近乎无尽的视觉更改:定位、缩放、旋转、倾斜,甚至应用三维矩阵变换。某些情况下需要转变思维,考虑如何用变换实现原本会导致重排或重绘的更改。

例如,沿水平方向(`x` 轴)来回移动一个元素,与其更改 `left` 或 `margin-left` 属性:

```CSS
@keyframes moveX {
    to {
        left: 80vw;
    }
}
.ball {
    animation: moveX 2s linear infinite alternate;
}
```

不如使用 `translate()` 或 `translate` 属性,使元素沿 `x` 轴来回移动:

```CSS
@keyframes moveX {
    to {
        translate: 80vw;
    }
}

.ball {
    animation: moveX 2s linear infinite alternate;
}
```

> Demo 地址：https://codepen.io/airen/pen/KKJjWyy

两者在视觉效果上差异不大,但性能差异明显。假设页面上有 `100` 个这样的元素在移动,[动画化 left 属性](https://codepen.io/airen/full/VwgJpXw) 时,页面重排和重绘所占资源明显高于[动画化 translate 属性](https://codepen.io/airen/full/wvNLJEd)。

这两个示例说明:除非有特定需求,否则不要对 `width`、`height`、`margin`、`padding`、`top`、`right`、`bottom`、`left` 以及对应的逻辑属性做动画,即**不要对 CSS 盒模型中的任意属性做动画**。每次修改这些(以及其他影响布局的)属性的值时,浏览器都会额外计算修改对整个文档布局的影响。在布局中使用这些属性没有问题,但作为动画或过渡的一部分,以每秒 `60` 次的频率修改它们的值绝不可取——计算和重新计算页面中的元素是浏览器计算中最昂贵的部分。

一种优化方式是将要做动画的元素的 `position` 属性设置为 `fixed` 或 `absolute`,这样浏览器不必计算整个文档的布局。注意 `fixed` 的开销同样昂贵,应尽可能避免;而且浏览器仍需在元素移动时计算其位置,开销依然存在。

结论:更改元素位置、大小、旋转和倾斜时,对 `transform` 属性做动画是最佳选择。

### 透明度

改变 `opacity` 属性的值可以轻松显示(`opacity: 1`)和隐藏(`opacity: 0`)元素,类似于更改 `display` 或 `visibility` 属性,但性能更好。以移动菜单切换动画为例:菜单打开时不透明度为 `1`,关闭时为 `0`。最佳实践是同时定义 `pointer-events: none`,确保用户不会意外地与"隐藏"的菜单交互;在用户点击"打开"或"关闭"按钮时切换 `.open` 类:

```CSS
.menu {
    opacity: 0;
    pointer-events: none;
    transition: .2s;
}

.menu.open {
    opacity: 1;
}
```

对比[通过改变 opacity 来显示隐藏元素](https://codepen.io/airen/full/jOdjmGQ)与[通过 visibility 来显示隐藏元素](https://codepen.io/airen/full/OJdemMx):布局上的开销相差无几,但在绘制上,`opacity` 明显低于 `visibility`。

不透明度的变化还能控制元素的可见性级别,可用性更强。例如,给按钮背景颜色添加一个简短的过渡,使 `:hover` 状态感觉更流畅自然:

```CSS
.button {
    background-color: #15dea5;
    transition: background-color 250ms;
    
    &:hover {
        background-color: #13c794;
    }
}
```

> Demo 地址：https://codepen.io/airen/full/gOqNWqz

在过渡(`transition`)的每一帧中对 `background-color` 做动画,会触发按钮的新的绘制计算。这个简单场景性能尚可接受,但在更复杂的页面和动画中,可能出现不连贯的情况。

因此对 `background-color` 做动画并不是颜色动画的最佳实践,应该使用 `opacity` 属性。`opacity` 改变元素及其子元素的透明度,取值范围 `0 ~ 1`,`0` 表示完全透明(不可见),`1` 表示完全不透明(可见)。

想要的效果是悬浮时颜色变暗而不是按钮变透明,这可以通过分层实现:底层保持正常的非活动状态颜色,顶层放置悬浮状态(`:hover`)的较暗颜色,再通过 `opacity` 在两种颜色之间淡入淡出:

```CSS
.button {
    background-color: #15dea5;
    z-index: 1;

    &::after {
        background-color: #13c794;
        opacity: 0;
        z-index: -1;
        transition: opacity 250ms;
    }
    
    &:hover::after {
        opacity: 1;
    }
}
```

> Demo 地址：https://codepen.io/airen/full/oNmrwbo

`opacity` 在绘制上的花费要比 `background-color` 低得多。

`opacity` 动画并不局限于颜色变化,也可以用于渐变动画:唯一的变化是把 `::after` 伪元素背景中的纯色换成渐变:

```CSS
@layer animation {
    .button {
        background-color: #15dea5;
        z-index: 1;
    
        &::after {
            background: radial-gradient(circle, #22eab1 0%, #11af82 100%);
            opacity: 0;
            z-index: -1;
            transition: opacity 250ms;
        }
        
        &:hover::after {
            opacity: 1;
        }
    }
}
```

> Demo 地址：https://codepen.io/airen/full/BaMgwmr

这里需要再次强调:**制作动画时不要改变除不透明度(`opacity`)或变换(`transform`)之外的任何属性**。即使认为可能没问题,也不要这样做。这个基本原则通常能覆盖 `80%` 的动画场景。一旦习惯了这种思考方式,它就变得非常简单。

## 硬件加速与合成层

"硬件加速"是动画开发中的常见术语:它表示某个进程在 GPU 上运行。使用 `transform` 和 `opacity` 对元素做动画时,浏览器不会在每一帧上对像素进行光栅化,而是将一切作为纹理传递到 GPU。GPU 非常擅长执行基于纹理的变换,因此能得到非常流畅、性能卓越的动画,这就是"硬件加速"。

对 `transform` 和 `opacity` 做动画时,这些属性的渲染会被推送到 GPU,浏览器因此可以重用布局和绘制信息——CPU 不必向 GPU 发送新图像,而是由 GPU 保存并重用先前的图像,以不同的不透明度、位置和效果将它们组合在一起。

其中一个前提是:元素必须位于自己的图层上。某些情况下浏览器会自动将元素提升到图层,也可以手动触发。动画元素在 GPU 还是 CPU 上渲染,取决于修改的 CSS 属性、查看动画的设备以及各浏览器的具体实现。

通过明确告诉 GPU 主动渲染需要做动画的元素,可以避免这些不确定性。方式相当简单:

- 在 CSS 中:设置 `will-change` 属性。对不支持 `will-change` 的旧浏览器,可将 `transform: translateZ(0);` 添加到元素上作为一种技巧。
- 在 JavaScript 中:设置一个带 3D 特征的变换,如 `translate3d()` 和 `matrix3d()`,将创建一个图层。一些 JavaScript 动画库会在幕后执行这个操作。

示例:

```CSS
.animated {
    transform: translate3d(0, 0, 0);
}
```

这样就把动画元素 `.animated` 的渲染完全推送到 GPU,开启了硬件加速,该元素上的动画将运行在专为确保其顺利运行而设计的地方。

这确实是确保流畅动画的技巧,但需要负责任地使用。

### 合成的工作原理

与 CPU 不同,GPU 擅长处理简单任务但可同时运行多个核心,其开发初衷就是处理图形,因此在图形上下文中"使用 GPU"与快速渲染、流畅互动直接相关。近年来随着 GPU 加速计算的发展,越来越多的计算可以仅靠 GPU 完成。

> 参考来源：https://developer.chrome.com/blog/inside-browser-part1

制作 Web 动画时,为了让 GPU 处理动画,需要了解浏览器的合成工作原理。

合成是一种将页面各个部分分离成图层、单独光栅化,然后在单独线程(合成器线程)中合成页面的技术。发生滚动时,由于图层已经光栅化,只需合成一个新帧即可;通过移动层与合成新帧,可以用相同方式实现动画。

以下示例是一个简单页面对 `.element--a` 和 `.element--b` 设置绝对定位,并使用不同的 `z-index`:

```HTML
<div class="container">
    <div class="element--a element">Element A</div>
    <div class="element--b element">Element B</div>
</div>
```

```CSS
@layer demo {
    .container {
        width: 50vw;
        aspect-ratio: 21 / 9;
        background-color: rgb(255 34 124 / 0.5);
        position: relative;
    
        .element {
            width: 150px;
            aspect-ratio: 1;
            display: grid;
            place-content: center;
            position: absolute;
        }
    
        .element--a {
            background: #09f;
            left: 100px;
            top: 100px;
            z-index: 2;
        }
    
        .element--b {
            background: #89aefc;
        }
    }
}
```

浏览器先在 CPU 上完成绘制,然后将结果图像发送到 GPU,由 GPU 在屏幕上显示。通过浏览器调试工具的图层(Layers)选项,可以查看当前页面内的所有图层:

> Demo 地址：https://codepen.io/airen/full/oNmraYb

在上面的示例基础上,给 `.element--a` 添加一个关键帧动画,改变 `left` 值,动态改变元素在水平方向的位置:

```CSS
@layer animation {
    @keyframes moveA {
        from {
            left: 100px;
        }
        to {
            left: 100%;
        }
    }
  
    .element--a {
        animation: moveA 2s linear infinite alternate;
    }
}
```

> Demo 地址：https://codepen.io/airen/full/NWoZOjM

元素 `.element--a` 在屏幕上来回移动(动态改变 `left`),图层视图会相应更新。对每一帧动画,浏览器必须重新计算 `.element--a` 的位置(重排/回流),渲染页面新状态的图像(重绘),然后再次发送到 GPU 显示。重绘的计算是昂贵的,尽管现代浏览器只会重绘页面的更改区域而不是整个页面,且大多数情况下速度很快,动画仍然不够流畅。

在动画的每一步重新计算和重绘,对大型复杂布局来说非常慢。更有效的方法是只绘制两张独立图像:一张给 `.element--a`,另一张给不含 `.element--a` 的整个页面,然后简单地将这两张图像相对偏移——组合缓存元素的图像会更快。这正是 GPU 的强项:**它能够以亚像素精度快速合成图像,使动画更流畅。**

为优化合成,浏览器必须确保要动画的 CSS 属性不影响文档流、不依赖文档流、不会引起重绘。

有一种误解认为 `.element--a` 与 `.element--b` 都设置了绝对定位(`position: absolute`),已脱离文档流,`left`、`top` 等属性不再依赖元素环境。事实并非如此:元素的 `left` 属性可能接收依赖于 `.container` 大小的百分比值,`em`、`vw` 等相对单位同样依赖其环境。相反,`transform` 和 `opacity` 是唯一满足上述条件的动画友好属性——不影响文档流、不依赖文档流、不会引起重绘。

将上面示例中的 `left` 替换为 `translate` 或 `transform`:

```CSS
@layer animation {
    @keyframes moveA {
        from {
            translate: 100px;
        }
        to {
            translate: 50vw;
        }
    }
  
    .element--a {
        animation: moveA 2s linear infinite alternate;
    }
}
```

> Demo 地址：https://codepen.io/airen/full/OJdeBOz

对 `translate` 属性做动画时,浏览器看到没有任何属性会导致重排或重绘,便可以应用合成优化:将两张图像绘制为合成层并发送到 GPU。这种优化让动画运行在专为图形任务优化的计算单元上,丝般顺滑、亚像素精度、速度极快,且不再受限于 CPU。

### 强制提升图层

可以手动将元素提升到它们自己的合成器图层。强制提升能确保元素始终处于绘制和准备就绪的状态。

早期,开发者只能通过应用会触发新合成器图层但不一定有视觉效果的样式来"欺骗"浏览器提升元素,通常通过 `backface-visibility:hidden`、`translate3d(0,0,0)` 或 `translateZ(0)` 实现,即俗称的"人肉手工开启 3D 加速"。这些都是隐式触发新合成器图层的方式,此外还有:

- 3D CSS 属性,例如 `rotateY()`、`rotateZ()`、`translateZ()`、`perspective` 等
- `<video>`、`<canvas>` 和 `<iframe>` 加速元素
- 通过 `Element.animate()` 动画 `transform` 和 `opacity`
- 通过 CSS 过渡(`transition`)和动画(`animation`)进行的变换(`transform`)和不透明度(`opacity`)动画
- 具有较低 `z-index` 的同级元素,该元素有自己的图层
- 设置元素的 `position` 为 `fixed`
- 设置元素的 `filter`
- 具有 `will-change: transform` 属性的提示
- 具有 `mix-blend-mode` 属性的元素

### will-change 属性

归根结底,现代浏览器更了解要优化哪些元素以及何时优化。开发者可以尽力预测并采取措施,但始终存在猜测的成分——前面列举的每个技巧都伴随着各种注意事项,都不能百分之百保证动画流畅运行。

现代浏览器为此提供了一个显式属性,用于提前通知浏览器将需要哪些类型的优化,这就是 `will-change`。它使浏览器能够提前优化元素的渲染,可能带来更好的性能。例如,页面包含许多相同大小和颜色的元素,已知其中某个元素的大小或颜色即将改变,可以在变化发生之前用 `will-change` 通知浏览器:

```CSS
@keyframes ani {
    to {
        transform: scale(2);
        background-color: #09f;
    }
}

.element {
    will-change: transform, background-color;
    background-color: #f36;
    
    &.animated {
        animation: ani .2s linear;
    } 
}
```

这种"预警"让浏览器提前优化元素的渲染,从而在变化发生时获得更好的性能,使动画尽可能高效。

`will-change` 是一个常被误解或不正确使用的 CSS 属性,它可以有一个或多个值:

- `auto`:浏览器将应用优化
- `scroll-position`:表示开发者预计在不久的将来会动画或更改元素的滚动位置
- `contents`:表示开发者预计在不久的将来会动画或更改元素内容的某些方面
- `<custom-ident>`:表示开发者预计在不久的将来会动画或更改元素上给定名称的属性,可以是任何用户定义的属性,如 `transform` 或 `background`,也可以是逗号分隔的多个属性。注意,如果指定简写属性(例如 `background`),则表示告诉浏览器 `background-color`、`background-image`、`background-position` 等所有与背景相关的属性都可能发生变化。

实际使用中关注的是 `<custom-ident>`,即 `transform`、`opacity` 等。

**为什么要使用 will-change**

- **性能优化**:使用 `will-change` 的主要原因是改善性能。告诉浏览器哪些元素可能很快变化,浏览器可以提前优化这些元素的渲染,在实际变化发生时获得更好的性能。
- **改进动画效果**:`will-change` 允许浏览器优化元素渲染,可能产生更平滑流畅的动画。已知元素将做动画时,可用 `will-change` 通知浏览器。
- **防止重绘和重排**:重绘和重排是昂贵操作,会显著影响页面性能。重绘发生在元素更改不影响 DOM 布局时(如背景更改);重排发生在更改影响 DOM 布局时(如更改宽度或高度)。`will-change` 有助于避免不必要的重绘和重排。

**何时使用、何时不使用**

使用 `will-change` 的目的是提高性能、使动画更流畅,但并非任何时候都适合。[MDN 文档](https://developer.mozilla.org/en-US/docs/Web/CSS/will-change)明确指出:

> **`will-change` 应该被视为最后的应对手段,用于解决现有的性能问题。不应该被用来预测性能问题**。

滥用 `will-change` 反而会损害性能。如果动画或过渡本身流畅清晰,就没有必要使用 `will-change`,浏览器已经在不使用它的情况下做了优化。

只有在观察到动画某些部分运行不够平滑、且其他优化措施无效时,才值得尝试 `will-change`:

```CSS
#animated-element {
    will-change: transform, opacity;
    
    &.animated {
        transition: transform 0.5s, opacity 0.5s;
        transform: scale(2);
        opacity: 0;
    }
}
```

```JavaScript
const element = document.querySelector('#animated-element');

element.addEventListener('click', () => {
    element.classList.toggle('animated');
});
```

上例中,`will-change` 告诉浏览器 `#animated-element` 的 `transform` 和 `opacity` 属性在元素被点击时可能变化,浏览器据此优化渲染,产生更平滑流畅的动画。

另一个用例是已知元素的大小或位置即将变化时,提前告知浏览器:

```CSS
#changing-element {
    will-change: width, height, transform;
    
    &.changed {
        width: 200px;
        height: 200px;
        transform: translateX(100px);
        transition: width .2s linear, height .2s linear, transform .2s linear;
    }
}
```

```JavaScript
const element = document.querySelector('#changing-element');
element.addEventListener('click', () => {
    element.classList.toggle('changed');
});
```

**使用位置上的注意事项**

不要在动画或过渡发生的地方使用 `will-change`,而应在动画或过渡之前使用。`will-change` 告诉浏览器即将发生的变化,以便浏览器提前准备;浏览器无法为正在发生或已经发生的变化做准备。

反例——直接在动画发生的地方添加:

```CSS
.element:hover {
    will-change: color;
    color: red;
}
```

这样做弊大于利。`will-change` 是将来时态,不应在动画发生时应用,而应添加在元素的初始状态(尚未发生任何变化时):

```CSS
.element {
    will-change: color;
    transition: color 300ms ease-in-out;
}

.element:hover {
    color: red;
}
```

或者将 `will-change` 放在 `.element` 的父元素上:

```CSS
.parent-element:hover {
    will-change: opacity;
}

.element:hover {
    transition: opacity .25s ease-in-out;
}
```

注意:`will-change` 只有在动画不流畅或闪烁时才应作为最后的手段使用。

**动态开启与关闭**

最佳做法是在期望的变化发生之前和之后打开和关闭 `will-change`,特别是变化不频繁的场景。这也是 Mozilla 推荐通过 JavaScript 设置 `will-change` 的原因——写在 CSS 样式表中的 `will-change` 无法被移除:

```JavaScript
const el = document.querySelector('.parent-element')
el.addEventListener('mouseenter', addWillChange)
el.addEventListener('animationend', removeChange)

const addWillChange = () => {
    this.style.willChange = 'opacity'
}

const removeChange = () => {
    this.style.willChange = 'auto'
}
```

鼠标悬停在父元素上时添加 `will-change`,`animationend` 事件触发时移除 `will-change`。

在样式表中设置 `will-change` 仅在某些情况下有意义:元素会被多次交互的场景,如按钮上的涟漪效果或侧边栏滑出。通常样式表中只应保留少数几个 `will-change`,其余通过 JavaScript 设置。

**应避免使用 will-change 的场景**

- **在动画或过渡期间**:不要在元素正在做动画或过渡时应用。变化已经发生时使用 `will-change` 会对浏览器造成压力并影响性能。
- **变化不可预测**:元素变化经常或意外发生时,`will-change` 带不来收益,反而造成不必要的性能开销。
- **小元素**:优化小元素的渲染收益微乎其微,`will-change` 可能适得其反。
- **不可动画的属性**:应用于 `font-family` 或 `display` 等不可动画属性时,可能对性能没有影响甚至产生负面影响。
- **滥用**:在页面多个元素上应用 `will-change` 可能损害性能,导致浏览器占用大量机器资源、拖慢页面加载。

**关键注意事项**

- **不是改进性能的保证**:浏览器可能忽略该提示,优化也可能产生相反效果。建议在各种浏览器和设备上测试动画以确认影响。
- **作为最后的解决方案**:不要试图通过给没有性能问题的元素添加 `will-change` 来获得轻微提升,这样做可能损害性能。
- **不要过度使用**:具有该属性的元素太多会导致内存使用增加并降低性能;只在确实会发生变化的元素上使用,在保持不变的元素上指定反而可能降低性能。
- **为浏览器提供足够的时间优化**:在元素属性更改之前,浏览器需要提前一点时间做优化。应预测变化即将发生的时间,并在那时设置 `will-change`。
- **注意对元素视觉外观的影响**:`will-change` 可能影响堆叠上下文中的视觉表现。例如 `will-change: opacity` 会让浏览器为该元素创建新的堆叠上下文,可能改变其堆叠顺序中的位置。
- **不要为过早优化而应用**:页面表现良好时,不要仅为提升一点速度而添加 `will-change`。过度使用会导致内存占用过多、渲染更复杂,反而性能更差。
- **谨慎使用**:浏览器优化通常会在尽可能短的时间内移除并恢复正常;写进样式表意味着浏览器会保留优化更长时间,因此最好用脚本在变化前后开启和关闭。

总之,`will-change` 用得不好或不恰当会起反作用。正如 Mozilla 所言:"**不到万不得已,请慎用,更别滥用!**"

### 硬件加速的利弊权衡

硬件加速并非免费午餐。开启硬件加速的优点:

- 动画流畅,几乎能达到每秒 `60` 帧
- 经过良好设计的动画在独立的线程中运行,不受大量 JavaScript 计算的阻塞
- 3D 变换成本较低

不足之处:

- 需要额外的重绘来将元素提升到复合层,即全层重绘而不是增量重绘,有时会起反作用,使页面或动画非常慢
- 已绘制的图层必须传输到 GPU,图层数量和大小较大时传输可能很慢,可能在低端和中端设备上引起元素闪烁
- 每个复合层都会消耗额外内存;移动设备内存宝贵,过度使用可能导致浏览器崩溃
- 若不考虑隐式合成,慢速重绘、额外内存使用和浏览器崩溃的可能性都会很高

GPU 动画虽有独特优点,但重绘与过度内存使用是严重问题,以这种方式优化的元素越少越好。与 `will-change` 类似,要抵制随意开启硬件加速的冲动,不要随意书写:

```CSS
.element {
    transform: translate3d(0,0,0);
}

/* 或者 */
.element {
    transform: translateZ(0);
}

/* 或者 */
.element {
    translate:  0 0 0;
}
```

这会告诉浏览器将元素推送到 GPU。基于前述性能与内存原因,**不要随意开启 3D 加速,只有在需要的时候才开启**。

在即将做属性动画的同时才将元素推送到 GPU 同样不是好主意:

```CSS
.element {
    transition: all .2s ease-in-out;
    background-color: #fff;
    
    &:hover {
        transform: translate3d(0,0,0);
        background-color: #eee;
    }
}
```

鼠标悬停时 `background-color` 从 `#fff` 动画到 `#eee`,同时通过 `translate3d()` 在悬停状态才开启硬件加速——看似合理,实际上元素传递到 GPU 时浏览器已经开始动画,期望的优化将会丧失。

无论用哪种方式开启硬件加速,都应提前告知浏览器;临时开启不但起不到优化作用,反而加重浏览器负担,使页面变慢、动画不流畅甚至卡顿。

## 优化绘制

无论是使用动画友好的属性还是开启硬件加速,目的都是优化绘制。改变除变换(`transform`)和不透明度(`opacity`)之外的任何属性都会触发绘制,而绘制通常是渲染过程中最昂贵的步骤。优化绘制的可行手段:

- **将移动或经常绘制的元素提升到自己的图层**:元素在自己的图层上绘制时,不会触发相邻元素的绘制。可通过硬件加速方式提升,但要有选择性,并审核其对性能的影响。
- **减少绘制区域**:确保元素不重叠可以减少绘制区域;也可以寻找避免对页面某些部分做动画的方法。有时存在挑战:浏览器可能将需要绘制的两个区域联合在一起,导致整屏重绘。
- **简化绘制复杂性**:某些绘制属性成本很高。例如任何涉及模糊的东西(`box-shadow` 比 `background-color` 绘制起来昂贵得多),这也是经常使用伪元素单独绘制一层来模拟阴影的主要原因,动画化阴影相关属性时尤其如此。

## 动画实现方式与技术选型

制作流畅动画不限于属性选择和硬件加速,实现方式的选择同样重要。制作动画主要有两种方式:CSS(声明式)或 JavaScript(命令式),具体取决于如何最好地实现目标。

### 声明式动画:CSS

CSS 动画是声明式的:声明浏览器要做什么,浏览器知道操作的全部范围和结束点,因此可以进行优化。对 `transform` 和 `opacity` 这类动画友好属性,浏览器可以把 CSS 动画放到合成器线程上运行。**CSS 动画(声明式动画)是性能更好的选项,是制作流畅动画的首选方式**。使用关键帧(`@keyframes`)可以创建大多数需求的动画,例如一个简单的旋转元素动画:

```CSS
@keyframes spin {
    from {
        transform: rotate(0deg);
    }
    to {
        transform: rotate(360deg);
    }
}

.animated {
    animation: spin .3s linear infinite;
}
```

CSS 动画也有不足,例如缺乏 JavaScript 的表达力。一种解决方案是用 JavaScript 事件弥补:监听用户输入(相关事件)并做出响应,比如切换类,再在新类中设置动画所需样式。以下示例演示动画元素类的切换:

```JavaScript
var box = document.getElementById("box")

box.addEventListener("click", function(){
    box.classList.toggle("animated");
});
```

```CSS
@keyframes scale {
    to  {
        scale: 2;
    }
}

#box {
    width: 50px;
    aspect-ratio: 1;
    
    &.animated {
        animation: scale .2s linear both;
    }
}
```

此外,还可以用 JavaScript 操作 CSS 自定义属性,尤其是 `@property` 定义的自定义属性,同样能达到动画属性的效果,这类场景正越来越多。

值得一提的是,新的 Web Animations API(WAAPI)允许在 JavaScript 中使用 CSS,可以轻松处理动画的同步和时序,同时保留声明式动画的优势。

### 命令式动画:JavaScript

命令式动画会告诉浏览器如何执行动画。在 CSS 动画过于庞大或需要更多控制时使用 JavaScript。注意:与 CSS 动画不同,JavaScript 动画在主线程上运行,更有可能丢帧,通常是性能较差的选项。需要 JavaScript 动画时,有一些选项值得考虑,例如 `requestAnimationFrame`。

理论上 `requestAnimationFrame` 是创造流畅动画的选项之一:它以 `60fps` 的速度调用,浏览器通过将更改分组到单个重绘中进行优化,节省 CPU 周期。它可以递归调用:

```JavaScript
function doSomething() {
    requestAnimationFrame(doSomething);// Do stuff
}
doSomething();
```

此外,在性能密集型事件(如 `resize` 或 `scroll`)上应考虑使用 `requestAnimationFrame`(而不是直接绑定到事件)。

> 注意,确保 JavaScript 在帧的开始运行的唯一方法是使用 `requestAnimationFrame` 或 Web Animations API。避免使用 `setTimeout` 或 `setInterval` 进行动画,它们是不可靠的,本质上在帧的某个时刻运行,可能引入顿挫。

大多数场景下,声明式动画(CSS)与命令式动画(JavaScript)表现一致。一些基于 JavaScript 的动画库(例如 [GSAP](https://greensock.com/gsap/))甚至声称性能可以做得比原生 CSS 的过渡(`transition`)和关键帧动画(`animation`)更好。这是可能的:在重绘事件发生之前,CSS 的 `transition` 和 `animation` 在主 UI 线程上只是重新采集元素样式,这与通过 `requestAnimationFrame()` 回调获取重新采集的元素样式一样,都在下一次重绘之前触发。假如二者都是在主 UI 线程上创建的动画,性能方面没有差异。

每种方法都有其适用场景:

- **为界面元素设置较小的独立状态时,使用 CSS 动画**:CSS 过渡和动画非常适合从侧面引入导航菜单或显示提示。状态切换可能由 JavaScript 控制,但动画本身位于 CSS 中。
- **需要对动画进行大量控制时,使用 JavaScript 动画**:Web Animations API 是基于标准的方法,目前适用于大多数现代浏览器,提供真实对象,适合复杂的对象导向型应用。需要停止、暂停、减慢或倒放动画时,JavaScript 也很有用。
- **需要手动编排整个场景时,直接使用 `requestAnimationFrame`**:这是一种高级 JavaScript 方法,构建游戏或绘制到 HTML 画布时很有用。

### FLIP 技术

FLIP 是一种记忆设备和技术,最早由 [@Paul Lewis](https://aerotwist.com/blog/flip-your-animations/) 提出,是 First、Last、Invert 和 Play 四个单词首字母的缩写:

- **First(F)**:在任何事情发生之前(过渡之前),记录当前元素的位置和尺寸,可以使用 `getBoundingClientRect()` 这个 API 处理
- **Last(L)**:执行一段代码让元素发生相应变化,并记录元素在最后状态的位置和尺寸
- **Invert(I)**:计算元素第一个位置(`First`)和最后一个位置(`Last`)之间的位置变化(如需要还可计算两个状态的尺寸变化),使用这些数字做计算,让元素移动(通过 `transform` 改变位置和尺寸),创建它位于初始位置的错觉
- **Play(P)**:元素反转后(假装在 `First` 位置),把 `transform` 设置为 `none`,将其移动到 `Last` 位置,让元素有动画效果

FLIP 技术在执行动画之前对其进行预优化,核心思想是反转动画的状态。通常直接做动画需要对每一帧做昂贵的计算;FLIP 基于最终状态预先计算这些变化,第一帧是最终状态的偏移,动画的播放成本大大降低。

```JavaScript
// 获取当前元素的边界 
const first = el.getBoundingClientRect() 
// 通过给元素添加一个类名，设置元素最后状态的位置和大小 （在.totes-at-the-end中添加相应的样式规则） 
// 布局发生了变化 
el.classList.add('totes-at-the-end') 
// 记录元素最后状态的位置和尺寸大小 
const last = el.getBoundingClientRect() 
const deltaX = first.left - last.left 
const deltaY = first.top - last.top 
const deltaW = first.width / last.width 
const deltaH = first.height / last.height 
elm.animate([ { 
    transformOrigin: 'top left', 
    transform: ` translate(${deltaX}px, ${deltaY}px) scale(${deltaW}, ${deltaH}) ` 
}, { 
    transformOrigin: 'top left', transform: 'none' 
}], { 
    duration: 300, 
    easing: 'ease-in-out', 
    fill: 'both' 
});
```

FLIP 的整个流程可以拆解为:First 记录 → Last 变化 → Invert 反向偏移 → Play 正向播放。加上最后的 Play 过程,动画即完成。

来看一个由 [@David Khourshid 使用 FLIP 技术制作的真实案例](https://codepen.io/davidkpiano/full/JKEraQ/305a618d4dd75cbe8423183c70d6a43e):

> Demo 地址：https://codepen.io/airen/full/NWoZmOj （来源于 [@David Khourshid](https://codepen.io/davidkpiano/full/JKEraQ/305a618d4dd75cbe8423183c70d6a43e) ）

FLIP 是一种不同的动画思维模型,需要一些时间掌握。@David Khourshid 在文章《[使用 FLIP 技术制作布局动画](https://css-tricks.com/animating-layouts-with-the-flip-technique/)》中详细介绍了这个主题。

### CSS 视图过渡

熟悉 CSS 视图过渡的技术后发现,其制作动画效果的思路与 FLIP 极其相似。

> Demo 地址：https://astro-movies.pages.dev/

CSS View Transitions API 使 Web 开发人员能够以更少的代码和更少的可访问性问题创建流畅的视图过渡。开发人员只需更新 DOM 即可创建过渡效果更流畅的动画。它主要通过以下方式工作:

- 快速切换 DOM 状态:CSS View Transitions API 可以瞬间切换 DOM 的两个状态,无需中间状态
- 创建可自定义的过渡效果:默认创建页面级别的交叉淡入淡出效果,开发人员可以使用 CSS 属性自定义,以独立控制哪些元素被捕获和独立动画处理
- 使用伪元素:过渡状态由伪元素表示,可以使用熟悉的 CSS 动画自定义每个过渡效果

CSS View Transitions API 允许开发者在视觉 DOM 更改状态之间添加动画过渡,使 Web 应用的过渡效果更流畅、更具交互性,而无需大量 JavaScript 和 CSS 代码,同时提升开发效率与用户体验。

### 离散属性动画与进入退出动画

现代 CSS 新增了为离散属性添加动画的能力,例如在 `display: none` 之间添加动画。从 Chrome 116 开始,可以在关键帧中使用 `display` 和 `content-visibility`;也可以在 `@keyframes` 的 `50%` 处转换任何离散属性:

```CSS
.fade-out {
    animation: fade-out 0.25s forwards;
}

.spin-out {
    animation: spin-and-delete 1s ease-in forwards;
}

@keyframes fade-out {
    100% {
        opacity: 0;
        display: none;
    }
}

@keyframes spin-and-delete {
    0% {
        transform: rotateY(0);
        filter: hue-rotate(0);
    }
    80% {
        transform: rotateY(360deg);
        filter: hue-rotate(180deg);
        opacity: 1;
    }
    100% {
        opacity: 0;
        display: none;
    }
}
```

> Demo 地址：https://codepen.io/web-dot-dev/full/vYbRQaE （来源于 [web.dev](https://codepen.io/web-dot-dev) ）

与关键帧动画不同,对离散属性做过渡转换需要使用 `allow-discrete` 过渡行为模式。`allow-discrete` 是 `transition-behavior` 属性的值,该属性接受 `normal` 和 `allow-discrete` 两个值:

```CSS
.card {
    transition: opacity 0.25s, display 0.25s;
    transition-behavior: allow-discrete;

    &.fade-out {
        opacity: 0;
        display: none;
    }
}
```

> Demo 地址：https://codepen.io/web-dot-dev/full/poQMLrN （来源于 [web.dev](https://codepen.io/web-dot-dev) ）

`@starting-style` 是 CSS 新增的 `@` 规则,主要用于在 `display: none` 之间添加动画效果。该规则为元素指定"打开之前"(before-open)样式,让浏览器在元素打开之前可以查询到该样式,对进入动画以及为弹出式窗口或对话框等元素添加动画非常有用。以下示例将 `popover` 属性以动画形式呈现,使其从视口外平滑进入视图并进入顶层:

```CSS
@starting-style {
    dialog[open] {
        translate: 0 100vh;
    }
}

dialog {
    transition: translate 0.7s ease-out, overlay 0.7s ease-out, display 0.7s ease-out allow-discrete;
    translate: 0 100vh;
    
    &[open] {
        translate: 0 0;
    }
}
```

`@starting-style` 应用的样式在元素打开之前即可被浏览器查询,即"打开之前"状态(播放动画的场景)。

> Demo 地址：https://codepen.io/web-dot-dev/full/OJdjjdX （来源于 [web.dev](https://codepen.io/web-dot-dev) ）

CSS 还新增了 `overlay` 属性,让具有顶层样式(例如 `popover` 和 `dialog`)的元素顺畅地从顶层呈现动画效果。如果不使用叠加层过渡,元素会立即恢复为经过裁剪、转换和覆盖的状态,看不到过渡效果。`overlay` 也能让 `::backdrop` 在添加到顶层元素后流畅地做动画。

需要从顶层淡出 `popover` 或 `dialog` 时,请将 `overlay` 添加到过渡列表。这些元素会脱离祖先裁剪和转换并将内容放在顶层;反之则立即恢复为被剪裁、转换和覆盖的状态,看不到过渡效果:

```CSS
[popover],
dialog,
::backdrop{
    opacity: 0;
    transition: opacity 1s, display 1s allow-discrete;
}

:popover-open,
[open],
[open]::backdrop {
    opacity: 1;
}

@starting-style {
    :popover-open,
    [open],
    [open]::backdrop {
        opacity: 0;
    }
}

.overlay, 
.overlay::backdrop {
    transition: opacity 1s, display 1s allow-discrete, overlay 1s allow-discrete;
}

::backdrop {
    background-color: rgba(0,0,0,.6);
}
```

> Demo 地址：https://codepen.io/web-dot-dev/full/zYeJbgw （来源于 [web.dev](https://codepen.io/web-dot-dev) ）

这些新功能与 CSS View Transitions API 一起,使 Web 上的进入和退出动画效果更进一步,可用于制作流畅的转场动画。

### 动画编排

单个动画独立运行时非常流畅,但与许多其他动画同时运行时可能出现混乱、不协调等问题,使页面整体动画看起来不流畅,甚至引起用户反感。因此,制作流畅动画除了性能优化之外,还需要动画编排:事物需要从正确的方向、正确的时间进入,即使各个动画是分开的,也应感觉像一个设计良好的整体。

制作动画时不要同时对所有元素做动画,而要使用动画编排。通过调整动画的时间(持续时间和延迟时间)以及动画速度,让动画整体更为流畅。

动画编排并不复杂,可以通过时间轴对动画进行编排。例如一个标题、副标题与按钮依次进入的动画:

> Demo 地址：https://codepen.io/airen/full/LYqmBav

创建一个可视化的动画序列时间轴:首先是主标题(Heading)动画,接着是次标题(Subheading)动画,最后是按钮(Button)动画。可以用 CSS 自定义属性编写与时间轴相匹配的 CSS:

```CSS
:root {
    --base-speed-unitless: 0.2;
    --base-speed: calc(var(--base-speed-unitless) * 1s);

    --relative-heading-speed: 0.5;
    --relative-subheading-speed: 0.5;
    --relative-button-speed: 1;

    /* 持续时间 */
    --heading-duration: calc(var(--base-speed) * var(--relative-heading-speed));
    --subheading-duration: calc(
      var(--base-speed) * var(--relative-subheading-speed)
    );
    --button-duration: calc(var(--base-speed) * var(--relative-button-speed));

    /* 延迟时间 */
    --heading-delay: 0s;
    --subheading-delay: calc(var(--heading-delay) + var(--heading-duration));
    --button-delay: calc(var(--subheading-delay) + var(--subheading-duration));
}
```

> Demo 地址：https://codepen.io/airen/full/mdvLzEp

动画编排的核心是动画速度与时间之间的关系,尤其是持续时间与延迟时间,找到它们之间的平衡即可。这是一个微妙的平衡,找到正确的数字组合时,整体效果会非常完美。动画编排的更多细节可参考《深入了解 CSS 动画的持续时间和延迟时间》一文。

## 渲染隔离:contain 与 content-visibility

浏览器正在持续添加微调性能的选项,其中 [CSS 容器模块](https://www.w3.org/TR/css-contain-2/)中的 `contain` 和 `content-visibility` 两个属性有助于提高 Web 页面性能,对优化动画性能也非常有益。

### contain 属性

`contain` 允许指定特定的 DOM 元素和它的子元素独立于整个 DOM 树结构之外,目的是让浏览器有能力只对部分元素进行重绘、重排,而不必每次针对整个页面。这是一种告诉浏览器可以安全优化元素的简单方式。可以指定 `strict`(适用于所有规则)、`content`、`size`、`layout`、`style` 或 `paint` 作为值,以限制任何更改的范围,确保子树中的 DOM 更新不会触发父文档上的回流:

- **`layout`**:元素的内部布局不受外部的任何影响,同时该元素及其内容也不会影响上级元素
- **`paint`**:元素的子级不能在该元素的范围外显示,该元素不会有任何内容溢出(即使溢出也不会被显示)
- **`size`**:元素盒子的大小独立于其内容,计算元素盒子大小时会忽略其子元素
- **`content`**:`contain: layout paint` 的简写
- **`strict`**:`contain: layout paint size` 的简写

其中 `size`、`layout` 和 `paint` 可以单独使用,也可以相互组合;`content` 和 `strict` 是组合值。

以手风琴效果为例解释 `contain` 的作用:

> Demo 地址：https://codepen.io/airen/full/XWOvJaq

在 `.accordion__item` 上设置:

```CSS
.accordion__item { 
    contain: size;
}
```

手风琴展开,但容器高度并没有变化:

> Demo 地址：https://codepen.io/airen/full/XWOvJaq

这在某些场景中非常有用,例如制作展开与合拢的动画(如下拉菜单):子元素出现时不改变父元素尺寸,不产生重排,对性能非常有益。

[@Manuel Rego Casasnovas 专门为 contain 写了一个测试用例](https://blogs.igalia.com/mrego/files/2019/01/css-contain-example.html),`.wrapper` 中包含差不多 `10000` 个 `.item` 元素:

```HTML
<div class="wrapper">
    <div class="item">
        <div style="background-color: rgb(226, 127, 90);">Lorem ipsum...</div>
    </div>
    <!-- 有 10000 个 item -->
<div>
```

不使用 `contain` 时,即使更改发生在单个元素上,浏览器在布局上也会花费大量时间,因为它会遍历整个 DOM 树(本例中 DOM 树有 `10000` 个 DOM 元素):

> 参考来源：https://blogs.igalia.com/mrego/2019/01/11/an-introduction-to-css-containment/

本例中 `div` 的大小固定,内部更改不会溢出。将 `contain: strict` 应用到 `.item` 上,当 `.item` 内部发生变化时,浏览器不需要访问其他节点,可以停止检查该元素上的内容,避免波及元素外部:

> 参考来源：https://blogs.igalia.com/mrego/2019/01/11/an-introduction-to-css-containment/

尽管例子中每一项都很简单,但通过使用 `contain`,Web 性能得到巨大改变:布局耗时从 `~4ms` 降到 `~0.04ms`。如果 DOM 树结构复杂但只修改了页面的一小部分,将其与页面其他部分隔离开来收益巨大;若该计算发生在动画中,收益同样可观。

### content-visibility 属性

`content-visibility` 可跳过不在屏幕上的内容渲染,包括布局(Layout)和渲染(Paint),直到真正需要布局渲染为止。由于系统会跳过渲染,如果很大一部分内容在屏幕之外,该属性可以显著加快初始加载速度,并支持更快地与屏幕上的内容互动。

> 参考来源：<https://web.dev/articles/content-visibility>

`content-visibility` 属性接受 `visible`、`hidden` 和 `auto` 三个值:

- **`visible`**:没有效果,元素的内容以正常方式布局和渲染
- **`hidden`**:元素跳过其内容。跳过的内容不能被用户代理特性(如页内查找、标签顺序导航等)访问,也不能被选择或定焦,类似于 `display: none`
- **`auto`**:元素开启 `contain`(取值可能是 `layout`、`paint` 等),如果元素与用户无关,也会跳过其内容

取 `auto` 值能够立即提升性能。具有 `content-visibility: auto` 的元素会获得 `layout`、`style` 和 `paint` 包含关系:元素在屏幕之外时不呈现其后代,浏览器在不考虑元素内容的情况下确定元素大小后即停止,跳过元素子树的样式和布局等大部分渲染;当元素接近视口时,浏览器不再添加 `size` 包含项,而是开始绘制和点击测试该元素的内容,从而及时完成渲染工作。

取 `hidden` 值可以让内容(无论是否在屏幕上)保持不渲染,同时利用缓存渲染状态的优势:`content-visibility: hidden` 具有未渲染内容和缓存渲染状态的所有优势,与 `auto` 在屏幕外提供的优势相同;但与 `auto` 不同,它不会自动开始在屏幕上渲染,从而获得更多控制权,可隐藏元素内容后快速取消隐藏。

这两个属性让 CSS 告诉浏览器如何对元素进行布局和渲染,在特定场景下可以让页面在布局和渲染过程中尽可能避免重排和重绘,减少相应开销。制作动画时,除了使用动画友好的属性之外,还要尽可能减少重排和重绘——`contain` 和 `content-visibility` 正好吻合这一原则,可用于优化动画,使其更为流畅。

## 案例:圣诞飘雪动画优化

接下来通过实际用例验证前文的理论。假设需要构建一个圣诞飘雪的动画效果:

实现方式有很多种,最终呈现的动画效果有所差异。

## 测试和调试动画的流畅度

掌握理论之后,仍需通过工具验证。浏览器开发者工具使测试、调试以及检查哪个阶段响应哪个属性变得非常简单。制作流畅动画的过程中,必须掌握通过调试工具来调试和优化动画的方法。

以下用三种不同方式构建一个相同的动画效果——自定义复选框按钮:

```HTML
<div class="checkbox">
    <input type="checkbox" id="checkbox">
    <label for="checkbox" class="label">Scale(Click Me)</label>
</div>
```

**方式一:改变尺寸(`width` 和 `height`)**

```CSS
@layer animation {
    .label::after {
        width: 0;
        background-color: transparent;
        transition: all 0.25s ease-in-out;
    }
    input[type="checkbox"]:checked ~ .label::after {
        width: 100%;
        background-color: currentColor;
    }
}
```

> Demo 地址：https://codepen.io/airen/full/gOqVPdP

**方式二:通过 `clip-path` 控制**

```CSS
@layer animation {
    .label::after {
        clip-path: inset(100%);
        background-color: transparent;
        transition: all 0.25s ease-in-out;
    }
    
    input[type="checkbox"]:checked ~ .label::after {
        clip-path: inset(0%);
        background-color: currentColor;
    }
}
```

> Demo 地址：https://codepen.io/airen/full/RwvXrOW

**方式三:使用 `scale`**

```CSS
@layer animation {
    .label::after {
        scale: 0;
        background-color: transparent;
        transition: all 0.25s ease-in-out;
    }
    input[type="checkbox"]:checked ~ .label::after {
        scale: 1;
        background-color: currentColor;
    }
}
```

> Demo 地址：https://codepen.io/airen/full/ExrqPJG

对[第一个示例](https://codepen.io/airen/full/gOqVPdP)更改 `width`、`height` 后查看性能火焰图,可以看到发生了四个阶段:样式计算、布局、绘制和合成。该方法的直接问题是 `width` 和 `height` 需要计算布局并在动画的每一帧上绘制结果,成本高昂,通常导致错失 `60fps`。

使用 `clip-path` 这样的属性(第二个示例)时,看不到布局阶段:浏览器知道该属性不影响布局,跳过布局阶段,只触发绘制和合成。虽然比为 `width`、`height` 做动画更好,缺点是仍然触发绘制。

切换 `scale` 或 `transform` 这样的属性(第三个示例)时,看不到布局或绘制阶段:浏览器知道动画元素只改变其位置,避免计算几何形状和绘制样式,重用上一帧的信息将其移动到屏幕上。

仔细观察第一帧和最后一帧会发现两个绘制事件——这是优化过程的一部分:动画化 `transform` 或 `scale` 属性是创建新图层的原因之一。浏览器可以将 DOM 划分为不同的图层(不同区域或图像),在合成阶段拼接在一起;它们足够智能,只在需要时重绘一个图层,甚至重绘某个图层的特定区域,称为增量重绘,可视为不同的缓存级别。

打开浏览器"图层"(Layer)选项:第一个示例中,复选框在选中和未选中时,整个绘制图层是在整个页面的文档层上进行的;第二个示例(`clip-path`)也是如此;第三个示例(`scale`)有所不同,只在 `.label::after` 层进行绘制。

这可能已经足够好,因为就像容器上的动画一样,它也可以加速。若要确保添加动画效果的元素有自己的合成器层,可以添加 `will-change`:

```CSS
@layer animation {
    .label::after {
        background-color: transparent;
        transition: all 0.25s ease-in-out;
    }

    input[type="checkbox"]:checked ~ .label::after {
        background-color: currentColor;
    }

    .size {
        will-change: width;
    }

    .size::after {
        width: 0;
    }
    
    input[type="checkbox"]:checked ~ .size::after {
        width: 100%;
    }

    .clip-path {
        will-change: clip-path;
    }

    .clip-path::after {
        clip-path: inset(100%);
    }
    
    input[type="checkbox"]:checked ~ .clip-path::after {
        clip-path: inset(0%);
    }

    .scale {
        will-change: scale;
    }

    .scale::after {
        scale: 0;
    }
    
    input[type="checkbox"]:checked ~ .scale::after {
        scale: 1;
    }
}
```

> Demo 地址：https://codepen.io/airen/full/MWLNyGx

仔细观察可以发现,只有 `scale` 元素才因 `will-change` 获得了独立的合成层。

独立的合成层虽好,但需要注意:太多图层意味着消耗更多内存,高端设备通常没问题,低端设备会出问题;图层像素信息必须发送到 GPU。图层适合避免重绘某些区域,但不应该过度使用。

创建新图层的常见方式如下:

- 3D CSS 属性,例如 `rotateY()`、`rotateZ()`、`translateZ()`、`perspective`
- `transform` 和 `opacity` 属性的动画
- 视频或画布等加速元素
- 具有较低 `z-index` 的同级元素,该元素有自己的图层
- `position: fixed` 的元素
- 具有 `will-change: transform` 属性的提示
- 具有 `mix-blend-mode` 属性的元素

启动复合属性的动画是创建新图层的原因之一,这个过程称为图层提升,与之相关联的是两个绘制事件——这就是上述示例第一帧和最后一帧出现绘制事件的原因。

图层越复杂,浏览器绘制它所需的时间越长:DOM 节点数量、复杂的 CSS 选择器以及滤镜、阴影之类的昂贵属性都会影响总渲染时间,保持代码尽可能简单非常重要。

合成图层是在 GPU 上发生的过程:CPU 准备每个图层的图像并发送到 GPU 组合,因为 GPU 在这类任务上表现出色。这个阶段发生的动画称为硬件加速。

使用浏览器调试工具调试动画时,需要关注与动画相关的重要参数,例如每秒帧数(**FPS**)、CPU、布局和绘制等。详见《[分析运行时性能](https://developer.chrome.com/docs/devtools/performance?hl=zh-cn)》一文,其中详细阐述了如何在 Chrome 浏览器中分析性能(包括动画性能)。每款现代浏览器调试工具在查看和分析运行时性能时略有不同,具体请参阅各浏览器官方文档。

## 实践策略汇总

为用户提供流畅动画对用户体验至关重要;当动画不流畅或占用过多系统资源时,会影响体验和页面性能。以下策略可以确保动画既引人入胜又性能出色:

### 优先考虑性能

- 性能至关重要。追求以每秒 `60` 帧(FPS)运行的平滑动画,以确保无缝的用户体验。
- 在各种设备和浏览器上测试动画,找出潜在的性能瓶颈。

### 使用硬件加速

- 利用硬件加速将动画渲染卸载到设备的 GPU,确保动画更加流畅。
- 将动画应用于 `transform` 和 `opacity` 属性,可以触发硬件加速,使动画在 GPU 上运行。
- 通过在动画元素上使用 `will-change` 属性,提前告知浏览器该元素将发生动画效果,使浏览器优化渲染过程。

### 优化 CSS 动画

- 尽量减少昂贵的 CSS 属性在动画中的使用,如 `width`、`height` 和 `margin`。
- 更倾向于使用 `transform` 和 `opacity` 进行动画以获得更好的性能。
- 使用 `will-change` 属性向浏览器暗示元素将进行动画。
- 使用 `contain` 和 `content-visibility` 进一步优化页面性能。
- 使用视图过渡 API 等现代 CSS 特性来制作转场动画。

### 优化关键帧动画

- 尽可能使用对动画友好的属性,例如 `transform` 和 `opacity`,而不是 `top`、`left` 等属性,以利用硬件加速。
- 避免不必要的关键帧:仅在必要的位置设置关键帧,减少资源消耗。

### 防抖和节流

- 使用防抖和节流技术控制动画更新的频率,防止不必要的重新渲染。

### 使用 `requestAnimationFrame`

- 对于由 JavaScript 驱动的动画,使用 `requestAnimationFrame` 方法替代 `setTimeout` 或 `setInterval`,确保动画在每个浏览器重绘周期之前运行。
- 它有助于将动画与浏览器的重绘周期同步,使性能更加顺畅。

### 避免布局抖动

- 动画过程中尽量减少对元素布局的更改,避免触发布局抖动。
- 批量进行 DOM 修改,并使用 CSS 类进行有效更新。

### 减少复杂度和资源消耗

- 避免过度绘制:减少动画中不必要的元素绘制,减少页面的重绘和重排。
- 控制帧率和缓动函数:适当控制帧率和缓动函数,避免产生过多的绘制操作,保持动画平滑自然。

### 避免动画阻塞

- 将 `will-change` 属性设置为 `transform`,预先告知浏览器该元素将进行变换。
- 分离动画和渲染:避免将动画和渲染操作混合在一起,减少阻塞。

### 考虑用户喜好

- 允许用户自定义或禁用动画,以便获得更简单或更快速的体验。
- 尊重系统级别的减少动效的偏好。

### 在真实设备上进行测试

- 在真实设备上测试动画,确保其在不同平台和屏幕尺寸上表现良好。

### 渐进增强

- 将动画作为渐进增强来实施。确保即使在动画被禁用或不受支持的情况下,网站仍然保持功能性和可用性。

### 使用动画性能工具

- 借助浏览器开发者工具的性能分析工具,监测动画的性能指标,识别性能瓶颈并进行优化。

关键在于在视觉吸引力和性能之间找到平衡。经过深思熟虑的实施与优化,高质量动画可以极大增强用户体验。

## 小结

以上内容围绕如何在 Web 开发中创建高性能动画展开,聚焦于属性选择、过度绘制的避免、GPU 图层的合理使用等方面。

**选择合适的属性进行动画**:在现代浏览器中,位置(`translate`)、缩放(`scale`)、旋转(`rotate`)和透明度(`opacity`)是可以在 GPU 上高效进行动画的属性。避免使用影响布局(Layout)和绘制(Paint)的属性,例如改变宽度(`width`)、高度(`height`)、偏移(`top`、`right`、`bottom`、`left`)。GPU 能更有效地处理这些属性的动画,从而提升整体性能。

**避免过度绘制**:过度绘制不仅影响性能,还可能导致卡顿。只在必要的时候进行绘制操作,合理安排动画的时间表、确保动画之间有序执行、通过协同技术合理分布动画的执行时间,可以有效降低系统负担。

**注意内存消耗**:GPU 是独立的计算机,需要存储渲染层图像的内存。减少图层的复杂性、避免不必要的内存消耗(尤其在移动设备上),可以提高动画的运行效率。使用浏览器开发工具的性能面板测量渲染管道,了解动画各阶段的性能影响。

完整的实践要点如下:

- **选择合适的属性进行动画**:位置(`translate`)、缩放(`scale`)、旋转(`rotate`)和透明度(`opacity`)可在 GPU 上高效动画;避免影响布局和绘制的属性。
- **避免过度绘制**:过度的绘制操作影响性能,确保只在有必要的时候绘制,而不是每一帧都触发。
- **注意图层的使用**:GPU 图层用于提高动画性能,但不应滥用;仅在必要情况下使用(3D CSS 属性、transform/opacity 动画、加速元素、固定定位元素等)。
- **合理安排动画**:使用编排技术,而不是同时触发多个动画;确保动画时间表合理分布。
- **优化内存消耗**:减少图层的复杂性,避免不必要的内存消耗,尤其是移动设备。
- **测量渲染管道**:使用浏览器开发工具的性能面板测量渲染管道的各个阶段,了解哪些属性触发了样式、布局、绘制和合成。
- **使用合适的工具**:利用图层面板和实时 3D 查看器查看当前图层情况,以及为什么创建了新的图层。
- **避免过度复杂的图层**:图层越复杂,绘制时间越长;简化代码,避免过度使用复杂的 CSS 选择器和昂贵的属性。
- **了解硬件加速**:理解动画在 GPU 上的硬件加速原理,以更好地掌握优化方法。

综合运用这些技巧和实践,可以提高 Web 动画的性能,确保用户体验流畅而不卡顿。

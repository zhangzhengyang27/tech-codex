# in运算符与属性检测

## 概念说明

最早的 JavaScript 只有一个非常弱的对象系统:在语法上更像 Java,而在实现上却谁也不像。理解 `in` 运算符与属性检测,需要从 JavaScript 1.0~1.3 的对象模型、属性可见性、包装类与原型链一路梳理下来,最终才能完整解释标题表达式 `1 in 1..constructor` 的求值过程。

## 核心要点

- ECMAScript 规范明确定义:对象是零到多个属性的集合(In ECMAScript, an object is a collection of zero or more properties)。
- JavaScript 1.0 使用"类抄写"技术创建对象,不支持继承;1.1 起才引入原型继承。
- 向未声明的变量名赋值会隐式创建全局变量,全局变量绑定为全局对象(global)的属性;闭包与对象都具有实现变量环境的能力,分别构成"函数闭包"与"对象闭包",其环境统称为"域(Scope)"。
- 属性可见性(可列举性)在早期 JavaScript 中没有规范约定,ECMAScript 5 之后通过"属性的性质(attributes)"(可写性、可列举性、可配置性)与属性描述符统一管理。
- 子类实例重写属性时,实际是在自有属性表中添加新项,不改变原型中同名属性的值。
- 除 `Undefined` 外,所有基本类型数据都有自己的包装类;包装过程发生在函数调用运算 `( )` 的处理过程中,仅"对象属性存取"行为本身不触发值类型向包装类型的转换。
- 字面量与标识符在文本解析阶段就被区分:字面量直接处理,标识符需要建立"引用"来处理;`1.toString` 报错来自浮点数字面量解析,`1..constructor` 则是浮点数字面量 `1.` 的 `.constructor` 属性存取。
- 属性存取结果是不确定的:属性不是自有时,值由原型决定;属性是存取方法时,值由求值决定。

## JavaScript 1.0~1.3 中的对象

在 JavaScript 1.0 的时候,对象不支持继承,使用的是称为"类抄写"的技术来创建对象:

```javascript

function Car() { this.name = "Car"; this.color = "Red";}
var x = new Car();

```

在 `Car()` 这个函数中,该函数以"类"的身份声明了一系列的属性(Property)。使用 `new Car()` 创建的"类的实例"(也就是对象 `this`)就具有了这些属性。这种"类 -> 对象"的模型简单而粗糙,但 JavaScript 1.0 时代的对象就是如此,并且直到现在 JavaScript 的对象仍然如此——ECMAScript 规范明确定义:对象是零到多个属性的集合。

JavaScript 1.0 的对象系统有类,语义上是"对象创建自类",在表面上"看起来"有一些继承性:一个对象必然继承了它的类所声明的那些性质(属性)。但 1.0 版存在的时间很短,大多数人都不记得 JavaScript"有类,而又不支持类的继承"这件事,从而将从 JavaScript 1.1 才开始具有的原型继承作为它最主要的面向对象特征。

在这个阶段,JavaScript 中全局环境和全局变量的设计已经成熟:向未声明的变量名赋值,会隐式地创建一个全局变量;全局变量会被绑定为全局对象(global)的属性。这样一来,JavaScript 的变量环境(或全局环境)与对象系统关联了起来。又由于 JavaScript 实现了带有闭包性质的函数,"闭包"也成了环境的管理组件——闭包与对象都具有实现变量环境的能力。因此,这个阶段 JavaScript 提出了"对象闭包"与"函数闭包"两个概念,把它们用来实现的环境称为"域(Scope)"。这些概念和语言特性一直支持 JavaScript 走到 1.3 版本,并随 ECMAScript ed3 确定下来。

JavaScript 1.3 时代的执行环境,可以从布兰登·艾奇的开源项目 Narcissus(用 JavaScript 实现的一个完整的 JavaScript 1.3)中读到。在这个项目中,对象和函数所创建的闭包都统一由一个简单的对象表示,称为 scope:

```

scope = { object: < 创建本闭包的对象或函数 >, parent: < 父级的 scope>}

```

因此,所谓"使用 with 语句创建一个对象闭包"就被简单地实现为:

```javascript

// code from $(narcissus)/src/jsexec.js...

// 向 x 所代表的 scope-chain 表尾加入一个新的 scope
x.scope = {object: t, parent: x.scope};
try { // n.body 是 with 语句中执行的语句块
  execute(n.body, x); // 指在该闭包（链）`x`中执行上述语句
}
finally {
  x.scope = x.scope.parent; // 移除链尾的一个 scope
}

```

可见 JavaScript 1.3 时代的执行环境,其实就是一个闭包链的管理,而且这种闭包既可以是对象的,也可以是函数的。尽管在静态语法说明或描述时它们被称为作用域或域(Scope),在动态环境中被称为上下文(Context),但本质上是同样的一堆东西。

综合来看:JavaScript 中的对象本质上是属性集,可以视为一个键值列表,对象继承是由这样的列表构成的、称为原型的链;执行的上下文就是函数或全局的变量表,同样可以表达为一个键值列表,执行环境也可视为一个由该键值列表构成的链。在 JavaScript 1.3 以及 ECMAScript ed3 的整个时代,这门语言仅仅依赖键值列表和基于它们的链实现并完善了它最初的设计。

## 属性访问与可见性

从一开始,JavaScript 就有一个没有说清楚的东西:属性名的可见性。这种可见性在 OOP(面向对象编程)中有专门的、明确的说法,但在早期的 JavaScript 中,可以简单理解为"一个属性是否能用 for…in 语句列举出来":可以被列举就是可见的,否则称为隐藏的。

任何对象都有 "constructor" 这个属性,缺省指向创建它的构造器函数,并且它应当是隐藏的属性。但在早期的 JavaScript 中,这个属性如何隐藏没有规范约定。例如在 JScript 中,它就是一个特殊名字,只要是这个名字就隐藏;而在 SpiderMonkey 中,当用户重写这个属性后,它就变成了可见的。

后来 ECMAScript 约定了"属性的性质(attributes)",即现在所知的三种性质:

- 可写性
- 可列举性(可见性)
- 可配置性

ECMAScript 约定:"constructor" 缺省是一个不可列举的属性;使用赋值表达式添加属性时,属性的可列举性缺省为 `true`。这样一来,"constructor" 在可列举性上的行为就变得可预期了。类似于此,ECMAScript 约定了读写属性的方法,以及在属性中访问、操作性质的全部规则,统一使用"属性描述符"来管理这些规则——这使得 ECMAScript 规范进入了 5.x 时代。相较于早期的 3.x,5.x 没有太多改变,主要是从语言概念层面上实现了"大一统":所有浏览器厂商与引擎开发者都遵循这些规则,为后续 ECMAScript 6 的发布铺平了道路。

到目前为止,JavaScript 中的对象仍然是简单的、原始的、使用 JavaScript 1.x 时代基础设计的原型继承,每一个对象仍然都只是简简单单的一个"属性包"。

## 从原型中继承来的属性

对绝大多数对象来说,"constructor" 是从它的原型继承来的一个属性,这有别于它"自有的(Own)"属性。在原型继承中,子类实例重写属性时,实际发生的行为是"在子类实例的自有属性表中添加一个新项"——这并不改变原型中相同属性名的值,但子类实例中的属性性质以及值覆盖了原型中的。这是原型继承几乎公开的全部秘密。

使用原型继承来的属性时,有两种可能的行为,取决于属性的具体性质(属性描述符的类型):如果是数据描述符(d),那么 `d.value` 总是指向这个数据的值本身;如果是存取描述符,那么 `d.get()` 和 `d.set()` 将分别指向属性的存取方法。存取方法(get/setter)并不一定关联到数据,也并不一定是数据的置值或取值,某些情况下可能用作特殊用途,例如模拟在 VBScript 中常常出现的"无括号的方法调用":

```javascript

excel = Object.defineProperty(new Object, 'Exit', { get() { process.exit(); }});
// 类似 JScript/VBScript 中的 ActiveObject 组件的调用方法
excel.Exit;

```

当用户不使用属性赋值或 `defineProperty()` 等方法来添加自有属性时,属性访问会(默认地)上溯原型链直到找到指定属性。这在一定程度上成就了"包装类"这一特殊的语言特性。

## 包装类:字面量与标识符

包装类是 JavaScript 从 Java 借鉴来的特性之一,它使得用户代码可以用标准的面向对象方法来访问普通的值类型数据,于是"一切都是对象"就变成了现实。例如下面这个示例中使用的字符串常量 x:

```javascript

x = "abc";
console.log(x.toString());

```

在使用 `x.toString()` 时,JavaScript 会自动将"值类型的字符串("abc")"通过包装类变成一个字符串对象。这类似于执行:

```javascript

console.log(Object(x).toString());

```

这个包装的过程发生于函数调用运算"( )"的处理过程中,或者将 `x.toString` 作为整体来处理的过程中。也就是说,仅仅是"对象属性存取"这个行为本身,并不会触发一个普通"值类型数据"向它的包装类型转换。

除了 `Undefined`,基本类型中的所有值类型数据都有自己的包装类,包括符号(Symbol),以及布尔值。这使得这些值类型的数据也可以具有与之对应的包装类的原型属性或方法。这些属性与方法引用自原型,而不是自有数据——值类型数据本身并不是对象,因此不可能拥有自有的属性表。

**字面量与标识符的区分**

通常情况下,开发人员将标识符直接称为名字(在 ECMAScript 规范中,全称是"标识符名字(IdentifierName)"),而字面量是一个数据的文本表示,标识符通常用作后者的名字标识。对于这两种东西,ECMAScript 的处理机制并不太一样,并且在文本解析阶段就会把二者区分开来:

```javascript

// var x = 1;
1;
x;

```

其中"1"是字面量值,JavaScript 直接处理它;而 x 是一个标识符,需要建立一个"引用"来处理。再看下面的代码(假设成立):

```

1.toString

```

它作为"整体"需要被创建为一个引用,以作为后续计算的操作数(取成员值,或仅是引用该成员)。就它们同是"引用"这一事实而言,"1.toString"与"x"在引擎级别有些类似。

然而在数字字面量中,"1.xxxxx" 这样的语法是有含义的——它是浮点数的表示法。所以 `1.toString` 这样的语法在 JavaScript 中会报错,这个错误来自浮点数的字面量解析过程,而不是"`.` 作为存取运算符"的处理过程。JavaScript 中浮点数的小数位可以为空,因此"1."和"1.0"将作为相同的浮点数被解析出来。既然"1."表示浮点数,那么"1..constructor"表示的就是该浮点数字面量的".constructor"属性。

## 表达式「1 in 1..constructor」的求值

标题中的表达式:

```javascript

1 in 1..constructor

```

其实是一个表达式。在语义上,它与如下表达式等义:

```text

# 检查对象“constructor”是否有属性名“1”
> 1 in Object(1.0).constructor
false
# (同上)
> 1 in 1..constructor
false

```

## 属性存取的不确定性

除了存取器(get/setter)带来的不确定性之外,JavaScript 的属性存取结果还受到原型继承(链)的影响。上例中的表达式值并不恒为 `false`:

```text

# 修改原型链中的对象
> Number[1] = true; // or anything
# 影响到上例中表达式的结果
> 1 in 1..constructor
true

```

原因在于:`Object(1.)` 意味着将数字"1.0"封装成它对应的包装类的一个对象实例(x):

```javascript

x = new Number(1.0);

```

而 "x.constructor" 不是自有属性;由于 x 是 `Number()` 这个类/构造器的子类实例,该属性实际继承自原型链上的 "Number.prototype.constructor" 属性。缺省情况下,"aFunction.prototype.constructor" 指向这个函数自身,也就是说 "Number.prototype.constructor" 与 "1..constructor" 相同,且都指向 Number() 自身。所以上面的示例中,添加了 "Number[1]" 这个下标属性之后,标题中表达式的值就变了。

## 小结

标题 `1 in 1..constructor` 看起来像其他语言中的循环或迭代,在代码文本上也像是一个范围检查(语义上像"1 在某个 1…n"的范围中),但事实上,它涵盖了从对象成员存取这样的基础话题,到包装类这样的复杂概念的全部知识。更重要的是,源于 JavaScript 面向对象系统的独特设计,对象属性存取的结果总是不确定的:如果属性不是自有的,那么它的值就是原型决定的;当属性是存取方法时,那么它的值就是求值决定的。

# super与类继承

## 概念说明

JavaScript 面向对象模型的形成经历了两个阶段：JavaScript 1.0 连继承都没有，但实现了以"类抄写"为基础的、基本的面向对象模型；JavaScript 1.1 开始提出原型继承，并在后来逐渐完善。

从 JavaScript 1.1 起，从概念上讲，对象就是一个从原型对象衍生出来的实例，子级对象具有原型对象的全部特征。然而子级对象必然与原型对象有所不同——如果没有不同，就没有必要派生出一级关系，直接使用原型的那个抽象层级即可。所以，有了原型继承带来的子级对象之后，还需要有让它们跟原型表现得有所不同的方法。JavaScript 1.0 的"类抄写"特性正好可以承担这个职责：通过"抄写"往对象（也就是构造出来的 this）上添加内容，制造这种不同。

因此，JavaScript 1.1 面向对象系统的设计原则是：**用原型来实现继承，并在类（也就是构造器）中处理子一级的抽象差异**。示例代码如下：

```javascript

// 这里用于处理“不同的东西”
function CarEx(color) {
  this.color = color;
  /* ... */
}

// 这里用于从父类继承“相同的东西”
CarEx.prototype = new Car("Eagle", "Talon TSi", 1993);

// 创建对象
myCar = new CarEx("red")

```

一个对象系统既能处理继承关系中"相同的东西"，又能处理"不同的东西"，也就意味着它能处理基于对象的"全部的东西"。正是由于这种概念上的完整性，从 JavaScript 1.1 开始，一直到 ECMAScript 5，对象系统的设计上都没有再出现突破。

## 为什么要有 super

子级对象除了要继承父级的"全部的东西"之外，还要继承"全部的能力"。如果只继承全部的东西，子级相对于父级只是系统的静态变化，没有行为层面的延续。

传统的 JavaScript 只能在一定程度上继承来自原型的"部分能力"：原型有一个方法，子级的实例就可以使用这个方法，这时子级继承了原型的能力。然而，如果子级对象重写了这个方法，在 ECMAScript 6 之前，原型中的这个方法相对于子级对象就失效了——原则上在子级对象中再也找不到这个原型的方法。

这个问题非常致命：这意味着子级对象必须重新实现原型中的能力，才能安全地覆盖原型中的方法；如果每个子级对象都要重新实现一遍原型，继承性就毫无意义了。问题的根源在于 JavaScript 1.0~1.1 设计面向对象模型时的原始缺陷："类抄写"只能处理显而易见的属性、属性名、属性性质等，无法处理"方法/行为"背后逻辑的继承。JavaScript 1.1 之后的各种大规模系统中，都需要不断修补这个问题：在"类抄写"导致的子类覆盖中，父类的能力丢失了。

为了解决这种继承问题，ECMAScript 6 提出了标准解决方案，即 super 关键字。ECMAScript 6 约定：如果父类中的名字被覆盖了，可以在子类中用 super 来找到它们。

## super 指向什么

### super 只能在方法中使用

super 出现的目的是解决父类能力丢失的问题，由此可以理解一个语言设计：在 JavaScript 中，super 只能在方法中使用。所谓方法，就是"类的，或者对象的能力"，super 正是用来弥补覆盖父类同名方法所导致的缺陷，因此只能出现在方法之中。

### [[HomeObject]] 内部槽

实现 super 的核心难点在于"怎么找到父类"。在传统 JavaScript 中，所谓方法就是函数类型的属性，它与一般属性并没有什么不同（可以被不同的对象抄写来抄写去），这正是"类抄写"机制得以实现的核心依赖条件之一。但也正因如此，传统方法没有"归属于哪个类或哪个对象"的性质，根本上找不到它自己的类，进而也找不到它的父类。

实现 super 的关键，是为每一个方法添加一个"它所属的类"的性质，这个性质被称为"主对象（HomeObject）"。ECMAScript 6 之后通过方法声明语法得到的"方法"，虽然仍然是函数类型，但与传统的"函数类型的属性（即传统的对象方法）"存在一个根本上的不同：这些新方法增加了一个内部槽，用来存放主对象，也就是 ECMAScript 规范中名为 [[HomeObject]] 的内部槽。主对象的登记有三种情况：

- 类静态方法（使用 static 声明的方法）：主对象就是这个类本身，例如 AClass；
- 类一般方法：该方法的主对象是该类所使用的原型，即 AClass.prototype；
- 对象字面量方法：方法的主对象是对象本身。

### 对象字面量方法为何也能使用 super

这里存在一个问题：super 指向的是父类，但对象字面量并不是基于类继承的，为什么字面量中声明的方法可以使用 super.xxx？对象本身不是类，super"指向父类"的含义岂不是就没了？

答案回到 JavaScript 1.1 的那项基础设计——"用原型来实现继承"：原型就是一个对象，本质上子类或父类都是对象；类声明只是这种继承关系的一个载体，真正继承的是原型对象本身。既然子类和父类都可能是（或者说必须是）对象，那么对象上的方法访问"父一级的原型上的方法"就是必然存在的逻辑。因此，在 JavaScript 中，只要是方法——并且这个方法可以在声明时明确它的主对象（HomeObject）——就可以使用 super，对象方法也就可以引用到它父级原型中的方法了。

### 通过 HomeObject 找到父类

当每一个方法都在其内部登记了主对象之后，ECMAScript 约定：在方法中取出这个主对象 HomeObject，它的原型就一定是父类。因为方法登记的是它声明时所在的类或对象，而"通过原型继承得到子类"反过来使用，就得到了父类的概念。

## super.xxx() 的调用机制

super.xxx 在语法上只是属性存取，但 super.xxx() 是方法调用，而且 super.xxx() 是表达式计算中罕见的、在双表达式连用中传递引用的一个语法。关键不在于 super.xxx 如何存取属性，而在于 super.xxx 存取到的属性在 JavaScript 内核中是一个"引用"。按照语法设计，这个引用包括了左侧的对象，并且在它连用"函数调用（）"语法的时候，将这个左侧的对象作为 this 引用传入给后者。

按照传统属性存取语法推论，"在 super.xxx() 调用时，函数 xxx() 中得到的 this 是什么"的答案应该是 super，但这并不是真的。

### super.xxx() 中的 this 值

在 super.xxx() 这个语法中，xxx() 函数中得到的 this 值来自当前环境，而不是 super。super 总是在一个方法（如下例中的 obj.foo 函数）中引用：

```javascript

obj = {
  foo() { super.xxx(); }
}

// 调用 foo 方法
obj.foo();

```

调用 foo() 方法时，obj 会传入作为 this，所以 foo() 函数内的 this 就是 obj。super.xxx() 调用父类的 xxx() 方法时，期望传入的当前实例正是 foo() 函数内的那个 this：继承来的行为应该施加给现实中的当前对象，而不是原型。所以在这几个操作符的连续运算中，只需要把当前函数中的那个 this 传给父类 xxx() 方法。

具体机制是：super.xxx 在语言内核上是一个"引用"，ECMAScript 将这个语法标记成"Super 引用（SuperReference）"，并为这个引用专门添加了一个 thisValue 域（函数上下文中也有一个相同名字、相同含义的域）。ECMAScript 约定优先取 Super 引用中的 thisValue 值，然后再取函数上下文中的。事实上，这个 thisValue 是在执行引擎发现 super 这个标识符（GetIdentifierReference）的时候，就从当前环境中取出来并绑定给 super 引用的。

::: tip 两个关键细节
- super 关键字所代表的父类对象，是通过当前方法的 [[HomeObject]] 的原型链来查找的；
- this 引用是从当前环境所绑定的 this 中抄写过来，并绑定给 super 的。
:::

### 构造方法中的"先有鸡还是先有蛋"问题

上述两个细节解释了构造方法中的一条重要限制。构造方法中的 this 引用（也就是将要构造出来的对象实例）事实上是由祖先类创建的：刚进入构造方法时，this 引用还没有值，必须让父类以及祖先类先把 this 构造出来。这里存在一个"先有鸡还是先有蛋"的矛盾：一方面构造方法中要调用父类构造方法来得到 this；另一方面调用父类方法的 super.xxx() 需要先从环境中找到并绑定一个 this，概念上无解。

ECMAScript 为此约定：只能在调用了父类构造方法之后，才能使用 super.xxx 的方式来引用父类的属性或调用父类的方法——也就是访问 SuperReference 之前必须先调用父类构造方法（这称为 SuperCall，在代码上就是直接的 `super()` 调用）。这其中还隐含了一个限制：在调用父类构造方法的 `super()` 代码中，super 不绑定 this 值，也不在调用中传入 this 值，因为这个阶段根本还没有 this。

### super() 如何找到父类构造方法

调用父类构造方法时，事实上通过 [[HomeObject]] 找不到 super。以 new MyClass() 为例，类 MyClass 的 constructor() 方法声明时，它的主对象是 MyClass.prototype 而不是 MyClass——后者是静态类方法的主对象，而 constructor() 方法只是一般方法，不是静态类方法（没有 static 关键字）。所以在 MyClass 的构造方法中访问 super 时，通过 HomeObject 找到的将是原型的父级对象，而不是父类构造器：

```javascript

class MyClass extends Object {
  constructor() { /* ... */ } // <- [[HomeObject]] 指向 MyClass.prototype
}

```

super() 的语义是"调用父类构造方法"，也就是 `extends` 所指定的 Object()。在当前构造方法中无法通过 [[HomeObject]] 找到父类构造方法的情况下，JavaScript 的处理方式是：从当前调用栈上找到当前函数——也就是 new MyClass() 中的当前构造器，并返回该构造器的原型作为 super。类的原型就是它的父类，这又是把"通过原型继承得到子类"的概念反过来使用。

### 为什么构造方法不是静态的

一个自然的疑问是：为什么不直接将 constructor() 声明为类静态方法？类静态方法的 [[HomeObject]] 就是 MyClass 自己，似乎这样就不必换个方式查找 super。

根本原因在于：构造方法 constructor() 中也可以使用 super.xxx()，与调用父类一般方法（即 MyClass.prototype 上的原型方法）的方式类似。一方面 super() 需要将父类构造器作为 super，另一方面 super.xxx 需要引用父类原型上的属性，这两个需求无法通过同一个 [[HomeObject]] 来实现。这个问题只出现在构造方法中，并且只与 super() 冲突，所以 super() 中的 super 采用了另一种方式（在调用栈上查找当前函数）来查找当前类以及父类，并作为特殊语法处理。

至此，JavaScript 通过当前方法的 [[HomeObject]] 找到了 super，也找到了它的属性 super.xxx（称为 Super 引用，SuperReference），并为这个 SuperReference 绑定了一个 thisValue，随后执行 super.xxx() 调用。

## 实践要点

1. 只能在方法中使用 super，因为只有方法有 [[HomeObject]]。
2. super.xxx() 是对 super.xxx 这个引用（SuperReference）作函数调用操作，调用中传入的 this 引用是在当前环境的上下文中查找的。
3. super 实际上是在通过原型链查找父一级的对象，而与它是不是类继承无关。
4. 如果在类的声明头部没有声明 extends，那么在构造方法中也就不能调用父类构造方法。

> 注：第 4 个要点涉及两个问题：其一是它显然（显式的）没有所谓 `super`；其二是没有声明 extends 的类其实是采用传统方式创建的构造器，后者不在本文讨论范围内。

# 认识 HTTP 协议

## 概念说明

HTTP 请求的场景相对复杂，对应的 HTTP 协议也是各式各样的，因此很多人认为内容太多太杂、学习 HTTP 协议性价比太低。实际上，日常开发中经常使用的 cookie、浏览器缓存机制、各种形式的网络连接（比如 WebSocket）都与 HTTP 协议有密切关系。对前端开发来说，HTTP 协议是最核心的网络知识之一，其内容虽然繁多，但主线可以概括为两块：协议本身的设计与演变，以及前端最相关的典型场景（Cookie、缓存、双向通信）。

## 认识 HTTP 协议

在网络请求过程中，当服务端建立起与客户端的 TCP 连接之后，服务端会持续监听客户端发起的请求。客户端发起 HTTP 请求，请求内容通常包括请求方法、请求的资源等；服务端收到请求后进行回复，回复内容通常包括 HTTP 状态、响应消息等。

网络请求的过程包括两个步骤：客户端发送请求，服务器返回响应。这就是 **HTTP 协议的主要特点：遵循经典的"客户端-服务端"模型**。

除此之外，HTTP 协议还被设计得简单易读。在 HTTP/2 之前，HTTP 协议是语义可读的，可以直观地获取其中的内容：

- HTTP 请求方法：代表着客户端的动作行为（`GET`-获取资源/`POST`-提交资源/`PUT`-修改资源/`DELETE`-删除资源）。
- HTTP 状态码：代表着当前请求的状态（`1XX`-提示信息/`2XX`-成功/`3XX`-重定向/`4XX`-客户端错误/`5XX`-服务端错误）。
- HTTP 消息头：客户端和服务端通过`request`和`response`传递附加信息。

通过 HTTP 协议，可以看到该请求是否成功、错误原因是哪些、请求是否使用了缓存、请求和响应数据是否符合预期等。

那么 HTTP/2 之后发生了什么？这要从 HTTP 协议的演变过程说起。

### HTTP 协议的演变

HTTP 协议从被创造以来一直在不断演变：从 HTTP/1.0、HTTP/1.1，到 HTTP/2、HTTP/3，协议在保持简单性的同时拓展了灵活性，提供越来越快、更加可靠的传输服务。

**HTTP/1.0 到 HTTP/1.1，主要实现了对 TCP 连接的复用。** 最初在 HTTP/1.0 中，每一对 HTTP 请求和响应都需要打开一个单独的 TCP 连接，资源消耗很大。HTTP/1.1 引入了持久连接的概念：通过设置 `Connection` 头部为 `keep-alive`，可以让 TCP 连接不关闭。该功能避免了 TCP 连接的重新建立，客户端可在已建立的 TCP 连接上长时间地对同一个服务端发起请求。

**HTTP/1.1 到 HTTP/2，主要实现了多个请求的复用。** HTTP/2 通过将 HTTP 消息拆分为独立的帧、进行交错发送，实现在同一个连接上并行多个请求，从而减少网络请求的延迟。为了实现多路复用，HTTP/2 对 HTTP 头部进行了二进制编码，因此不再语义可读。除此之外，HTTP/2 还实现了 Header 压缩、服务端主动推送、流优先级等能力。

**HTTP/2 到 HTTP/3，主要实现了基于 UDP 协议、更快的传输。** HTTP/3 使用了基于 UDP 的 QUIC 协议，实现又快又可靠的传输。UDP 协议本身不负责可靠传输（没有重传与拥塞控制），因此通信开销更小、速度更快；同时 QUIC 协议在应用层负责纠错、重建丢失的数据，解决了 UDP 传输丢包的问题。

总的来说，**HTTP 协议的演变过程主要围绕着传输效率和速度上的优化**，可以通过升级 HTTP 协议来优化前端应用。日常工作中同样可以借鉴 HTTP 协议的优化手段，例如使用资源压缩、资源复用等技术手段优化前端性能——技术常常是通用的，很多看似不相关领域的技术演进都值得思考和参考。

## HTTP Cookie

HTTP 协议是无状态的：在同一个 TCP 连接中，先后发起的请求之间没有任何关系。这给服务端带来了挑战——用户在同一个网站中进行连续操作时，服务端无法知道这些操作来自哪里。

使用 HTTP Cookie 可以解决这个问题。当服务端将 HTTP 响应返回给客户端时，通过在响应头里添加一个 `Set-Cookie` 信息，浏览器收到带 `Set-Cookie` 的响应后会将 Cookie 保存；之后发送给该服务端的每个请求都会自动带上 Cookie 信息，服务端根据 Cookie 就能取得客户端的数据信息。

由于 Cookie 由浏览器识别并自动保存和发送，默认情况下浏览器关闭后它会被自动删除；也可以通过指定过期时间（`Expires`）或有效期（`Max-Age`），让 Cookie 获得更长的有效期。

需要注意的是，某个网站设置了 Cookie 之后，所有符合条件（有效期、域名、路径、适用站点等）的请求都会自动带上 Cookie。这带来一个 Web 安全隐患：服务端只知道请求来自某个用户的浏览器，却不知道请求本身是否用户自愿发出的。

利用这一漏洞，攻击者可通过一些技术手段（图片地址、超链接等）欺骗用户的浏览器访问曾经认证过的网站，并利用用户的登录态进行操作，可能导致用户信息泄露、资产被转移、在不知情的情况下发送信息等恶劣后果。这就是典型的 Web 安全问题之一：跨站请求伪造（CSRF）。

应对方式之一是校验 HTTP 请求头中的 `Referer` 字段，该字段用以标明请求来源于哪个地址；但由于该字段可能被篡改，只能作为辅助校验手段。防范 CSRF 的有效方法是避免依赖浏览器自动带上的 Cookie 信息：使用其他方式校验用户登录态，例如将用户登录态保存在浏览器缓存中，在发送请求时添加用于标识用户的参数值——现在大多数应用使用 Token 来进行用户标识。

## HTTP 缓存

缓存常被用作性能优化的技术方案之一：通过缓存可以有效减少资源获取的耗时、减少用户等待时长，从而提升用户体验。

通过 HTTP 协议可以设置浏览器对 HTTP 响应资源进行缓存。使用浏览器缓存后，再发起 HTTP 请求时，如果浏览器缓存发现请求的资源已经被存储，它会拦截请求并返回该资源的副本，不再去请求服务端获取资源——既减少了 HTTP 请求的耗时，也能有效缓解服务端压力。

一般来说，HTTP 缓存只能存储 GET 请求的响应内容。对这些响应内容可能存在两种情况：

- 不缓存内容，每次请求都从服务端获取最新的内容；
- 设置了缓存内容，则在有效期内从缓存获取；如果用户刷新或内容过期，则去服务端获取最新的内容。

给 GET 请求设置缓存依靠请求和响应中的头信息来控制。根据缓存行为，可分为强制缓存和协商缓存两种：

- **强制缓存**：在规定有效期内直接使用缓存。使用方式：服务端通过设置 `Expires` 和 `Cache-Control`，与客户端约定缓存内容的有效时间；若符合缓存条件，浏览器响应 `HTTP 200(from cache)`。
- **协商缓存**：与服务端协商是否使用缓存。使用方式：服务端首次响应时通过 `Last-Modified` 和 `ETag` 响应头标识资源版本，与客户端约定协商缓存的标识；当有效期过后，浏览器将缓存信息中的 Etag 和 Last-Modified 信息分别使用 If-None-Match 和 If-Modified-Since 请求头设置并提交给服务端；若符合缓存条件，服务端响应 `HTTP 304`，浏览器从缓存读数据。

若以上缓存条件均不符合，服务端响应 `HTTP 200`，返回更新后的数据，同时通过响应头更新 HTTP 缓存设置。整个过程可以用下面的流程图表示：

除了 Cookie 和 GET 请求的缓存，客户端和服务端在实现双向通信时同样会依赖 HTTP 协议。

## 客户端服务端双向通信

客户端和服务端的通信方式有很多种，大多数场景下由客户端主动发送数据给服务端；但在特定场景下（如多人协作、在线游戏），客户端还需要和服务端保持实时通信，此时需要使用双向通信。

常见的双向通信方式包括 HTTP 短轮询（polling）、HTTP 长轮询（long-polling）、XHR Streaming、Server-Sent Events、WebSocket 等。

**HTTP 短轮询**是最简单直接的方式：客户端每隔特定时间（比如 1s）向服务端发起请求，获取最新的资源信息。该方式会造成较多的资源浪费，尤其当服务端内容更新频率低于轮询间隔时，服务端资源、客户端资源都被浪费；过于频繁的请求也会给服务端造成额外压力，当服务端负载较高时甚至可能导致雪崩。

**HTTP 长轮询**解决了短轮询的部分问题：客户端向服务端发起请求后，服务端保持住连接，当数据更新响应之后才断开连接，然后客户端重新建立连接并继续等待新数据。此技术的主要问题在于重新连接过程中，页面上的数据可能过时且不准确。

**XHR Streaming** 相比长轮询可以维护客户端和服务端之间的连接，但使用过程中 `XMLHttpRequest` 对象的数量会不断增长，因此需要定期关闭连接来清除缓冲区。

**SSE（Server-Sent Events）** 的思想便是 XHR Streaming，主要基于浏览器中 `EventSource` API 的封装和协议。它对 HTTP 服务开启一个持久化的连接，以 `text/event-stream` 格式发送事件，会一直保持开启直到被要求关闭。

**WebSocket** 实现了浏览器与服务端全双工通信。HTTP 短轮询、长轮询都会带来额外的资源浪费，而 WebSocket 在实现实时通信的同时能更好地节省服务端资源和带宽。

WebSocket 建立在 TCP 协议之上，握手阶段采用 HTTP 协议，但请求头中有以下标识性内容：

- `Connection: Upgrade`、`Upgrade: websocket`：表示这个连接将要被转换为 WebSocket 连接。
- `Sec-WebSocket-Key`：向服务端提供所需的信息，以确认客户端有权请求升级到 WebSocket。
- `Sec-WebSocket-Protocol`：指定一个或多个的 WebSocket 协议。
- `Sec-WebSocket-Version`：指定 WebSocket 的协议版本。

如果服务端同意启动 WebSocket 连接，会在握手过程中的 HTTP 协议中返回包含 `Sec-WebSocket-Accept` 的响应消息，接下来客户端和服务端便建立 WebSocket 连接，并通过 WebSocket 协议传输数据。

由于不再需要通过 HTTP 协议通信、省去请求头等内容设置，WebSocket 数据格式更轻量、通信更高效、性能开销也相应降低。此外，不同于 HTTP 协议，WebSocket 协议没有同源限制，客户端可以与任意服务端通信。

## 小结

HTTP 协议遵循"客户端-服务端"模型，其演变（1.0→1.1 连接复用、1.1→2 多路复用、2→3 基于 UDP 的 QUIC）始终围绕传输效率与速度。对前端而言，三个典型场景与协议紧密相关：无状态的 HTTP 依靠 Cookie 维持会话（并需防范 CSRF）；HTTP 缓存通过强制缓存与协商缓存减少请求耗时、缓解服务端压力；实时双向通信则可在短轮询、长轮询、XHR Streaming、SSE 与 WebSocket 之间按场景选型。

# 页面的请求过程

## 概念说明

浏览器的主要功能是展示网页资源：向服务器发起请求、从服务器获取相关资源，并将网页显示在浏览器窗口中。"在浏览器里面输入 URL，按下回车键，会发生什么？"是考察浏览器运行机制和页面加载流程的经典问题，其内容也贯穿于日常开发，包括前后端联调、网页性能优化等。

理解浏览器中网络请求的完整过程，有助于建立对整个网页渲染链路的认知。

## 页面的请求过程

打开某个网站的页面时，浏览器就会发起网络请求获取该页面的资源。从控制台可以看到这些请求信息：

![](/fe-notes-images/a5905b123304.png)![](/fe-notes-images/ce95a06f6394.png)

在 Network 面板里，能看到所有浏览器发起的网络请求，包括页面、图片、CSS 文件、XHR 请求等，还能看到请求的状态（200 成功、404 找不到、缓存、重定向等）、耗时、请求头和内容、返回头和内容等。

图中第一个就是网站页面的请求，返回 `<html>` 页面。接下来，浏览器会加载页面，同时页面中涉及的外部资源也会根据需要在特定时机触发请求下载，包括 PNG 图片、JavaScript 文件等（示例中没有 CSS 样式请求，是因为样式被直出在 `<html>` 页面内容里了）。

在浏览器输入网页地址、按下回车键后，浏览器的处理过程如下：

- DNS 域名解析（此处涉及 DNS 的寻址过程），找到网页的存放服务器；
- 浏览器与服务器建立 TCP 连接；
- 浏览器发起 HTTP 请求；
- 服务器响应 HTTP 请求，返回该页面的 HTML 内容；
- 浏览器解析 HTML 代码，并请求 HTML 代码中的资源（如 JavaScript、CSS、图片等，此处可能涉及 HTTP 缓存）；
- 浏览器对页面进行渲染呈现给用户（此处涉及浏览器的渲染原理）。

其中 HTTP 缓存属于《认识 HTTP 协议》的内容，页面渲染属于浏览器原理的内容，本文主要围绕 HTTP 请求相关展开。

### DNS 解析

DNS 的全称是 Domain Name System（域名系统），它负责把 `www.qq.com` 这样的域名地址翻译成一个 IP（比如 `14.18.180.206`），而客户端与服务器建立 TCP 连接需要通过 IP 通信。

客户端和服务器之间的连接并不靠域名进行：网络中每个终端之间的连接和通信是通过唯一的 IP 地址完成的。在建立 TCP 连接前，需要找到建立连接的服务器——DNS 解析过程让用户可以通过域名找到存放文件的服务器。

DNS 解析过程会进行递归查询，分别依次尝试从以下途径按顺序获取该域名对应的 IP 地址：

- 浏览器缓存
- 系统缓存（用户操作系统 Hosts 文件 DNS 缓存）
- 路由器缓存
- 互联网服务提供商 DNS 缓存（联通、移动、电信等互联网服务提供商的 DNS 缓存服务器）
- 根域名服务器
- 顶级域名服务器
- 主域名服务器

如果当前步骤没查到，则自动跳转到下一步骤通过下一个 DNS 服务器进行查找；如果最终依然没找到，浏览器便会将页面响应为打开失败。

在前后端联调过程中常常需要配置 HOST，这个过程实际上就是修改了浏览器缓存或系统缓存：将特定域名指向自身的服务器 IP 地址，便可以实现通过域名访问本地环境、测试环境、预发布环境的服务器资源。

为什么需要配置域名 HOST，而不直接使用 IP 地址访问？原因是**浏览器的同源策略会导致跨域问题**。

同源策略要求，只有当请求的协议、域名和端口都相同的情况下，才可以访问当前页面的 Cookie/LocalStorage/IndexedDB、获取和操作 DOM 节点，以及发送 Ajax 请求。通过同源策略的限制，可以避免恶意攻击者盗取用户信息，保证用户信息的安全。

对于非同源的请求（常称为跨域请求），需要进行跨域处理。常见的跨域解决方案有以下几种：

- 使用`document.domain + iframe`：只有在主域相同的时候才能使用该方法。
- 动态创建 script(JSONP)：通过指定回调函数以及函数的传参数据，让页面执行相应的脚本内容。
- 使用`location.hash + iframe`：利用`location.hash`来进行传值。
- 使用`window.name + iframe`：原理是`window.name`值在不同的页面（甚至不同域名）加载后依旧存在。
- 使用`window.postMessage()`实现跨域通信。
- 使用跨域资源共享 CORS（Cross-origin resource sharing）。
- 使用 WebSocket。

其中，CORS 作为现在的主流解决方案，允许浏览器向跨源服务器发出 XMLHttpRequest 请求，从而克服了 Ajax 只能同源使用的限制。实现 CORS 通信的关键是服务器：只要服务端实现了 CORS 接口，就可以进行跨源通信。

DNS 解析完成后，浏览器获得了服务端的 IP 地址，接下来便可以向服务端发起 HTTP 请求。目前大多数 HTTP 请求都建立在 TCP 连接上，因此客户端和服务端会先建立起 TCP 连接。

### TCP 连接的建立

TCP 连接的建立过程偏通信底层，前端日常开发过程中不容易直接接触。但优化应用的加载耗时、请求耗时，或定位一些偏底层的问题（请求异常、HTTP 连接无法建立等），都或多或少依赖这些底层知识。需要掌握的重点包括：

- TCP 协议提供可靠传输服务，UDP 协议则可以更快地进行通信；
- 三次握手：指 TCP 连接的建立过程，该过程中客户端和服务端总共需要发送三个包，从而确认连接存在；
- 四次挥手：指 TCP 连接的断开过程，该过程中需要客户端和服务端总共发送四个包，从而确认连接关闭。

当客户端和服务端建立起 TCP 连接之后，HTTP 服务器会监听客户端发起的请求，此时客户端会发起 HTTP 请求。

### HTTP 请求与 TCP 协议

由客户端发起的 HTTP 请求，服务器收到后会进行回复，回复内容通常包括 HTTP 状态、响应消息等（具体内容在 HTTP 协议部分介绍）。

目前大多数 HTTP 请求都基于 TCP 协议。TCP 协议的目的是提供可靠的数据传输，它确保可靠传输的途径主要包括两个：

- 乱序重建：通过对数据包编号来对其排序，使得另一端接收数据时，可以重新根据编号还原顺序；
- 丢包重试：通过发送方是否得到响应，检测出丢失的数据并重传这些数据。

通过以上方式，TCP 在传输过程中不会丢失或破坏任何数据——这也是即使出现网络故障也不会损坏文件下载的原因。

不过，在 HTTP/3 中底层支撑是 QUIC 协议，该协议使用的是 UDP 协议。因为 UDP 协议不负责可靠传输，可以更快地进行通信，更常用于直播和在线游戏等应用。也就是说，HTTP/3 基于 UDP 协议实现了数据的快速传输，同时通过 QUIC 协议保证了数据的可靠传输，最终实现了又快又可靠的通信。

除此之外，TCP/IP 协议的分层模型、IP 寻址过程、IP 协议如何将数据包准确无误地传递，以及 HTTP/2、HTTP/3、HTTPS 这些协议的设计变更与解决的问题，都是网络请求知识体系的延伸内容。

这些底层知识对大多数前端开发来说很少直接接触，却几乎贯穿所有网络请求问题。日常开发中，对网络请求的认知常常停留在"前端发起了请求，后台就能收到""请求没有按预期结果返回，要么是请求包内容有误，要么后台服务异常"的层面。但如果某一天应用整体请求耗时突然变长，且前后端都没有时间上可关联的发布，只有了解一个网络请求的完整流程，才能定位到底是哪个步骤出现了问题——甚至 HTTP 切换到 HTTPS 也可能影响请求耗时，这类因素也需要纳入排查范围。

## Ajax 请求

Ajax 并不是 JavaScript 的规范，而是 Jesse James Garrett 提出的新术语：`Asynchronous JavaScript and XML`，意思是用 JavaScript 执行异步网络请求。

### 网络请求的发展

对浏览器来说，网络请求用于从服务端获取需要的信息，然后解析协议和内容，进行页面渲染或信息获取。

早期的网络请求除了静态资源（HTML/CSS/JavaScript 等）文件的获取外，主要用于表单的提交：完成表单内容填写后点击提交按钮，浏览器刷新页面，在新页面里告知操作成功还是失败。

页面跳转刷新会影响用户体验；同时表单提交过程中使用同步请求会阻塞进程，用户无法继续操作页面，页面呈现假死状态。

为了避免这种情况，开始使用`异步请求 + 回调`的方式处理请求，这就是 Ajax。随着时间发展，Ajax 的应用越来越广，如今使用 Ajax 已经是前端开发的基本操作。但 Ajax 是一种解决方案，在前端中的具体实现依赖 `XMLHttpRequest` 相关 API。页面局部更新、动态加载，乃至懒加载、首屏加载等，都是以 `XMLHttpRequest` 为前提。

### XMLHttpRequest

`XMLHttpRequest` 让发送一个 HTTP 请求变得非常容易：创建一个请求对象实例并对它进行操作即可：

```javascript
var request = new XMLHttpRequest(); // 新建XMLHttpRequest对象

request.onreadystatechange = function () {
  // 状态发生变化时，函数被回调
  if (request.readyState == 4) {
    // 成功完成
    // 判断响应结果:
    if (request.status == 200) {
      // 成功，通过responseText拿到响应的文本
      console.log(request.responseText);
    } else {
      // 失败，根据响应码判断失败原因:
      console.log(request.status);
    }
  }
};

// 发送请求
// open的参数：
// 一：请求方法，包括get/post等
// 二：请求地址
// 三：表示是否异步请求，若为false则是同步请求，会阻塞进程
request.open("GET", "/api/categories", true);
request.send();
```

上面是处理一个 HTTP 请求的基本方法。实践中通常会将它封装成通用方法方便调用。上面例子根据返回的 `request.status` 是否为 `200` 来判断是否成功，但实际上 `200-400`（不包括 `400`）的范围都可以算成功，因为其中还包括使用缓存、重定向等情况。

将请求封装起来，同时使用 ES6 的 `Promise`，可以变成一个通过 Promise 进行异步回调的请求函数：

```javascript
function Ajax({ method, url, params, contentType }) {
  const xhr = new XMLHttpRequest();
  const formData = new FormData();
  Object.keys(params).forEach((key) => {
    formData.append(key, params[key]);
  });
  return new Promise((resolve, reject) => {
    try {
      xhr.open(method, url, true);
      xhr.setRequestHeader("Content-Type", contentType);
      xhr.onreadystatechange = function () {
        if (xhr.readyState === 4) {
          if (xhr.status >= 200 && xhr.status < 400) {
            // 这里我们使用200-400来判断
            resolve(xhr.responseText);
          } else {
            // 返回请求信息
            reject(xhr);
          }
        }
      };
      xhr.send(formData);
    } catch (err) {
      reject(err);
    }
  });
}
```

通过这样简单的封装，就可以以 Promise 的方式发起 Ajax 请求。

在具体的项目使用中，通常还需要考虑更多问题，比如防抖节流、失败重试、缓存能力、浏览器兼容性、参数处理等。

## 小结

从输入 URL 到页面呈现，完整链路为：DNS 域名解析（递归查询多级缓存与域名服务器）→ 建立 TCP 连接（三次握手）→ 发起 HTTP 请求并接收响应 → 解析 HTML 并请求页面资源（涉及 HTTP 缓存）→ 渲染页面。TCP 协议通过乱序重建与丢包重试保证可靠传输，HTTP/3 则改用基于 UDP 的 QUIC 协议实现又快又可靠的通信。在前端编程层面，Ajax（`XMLHttpRequest`）是实现异步网络请求的基础，配合 Promise 封装可以形成简洁可复用的请求函数。

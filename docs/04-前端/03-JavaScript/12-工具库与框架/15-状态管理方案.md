# 数据管理

## 概念说明

对于规模较小、各模块间依赖较少的项目，一般不会引入复杂的状态管理工具。但业务的发展和变化很快：随着项目不断变大、页面间需要共享和通信的内容越来越多，加上团队成员开发习惯不一致，项目后期容易出现事件传递、全局数据"满天飞"的情况。

这种状态的隐患：修改某个状态数据时，无法直观确认改动会不会影响其他地方；且这类问题在测试阶段难以发现（项目规模越大，回归测试成本越重），最终可能触发线上事故。

::: tip 选型原则
并非所有项目都应该在最初引入状态管理方案。除非项目最初就定位为大型或复杂应用，否则应根据预期来选型、根据需要引入不同的工具库。随着项目的发展迭代，状态管理方案也可能需要随之变更。
:::

要理解数据在前端应用中怎么流动，首先需要了解数据如何管理。

## 数据的组织管理

一般来说，组件的数据在组件自身的实例中维护。涉及跨组件共享、全局共享的数据，则需要统一保存和维护——大多数情况下使用**共享对象**的方式。

### 共享对象

共享对象的原理：多个地方需要使用相同的数据时，把数据放置在一个统一的地方，各处都从这里获取和更新。

![](/fe-notes-images/66cbcdb61150.png)

例如，可以用一个 `globalData.js` 文件管理全局数据：

```
// globalData.js
// globalData 用来存全局数据
let globalData = {};
// 获取全局数据
// 传 key 获取对应的值
// 不传 key 获取全部值
export function getGlobalData(key) {
  return key ? globalData[key] : globalData;
}
// 设置全局数据
export function setGlobalData(key, value) {
  // 需要传键值对
  if (key === undefined || value === undefined) {
    return;
  }
  globalData = { ...globalData, [key]: value };
  return globalData;
}
```

局部数据的管理同样可以使用共享对象：将需要共享的数据维护在一个对象中，需要时主动获取。

### 根据模块进行划分

大型应用中维护的全局数据更复杂，通过合适的方式拆分可以更方便地管理，例如根据数据的类型、使用场景、涉及的功能，以拆分模块的方式进行管理。

### 使用树状结构管理数据

前端页面中的 DOM 节点基于树状结构管理；前端应用即使通过模块化和组件化一层层封装，最终依然呈现为树状。

因此可以根据组件的树状作用域，结合共享对象的管理，注入树状的数据结构。例如 Angular 使用依赖注入的方式，配合树状的组件管理，实现数据的共享或隔离。

## 数据变更方式

应用和界面被抽象成数据管理后，被抽象的数据即通常所说的**状态**。前端项目中的数据不是孤立存在的，相互之间会交互和影响——数据间的相互作用即数据通信或状态管理，方式包括但不限于：

- 事件监听与触发
- 单向数据流
- 响应式数据流

### 事件监听与触发

事件监听与触发的设计一般基于**发布-订阅模式**。浏览器对点击、输入框输入等操作事件的绑定就是典型的事件机制；也可以通过事件管理的方式进行数据交互，例如 WebSocket 机制。

事件监听和触发的原理：**监听者在进行事件监听后，会被添加到该事件的监听者队列中；事件被触发后，根据该事件的监听者队列通知相应的监听者。**

事件中心的挂载位置有两种：在很多前端框架中，事件委托挂载在页面的组件根实例上；也可以自行创建一个事件中心来管理。

事件通知机制很方便：可以随意控制触发的时机，也可以在任意地方监听或触发。但事件机制的弊端也很明显——每一个事件的触发对应一个或多个监听，关系是一对多。设计不合理时，甚至可能出现一个事件被多处触发的问题：事件散落在各处、数据流难以跟踪，定位问题时只能通过全局搜索的方式跟踪数据的去向，维护难度大大上升。

以一个简单的博客系统为例：

![](/fe-notes-images/46328fc2f4c3.png)

图中只有事件 1 和事件 2 的触发和监听，就存在跨组件甚至跨页面的事件通知。在规模较大的应用中，可能导致满屏的事件，且事件之间没有规律可循。每次改动事件相关的代码（例如多传一个参数、改变某个参数）都可能引发未知错误，需要全局搜索出相关事件并一一回归测试。此外，绑定的事件如果不能及时销毁，还会导致内存泄漏等问题。

大型复杂的前端应用并非不适合事件机制，关键在于管理方式。大型前端项目 VS Code 就使用了事件机制，并配合依赖注入的框架设计了一套事件管理模式，包括：

- 提供标准化的 `Event` 和 `Emitter` 能力；
- 通过注册 `Emitter`，并对外提供类似生命周期的方法 `onXxxxx` 的方式，进行事件的订阅和监听；
- 通过提供通用类 `Disposable`，统一管理相关资源的注册和销毁；
- 通过使用同样的方式 `this._register()` 注册事件和订阅事件，将事件相关资源的处理统一挂载到 `dispose()` 方法中。

由于 VS Code 使用了依赖注入，模块的实例创建、销毁等统一交给框架处理，从而有效解决了事件机制的弊端。

::: tip 方案落地的思考
技术方案的选择不只是"选某个方案"这么简单，方案如何在项目中落地、是否需要进行适当的调整，同样是设计的一部分。
:::

### 单向数据流

很多前端框架都会搭配状态管理工具处理应用中的数据变更。Vuex/Redux/Flux 这些状态管理工具的设计思想都基于**单向数据流**：采用集中式存储管理应用的所有组件的状态，并以相应的规则保证状态以一种可预测的方式发生变化。

以 Redux 为例，为了保证数据单向流动：

![](/fe-notes-images/0a1ef2ca2a71.png)

- 使用单一的数据源：所有的状态数据都存储在 `store` 中；
- 状态数据只读：只能通过 `action` 来触发数据变更；
- 修改无副作用：修改现有数据的副本，并通过传递副本来更新数据。

全局数据使用变频繁之后，定位问题时常遇到"不知道这个数据为何改变"的情况——所有引用到这个全局数据的地方都可能修改它。给数据的流动一个方向，则可以方便地跟踪数据的来源和去处。

同样以博客系统为例：

![](/fe-notes-images/bcd61a2896d9.png)

使用单向数据流的状态管理方案后，数据的变更来源、更新方向都比事件触发清晰，因此被更多开发者推崇。

### 响应式数据流

响应式数据流的设计基于**响应式编程**。响应式编程同样基于观察者模式，是一种面向数据流和变化传播的声明式编程方式。前端领域常见的异步场景包括事件处理、用户输入、HTTP 响应等。

对于这类异步数据流，可以使用响应式编程设计：通过订阅某个数据流，对数据进行一系列流式处理（过滤、计算、转换、合流等），配合函数式编程可以实现很多优秀的场景。

以 RxJS 为例，对用户的交互通过订阅的方式获取需要的信息：

```javascript
import { fromEvent } from "rxjs";
import { map, filter, distinctUntilChanged } from "rxjs/operators";

const input = document.querySelector("input");
const observable = fromEvent(input, "input") // 监听 input 元素的 input 事件
  .pipe(
    map((e) => e.target.value), // 一旦发生，把事件对象 e 映射成 input 元素的值
    filter((value) => value.length >= 1), // 接着过滤掉值长度小于 1 的
    distinctUntilChanged() // 如果该值和过去最新的值相等，则忽略
  );
// 订阅
observable.subscribe(
  (x) => console.log(x),
  (err) => console.error(err)
);
```

Angular 框架推荐使用的响应式编程工具便是 RxJS：在 Angular 中结合依赖注入进行数据流的订阅和触发，可以方便地对数据源和流向进行管理。

除了 RxJS，基于响应式数据流设计的状态管理库还包括 MobX。其中，RxJS 提供基于可观察对象（Observable）的响应式服务，MobX 提供基于状态管理的响应式服务。基于响应式数据流的设计，可以通过各种合流方式、订阅分流方式，将应用中的数据流动从头到尾串在一起——可以清晰地知道当前节点上的数据来自哪里（用户操作还是网络请求）。

对于复杂程度较低的前端应用，响应式数据流的入门成本较高；但在复杂应用场景下，合理使用响应式编程可以有效降低各模块间的依赖，更容易进行整体数据流动管理和维护。

除了天然异步的前端、客户端等 GUI 开发以外，响应式编程在大数据处理中也拥有高并发、分布式、依赖解耦等优势，在同步阻塞转异步的并发场景下会有较大的性能提升，淘宝业务架构就是使用响应式的架构。

## 小结

| 维度 | 事件监听与触发 | 单向数据流 | 响应式数据流 |
|---|---|---|---|
| 基础模式 | 发布-订阅 | 集中式 store + 单向变更 | 观察者 + 数据流 |
| 优点 | 触发时机灵活、监听/触发位置自由 | 变更来源可预测、易于跟踪 | 流式处理能力强、降低模块依赖 |
| 风险 | 一对多关系散乱、数据流难跟踪、可能内存泄漏 | 样板代码较多 | 入门成本高 |
| 典型实现 | DOM 事件、WebSocket、VS Code Event/Emitter | Redux/Vuex/Flux | RxJS、MobX |

数据管理分两个层面：**组织管理**（共享对象、模块划分、树状结构）解决"数据放在哪里"；**变更方式**（事件监听、单向数据流、响应式数据流）解决"数据变化如何通知"。根据项目规模和复杂度选择并组合这些方案，是前端状态管理的核心内容。

# 如何进行应用的模块化设计

## 概念说明

很多前端开发者认为写业务代码枯燥无趣，且容易达到技术瓶颈，实际情况并非如此：几乎所有被称为"技术需求""技术工具"的开发都来自业务的需要，Angular、React、Vue 这类框架也是如此。

前端业务开发的内容看似只是调整样式、拼接模板、绑定事件、接口请求、更新页面，但通过更好的代码设计，可以显著提升写业务代码过程中的编程体验。

一个实用的判断标准：当开始写重复的代码，或进行较多的复制粘贴时，就应当考虑对应用进行适当的抽象了。模块化与组件化设计正是这种抽象的系统方法。

## 应用模块化设计

拿到一个设计好的应用之后，为避免出现文件内容过多、功能之间耦合严重等问题，提升项目代码的可用性和可维护性，需要对它进行模块拆分。

### 模块与层级划分

每个团队对模块的理解有所区别，因此模块拆分有多种方式：

- 对于简单的管理端应用，可以采用类似 MVC 这样的结构进行模块拆分，比如拆分成视图模块、数据模块、逻辑控制模块等。
- 对于页面内容较丰富的应用，可以结合业务进行更加细致的模块和组件拆分，比如拆分成核心模块、功能模块、公共组件模块等。
- 对于交互和逻辑复杂的应用，可以根据系统架构将应用进行模块和层级的划分，比如拆分成渲染层、数据层、网络层等。

例如，常见的客户端和服务端的通信过程可以根据功能模块进行分层，如图：

对于大型应用的模块划分，很多时候还需要结合模块粒度进行由上至下的多次划分，划分规则可能是上述规则，也可能与应用的业务场景相关。

以在线文档这类交互复杂的在线协作应用为例：将模块拆分成核心模块、功能模块、公共组件模块之后，还需要将各个模块进行分层或二次模块划分处理。比如核心模块可分成渲染层、数据层、网络层，功能模块可分成函数计算模块、复制粘贴模块，公共组件模块可拆分成头像模块、工具栏模块，等等。

### 模块划分与设计原则

在通用编程设计领域，架构设计有很多设计理念和原则，其中两种值得了解：

- **领域驱动设计**（Domain-Driven Design，简称 DDD）：从业务领域的角度来对系统进行领域划分和建模。
- **职责驱动设计**（Responsibility-Driven Design，简称 RDD）：从系统内部的角度来进行职责划分、模块拆分以及协作方式。

领域驱动设计（DDD）用于业务领域的划分，在业务复杂的系统架构设计中比较实用，比如电商领域的商品、买家/卖家、订单、优惠券、风控等各个领域的划分。但在前端领域中，不同的业务领域通常会通过不同的页面、组件等方式出现，比如商品页面、订单页面、优惠券页面等，因此领域驱动设计很少在前端开发中直接使用，或者可以说其在前端领域的应用与前端组件化思想比较相似。

职责驱动设计（RDD）更倾向从角色和职责的角度来定义和划分模块，与前端的公共组件、工具库、MVC/MVVM 设计、功能模块划分等类似。它在功能复杂的系统架构设计中可带来不少帮助，比如在在线文档的各个功能模块设计中，可以通过对系统进行职责划分以及定义模块之间的边界和协作方式，清晰地划分模块的功能。

这两种设计模式并不互斥，可以配合使用：

- 将与业务逻辑关系密切的功能按照业务领域进行划分和建模，比如电商网站中的购物车组件、商品组件等；
- 对于与前端实现（视图渲染逻辑、与服务端交互逻辑、与用户交互逻辑）相关的功能，在系统搭建过程中对这些功能进行职责分配和模块划分。

完成模块划分之后，还需要考虑模块的设计、模块间的依赖关系和通信等问题，其中最常见的就是如何解决模块间的依赖耦合。

### 模块间依赖的解耦

低耦合、高内聚常被用来描述系统设计中的模块依赖关系：

- 低耦合基于抽象，使系统更具模块化，不相关的事物不应相互依赖；
- 高内聚则意味着对象专注于单一职责。

低耦合和高内聚是每个设计良好的系统的目标，具体的设计模式在相关书籍中有系统论述。下面介绍复杂前端领域中比较常用的两种依赖解耦方式。

**方式一：依赖倒置。** 依赖倒置原则有两点：

- 高层次的模块不应该依赖于低层次的模块，两者都应该依赖于抽象接口；
- 抽象接口不应该依赖于具体实现，而具体实现则应该依赖于抽象接口。

举例来说，数据层模块（`DataManager`）依赖了网络层模块（`NetworkManager`）中的发送数据接口（`sendData()`），还依赖了渲染层模块（`RenderManager`）的更新界面接口（`updateView`）。通过 TypeScript 定义接口，可以表达为：

```typescript
interface INetworkManagerDependency {
  sendData: (data: string) => void;
}
interface IRenderManagerDependency {
  updateView: () => Promise<void>;
}
class DataManager {
  constructor(
    networkManagerDependency: INetworkManagerDependency,
    renderManagerDependency: IRenderManagerDependency
  ) {
    // 相关依赖可以保存起来，在需要的时候使用
  }
}
```

这样只按照约定依赖抽象的接口来实现功能调用，就不会依赖具体的模块和细节。如果项目中有完善的依赖注入框架，就可以使用项目中的依赖注入体系，例如 Angular 框架自带依赖注入体系，VS Code 中也使用到了依赖注入。依赖注入在大型项目中比较常见，对管理各模块间的依赖关系很实用。

**方式二：事件通信。** 事件驱动在各种系统设计中经常使用，可以解耦目标对象和它的依赖对象：目标只需要通知它的依赖对象，具体怎么处理由依赖对象自己决定。事件驱动可以快速、简单地实现模块间的解耦，但也常带来新的问题：

- 全局事件满天飞，不知道某个事件来自哪里、被多少地方监听了；
- 无法进行事件订阅的销毁管理，容易存在内存泄漏的问题；
- 事件维护困难，增加和调整参数影响面广，容易触发 Bug。

这些问题的应对方法与状态管理方案相关，可参考状态管理相关文档。

除了以上两种方式，许多设计模式和理念对解耦模块间的依赖也很有帮助，比如接口隔离原则、最少的知识原则、迪米特原则等。

## 应用组件化设计

在前端日常开发过程中，更多涉及业务逻辑和界面开发的内容，因此组件化设计比模块划分更常被提及。首先需要定义什么是组件。

### 组件的划分

简单来说，组件可以扩展 HTML 元素、封装可重用的代码，比如：

```html
<!--封装后的一个组件可能长这样-->
<my-component></my-component>
```

看起来这个组件什么都没有，这是因为逻辑都封装在组件里面了。组件有自身的呈现形式、状态数据和功能逻辑，一只猫也可以是一个组件，如图：

![](/fe-notes-images/1e13c2debdb4.png)

这只猫虽然是个 Gif 图片，但它可以拖动，鼠标悬浮会弹出一个提示框，双击或长按会让它消失。这些逻辑都可以封装在组件里，通过这样的方式对外屏蔽实现细节：外部使用时只需要引入组件，然后在页面里插入 `<Kitty></Kitty>` 即可。

一般来说，组件的划分可以通过两个角度来进行：

- **通过代码复用划分**。写代码时观察到一些代码在结构和功能上可复用，就可以把它们封装起来，以减少重复代码。
- **通过视觉和交互划分**。组件的划分通常与视觉、交互密切相关，可通过功能、独立性来判断是否适合作为一个组件。

确定将哪些功能划分成组件之后，就需要定义组件的职责，然后进行组件封装。

### 组件的封装四要素

组件封装过程和模块的职责定义有些相似，首先需要定义这个组件的职责。一个设计良好的组件，通常提供以下四种能力：

- 组件内维护自身的数据和状态；
- 组件内维护自身的事件（方法）；
- 对外提供配置接口，来控制展示以及具体功能；
- 通过对外提供查询接口，可获取组件状态和数据。

下面以视频网站为例进行说明：

![](/fe-notes-images/3da5ab139290.png)

**1. 组件内维护自身的数据和状态。** 以图中的小卡片为例：

![](/fe-notes-images/94c0e6d43e0e.png)

这个小卡片维护着自己的数据：封面图、描述、头像、作者，还有一个初始状态，即页面中呈现的样子。这些内容保存在组件自己的作用域中，每个卡片组件都拥有自己的数据和状态。

**2. 组件内维护自身的事件。** 鼠标放在卡片上时，随着鼠标的位置，顶部会出现一个进度条，同时封面图会随着进度条的变化而改变，如图：

![](/fe-notes-images/ef52c6f4e414.png)

可见，小卡片组件封装有自己的 `mousemove` 事件，以及对应的处理逻辑方法。

**3. 对外提供配置项，来控制展示以及具体功能。** 再看另外一个小卡片：

![](/fe-notes-images/3aa362e3e637.png)

这个卡片和前面的卡片不同：左下角展示的是视频时长，而不是头像和名字。这种差异可以通过传入配置项的方式来控制。

**4. 通过对外提供查询接口，可获取组件状态。** 大多数时候，组件独立维护着自身的数据和状态。但在一些特殊场景下，父组件或者应用需要知道组件当前的状态，比如在页面中要浮动展示最近聚焦的卡片视频内容，外层需要知道卡片中的具体进度并在浮窗中播放。在这种情况下，组件需要对外提供接口以供查询。

组件封装也可以包含一定的层级关系，比如卡片组件里也可以包括视频组件，提供点击播放的功能。很多前端应用最终会以组件树的方式呈现，这是因为 DOM 元素本身就是树状结构。

### 应用中的组件树

几乎任意类型的应用界面都可以抽象为一个组件树。例如 GitHub 上 Vue 主页，页面能划分成一块块的内容块，其中有些内容块就可以看作组件。

![](/fe-notes-images/8f3ec88f92ea.png)

一般来说，这样一个管理页面可以抽象成这样的组件树：

![](/fe-notes-images/c260a6c8cce4.png)

以代码的方式来表达这样的组件树，会是这样：

```html
<div id="app">
  <app-header>
    <header-search></header-search>
    <header-nav></header-nav>
    <header-aside></header-aside>
  </app-header>
  <app-view>
    <group-info></group-info>
    <app-tab></app-tab>
    <app-tab-container>
      <project-card></project-card>
      <card-list></card-list>
    </app-tab-container>
  </app-view>
</div>
```

在这段代码中，页面不再由一个个 `<div>` 拼装而成，而是使用自定义组件名字（比如 `<my-component>`）。使用自定义组件可快速高效地复用代码，也可以降低维护成本。

为了让组件与外界环境隔离（样式不会相互影响），像 Vue 这样的框架会通过在 DOM 节点上使用唯一的 ID 标记 DOM 元素，通过节点属性等方式匹配对应的元素并添加样式。

2011 年提出的 Web Components，允许仅使用 HTML、CSS 和 JavaScript 创建可重用的组件，它由自定义元素、Shadow DOM、HTML templates 三项技术结合而成。通过 Web Components，可以不依赖前端框架，只使用 HTML/CSS/JavaScript 创建在任何现代浏览器中运行的可重用组件。

## 小结

前端应用的模块化设计包括模块与层级划分、依赖解耦；组件化设计包括组件划分与封装四要素。实际上，组件可以看作是带有视图功能的特殊模块，它在前端开发过程中更为常见。

无论是组件封装还是模块划分，过度的抽象都会导致代码难维护、可读性差。当应用很小时，甚至不需要对这些状态、数据进行特殊管理，几个简单的变量就可以满足需求；随着应用组件数量变多，开始有了组件的作用域，组件需要通信时可以通过简单的事件机制或共享对象的方式交互；当项目规模继续增大，需要按照预期的方式管理上百个状态、上万条数据时，就需要引入合适的状态管理工具。这些设计知识较为抽象，需要结合实际项目反复思考和实践才能掌握。

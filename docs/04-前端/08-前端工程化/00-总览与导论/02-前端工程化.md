# 前端工程化

## 概念说明

前端工程化是一个出现频率很高却长期缺乏明确定义的概念。一种常见误解是把它等同于模块化和自动化工具，例如 Webpack/Gulp、脚手架、组件化等，但工具只是辅助手段，并不能作为工程化本身来理解。

从工程角度来看，前端工程化致力于提升工程的开发效率、协作效率、项目质量，贯穿项目设计、开发、测试、上线、维护的整个过程。其核心可概括为两个方向：

- **提升系统质量**：通过项目设计和架构优化，保证系统的稳定性、可维护性与可测试性。
- **提升开发效率**：通过研发和发布流程的自动化优化，减少人工操作与注意力损耗。

::: tip 核心原则
前端工程化不是引入某个工具，而是围绕"系统质量"与"开发效率"两个目标，对项目架构与研发流程进行系统性建设。
:::

## 项目中的典型问题

相比从 0 到 1 搭建项目，大部分开发工作发生在已有项目的维护与迭代上。项目会经历多名开发者的参与、协作和交接，随之产生的问题可以归为两类：

- 系统质量的下降。
- 开发效率的下降。

### 问题 1：系统质量的下降

Bug 的出现有多种可能：需求设计不严谨、代码实现逻辑存在漏洞、不在预期之内的异常分支等。概括来说，Bug 往往源于对项目不熟悉、对系统理解不深入，因此以下过程都会导致 Bug 增加：

- 项目频繁地调整（新增或者更换）开发人员，新加入的成员因不熟悉项目，可能埋下新的 Bug；
- 系统功能不断新增和迭代、规模持续壮大，模块间耦合增加、复杂度增加，在无法掌握系统全部细节的情况下，容易出现认知以外的 Bug。

对于处于快速迭代、不断拓展阶段的项目来说，人员变动与项目拓展都无法避免，这种情况下需要通过系统上线前的质量检测来确保问题尽早发现。但系统本身趋向复杂，测试成本随之上升，未发现的 Bug 进入线上版本的可能性也上升。

为了降低系统复杂度，当项目发展到一定阶段时，通常会对系统进行局部或整体的架构调整，例如模块拆分、模块间依赖解耦、引入新的状态管理工具、对重复逻辑进行抽象和封装等。

新技术的引入能缓解系统复杂度带来的稳定性问题，但也可能引入新问题：

- 部分功能无法与新技术兼容，成为历史遗留问题；
- 较大范围的架构调整影响面广，可能埋下难以发现的 Bug。

可见，项目在持续发展过程中必然面临系统质量下降的问题，同时还会引发开发效率的下降。

### 问题 2：开发效率的下降

系统上线之后，开发工作的重心会从功能开发逐渐转向其他内容。除了新功能的评审和设计以外，还包括：

- 用户反馈问题跟进和定位；
- 线上 Bug 修复和紧急发布；
- 处理系统的监控告警，排查异常问题；
- 新功能灰度发布过程中，自测、产品验证、提测、修复 Bug、灰度发布等各环节都需要人工操作和主动关注；
- 为保证系统质量，需要完善自动化测试能力，包括单元测试、UI 测试、集成测试等；
- 项目成员调整时，需要进行工作交接与指导。

开发的工作内容变得复杂，需要关注的事情更多，对监控告警系统、日志系统、测试系统、发布系统等各系统也存在熟悉成本和操作成本。在各项工作内容之间切换时，容易出现步骤遗漏，导致流程问题，例如：

- 系统灰度到一半，处理其他事情后忘记全量；
- 系统发布之后去处理紧急 Bug、忘记查看监控，直到收到大量用户反馈；
- 线上紧急 Bug 修复后急于发布，忘记执行自动化测试。

随着项目规模变大、系统复杂度上升，上述工作量都会增加，开发效率会受到明显影响：过去一天工作量的功能开发，可能需要三天才能完成，因为每天只有三分之一甚至更少的时间可以用于开发新功能。团队随之面临项目复杂度上升、系统质量不稳定、技术债务增多、整体效率下降等问题。

前端工程化的目标，正是解决系统质量与开发效率这两个问题。

## 实践路径

项目维护阶段的最大痛点，在于开发者无法聚焦自身工作内容，需要在各种系统之间操作和切换，由此带来开发效率下降；注意力分散又会导致设计不合理、引入新 Bug，进一步影响系统质量。

对应地，前端工程化从两个角度展开：

- 提升系统质量：项目设计和架构优化。
- 提升开发效率：项目研发和发布流程优化。

### 路径 1：项目设计和架构优化

提升系统质量需要对项目进行合理的架构调整，提升系统的可读性、可维护性、可测试性、稳定性，从而提升系统发布的稳定性。

项目设计阶段的工作包括项目定位、技术选型、团队开发规范制定等；项目维护阶段则需要根据项目的预期和现状持续优化，保留扩展性的同时避免过度设计。常见的优化点如下：

- 引入新技术和工具时，评估其是否能兼容原有设计、团队成员的熟悉成本、改造工作量和预期效果，选择性价比合适的方案落地。
- 团队成员增加会导致沟通成本上升、对规范的理解出现差异。使用工具（ESLint/Prettier/Git hooks 等）将团队规范落地，保证开发过程中使用一致的技术栈、代码规范以及公共物料库（组件库、工具库），降低沟通成本，确保代码的可读性和可维护性。
- 项目功能模块过多时，需要进行模块的拆分和解耦：将职责独立的模块拆包，使用 monorepo 或 multirepo 方式管理，让模块在技术方案、依赖关系梳理、变更、测试、发布等环节自行闭环，降低模块间的相互影响与系统复杂度。
- 项目代码量和文件数增加时，除拆包外还需更新或优化项目构建工具（使用增量编译、Tree-shaking、升级 Webpack 版本等），减少编译、打包耗时，提升开发效率。
- 进行自动化测试能力覆盖，补齐单模块功能测试、模块间集成测试、UI 组件界面测试、接口模拟环境测试、性能测试等。每次系统发布时自动执行回归测试，避免某个改动影响其他功能模块、带来认知以外的风险。
- 搭建完善的监控体系，在系统灰度、发布、线上运行过程中实时观察系统质量，配合告警能力及时发现并解决问题，保证系统运行稳定。

需要注意的是，这一过程会引入新的代码构建、代码规范和自动化测试工具，搭建新的监控系统、发布系统等，开发流程会随之变得烦琐，工具和系统的熟悉成本也会增加。因此还需要通过优化研发和发布流程来提升开发效率。

### 路径 2：项目研发和发布流程优化

流程优化的核心原则：**将一切需要手动操作和关注的内容自动化**。

以一次典型的需求交付为例，开发在接到产品需求单后需要处理的事项包括：

- 从主干创建分支，进入开发；
- 开发完成后，补充相关自动化测试（单元测试、集成测试、UI 测试等）；
- 执行自动化测试回归，确保系统整体功能正常运行；
- 构建代码，部署测试环境，进入产品体验和测试流程；
- 修复产品体验问题和 Bug，并重复前述步骤；
- 代码验证完成后，进行团队内代码 Review，更新主干分支，并执行代码构建和自动化回归测试；
- 根据团队 Git 规范（例如 Git Flow 流程）准备发布；
- 先进行版本灰度，灰度过程中通过监控系统关注各指标是否异常；
- 若监控系统出现异常，进行问题定位，Bug 修复后回到测试步骤；
- 灰度过程无异常，进行全量发布，发布后同样观察监控系统；
- 全量发布完成，结束需求单，并将版本归档（使用分支或 git tag）。

可见一次功能发布需要花费大量精力在流程步骤上。将这些步骤转为自动化后，开发的精力即可聚焦在功能设计和实现上。流程自动化的业界成熟方案是持续集成（continuous integration，简称 CI）与持续部署（continuous deployment，简称 CD）：

- 持续集成（CI）：目的是让产品可以快速迭代，同时保持高质量。
- 持续部署（CD）：目的是代码在任何时刻都处于可部署、可进入生产阶段的状态。

CI 在项目中的实践，指团队成员频繁（一天多次）提交代码到主干分支，每次提交自动触发自动化验证的任务集合，尽可能提前发现问题；CD 在项目中的实践，指代码通过评审后，可自动化、可控、多批次地部署到生产环境，其前提是测试、构建、部署等步骤均能自动化完成。

CI/CD 在项目中的落地，通常表现为流水线的开发模式：通过建立完整的 CI/CD 流水线涵盖整个研发流程，有效提高效率。以上述开发流程为例，可搭建如下流水线：

> 提交代码 → 自动测试 → 自动构建 → 部署测试环境 → 代码评审 → 灰度发布 → 全量发布 → 监控回归

流程自动化带来三方面收益：节省人工操作时间、提升开发效率；避免人工操作容易出现的遗漏和失误；与通知/告警机器人、工作群、需求单系统、Bug 系统、代码管理系统、发布系统、监控系统结合后，实现全研发和发布流程自动化，开发者得以从杂事中释放，专注于功能实现。

越是大规模、系统建设完备的团队，流程中消耗在多人协作和各系统操作上的精力越多，搭建 CI/CD 后的收益也越明显。同时，搭建 CI/CD 本身需要投入人力精力，实践中应考虑性价比，从对研发效能影响最大的痛点开始建设，以最快速、有效的方式提升团队开发效率，让更多人愿意参与 CI/CD 的持续建设。

## 小结

前端工程化的本质可以概括为两条主线：通过项目设计和架构优化提升系统质量；通过自动化方式优化项目研发和发布流程，提升开发效率。工具与系统是载体，衡量标准始终是系统质量的稳定与开发效率的提升。

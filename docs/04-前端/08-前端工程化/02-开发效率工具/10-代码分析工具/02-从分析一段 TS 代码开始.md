# 从分析一段 TS 代码开始

AST 是开发代码分析工具的前提，通过 TypeScript 的 Compiler API 可以获取 TS 代码的 AST。核心结论是：代码的含义可以通过 AST 对象来表述，通过程序对 AST 进行处理就可以实现分析代码的目的。

要通过程序实现对全部子应用项目代码中真实 API 调用的分析，需要先学会如何分析单个项目中的 API 调用信息；而对单个项目进行分析的前提，是先掌握如何对单个 TS 文件中的 API 调用进行分析。学习一项技能最好的方式就是先学习它的最小可用性实现。本文从分析一小段 TS 代码中的 API 调用讲起，内容以代码实操为主，穿插 TypeScript Compiler API 的介绍，目标是实现一个简单的分析脚本，迈出开发代码分析工具的第一步。

## 目标：找出 API 的调用信息

下面是一段 TS 代码片段。直接阅读代码，它的 API 调用信息是：从依赖 `framework` 中引入了名为 `app` 的 API，并且在第 `6` 行和第 `11` 行中进行了调用。

```typescript
import { app } from 'framework';

const dataLen = 3;
let name = 'iceman';

if(app){
    console.log(name);
}

function getInfos (info: string) {
    const result = app.get(info);
    return result;
}
```

问题在于：如何通过程序的方式从代码片段中找出 `app` 这个 API 被导入后是否有调用、调用的次数、代码行分布等信息。

## 第一步：将待分析的代码解析为 AST

代码分析的前提是 AST，因此第一步将需要分析的代码解析为 AST。由于分析目的简单，这里使用 `createSourceFile` 这个 Compiler API 来获取 AST：

```typescript
const tsCompiler = require('typescript');              // TS编译器

// 待分析代码片段字符串
const tsCode = `import { app } from 'framework';

const dataLen = 3;
let name = 'iceman';

if(app){
    console.log(name);
}

function getInfos (info: string) {
    const result = app.get(info);
    return result;
}`;

// 获取AST
const ast = tsCompiler.createSourceFile('xxx', tsCode, tsCompiler.ScriptTarget.Latest, true);
console.log(ast);
```

将 `ast` 对象打印出来，会发现它是一个结构很复杂的 JS 对象。下一步需要弄清楚这段代码对应的 AST 节点组成。

## 第二步：观察代码的 AST 结构及特征

直接通过打印结果观察节点信息效率很低，可以把要分析的代码片段放到 [AST explorer](https://astexplorer.net/?spm=taofed.bloginfo.blog.3.3ba15ac8enL4hJ#/gist/9e56e9ae71087546eb048cbc7a62b83b/2eb7901942b10bee8e8dc2dc38d3598497440135) 中，结合可视化工具来观察节点及相关特征。

观察结论：要分析的代码片段总共包含 5 条语句，分别为 `ImportDeclaration`、`VariableStatement`、`VariableStatement`、`IfStatement`、`FunctionDeclaration`，然后这 5 个 AST 节点再继续派生出更详细的子节点，共同组成了映射这段 TS 代码的 AST 语法树结构。将所有 AST 节点类型以树状图的形式展示会更直观，其中所有 `Identifier` 类型节点均可被标注出来。

依据 AST 节点类型知识，`Identifier` 节点通常为变量名、属性名、参数名等一系列声明和引用的名字。既然 `Identifier` 代表的是各种名字，而分析目标是 `app` 这个 API 在代码中的调用情况，那么可以通过遍历所有 `Identifier` 类型节点并判断它的名字是否为 `app`，以此来判定 `app` 这个 API 有没有被调用。

## 第三步：遍历分析 AST 各级节点

有了思路，接下来需要遍历 AST 并找到所有的 `Identifier` 类型节点。TypeScript 有一个非常重要的 Compiler API：`forEachChild`，它可以实现对 AST 各层级节点的深度遍历。该方法第一个参数是指 AST 根节点或正在被遍历的子节点，第二个参数是一个回调函数，对当前节点的判定逻辑可以写在里面。完善后的分析脚本如下：

```typescript
const tsCompiler = require('typescript');           // TS编译器

// 待分析代码片段字符串
const tsCode = `import { app } from 'framework';

const dataLen = 3;
let name = 'iceman';

if(app){
    console.log(name);
}

function getInfos (info: string) {
    const result = app.get(info);
    return result;
}`;

// 获取AST
const ast = tsCompiler.createSourceFile('xxx', tsCode, tsCompiler.ScriptTarget.Latest, true);
console.log(ast);

function walk (node) {                            // AST遍历函数
    tsCompiler.forEachChild(node, walk);          // 遍历AST节点
    console.log(node);                            // 输出节点信息
}

walk(ast);                                        // 执行遍历
```

分析脚本会将遍历后的 AST node 节点信息依次打印出来，可在本地执行并观察输出的节点信息。

遍历每个 AST 节点的目的并不是单纯输出节点信息，而是判断它是否为 `Identifier` 类型节点：如果是，接着获取该节点的名称并判断是否为 `app`；如果不是就跳过该节点。

判定节点类型需要使用 TypeScript 提供的一系列判断节点类型的 Compiler API：

```typescript
const tsCompiler = require('typescript');

// 判断节点类型的函数，返回值类型为 boolean
tsCompiler.isFunctionDeclaration(node);            // 判定是否为函数声明节点
tsCompiler.isArrowFunction(node);                  // 判定是否为箭头函数
tsCompiler.isTypeReferenceNode(node);              // 判定是否为Type类型节点
tsCompiler.isVariableDeclaration(node);            // 判定是否为变量声明节点
tsCompiler.isIdentifier(node);                     // 判定是否为Identifier节点
```

在 walk 函数中使用 `tsCompiler.isIdentifier(node)` 判定当前节点是否为 Identifier 类型节点，进而判断它的名字是否为 app。两个条件都满足时，把节点信息记录到一个 Map 结构中——Map 结构非常适合需要统计信息的分析场景：以 API 名称作为 key，将 API 调用相关的信息以对象的形式写入 value。等遍历完 AST 的全部节点后，就可以得到 app 这个 API 在代码中真实的调用情况。

通过 ast 对象上的 `getLineAndCharacterOfPosition` 方法可以获取当前遍历节点的代码行信息：

```typescript
// 获取当前node节点所在代码行
ast.getLineAndCharacterOfPosition(node.getStart()).line + 1;
```

基于以上知识，完善后的分析脚本如下：

```typescript
const tsCompiler = require('typescript');            // TS编译器

// 待分析代码片段字符串
const tsCode = `import { app } from 'framework';

const dataLen = 3;
let name = 'iceman';

if(app){
    console.log(name);
}

function getInfos (info: string) {
    const result = app.get(info);
    return result;
}`;

// 获取AST
const ast = tsCompiler.createSourceFile('xxx', tsCode, tsCompiler.ScriptTarget.Latest, true);
console.log(ast);

const apiMap = {};                               // 记录API分析结果

function walk (node) {                                                  // AST遍历函数
    tsCompiler.forEachChild(node, walk);                                            // 遍历AST节点
    const line = ast.getLineAndCharacterOfPosition(node.getStart()).line + 1;       // 获取节点所在行
    if(tsCompiler.isIdentifier(node) && node.escapedText ==='app') {                // 判断isIdentifier节点名称是否为app
        if(Object.keys(apiMap).includes(node.escapedText)){
            apiMap[node.escapedText].callNum++;
            apiMap[node.escapedText].callLines.push(line);
        }else{
            apiMap[node.escapedText] = {}
            apiMap[node.escapedText].callNum =1;
            apiMap[node.escapedText].callLines = [];
            apiMap[node.escapedText].callLines.push(line);
        }
    }
}

walk(ast);

console.log(apiMap);                                                                // 输出分析结果
// {
//      app: {
//          callNum: 3,
//          callLines: [1, 6, 11]
//      }
// }
```

执行分析脚本会发现输出结果并不符合预期：脚本遍历了所有节点，其中包含 `import` 节点中的 `app`，这一干扰应当被排除。增加一个判断条件后，代码如下：

```typescript
const tsCompiler = require('typescript');              // TS编译器

// 待分析代码片段字符串
const tsCode = `import { app } from 'framework';

const dataLen = 3;
let name = 'iceman';

if(app){
    console.log(name);
}

function getInfos (info: string) {
    const result = app.get(info);
    return result;
}`;

// 获取AST
const ast = tsCompiler.createSourceFile('xxx', tsCode, tsCompiler.ScriptTarget.Latest, true);
console.log(ast);

const apiMap = {};                           // 记录API分析结果

function walk (node) {                                                              // AST遍历函数
    tsCompiler.forEachChild(node, walk);                                            // 遍历AST节点
    const line = ast.getLineAndCharacterOfPosition(node.getStart()).line + 1;       // 获取节点所在行
    if(tsCompiler.isIdentifier(node) && node.escapedText ==='app') {                // 判断isIdentifier节点名称是否为app
        if(line !=1){             // 排除import导入自身
            if(Object.keys(apiMap).includes(node.escapedText)){
                apiMap[node.escapedText].callNum++;
                apiMap[node.escapedText].callLines.push(line);
            }else{
                apiMap[node.escapedText] = {}
                apiMap[node.escapedText].callNum =1;
                apiMap[node.escapedText].callLines = [];
                apiMap[node.escapedText].callLines.push(line);
            }
        }
    }
}

walk(ast);                         // 遍历AST
console.log(apiMap);               // 输出分析结果
// {
//      app: {
//          callNum: 2,
//          callLines: [6, 11]
//      }
// }
```

执行脚本即可得到符合预期的分析结果：这段 TS 代码中引入了 `app` 这个 API，且有 `2` 次调用，分别在代码第 `6` 行、第 `11` 行。

## 分析脚本存在的问题

仔细审视上述实现思路，存在明显缺陷。

首先，脚本没有先对 import 节点进行分析。如果代码中不存在 import 导入语句，那么"遍历所有 `Identifier` 类型节点、判断名称是否为 `app`"的思路只能找到与 `app` 同名的 AST 节点，并不能代表这些 `app` 都是从 framework 导入的。例如：

```typescript
import { app } from 'framework';        // import app 定义

const dataLen = 3;
let name = 'iceman';

function doWell () {
    const app =4;                       // 局部常量 app 定义
    return app;                         // 局部常量 app 调用
}

function getInfos (info: string) {
    const result = app.get(info);       // import app 调用
    return result;
}
```

在这段代码片段中新增了函数 `doWell`，其内部定义了一个局部常量也叫 `app`。此时分析脚本无法区分 `doWell` 方法中的 `app` 与 `getInfos` 方法中的 `app`，即无法判定同名 `Identifier` 节点是否属于同一语义上下文。

**其它的问题：**

1. 无法判断 `app` 这个 API 的具体用途（类型、属性、方法、类...）；

2. 无法区分 `app.get` 链式调用与 `app` 直接调用这两种场景；

3. 排除 import 节点的判断方式不准确。

可见设计一个完整的代码分析工具还需要学习更多知识。在进入后续内容前，需要先明确一个问题：依赖调用分析到底要做些什么？

## 依赖调用分析的目标

简单来说，首先针对每一个需要分析的 TS(JS) 文件：

1.  遍历其所有 `import` 节点，分析并记录从目标依赖引入的 `API` 信息，并排除非目标依赖项的干扰。
1.  判定引入的 `API` 在具体代码中是否有调用，过程中还需要排除局部同名变量等一系列干扰。
1.  根据分析指标如用途识别（类型、属性、方法）等对该 `API` 调用进行指标判定分析，命中则记录到指定 Map 中。

然后按照上面的步骤依次遍历所有项目中指定的 TS(JS) 文件，就可以得到全部应用对于特定依赖（如：framework）的 `API` 调用分析数据了，最后根据使用场景（告警、评分、代码报告、代码建议等）对分析数据进行标记，二次整理，即可输出最终的分析结果。

## 小结

本文实现了分析单个 TS 文件 API 调用的最小可用脚本：通过 `createSourceFile` 将代码解析为 AST，借助 AST Explorer 观察节点结构特征，再以 `forEachChild` 深度遍历并结合 `isIdentifier` 与行号信息，将 API 调用次数与位置统计到 Map 中。脚本找到了 API 在代码中的调用位置与调用频次，但也暴露了无法区分语义上下文、无法识别 API 用途、import 排除方式不准等缺陷。设计完整的代码分析工具还需要进一步学习架构设计与分析范式。

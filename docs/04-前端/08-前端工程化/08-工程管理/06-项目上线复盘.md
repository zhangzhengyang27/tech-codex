# 项目上线与复盘

## 概念说明

前端开发者除了承担技术方案设计与代码编写之外，通常还会以项目的形式参与具体开发：或负责项目主导，或作为核心开发负责某个模块、某项技术方案的落地。项目的管理、推动与落地属于工作中的**软技能**，与硬技能并列，共同决定工作成果与成长速度，也是职业晋升所需的基础能力。

**预期 → 结果 → 复盘**是贯穿项目各阶段的基本方法：项目开始前对过程做预估，项目进行中对结果做核对，项目结束后对差异做复盘。三个环节循环执行，构成项目管理能力的提升路径。

::: tip 核心原则
项目管理能力与编码能力相互独立。一个项目能否按预期上线，取决于工作量评估、风险把控、协作机制等非编码环节，这些环节同样需要方法论支撑。
:::

## 事前：预估与风险把控

### 工作量评估与分工排期

项目开始前需要对整个过程进行初步预估，包括：

- 预期功能是否能实现，存在哪些不确定的功能；
- 预计的工作量和分工排期；
- 各阶段（开发、联调、产品体验、提测、发布）的时间点；
- 哪些工作涉及外部资源依赖和对接（交互、设计、接口协议等），是否存在延期风险；
- 如果存在风险，有哪些规避手段。

工作量评估的过程可以分为三步：

1. 确认技术方案，以及分工合作方式；
2. 拆分具体功能模块，分别进行工作量评估，输出具体的排期时间表；
3. 标注资源依赖情况和协作存在的风险，进行延期风险评估。

**实践要点**：

- 技术方案确认后再拆分功能模块做预估与排期。跳过这一步可能面临分工不明确、接口协议未对齐就匆忙开工、最终返工等问题。
- 工作量评估可以精确到半天。对独自开发的项目，拆解功能模块的过程本身也有助于思考实现方式、提前发现潜在问题。
- 排期计划表应输出完整、精确到具体日期的版本，并在开发过程中及时更新执行情况，供团队其他成员了解进度。
- 排期计划表的重要作用是通过时间线约束工作效率、及时发现问题，并在项目结束后针对时间维度进行复盘。

### 项目风险把控

项目开发过程中的典型延期风险包括：

- 方案设计考虑不周，部分工作返工，导致项目延期；
- 依赖资源无法及时给到、依赖方无法按时支援，导致项目无法按计划进行；
- 团队协作方式未对齐，开发过程中出现矛盾，反复争执和调整协作方式导致项目延期。

一个项目能按预期计划进行，依赖技术方案设计、分工和协作方式、依赖资源是否确定等多个环节；任何一个环节出问题都可能导致延误。因此需要**主动把控各环节的情况，及时推动和解决多方协作的问题**。

::: warning 风险预判方法
对历史项目中出现过的问题进行系统性调研（如需求反复、外部协作沟通成本高、验收标准模糊、排期不合理等），并将其归类为可预估的风险，再针对性地做前期准备（明确验收标准、制定排期、建立沟通机制），可以显著降低同类风险复发的概率。
:::

## 事后：反馈与复盘

很多开发在代码发布上线之后就结束了对项目的关注，遗漏了复盘环节。

### 复盘的价值

- 及时发现自身的问题并改进，避免掉进同一个坑；
- 让团队成员和管理者知道自己在做什么——把一件事做好是必须的，将这件事分享出来同样可以给团队带来成长；
- 整理、沉淀和分享项目经验，让整个团队得到成长。

### 复盘的内容结构

以一个带外部协作方进行小程序开发的项目为例，一期结束后复盘的问题整理通常包括：

- **延期原因**：等待后台接口联调时间比预期长；产品对接问题（提供资源、体验产品不够及时，需求描述不够详细）；过程中存在需求变更（设计和交互调整）。
- **沟通改进点**：每日、每周工作进度及时总结汇总；对产品设计和体验的合理性主动思考，主动发现问题、提出问题、解决问题。
- **开发风格问题**：过度抽象、逻辑管理较乱、变量类型混乱、重复代码过多。

同时收集协作方的反馈：

- **项目优点**：初始化代码减少了搭建环境的时间，部分功能模块得到复用；项目文档详细，降低沟通成本；协作方在开发过程中有明显成长。
- **改进建议**：提供一份前端代码规范；明确分工（协作方负责业务页面开发，负责人提供基础框架和工具库）；协作方对 UI 理解不深，若希望高度还原视觉或做细致交互，需在开发前特别提醒。

复盘结果可以通过邮件等方式同步给团队及合作方，同时作为经验沉淀供后续项目参考。纯文字内容之外的量化数据（见下节）能显著提升复盘的说服力。

## 用数据说话

性能优化可以用耗时和 CPU 资源占用做总结，工具开发可以用接入用户数量说明效果；常规业务项目则需要通过**时间线与质量维度的数据对比**来体现改进效果。

### 时间维度对比

将两期开发中每类延期原因的发生情况整理成数据（如接口联调超时次数、需求变更未纳入排期的次数），并在下一期通过对策规避。典型对策包括：

- 开发评估预留更多 buffer；
- 涉及多方合作的项目，开发负责人预留更多 buffer；
- 需要高度还原视觉或细致交互时，提前告知协作方；
- 体验过程中，对开发和体验问题及时反馈；
- 把控需求文档质量，完善交互细节后再交给协作方开发；
- 开发者预留足够的自测时间，对正常路径、异常路径都完成充分自测。

### 质量维度对比

除时间维度外，还可以通过 Bug 数量、需求返工率等质量指标对比两期开发情况。

::: tip 复盘的完整闭环
问题整理（定性）→ 反馈收集（定性）→ 数据对比（定量）→ 对策固化 → 下一期验证效果。完成这个闭环，复盘才能从"总结"升级为"改进机制"。
:::

## 小结

- 项目的管理、推动和落地是前端开发者不可或缺的软技能，遵循"预期 → 结果 → 复盘"的循环方法。
- 事前：确认技术方案后拆分模块做工作量评估，输出精确到日期的排期表，并做延期风险评估。
- 事中：主动把控技术方案、协作方式、依赖资源各环节，及时推动多方协作问题的解决。
- 事后：整理延期原因、沟通改进点与开发风格问题，收集协作方反馈，用时间与质量维度的数据对比验证对策效果。
- 复盘结果应同步给团队与合作方，并沉淀为可复用的项目经验。

# 开发许可证-维护自己的版权、拒绝拿来党

## 概念说明

软件是一种著作，天然拥有版权。一种常见误解是"放在 Github 上的就是开源软件，既然公开了源代码，就可以随便使用"。实际上版权法规定著作是禁止共享的，**没有许可证的软件等于保留所有权利**：源代码公开并不等于授权使用，未经许可的使用即构成侵权。软件要合法地被他人使用，必须由作者明确授予开源许可证。

许可证同时也承担着维护开源秩序的作用。部分公司会大量使用开源产品，组合、封装、修改后当做自己的劳动成果（俗称"拿来党"），这类行为破坏了开源的游戏规则。GPL 等协议的设计初衷之一，正是防止这种情况发生。

## 核心要点

- 版权自动取得，无需登记；没有 LICENSE 文件的项目默认保留所有权利，不能默认拿来使用。
- 严格意义上的开源许可证主要分为两大类：**Copyleft**（传染性、要求衍生品继续开源）与 **Permissive**（宽松、允许闭源商用）。
- 前端生态普遍采用 MIT 协议，Vue、React、Element、Ant Design 均是如此。
- 选择许可证时应同时考虑两个方向：为自己的项目挑选协议，以及在使用第三方开源库时确认其协议类型，避免版权风险。
- ⚠️ 常见误区：把"源代码公开"等同于"可以自由使用"。
- ⚠️ 常见误区：只看协议名称不看附加条款，React 历史上的附加专利条款就是典型反例。

## 版权与许可证的关系

**版权是知识产权的一种**，与著作权是同一个概念，可以自动取得，也可以登记取得，是作者对自己的著作享有的法定权利。著作权是公民、法人依法享有的一种民事权利，属于无形财产权。享有著作权的作者可以决定是否对作品进行著作权意义上的使用和处理；在中国，作品一经发表即受保护。

**开源许可证本质上就是作者的版权声明**：声明在保留版权的前提下，允许他人以何种方式使用、修改、分发这份作品。选择开源许可证，就是在为自己的作品选择授权规则。

## 许可证的分类

版权许可可分为四大类：

-   Copyright - 受版权保护的；未经准许不得复制的。
-   Copyleft - 有限空间内的自由使用，不得用于商业目的，且不得闭源，衍生品仍需开源。
-   Permissive - 宽松自由软件许可协议，对软件的使用、修改、传播等方式采用最低限制的自由软件许可协议条款类型。
-   Creative Commons - 大多是被用于设计类的工程上，署名权，非商业用途，禁止衍生。

实际上，一般只会把 Copyleft 和 Permissive 叫做开源，其中 Permissive 限制比较宽松。而 Copyleft 要求不得用于商业目的且不得闭源，并且后续衍生子软件必须遵守条款。这种协议的设计目的在于弘扬开源精神，防止某些公司垄断和强占开发成果。

### Permissive 宽松自由许可

Permissive 类许可证包括：

-   BSD(二条版)；
-   BSD(三条版)；
-   MIT；
-   Apache2。

|                 | BSD(二条版) | BSD(三条版) | MIT | Apache2 |
| --------------- | -------- | -------- | --- | ------- |
| 允许修改后闭源         | ✅        | ✅        | ✅   | ✅       |
| 不保证代码质量         | ✅        | ✅        | ✅   | ✅       |
| 必须披露原始作者        | ✅        | ✅        | ✅   | ✅       |
| 不得使用原始作者名字为软件推广 |          | ✅        |     |         |
| 分发时必须保留原始许可声明   | ✅        | ✅        | ✅   | ✅       |
| 修改过必须向用户声明修改    |          |          |     | ✅       |
| 未修改必须保持许可证不变    |          |          |     | ✅       |

从表格可以看出：四者都允许修改后闭源；BSD(三条版) 额外禁止使用原作者名字做推广；Apache2 额外要求对修改部分做出声明，且未修改的代码必须保持许可证不变。

### Copyleft 有限空间内的自由

Copyleft 类许可证包括：

-   Copyleft；
-   GPL；
-   Affero GPL (AGPL)；
-   LGPL；
-   Mozilla（MPL）。

|                          | GPL | Affero GPL (AGPL) | LGPL | Mozilla（MPL） |
| ------------------------ | --- | ----------------- | ---- | ------------ |
| 分发二进制格式，必须提供源码           | ✅   | ✅                 | ✅    | ✅            |
| 修改后，必须与修改前保持许可一致         | ✅   | ✅                 | ✅    | ✅            |
| 不得在原始许可以外附加限制            | ✅   | ✅                 | ✅    | ✅            |
| 如果项目包含GPL许可代码， 整个项目必须开源  | ✅   |                   |      |              |
| 云服务用到的代码， 云服务代码必须开源      |     | ✅                 |      |              |
| 如果项目属于动态链接库使用许可证库 项目不用开源 |     |                   | ✅    |              |
| 许可证代码在单独文件中 新增其他文件可以不开源  |     |                   |      | ✅            |

四个协议在"传染强度"上递减：GPL 最强（包含 GPL 代码则整个项目必须开源）；AGPL 把传染范围扩展到了云服务场景；LGPL 只要求动态链接的库本身开源；MPL 传染范围仅限许可证代码所在的单独文件。

## 前端主流项目的许可证选择

目前前端项目普遍选择 MIT 协议。

-   Vue： MIT [https://github.com/vuejs/vue/blob/dev/LICENSE](https://link.zhihu.com/?target=https%3A//github.com/vuejs/vue/blob/dev/LICENSE)

-   React：MIT [https://github.com/facebook/react/blob/master/LICENSE](https://link.zhihu.com/?target=https%3A//github.com/facebook/react/blob/master/LICENSE)

-   Element： MIT [https://github.com/ElemeFE/element/blob/master/LICENSE](https://link.zhihu.com/?target=https%3A//github.com/ElemeFE/element/blob/master/LICENSE)

-   Ant Design：MIT [https://github.com/ant-design/ant-design/blob/master/LICENSE](https://link.zhihu.com/?target=https%3A//github.com/ant-design/ant-design/blob/master/LICENSE)

MIT 协议是最简单的开源协议，只需保留最基本的版权许可声明即可自由使用、修改、分发。

## 案例：React 协议风波

React 现在虽然是 MIT 协议，但历史上曾在开源协议之外附加了专利条款，这也是"百度要求内部全面停止使用 React"事件的起因。

附加条款的大意是：当发生下列情况时，Facebook 有权吊销 React 的使用权：

-   与 Facebook 及其附属机构发生利益冲突；
-   同任何一个和 Facebook 有关的组织发生了法律纠纷；
-   同任何与 React 有关的组织发生利益冲突。

也就是说，使用 React 的项目只要与 Facebook 存在利益冲突，都可能被吊销使用权。对大型公司而言，这种不确定性无法接受。事件持续发酵后，开源社区在更多 Facebook 开源项目中发现了类似规定，开发者普遍认为这种许可证模式正在毒害社区。最终 Facebook 修改了开源协议，React 转为标准的 MIT 协议。

::: warning 启示
选型开源库时不能只看协议名称，还要检查 LICENSE 文件中的附加条款。协议层面的风险在大规模商用场景下会被显著放大。
:::

## 如何选择开源协议

面对多种协议对比，Github 提供了专门的网站 **[Choose an open source license](https://choosealicense.com/)** 来简化判断。

该网站主张从使用目的出发选择许可证：

-   需要简单宽松的协议： MIT 协议

    -   代表项目： Vue 、React 、Element

-   比较关心专利： Apache协议

    -   代表项目： Apache、SVN
-   比较关心项目的共享改进: GPL

    -   代表项目： Linux 、Git

-   非代码项目： Creative Commons

    -   署名： 必须提到作者
    -   非商业用户
    -   禁止演绎，禁止修改原作品再创作

对前端组件库这类项目而言，通常选择宽松的 MIT 协议即可。

## 在 Github 中添加开源许可证

Github 内置了各种开源许可证的模板，创建项目时可以直接选择对应的开源协议；也支持后期添加和修改。开源许可证本质上就是一个放在项目根目录的文本文件，添加步骤如下：

1. 在项目根目录点击 【Add file】，选择 【Create new file】。
2. 填入文件名 【 LICENSE 】。Github 会自动识别出这是在添加开源协议，并显示 【 Choose a license template 】选择许可证模版按钮，点击按钮即可选择需要的模版。
3. 填写有效期与作者全名：
    - 有效期填写： 2022 - present
    - 作者全名可做中英文混合填写，例如 ： Ran (Joseph) Xia
4. 点击 Review and Submit，许可证即创建完成。

## 小结

开源许可证是软件作者保留版权、授予他人使用权限的法律工具。许可证体系分为 Copyright、Copyleft、Permissive、Creative Commons 四大类，其中 Copyleft 与 Permissive 是通常所说的开源许可证：Permissive（MIT、BSD、Apache2）限制宽松、允许闭源商用，Copyleft（GPL、AGPL、LGPL、MPL）要求衍生品继续开源。前端生态普遍采用 MIT 协议，为组件库选择协议时可直接使用 Github 提供的 LICENSE 模板添加；同时在使用第三方开源库时也应确认其许可证类型，避免版权纠纷。

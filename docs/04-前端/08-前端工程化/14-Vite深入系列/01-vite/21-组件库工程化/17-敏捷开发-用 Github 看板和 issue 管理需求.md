# 敏捷开发-用 Github 看板和 issue 管理需求

## 概念说明

Github 上的项目往往都采用敏捷方式管理。一个项目可能由几个处于不同时区国家的程序员合作完成，项目中的大量沟通任务都可以在 Github 上进行，团队有条不紊地向着同一个目标前进。Github 的项目管理主要由 **Issue（问题管理）** 和 **Project（项目看板）** 两个功能组成。

## 核心要点

- 问题管理系统是任何项目都需要的，与是否采用敏捷无关。项目开发过程可以视为一个挖掘问题、表达问题、归结问题、处理问题的循环。
- Issue 是 Github 内置的工单系统，承担优先级管理、人员分配、代码关联、讨论协作四类能力。
- Project 的理论根源是敏捷开发的看板模式（源自丰田精益生产），通过"创建项目 → 纳入 Issue → 分配任务 → 看板跟踪"四步实现可视化管理。
- 项目 ≠ 代码。Vue 代码本身不是项目，"八月底完成 Vue1.0 发布"才是项目；一次项目对应解决一部分特定的 Issue。
- 开发完成不等于任务完成：代码 review 与关闭 Issue 需要第三者确认。
- ⚠️ 常见误区：把代码仓库等同于项目，缺少目标、边界与进度跟踪。

## 问题管理 - Issue

无论项目管理方式是否敏捷，问题管理系统是一定需要的。问题管理是四大管理模式之一，项目开发过程可以当做一个挖掘问题、表达问题、归结问题、处理问题的过程。一个项目本质上就是将一个大问题分拆、并各个击破的过程。

项目中的问题大致可归纳为以下几类：

- 任务  - 待完成任务；

- Bug 缺陷；

- Feature 新特性；

- 问题：
  - 功能建议；
  - 项目中不能计划或不期望发生的问题和困难。

基于问题的管理，需要一个强大的工单系统支撑——就好比大企业面向无数客户需要一个 Call Center 不断处理工单。这个工单系统需要提供以下功能：

- 项目管理
  - 优先级
  - 关联项目、基线、里程碑
  - 分配人员
  - 制定日程
  - 监控进度提供统计

- 项目合作 - TeamWork
  - 讨论
  - 邮件通知

- 代码管理
  - 将 Issue 关联代码
  - 将 Issue 关联代码提交与合并

Issue 就是 Github 中内置的工单系统，即问题管理系统。在 Github 中打开 【Issue】选项卡即可提交 Issue，主要字段包括：

- 标题： 简述问题内容；

- 描述： 聊天室模式，所有人都可以评论；

- 指派者： 即目前的负责人。发现 Bug 的人可以指派给项目负责人，负责人可以根据分工指派给具体开发，也支持自行认领；

- 分类： 标签体系，重要程度、优先级、分类都可以靠标签实现；

- 项目和里程碑： 表示该问题与哪个项目相关。一般所有属于这个项目的问题都解决或被移出后，项目才能算完结；

- 相关代码： 可以链接某一个代码的提交，标明相关代码的位置。

在 ISSUE 中可以不断讨论问题、链接代码、指派给相关人，直到最终将问题解决并 Close。这就是问题管理系统的完整闭环。

## 项目 - Project

项目是在一定约束条件下（时间、资源（人力、设备）），完成一个明确的一次性任务。很多人把代码称之为项目，这是错误的。具体来讲，Vue 代码不是一个项目，"在八月底完成 Vue1.0 版本的发布"才是一个项目。

为了完成项目，需要确定项目的目标，拆分（Break Down）成 Task ISSUE；在完成过程中不断测量、不断平衡质量、进度、成本，促使项目在约定时间用合理的成本达成目标——这就是项目管理。

Github 使用敏捷方式管理项目：在问题管理的基础上，一次项目（例如完成某一个版本）可以看做是解决一部分特定的 Issue。这一功能由 Project 实现，其理论根源来自敏捷开发的**看板模式**。看板模式源于丰田的精益生产，是一种可视化的流程管理系统。

### 看板管理项目的步骤

使用看板管理项目需要以下步骤：

- 创建项目:  确定目标；

- 将相关 ISSUE 纳入项目中： 拆分任务、划分任务边界；

- 分配任务到个人；

- 看板跟踪项目进度。

#### 1. 创建项目

Github 项目的面板在最新版中调整到了组织或个人目录中（https://github.com/orgs/smarty-team/projects），这样更容易在多个代码仓库之中管理。

开启一个项目 【Smarty UI Vite Alpha.1】 开发，可以选择项目的种类。视图方式有 Table 和 Board 两种，Board 就是看板模式，与大多数敏捷团队中使用的实体看板一致。

创建后，回到 smarty-admin 仓库中将 Project 挂载到该仓库。

#### 2. 将 ISSUE 纳入项目

根据项目目标划定具体的功能。这一步相当于把目标分解和确定开发边界。

以 Alpha.1 版本为例：目标是"完善工程化闭环 + 添加典型组件"，因此需要将相关的功能 ISSUE 和 Bug ISSUE 添加到项目之中；如果还缺少一些功能，可以新建 ISSUE。

#### 3. 分配项目

评估 ISSUE 的重要度和复杂度，确定开发的优先顺序，然后分配任务到开发者，或由开发者自觉认领。开源团队中这个过程一般以认领为主。

#### 4. 看板跟踪进度

使用看板功能跟踪项目过程，流程状态一目了然。

需要强调的是：**开发完成不是完成任务**。代码的 review 和关闭项目需要第三者确认才有意义——例如新开发的组件，必须经过他人检查代码、跑通测试用例并确认，才算完成该 ISSUE。

正常情况下，当项目的所有 ISSUE 都完成后，就可以宣布项目成功完结。实际操作中很多时候还会临时加入一些任务，或者把不太好完成的内容放到下一期。

## 小结

Github 的项目管理由 Issue 与 Project 组成：Issue 是内置工单系统，负责问题的记录、分类、指派与代码关联，形成"发现 → 讨论 → 修复 → Close"的闭环；Project 基于敏捷看板模式，通过创建项目、纳入 Issue、分配任务、看板跟踪四步，将一次版本开发（即一部分特定 Issue 的解决）可视化地管理起来。开源团队身处不同时区、彼此不熟悉，更需要这类工具化的敏捷管理模型支撑协作。

# 容器与云安全

## 概念说明

容器与云改变了"主机"的边界：一台物理机上跑着几十个共享内核的容器，一个云账号控制着成百上千个按 API 管理的资源。传统"给服务器打补丁、装杀毒"的安全模型在这里失效，取而代之的是三层防线：

- **镜像层**：容器内容物是否干净、可被利用面是否最小（最小镜像、非 root、去能力）。
- **运行时层**：容器与宿主机、容器与容器之间的隔离（seccomp、capabilities、网络策略）。
- **平台层**：编排与云资源的访问控制（K8s RBAC、云 IAM 最小权限）。

责任划分遵循**共享责任模型**：托管 K8s 中，云厂商负责控制面与宿主机安全，用户负责镜像、工作负载配置、IAM 与数据安全。出了事故先分清责任侧，再谈整改。

::: tip 核心原则
容器安全的主旋律是**最小化**：最小镜像、最小权限、最小能力、最小网络可达面。每一个"为了方便"保留的 `--privileged`、`:latest`、`CAP_SYS_ADMIN`，都是攻击者眼中一条现成的逃逸路径。
:::

## 核心要点

- 镜像基线：优先 distroless / alpine 等最小镜像，多阶段构建，固定 tag（禁 `latest`），不含包管理器与 shell 可大幅降低被利用概率。
- 容器一律**非 root** 运行（`USER app`），Dockerfile 与 K8s `runAsNonRoot: true` 双重声明。
- 能力最小化：`cap_drop: [ALL]`，再按需加回（通常只需绑定 80 端口的 `NET_BIND_SERVICE`）。
- **挂载 `/var/run/docker.sock` 等同于把宿主机 root 交给容器**，这是最常见的容器逃逸根因。
- K8s 用 Pod Security Admission（restricted 级别）+ 显式 `securityContext`，替代已废弃的 PodSecurityPolicy。
- 云 IAM 按"角色 + 最小权限"建模：一个工作负载一个角色，策略精确到资源 ARN 与动作，拒绝 `*:*`。
- 镜像扫描纳入 CI/CD 门禁：Trivy / Grype 扫描 CRITICAL/HIGH 漏洞阻断发布，SBOM 留档。
- ⚠️ 常见误区：以为容器命名空间隔离等于安全边界。共享内核的容器隔离弱于虚拟机，`--privileged` + 内核漏洞即可逃逸。
- ⚠️ 常见误区：把云 AK/SK 写进容器环境变量或镜像层。Secret 走密钥管理服务（KMS/Secrets Manager/Sealed Secrets）。
- ⚠️ 常见误区：K8s `ClusterRoleBinding` 一把梭绑定所有命名空间。按命名空间做 Role 划分。

## Docker 安全基线

### 1. 安全的 Dockerfile 模板

```dockerfile
# ---- 构建阶段：完整工具链 ----
FROM python:3.12-slim AS builder
WORKDIR /build
COPY requirements.txt .
RUN pip install --no-cache-dir --prefix=/install -r requirements.txt

# ---- 运行阶段：最小镜像 + 非 root ----
FROM python:3.12-slim

# 最小化：清理文档与包缓存，减少可被利用的文件面
RUN apt-get update \
    && apt-get install -y --no-install-recommends --no-install-suggests \
        ca-certificates \
    && rm -rf /var/lib/apt/lists/* /usr/share/doc/* /usr/share/man/*

# 创建专用用户：无 shell、无 home 写入需求
RUN groupadd -r app && useradd -r -g app --shell /usr/sbin/nologin app

COPY --from=install /install /usr/local
COPY --chown=app:app ./src /app/src
WORKDIR /app
USER app                                   # 非 root 运行

EXPOSE 8000
HEALTHCHECK --interval=30s CMD ["python", "-c", "import urllib.request; urllib.request.urlopen('http://localhost:8000/healthz')"]
ENTRYPOINT ["python", "-m", "app.main"]
```

```bash
# 以安全参数运行容器
docker run -d \
  --name webapp \
  --read-only \                          # 只读根文件系统
  --tmpfs /tmp \                         # 可写目录用 tmpfs
  --cap-drop=ALL \                       # 移除全部 Linux capabilities
  --security-opt=no-new-privileges \     # 禁止提权
  --security-opt seccomp=/etc/docker/seccomp-default.json \
  -p 8000:8000 \
  --restart=on-failure \
  registry.example.com/webapp:1.42.0     # 固定版本 tag
```

### 2. 危险配置对照表

| 危险配置 | 后果 | 正确做法 |
|---|---|---|
| `--privileged` | 容器获得宿主机全部能力，逃逸几乎零门槛 | 明确所需能力，逐项 `--cap-add` |
| 挂载 `docker.sock` | 可直接控制宿主机 Docker，等同 root | 通过代理/SSH 管理容器，不进容器 |
| `USER root` 或缺省 | 容器被攻破即 root 提权点 | 专用 UID 运行 |
| `:latest` / 未固定 tag | 构建不可复现，供应链不可审计 | 语义化版本 + digest 固定 |
| 宿主机宽目录挂载（`/`、`/etc`） | 容器内可读写宿主机敏感路径 | 最小目录、只读挂载 |
| 密钥写入镜像层 | 镜像分发即密钥泄露 | 运行时注入（KMS/Secrets） |

### 3. 基线自查命令

```bash
# 查看镜像内的 capabilities 与用户
docker inspect webapp --format '{{.Config.User}} | Caps: {{.HostConfig.CapAdd}} / Dropped: {{.HostConfig.CapDrop}}'

# 使用 Docker Bench 快速体检（CIS Docker Benchmark）
docker run --rm --net host --pid host --userns host --cap-add audit_control \
  -v /etc:/etc:ro -v /var/lib:/var/lib:ro -v /var/run/docker.sock:/var/run/docker.sock:ro \
  docker/docker-bench-security
```

## Kubernetes 安全上下文

### 1. restricted 级别的 Pod 示例

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: webapp
  labels: { app: webapp }
spec:
  automountServiceAccountToken: false      # 不需要访问 API 时关闭 SA token 自动挂载
  securityContext:                         # Pod 级
    runAsNonRoot: true
    runAsUser: 10001
    runAsGroup: 10001
    fsGroup: 10001
    seccompProfile: { type: RuntimeDefault }
  containers:
    - name: webapp
      image: registry.example.com/webapp@sha256:3f5c...   # digest 固定
      securityContext:                     # 容器级
        allowPrivilegeEscalation: false    # 禁止 setuid 提权
        readOnlyRootFilesystem: true
        capabilities:
          drop: [ALL]
      resources:                           # 资源限制也是安全项：防 DoS 与节点挤占
        requests: { cpu: 250m, memory: 256Mi }
        limits:   { cpu: "1",  memory: 512Mi }
      volumeMounts:
        - { name: tmp,     mountPath: /tmp }
        - { name: cache,   mountPath: /app/.cache }
  volumes:
    - { name: tmp,   emptyDir: {} }
    - { name: cache, emptyDir: {} }
```

### 2. NetworkPolicy：默认拒绝，按需放行

```yaml
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: default-deny-ingress
  namespace: prod
spec:
  podSelector: {}
  policyTypes: [Ingress, Egress]
---
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: webapp-allow
  namespace: prod
spec:
  podSelector: { matchLabels: { app: webapp } }
  ingress:
    - from:
        - namespaceSelector: { matchLabels: { name: ingress-nginx } }
      ports: [{ port: 8000, protocol: TCP }]
  egress:
    - to: [{ podSelector: { matchLabels: { app: postgres } } }]
      ports: [{ port: 5432, protocol: TCP }]
    - ports: [{ port: 53, protocol: UDP }]   # DNS
```

::: warning 没有 NetworkPolicy 的集群等于全内网互通
默认情况下 K8s 不限制 Pod 间流量，一个被攻破的 Pod 可以直接横向扫描整个集群。参考 [16-内网渗透](./16-内网渗透.md) 中的横向移动手法，先"默认拒绝"再按需放行是唯一正确的姿势。
:::

### 3. RBAC 最小权限

```yaml
# 只读访问本命名空间 Pod 的角色——CI巡检类服务账号的典型配置
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata: { name: pod-reader, namespace: prod }
rules:
  - apiGroups: [""]
    resources: [pods, pods/log]
    verbs: [get, list, watch]
---
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata: { name: ci-reader, namespace: prod }
subjects:
  - kind: ServiceAccount
    name: ci-inspector
    namespace: ci
roleRef: { kind: Role, name: pod-reader, apiGroup: rbac.authorization.k8s.io }
```

## 云 IAM 最小权限

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "ReadOnlyOneBucket",
      "Effect": "Allow",
      "Action": ["s3:GetObject", "s3:GetObjectVersion"],
      "Resource": "arn:aws:s3:::app-assets-prod/*"
    },
    {
      "Sid": "DenyAllElse",
      "Effect": "Deny",
      "Action": "*",
      "Resource": "*"
    }
  ]
}
```

IAM 建模四步法：

1. **识别工作负载**：每个微服务、每条流水线一个独立角色，禁止共享账号。
2. **枚举实际调用**：用云平台的访问分析器（如 IAM Access Analyzer）生成"实际使用的动作清单"。
3. **按清单授权**：动作精确、资源 ARN 精确，附 `Deny` 兜底。
4. **短期凭证**：工作负载用角色联合/IRSA/OIDC 联合换取临时 token，长期 AK/SK 只允许出现在不可消除的场景且进轮换计划。

::: danger IAM 通配符是云上第一大事故源
`Action: "*"` 或 `Resource: "*"` 出现在生产策略中，一次凭证泄露即可遍历读写全量资源。审计策略时，`*` 出现的位置比出现与否更重要——只允许在边界明确的只读场景。
:::

## 镜像扫描：Trivy 与 Grype

```bash
# Trivy：漏洞 + 配置 + 密钥 + SBOM 一站式
trivy image --severity HIGH,CRITICAL --exit-code 1 registry.example.com/webapp:1.42.0
trivy fs --scanners vuln,secret .              # 仓库文件系统扫描
trivy image --format cyclonedx --output sbom.json registry.example.com/webapp:1.42.0

# Grype：与 Syft SBOM 配套的漏洞扫描
syft registry.example.com/webapp:1.42.0 -o json > sbom.json
grype sbom.json --fail-on high
```

CI 门禁集成（GitHub Actions 示例）：

```yaml
name: image-security-gate
on: [push]
jobs:
  scan:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - name: Build image
        run: docker build -t webapp:${{ github.sha }} .
      - name: Trivy scan (block on HIGH/CRITICAL)
        uses: aquasecurity/trivy-action@master
        with:
          image-ref: webapp:${{ github.sha }}
          severity: HIGH,CRITICAL
          exit-code: "1"
          ignore-unfixed: true
      - name: Upload SBOM
        if: always()
        uses: actions/upload-artifact@v4
        with: { name: sbom, path: sbom.json }
```

::: tip 扫描器只是门禁，不是修复
CI 扫描的价值在于把"新增 CRITICAL 漏洞的镜像"挡在发布之外，但修复依赖基础镜像更新与依赖升级流程，应与 [27-供应链安全](./27-供应链安全.md) 的依赖治理合并推进，否则门禁会被 ignore 清单慢慢腐蚀。
:::

## 常见陷阱

| 陷阱 | 后果 | 正确做法 |
|---|---|---|
| `--privileged` 或挂载 docker.sock | 容器逃逸直取宿主机 | 能力逐项加回，socket 不进容器 |
| 容器以 root 运行 | 提权/逃逸起点 | `USER app` + `runAsNonRoot` |
| 镜像用 `latest` | 版本漂移、无法追溯 | 固定 tag + digest |
| Secret 写进镜像/环境变量明文 | 镜像层泄露 | KMS/Sealed Secrets 运行时注入 |
| K8s 全部 `ClusterRoleBinding` | 横向移动无阻拦 | 命名空间 Role + 最小 verbs |
| 无 NetworkPolicy | 内网互通，一台沦陷全网沦陷 | 默认拒绝 + 按需放行 |
| IAM `Action: "*"` | 凭证泄露即全域沦陷 | 动作/资源精确 + Deny 兜底 |
| 扫描不设门禁/ignore 无限期 | 漏洞镜像持续上线 | CI exit-code 门禁 + ignore 有效期 |

## 最佳实践

### 1. 从镜像供应链源头减负

最小镜像不只是"体积小"：没有 shell、没有包管理器的 distroless 镜像，让大量利用链直接失效。配合多阶段构建与 digest 固定，把运行时攻击面压到最低。

### 2. 策略即代码，集群统一执行

`securityContext`、NetworkPolicy、RBAC 用 Kyverno/OPA Gatekeeper 以策略代码方式在准入层强制执行，而不是靠人肉审查 YAML。违反策略的提交在 CI 阶段即失败。

### 3. IAM 定期做"减法审计"

季度级审计：清理未使用角色与凭证、回收长期 AK/SK、核对 `*` 通配符、确认 MFA 覆盖所有人类账号。IAM 的权限只会自然增长，不主动减就会膨胀。

### 4. 与主机加固和运维监控衔接

容器安全不是孤岛：宿主机基线见 [17-服务器安全加固](./17-服务器安全加固.md)，运行时异常的排查见 [18-入侵排查与追踪](./18-入侵排查与追踪.md)，DevSecOps 流水线的整体位置见 [19-研发安全：从 SDL 到 DevSecOps](./19-研发安全：从%20SDL%20到%20DevSecOps.md)。

## 版本说明

- **Kubernetes 1.25+**：PodSecurityPolicy 已移除，替代方案为 Pod Security Admission（内置，支持 privileged/baseline/restricted 三级）。
- **Docker 20.10+**：`--cap-drop=ALL`、`no-new-privileges`、seccomp 默认 profile 均为稳定能力。
- **Trivy**：v0.40+ 支持 vuln/misconfig/secret/sbom 多扫描器合一。
- **Grype / Syft**：Anchore 开源组合，Syft 生成 SBOM（SPDX/CycloneDX），Grype 基于 SBOM 做漏洞匹配。
- **CIS Benchmarks**：Docker Engine 与 Kubernetes 分别有 CIS 基线文档，Docker Bench 安全脚本据此打分。

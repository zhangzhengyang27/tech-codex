# 分表分库：单表数据量大读写缓慢如何解决？

## 概念：什么是分表分库

查询分离方案存在三大不足，其中一个不足是：当主数据量越来越大时，写操作缓慢。分表分库正是针对这一问题的解决方案。

**定义：**

- **分表**：将一份大的表数据拆分存放至多个结构一样的拆分表；
- **分库**：将一个大的数据库拆分成多个结构一样的小库。

## 问题背景

以一个电商系统的架构优化为例。该系统包含用户和订单 2 个主要实体，其中：

- 订单数据量已达上亿，且每日以百万级的速度增长，之后还可能是千万级；
- 存储订单的数据库表仍是单库单表。

对于单库单表而言，一旦数据量疯狂增长，无论是 IO 还是 CPU 都会扛不住。为使系统抗住千万级数据量的压力，有效的方案是先将订单表拆分，再进行分布存储——即分表分库。

落地分表分库需要依次解决三个问题：拆分存储的技术选型、分表分库的实现思路、分表分库的不足。

## 拆分存储的技术选型

拆分存储常用的技术解决方案目前主要分为 4 种：MySQL 的分区技术、NoSQL、NewSQL、基于 MySQL 的分表分库。

### 1. MySQL 的分区技术

MySQL 的分区主要在文件存储层做文章，它可以将一张表的不同行存放在不同存储文件中，对使用者比较透明。

实战项目中不使用它的原因主要有三点：

- MySQL 的实例只有一个，它仅仅分摊了存储，无法分摊请求负载；
- 正因为 MySQL 的分区对用户透明，实际操作时往往不被注意，跨分区操作会严重影响系统性能；
- MySQL 还有一些其他限制，比如不支持 query cache、位操作表达式等，详见官方文档：<https://dev.mysql.com/doc/refman/5.7/en/partitioning-limitations.html>。

### 2. NoSQL（如 MongoDB）

MongoDB 是比较典型的 NoSQL 数据库。其分片功能从并发性和数据量这两个角度已能满足一般大数据量的需求，但需注意三大要点：

- **约束考量：** MongoDB 不是关系型数据库而是文档型数据库，它的每一行记录都是一个结构灵活可变的 JSON。存储订单这类非常重要的数据时不能使用 MongoDB，因为订单数据必须使用强约束的关系型数据库进行存储；
- **业务功能考量：** 多年来，事务、锁、SQL、表达式等千奇百怪的操作都在 MySQL 身上一一验证过，MySQL 久经考验，功能上能满足所有业务需求，MongoDB 却不能，且大部分 NoSQL 也存在类似问题；
- **稳定性考量：** MySQL 的运维成熟、稳定性没有问题；MongoDB 的稳定性在不熟悉的情况下无法保证。因此在拆分存储技术选型中，NoSQL 通常不作为首选。

### 3. NewSQL（如 TiDB）

NewSQL 技术还比较新。从稳定性和功能扩展性两方面考量后，一般不将其用于核心数据存储，具体原因与 MongoDB 类似。

### 4. 基于 MySQL 的分表分库

选择基于 MySQL 的分表分库，主要有一个重要考量：分表分库对第三方依赖较少，业务逻辑灵活可控；它本身并不需要非常复杂的底层处理，也不需要重新做数据库，只是根据不同逻辑使用不同 SQL 语句和数据源而已。

使用分表分库，存在 3 个技术通用需求需要实现：

- **SQL 组合：** 关联的表名是动态的，需要根据逻辑组装动态的 SQL；
- **数据库路由：** 数据库名也是动态的，需要通过不同的逻辑使用不同的数据库；
- **执行结果合并：** 有些需求需要通过多个分库执行，再合并归集起来。

### 中间件的两种模式

市面上能解决以上问题的中间件分为 2 类：Proxy 模式、Client 模式。

**（1）Proxy 模式：** 把 SQL 组合、数据库路由、执行结果合并等功能全部存放在一个代理服务（如 ShardingSphere 的 Sharding-Proxy 层）中，而与分表分库相关的处理逻辑全部存放在另外的服务中。这种设计模式的优点是对业务代码无侵入，业务只需要关注自身业务逻辑即可。

**（2）Client 模式：** 把分表分库相关逻辑存放在客户端，一般客户端的应用会引用一个 jar，然后在 jar 中处理 SQL 组合、数据库路由、执行结果合并等相关功能。这种模式的优点是代码灵活可控。

**选型结论：** 对比两种模式的优缺点即可得出答案——看重代码灵活可控时，可选 Client 模式的 Sharding-JDBC；追求对业务零侵入时，可考虑 Proxy 模式。当然，拆分存储选择哪种技术，实际工作中需根据各自的实际情况来定。

## 分表分库实现思路

技术选型解决后，接下来是具体落地。落实分表分库解决方案时，需要考虑 5 个要点。

### 1. 使用什么字段作为分片键

以电商订单系统为例，常见的业务需求包括：

- 用户需要查询所有订单，订单数据中肯定包含不同的 merchant_id、order_time；
- 后台需要根据城市查询当地的订单；
- 后台需要统计每个时间段的订单趋势。

根据这些常见业务需求判断优先级：用户操作（第一个需求）必须优先满足。使用 user_id 作为订单的分片字段，就能保证每次用户查询数据时，在一个分库的一个分表里即可获取数据；分表分库查询时，首先会把 user_id 作为参数传过来。

**选择字段作为分片键的三点要求：**

- 数据尽量均匀分布在不同表或库；
- 跨库查询操作尽可能少；
- 这个字段的值不会变（这点尤为重要）。

### 2. 分片的策略是什么

确定 user_id 作为订单分片字段后，接下来考虑分片策略。目前市面上通用的分片策略分为三种：

- **根据范围分片：** 比如用户 id 是自增型数字，把用户 id 按照每 100 万份分为一个库、每 10 万份分为一个表的形式进行分片（此处只讲分表，分库即把分表分组存放在一个库）；
- **根据 hash 值分片：** 根据用户 id 的 hash 值 mod 一个特定的数进行分片（为了方便后续扩展，一般是 2 的几次方）；
- **根据 hash 值及范围混合分片：** 先按照范围分片，再根据 hash 值取模分片。比如表名 = order_#user_id%10#_#hash(user_id)%8，即被分成了 10*8=80 个表。

**策略选择原则：** 假设之后数据量变大、需要把表分得更细，此时保证迁移的数据尽量少即可。因此，根据 hash 值分片时一般建议拆分成 2 的 N 次方张表。比如分成 8 张表，数据迁移时把原来的每张表拆一半出来组成新表，这样数据迁移量就小。

**示例方案：** 根据用户 id 的 hash 值取模 32，把数据分成 32 个数据库，每个数据库再分成 16 张表。简单计算一下：假设每天订单量 1 千万，每个库日增 1000万/32=31.25 万，每个表日增 1000万/32/16=1.95 万；3 年后每个表的数据量约为 2 千万，还在可控范围内。

因此，如果业务增长特别快，且运维还扛得住，为避免以后出现扩容问题，建议库分得越多越好。

### 3. 业务代码如何修改

业务代码修改部分与业务强关联，通用性有限，但有几个要点值得注意：

- 微服务架构下，对特定表的分表分库，其影响面只在该表所在的服务中；如果是一个单体架构的应用做分表分库，改造会复杂得多；
- 在互联网架构中，基本不使用外键约束；
- 随着查询分离的流行，后台系统中有很多操作需要跨库查询，导致系统性能非常差。这时分表分库一般会结合查询分离一起操作：先将所有数据在 ES 索引一份，再使用 ES 在后台直接查询数据。如果订单详情数据量很大，还有一个常见做法，即先在 ES 中存储索引字段（作为查询条件的字段），再将详情数据存放在 HBase 中。

一般来说，业务代码的修改不会很复杂，最麻烦的是历史数据的迁移。

### 4. 历史数据迁移

历史数据的迁移非常耗时，有时迁移几天几夜都很正常。而在互联网行业中，别说几天几夜，就连停机几分钟业务都无法接受，这就要求给出一个无缝迁移的解决方案。

该迁移方案与查询分离中的数据同步思路一致。**基本思路：存量数据直接迁移，增量数据监听 binlog，然后通过 canal 通知迁移程序搬运数据；新的数据库拥有全量数据，且校验通过后逐步切换流量。**

数据迁移解决方案的详细步骤如下：

1. 上线 canal，通过 canal 触发增量数据的迁移；
2. 迁移数据脚本测试通过后，将老数据迁移到新的分表分库中；
3. 注意迁移增量数据与迁移老数据的时间差，确保全部数据都被迁移过去，无遗漏；
4. 第二步、第三步都运行完后，新的分表分库中已经拥有全量数据，这时运行数据验证的程序，确保所有数据都存放在新数据库中；
5. 到这步数据迁移就算完成，之后是新版本代码上线；至于是灰度上还是直接上，需要根据实际情况决定，回滚方案也是一样。

### 5. 未来的扩容方案是什么

随着业务的发展，如果原来的分片设计已经无法满足日益增长的数据需求，就需要考虑扩容。扩容方案主要依赖以下两点：

- 分片策略是否可以让新表数据的迁移源只是 1 个旧表，而不是多个旧表——这正是前面建议使用 2 的 N 次方分表的原因；
- 数据迁移：把旧分片的数据迁移到新的分片上，方案与历史数据迁移一致。

## 分表分库的不足

以上是业界常用的分表分库做法，此方案仍然存在不足之处：

- **ES+HBase 做数据查询分离的方案：** 查询分离可单独使用 ES，也可采用 ES+HBase 组合方案；
- **增量数据迁移：** 如何保证数据的一致性及高可用性？这个问题需要单独设计同步方案解决；
- **短时订单量大爆发：** 分表分库仍然扛不住时，解决方案是什么？这个问题需要结合缓存和秒杀架构单独展开。

## 小结

分表分库的核心决策链路为：技术选型（MySQL 分区 / NoSQL / NewSQL / 基于 MySQL 的分表分库四种方案对比）→ 分片键（均匀分布、少跨库、值不变）→ 分片策略（hash 取模建议 2 的 N 次方）→ 业务改造（结合查询分离，ES 索引 + HBase 详情）→ 无缝迁移（canal + binlog，存量直迁 + 增量同步）→ 扩容预案（单源迁移）。具体落地时，需结合自身的数据规模与查询形态推演细节。

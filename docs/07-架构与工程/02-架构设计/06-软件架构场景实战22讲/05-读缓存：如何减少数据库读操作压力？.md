# 读缓存：如何减少数据库读操作压力？

## 问题背景

某电商系统中存放了 50000 多条商品数据，用户每次浏览商品详情页时，系统需要先从数据库中读取数据，再进行数据拼装和计算，耗时有时长达 1 秒，导致页面打开速度慢。

项目初期因时间紧张，未从系统性能角度深入考量；当系统流量起来后，减少数据库读操作压力就成为必须解决的问题。采取的通用方案是：把所有商品数据缓存起来。

## 本地缓存与分布式缓存

### 本地缓存及其局限

最简单的实现方法是使用本地缓存。Google Guava 提供了 cache 内存缓存模块，它把所有商品的 ID 与商品详情信息一对一缓存至 JVM 内存中；用户获取商品详情数据时，系统根据商品 ID 直接从缓存读取数据，可大大提升页面访问速度。

但简单换算后即可发现该方案明显不合理：

1 条商品数据往往包含品牌、分类、参数、规格、服务、描述等字段，仅存储这些数据就要占用 500K 左右内存；将这些数据缓存到本地，约需 500K × 50000 = 25G 内存。假设商品服务有 30 个服务器节点，仅缓存商品数据就需要额外准备 750G 内存空间，这种方法显然不可取。

### 分布式缓存

另一个解决办法是分布式缓存：将所有缓存数据集中存储在同一个地方，而非保存到各个服务器节点，所有服务器节点从这个地方读取数据。

统一存储缓存的地方需要使用什么技术，就涉及缓存中间件的技术选型。

## 缓存中间件技术选型

市面上比较流行的缓存中间件有 Memcached、MongoDB、Redis 三种。目前市面上通用的缓存中间件技术是 Redis，使用 MongoDB 的公司最少——它本质上是一个数据库，只是因为读写速度与其他数据库相比较快，才被人们当作类似缓存的存储使用。

Redis 之所以比 Memcached 流行，主要有三种原因。

**（1）数据结构**

以保存 List 缓存对象为例：使用 Memcached 时，往 List 增加一条数据，首先需要读取整个 List，再反序列化塞入数据，接着再序列化存储回 Memcached；而对 Redis 而言，这仅仅是一个 Redis 请求，会直接塞入数据并存储，简单快捷。

**（2）持久化**

对 Memcached 来说，一旦系统宕机数据就会丢失。Memcached 官方文档显示，1.5.18 以后 Memcached 支持 restartable cache，其实现原理是重启时 CLI 先发信号给守护进程，然后守护进程将内存持久化至一个文件中，系统重启时再从那个文件恢复数据。不过，这个设计仅在正常重启情况下使用，意外情况仍然不处理。

**（3）集群（尤为重要）**

Memcached 的集群设计非常简单，客户端根据 Hash 值直接判断存取的 Memcached 节点；而 Redis 的集群因在高可用、主从、冗余、failover 等方面都有所考虑，集群设计相对复杂，属于较常规的分布式高可用架构。

综合以上对比，最终选用 Redis 作为缓存中间件。

## 缓存何时存储数据

使用缓存的基本逻辑是：

- 先尝试从缓存中读取数据；
- 缓存中没有数据或者数据过期，再从数据库中读取数据保存到缓存中；
- 最终把缓存数据返回给调用方。

**这种逻辑唯一麻烦的地方：当用户发来大量并发请求，且所有请求同时挤在上面第 2 步时，如果这些请求全部从数据库读取数据，会直接挤爆数据库。**

挤爆的情况可以分为三种，逐一说明。

**1. 单一数据过期或者不存在——缓存击穿**

解决方案：第一个线程如果发现 key 不存在，先给 key 加锁，再从数据库读取数据保存到缓存中，最后释放锁。其他线程若正在读取同一个 key，必须等到锁释放后才能继续。

**2. 数据大面积过期或者 Redis 宕机——缓存雪崩**

解决方案：设置缓存的过期时间随机分布，或永不过期。

**3. 恶意请求获取的 key 不在数据库中——缓存穿透**

这种情况如果不作处理，恶意请求每次都会查询数据库，无疑给数据库增加了压力。有两种解决办法：

- ① 在业务逻辑上直接校验，在数据库不被访问的前提下过滤掉不存在的 key；
- ② 将恶意请求的 key 在缓存中存放一个空值，防止恶意请求骚扰数据库。

**缓存预热**：在深夜无人或访问量小的时候，可以考虑将热点数据预先保存到缓存中，流量大的时候用户查询无须再从数据库读取数据，可大大减少数据读压力。

## 如何更新缓存

更新缓存的步骤特别简单，总共两步：更新数据库和更新缓存。但就这两步，需要考虑好几个问题：

- 先更新数据库还是先更新缓存？更新缓存时先删除还是直接更新？
- 假设第一步成功了，第二步失败了怎么办？
- 假设 2 个线程同时更新同一个数据，A 线程先完成第一步，B 线程先完成第二步，此时该怎么办？

第一个问题存在 4 种组合，逐一给出对应的解决方案（以上几个问题紧密关联，没法单独考虑，以下一起说明）。

### 组合一：先更新缓存，再更新数据库

该组合会遇到这种情况：假设第 2 步数据库更新失败，要求回滚缓存的更新，而 Redis 不支持事务回滚；除非采用手工回滚的方式——先保存原有数据，然后再将缓存更新回原来的数据，这种解决方案比较尴尬。

举例说明：

- 原来缓存中的值是 a，两个线程同时更新库存；
- 线程 A 将缓存中的值更新成 b，且保存了原来的值 a，然后更新数据库；
- 线程 B 将缓存中的值更新成 c，且保存了原来的值 b，然后更新数据库；
- 线程 A 更新数据库时失败了，必须回滚，那现在缓存中的值应更新回什么？

一种思路是在 A 线程更新缓存与数据库的整个过程中，先把缓存及数据库都锁上，确保其他线程不能更新。这种方法可行，但其他线程能不能读呢？假设 A 更新数据库失败回滚缓存时，线程 C 也来读取缓存中的值，这时又应返回什么值？

这正是典型的事务隔离级别场景。仅仅使用缓存就要自行实现事务隔离级别，要求过高，因此不考虑该方案。

### 组合二：先删除缓存，再更新数据库

使用这种方案，就算更新数据库失败了也不需要回滚缓存。这种做法虽然巧妙规避了失败回滚的问题，却引来了两个更大的问题：

- 假设 A 线程先删除缓存，再更新数据库。在 A 线程完成更新数据库之前，后执行的 B 线程反而超前完成了操作，读取 key 发现没数据后，将数据库中的旧值存放到了缓存中。这样就会出现缓存（旧值）与数据库的值（新值）不一致的问题。
- 为了解决一致性问题，可以让 A 线程给 key 加锁；但写操作特别耗时，这种处理方法会导致大量的读请求卡在锁中。

以上描述的是典型的高可用和一致性难以两全的问题，再加上分区容错就是 CAP。继续讨论另外两种组合。

### 组合三：先更新数据库，再更新缓存

该组合同样需要考虑两个问题：

- 假设第一步成功，第二步失败了怎么办？缓存不是主流程，数据库才是，因此不会因为更新缓存失败而回滚第一步对数据库的更新。一般采取的做法是做重试机制，但重试机制如果存在延时，还是会出现数据库与缓存不一致的情况，非常不好处理。
- 假设 2 个线程同时更新同一个数据，A 线程先完成了第一步、B 线程先完成了第二步怎么办？推演整个过程：A 线程把值更新成 a，B 线程把值更新成 b，此时数据库中的最新值是 b；因为 A 线程先完成了第一步、后完成第二步，所以缓存中的最新值是 a——数据库与缓存的值不一致，同样不好处理。

因此不建议采用该方案。

### 组合四：先更新数据库，再删除缓存（推荐）

针对组合四推演可能存在的问题：

- 假设第一步成功、第二步失败怎么办？这种情况的出现概率与上个组合相比明显更少，因为删除比更新容易得多。此时虽然不完美，但出现一致性问题的概率低。
- 假设 2 个线程同时更新同一个数据，A 线程先完成第一步、B 线程先完成第二步怎么办？推演整个过程：A 线程把值更新成 a，B 线程把值更新成 b，此时数据库中的最新值是 b；因为 A 线程先完成第一步，至于第二步谁先完成已经无所谓了——反正是直接删除缓存数据。

**组合四完美地解决了以上难题，因此推荐更新缓存时，先更新数据库再删除缓存。**

不过，这个解决方案也会引发另外 3 个问题：

- 删除缓存数据后变相出现缓存击穿，此时该怎么办？该问题在前文已有对应方案（加锁）。
- 删除缓存失败如何重试？可参考《查询分离》篇中使用重试的方案解决。
- 删除缓存失败、重试成功前出现脏数据。这需要与业务方商量：这种情况比较少见，可根据实际业务情况判断是否需要解决这个瑕疵。任何一个方案都不是完美的，但如果剩下 1% 的问题需要花好几倍的代价去解决，从技术上来讲得不偿失，这就要求架构师去说服业务方。

## 缓存的高可用设计

设计高可用方案时，需要考虑 5 个要点：

- **负载均衡**：是否可以通过加节点的方式水平分担读请求压力。
- **分片**：是否可以通过划分到不同节点的方式水平分担写压力。
- **数据冗余**：一个节点的数据如果挂掉了，其他节点的数据是否可以直接接管挂掉节点的职责。
- **Fail-over**：任何节点挂掉后，集群的职责是否可以重新分配，以此保障集群正常工作。
- **一致性保证**：在数据冗余、failover、分片机制的数据转移过程中，如果某个环节出问题，能否保证所有节点数据或节点与数据库之间数据的一致性。（依靠 Redis 本身是不行的。）

如果对缓存高可用有需求，可以使用 Redis 的 Cluster 模式，上述要点它都有涉及。至于 Cluster 怎么配置，Redis 官方文档或网上都有很多教程，可自行查找相关资料学习。

## 缓存的监控

缓存上线以后，还需要定时查看缓存使用情况，再判断业务逻辑是否需要优化，也就是所谓的缓存监控。

查看缓存使用情况时，一般会监控缓存命中率、内存利用率、慢日志、延迟、客户端连接数等数据；随着问题的深入，还可以增加其他指标。

至于最终使用哪种监控工具，需要根据实际情况而定。市面上有很多开源的监控工具，比如 RedisInsight，或 Prometheus 配合 redis_exporter 搭建监控大盘。

## 此方案的价值和不足

以上方案可以顺利解决读数据请求压垮数据库的问题，目前互联网架构也基本采取这个方案。但这个方案还存在一个不足：无法解决写数据请求量大的问题——写请求多时，数据库还是会扛不住。针对这个问题，《写缓存：如何节省数据库写操作资源？》篇给出了对应解决方案。

## 小结

本文围绕数据库读压力给出了一条完整的方案链路：缓存中间件选型（Redis）→ 缓存存储时机（击穿/雪崩/穿透/预热）→ 更新策略（先更新数据库再删除缓存）→ 高可用设计（负载均衡/分片/数据冗余/Fail-over/一致性保证，Cluster 模式）→ 监控（命中率、内存利用率、慢日志、延迟、客户端连接数）。方案仍有未覆盖的场景，可结合实际的读写比例与数据规模补全。

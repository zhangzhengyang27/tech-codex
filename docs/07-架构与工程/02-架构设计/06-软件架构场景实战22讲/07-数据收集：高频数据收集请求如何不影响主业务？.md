# 数据收集：高频数据收集请求如何不影响主业务？

## 概念说明

写缓存方案（参见《[写缓存：如何节省数据库写操作资源？](./06-写缓存：如何节省数据库写操作资源？.md)》）能够减少数据库写操作的压力，但在需要**长期高频插入数据**的场景下无法满足需求。数据收集（如用户行为埋点）正是这类场景：埋点请求持续高频到达，且数据需要进入查询与分析链路。本文围绕这个问题逐步展开解决方案，重点阐述技术选型背后的思考过程。

## 业务背景（架构经历六）

业务快速发展后，日活用户达到 500 万。基于现有业务模式，业务侧提出以下需求：

- **用户行为埋点**：记录用户在特定页面的所有行为，用于开展数据分析与第三方费用结算。
- **后台准实时查询**：能在后台实时查询用户行为数据及统计报表。这里的"实时"实际上是准实时——特定时间内的延迟业务方可以接受，因此称为**准实时**。

埋点原始数据的核心字段包括：城市（根据经纬度换算）、性别（从业务表抽取）、年龄（从业务表抽取）、目标类型、目标 ID、事件动作等。

基于以上数据结构，后台查询有两类需求：

1. **原始数据查询**：以城市、性别、年龄、目标类型、目标 ID、事件动作等作为查询条件，准实时查看用户行为数据。
2. **统计报表查询**：以时间（天/周/月/年）、性别、年龄等维度，准实时查看每个目标 ID 的总点击数、平均点击次数、每个页面的转化率等统计数据。

此外，为实现费用结算，还需收集一份费用结算数据结构，其数据由埋点数据分析动态计算得出。

## 需求提炼与技术选型总览

从以上业务场景可以提炼出 6 点业务需求，以及对应的技术选型思路：

| 业务需求 | 选型思路 |
|---------|---------|
| **原始数据海量** | 使用 HBase 进行持久化 |
| **埋点记录的请求响应要快** | 埋点记录服务先把原始埋点记录写入一个缓冲位置以保证快速响应（候选方案后文展开） |
| **可通过后台查询原始数据** | HBase 直接作为查询引擎速度太慢，需使用 ES 保存查询页面上的条件字段和活动 ID |
| **各种统计报表需求** | 数据可视化工具（Kibana、Grafana 等）灵活性不足，最终选择自研报表功能 |
| **根据埋点日志生成费用结算数据** | 费用结算数据保存在 MySQL 中 |
| **将缓存数据加工后写入 ES、HBase、MySQL** | 业务有准实时查询需求，需使用实时处理工具；市面主流为 Storm、Spark Streaming、Apache Flink（后文展开） |

整体方案的骨架：**埋点服务写缓冲 → 缓冲数据进入 MQ → 实时计算框架加工 → 写入持久化层（ES、HBase、MySQL）**。落地过程中需要依次解决 4 个关键问题。

## 关键决策一：使用什么技术保存埋点数据的第一现场

市面上适合快速保存埋点数据的技术主要有 Redis、Kafka、本地日志三种。

### Redis 的 AOF 机制问题

Redis 的 AOF 机制会持久化保存所有操作记录，用于服务器宕机后数据还原。落盘时机由 AOF 配置 `appendfsync` 决定：

| appendfsync 配置 | 行为 | 后果 |
|-----------------|------|------|
| `everysec` | AOF 每秒落盘一次 | 有可能丢失 1 秒的数据 |
| `always` | 每次操作请求的记录都落盘后再返回成功信息给客户端 | 系统性能很慢 |

埋点记录的请求要求响应快，两种配置都有缺陷，因此不选择 Redis。

### Kafka 的 acks 配置问题

Kafka 的冗余设计：每个分区有多个副本，其中一个副本是 Leader，其他副本都是 Follower。Leader 负责处理所有读写请求，并同步数据给其他 Follower。

数据从 Leader 同步到 Follower 的时机由 producer configs 中的 `acks` 配置控制，共有三种方式：

| acks 配置 | 行为 | 后果 |
|----------|------|------|
| `acks=0` | 不等 Leader 将数据落到日志，Kafka 直接返回完成信号给客户端 | 响应快，但数据持久化没有保障——数据未落到本地日志时系统宕机就会丢数据 |
| `acks=1` | 等 Leader 将数据落到本地日志，但不等 Follower 同步数据，即返回完成信号 | 折中，但 Follower 未同步时 Leader 宕机仍有丢数据风险 |
| `acks=all` | 等 Leader 落盘且 `min.insync.replicas` 个 Follower 都同步数据后再返回完成信号 | 数据有保证，但响应慢 |

Redis 与 Kafka 的结论一致：**想保证数据可靠性，必然牺牲系统性能**。而本地日志方案可以性能与可靠性兼得——最终决定把埋点数据保存到本地日志中。

## 关键决策二：使用什么技术把缓冲数据搬到持久化层

最简单的方式是用 Logstash 直接把日志文件中的数据搬运到 ES，但业务侧要求存入 ES 的记录包含城市、性别、年龄等原始数据，而这些字段需要调用业务系统数据抽取、日志文件中并不存在，Logstash 直接搬运无法完成字段补齐。

如果坚持用 Logstash，有 3 种实现方式，均被否决：

| 方式 | 做法 | 否决原因 |
|------|------|---------|
| **自定义 filter** | 在 Logstash 自定义 filter 里封装业务数据后再保存到 ES | Logstash 自定义 filter 使用 Ruby 编写，业务逻辑需用另一种语言实现 |
| **修改客户端埋点逻辑** | 客户端在发送埋点数据前先提取业务字段再上传 | 业务侧否决：后台每更新一次查询条件，客户端就需要重新发一次版 |
| **修改埋点服务端逻辑** | 服务端写日志文件前先从数据库获取业务字段组合埋点记录 | 会直接影响每个请求的效率，间接影响用户体验 |

不选择 Logstash 还有 2 点原因：

- 日志文件中的数据需要同时输出到 ES 和 HBase 两个输出源，而 Logstash 的多输出源基于同一个 pipeline——1 个输出源出错，另 1 个输出源也会出错，两者互相影响。
- MySQL 中的费用结算数据需要通过分析埋点数据动态计算，Logstash 的 filter 只能改变每条数据某些字段的值，不适合这种计算场景。

最终方案：**引入 Logstash 作为日志搬运 + 实时计算框架做数据加工**。即先通过 Logstash 把日志文件搬运到 MQ，再由实时计算框架处理 MQ 中的数据——在原始埋点数据中填充业务数据、统计埋点数据生成费用结算数据——最后把处理转换出来的数据分别保存到持久层。

### Logstash 与 Filebeat 的取舍

Logstash 由 Ruby 语言编写，资源消耗大，官方为此推出了轻量的 Filebeat。可选组合：

- **Filebeat 收集 + Logstash 过滤**：兼顾轻量收集与强大过滤。
- **仅 Filebeat 收集后直接发送给 Kafka**：不需要 Logstash 的过滤功能时使用。

但 Filebeat 以轮询方式采集文件变动，存在一定（有时很大）延时；Logstash 可直接监听文件变动。权衡资源消耗与延时后，最终继续选择 Logstash。

## 关键决策三：为什么使用 Kafka

Kafka 是 LinkedIn 推出的开源消息中间件，为收集日志而设计，具备超高的吞吐量和数据量扩展性，号称无限堆积。按 LinkedIn 官方说法，使用 3 台便宜的机器部署 Kafka 就能每秒写入 200 万条记录（见 [Kafka 官方文档](http://kafka.apache.org/documentation/#log)）。

Kafka 吞吐量高的原因在其存储结构：每个 Topic 分区相当于 1 个巨型文件，每个巨型文件由多个 segment 小文件组成。Producer 对该巨型文件进行"顺序写"，Consumer 对该文件进行"顺序读"。写数据通过追加数据到文件尾实现，读取数据时直接从文件中读，**读操作不会阻塞写操作**——这就是吞吐量大的来源。

另外，理论上只要磁盘空间足够，Kafka 就能实现消息无限堆积，因此特别适合日志收集场景。

## 关键决策四：使用什么技术把 Kafka 的数据搬运到持久化层

需要一个**分布式实时计算框架**，原因有 2 点：

- 数据量特别大：每天上亿条埋点数据需要快速分析和处理，且必须多节点并发处理才来得及，再写入 ES、HBase 和 MySQL——属于大数据计算，有分布式计算诉求。
- 业务要求实时查询统计报表数据：需要一个实时计算框架处理埋点数据。

市面流行的分布式实时计算框架有 3 种：Storm、Spark Streaming、Apache Flink。选型结论：三者都可以，取决于公司具体情况——公司已使用某框架就不必再选型；尚未使用则可按团队偏好决定。

Apache Flink 的优势：性能强（阿里双 11 使用它后，1 秒内处理了 17 亿条数据）；容错机制能保证每条数据仅处理 1 次；有时间窗口处理功能。

### 流处理的容错机制

流处理过程中，一条消息处理时系统出现故障该怎么办？重试会不会重复处理？不重试会不会丢失？不同流处理框架采取不同容错机制，保证不一样的一致性：

| 容错机制 | 语义 | 风险 |
|---------|------|------|
| **At-Most-Once** | 至多一次：一条消息不管后续处理成功与否，只会被消费处理至多一次 | 存在数据丢失可能 |
| **Exactly-Once** | 精确一次：一条消息从消费到后续处理成功，只会发生一次 | 无（实现成本最高） |
| **At-Least-Once** | 至少一次：一条消息从消费到后续处理成功，可能会发生多次 | 存在重复消费可能 |

Exactly-Once 是业务场景中的最优选择，因为正常业务一般只要求消息处理一次。Apache Flink 的容错机制可以保证所有消息只处理 1 次（Exactly-Once）的一致性，同时保证系统安全性能。

### 时间窗口与事件时间

以下是 Apache Flink 的一个代码示例，它把每个小时里发生事件的用户聚合在一个列表中：

```
final StreamExecutionEnvironment env = StreamExecutionEnvironment.getExecutionEnvironment();
env.setStreamTimeCharacteristic(TimeCharacteristic.ProcessingTime);
// alternatively:
// env.setStreamTimeCharacteristic(TimeCharacteristic.IngestionTime);
// env.setStreamTimeCharacteristic(TimeCharacteristic.EventTime);
DataStream<MyEvent> stream = env.addSource(new FlinkKafkaConsumer09<MyEvent>(topic, schema, props));
stream
    .keyBy( (event) -> event.getUser() )
    .timeWindow(Time.hours(1))
    .reduce( (a, b) -> a.add(b) )
    .addSink(...);

```

> 注：以上为 Flink 1.x 早期 API 的示例。Flink 1.12 起默认即按事件时间处理，`setStreamTimeCharacteristic` 已废弃；时间窗口建议使用 `window(TumblingEventTimeWindows.of(Time.hours(1)))`，Kafka 接入建议使用新的 `KafkaSource` 连接器。

日志中事件发生的时间与计算框架处理消息的时间可能不一致。假定计算框架收到消息的时间延后 2 秒：某事件发生在 6:30，处理时间已是 6:32，那么计算 6:01-6:30 区间的数据和时，这条消息不会被计入——不符合实际业务需求。

**实际业务中按时间窗口统计数据时，应根据消息的事件时间计算。Apache Flink 恰恰基于消息的事件时间而非计算框架的处理时间，这是它的另一个杀手锏。**

## 实践要点

- 高频写场景下，Redis AOF 的 `everysec`（可能丢 1 秒数据）与 `always`（性能差）都难以两全；Kafka 的 `acks` 配置同样在可靠性与性能之间取舍；**写本地日志是性能与可靠性兼得的方案**。
- Logstash 适合日志搬运与过滤，但不适合需要调用业务系统补齐字段、多输出源隔离、动态计算结算数据的场景；其 Ruby 实现带来的资源消耗需要与 Filebeat 的轮询延时权衡。
- Kafka 高吞吐的理论依据是分区巨型文件 + segment 小文件的顺序写/顺序读，读不阻塞写。
- 分布式实时计算框架选型：优先沿用公司已有框架；新选型时 Flink 的 Exactly-Once 容错与基于事件时间的时间窗口是决定性优势。
- 统计需求应按**事件时间**而非处理时间计算，否则迟到消息会被错误归入相邻窗口。

## 小结

本文以日活 500 万的用户行为埋点收集为案例，围绕"高频数据收集请求如何不影响主业务"完成了完整方案设计：埋点服务先写本地日志保证快响应与高可靠，Logstash 搬运日志进 Kafka，实时计算框架（推荐 Apache Flink）填充业务字段、按事件时间做时间窗口统计并保证 Exactly-Once，最终数据落入 ES（查询）、HBase（海量原始数据）、MySQL（费用结算）。方案的核心价值不在具体组件，而在每个技术选型背后"需求 → 机制 → 权衡"的思考过程。

**延伸思考**：本方案仍有未覆盖的场景，例如埋点日志文件损坏、Kafka 积压超过消费能力时的降级策略，可结合具体业务形态补全。

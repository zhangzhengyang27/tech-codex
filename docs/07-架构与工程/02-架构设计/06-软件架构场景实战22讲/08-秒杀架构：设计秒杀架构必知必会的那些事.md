# 秒杀架构：设计秒杀架构必知必会的那些事

## 概念说明

秒杀架构是综合性非常强的一个架构场景,也是技术面试中高频出现的提问场景。秒杀场景的特点是:流量在极短时间内形成瞬间峰值,系统需要在流量洪流下保证核心交易链路稳定。

秒杀架构的设计方案建立在几个基础架构手段之上:

- **读缓存**:先把数据存放在缓存中,每次请求通过缓存读取数据,大幅减少数据库读请求压力(详见《读缓存:如何减少数据库读操作压力?》);
- **写缓存**:流量洪峰时,先将数据写入缓存中,再逐步搬运数据到数据库,大幅减少数据库写请求压力(详见《写缓存:如何节省数据库写操作资源?》);
- **数据收集**:利用消息队列把缓存中的数据搬运到数据库中(详见《数据收集:高频数据收集请求如何不影响主业务?》)。

这三类架构设计思路在秒杀架构中均会使用到。

## 业务场景

一个典型的秒杀活动案例:

- 活动提供 100 件特价商品(商品价格非常低),于 10 月 10 日 22 点 10 分 0 秒正式开启秒杀;
- 平台已积累几千万用户量,预计数十万用户对特价商品感兴趣;
- 按照秒杀活动的调性,特价商品一般会在 1-2 秒内被一抢而光,剩余时间涌入的流量只能看到秒杀结束界面,因此秒杀开启瞬间会出现一个瞬间流量峰值;
- 活动为短期性质,且约束条件明确:不增加太多服务器、不花太多时间重构架构,即以最小的技术代价完成本次秒杀活动。

由此得出本次秒杀架构的设计目标:**以较小的改动保证秒杀时间的流量洪流不会冲垮服务器。**

## 设计原则

秒杀架构设计的难点在于"僧多粥少"。设计秒杀架构时,一般需要遵循以下 4 个原则:

1. 东西不能超卖;
2. 下单成功的订单数据不能丢失;
3. 服务器和数据库不能挂;
4. 尽量别让机器人抢走商品。

实现这 4 个原则的整体思路见下文。

## 整体思路:不断过滤请求

**秒杀架构的设计方案本质是一个不断过滤请求的过程。** 秒杀系统的分层设计目标是:尽量在上层把用户的请求处理掉,不让其往下层游动。

由于整个秒杀系统涉及多个用户操作步骤,解决"如何将请求拦截在系统上层"这个问题时,需要结合实际业务流程,将用户的每个操作步骤考虑在内。用户操作按页面分为三类:浏览页面、下单页面、付款页面,下文按此流程逐段说明如何在各环节将请求拦截在系统上游。

### (一)浏览页面:请求拦截在上游

#### 踩坑案例:出口带宽被打满

某次秒杀系统架构实施中,系统上线前已对各方面进行检查,性能指标均无问题;但活动一上线,系统立即显示异常。排查发现所有服务器的性能指标都正常,唯独出口带宽被占满,导致参与活动时页面严重卡顿、用户吐槽不断。

该案例的教训:**静态资源必须外移**。调整后的设计思路:静态资源能上 CDN 就上 CDN;若涉及 PC 网站,首先必须前后端分离,然后静态资源尽量全部上 CDN。

#### CDN 机制

以访问请求 `https://static.weimu.xx/1.jpg` 为例,该地址原本指向自己的服务器。改造后,将 `static.weimu.xx` 这个域名解析交给 CDN 服务商。CDN 服务商在全国各地都有服务器,服务器中存放着静态资源的缓存。CDN 收到域名请求后,会寻找一台响应最快的服务器,并指向该服务器的 IP。

使用 CDN 的好处:不浪费自己的服务器资源和带宽,且响应速度快。通过这种方式,静态资源的压力被拦截在系统分层之外。

#### 动态请求的处理方式

对评论、商品属性详情、购买数等原本通过 JS 后台动态调用的动态请求,有如下 3 种处理方式:

- **动态数据静态化**:把动态的数据与页面进行整合,例如把每个秒杀商品的详情页面变成静态页面,再放入 CDN。若嫌改造太大,也可以放在 Redis 缓存中,但更倾向于 CDN 方案。
- **服务器时间判断前置**:页面中通常有一个 JS,通过访问服务器获取服务器时间,然后根据时间开启秒杀下单按钮(秒杀开始时将下单按钮设置为可购买)。针对获取服务器时间的这个请求,把它放在静态资源或负载均衡层处理即可,这样用户请求就不会进入系统下游。
- **秒杀结束标识分层判断**:将秒杀结束的标识放在 cookie 中。请求到达后台服务器时,先判断本地内存中有没有结束标识;本地内存没有,再进入缓存中查找;若缓存中也没有结束标识,说明秒杀没结束。

小结:对于浏览页面的用户行为,应把用户请求尽量拦截在 CDN、静态资源或负载均衡侧,实在不行再拦截在缓存中。

### (二)下单页面:请求拦截在上游

用户进入下单页时,主要分为 2 个操作动作:进入下单页、订单提交。

#### (1)进入下单页

为防止爬虫抓取下单页页面信息、给服务器增加压力,需要在下单页中做以下 2 层防护,以防止(恶意)请求重复提交:

- **页面 URL 后台动态获取**:按照正常的活动设计流程,用户只有在秒杀活动开启后才可进入下单页,但难免有同行在活动开启前直接获取下单页的 URL 并不断刷新,使恶意请求跑到后台服务器中。虽然后台服务器也可以拦截恶意请求,但会徒增不少压力。处理方式是使用一个"诡异的 URL":不把它放在静态页面中,而是通过后台动态获取——前述用于判断秒杀开始时间的 JS 在秒杀时间一到,便可通过另一个请求获取这个 URL。
- **购买按钮防重复点击**:用户点击下单页的购买按钮后直接 disable,防止用户不断点击购买按钮。

#### (2)订单提交

秒杀系统架构方案的重心是订单提交,因为订单提交这个步骤的逻辑最复杂;其他步骤仅是页面展示逻辑,针对高并发问题使用缓存或 CDN 处理难度不大。因此在订单提交环节,要在系统各个分层中把不必要的请求过滤掉。

**网关层面过滤请求**

对系统而言,在网关层面拦截用户请求性价比很高。若能在这层过滤 95% 以上的请求,整个系统就很稳定。网关层面的请求过滤有三种方式:

- 限定每个用户访问频率,比如每 5 秒下单 1 次;
- 限定每个 IP 访问频率。这种方式需注意:存在通过机器人自动下单绕过限制的可能,也存在错杀真实用户的风险;
- 把一个时间段内的请求拦截掉一个百分比,或者只允许特定数量的请求进入后台服务器(可使用限流的漏桶或令牌桶算法,详见《限流:如何保障服务器承受亿级流量?》)。

**后台服务器过滤请求**

请求进入后台服务器后,目标已从"过滤请求"转为:保证特价商品不超卖,以及保证特价商品订单数据的准确性。具体通过以下三种方式实现:

- **商品库存放入缓存 Redis 中**:如果每个请求都前往数据库查询商品库存,数据库肯定扛不住,因此需要把库存存放在缓存中。每次用户下单前,先使用 `decr` 扣减库存并判断返回值:若 Redis 的库存扣减后 <0,说明秒杀失败,库存 `incr` 回去;若 Redis 的库存扣减后 >=0,说明秒杀成功,开始创建订单。
- **订单写入缓存中**:订单数据先不放入数据库,而是先放到缓存中,然后每隔一段时间(比如 100ms)批量插入订单。用户下单后首先进入一个等待页面,该页面向后台定时轮询订单数据。轮询过程中,后台先在 Redis 中查询订单数据,查不到说明已落库,再去数据库查询订单数据;查到后直接返回给用户,用户收到消息通知后可直接进入付款页面支付。在数据库查询订单数据时查不到,说明秒杀失败(理论上不会查不到,若一直查不到应抛出异常并做后续跟踪处理)。
- **订单批量落库**:定期将订单批量落库,且在订单落库的同时扣减数据库中的库存。

订单提交操作的架构设计主要集中在网关层和后台服务器两层。

### (三)付款页:一致性与库存返还

在付款页面,基本不需要再过滤用户请求。这个环节需要保障数据的一致性,并注意一个要点:如果业务逻辑上出现一个订单未及时付款而被取消,要把数据库及 Redis 的库存加回去。

## 整体服务器架构

秒杀系统的整体服务器架构即前述分层设计思路。为保障秒杀系统的高可用性,所有层级都需要高可用:

- 静态资源服务器、网关、后台服务器均需要配置负载均衡;
- 缓存 Redis 和数据库均需要配置集群模式。

整体服务器架构中还有一个重要组成部分——MQ。本次秒杀架构方案的主体流程不涉及它的设计逻辑,但服务间触发通知时需要使用它,因此同样需要保证其高可用(主从、分片、failover 机制都需考虑进去)。

## 小结

秒杀架构的核心思路是"不断过滤请求":浏览页面的请求尽量拦截在 CDN、静态资源或负载均衡侧;下单页面的请求通过 URL 动态获取、按钮 disable、网关限流逐层过滤;到达后台服务器的请求通过 Redis 库存扣减(`decr`/`incr` 判断)、订单写缓存、订单批量落库保证不超卖且订单数据不丢失;付款环节重点保障数据一致性并在订单取消时返还库存。配合全链路的高可用部署(负载均衡 + 集群),即可在最小技术代价下支撑秒杀流量洪峰。

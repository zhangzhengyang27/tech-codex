# 注册发现：如何对后台服务进行高效管理？

本文从一个多语言微服务的实际场景入手，还原服务注册发现的旧架构、它的问题，以及基于分布式协调服务的解决思路与落地注意事项。

## 问题背景

某公司已拥有 50 多个服务，很多服务之间都有调用关系，且这些服务使用各种语言编写，比如 Java、Go、Node.js。

因为跨语言，而流行的 Spring Cloud、Dubbo 都是针对 Java 语言的，所以没有使用这些微服务框架。

那么，各服务之间的调用关系是如何配置的？当时的配置过程如下。

因为这 50 个服务都有负载均衡，所以首先需要把服务的地址和负载均衡全部配置在 Nginx 上，类似这样：

```
upstream user-servers {
  server 192.168.5.150:80;
  server 192.168.5.151:80;
}
upstream order-servers {
  server 192.168.5.153:80;
  server 192.168.5.152:80;
}
…
server{
  listen 80;
  server_name user-servers;
  location / {
    proxy_pass http://user-servers;
    proxy_set_header Host $host;
    proxy_set_header X-Real-IP $remote_addr;
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
  }
}
server{
  listen 80;
  server_name order-servers;
  location / {
    proxy_pass http://order-servers;
    proxy_set_header Host $host;
    proxy_set_header X-Real-IP $remote_addr;
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
  }
}

```

服务之间的调用关系则主要通过本地配置文件配置，如下所示：

```
user.api.host=https://user-servers/
order.api.host=https://order-servers/

```

配置过程说明：先通过本地配置文件获取需要调用的服务的主机地址，再在代码中加上 URI 组装成 URL，然后所有服务之间的调用都通过 Nginx 代理。

## 旧架构会出现的问题

在后续实战经历中，通过不断总结，可以理清以上架构经常出现的一些问题。

### 1. 配置烦琐，上线容易出错

上线部署时这个问题经常发生：每次增服务/加机器/减机器时，Nginx 都需要手工配置，而且每个环境都不一样，很容易出错。

因此，服务器迁移或网络变动时，需要把这些配置重新捋一遍，并进行多轮测试才能确保没问题；如果没有进行详细检查，某些节点负载均衡出错了可能还不知道。

### 2. 加机器要重启

公司流量起来后，通过监控发现有些服务需要增加机器，这个时候最考验系统的抗压性。因为这个过程需要手工配置，稍不留神系统就会出错，比如多输了一个字符或没输对 IP。

而系统一旦出错，就需要重启 Nginx。重启一旦失败，所有服务都会受影响。加机器是一件很急的事情，不会留出太多时间进行检查，因此必须在短时间内确保配置准确无误。

### 3. Nginx 单点

因为所有的服务都需要经过 Nginx 代理，所以 Nginx 很容易成为瓶颈；如果 Nginx 配置出了问题，所有的服务就都不能用了，风险很大。

一种应对方法是让每个服务拥有自己的 Nginx，而不是所有后台服务共用 1 个 Nginx。这种方法可行，但配置多了以后，运维出错概率也随之变大。

### 4. 管理困难

在实际工作中，因为合规的要求，经常需要对全系统调用库进行升级；为了保证所有服务不遗漏，必须有一个后台服务清单。

后台服务清单通常通过手工维护，需要定期整理，负担很重。为了解决这个问题，有 3 种有效的解决思路。

**思路 1**：将所有后台服务的服务清单及每种服务的服务器节点列表推送到所有的后台服务，后台服务自己控制调用哪个服务的哪个节点。这就是 Spring Cloud 和 Dubbo 的做法。

**思路 2**：将所有的服务部署到容器上，利用 Kubernetes 的 Service 与 Pod 的特性进行服务注册发现。

具体操作：在部署 User 服务的 Pod 上打上“User-App”标签，K8s 上可以启动多个 User 的 Pod；其中 1 个 Service 叫 User Service，专门处理标签为“User-App”的 Pod。从 Client 过来的请求首先会到 User Service，再自动负载均衡到某个 User 服务的 Pod。

**思路 3**：每个服务自动将服务和 IP 注册到协调服务（比如 ZooKeeper），然后设计一个工具自动获取 ZooKeeper 中后台服务的机器列表，最终根据列表自动更新 Nginx 的配置，更新完后再重启。

最终方案采用的是第一种解决思路。不用第二种思路的原因是当时团队对容器不熟悉，且几年前容器的生产环境还没有那么成熟，把所有服务迁移到容器的代价与风险都太大；不使用第三种思路的原因是它并没有解决 Nginx 单点瓶颈、加机器后需要重启的问题。

最终解决思路分为以下几个步骤：

- 每个后台服务自动把服务类型和 IP 注册到中心存储；
- 中心存储将服务列表推送到每个后台服务；
- 后台服务在本地做负载均衡，轮流访问同服务的不同节点。

## 落地注意事项

解决思路明确后，共有四点注意事项。

### 1. 中心存储服务使用什么技术？

就基础的服务清单存储而言，使用一个 Redis 就可以解决，但还需要考虑以下 2 个需求：

- **服务变更的需求，实时推送给所有后台服务。**比如新增了一个服务器节点，服务器节点启动时会自动连接中央存储；当后台服务列表更新时，其他后台服务如何实时收到更新请求？
- **随时监听所有后台服务的状态，如果某个服务宕机了，及时通知其他服务。**

分布式协调服务这个中间件技术刚好能全部满足以上 2 点需求，所以最终使用分布式协调服务来存储服务器列表。

### 2. 到底使用哪个分布式协调服务？

关于到底使用哪个分布式协调服务技术，网络上存在内容比较详细的技术对比表格，可参考了解。

实际技术选型过程中，不光需要考虑技术本身，还需要考虑组织的背景。比如该公司当时已经在使用 ZooKeeper，而运维团队一般不会同时维护 2 种协调服务中间件，所以最终没有选择 ZooKeeper 以外的协调服务。

### 3. 基于 ZooKeeper 需要实现哪些功能？

需要实现的几个要点是：

- 服务启动的时候，将信息注册到 ZooKeeper；
- 将所有的后台服务信息从 ZooKeeper 拉取下来；
- 监听 ZooKeeper 事件，如果后台服务信息出现变更，就更新本地列表；
- 调用其他服务时，如果需要实现负载均衡策略，一般用轮询（Ribbon）就可以了。

以上几个要点整体实现起来并不复杂。

### 4. ZooKeeper 宕机了怎么办？

后台服务都是多台部署，某个节点宕机时，需要保证同服务的其他节点还可以正常工作，因此重点是保证 ZooKeeper 集群的高可用（ZooKeeper 本身就具备集群能力）。

ZooKeeper 设计本身为了一致性牺牲了高可用性，它同时兼有 Leader、Follower 和 Observer 三种角色，如果 Leader 或半数的 Follower 宕机了，ZooKeeper 就会进入漫长的恢复模式。在这段时间里，ZooKeeper 不接受客户端的任何请求，容易出现以下三种问题：

- 假设后台服务之前在本地已经有所有后台服务的清单，这种情况算运气好，只需保证这段时间新的后台服务器没有变更即可。
- 假设这段时间服务器刚好变更了，那就可能出现调用失败的情况。
- 假设后台服务在 ZooKeeper 恢复期间启动了，它便连不上 ZooKeeper，也获取不到后台服务清单，这种情况影响最大。

针对以上问题的应对做法：每次通过某个特定服务把所有服务清单同步一份到配置中心，新的后台服务获取不到服务清单时，再从配置中心获取。这个做法虽然没法解决 100% 的问题，但已经是一个性价比不错的方案，且该方案至今未发生过上述问题。

## 总结

这次架构经历类似于自己造轮子，因为注册发现本来就是 Spring Cloud 或 Dubbo 已经实现的功能。它的价值在于从另外一个角度帮助理解微服务中服务注册发现的实现原理。方案仍有未覆盖的场景，可结合自己的服务规模补全。

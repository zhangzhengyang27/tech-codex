# 全链路日志：这个请求到底经历了什么？

全链路日志是所有微服务都会遇到的问题。本文从一个真实的业务场景出发，梳理日志规范化需求、技术选型标准与落地注意事项。

## 问题背景

某公司的微服务刚迁移到 Spring Cloud，服务的注册发现基于 Spring Cloud ZooKeeper 实现，组件方面只使用了 Spring Cloud 的服务间调用（Feign）。

迁移到微服务后，日志跟踪成为必须考虑的问题。此前的做法只是简单地把日志打印到本地文件上，再使用 ELK 进行日志收集、分析，日志记录比较随意且没有形成统一规范。

经过讨论，团队提出了日志规范化的如下 3 点需求：

- 记录什么时候调用了缓存/MQ/ES 等中间件，在哪个类的哪个方法中耗时多久？
- 记录什么时候调用了数据库，执行了什么 SQL，耗时多久？
- 记录什么时候调用了另一个服务，服务名是什么？方法名是什么？耗时多久？

一般来说，一个请求会跨多个服务节点。针对这种情况，又梳理了 2 条重要需求：

- 把同一个请求在全部服务的以上所有记录进行串联，最终实现一个树状的记录。
- 设计一个基于这些基础数据的查询统计功能。

需求梳理并将日志规范化后，即可在一个页面上看到每个请求的树状结构日志。这样，后期线上环境出现问题需要进一步调查时，就有了更多的依据。

需求明确后，需要选择一款真正适合的开源技术进行方案实现，这就涉及技术选型过程。

## 技术选型

技术选型时可参考下方知名框架的对比表。

技术选型对比表

可供选择的系统很多，如何选择？经过讨论，最终确定了如下选型标准。

### 1. 日志数据结构支持 OpenTracing

平时日志行都是独立记录的，只能通过线程 id 把它们关联起来。因此需要一个数据结构把每个请求在全部服务的相关日志关联起来。

当时市面上已经有一个比较通用的全链路数据格式——OpenTracing，它的标准和 API 由一个开源组织（Cloud Native Computing Foundation 云原生计算基金会孵化）维护，这个开源组织也包含了一些全链路日志系统的维护者。（2026 年注：OpenTracing 项目已于 2022 年初归档，与 OpenCensus 合并为 OpenTelemetry 并成为现行行业标准；如今新建链路追踪体系应基于 OpenTelemetry 而非 OpenTracing。）

OpenTracing 通过提供一个与平台/厂商无关的 API，使开发人员能够更方便地添加（或更换）追踪系统。这样即使之前引入的全链路日志不好用，以后想再换掉也非常方便。

OpenTracing 标准主要包含两个概念：一个是 Trace，一个是 Span。

以一个典型调用为例：客户端调用 Order API 的请求所经历的整个流程（1 到 10）即 1 个 Trace；之后它调用 Product Service 的整个过程（2 到 5）就是 1 个 Span。每个 Span 代表 Trace 中被命名且被计时的连续性执行片段。

Span 中又可以包含子 Span：调用 Product Service 的过程中，Product Service 会访问一次数据库（3 到 4），这也是一个 Span。因此，一个 Span 可以包含多个子 Span，而 Span 与 Span 之间的关系就叫 Reference。

**在技术选型时，必须保证系统的可替代性，尽量别在一项开源技术上绑死。**强依赖一个框架而该框架停止维护时，后续维护相关代码会非常痛苦；全部迁移则代价太大且工作量也大，付出与回报产出比不足以支撑决策；不迁移，就只能一直使用上个年代的技术。**因此本次选型坚决使用基于 OpenTracing 的日志系统。**

### 2. 支持 Elasticsearch 作为存储系统

流量大的情况下记录的日志数据量也很大，这要求存储日志的系统必须支持海量数据且保证查询高效。

最终，因为公司运维同事对 Elasticsearch 比较熟悉，所以提出可以使用 Elasticsearch 对日志进行存储。

### 3. 保证日志的收集对性能无影响

服务记录日志时，需要确保日志的记录与收集对服务器性能不产生影响。

一个反例是 Pinpoint：调研发现当服务正在记录日志时，Pinpoint 的并发数达到一定数量且整体吞吐量少了一半，对服务器性能影响很大，无法接受。

### 4. 查询统计功能的丰富程度

查询统计的功能越丰富越好，但必须首先满足一个基础功能：支持每个请求树状结构的全链路日志，比如 SkyWalking 的功能就非常适用。

查询系统除了满足基本功能以外，如果能实现监控报警、指标统计等功能，还可以减轻大量二次开发的工作量。

### 5. 如何以最小的业务代码侵入性引入系统

理想的方案是让日志数据的收集过程对写业务代码的人保持透明，例如使用 Java 的探针、通过字节码加强的方式进行埋点。不过，这种方式对系统性能也会产生一定影响。

而且在实际业务中，公司都会把对数据库、Redis、MQ 访问的代码进行封装，无法通过字节码加强的方式实现埋点，只能尝试在封装的代码中实现埋点，这样对开发业务代码的人来说同样透明。

### 6. 客户案例

技术选型时，还需要了解哪些知名公司使用了这个技术。大公司的业务场景相对复杂，提前踩的坑较多；一个技术如果被很多公司使用过，使用起来就会平稳很多。

### 7. 最终选择

根据以上问题的剖析及性能测试结果的分析，**SkyWalking 比较符合需求。**

做性能测试时发现：500 线程压力以下的服务是否使用 SkyWalking，对服务的吞吐量影响不大，差别一般不超过 10%。

SkyWalking 官方测试报告中也提到：假如有 500 个并发用户，每个用户的每次请求间隔是 10ms，TPS 基本没什么变化。

技术选型时，不仅仅需要关注需求本身，还需要考虑组织或个人主观上的因素。从主观层面看：随着中国互联网的崛起，如今国产开源框架的质量不比国外差，反而更贴近本土需求，比如 Vue、Dubbo，这也是选择 SkyWalking 的原因之一。

## 注意事项

在正式使用 SkyWalking 之前，还需要注意如下 5 大注意事项。

### 1. SkyWalking 的数据收集机制

SkyWalking 的数据收集机制：服务中有一个本地缓存，收集的所有日志数据先存放在这个缓存中，然后后台线程通过异步的方式将缓存中的日志发送给 SkyWalking 服务端。通过这种机制，在日志埋点的地方无须等待服务端接收数据，也就不影响系统性能。

### 2. 如果 SkyWalking 服务端宕机了，会出现什么情况？

如果服务端宕机了，理论上日志缓存中的数据会出现没人消费的情况，可能导致数据越积越多，最终撑爆内存。

**SkyWalking 中可以设置缓存的 size，如果这部分数据超出了缓存 size，Trace 不会保存，内存也就不会被撑爆。**

### 3. 流量较大时，如何控制日志的数据量？

流量大时不可能收集每个请求的日志，否则数据量太大。SkyWalking 通过采样比例控制数据量：在每个服务器上配置采样比例，比如设置为 100，代表 1% 的请求数据会被收集，配置如下所示。

```
agent-analyzer:
  default:
    ...
    sampleRate: ${SW_TRACE_SAMPLE_RATE:1000} # The sample rate precision is 1/10000. 10000 means 100% sample in default.
    forceSampleErrorSegment: ${SW_FORCE_SAMPLE_ERROR_SEGMENT:true} # When sampling mechanism activated, this config would make the error status segment sampled, ignoring the sampling rate.

```

这样就可以通过 sampleRate 控制采样比率了。一般而言，流量越大，采样比例越小。

不过，这里有 2 点需要特别注意：

- 一旦启用 forceSampleErrorSegment，出现错误时所有的数据全部会收集，此时 sampleRate 对出错的请求不再适用。
- 所有相关联服务的 sampleRate 最好保持一致。如果 A 调用 B，而 A、B 的采样率不一样，就会出现一个 Trace 串不起来的情况。

### 4. 日志的保存时间

一般来说，日志不需要永久保存，通常保存 3 个月的数据，具体结合公司的实际情况进行配置即可。

按照传统的设计方案，需要自己设计一个工具将数据进行定时清理；而使用 SkyWalking 可以直接进行配置，如下所示：

```
    # Set a timeout on metrics data. After the timeout has expired, the metrics data will automatically be deleted.
    recordDataTTL: ${SW_CORE_RECORD_DATA_TTL:3} # Unit is day
    metricsDataTTL: ${SW_CORE_METRICS_DATA_TTL:7} # Unit is day

```

## 总结

在方案中使用 SkyWalking 后，对问题排查的帮助非常大。但 SkyWalking 也存在不足，比如之前的版本存在很多兼容性问题，不过现在好多了。

本文的架构经历不涉及太多架构设计，主要是技术选型和注意事项的内容，可帮助快速理解全链路日志并针对技术选型问题做出决策。方案仍有未覆盖的场景，可结合自己的技术栈补全。

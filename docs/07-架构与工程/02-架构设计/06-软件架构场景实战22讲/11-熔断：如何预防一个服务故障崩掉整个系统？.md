# 熔断：如何预防一个服务故障崩掉整个系统？

## 概念说明

熔断（Circuit Breaker）是微服务体系中继全链路日志之后的第二个普适性问题：**防止一个服务故障沿调用链向上传播，最终崩掉整个系统**。

::: warning 常见误区
一种常见观点认为"熔断是流量大时才会出现的技术，公司流量不大就不用考虑"。这是一个误区——熔断解决的是**故障隔离**问题，与流量大小无关：哪怕流量不大，只要存在慢依赖或依赖服务崩溃，故障就会沿同步调用链逐级放大。流量不大同样需要熔断。
:::

## 核心要点

- 熔断的两大技术手段是**线程隔离**与**熔断降级**：前者限制对慢依赖的并发调用数，后者在依赖持续失败时暂时停止访问并转入备用逻辑。
- 慢接口的危害在于线程占用：一个接口响应慢，会把当前服务的所有连接线程逐步卷入等待，导致其他正常页面也无法受理请求。
- 缓存超时 + 高并发会造成**缓存击穿式雪崩**：缓存失效瞬间所有请求打到数据库，DB CPU 飙满，故障沿"DB → 基础数据服务 → 上层 API → App"逐级传导。
- Hystrix 的设计思想是**事前配置熔断机制**：事先预见流量与系统负载能力，预先配置熔断规则；缺点是实际流量与预测不符时，预配机制达不到预期效果。
- Netflix 官方在 2018 年后已不再为 Hystrix 开发新功能、仅做简单维护，社区转而使用更轻量的替代方案（如 Resilience4j、Sentinel 等）。
- 熔断触发条件基于**滚动时间窗口**内的失败数/失败率统计；熔断后进入休眠窗口直接调用本地降级方法；休眠结束后以半开状态放行单个请求试探恢复。
- 使用熔断框架前必须考虑四件事：**数据一致性、超时降级、用户体验、熔断监控**。
- ⚠️ 熔断上线只是设计的第一步：配置是否合理只有实际运行后才知道，必须持续盯监控面板并调整。

## 典型故障场景

以下案例来自某新零售架构系统。系统中有一个通用用户服务（很多页面都会使用），包含两个接口，两个接口分别遇到了典型问题。

### 场景一：慢依赖拖垮整个服务（请求慢）

**接口说明**：用户状态接口，包含用户车辆所在位置，在用户信息展示页面都会使用到（比如客服系统中的用户信息页面）。

**调用关系**：User API 调用 Basic Data Service，Basic Data Service 中的接口 `/currentCarLocation` 需要调用第三方系统的数据；第三方响应速度很慢且时常不稳定，导致响应时间更长，接口经常超时报错。

**故障过程**：

- 一次用户反馈 App 整体运行速度慢到无法接受。通过后台监控查看几个 Thread Dump，发现 User API 与 Basic Data Service 的线程请求数爆满，且所有线程都在访问第三方接口。
- 因为连接数满了，其他页面便不再受理 User API 的请求，最终导致 App 整体出现卡顿。

**当时的临时处理**：把超时时间设置得很长。超时报错概率变小了，其他页面也保持正常，但代价是客服后台查看用户信息的页面响应时间变长——治标不治本。

### 场景二：流量洪峰缓存超时引发雪崩

**接口说明**：用户权限接口，返回用户可操作的权限列表，包含通用权限与用户定制权限，每次用户打开 App 时都会调用。

**服务间调用流程**：

- App 访问 User API；
- User API 访问基础数据服务的接口 `/commonAccesses`；
- 基础数据服务提供通用权限列表。因为权限列表对所有用户都一样，所以把它放在了 Redis 中；如果通用权限在 Redis 中找不到，再去数据库中查找。

**故障过程**：

1. 因历史代码原因，流量高峰时 Redis 中的通用权限列表超时失效，一瞬间所有线程都去数据库读取数据，DB 的 CPU 立马飙到 100%。
2. DB 挂后，Basic Data Service 也随之挂掉——所有线程阻塞，获取不到数据库连接，无法接受新请求。
3. User API 因调用 Basic Data Service 的线程出现堵塞，所有线程也出现堵塞，User API 也挂了。
4. 最终 App 上的所有操作都不能使用。

## 设计需求：熔断技术要满足的条件

为了解决以上两个问题，需要引入一项技术，且它必须满足两个条件。

### （1）线程隔离

针对场景一（慢依赖）。假设 User API 中每个服务配置的最大连接数是 1000，每次 API 调用 Basic Data Service 的 `/currentCarLocation` 速度都很慢。

期望的处理方式：控制 `/currentCarLocation` 的调用请求数不超过 50 条，以此保证至少还有 950 条连接可用来处理常规请求；如果 `/currentCarLocation` 的调用请求数超过 50 条，则走备用逻辑处理，比如在界面上给用户进行提示。

### （2）熔断

针对场景二（流量洪峰缓存超时）。当时 DB 没有死锁，故障单纯因压力太大而起——此时只需让 Basic Data Service 暂缓一段时间，不接受新请求，Redis 的数据会被补上，数据库的连接也会降下来，服务即可自行恢复。

因此，熔断技术需要实现两点需求：

- 发现近期某个接口的请求持续异常时，先停止访问该接口的服务；
- 发现某个接口的请求持续超时时，先判断该接口的服务是否不堪重负；如果不堪重负，先停止访问它。

## 原理与机制：Hystrix 的设计思路

本场景的技术选型采用 Spring Cloud 中的 Hystrix 组件。使用 Spring Cloud 的原因之一即是需要使用其生态组件。

::: warning Hystrix 的时代局限
Spring Cloud Hystrix 的设计思想是**事前配置熔断机制**：事先预见流量情况与系统负载能力，然后预先配置好熔断机制。这种操作的缺点是，一旦实际流量或系统状况与预测不一样，预先配置好的机制就达不到预期效果。Netflix 官方在 2018 年后已不再为 Hystrix 开发新功能、仅做简单维护，社区转而使用更轻量的替代方案（如 Resilience4j、Sentinel 等）。
:::

### （1）线程隔离机制

在 Hystrix 机制中，当前服务与其他接口存在强依赖关系，且每个依赖都有一个隔离的线程池。例如：当前服务调用接口 A 时，并发线程的最大个数是 10；调用接口 M 时，并发线程的最大个数是 5。

一般来说，当前服务依赖的一个接口响应慢时，当前运行的线程会一直处于未释放状态，最终把所有连接线程卷入慢接口。为此，Hystrix 在隔离线程时的做法是：为每个依赖接口（也可以配置成几个接口共用）维护一个线程池，通过线程池大小、排队数等隔离每个服务对依赖接口的调用，避免全部线程被慢接口卷走。

除线程池外，Hystrix 还支持使用**信号量（计数器）**隔离。以调用接口 A（并发线程最大个数 10）为例：信号量隔离不使用 1 个 size 为 10 的线程池，而是使用一个信号 `semaphoresA`——每当调用接口 A 时 `semaphoresA++`，A 调用完后 `semaphoresA--`；`semaphoresA` 一旦超过 10，不再发起调用。

::: tip 延伸思考
`semaphoresA` 超过 10 后，业务代码会如何？可结合 Hystrix 的拒绝与降级行为验证。
:::

**线程池隔离与信号量隔离的对比**：

- 线程池隔离：使用线程池时经常需要切换线程，资源损耗较大；但调用依赖的是另外的线程，当前请求的主线程可以根据超时时间把调用中断。
- 信号量隔离：切换快，资源损耗小；但接口一旦开始调用就无法中断——因为调用依赖的线程就是当前请求的主线程。

线程隔离机制解决了场景一的问题；场景二则需要熔断机制。

### （2）熔断机制

#### 1. 在哪种条件下会触发熔断？

熔断判断规则：**某段时间内调用失败数超过特定的数量或比率时，触发熔断**。统计数据来自滚动时间窗口（见下文）。

在 Hystrix 机制中，配置一个不断滚动的统计时间窗口 `metrics.rollingStats.timeInMilliseconds`，在每个统计时间窗口中，当调用接口的总数量达到 `circuitBreakerRequestVolumeThreshold`，且接口调用超时或异常的调用次数与总调用次数的占比超过 `circuitBreakerErrorThresholdPercentage`，此时就会触发熔断。

#### 2. 熔断了会怎么样？

熔断被触发后，在 `circuitBreakerSleepWindowInMilliseconds` 的时间内，不再对外调用接口，而是直接调用本地的一个降级方法，如下代码所示：

```
@HystrixCommand(fallbackMethod = "getCurrentCarLocationFallback")

```

#### 3. 熔断后怎么恢复？

`circuitBreakerSleepWindowInMilliseconds` 到时间后，Hystrix 首先放开对接口的限制（断路器状态 **HALF-OPEN**），然后尝试使用 1 个请求去调用接口：如果调用成功，则恢复正常（断路器状态 **CLOSED**）；如果调用失败或出现超时等待，则需要重新等待 `circuitBreakerSleepWindowInMilliseconds` 的时间后再重试。

### （3）滚动（滑动）时间窗口

滚动时间窗口的含义：把滑动统计的时间窗口设置为 10 秒，并不是只在 1 分 10 秒统计一次、1 分 20 秒再统计一次，而是**统计每一个 10 秒的时间窗口**。

因此还需要设置 `metrics.rollingStats.numBuckets`。假设设置为 10，表示时间窗口划分为 10 小份，每 1 份是 1 秒；然后每隔 1 秒都有 1 个时间窗口——1 分 0 秒 - 1 分 10 秒统计 1 次、1 分 1 秒 - 1 分 11 秒统计 1 次、1 分 2 秒 - 1 分 12 秒统计 1 次……

每个 10 秒时间窗口被分成 10 个桶。每个桶中 Hystrix 首先统计调用请求的成功数、失败数、超时数和拒绝数，再单独统计每 10 个桶的合计数据（到了第 11 个桶时，统计的就是第 2 个桶到第 11 个桶的合计数据）。

### （4）Hystrix 调用接口的请求处理流程

Hystrix 调用接口有两条完整路径：

- **调用成功的流程**：请求进入 → 检查断路器状态 → 线程池/信号量允许 → 执行依赖调用 → 返回结果；
- **调用失败的流程**：请求进入 → 检查断路器状态（OPEN 则直接降级）→ 线程池/信号量已满则拒绝 → 执行依赖调用超时或异常 → 计入统计 → 调用降级方法。

理解上述流程后即可直接启用 Hystrix。在 Spring Cloud 中启用 Hystrix 的操作比较简单（引入依赖并加开关注解即可），此处不再展开。

::: tip 相关功能
Hystrix 还包含 request caching（请求缓存）和 request collapsing（请求合并）两个功能，因为它们与熔断关系不大，本文不展开。
:::

## 实践要点：使用注意事项

把 Hystrix 的设计思路搞清楚后，使用之前还需要考虑以下注意事项。

### （1）数据一致性

通过两个例子理解。

**例子一**：服务 A 更新了数据库，在调用服务 B 时直接降级了——服务 A 的数据库更新是否需要回滚？

**例子二**（更复杂）：服务 A 调用服务 B，服务 B 调用服务 C。服务 A 成功更新了数据库并成功调用了服务 B，而服务 B 调用服务 C 时降级了、直接调用了 Fallback 方法。此时出现两个问题：服务 B 向服务 A 返回成功还是失败？服务 A 的数据库更新需不需要回滚？

以上两个例子体现的就是**数据一致性**问题。这个问题没有固定的设计标准，在不同需求下使用熔断时，需要结合具体情况设计。

### （2）超时降级

服务 A 调用服务 B 时，因为调用过程中 B 没有在设置的时间内返回结果，被判断超时，服务 A 转而调用降级方法。但服务 B 在接收到服务 A 的请求后，已经在执行工作并且没有中断；等服务 B 处理成功后，还是会把处理成功的结果返回给服务 A。可是服务 A 已经走了降级方法，而服务 B 又已经把工作做完了——此时就会导致**服务 B 中的数据出现异常**。

### （3）用户体验

请求触发熔断后，一般会出现以下三种情况：

- **读请求**遇到接口降级，部分数据获取不到——需要在界面上给用户提供一定的提示，或让用户发现不了这部分数据的缺失；
- **写请求**熔断触发降级后，有些写操作改为异步，后续处理对用户没有任何影响——但要根据实际情况判断是否需要给用户提供一定的提示；
- **写请求**熔断触发降级后，操作可能直接回滚——此时必须提示用户重新操作。

因此，服务调用触发熔断降级时，需要把这些情况都考虑到，以此保证用户体验，而不是仅仅保证服务器不宕机。

### （4）熔断监控

熔断上线后，其实只是完成了熔断设计的第一步。Hystrix 是一个事前配置的熔断框架，熔断配置到底对不对、效果好不好，只有实际使用后才知道。

为此，实际使用时需要盯着 Hystrix 的监控面板查看各个服务的熔断数据，然后根据实际情况再做调整。只有这样，才能在真正使用熔断时将服务器的异常损失降到最低。

## 小结

市面上的熔断框架已经设计得非常成熟。对使用者而言，虽然可以通过简单配置或少量代码实现熔断，但熔断是高并发体系中的核心技术，有必要搞懂其原理机制及使用场景：

- 线程隔离（线程池 / 信号量）解决慢依赖占用线程的问题；
- 熔断（滚动窗口统计 + 断路器状态机 CLOSED / OPEN / HALF-OPEN）解决依赖持续失败时的雪崩问题；
- 数据一致性、超时降级、用户体验、熔断监控是落地前必须补齐的四块设计。

本文的方案仍有未覆盖的场景，可结合实际的依赖形态补全。

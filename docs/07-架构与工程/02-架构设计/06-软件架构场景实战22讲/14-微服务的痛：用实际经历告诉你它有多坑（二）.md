# 微服务的痛：用实际经历告诉你它有多坑（二）

## 概念说明

本文是微服务痛点系列的第二篇，承接前一篇的两个痛点，继续用四个真实场景剖析微服务落地过程中的典型问题：**没人知道系统整体架构的全貌、重复代码多、耗费更多服务器资源、分布式事务**。这些场景均来自实际公司的架构经历，把场景与现实问题对照分析，是理解微服务代价的有效方式。

## 核心要点

- 微服务规模扩大后，**几乎不存在能掌握系统整体架构全貌的人**：数百个微服务连负责人都只熟悉自己的一亩三分地，故障定位只能临时学习相关系统。
- 单体时代的 Common 包重用模式在微服务中频繁失效：公用 JAR 的版本冲突会让重用成本失控，最终演化为 fork 出多个并行版本。
- 公用 JAR 困局的根因是**JAR 版本太多**；而"统一所有 JAR 版本"的中心化项目往往因投入产出比不高、被紧急业务需求反复 PK 而无法落地。
- 可行的折中：接受部门间的重复代码，用部门内部的 framework/Common/shared/arc 类 GitLab subgroups 重用内部通用代码——维护小重复代码的成本低于统一排期重构与统一评审 JAR 版本。
- 微服务拆分天然消耗服务器资源：6 个微服务 × 2 节点高可用 + 网关层，就把 5 台服务器的单体扩到了 15 台；混合部署方案因运维命名与排查不便被否定，"服务器便宜"的心态进一步放大浪费，大小公司皆然。
- 分布式事务是微服务痛点中最难的一个：跨服务更新多个数据库时，回滚、部分回滚、重试异步三条路各有坑。
- 实际工程中大量场景的选择是**只写 Happy Path**：报错记异常日志、线下手工处理——代价是网络抖动时上下游数据不一致，需要业务工单兜底。
- 分布式事务的系统化解决方案在后续文档中专门讨论。

## 痛点一：没人知道系统整体架构的全貌

### 现象

一个反复出现的场景：每隔几个月或半年，公司高层就会要求汇报每个部门的微服务数量、公司微服务总数量、每个微服务都用来做什么等情况。因为企业微服务数较多，每次汇报都是长长的一条清单。

高层随之而来的质疑通常是："几百个微服务？系统这么复杂了吗？谁能知道所有系统的全貌啊，如果出现问题，如何快速定位问题点呢？"而各负责人的实情是——连自己部门的微服务列表都没完全搞清楚。

### 对比：单体时代的经验失效

在以前的公司（单体架构），通行做法是首先把公司的整个架构系统全貌搞清楚，之后一旦出现问题，就容易定位故障点。而在使用微服务的公司，这种冲动消失了：只要求搞懂自己负责的部分，出现问题临时学习一下相关系统即可。

### 结论

在实际工作中，很难找到一个知道系统整体架构全貌的人——这是微服务的一个核心痛点：**系统复杂度从"一个人可全览"退化为"分布式无知"**，故障定位与架构治理的前提条件（全局可见性）不再天然存在。

## 痛点二：重复代码多

### 单体时代的 Common 包模式在微服务中失效

在单体公司，所有代码放在同一个工程中，发现可重复使用的代码，抽取出来存放在 Common 包中即可。这种代码设计在微服务中经常出问题。

### 案例：公用埋点 JAR 的三连败

某团队做了一个日志自动埋点功能，能自动记录一些特定方法的调用。其他团队想直接使用，埋点团队给出了 Maven 声明。后续过程如下：

1. **第一个使用方**：立马报出 JAR 版本冲突问题；若将冲突的 JAR 升级，其原始代码就无法使用。为节省人力成本，只能询问埋点团队如何实现版本兼容。
2. **埋点团队的补救**：重新设计了一版埋点 JAR，去掉了一些特定 API 的使用，两个团队终于可以正常使用。
3. **第三个使用方**：又报出一个 JAR 版本冲突问题。自动埋点团队从投入产出比角度考虑，放弃维护这个公用 JAR，直接告知其他团队：代码在 Git 上，各团队自己 fork 修改。
4. **最终结局**：这个代码在不同团队的微服务中存在了多个不同版本。

### 复盘结论

- 重用 JAR 本身没有错，**错在使用太多不同的 JAR 版本**，必须改变这个局面。
- "统一所有 JAR 版本"的项目正式立项后，第二天就被紧急业务需求打断；一段时间后再次被提起，又被紧急业务需求 PK 掉。最终大家明白：这个项目没法做，因为**投入产出比不高**。

### 实践要点

- 微服务之间存在重复代码是可接受的现实：部门之间的重复代码比比皆是。
- 技术中心的每个部门都有自己的 framework/Common/shared/arc 类 GitLab subgroups，可以对部门内部的通用代码进行重用。
- **维护这些小的重复代码，总比统一排期做重构、统一评审 JAR 版本的成本低得多**。

## 痛点三：耗费更多服务器资源

### 案例：从 5 台到 15 台

一家原使用单体式架构的小公司，共部署 5 台服务器；因抱怨系统耦合性太强、代码之间经常互相影响，决定迁移架构。拆分过程如下：

- 按业务模块，把单体架构拆分为 **6 个微服务**；
- 考虑高可用，每个服务至少部署在 2 个节点上；
- 再加网关层 2 台服务器；
- 其中一个服务比较耗资源，为保险起见多加 1 个节点；
- **最终共部署 15 台服务器**。

业务没有变，流量没有变，代码逻辑改动也不大，却多出了 9 台服务器。

### 混合部署方案的争议与否定

针对资源浪费，曾提出过压缩方案：一台服务器不只部署一种服务，例如服务 AB 部署在 1 个节点、BC 部署在 1 个节点、AC 再部署在 1 个节点（这样理论上可以覆盖 3 个服务且各服务均有实例）。

该方案很快被否定，理由是运维视角：每个服务器只部署一种服务时，服务器的名字直接以服务名字命名，排查问题方便；混合部署后，服务器命名与排查都变得麻烦。

### 放大浪费的组织因素

于是有人提议："反正服务器比较便宜，多几台也无所谓。"大家纷纷附和。小公司如此，大公司同样如此——后续经历的一些大公司，也经常有人抱怨服务器资源不够用。几天后 CTO 召集研发开会："这个季度服务器预算太多，财务部门审核不通过，需要缩减服务器数量，把不用的服务器都下掉。"于是研发人员对每个服务进行检查，出现了下面这段对话：

> A："这个服务怎么使用了这么多台服务器？很耗资源吗？"
>
> B："不是，主要是公司强制要求实现多数据中心部署。"
>
> A："这个服务很重要吗？内部使用的吗？"
>
> B："是，这个目前只是开发人员在使用。"
>
> A："那干吗做负载均衡，下了下了，只留一台。"
>
> B："好吧。"
>
> A："现在我们缩减了多少台服务器了？"
>
> B："……"

这段对话暴露的典型问题是：内部工具型服务也被强制多数据中心部署 + 负载均衡，资源策略与服务重要性不匹配。

### 结论

在经历过的大量公司中，这种情形很常见——**微服务确实很耗服务器资源**，且浪费往往由"高可用标配 + 部署隔离惯例 + 服务器便宜心态"三者叠加造成。

## 痛点四：分布式事务

### 背景：下单流程的跨服务化

分布式事务对微服务来说堪称最难的痛点。以一个曾经经历的下单流程为例：

**原本的下单流程**：插入订单 → 修改库存 → 插入交易单 → 插入财务应收款单 → 返回结果给用户，让用户跳转。

**单体式架构的处理**：把上面的下单流程包在一个事务里即可。某个流程出错时，直接回滚数据，并通过业务代码告知用户出错了，让用户重试。

**迁移到微服务后**：这几个流程分别存放在不同的服务中，需要更新不同的数据库，随之产生以下纠结。

### 三种方案及其问题

1. **全部回滚**：某个流程出错是否需要将数据全部回滚？如果需要，就要在每个流程中写上回滚代码。那万一回滚失败了呢？是不是还需要写回滚的回滚代码？回滚的回滚代码算回滚吗？
2. **部分回滚**：某些流程回滚、某些流程不回滚？那哪些流程回滚、哪些不回滚，边界如何确定？
3. **统一不回滚、失败重试**：这样岂不是需要做成异步？如果做成异步，会不会出现时间超时？超时了用户怎么办？需要回滚吗？（问题又绕回了回滚。）

问题的规模在于：分布式服务更新数据的场景实在太多，如果每个场景都要纠结这些逻辑，交付速度将无法接受。

### 实际采用的策略：只写 Happy Path

针对这种情况，大部分场景下的选择是**不考虑回滚和重试，只写 Happy Path**：如果报错就记个异常日志，再线下手工处理。

**后果**：机房网络抖动是常有的事情，以至于三天两头数据更新出现异常——比如上游数据更新了、下游数据没有更新，数据就对不上了。业务部门的抱怨随之而来："这个订单怎么找不到收款单了？""这个交易单怎么没有交易流水？"而研发侧的处理方式是：提个工单，线下修复。

### 结论

使用微服务时，分布式事务一直是痛点也是难点。上述 Happy Path 策略只是权宜之计，系统化的解决方案（依赖治理与分布式事务设计）在后续文档中专门讨论。

## 小结

本文通过四个实际场景剖析了微服务的四个痛点及其工程含义：

| 痛点 | 核心表现 | 根因 / 应对 |
|---|---|---|
| 没人知道系统全貌 | 数百个微服务，无人能全览 | 全局可见性缺失，只按领域自治 + 故障时临时学习 |
| 重复代码多 | 公用 JAR 版本冲突 → fork 泛滥 | JAR 版本失控；接受部门内 subgroup 重用，放弃中心化统一 |
| 耗费更多服务器 | 5 台单体扩到 15 台微服务 | 高可用标配 + 部署隔离惯例 + 资源策略与服务重要性不匹配 |
| 分布式事务 | 跨服务多库更新无法简单回滚 | 回滚/部分回滚/重试异步三路皆难；实际常退化为 Happy Path + 工单兜底 |

这些痛点不是微服务"用错了"的结果，而是其架构形态的固有代价；认识它们是后续治理方案（依赖治理、分布式事务、数据同步）的认知基础。

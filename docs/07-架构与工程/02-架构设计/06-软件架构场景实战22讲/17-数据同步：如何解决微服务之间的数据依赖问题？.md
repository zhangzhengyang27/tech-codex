# 数据同步：如何解决微服务之间的数据依赖问题？

## 概念说明

本文讨论微服务之间的**数据依赖**问题，是数据一致性方案（见前文）的延续：当服务 A 的业务数据需要被多个其他服务查询使用时，跨服务的关联查询会把依赖压力全部压到数据提供方服务上。本文以一个真实的供应链系统案例，对比三种方案的演进过程：跨服务查询 → 数据冗余 + 消息订阅 → 解耦业务逻辑的数据同步。

## 核心要点

- 严格按微服务划分原则存储数据后，跨服务关联查询需要"先调用数据提供方服务匹配 ID，再用 IN 语句关联查询"，随着数据量增长会出现**查询越来越慢、核心服务不堪重负、请求超时、下游服务处理失败**的连锁问题。
- **数据冗余**方案：在订单、采购单中保存部分商品字段，查询时不再依赖商品服务；冗余数据的更新有"直接调用同步"与"消息发布订阅同步"两种办法。
- 直接调用同步存在两个问题：**数据一致性**（冗余更新失败需回滚，边缘流程阻断了核心流程）与**依赖倒挂**（商品这一核心底层服务反向依赖一大堆下游冗余更新服务）。
- 消息发布订阅同步有两点优势：商品无须调用其他服务；订阅方更新失败可用消息重试机制保证最终一致性。但它存在三个问题：**订阅方要复制商品服务的近一半逻辑**（订阅近十种消息）、**每个依赖服务重复实现同步逻辑**、**MQ 消息类型太多导致联调困难**。
- **解耦业务逻辑的数据同步方案**：将商品及相关表（分类表、生产批号表、保修类型、包换类型等）实时同步到依赖方数据库且表结构不变，依赖方直接关联查询、只读不可写。
- 存储空间对比：冗余方案中 N 条订单产生 N 份商品冗余数据（N 远大于 M 条商品总数），同步方案只增加 M 条商品数据，**更省空间**。
- 同步中间件的选型要求：支持实时同步、支持增量同步、不用写业务逻辑、支持 MySQL 之间同步、活跃度高；候选为 Canal、Debezium、DataX、Databus、Flinkx、Bifrost。
- 终选 Bifrost，理由：界面管理不错、架构简单可自行调查维护（可控）、作者更新活跃、自带监控报警功能。
- ⚠️ Bifrost 不支持集群、无法保障高可用，是该方案的遗留风险；上线至今未宕机，反而多节点负载均衡的后台服务时常宕机。

## 业务场景（架构经历十三）

某供应链系统中存在**商品、销售订单、采购**三个服务，它们的主数据部分结构如下：

**商品**

**订单和子订单**

**采购单和子订单**

系统设计时需要满足以下两个需求：

- 根据商品的型号/分类/生成年份/编码等查找订单；
- 根据商品的型号/分类/生成年份/编码等查找采购订单。

### 初期方案：严格划分职责 + 跨服务查询

初期方案严格按照微服务划分原则，将商品相关的职责存放在商品系统中。查询订单与采购单时，如果查询字段包含商品字段，需按如下顺序进行查询：

- 先根据商品字段调用商品的服务，返回匹配的商品信息；
- 在订单或采购单中，通过 IN 语句匹配商品 ID，再关联查询对应的单据。

### 初期方案暴露的问题

方案上线后很快遇到一系列问题：

- 随着商品数量的增多，匹配的商品越来越多，订单服务中包含 IN 语句的查询效率越来越慢；
- 商品作为核心服务，依赖它的服务越来越多；同时随着商品数据量增长，商品服务已不堪重负，响应速度变慢，还存在请求超时的情况；
- 由于商品服务超时，相关服务处理请求经常失败。

结果就是：业务方每次查询订单或采购单时，只要带上商品关键字，查询效率就很慢而且经常失败。因此引入新方案——**数据冗余**。

## 方案一：数据冗余

### 冗余方案的定义

数据冗余方案即在订单、采购单中保存一些商品字段信息。冗余后的数据结构如下：

**商品**

**订单和子订单**

**采购单和子订单**

调整架构方案后，每次查询时就可以不再依赖商品服务了。

但新的问题随之而来：如果商品进行了更新，如何同步冗余的数据？有两种解决办法：

1. 每次更新商品时，先调用订单与采购服务，再更新商品的冗余数据。
2. 每次更新商品时，先发布一条消息，订单与采购服务各自订阅这条消息后，再各自更新商品的冗余数据。

### 办法一（直接调用）的两个问题

**数据一致性问题**：如果订单与采购的冗余数据更新失败了，整个操作都需要回滚。商品服务的开发人员不会接受——冗余数据不是商品服务的核心需求，不能因为边缘流程阻断自身的核心流程。

**依赖问题**：从职责来说，商品服务应该只关注商品本身，但此时商品还需要调用订单与采购服务。而且依赖商品这个核心服务的服务实在太多，后续商品服务每次更新商品时，都需要调用更新订单冗余数据、更新采购冗余数据、更新门店库存冗余数据、更新运营冗余数据等一大堆服务。商品到底是下游服务还是上游服务？核心底层服务的定位被彻底破坏。

因此，办法一被否决。

### 办法二（消息发布订阅）的优势与遗留问题

采纳的方案是通过消息发布订阅同步冗余数据（整体链路为：商品服务发布变更消息 → MQ → 订单、采购等服务订阅消息并各自更新冗余数据），它有两点优势：

- 商品无须调用其他服务，只需关注自身逻辑，顶多多生成一条消息送到 MQ；
- 如果订单、采购等服务的更新冗余数据失败了，使用消息重试机制即可，最终能保证数据的一致性。

不过该方案存在三个问题。

**1. 冗余字段太多，订阅消息近十种**。仅仅保存冗余数据还远远不够：还需要将商品分类与生产批号的清单进行关联查询，即每个服务不只订阅商品变更这一种消息，还需要订阅商品分类、商品生产批号变更等消息（订单表结构中相应新增了商品分类、生产批号等冗余字段）。以上仅列举了部分结构——事实上商品表中还有很多字段存在冗余，比如保修类型、包换类型等。为了更新这些冗余数据，采购服务与订单服务往往需要订阅近十种消息，基本上需要把商品的一小半逻辑复制过来。

**2. 每个依赖服务需要重复实现冗余数据同步逻辑**。采购、订单及其他服务都依赖商品数据，因此每个服务都需要把冗余数据的订阅、更新逻辑做一遍，最终重复的代码很多。

**3. MQ 消息类型太多，联调困难**。联调时最麻烦的是 MQ 之间的联动：接口联调相对可控且好追溯（调用哪个服务器的接口明确）；消息联调则麻烦得多——常常不知道某条消息被哪台服务节点消费了；为了让特定的服务器消费特定的消息，需要临时改动双方的代码，而且联调完成后经常忘了改回原代码。

由于不希望为"冗余数据"这种非核心需求付出这么多代价，最终转向一个特别的同步冗余数据方案。

## 方案二（终选）：解耦业务逻辑的数据同步方案

### 设计思路

- 将商品及商品相关的一些表（比如分类表、生产批号表、保修类型、包换类型等）实时同步到需要依赖使用它们的服务的数据库，并且保持表结构不变；
- 在查询采购、订单等服务时，直接关联同步过来的商品相关表；
- 不允许采购、订单等服务修改商品相关表（只读）。

### 该方案解决的问题与代价

轻松解决了两个问题：

- 商品无须依赖其他服务，如果其他服务的冗余数据同步失败，它也不需要回滚自身的流程；
- 采购、订单等服务无须关注冗余数据的同步。

方案的"缺点"表面上是增加了订单、采购等数据库的存储空间（因为增加了商品相关表）。但仔细计算后结论相反：数据冗余方案中每个订单都需要保存一份商品的冗余数据，假设订单总数是 N、商品总数是 M，而 N 一般远远大于 M——冗余方案中 N 条订单就会产生 N 条商品的冗余数据；相比之下，**解耦业务逻辑的数据同步方案更省空间，因为只增加了 M 条商品的数据**。

### 同步中间件选型

新问题是：如何实时同步相关表的数据？直接使用现成的开源中间件即可，但它需要满足五点要求：

- 支持实时同步；
- 支持增量同步；
- 不用写业务逻辑；
- 支持 MySQL 之间同步；
- 活跃度高。

根据这五点要求对市面上多款开源中间件做了对比，候选包括 Canal、Debezium、DataX、Databus、Flinkx、Bifrost。

比较贴近需求的是 **Bifrost**，原因如下：

- 界面管理不错；
- 架构比较简单，出现问题后可以自行调查，之后就算作者不维护了也可以自我维护，相对比较可控；
- 作者更新活跃；
- 自带监控报警功能。

最终使用 Bifrost 开源中间件，整体链路为：Bifrost 将商品及商品相关表从商品库实时同步到订单、采购等服务的数据库（表结构不变、只读关联）。

### 上线效果

整个架构方案上线后，商品数据的同步比较稳定：

- 商品服务的开发人员只需关注自身逻辑，无须再关注使用数据的人；
- 需要关联使用商品数据的订单、采购服务的开发人员无须关注商品数据的同步问题，只需在查询时加上关联语句即可。

实现了双赢。

::: warning 遗留风险
唯一需要持续关注的是 Bifrost 不支持集群，没法保障高可用性。不过到目前为止它还没有出现宕机的情况，反而是那些部署多台节点负载均衡的后台服务常常出现宕机。
:::

## 小结

本文讲解了服务之间的数据依赖问题及对应解决方案的演进：

| 方案 | 核心思路 | 主要问题 |
|---|---|---|
| 跨服务查询（初期） | 严格划分职责，IN 语句关联 | 查询慢、核心服务不堪重负、超时连锁失败 |
| 数据冗余 + 消息订阅 | 订单/采购单存冗余字段，MQ 同步 | 复制一半商品逻辑、重复实现、MQ 消息太多联调难 |
| 解耦业务逻辑的数据同步（终选） | 开源中间件实时同步原表，依赖方只读关联 | 需选型可控的中间件；存在单点高可用风险 |

服务之间逻辑与流程上的依赖问题在后续文档中讨论。本方案并非通用解，仍有未覆盖的场景，可结合实际的依赖关系补全。

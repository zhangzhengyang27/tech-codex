# 一人一套测试环境：测试环境何时能释放出来使用？

## 概念说明

"一人一套测试环境"是一套基于容器化与 Kubernetes 的测试环境方案:按需在几秒内快速搭建一套独立的测试环境,使用完立即销毁。该方案在网上较少被系统讲解,但对多项目并行研发的组织具有普遍适用性。

## 业务场景

某公司的基础设施使用虚拟机,尚未迁移到容器,一共搭建了 3 套测试环境。之所以搭建 3 套而不是 1 套,主要考虑是:多个并行项目同时进行时,需要实现分开测试和分开上线,3 套测试环境可以在一定程度上避免并行项目因排队导致延期。

一般研发流程为:需求宣讲 → 接口/方案设计 → 功能开发 → 联调 → 测试 → 预生产 → 上线。在这 3 套测试环境中,1 套专门用于联调,另外 2 套专门用于测试。

然而 3 套仍然不够用,一个具体案例:

- 某项目已上测试环境,功能测试反馈没问题,但第三方验收拖了很久,导致不得不继续占用这套测试环境;
- 同时,一个小迭代项目要求下周四上线,还有一个上百人参与的超大项目刚进入测试阶段,这就需要 2 套测试环境——测试环境立即不够用,连联调环境都被征用了;
- 此时业务方又提出一个加急需求,要求本周四上线。团队内部协商的结果是:测试 1 的功能需要测试一周且下周四上线,让出一两天就要延期一天;测试 3 被领导亲自跟进的验收项目占用;另一个长周期项目号称公司第一优先级,不好开口借用。
- 最终结果是:因为抢测试环境,紧急需求无法按时上线。

在实际工作中,一个组同时开展多个项目的情况经常发生,尤其是业务对接方比较多的小组。为解决这个问题,该团队实施了"一人一套测试环境"方案。

## 解决思路

目标:可以快速搭建一套新的测试环境,使用完立马销毁。

解决思路:

- 利用容器的特性,在几秒内快速启动服务实例;
- 将测试环境需要搭建的服务通过容器实例部署起来;
- 将这些容器通过 Kubernetes 管理(编排)起来。

### 组件范围决策:全部组件还是部分组件

决定使用容器灵活创建测试环境后,团队对"每一套容器环境是包含全部组件还是部分特定组件"调研了很久。

使用过容器的开发人员都知道,在容器中部署 MQ、ZooKeeper、Redis 或配置中心是一件很简单的事情。例如使用容器部署 Redis,只需 2 行命令:

```bash
$ docker pull redis

$ docker run --name a-redis-name -d redis
```

使用容器部署 ZooKeeper、MQ 的方法也类似。

但该公司所有的中间件基本不是纯洁的开源版本:配置中心没有使用 Spring Cloud Config,也没有使用 Nacos,而是使用了一个完全自研的产品(MQ 和网关也是自研),它既不支持容器,也不支持单机版;ZooKeeper、Redis 基于开源版本,并在服务端加了一些封装;客户端强制使用一个自定义的客户端 SDK,且使用的中间件必须强绑定配置中心。

经过评估,如果把这些中间件部署到容器中,将会出现如下 3 种情况:

1. 中间件服务端改造成本大;
2. 客户端的 SDK 需要进行大量的改造;
3. 最重要的一点:会导致容器环境与其他普通环境存在很大的代码差异。因此,就算在容器中测试没问题,还需要在其他环境进行大量测试,此时容器测试环境就失去意义了。

**最终决策:在容器测试环境中只部署独立的 API 服务或后端服务,其他组件直接重用测试环境的中间件。**

基于这个设计方案,想快速部署一套独立的测试环境,需要解决如下 5 个问题。

### 1. API 服务间的隔离

问题:如何确保容器环境的客户端请求到达容器的 API 服务,而非容器环境的客户端仍然正常到达测试环境的 API 服务?

原系统设计:每一个 API 服务中都会带一个配置项 channelID,客户端每次访问 API 时都需要带上一个 channelID 参数。网关层接收到请求后,会根据 channelID 将请求匹配到对应 channelID 的 API 服务中(当然 URI 也需要匹配),隔离过程因此比较简单。

环境标识约定:每个项目都有一个 JIRA Issue(例如 XXXX123 就是一个 JIRA Issue ID),为每个项目单独起一套容器测试环境,该 Issue ID 自然而然地被当作环境标识。

具体实现:客户端通常把 channelID 放在配置文件中,等到容器测试时再打一个包,此包中 channelID 的配置值为 JIRA Issue ID,即容器测试环境的标识。同时,在容器环境打包 API 服务时,自动将 channelID 的配置值改为 JIRA Issue ID。

调用请求处理过程:网关层接收到所有请求后,根据不同的 channelID 将请求分发到不同的 API 服务中,API 服务的隔离问题就此解决。

### 2. 后台服务间的隔离

问题:如何确保容器环境部署的服务只调用容器服务,而测试环境虚拟机的服务只调用虚拟机服务?

原系统设计:在打包 RPC 服务时,将一个环境变量 env 的值设置为容器测试环境的标识(即 JIRA Issue ID,如 XXXX123)。每个 RPC 服务注册 ZooKeeper 时,在 service 的 meta data 中加一个 tag,并设置 tag 的值为 XXXX123。之后,RPC 服务只会调用同样 tag 的服务。

示例:测试环境中有 3 个 UserService,其中 1 个是测试环境的虚拟机,2 个是容器测试环境部署的 UserService。前者的 tag 为空,后两个容器 UserService 注册 ZooKeeper 后,tag 值分别为 XXXX123 和 XXXX245。另一个 OrderService 调用 UserService 时:如果 OrderService 也是 XXXX123 这个容器环境的服务,则它只会调用带 XXXX123 这个 tag 值的 UserService;如果它是正常虚拟机的服务,则只会调用不带 tag 值的 UserService。

由此,后台 RPC 服务间的隔离问题解决。

补充说明:上述要点中没有专门提及 ZooKeeper,因为 API 和 RPC 服务的隔离问题解决后,ZooKeeper 的数据隔离问题基本也解决了。ZooKeeper 在每套测试环境中起的作用只是 API 服务和 RPC 服务的注册发现。

### 3. MQ 和 Redis 隔离

问题:如何确保容器环境和虚拟机之间的 MQ 消息不互串、Redis 数据不互相影响?

备选方案:使用类似 tag 的概念解决这个问题——通过封装 MQ 与 Redis 的客户端代码,让它们只消费同样 env 环境变量值的服务生产的内容。

最终决策:需要遵循"尽量减少容器测试环境与正式环境的代码差异"这一原则,因此没必要专门定制,只需保证走测试流程时使用不同的测试数据即可(本来不同的项目就会使用不同的测试数据,包括不同的用户、不同的订单等),这样基本不会再出现不同容器测试环境流转同样的 MQ 消息、缓存数据的情况。

例外:Redis 中的一些通用数据(比如城市之类的基础数据)还是会共同使用。不过,这些数据即使不同容器测试环境之间互相串联也不要紧。

### 4. 配置中心数据的隔离

设计方式:如果容器测试环境的值与虚拟机测试环境的值不一样,不修改配置中心的值,而是在容器环境的启动脚本中动态加上针对各自容器测试环境的环境变量,然后在业务代码中让环境变量优先级高于配置中心的参数。这样就确保了容器测试环境的特殊配置,同时不影响配置中心的值。

### 5. 数据库间的数据隔离

数据库互相影响的情况一般分为两种:

**(1)测试数据互相影响**

与 MQ/Redis 的情况一样,只需保证测试数据各自独立即可。

**(2)数据库结构兼容问题**

示例:同时进行 2 个项目,XXXX123 项目删除了 user 表的 updateFlag 字段,而 XXXX100 项目还需要使用这个字段。此时如果 2 个项目共用 1 个数据库就会互相影响。

处理原则:每次版本迭代时,都需要保证数据库可以兼容前一个版本的代码。例如上例中,不会直接在 XXXX123 中删掉 updateFlag 字段,而是等 XXXX123 上线后再删掉。

另一个兼容性示例:在 XXXX123 项目中增加了 1 个字段,且 updateUserId 字段的值为必填,不然数据就会报错;而 XXXX100 项目并不会更新 updateUserId,这样如果 XXXX123 读到了 XXXX100 写入的数据就会报错。

处理方式有两种:

- 在项目 XXXX123 中增加容错代码,即允许 updateUserId 为空;
- 将项目 XXXX123 与项目 XXXX100 部署到不同测试环境的数据库中。

解决完以上 5 个问题后,基于现有测试环境快速部署多套容器环境的方案就基本成立了。

## 使用流程

具体使用流程如下:

- 每次新建一个工程(新的 API 或者后台服务)时,都会在 Jenkins 上配置一个 Job,这个 Job 需要接受 3 个参数:
  - **Branch**:需要部署的代码分支;
  - **测试环境**:test1/test2/test3(已有 3 个测试环境,它决定了部署需要使用哪个测试环境的中间件);
  - **容器测试环境标识**:即 JIRA Issue ID。
- Job 启动时,调用一个小工具连接 Kubernetes 创建 namespace(=JIRA Issue ID),然后在 namespace 中增加一个 pod(pod 中运行的是专门为该 JIRA Issue ID 打包的代码)。
- 做某个项目(如 XXXX123)需要使用 UserAPI、UserService、OrderService、ProductService 时,配置一个新的 Jenkins Job 联动这 4 个服务的 Job,并将各个服务对应的 Branch、测试环境和 JIRA Issue ID 传入(这些值通过 hard code 配置在新的 Jenkins Job 中)。之后,每次点击这个项目的 Jenkins Job,就可以对这个项目的容器测试环境进行部署。
- 如果项目成员想自己部署一套环境,只需单独配置一个新的 Jenkins Job,并找一个不一样的容器测试环境标识(比如开发任务的 Issue ID)即可。

## 实施效果

通过这套方案,团队不再需要在联调测试时协调借用环境。方案成本非常小:代码改动很少,1 周半即可把整个方案实施完成(时间主要花在申请服务器和部署 Kubernetes 上)。

方案上线后得到使用者的一致好评,尤其是测试同学,原因有三:

- 不再需要因为协调测试环境花费大量沟通时间;
- 一键就可以将相关服务部署起来,不像以前需要一个服务一个服务部署;
- 因为容器测试环境的搭建很简单,开发人员每完成一个功能,测试人员即可介入测试,而不需要等整个项目提测后再介入,大大缩短了提测后的测试周期。

总体来说,项目效果非常好,后续容器测试环境基本保持人均一套的使用频率。

## 小结

"一人一套测试环境"方案的关键在于:用容器 + Kubernetes 实现环境的秒级创建与用完即毁,同时将容器环境的范围收窄为"只部署 API 服务与后端服务",通过 channelID 网关路由实现 API 隔离、通过 ZooKeeper meta data tag 实现 RPC 隔离、通过独立测试数据实现 MQ/Redis/数据库隔离、通过启动脚本环境变量覆盖配置中心实现配置隔离,从而在不改造自研中间件、不放大代码环境差异的前提下,彻底解决多项目并行时的测试环境争抢问题。

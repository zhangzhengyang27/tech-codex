# 如何使用简洁的架构实现高性能读服务？

## 概念说明

按"目的性"维度划分，后台系统的架构可归类为读业务、写业务及扣减类业务。在实际业务中，绝大多数情况都是读场景高于写场景——浏览多少次商品才会下一单？一天看多少条朋友圈、才会发几条朋友圈？

因此，读业务是后台架构实战的起点。本文覆盖读业务在实现上需要满足的功能特点、遵守的基本原则，以及常见实现方案的优缺点。

::: tip 术语约定
"读业务"这个名词偏业务和产品；研发在做系统设计或日常沟通中，会采用偏技术实现的名词，如读接口或读服务。本文统一用**读服务**代指读业务。
:::

## 核心要点

- 读服务是无状态/无副作用的：纯粹地从存储中一次或多次获取原始数据，进行简单逻辑加工后返回，每一次执行都不会在存储中记录或修改数据，每次读请求都和上一次无关。
- 读服务的三条功能性要求：**保证高可用**、**保证高性能**（TP999 在 100ms 以内）、**支持超高 QPS**（上万~百万的峰值）。
- 原则一：**架构尽量不要分层**。读服务业务逻辑简单、性能主要消耗在网络传输上，分层使网络传输翻倍；将数据访问层编译为 JAR 包直接依赖（同进程部署）后，TP999 可降一半、平均性能提升 20%~30%。
- 原则二：**代码尽可能简单**。尽量少引入框架，必须引入时要严格压测；序列化日志、全量取数后过滤等"方便做法"都是性能杀手。
- 读服务最主要的依赖中间件是存储，**存储的性能很大程度上决定了读服务的性能**；MySQL、HBase 即使优化后并发量大时也很难达到 200ms 以内。
- 实战主流架构：**基于内存的 Redis 作为主存储、MySQL 作为兜底**的懒加载模式——缓存未命中时降级查库并回填缓存，缓存设置过期时间防脏数据。
- 懒加载架构的四类问题：**缓存穿透**（占位符 + 参数前置校验应对）、**缓存集中过期雪崩**（过期时间加盐）、**无法感知实时变更**（改为更新库后主动更新缓存，但有分布式事务缺失与遗漏风险）、**毛刺无法摆脱**（缓存过期瞬间毫秒/秒级差距）。
- 提升读性能的通用手段是**数据前置**（浏览器本地缓存、CDN），代价是数据更新不及时。
- 尽管存在不足，懒加载架构及其变种因实现简单、成本低，仍是实际应用中使用较多的解决方案。

## 读服务的功能实现要求

### 读服务的定义与特征

读服务在实现流程上，基本上是纯粹地从存储中一次或者多次获取原始数据，进行简单的逻辑加工，或者直接返回给用户/前端业务系统。它是无状态的或者是无副作用的：每一次执行都不会在存储中记录数据或者修改数据，每一次读请求都和上一次无关。

典型场景：

- 打开资讯类 App 有两类场景：一类是业务后台系统直接从存储中获取今日的新闻列表；另一类是推荐系统生成一个新闻推荐列表，给到业务前台系统并展示给用户。
- 电商 App 首页展示的商品和促销等信息，是运营根据营销策略配置的；业务后台接收到读请求，直接去存储获取数据并进行加工后返回给业务前台系统。

### 三条功能性要求

- **保证高可用**：不管是不是读服务，都需要满足高可用。
- **保证高性能**：以 TP999 在 100ms 以内为指标。浏览新闻和电商 App 时，如果首页打开非常慢，体验一定非常差。
- **支持的 QPS 非常高**（如上万~百万的峰值 QPS）：因为大部分业务场景都是"读多写少"。

## 原则一：架构尽量不要分层

### 分层架构的性能问题

通过水平拆分可以将共性的、不易变的代码逻辑单独封装成一个模块对外服务，减少重复、提升效率。但在实际应用中，通过监控图可以发现：分层架构下读服务性能的平均值离 TP99 或 TP999 有较大的差距，通常在一倍以上，且性能毛刺比较多。

产生这种情况有两个原因：

- 采用分层架构之后，网络传输相比不分层的架构多了一倍。
- 读服务的业务逻辑都比较简单，性能主要消耗在网络传输上。请求查询的数据越少，性能越好（假设 10ms）；数据多时性能较差（假设 50ms）。叠加上分层架构，性能就会翻倍——数据少时从 10ms 变成 20ms，数据多时从 50ms 变成 100ms。分层后，数据的多与少带来的性能差距达到了 80ms，这就是产生毛刺的原因。

### 优化方案：数据访问层编译进读服务进程

为了提高查询性能、减少毛刺、同时降低部署机器的数量：**将水平拆分的数据访问层代码工程保留独立，但在实际编译时直接编译到读服务里**。以 Java 举例，直接将数据访问层编译为 JAR 包并由读服务进行依赖；部署时两者在同一个进程里，去掉网络传输。

实际案例中，此项升级后的性能变化明显：**TP999 基本降了一半，平均性能提升 20%~30%**。

### 隐含原则：数据前置

上述优化的隐含原则是，**读服务要尽可能和数据靠近，减少网络传输**。此项原则已经应用在很多类似的场景里：

- 现在很多浏览器都自带本地缓存功能：浏览一个网页后，在一段时间内再次访问时，网页数据直接从浏览器缓存获取，网页打开速度非常快。
- CDN 也是一样的道理：把数据推送到离用户最近的机房里，缩短网络传输的距离。

这两种场景里提升性能的方式又称为**数据前置**。但数据前置也会带来另一个问题——数据更新不及时，该问题的有效解决方案在后续文档中详细介绍。

## 原则二：代码尽可能简单

### 读服务的执行步骤

读服务的实现流程非常简单，接口在接收请求时：

- 首先将外部的入参解析成内部模型并进行校验；
- 之后根据具体的存储类型使用内部模型构建查询条件并请求对应的存储；
- 获取到数据后，进行反序列化转换为内部模型；
- 根据业务情况进行适当地处理；
- 将处理后的数据转换为对外 SDK 的模型并返回。

在上述流程里，有大量的模型映射——比如将外部的模型映射为代码中的内部模型、将内部模型映射为查询条件等。这些不同层次的模型，字段都差不多。为了提升映射效率，有时可能会借助一些框架对相同的字段进行自动化的转换。

### 框架引入的红线

对于其他能够提升效率的地方，也可能引入框架。**在读服务对于性能要求非常严格的情况下，要尽可能地减少引入框架；如果一定要引入，必须经过严格的压测**。在实际应用中，很多能够提升效率的框架性能都非常差。比如 Java 中的 `BeanUtils.copyProperties`，它采用反射机制进行字段 copy，在数据量较大时性能较低。

### 日志序列化的消耗

在读服务的处理链路上，为了方便排查问题，经常会直接将请求的入参及从存储中获取的数据使用 JSON 序列化为字符串并进行日志打印。这种粗暴的方式对性能有非常大的消耗，建议不要直接全量序列化，而是**精细化地按需打印**。

### 按需取数

对于读取的内容要在存储处按需取，而不是全量取回后再在服务内部进行过滤：

- 存储为 MySQL 时，不要使用 `select *`，需要手动指定查询的字段；
- 存储为 Redis 时，使用 Redis 的 hash 结构存储数据——hash 结构可以在查询时指定需要返回哪些字段；
- 其他存储结构，如 ElasticSearch 等亦然。

## 存储的选型和架构

**读服务最主要依赖的中间件是存储，因此存储的性能很大程度上决定了读服务的性能**。对于 MySQL、HBase 等数据库，即使使用分库分表、读写分离、索引优化等手段，在并发量大时，性能也很难达到 200ms 以内。

为了提升性能，实战中的架构通常选用**基于内存的、性能更好的 Redis 作为主存储，MySQL 作为兜底**来构建。

### 懒加载模式的机制

该架构称为**懒加载模式**：

- 初始时，所有数据都存储在数据库中；
- 读服务接收请求时，先去缓存（Redis）中查询数据；
- 如果没有查询到数据，就降级到数据库中查询，并将查询结果保存在 Redis 中，以供下一次请求查询；
- 保存在 Redis 中的数据会设置一个过期时间，防止数据库的数据变更后，请求还一直读取缓存中的脏数据。

该架构设计简单清晰且实现成本较低，但还存在一些潜在问题，不能满足高可用及完全高性能的要求。主要有以下四类。

### 1. 存在缓存穿透的风险

**问题**：如果恶意请求不断使用缓存中不存在的数据发送请求，就会导致该请求每次都被降级到数据库中。因为数据库能够支持的并发有限，请求量很大时可能会把数据库打挂，进而引起读服务不可用，不满足高可用要求。

**应对一——占位符**：针对数据库中没有的数据，可以在缓存中设置一个占位符。第二次请求处理时，读取缓存中的占位符即可识别数据库中没有此数据，然后直接返回给业务前台系统。

**占位符的副作用**：如果恶意请求不断变换请求条件，同时这些条件对应的数据在数据库中均不存在，那么缓存中存储的"无数据"占位符也会把整个缓存撑爆，进而导致有效数据被缓存清理策略清除，或者整个读服务宕机。

**应对二——业务侧前置校验**：对于此种恶意请求，需要从业务上着手处理。请求的参数可以内置一些 token 或验证数据，在读服务中前置进行校验并拦截，而不是透传到缓存或数据库中。

### 2. 缓存集中过期导致雪崩

**问题**：对存储在缓存中的数据设置过期时间是为了定期获取数据库中的变更，但如果设置不合理，可能导致缓存集中过期，进而所有读请求都因缓存未命中而直接请求到数据库。因缓存支持的量级至少是数据库的十倍以上，此类瞬间高并发流量会直接将数据库打挂，进而宕机。

**应对——过期时间加盐**：设置缓存过期时间时进行加盐操作。假设原先统一是 2 个小时过期，设置时根据随机算法在一个区间内获取一个随机值，在 2 个小时的过期时间上再加上此随机值——这就做到了各个缓存的过期时间不一致，同时过期的缓存数量最可控。

### 3. 懒加载无法感知实时变更

**问题**：在缓存中设置过期时间，虽然可以让用户感知到数据的变更，但感知并不是实时的，会有一定延迟。在某些对数据变更不敏感的场景是可以的——比如编辑新发布了一个新闻，用户没看到，因为根本不知道编辑发布了新新闻。

**升级方案——主动更新缓存**：想要实时看到数据变更，可以升级架构：在每次修改完数据之后，主动将数据更新至缓存里。此种方案下，缓存里的数据均和数据库保持一致。

**升级方案的细节问题**：

- **一致性无法完全保障**：如果修改完数据库再更新缓存，异常情况下可能出现数据库更新成功、但缓存更新失败的情况。因为数据库和缓存是两个存储，没有分布式事务机制时，缓存更新失败后数据库的数据不会回滚，缓存和数据库中的数据依然不一致——方案并没有完美解决问题。若先更新缓存再更新数据库，同样会因为没有分布式事务的保障，出现缓存中存在脏数据的问题。
- **实施层面容易遗漏**：更新数据库后主动更新缓存的模式，需要在所有更新数据库的地方都加上主动更新缓存的代码。当开发人员不断变更时，很容易出现遗漏——比如某一个需求里只更新了数据库而没有更新缓存。
- **成本较高**：在所有更新数据库的地方，都利用缓存和数据库的分布式事务来保证数据完全一致的成本较高；实际工作中，成本是必须考虑的问题。针对遗漏问题的更简单解决方案在后续文档中介绍。

### 4. 懒加载无法摆脱毛刺的困扰

**问题**：使用懒加载的缓存过期方案，还有一个无法避免的问题——性能毛刺。当缓存过期时，读服务的请求都会穿透到数据库中；穿透请求的性能和使用缓存的性能差距非常大，时常是毫秒和秒级别的差异。

大部分普通业务场景可以容忍此问题，但在一些对性能要求极高的场景里（比如 App 首页），毛刺问题仍需重视和解决。此问题的解决方法在后续文档中讲解。

::: tip 结论
懒加载架构的四个问题及对应的潜在解决方案各有取舍。虽然懒加载架构存在一些问题，但在实际应用中，此方案及其变种方案因为**实现简单、成本低**，仍是使用较多的解决方案。
:::

## 小结

读服务在实现时应满足的技术功能性要求：高可用、高性能（TP999 < 100ms）、超高 QPS。实现时应遵守两个基本原则：

- **架构尽量不要分层**：读服务尽可能和数据靠近，减少网络传输（数据访问层编译进读服务进程；浏览器缓存、CDN 等数据前置手段同理，但需接受数据更新不及时）。
- **代码尽可能简单**：少引入框架（引入必压测）、日志精细化按需打印、存储处按需取数。

在此原则之上，实战中常见的架构方案是 Redis 主存储 + MySQL 兜底的懒加载模式，其四点不足及应对为：缓存穿透（占位符 + 参数前置校验）、缓存集中过期雪崩（过期时间加盐）、无法感知实时变更（主动更新缓存，但有一致性与遗漏问题）、毛刺困扰（待深入解决）。

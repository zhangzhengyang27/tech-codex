# 如何基于流量回放实现读服务的自动化测试回归？

## 概念说明

读服务的系统架构方案（懒加载缓存、全缓存、数据同步等）可以直接落地使用，支撑百万并发。但升级系统架构时，有一个很容易被研发忽略的问题：**只评估了升级的工作量就直接开干**，最后提测时发现**改造范围太大**、**测试根本回归不完**、**升级重构上线遥遥无期**。

随着业务发展，系统升级重构不可避免，但同时也带来巨大的测试回归量。解决方案是一套**自动化的测试回归架构方案**：它能极大降低读业务因升级重构带来的回归问题，还能适配日常需求上线的回归工作量，真正做到**回归自动化、研发自助化，避免用户场景全覆盖遗留导致漏测的问题**。

## 核心要点

- 读服务能实现测试回归自动化有两个前置条件：**读服务无状态**（每次请求无副作用、可重复，同样入参在后台数据无变化时多次重试结果一致）、**对外接口出入参格式不变**（无论架构升级还是日常需求）。
- 自动化回归架构包含三大模块：**日志收集**（收集真实用户请求，按规则处理后作为系统用例）、**数据回放**（基于用例实时调用被测系统并存储返回出参）、**差异对比**（自动发现与预期不一致的用例，确定 Bug）。
- 日志收集可通过成熟的过滤器实现（Spring Interceptor、Servlet Filter 等），出入参经 MQ 发送；标识数据存数据库，入参出参（数据量大）存 NoSQL（如 HBase），并做过滤、去重、无效数据定期清理；压测等非业务场景需关闭采集。
- 过滤器与业务同进程会占用内存且具侵入性；可升级为**独立采集进程**监控日志文件——业务应用按格式打印出入参日志到指定文件，采集进程监控文件变化发送至 MQ，并可对其设置内存/CPU 限制与资源占用报警。
- 差异对比采用**文本（JSON）形式**而非二进制校验和：可直观看到哪个字段数据有差异，更快定位问题；对比工具需具备**忽略能力**（如忽略每次请求生成的唯一标识字段）。
- 回放有三种模式：**离线回放**（只调新服务对比历史出参，省资源但数据变更后不可比）、**实时回放**（只录不入参，手动触发后新老版本同参数实时对比，规避数据变更）、**无录制的实时回放**（不录制，日志消费即实时调用对比，长时间回放基本覆盖全部场景）。
- ⚠️ 注意事项：回放时**写接口一定要屏蔽**（避免产生垃圾数据）；实时类回放**会给线上系统带来流量压力**，可能打挂性能差或机器少的系统；覆盖率工具（如 Java 的 JaCoCo）可辅助判断是否存在漏测。

## 为什么要自动化？

### 场景一：架构升级

不管是因为技术还是业务导致的系统重构架构升级，改造量和范围都是非常大的。此类系统级重构的测试回归工作量至少以月为单位，人力消耗巨大。两种常见应对方案都很难实施：

- 先不改造，到系统实在扛不住了再想办法；
- 先暂停需求，全力进行改造。

### 场景二：日常需求

后台系统基本都是微服务架构，对外提供一至多个接口。一般一个需求只涉及一个或几个接口的某些场景修改，测试通常只对改造的接口及对应场景进行测试。

但在实际案例里，需求涉及的接口或场景上线后均不出现 Bug，而**同一个服务里其他未涉及修改的接口比较容易出现 Bug**——虽然对外接口不同，但底层逻辑很可能复用了相同的代码，导致相互影响。为避免此情况，任何一个需求都需要回归所有接口，工作量巨大。

针对上述问题，通过自动化的方式提升效率是必然选择。

## 如何实现自动化回归？

### 基本原理：两个前置条件

**1. 读服务均是查询，它是无状态的。**

无状态是指每次请求都是**无副作用的**、**可以重复的**。同样的请求入参，在后台数据无变化的情况下，多次重试的结果均一样。相比而言，写或扣减业务就不行——比如用户余额变化会产生副作用：上一次购物订单支付成功后，第二次使用同样的金额进行支付就不一定能成功，因为上一次的支付产生了副作用，用户余额减少了，导致此次支付不成功。

**2. 不管是架构升级还是日常需求，读服务对外接口的出入参格式是没有变化的。**

不管服务内部的逻辑如何变化，只要接口出入参格式不变，就可以利用读服务的无状态特性进行流量回放。

### 整体架构

读服务自动化测试回归的整体架构包含三大模块：**日志收集、数据回放、差异对比**。它们的分工如下：

- **日志收集**：收集被测系统的真实用户请求，基于一定规则处理后作为系统用例；
- **数据回放**：基于收集的用例，对被测系统进行数据回放，发起自动化测试回归；
- **差异对比**：类似人工测试发现 Bug 的过程，通过差异对比自动发现与预期不一致的用例，进而确定 Bug。

## 模块一：日志收集

### 过滤器采集方案

不管是提供 HTTP 形式还是 RPC 形式接口的后台读服务，都可以通过比较成熟的过滤器进行日志收集，比如 Spring 里的 Interceptor 拦截器、Servlet 里的 Filter 过滤器等。

在过滤器中，会对所有请求的入参和出参进行记录，并通过 MQ 发送出去。记录的数据格式类似如下：

```
{"应用名":"XXX","接口方法名":"RPC记录的接口方法名/HTTP记录域名及路径","入参":"XXX","出参":"XXX"}
```

对于发送出去的 MQ 消息，自动化回归的消费服务会按应用和接口进行处理：

- 应用和接口方法的标识数据存储在数据库里；
- 入参和出参存储在 NoSQL 里（如 HBase）——出入参数据量较大，存储在数据库里查询性能会比较差。

**数据治理**：即使将参数存储在原生支持分布式的 NoSQL 里，也要对采集的日志进行过滤、去重以及无效数据定期清理等操作。此外，对于压测等非业务场景，需要关闭日志采集——日常业务请求带来的数据量可能一天上亿或十几亿次，不做管控的话存储消耗巨大。

### 独立采集进程方案

当前日志收集采用的过滤器与业务应用同属一个进程，会占用业务应用的内存资源，对业务也存在一定的侵入性。此时可以将日志收集独立出来，采用单独进程运行：

- 业务应用按上述格式将出入参日志打印到指定文件；
- 单独的数据收集进程监控该文件，并将变化数据发送至 MQ；
- 在操作系统里，可以单独对采集进程设置资源占用限制（内存、CPU 等），并配置资源占用报警，保证业务应用不被日志采集影响。

## 模块二：数据回放

数据回放的主要作用：基于日志里记录的接口信息（HTTP 便为域名）和入参，实时调用被测系统，并存储实时回放返回的出参信息。

- HTTP 形式的接口：采用主流的 HTTP 客户端即可；
- RPC 形式接口：需要使用该 RPC 框架提供的、能够调用任意被测接口的客户端。

## 模块三：差异对比

### 为什么采用文本对比

完成数据回放后，对回放产生的结果数据与预期数据（比如收集日志里的出参）进行比较。数据对比有很多形式，比如基于二进制校验和、基于文本等：

- 二进制校验和只能判断数据是否整体一致，不会展示具体哪里不一致；即使展示了，因为是二进制，人工也无法查看。
- 文本形式先将数据转换为 JSON 格式再对比：可以看到数据整体不一致，以及具体是何处导致的不一致。

例如同一个 SKU 的名称在两边出现不一致——如果只是进行了系统重构，相同 SKU 对应的数据应该一样，此处出现不一致即代表出现了 Bug。**采用文本对比，可以直观地看到哪个字段数据有差异，从而更快定位到问题**。

**判定规则**：正常情况下，只要存在差异的数据，均可认为是 Bug，需要进行修复。但有些时候——比如接口会对每次请求产生一个唯一标识，用于打印日志并返回给调用方——差异对比时此类接口每次都会因唯一标识不同而出现差异，但此差异不会对业务产生影响。对于此类场景，需要差异对比工具具备**忽略能力**，在对比时忽略唯一标识字段。

通过数据收集、回放和差异对比，能够实现自动化、可视化，将读业务的测试回归完全自动化。

## 回放的三种模式

### 1. 离线回放模式

回放时只调用进行改造的新服务，将新服务返回的数据与收集日志里的出参进行比较。

**优点**：减少对线上老版本的调用量，避免对线上产生影响，也节约资源。

**局限**：如果后台存储中的数据已经发生变化，就不能使用收集日志里的出参——存储数据已变化，历史日志里的出参已过时，与新版本实时查出的数据不具备可比性。

### 2. 实时回放模式

为解决离线回放中"数据变化导致历史出参无效"的问题，采用实时回放模式：收集的日志里只记录入参、不记录出参；研发或测试手动触发回放功能后，使用入参实时调用新老版本的被测应用，对比双方返回的出参。此方式可以规避数据变更的问题。

### 3. 无录制的实时回放模式

离线回放和实时回放都存在一个问题：需要对接口的入参进行录制（存储至 NoSQL，如 HBase）再回放。因存储容量有限，只能存储一定数量的数据，很多日志用例可能会被丢弃，可能导致重要场景漏测。

无录制的实时回放模式不再记录入参数据：日志消费模块接收到收集的日志用例后，实时调用新老版本被测服务并进行数据对比。使用此方式持续回放几周或更久，基本能够覆盖全部场景。

## 注意事项

在线上部署及使用自动化回归工具时，需要注意与规避以下几点：

- **在进行自动化回归时，写接口一定要屏蔽**。以注册用户举例：如果回放时没有屏蔽，使用线上入参进行回放，将会产生很多垃圾用户，给后续业务流程带来巨大影响。
- **实时回放模式和无录制的实时回放模式都会对线上系统产生一定的流量压力**（离线模式除外）。假设被测系统性能比较差或机器数较少，自动化回放的流量会把线上系统打挂，进而影响业务可用性。特别是无录制的实时回放模式，带来的流量更大且持续时间更长。
- 即使采用了无录制的实时回放模式，也只是通过更长时间的回放尽可能覆盖更多业务场景，并没有足够证据表明一定不会漏测。**可以借助代码覆盖率工具（如 Java 里的 JaCoCo）统计一次回放后被测系统的代码覆盖率，通过数据来判断是否存在可能的漏测**。

## 小结

读业务在系统重构及日常需求开发时，均存在**测试回归耗时长**和**可能存在漏测**的问题。根据读业务无状态及可重复执行的特点，可以构建一套**基于业务日志的自动化回归平台**，主要包含三大子模块：日志采集、数据回放及差异对比。

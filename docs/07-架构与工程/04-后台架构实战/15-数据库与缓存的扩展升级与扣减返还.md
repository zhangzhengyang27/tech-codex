# 数据库与缓存的扩展升级与扣减返还

## 概念说明

本文讨论扣减方案中涉及的两个公共话题：**异步任务的设计**和**扣减中的返还的设计**。

在[如何利用缓存+数据库构建高可靠的扣减方案](/docs/架构与工程/04-后台架构实战/14-%E5%A6%82%E4%BD%95%E5%88%A9%E7%94%A8%E7%BC%93%E5%AD%98+%E6%95%B0%E6%8D%AE%E5%BA%93%E6%9E%84%E5%BB%BA%E9%AB%98%E5%8F%AF%E9%9D%A0%E7%9A%84%E6%89%A3%E5%87%8F%E6%96%B9%E6%A1%88%EF%BC%9F)和[如何打造无状态的存储实现随时切库的写入服务](/docs/架构与工程/04-后台架构实战/09-%E5%A6%82%E4%BD%95%E6%89%93%E9%80%A0%E6%97%A0%E7%8A%B6%E6%80%81%E7%9A%84%E5%AD%98%E5%82%A8%E5%AE%9E%E7%8E%B0%E9%9A%8F%E6%97%B6%E5%88%87%E5%BA%93%E7%9A%84%E5%86%99%E5%85%A5%E6%9C%8D%E5%8A%A1%EF%BC%9F)里，均使用了异步任务（Worker）来做无状态存储到正式业务库的数据同步，但具体如何设计异步任务以保证高可用、如何设计任务的执行以保障执行速度、避免任务积压，需要专门展开。此外，前述扣减方案只涉及扣减的正向流程，本文同时覆盖扣减后可能发生的返还过程中涉及的技术点。

## 核心要点

- 无状态存储集群的数据同步任务，最简单的实现是**每个分库启动一个自循环 Worker**；但单 Worker 单库方式**不具备扩展性**（任务积压无法靠扩容解决）且存在**单点问题**。
- 可扩展、高可用的任务架构：**每个分库配置多个并发 Worker，基于哈希环自主协调**——Worker 启动时按机器 IP、随机数、时间戳组合计算唯一串，再哈希为无符号整型值，上报到强一致的 etcd/ZooKeeper 集群。
- 借助 etcd/ZK 的**通知功能（Watch）**，每个 Worker 订阅同分库其他 Worker 的哈希值，哈希值组成环形区间（类似一致性 Hash），每个 Worker 负责任务 ID 落在其区间内的任务。
- Worker 故障或扩容时，通过 etcd/ZK 通知机制，所有其他 Worker 立即感知并更新各自负责的任务区间。
- ⚠️ 扩缩容间隙可能出现两个 Worker 获取到同一条任务：一方面**任务执行保持幂等**（业务上可重复执行），另一方面**任务增加状态字段**，获取任务时显式指定只处理"待执行"状态。
- 扣减的返还：扣减完成后业务上发生逆向行为（取消订单、退换货），原先已扣减的数据需要恢复。
- **返还的并发量远低于扣减**（可相差上万倍），实现上可直接基于数据库落地。
- 返还四原则：**扣减完成才能返还**（必须带扣减号）；**一次扣减可多次返还**（返还记录表 + 返还商品记录表两张表设计）；**返还总数 ≤ 原始扣减数**（返还前对扣减 ID 加锁串行化，防并发超返还）；**返还要保证幂等**（返还编号 + 数据库唯一索引防重）。

## 一、实现无主架构的任务

### 方案一：每个分库一个自循环 Worker

对于无状态存储集群的数据同步任务，最简单的实现方式是**对每一个分库启动一个自循环的 Worker**。

自循环的 Worker 在启动时，会开启一个不跳出的循环，或者借助一些开源工具（如 Java 中比较出名的 Quartz）保证任务不间断执行。在上述循环内，会使用类似如下的 SQL 批量获取未执行的任务或未同步的数据并执行同步，任务执行成功后修改任务状态为"完成"：

```
select task_id,task_body,... from t_task where id>lastId and status='未执行' limit 一批数量 order by task_id
```

上述流程在功能上能够满足需求，但在高可用及性能上存在不足：

- 如果任务库中任务特别多，单 Worker 单库的方式**不具备扩展性**：随着任务不断变多，会出现任务积压的瓶颈，且无法通过扩容解决；
- 单库单 Worker 的方式**存在单点问题**：执行过程中 Worker 发生故障宕机时，如果没有监控等机制发现故障，Worker 得不到执行，任务就会一直积压。

### 方案二：多 Worker 哈希环自主协调（无主架构）

针对上述两个问题，有一种既提升任务执行速度、又具备扩展性、还能保障高可用的任务架构模式。

每个分库对应的 Worker 的执行流程都类似，以单个分库为例（其余以此类推）：

- 为提升性能和高可用，**单个分库的执行 Worker 配置多个并发执行**；
- 单个分库的多个 Worker 在执行时**使用自主协调**，协调流程如下。

**（1）计算哈希值**：每个 Worker 在启动时，根据机器的 IP、随机数、当前时间戳等进行组合拼接计算一个唯一串，再在此基础上使用各种哈希工具计算一个**无符号整型哈希值**。

**（2）上报哈希值**：所有的 Worker 会将自己的无符号整型哈希值上报到强一致的 etcd 或 ZooKeeper 存储集群里。

**（3）订阅通知**：**etcd 等集群具备通知功能（Watch）**。借助通知功能，所有的 Worker 都去订阅某一个分库下的其他 Worker 的哈希值——比如一个新的 Worker 启动了，或者扩容新增了一个新的 Worker。

**（4）构建哈希环**：每一个 Worker 都会获取到当前分库的所有其他 Worker 的哈希值。假设一个分库配置了四个 Worker，其中一个 Worker 会获取到自己及其他三个 Worker 的哈希值，假设为 {200，300，500，800}。这四个 Worker 的 Hash 值便组成了一个**环形区间**。

这个环形区间就类似一致性 Hash：每一个结点都代表一个 Worker，这个 Worker 负责任务编号在它区间范围内的任务的执行。

**（5）任务分配**：有了上述哈希值列表后，就可以做任务分配了。如果当前 Worker 的哈希值为 300，那么当前 Worker 就处理任务 ID 在区间 [200,300) 里的值。比如哈希值为 200 的 Worker 则执行区间为 [800,无穷大) 和 [0,200) 的任务（即任务编号大于等于 800 和处在 [0,200) 区间内的任务），其他以此类推。区间处在 [200,300) 的 Worker 获取任务的 SQL 大致如下：

```
select * from task where id>=200 and id<300 and status='待执行' order by id limit 100;
```

### 扩缩容与故障感知

通过上述方式，无论是某一台 Worker 发生故障还是新扩容一台 Worker，通过 etcd 和 ZK 的通知机制，所有其他 Worker 都可以立刻感知，并更新自己所负责的任务区间。

例如四个 Worker 哈希值为 {200，300，500，800} 的案例里，哈希值为 300 的那个 Worker 发生故障时，哈希值列表就从 {200，300，500，800} 变成 {200，500，800}，此时负责 500 的 Worker 就会执行 [200,500) 这个区间里的所有任务；扩容 Worker 的流程与之类似。

### 临界并发：两个 Worker 获取到同一条任务

在 Worker 扩缩容的间隙里，可能存在临界的并发情况，即两个 Worker 可能获取到同一条任务。可以从两点着手解决：

- 首先，**任务执行需要保持幂等**，即任务可重复执行，可以从业务上着手实现；
- 其次，**可以给任务增加状态**（如上述 SQL 里的 status 字段）：当某一个 Worker 处理到该任务时，可以将该任务修改为"处理中"；其他 Worker 在获取任务时显式指定状态，只处理"待执行"的任务即可。

## 二、扣减返还的设计与实现

### 什么是扣减的返还

**扣减的返还指的是在扣减完成之后，业务上发生了一些逆向行为，导致原先已扣减的数据需要恢复以便供后续的扣减请求使用的场景**。

以购买商品时的扣减库存为例，常见的逆向行为有：

- 客户下单之后，发现某个商品买错了（商品品类买错或数量填错），客户取消订单，此时该订单对应的所有商品的库存数量都需要返还；
- 客户收到订单后，发现其中某一个商品质量有问题或功能与预期有差异，发起订单售后流程（如退、换货），此时该订单下被退货的商品需要单独进行库存返还。

### 返还实现原则

从业务场景可以看出，**相比扣减而言，返还的并发量比较低**——下单完成后发生整单取消或个别商品售后的概率较低。热点商品或爆品抢购带来的扣减并发量非常大，但抢到爆品后再取消订单的概率非常低；此类场景里，扣减和返还的并发量差距可能达到上万倍。

因此，返还在实现上可以参考商家对已有商品补货的实现，**直接基于数据库进行落地**。但返还自身也具备一些需要注意的实现原则，可总结为以下四点。

**原则一：扣减完成才能返还**

**返还接口在设计时，必须要有扣减号这个字段**。因为所有的返还都是依托于扣减的，如果某一个商品的返还没有带上当时的扣减号，后续很难对当时的情况做出准确判断：

- **当前商品是否能够返还**：没有扣减号，无法找到当时的扣减明细，无法判断此商品当时是否做了扣减——没有做扣减的商品是无法进行返还的。
- **当前返还的商品数量是否超过扣减值**：假设外部系统因为异常，传入了一个超过当时扣减值的数量，如果不通过扣减号获取当时的扣减明细，无法判断此类异常。

**原则二：一次扣减可以多次返还**

案例：一个订单包含 A、B 两件商品，各买 5 件，产生购买订单时即对应一次扣减。后续使用过程中可能会对某件不满的商品发起售后退货申请。极端情况下可能发生三次退货行为：

1. 第一次，先退 2 个 A；
2. 第二次，再退 3 个 B；
3. 最后一次退货，一起将剩余的 3 个 A 和 2 个 B 退回。

由此案例可以看出，**一次扣减（即一个订单）在业务上可以对应多次返还**，实现时需要考虑多次返还的场景。支持多次返还的数据库表设计如下：

```
create table t_return (
  id bigint not null comment '自增主键',
  occupy_uuid bigint not null comment '扣减的ID',
  return_uuid bigint not null comment '返还的唯一ID',
  unique idx_return_uuid (occupy_uuid,return_uuid) comment '返还标识唯一索引'
) comment '返还记录表';
create table t_return_detail (
  id bigint not null comment '自增主键',
  return_uuid bigint not null comment '返还标识',
  sku_id bigint not null comment '返还的商品ID',
  num bigint not null comment '返还的商品数量',
  unique idx_return_sku (return_uuid,sku_id) comment '返还商品唯一标识'
) comment '返还商品记录表';
```

上述**返还记录表**实现了一次扣减多次返还的数据记录；**返还商品记录表**实现了一次返还里有多个商品的场景（即上述案例里最后一次一起退了 A 和 B 两个商品的场景）。

**原则三：返还的总数量要小于等于原始扣减的数量**

从业务上看这是一个必要条件，但真正实现时很容易出现处理遗漏。仍以原则二的案例讲解：并发返还时，同一时刻有两个返还请求，一个请求返还 2 个 A，另一个请求返还 4 个 A。如果技术上没有并发的时序控制，处理两个请求时有可能都判断为可返还并实际进行返还，最终就会出现返还 6 个 A（实际当时只扣减了 5 个）的**超返还**场景。

**应对方案**：在返还前，对返还所属的扣减 ID 进行加锁来保证串行化操作，规避超返还的风险。

在扣减 ID 上加锁，会导致该扣减 ID 下的所有返还都串行执行，有一定的性能损耗。但从业务上看，同一个扣减 ID 并发产生返还的场景极低且返还的调用次数相对较少——从"架构是技术与业务场景的取舍"这个角度来看，暂不需要花费太大的人力构建一个更加复杂的加锁架构。

**原则四：返还要保证幂等**

设计的返还接口需要支持幂等性。比如外部系统调用返还接口超时后，因为外部系统不知道是否调用成功，就会再一次重试。如果返还接口不满足幂等性要求，且上次超时实际是执行成功的，则会导致同一个返还号产生两次数据的返还。

处理这个问题最简单的做法：**在返还接口增加返还编号（上述表结构中的 return_uuid）字段并由外部系统传入，通过数据库唯一索引来防重，进而实现幂等性**。

## 小结

本文讲解了各种扣减方案里都会涉及的**任务执行**和**扣减返还**两个公共话题。无论业务场景采用哪种扣减方案，都可以参考上述返还和任务执行方案：

- **异步任务**：从单库自循环 Worker 演进到多 Worker 哈希环自主协调（etcd/ZK Watch 通知 + 任务区间动态分配），兼顾扩展性与高可用；用幂等与状态机兜底扩缩容间隙的临界并发。
- **扣减返还**：并发量低、基于数据库落地；遵循"扣减完成才能返还、一次扣减可多次返还、返还总数不超扣减数（扣减 ID 加锁）、返还幂等（返还编号 + 唯一索引）"四原则。

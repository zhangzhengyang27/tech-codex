# 如何做好微服务间依赖的治理和分布式事务？

## 概念说明

微服务依赖治理准则共三条：**防备上游、做好自己、怀疑下游**。前两条从微服务的对外接口、消息消费以及微服务自身的相关编码规范上落地；本文讲解为什么要"**怀疑下游**"，以及有哪些手段可以落地此条准则。此外，还介绍微服务拆分后，调用外部依赖会产生的分布式事务、消息发送等问题的应对方案。

## 核心要点

- 微服务依赖的其他微服务接口、数据库、缓存及消息中间件，可能因代码 Bug、网络、磁盘故障、上线操作失误等因素引发线上问题；依赖不可用会导致接口可用率下降或直接宕机。**预先假设下游出现故障并设计对应方案，就是在实践"怀疑下游"**。
- 三大类依赖的治理对象：其他微服务、数据库、消息中间件。
- 对其他微服务：依赖后置、依赖并行化、设置超时和重试、服务降级等写服务治理手段同样适用于读服务；微服务化后的分布式事务可用**任务表补偿方案**（类似 TCC/Saga 思想、无须第三方框架）解决。
- 任务表方案的可靠性来源：**任务表与业务表同库**，靠本地事务保证"业务写入成功 → 任务状态必更新为已成功"；失败场景由异步补偿 Worker 返还资源，保证最终一致性；该模式可复用在其他存在分布式事务的场景。
- 数据库依赖四原则：**必配从库且跨机房部署**（测试环境同样要主从复制）；**SQL 尽可能简单**；**业务迭代快的场景不用外键**；**避免用上千长度的 varchar 存 JSON**（并发更新丢失）。
- 消息中间件依赖四原则：**先写数据库/缓存再发消息**（防消费方反查不到数据）；**消息带版本号**（防乱序消费数据错乱）；**消息数据尽可能全**（减少消费方反查，保持解耦）；**消息包含字段级变更标识**（防无效通知）。

## 为什么要怀疑下游

微服务会依赖很多其他微服务提供的接口、数据库、缓存，以及消息中间件等（可回顾[如何设计一锤子买卖的 SDK](/docs/架构与工程/04-后台架构实战/17-%E5%A6%82%E4%BD%95%E8%AE%BE%E8%AE%A1%E4%B8%80%E9%94%A4%E5%AD%90%E4%B9%B0%E5%8D%96%E7%9A%84%20SDK%20%EF%BC%9F)里介绍过的抽象的微服务架构）。这些接口及存储可能因为代码 Bug、网络、磁盘故障、上线操作失误等因素引发线上问题；由于依赖不可用，微服务对外提供的服务会受到影响，出现接口可用率下降或者直接宕机的情况。

为防止上述情况发生，在构建微服务时，就需要预先考虑所依赖的各项"下游"出现故障时的应对方案。**假设下游出现故障并预先设计对应方案的过程，便是在实践"怀疑下游"**。

## 如何落地

针对三大类依赖——其他微服务、数据库、消息中间件，逐一给出故障应对方案和使用准则。

### 对其他微服务的依赖

采用微服务架构后，各模块间均通过 RPC 方式依赖，有些模块完成一项业务流程时可能依赖多达几十、上百个外部微服务。比如完成下单流程，需要依赖用户、商品、促销、价格、优惠券等各个微服务提供的接口，这些被依赖微服务的稳定性直接影响用户能否成功下单。因此，需要对微服务依赖的其他微服务接口进行可用性治理。

此前已从写服务的角度介绍了通过**依赖后置、依赖并行化、设置超时和重试、服务降级**等手段对依赖进行治理、保障写服务高可用的方法，详见[如何利用依赖管控来提升写服务的性能和可用性](/docs/架构与工程/04-后台架构实战/10-%E5%A6%82%E4%BD%95%E5%88%A9%E7%94%A8%E4%BE%9D%E8%B5%96%E7%AE%A1%E6%8E%A7%E6%9D%A5%E6%8F%90%E5%8D%87%E5%86%99%E6%9C%8D%E5%8A%A1%E7%9A%84%E6%80%A7%E8%83%BD%E5%92%8C%E5%8F%AF%E7%94%A8%E6%80%A7%EF%BC%9F)。这些手段同样可以用在读服务里，可回到[如何利用依赖管控来提升写服务的性能和可用性](/docs/架构与工程/04-后台架构实战/10-%E5%A6%82%E4%BD%95%E5%88%A9%E7%94%A8%E4%BE%9D%E8%B5%96%E7%AE%A1%E6%8E%A7%E6%9D%A5%E6%8F%90%E5%8D%87%E5%86%99%E6%9C%8D%E5%8A%A1%E7%9A%84%E6%80%A7%E8%83%BD%E5%92%8C%E5%8F%AF%E7%94%A8%E6%80%A7%EF%BC%9F)复习。

#### 分布式事务的实际场景：提单案例

微服务架构下，订单和库存是两个单独的微服务。提单时，订单模块需要调用库存模块进行商品扣减，以判断用户购买的商品是否有货。订单调用库存的扣减接口会出现以下几种情况：

- 调用库存接口返回成功且库存数量充足，订单模块将此用户订单保存至数据库，并返回用户下单成功消息。
- 调用库存接口返回成功且库存数量充足，但订单模块将此用户订单保存至数据库时出错并进行数据库回滚，同时订单模块返回用户下单失败。
- 调用库存接口超时，订单模块判断此次调用库存接口失败，返回用户下单失败。
- ……

微服务化之后，订单模块和库存模块的交互会产生非常多的可能性场景。其中第 2、3 点描述的场景存在**分布式事务问题**：第 2 点里，订单模块本地的数据库事务回滚了，但调用库存接口产生的已扣减商品数量并没有回滚，导致库存数据少于实际数据。

有一些基于 TCC 和 Saga 的成熟基础框架可以解决上述分布式事务问题，但理解和接入成本较高。此处介绍一种与 TCC、Saga 理念相类似、无须借助第三方框架的简单易落地方案；理解此方案也有助于理解 TCC 和 Saga 的思想。

#### 任务表补偿方案

**架构**：订单模块的数据库里，除了订单原有的表之外，增加一张任务表。基于此架构，下单流程变更如下。

**步骤 1**：接收到下单请求后，在调用任何外部 RPC 前，先将此订单的相关信息——此次用户购买的商品、商品数量、用户账号、此次订单的编号等——写入新增的任务表中。

**步骤 2**：调用库存接口进行商品数量扣减，并根据库存模块的返回值更新订单模块的数据库。细分为以下场景：

- （1）如果调用库存接口**成功**，则在同一个事务中，将订单信息写入订单库，同时更新第一步写入任务的状态为"**已成功**"；
- （2）如果调用库存接口明确返回**失败**，则直接更新订单库中的任务状态为"**待回滚**"，并返回用户下单失败；
- （3）如果调用库存接口**超时**，则直接更新订单库中的任务状态为"**待回滚**"，并返回用户下单失败；
- （4）无论调用库存接口**是成功还是失败**，只要在更新本地订单库时失败，就返回用户下单失败，同时任务库的状态保留为"**初始化**"。

**步骤 3（异步补偿）**：下单完成后，异步 Worker 功能扫描订单库新增的任务表，获取状态为"**待回滚**"的任务，以及任务创建时间距扫描时间点超过一定时间区间（如 5 分钟）仍为"**初始化**"状态的任务；获取到这些任务后，基于任务表中的商品和对应数量信息，异步调用库存接口进行商品数据的返还。

**原理与可靠性**：

- 通过上述方式，能够将各种失败场景里漏返还的商品数量进行返还，保证库存数量的最终一致性，完成分布式事务。
- 最终一致性主要依赖**任务表和订单表在同一个数据库里**：可以通过本地事务保障"订单表数据写入成功后，任务表里的任务状态绝对能够更新为已成功"。
- 提单失败后，任务表状态为"非成功"状态，再通过类似 TCC 和 Saga 的异步补偿性 Worker 进行业务回滚，保证最终一致性。

::: tip 方案的复用性
**在发起分布式事务的业务模块的数据库里创建补偿性任务，基本上可以复用在其他存在分布式事务的场景里**。如果不希望引入更加复杂的 TCC 和 Saga 框架，可以尝试利用此方式解决架构微服务化之后带来的分布式事务问题。
:::

### 对数据库的依赖

除对其他微服务的依赖外，微服务中最常见的便是对数据库的依赖。使用时需遵守以下基本原则。

**原则一：数据库一定要配置从库，且从库部署的机房需要与主库不同，从而保障数据库具备跨机房灾备的能力。**

此外，测试环境的数据库依然要配置主从复制，防止某天测试环境的数据库磁盘损坏、需要耗费大量人力恢复测试环境。

**原则二：在能够完成功能的前提下，使用的 SQL 要尽可能简单。**

SQL 和代码一样，除完成功能之外，最重要的是清晰简单地表达自身含义，以供后续研发人员维护。曾经在线上遇到过为了不使用唯一索引、纯使用 SQL 完成防重的语句，它包含了四层 insert、select、exists、select 的语法嵌套。这一语句因为无法调试（Debug），导致后续一个需求的上线时间延期了 2 天，最终还是痛定思痛地进行了重构。

**原则三：在业务需求不断更新迭代的场景里，最好不要使用外键。**

数据库理论中，使用外键校验数据完整性：A、B 表之间建立外键约束后，可以设置外键级联删除——A 表中某条数据删除后，自动级联删除 B 表中的数据。此方式表面上极大地简化代码操作，实则隐藏巨大风险：现今互联网需求迭代速度非常快，上个月 A、B 表中还存在外键关系，下个月可能就因需求不存在了，或者需要更多字段组合才能形成外键关系。

此外，外键关系隐藏在数据库的建表语句里，新需求开发时很容易被遗忘、清除或者修改为新的外键关系。新需求上线后，也可能因疏漏导致线上数据被误删，进而引发线上问题。

**原则四：表结构中尽可能不要创建一个长度为上千或上万的 varchar 类型字段，且用其来存储类似 JSON 格式的数据，因为这会带来并发更新的问题。**

假设创建了一个长度一千的 varchar 字段，它存储了如下的信息：

```
{"fieldA":"valueA","fieldB":"valueB"}
```

此时假设有两个请求**同时**对此字段进行修改——A 线程将此字段的值读取后修改了其中 fieldA 的值：

```
{"fieldA":"valueAA","fieldB":"valueB"}
```

B 线程将此字段的值读取后修改了其中 fieldB 的值：

```
{"fieldA":"valueA","fieldB":"valueBB"}
```

最终数据库中此字段的值是什么？答案是不一定，取决于 A、B 两个线程的最终修改顺序。但不管顺序如何，最终结果都是错误的：A、B 两个线程各修改了 JSON 内容的其中一个字段，最终期望 fieldA、fieldB 两个字段都得到更新，但实际只会有一个字段得到更新（并发更新丢失）。

因此，创建表结构时不建议设置此类型字段。如果期望两个子字段都得到更新，需要借助**并发锁**实现，但这也增加了代码实现的难度。

### 对消息中间件的依赖

微服务架构里，微服务间通信除接口调用外，当前最常见的方式是基于消息中间件（如 RabbitMQ 和 Kafka）的消息通信。使用消息中间件时，仍有一些基础原则需要遵守。

**原则一：数据要先写入数据库或缓存后，再发送消息通知。**

很多消息接收方在接收到消息通知后，会调用发送消息的微服务的接口进行数据反查，以获取更多信息做下一步业务流转。

案例：订单模块判断用户的下单请求的库存能够满足后，便向外发送下单成功的消息。如果物流系统监听了此消息，就会在获取到下单成功通知后，第一时间去反查订单接口，获取更多订单相关信息（如用户期望的收货时间、用户是否为会员等）辅助判断何时发货。极端情况下，可能因订单模块的数据还未写入数据库，导致反查不到数据，进而影响业务正常流转。

**原则二：发送的消息要有版本号。**

有些消息中间件为了提升消息消费的吞吐量，支持乱序消费。但如果发送的消息没有数据变更版本号，消息消费方会因此无法判断数据是否乱序，进而可能导致数据错乱，产生线上问题。

**原则三：消息的数据要尽可能全，进而减少消息消费方的反查。**

微服务间使用消息通信的目的就是解耦。如果消息中包含的信息量太少，消息消费方就无法基于其中的信息处理业务，需要反查发送方的接口获取更多信息——这样就达不到解耦的目的了（可参考原则一物流系统的案例）。因此，在可能的情况下，建议发送尽可能全的信息。

**原则四：消息中需要包含标记某个字段是否变更的标识。**

根据原则三，消息可能包含较多字段，其中有些字段在当次消息中并未发生数据变更。如果没有标记字段是否变更，可能会产生无效通知。

案例：一个消息包含两个字段（如 A、B），而某一个消息接收方（如用户模块）只关心 A 字段是否变更。如果没有标记变更字段，B 字段变更后消息发送方也会发送消息，这会导致"用户模块"误以为 A 字段发生了变更，进而触发"用户模块"执行一次本不应该执行的业务流程。

## 小结

本文介绍了采用微服务架构后不可避免的分布式事务的解决方案（任务表补偿方案），以及微服务常见依赖（数据库、消息中间件）的基本治理原则：

| 依赖类型 | 治理要点 |
|---|---|
| 其他微服务 | 依赖后置、并行化、超时重试、服务降级；分布式事务用任务表补偿（同库本地事务 + 异步 Worker） |
| 数据库 | 主从 + 跨机房；SQL 简单；少用外键；避免 varchar 存 JSON |
| 消息中间件 | 先写库再发消息；消息带版本号；数据尽可能全；带字段变更标识 |

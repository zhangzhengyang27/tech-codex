# 开篇词 Serverless 大热，程序员面临的新机遇与挑战

## 背景与问题

2017 年国内 Serverless 技术刚刚兴起时，一个典型的落地场景来自前端中后台系统研发：后端为了方便扩展把接口设计得很原子化，导致前端渲染一个页面要发几十个请求，前后端联调痛苦、沟通成本高、开发效率低。

为了提升前端开发效率和页面加载性能，常见的做法是用 Node.js 开发 BFF（Backend for Frontend）应用做接口的聚合裁剪。可随着接入的系统增多，BFF 应用数量和复杂度日趋上升，不仅消耗大量机器，还导致前端运维成本急剧增高，经常需要排查服务器问题。

引入 Serverless 来实现 BFF 层之后，前端从运维中解放出来，同时也减少了不必要的机器资源浪费——这正是 Serverless 解决“效率与成本”两大问题的一个缩影。

## Serverless 时代已来临

Serverless 并不是最近两年才兴起的技术：概念从 2012 年就提出来了，随后 AWS 在 2014 年推出了第一款 Serverless 产品 Lambda，开启了 Serverless 元年。

此后国外 Serverless 生态迅速发展，诞生了如 [Serverless Framework](http://serverless.com/)、[Vercel](https://vercel.com/) 等很多优秀的产品。国内起步比较晚，2017 年阿里云和腾讯云才相继发布国内的 Serverless 产品：函数计算和云函数，这时 Serverless 才开始进入大多数国内开发者的视野，各大厂商开始极力宣传和实践 Serverless。此后短短几年，国内 Serverless 开发进入白热化阶段，**不论大厂小厂，都开始用 Serverless 解决各自业务中的效率和成本问题。**

典型案例如下：阿里这两年的“双十一”都在用 Serverless 提升应用弹性能力、降低服务器成本；Airbnb 在用 Serverless 做实时分析报警；微博在使用 Serverless 进行图片个性化处理；石墨文档也在用 Serverless 实现实时协作。

## Serverless 带来的机遇

Serverless 本质上是一种不用关心服务器的架构思想：开发者可以不关心除业务代码之外的事情，进而提高业务的迭代效率；使用的云服务按用量付费，从而节省成本。总的来讲，**Serverless 对开发者研发方式的影响是巨大的**。

对前端工程师来说，曾经部署一个 BFF 或者服务端渲染应用，要购买机器、安装环境，甚至考虑负载均衡、分布式缓存、流量控制等复杂后端问题；而 Serverless 把这些能力封装成服务、开箱即用，解决了不擅长服务器运维的困难。另外，由于 Serverless 把后端变得很简单，前端工程师自己就可以独立完成整个应用开发；再加上前端工程师离用户最近，前端可以成为产品负责人。

同时，国内 Serverless 生态距离国外还有不小差距：国外关于 Serverless 的开发框架、WebIDE 等技术已经比较成熟，而国内还处于发展初期。这种“差距”对于国内前端工程师来说是一个很好的机会。

对后端工程师同样有很大的影响。虽然关注 Serverless 的前端人数比后端多，但掌握 Serverless 技术对后端工程师极为必要：一方面，基于 Serverless，后端工程师不用再关心系统运维，可以专注于业务开发、深入业务细节，使业务快速迭代，帮助业务成功；另一方面，后端工程师也可以深入底层去构建 Serverless 基础设施，让技术为更多开发者服务。

从招聘市场看，**不管是前端岗位还是后端岗位，有 Serverless 开发经验的候选人都更受欢迎**。腾讯、头条等国内很多大型互联网公司都在招聘 Serverless 架构师，并且薪资非常高，反映出各大厂对 Serverless 技术人才的积极态度。在面试评价中，掌握 Serverless 往往被视为关注前沿技术的信号——意味着能够以更高效率、更低成本的方式完成业务、创造价值，给公司带来产品和技术上的领先。

## 学习 Serverless 所面临的挑战

虽然开发者开始关注、尝试 Serverless，但在学习中会遇到不少问题。

大部分网络文章对 Serverless 几乎都是概念的介绍，书籍中就算有实践案例也只是简单的 Demo，深度不够。**这让开发者的 Serverless 学习过程变得极其困难，很多知识盲点都要自己探索，难以建立自己的知识体系**。比如：Serverless 应用开发的全流程是什么？怎样对 Serverless 函数进行本地调试和编写单元测试？

随着国内云厂商对 Serverless 的支持越来越完善，一些大厂和实践者也开始推出 Serverless 的开发教程，但往往都局限于某个云产品，很容易成为云产品的宣传，不能深入 Serverless 技术本身，不具有普适性。由于 Serverless 本身严重依赖云产品，很容易让开发者被云厂商绑定——比如当开发者选择阿里云之后，就很难迁移到腾讯云，这也是开发者的痛点之一。

另外，虽然越来越多的企业和开发者开始尝试使用 Serverless，但整体还处于探索阶段，**落地经验输出还非常少**，更不用说大型 Serverless 架构项目的落地经验了。这导致开发者在使用 Serverless 开发复杂业务时缺少经验、容易踩坑，很难将传统应用迁移到 Serverless 架构；开发者需要汲取大厂落地经验，才能更好地使用和发挥出 Serverless 的价值。

## 学习路径

针对上述问题，一条循序渐进的 Serverless 学习路径可以划分为四个阶段，聚焦在 Serverless 技术本身、脱离具体云产品平台的限制：

- **概念阶段：** 从云计算发展历程的角度深度剖析 Serverless 兴起的必然因素，建立对 Serverless 的宏观认知，再通过一个案例理解 Serverless 这个概念。

- **开发基础阶段：** 从开发者视角，覆盖应用设计、开发、测试、部署的整个流程，掌握开发 Serverless 应用的基础知识，理清知识盲点；完成这一阶段即可开发一个简单的 Serverless 应用。

- **开发进阶阶段：** 针对系统迁移难、厂商依赖强、经济成本高、应用不安全等开发者最关心的痛点问题，吸收大型 Serverless 架构中的实践经验；完成这一阶段就能更好地进行 Serverless 技术选型、基于 Serverless 开发复杂业务。

- **场景案例阶段：** 选择开发者比较常见且十分典型的真实场景（比如基于 Serverless 实现弹性可扩展的 RESTful API 系统），将理论知识运用于实践，从零开始设计开发一个复杂的 Serverless 应用，体会 Serverless 给开发模式带来的改变与开发效率的提升。

## 小结

Serverless 已从概念走向大规模落地，用“效率”和“成本”两条主线重塑研发方式：前端借此摆脱运维负担、获得全栈机会，后端得以专注业务或深入基础设施建设。但生态不成熟、教程偏向云产品、落地经验稀缺，构成了学习的主要障碍。按“概念 → 开发基础 → 开发进阶 → 场景案例”的路径构建知识体系，是应对这些障碍的有效方式。

虽然 Serverless 技术还比较新，但从成本和效率——开发者和企业最关心的两大问题——来看，它终会成为技术架构的主流。技术新意味着更多的机会，越早学习、实践就越能占领技术先机。

# 开发框架：如何提高应用开发调试和部署效率？

## 概念说明

基于 FaaS 可以开发出单个函数的 Serverless 应用，但实际情况中，绝大部分应用都是由多个函数组成的：应用部署时需要将所有函数一同部署，并且函数运行依赖 FaaS 环境，函数代码不能直接在本地运行。这些限制给应用开发、调试和部署流程带来了挑战，例如：

- 函数太多如何管理？

- 本地开发时如何进行调试？

- 代码开发完成后如何部署？

- ……

要解决这些问题，就需要一套完整的开发、调试和部署 Serverless 的解决方案，这个解决方案最终可以抽象为一个开发框架。**Serverless 的开发框架不是传统的 Express.js、Spring Boot 等代码框架，而是集成 Serverless 思想、贯穿 Serverless 应用从开发到上线全流程的工具。** 基于 Serverless 开发框架，很容易开发一个 Serverless 架构的应用，企业也能轻松把现有业务演化为 Serverless 架构。对 Serverless 来说，除了底层的 FaaS、BaaS 等基础设施，上层的开发框架也是一个非常重要的部分，它直接决定了开发者使用 Serverless 的成本。

理解开发框架的底层设计思路和实现原理，有助于在面对任何开发框架时快速上手，也便于从框架开发者视角改进工具本身。

## 开发框架的设计原理

Serverless 开发框架是贯穿 Serverless 应用从开发到上线全流程的工具。基于这个定义，**一个开发框架至少要满足应用管理、应用开发、应用调试和应用部署这几个基本功能。** 从形态上来看，Serverless 开发框架可以抽象为一个平台或服务，最终以终端工具（命令行工具）或控制台的方式提供给开发者使用。

### 应用管理

Serverless 应用是由函数组成的，所以应用的管理主要就是函数的管理。各个 FaaS 平台也考虑到了这一点，例如函数计算的"服务"功能或 Lambda 的"应用"功能：把一个应用的函数都创建在同一个"服务"下，一个"服务"即代表一个应用。

"服务"和"函数"的关系是静态的，不会在代码运行时改变，因此可以用 YAML 或 JSON 配置文件来表示（推荐 YAML，因为它可以编写注释，可读性更好）。在创建函数时，还要指定函数的入口、编程语言、触发器等信息。**YAML 文件的内容可能是这样的：**

```yaml
# serverless.yaml
# 应用名称
service: myservice
# 函数列表
functions:
    # 函数1
  hello:
    handler: hello.main # 函数入口
    runtime: nodejs12
    events: # 函数触发器，一个函数可能有多个触发器
        - http
        - timer
  # 函数2
  goodbye:
    handler: goodbye.main
    runtime: nodejs12
    events:
        - http
```

其中的关键属性如下。

- service：应用名称。

- functions：它的属性就是组成应用的函数，一个应用可以有多个函数，并且函数名不能重复，例如 hello 和 goodbye 就是 myservice 应用的两个函数。

- handler：函数的入口。

- runtime：函数运行环境（在 Serverless 中函数的运行环境是预先定义好的）。

- events：一个函数可能有多个触发器，所以使用 events 数组来表示触发器，例如 hello 函数有 http 和 timer 两个触发器。

需要注意的是，当用户不了解 YAML 结构时，让用户手工编写这个配置文件会很困难，因此框架需要为用户提供一个初始化的功能。假设终端工具是一个可执行脚本，命令为 serverless，那么可以提供 serverless init 命令自动为用户创建一个管理 Serverless 应用的 YAML 配置文件。

### 应用开发

有了应用配置文件之后，开发者就可以开始开发代码了。为了进一步简化用户操作，框架可以提供一些代码模板，然后提供 init 命令让开发者基于模板一键生成一个 Serverless 应用。例如：

```shell
$ serverless init --template hello-world
|-- hello.js
|-- serverless.yaml
```

```yaml
# serverless.yaml
service: myservice
functions:
  hello:
    handler: hello.main
    events:
        - http
```

这样开发者就能直接在本地用自己喜欢的编辑器编写代码了。

此外，框架还可以提供一个 Web IDE，在 Web IDE 中为开发者初始化运行环境，这样开发者不用在本地安装编辑器就能开发，也不用关心运行环境的差异。目前各个 FaaS 平台也提供了自己的 Web IDE，比如 AWS 的 Cloud9、函数计算 Web IDE。

从 Cloud9 的发展历程可以了解 Web IDE 在 Serverless 时代的地位：Cloud9 原本是一家创业公司，提供云上应用开发、部署能力，其 Web IDE 功能很强大，在 2016 年 7 月被 AWS 收购。另一个相关事件是，腾讯在 2018 年投资了 Coding，Coding 的重点产品就是 Cloud Studio 这款 Web IDE，之后 Cloud Studio 集成到了腾讯云中，腾讯云函数的 Web IDE 就是 Cloud Studio；2019 年腾讯收购了 Coding。函数计算 Web IDE 则是基于 VS Code 开发的。微软在 2019 年 5 月发布了 Visual Studio Online，让开发者可以轻松实现一个 Web IDE；后来 Visual Studio Online 演化为 GitHub Codespaces、VS Code 网页版等产品，基于它们也可以开发一个 Web IDE。当然，做一个完善的 Web IDE 还是很难的，目前体验最好的 Web IDE 仍是 Cloud9，但相比本地开发还是有一定差距，未来 Web IDE 的体验会越来越好。

### 应用调试

应用开发结束后，就要进入调试阶段了。**在 Serverless 应用开发中，应用调试十分麻烦。**

以一个典型的 Serverless 函数为例，函数代码如下：

```javascript
exports.handler = (event, context, callback) => {
    // 从 event 中获取 URL query 参数
    const { name } = event.queryStringParameters;
    // 定义 HTTP Response
    const response = {
        statusCode: 200,
        headers: {
            "Content-Type": "application/json"
            },
        body: JSON.stringify({ message: `Hello ${name}!`} ),
    };
    callback(null, response);
};
```

要想调试这个函数，就需要手动构造 event、context 和 callback 三个对象，然后以它们为参数来调用函数，测试函数运行情况。麻烦点在于：这些参数的构造依赖于 FaaS 环境，不同运行环境、不同触发器函数的入参都有差异，手动模拟这些对象很麻烦，且容易出错。

让开发者方便调试有两种方式。

- 远程调试：将代码部署到 FaaS 平台，然后直接调用 FaaS 平台的接口执行函数，再得到函数运行日志及返回结果。

- 本地调试：由开发框架模拟函数运行时环境，构造函数参数来执行函数。

**对一个 Serverless 开发框架来说，这两种调试方式都需要**，也就是需要实现 serverless invoke 和 serverless local invoke 两个命令。虽然远程调试最接近代码真实运行情况，但需要进行网络调用，大部分情况下本地调试效率更高。

### 应用部署

代码开发完成后就要部署应用，过程是：根据 YAML 的配置，解析出应用的服务名称和函数列表，然后调用 FaaS 平台的接口来创建或更新服务和函数。

需要注意的是，在创建函数时，FaaS 平台中的函数代码通常以压缩包的方式存储在文件存储服务中，所以部署函数前需要先在本地把代码压缩成 .zip 文件。

在部署应用时，开发者通常会有这样一个担忧：代码调试需要把函数部署到 FaaS 中进行调试，可能每次代码改动都会影响到线上服务，如果有版本控制就可以避免了。FaaS 平台考虑了这个问题，提供了函数版本功能（默认是 LATEST 版本）。通过版本控制，开发时可以使用 LATEST 版本进行开发，测试稳定了再发布稳定的新版本，用稳定版本提供线上服务。

所以在远程调试时，就不能更新函数版本，一直用 LATEST；而当应用部署时，就需要更新函数版本。

### 账号设置与多平台支持

完成应用部署功能设计后，还有一个问题需要解决：应用要部署到哪个云账号上？这就需要账号功能。

在账号方面，对于接口编程访问，云厂商都是通过 AccessKeyId 和 AccessKeySecret 来授权的。框架可以提供一个命令，让用户输入自己的云账号 AccessKeyId 和 AccessKeySecret，然后把账号信息保存到用户自己的磁盘上。这样应用部署时，框架就可以从磁盘上读取账号信息，以用户的账号去调用 FaaS 平台的接口，把应用部署到用户云账号下；并且账号信息存储在用户自己的磁盘上，也没有安全问题。

除此之外，一个优秀的 Serverless 开发框架还应该具备多种不同 Serverless 平台或云厂商的支持，因为不能限制用户只使用某一种云服务。Serverless 开发框架最好还要抹平不同 Serverless 平台的差异，让应用能够在不同 Serverless 平台中进行平滑迁移，甚至让开发者使用一个开发框架、一套开发流程就能实现多云部署。**这是一个 Serverless 开发框架的核心竞争力之一。**

要支持多种 Serverless 平台，就需要在框架层去适配各个不同的平台。目前各个 Serverless 平台都没有遵循统一的标准，**这也是实现多平台支持的难点所在。** 因此在实现一个开发框架时，需要先抽象出各平台的公共部分，然后制订一套开发标准，再以适配器的方式去适配不同的 Serverless 平台。

至此，就完成了一个完整的 Serverless 开发框架的设计：通过一个 serverless 命令对开发者提供所有服务，贯穿 Serverless 应用开发到上线的全流程。**这也是现在主流 Serverless 开发框架的实现原理。**

## 主流 Serverless 开发框架的实现

整体而言，国外 Serverless 生态要比国内领先一到两年，国外有很多优秀的开发框架，而国内这方面还不够成熟。以下介绍国内外最具代表性的两个开发框架，[Serverless Framework](https://github.com/serverless/serverless) 和[函数计算 Fun](https://github.com/alibaba/funcraft)（Fun 已停止维护，阿里云官方现推荐使用 Serverless Devs 的 s 命令）。

### Serverless Framework

Serverless Framework 是目前最完善的 Serverless 开发框架之一。它不仅实现了应用开发、调试、部署等基础功能，还实现了多个 Serverless 平台的支持（它不仅支持 AWS、Azure、Google、阿里云、腾讯云等公有云 Serverless 平台，还支持 CloudFlare、Kubeless、OpenWhisk 等其他 Serverless 平台）。

**安装**

Serverless Framework 使用 Node.js 开发，可以使用 npm 直接安装，安装后即可使用 serverless 命令。

```shell
$ npm install -g serverless
$ serverless --version
Framework Core: 2.15.0
Plugin: 4.2.0
SDK: 2.3.2
Components: 3.4.3
```

**账号设置**

使用 Serverless Framework 时，第一件事就是进行账号设置，假设使用 AWS 则命令如下：

```shell
$ serverless config credentials --provider aws --key key --secret secret
```

- --provider 具体的 Serverless 平台

- --key AWS 账号的 aws_access_key_id

- --secret AWS 账号的 aws_secret_access_key

Serverless Framework 会把 AWS 的 aws_access_key_id 和 aws_secret_access_key 保存在 ~/.aws/credentials 文件中。

在 Serverless Framework 中，通过 provider 来实现不同平台的支持。在不同 provider 中，Serverless Framework 的命令大部分相同，但不同 provider 的功能完整性还是有一定差异，例如它虽然支持阿里云 provider，但目前只支持 HTTP 触发器和 OSS 触发器。

**应用配置**

接下来就可以使用 serverless 初始化一个应用了：

```shell
$ serverless create --template aws-nodejs
Serverless: Generating boilerplate...
 _______                             __
|   _   .-----.----.--.--.-----.----|  .-----.-----.-----.
|   |___|  -__|   _|  |  |  -__|   _|  |  -__|__ --|__ --|
|____   |_____|__|  \___/|_____|__| |__|_____|_____|_____|
|   |   |             The Serverless Application Framework
|       |                           serverless.com, v2.15.0
 -------'
Serverless: Successfully generated boilerplate for template: "aws-nodejs"
Serverless: NOTE: Please update the "service" property in serverless.yml with your service name
$ ls
handler.js    serverless.yml
```

Serverless Framework 也是通过 YAML 配置文件来定义应用和函数的，其 YAML 格式如下：

```yaml
service: myservice
frameworkVersion: '2'
provider:
  name: aws
  runtime: nodejs12.x
functions:
  hello:
    handler: handler.hello
    events:
      - http:
          path: users/create
          method: get
      - websocket: $connect
      - s3: ${env:BUCKET}
resources:
  Resources:
    NewResource:
      Type: AWS::S3::Bucket
      Properties:
        BucketName: my-new-bucket
  Outputs:
     NewOutput:
       Description: "Description for the output"
       Value: "Some output value"
```

在这份 YAML 中，有一个设计原理部分没有提到的属性 **resources**：它的作用是帮助创建或更新资源（如果资源不存在则创建，如果资源已存在则更新），例如示例中会创建一个 AWS 的 S3 存储桶。之所以会有 resources 属性，是因为通常一个应用都需要依赖其他云服务，比如存储、数据库等。此前这些资源往往需要手动在云厂商的控制台购买，一旦应用需要扩容，手动创建资源就非常复杂且容易出错。Serverless Framework 提供了一种新的方式去管理云上资源，即通过代码来描述基础设施。

**应用调试**

在 Serverless Framework 中，调试函数直接通过 invoke 命令即可：

```shell
# 远程调试
$ serverless invoke --function hello
{
    "statusCode": 200,
    "body": "{\n  \"message\": \"Go Serverless v1.0! Your function executed successfully!\",\n  \"input\": \"\"\n}"
}
# 本地调试
$ serverless invoke local --function hello
{
    "statusCode": 200,
    "body": "{\n  \"message\": \"Go Serverless v1.0! Your function executed successfully!\",\n  \"input\": \"\"\n}"
}
```

**应用部署**

应用开发完成后，使用 deploy 命令来部署应用，如下所示：

```shell
$ serverless deploy
Serverless: Packaging service...
Serverless: Excluding development dependencies...
Serverless: Service files not changed. Skipping deployment...
Service Information
service: myservice
stage: dev
region: us-east-1
stack: myservice-dev
resources: 6
functions:
  hello: myservice-dev-hello
layers:
  None

$ tree
|-- .serverless
     |-- myservice.zip
|-- handler.js
|-- serverless.yml
```

在将函数部署到 Lambda 之前，serverless 会先在本地将代码打包，最终代码是一个压缩包，路径为 .serverless/[serviceName].zip。也可以通过 serverless deploy function -f functionName 来单独部署某个函数。

除此之外，Serverless Framework 还提供了日志查询功能，其功能不止于此，可进一步探索其插件与组件体系。

### 函数计算 Fun

Fun 是阿里云函数计算团队开发维护的一个 Serverless 开发框架，因此只支持函数计算。因为它是用 Node.js 编写的，所以也可以使用 npm 安装：

```shell
$ npm install @alicloud/fun -g
$ fun --version
3.6.20
```

**账号设置**

安装后第一步同样是设置账号：

```shell
$ fun config
? Aliyun Account ID *******
? Aliyun Access Key ID ******
? Aliyun Access Key Secret ******
? Default region name cn-hangzhou
$ cat ~/.fcli/config.yaml
endpoint: 'https://******.cn-hangzhou.fc.aliyuncs.com'
api_version: '2016-08-15'
access_key_id: ******
access_key_secret: ******
security_token: ''
debug: false
timeout: 10
retries: 3
sls_endpoint: cn-hangzhou.log.aliyuncs.com
report: true
enable_custom_endpoint: false
```

配置完成后，fun 会将账号信息存储在 .fcli/config.yaml 文件中。除此之外，也可以在项目根目录中使用 .env 文件来配置账号信息，其优先级更高。

```shell
# 项目根目录 .env
ACCOUNT_ID=*****
REGION=cn-hangzhou
ACCESS_KEY_ID=******
ACCESS_KEY_SECRET=******
TIMEOUT=10
RETRIES=3
FC_ENDPOINT=******
ENABLE_CUSTOM_ENDPOINT=false
```

**应用配置**

可以通过 fun init `<templateName>` 命令来初始化一个项目：

```shell
$ fun init event-nodejs12
$ ls -l
index.js    template.yaml
```

其中 template.yaml 功能与 serverless.yaml 一致，但内容定义有较大差异。template.yaml 的定义如下：

```yaml
ROSTemplateFormatVersion: '2015-09-01'
Transform: 'Aliyun::Serverless-2018-04-03'
Resources:
  myservice:
    Type: 'Aliyun::Serverless::Service'
    Properties:
      Description: 'helloworld'
    hello:
      Type: 'Aliyun::Serverless::Function'
      Properties:
        Handler: index.handler
        Runtime: nodejs12
        CodeUri: './'
```

其中 Resources 是表示资源的对象，对象的属性就是具体资源，对象属性中的 Type 用来表示资源的类型。例如 Aliyun::Serverless::Service 就表示"服务"，Aliyun::Serverless::Function 表示函数。因此在 template.yaml 中可以定义多个服务，一个服务中也可以定义多个函数。

**应用调试**

通过 fun invoke functionName 命令可以对函数进行远程调试：

```shell
$ fun invoke hello
using template: template.yml
```

也可以通过 fun local invoke function 在本地调试。但本地调试前，必须先安装 Docker，因为 fun 的本地调试原理是通过 Docker 在本地启动一个代码运行环境来执行代码，而不是直接模拟函数参数。这样的好处是更接近 FaaS 平台的运行环境。

**应用部署**

应用开发完毕后，可以通过 fun deploy 进行应用部署。


## 实践要点

- 开发框架的意义在于提升 Serverless 应用的开发效率，其基本能力是应用管理、应用调试和应用部署，并辅以账号设置。
- 静态的应用结构用 YAML/JSON 描述，配合 init 命令与代码模板降低上手成本；resources 类属性实现了基础设施即代码。
- 远程调试与本地调试缺一不可：远程调试最接近真实运行情况，本地调试效率更高；不同框架的本地调试实现路径不同（模拟函数参数 vs Docker 启动运行环境）。
- 函数版本控制（LATEST + 稳定版本）是调试与线上服务隔离的关键手段。
- 两个框架的定位差异：Serverless Framework 功能完善、支持平台丰富，但由于 Serverless 平台尚无统一标准，支持多平台难度极大，对国内产品支持不够友好；Fun 只为函数计算服务，有很多针对函数计算的特定功能。

## 小结

与 FaaS、BaaS 等基础技术一样，Serverless 开发框架是 Serverless 领域中非常重要的一部分：一个优秀的开发框架可以让开发者很容易地开发 Serverless 架构的应用，也能让企业轻易将现有业务演化到 Serverless 架构。除 Serverless Framework 外，国外还有 [Vercel](https://vercel.com/)、[Apex Up](https://apex.sh/up/) 等优秀的开发框架（Vercel 的前身是 now.sh，Apex Up 是 Node.js 领域的 TJ 大神 2016 年就开始开发的产品）；国内除 Fun 外，也有 [Midway](https://github.com/midwayjs/midway)（原 Midway FaaS）、[Malagu](https://github.com/cellbang/malagu) 等新兴产品出现，这些产品虽然功能完善度尚不及国外产品，但随着时间推移，国内的 Serverless 开发体验会越来越好，国内 Serverless 生态的不完善也意味着更多的参与机会。另外，现在绝大部分 Serverless 开发框架都基于 Node.js 实现，并且大部分对 Node.js 语言支持最友好，甚至只支持 Node.js，这也体现出 Node.js 在 Serverless 领域的重要性。亲自体验上述各个开发框架，可以对 Serverless 的开发体系有更深的了解。

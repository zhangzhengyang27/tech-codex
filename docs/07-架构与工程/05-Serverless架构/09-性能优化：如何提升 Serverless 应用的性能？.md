# 性能优化：如何提升 Serverless 应用的性能？

Serverless 自动弹性伸缩的特性让应用具备了近乎无限扩展的能力，但基于 FaaS 的实现也带来了一个很大的副作用，即冷启动。**冷启动是代码在处理业务功能之前的额外开销，也是广大 Serverless 开发者面临的问题之一。** 冷启动会影响 Serverless 应用的性能，因此很多开发者担忧：Serverless 能否应对低延时、高并发的场景？答案是肯定的，关键在于如何优化 Serverless 应用的性能。

Serverless 性能优化的核心就是减少冷启动，内容分为两部分：

- **深入理解冷启动：** 分析冷启动耗时，澄清冷启动的常见误区，在此过程中理解如何减少冷启动时间。

- **如何优化 Serverless 的性能：** 详细介绍优化 Serverless 性能的方案。

## 深入理解冷启动

深入理解冷启动，是优化 Serverless 应用性能的前提。

函数的启动可以分为冷启动和热启动：函数执行要经过下载代码、启动容器、初始化运行环境、执行函数四个过程，其中前三个过程就是冷启动。

冷启动需要经过多个步骤，耗时比较长。**冷启动时间到底有多长？** 可以借助链路追踪工具测量，比如 AWS 的 [X-Ray](https://aws.amazon.com/cn/xray/)、阿里云的[链路追踪](https://www.aliyun.com/product/xtrace)。Lambda、函数计算等 FaaS 平台也都集成了链路追踪功能，通过链路追踪可以查询函数冷启动耗时、执行时间，对 Serverless 应用的性能进行诊断和分析。

一个函数调用链路的主要信息有五点：

- InvokeFunction:函数执行总时间。

- ColdStart:函数冷启动时间(如果函数是热启动的，不会有这个阶段)。

- PrepareCode:函数冷启动过程中，下载代码或下载自定义镜像的时间。

- RuntimeInitialize:执行环境启动的时间，包括启动容器和函数运行环境。

- Invocation:执行函数的时间。

从调用链路中可以判断本次执行是否为冷启动：热启动的函数没有 ColdStart、PrepareCode 和 RuntimeInitialize 这三个阶段。以一次实测为例，整个函数执行耗时 553ms,其中冷启动耗时 458ms,可见冷启动对函数性能的影响很大。

### 冷启动的常见误区：“只有第一个请求慢”

关于冷启动有一种流行说法：只有第一个请求需要冷启动，所以第一个请求很慢，后面的请求是热启动、都很快。实际情况并非如此——函数第一次执行时一定是冷启动，但后面的请求不一定都是热启动，这与触发函数执行的事件是串行还是并行有关。

下面以 HTTP 触发器为例说明。测试程序见[示例代码](https://github.com/nodejh/serverless-class/tree/master/09/performance-http),部署在函数计算中后，通过 Charles 等工具模拟用户连续请求该接口：将并发设置为 1,发起 100 个请求，函数就会被顺序调用 100 次，这 100 个请求就是串行的。

串行测试结果：第一个请求耗时 770ms(代码的响应体中返回了 requestId,根据 requestId 在链路追踪中查询确认第一个请求确实是冷启动)，后面的请求都只耗时 40ms 左右，通过链路追踪分析确认都是热启动。对性能要求不高的场景来说，100 个请求中只有一个冷启动，影响约 1%,可以忍受。

**但如果用户并发访问会怎么样？** 用户行为不可预测，不可能总是串行访问。模拟发起 100 个请求、并发为 10 的情况：前 10 个请求都是冷启动，情况明显不乐观。

如果网站在一天内流量有波峰波谷，例如以下场景：

- 团购订餐业务，可能在每天中午、晚上流量突增；

- 促销活动，在活动开始前流量突增；

- 社交软件，遇到重大新闻时流量突增；

对这类业务，流量突增意味着 FaaS 平台不得不添加更多实例来支持更大的并发，而新增实例时都会有冷启动，这对用户体验有较大影响。这正是性能优化要解决的问题。

## 如何优化 Serverless 的性能

Serverless 的性能优化主要围绕冷启动耗时进行，可以从四个方面入手：

- 避免函数冷启动；

- 减小代码体积；

- 提升函数吞吐量；

- 选择合适的编程语言。

### 避免冷启动

冷启动耗时，避免冷启动自然就能极大提高性能。有两种方案：对函数进行预热；使用预留资源。

**预热**是指通过定时任务(比如定时触发器函数)，在真实请求到来之前对函数发起请求，使函数提前初始化，这样真实请求就会使用已经初始化的函数实例执行代码。例如对订餐等可预估高峰流量的业务，可以在每天上午 11:58 通过定时任务并发发送大量请求到需要预热的 API,提前初始化函数实例，12:00 流量突增时就能使用已有的函数实例，处理请求的函数都是热启动。还可以使用特定的请求头标记预热请求，以便将其与正常的用户请求分开，并且可以不对预热请求做任何处理。

函数预热能消除冷启动时间，代价是需要维护预热的逻辑，并且提前预热的函数本质上没有处理用户请求，却持续占用资源。是否使用预热，既要考虑业务场景，也要平衡性能和成本：应用对延迟要求很高(比如秒杀业务)可以使用预热；对延迟不敏感的应用则没有必要。

此外，有些 FaaS 平台(比如函数计算)提供了**预留资源**功能，可以为函数持续保留一定数量的实例。预留的函数资源需要手动创建和释放。使用预留资源，函数每次启动都是热启动，可以完全消除冷启动，提升函数性能；也不需要像预热那样主动发请求，使用起来更简单，只是预留资源的成本通常会高一点。

### 减小代码体积

函数冷启动的第一个步骤就是下载代码，代码体积越大，下载时间越长，冷启动时间随之增加。减小代码体积的手段包括：避免引入不必要的依赖、不加载不需要的代码、对 SDK 进行精简、对代码进行压缩，甚至只构建需要执行的代码。

这对 Node.js 尤其重要，因为 Node.js 的依赖目录 node_modules 通常体积非常大且非常冗余。使用 ncc 构建 Node.js 的代码及依赖，既能减小体积，还能提升性能(参见依赖管理一篇)。

### 提升函数的吞吐量

初学 Serverless 容易进入一个误区：认为一个函数实例只能处理一个请求。很多早期的 FaaS 平台确实是这样设计的，但现在大多数 FaaS 都支持**单实例多并发**，本质上是为了提升函数吞吐量——一个实例同时处理多个请求，能够减少函数实例的生成，进而减少冷启动。

假设有 3 个并发请求同时需要处理：当函数并发为 1 时，FaaS 平台会生成 3 个函数实例来处理这 3 个请求，每个实例处理一个请求，需要经过 3 次冷启动；当函数并发为 10,则只会生成一个函数实例来处理 3 个并发请求。

单实例单并发的情况下，函数实例只能同时处理一个请求，处理完毕才能处理下一个；单实例多并发的函数实例则可以同时处理多个请求。从实例的生命周期也可以看出，单实例多并发的实例执行时间更短，成本自然也更低。

单实例处理多个请求时，代码的具体执行过程如下：

```javascript
const mysql = require('mysql');
// 创建数据库连接
const connection = mysql.createConnection({
  host     : 'localhost',
  user     : 'me',
  password : 'secret',
  database : 'my_db'
});

connection.connect();
// 函数入口
exports.handler = function(event, context, callback) {
  console.log('Start handler...')
  // 查询数据库
  connection.query('SELECT 1 + 1 AS solution', function (error, results, fields) {
    if (error) {
        return callback(error);
      }
        console.log('The solution is: ', results[0].solution);
    });
};
```

第一个请求到来时，函数冷启动：先下载代码，然后初始化一个 Node.js 运行环境，接着执行初始化代码——主要是引入 mysql 依赖包、初始化数据库连接(即第 1~10 行)，最后执行 handler 方法。第二个请求到来时，函数就是热启动：函数复用上一个运行环境，进而重复使用上次的执行上下文，包括 mysql 依赖、数据库连接，此时只会执行 handler 函数。

基于热启动的特点，可以将初始化逻辑都放在 handler 函数之外，只需要第一次冷启动进行初始化，这样就能提升函数性能。单实例多并发进一步放大了这个特点。基于单实例多并发，Serverless 应用就可以更好地支持低延迟、高并发场景了。

### 选择合适的编程语言

不同编程语言的冷启动时间差异较大，一般 Node.js、Python 的冷启动耗时要比 Java 等静态语言少很多。Java 冷启动慢主要是因为需要启动庞大的虚拟机，并将所有类加载到内存中初始化。选择冷启动时间短的编程语言，可以大幅提升应用性能，这也是 Node.js 在 Serverless 领域比较受欢迎的原因之一。

具体耗时需要数据支撑。在函数计算中，针对 Node.js、Python、Java、PHP 几种常见编程语言进行过冷启动性能测试。**测试方法：** 分别用这几种编程语言实现一个“Hello World”函数，给函数设置定时触发器，每半小时执行一次，这样函数执行时基本就是冷启动；然后使用链路追踪采集冷启动耗时，统计每种语言的耗时，并分别统计 128MB、1024MB、2048MB 几种不同内存下的冷启动时间。统计代码见 [ColdStart Performance Test](https://github.com/nodejh/serverless-class/tree/master/09/performance-language)。

从统计结果中可以得出：

- 函数计算中 PHP 冷启动最快，Node.js、Python 次之，Java 最慢；

- Java 冷启动耗时大约是 Node.js 或 PHP 的三倍，Node.js、Python、PHP 的冷启动耗时基本在 1s 内；

- 随着内存增加，冷启动耗时逐渐缩短。

针对 Lambda 的同类测试显示，Lambda 中 Node.js 的冷启动耗时最短，大约在 200ms,性能是函数计算的三四倍，说明国内 FaaS 产品还有提升空间；另外函数计算中 PHP 性能最好。由此可以得到新的性能优化方案：

- 尽量选择 Node.js、Python、PHP 等冷启动耗时短的语言编程；

- 为函数设置合适的内存，内存越大，冷启动耗时越短，但成本也越高，所以要设置一个合适的内存。

## 小结

Serverless 应用的性能优化主要围绕冷启动进行，同时可以针对代码运行时优化。实践方案汇总：

- 提前给函数预热；

- 使用预留资源；

- 减小代码体积、减少不必要的依赖；

- 执行上下文重用(初始化逻辑放在 handler 之外)；

- 为函数设置并发；

- 选择冷启动耗时少的编程语言；

- 为函数设置合适的内存。

除了应用侧的优化外，Serverless 性能还有很大一部分需要靠云厂商优化，例如各种编程语言的运行时。比如 Java 冷启动耗时长，这个优化只能依靠云厂商，开发者很难介入，只能尽量避免。

# 实战是学习新技术的不二法门

## 概念说明

微服务在业内的实践已经从流行走向成熟，诸多大厂（比如 Amazon、Netflix、蚂蚁金服、网易云音乐等）都已经迁移并采用了微服务架构；而随着 AWS、Google 云平台、微软 Azure、阿里云、腾讯云和华为云等云计算平台的流行，越来越多的中小型公司选择把应用迁移到云平台上运行。

微服务云原生应用结合了微服务架构和云计算平台两者的优势，成为中小型公司开发新项目或迁移已有项目的最佳选择，对微服务云原生应用开发人员的大量需求也应运而生。

在这背后，存在三个现实问题：

- **人才的供给具有滞后性**。即便是在庞大的 Java 开发者群体中，了解微服务架构、知道如何在云平台上实现微服务架构的开发人员数量也很有限——大部分 Java 开发者熟悉单体应用开发，对微服务架构缺乏必要的了解。
- **学习本身需要投入大量时间和精力**。单是微服务技术本身，概念就非常繁杂，而且各种概念相互关联，形成复杂的知识网络，让初学者不知何处下手，更难利用理论知识解决关键问题。
- **知识的理解和应用之间存在鸿沟**。只看概念而不进行实际操作，很难说真正理解。

针对这三个问题，有一条经过验证的学习路径：**把微服务架构相关的理论与具体的实例相结合，在真实项目中掌握云原生微服务架构的应用开发**。

## 核心要点

- **实战是学习新技术的不二法门**：学习一项新技术最有效的办法，是真正用它来开发一个实际应用。
- 实战路径的形态：先写出"蠢"代码 → 在踩坑中加深理解与认知 → 回头重构甚至推倒重来 → 形成可复用的实践经验。
- 只读资料不动手是不够的：大量阅读（十余本图书、官方文档、视频）仍会留下"无的放矢"的感觉，必须通过真实产品开发验证。
- 微服务架构的复杂性是多方面的：除技术层面外，还包括团队组织、项目管理和运营维护；**微服务自身的实现只是最基础的部分**。
- 微服务 API 确定后，可选用任何编程语言和框架实现（Java、Go、NodeJS 均可）；真正的难点在于**服务之间的交互、数据一致性、错误处理以及运维挑战**。
- 微服务划分（拆分）应在项目初始阶段借助领域驱动设计（DDD）完成：划分完成后，再迁移功能需要改动多个微服务的公开 API，代价很高。
- 每个微服务可采用最适合的技术实现（如数据库驱动方式、事件源技术），API 确定后实现方式不受限制。
- 非功能性需求（安全、日志管理、性能指标、调用追踪、异常处理）看似不如业务逻辑重要，却是健壮应用不可或缺的部分；上线只是第一步，运行离不开实时监控、错误追踪、故障处理和系统维护。
- 自动化单元测试、集成测试、持续集成与持续部署是成熟产品的标配，也是实际产品开发中不可省略的环节。
- 进阶技术包括：微服务之间的异步消息传递、Saga 模式跨服务协作、基于 Istio 的服务网格实现。
- 理论知识与实际产品开发之间存在不可避免的差异，只有通过第一个项目的反复试错，才能积累出可指导后续开发的完整流程。

## 一、实战学习法的原理与案例

### 核心观点

> **当要学习一项新技术时，最有效的办法就是真正用它来开发一个实际应用。**

### 实战学习法的运作机制

- 开始阶段写出的代码可能很"蠢"，但实战的过程会加深对技术的理解和认知。
- 对技术有了更深入的理解之后，完全可以回过头来对已有代码进行重构，甚至是推倒重来。
- 亲身经历整个过程，可以有效掌握开发实践并积累经验；之后在真正的工作中用到这项技术时，就能少走很多不必要的弯路。

### 一个典型学习路径的案例

以下是原版作者（本知识体系作者）学习和实践微服务的真实路径，可作为参照：

1. **判断技术趋势**：微服务架构出现后，认定它将引领产品开发的革命性潮流；Kubernetes 和云原生技术的出现，为微服务架构的落地找到了最佳平台。
2. **决定在真实产品中落地**：使用微服务架构和云平台来设计和实现公司的下一代产品。
3. **先做大量输入**：网上搜索阅读大量技术资料，看了不下十本微服务图书，还有 Kubernetes 官方文档和其他相关视频、文字资料，自认为对微服务架构在云平台上的实现方式已有非常清晰的认识。
4. **实战暴露真实问题**：把这些知识应用到实际产品开发时，仍遇到很多现实问题，例如：
   - 如何划分微服务，一个功能到底应该放在哪个微服务；
   - 如何在一个微服务中调用另外一个微服务的 API；
   - 当数据在多个微服务中分别存储时，如何保证这些微服务之间数据的一致性。
5. **结论**：初学时的困惑是普遍的、无的放矢的；破局点在于"实战永远是学习新技术的不二法门"。

本文所述经验已经覆盖了其中的大部分弯路，学习者不必一一重历，但仍应通过亲手实践完成闭环。

## 二、微服务架构的真实难点

### 复杂性来源

开始学习微服务架构和云原生应用时，通常第一个直观印象是"复杂"。这个印象是准确的：微服务架构带来的挑战是多方面的，除了技术层面的挑战，还包括团队组织、项目管理和运营维护等诸多方面。实际上，**在微服务架构中，微服务自身的实现反而只是最基础的部分**。

### API 与实现解耦

当一个微服务的 API 确定之后，可以选择任何编程语言和框架来实现它，不管是 Java、Go，还是 NodeJS。

### 最大难点清单

微服务架构最大的难点在于：

- 服务之间的交互
- 数据一致性
- 错误处理
- 运维方面的挑战

## 三、实战主线：以打车应用为例的完整知识体系

### 主线项目设计

本知识体系以一个类似优步、滴滴的打车应用的后台服务（Happy Ride）为主线，介绍微服务架构在云平台上落地的方方面面——从最初的构想，到最后在阿里云部署上线，一步一步实践一个微服务云原生应用的开发、部署和上线全过程。

### 知识体系的四个阶段

- **微服务划分**：项目初始时利用领域驱动设计（DDD）的思想帮助拆分微服务。微服务的划分看似简单，实则非常重要——微服务一旦划分完以后，再想把某个功能从一个微服务迁移到另外一个微服务会变得很困难，通常需要改动多个微服务的公开 API。因此，在微服务划分阶段就要仔细考虑。
- **技术选型**：对每个微服务采用最适合的技术来实现，比如有的使用数据库驱动的方式实现，有的使用事件源技术实现。微服务的 API 确定之后，对其实现本身并没有太多限制，可以根据每个服务的特征选择最适合的技术栈。
- **非功能性需求**：除微服务实现外，安全、日志管理、性能指标、调用追踪和异常处理等非功能性需求同样是体系的一部分。这些需求相对于实际业务逻辑来说并不那么显眼，却是一个健壮的应用所不可或缺的。对一个微服务架构的应用来说，上线只是第一步，应用的运行离不开实时监控、错误追踪、故障处理和系统维护的支持。
- **持续集成与部署**：通过持续集成和持续部署服务，把应用部署到阿里云平台的 Kubernetes 上。在实际产品开发中，无法想象没有自动化单元测试和集成测试、以及自动化的持续集成和部署；在一个成熟的产品中，不可能不考虑服务的版本更新。与很多集中于过度简化用户场景、离实际产品开发太远的资料不同，这些容易被忽略的内容都包含在本体系中。

### 进阶内容与示例代码

体系还包含大量贴近实际的进阶内容：

- 微服务之间的异步消息传递
- 使用 Saga 模式进行跨服务的协作
- 基于 Istio 的服务网格实现

介绍相关技术时，同时着重讲解背后的原理，做到"知其然"的同时也"知其所以然"。

**示例代码**：重要功能的实现均配有详细的示例代码，可将该示例应用作为自身微服务应用的基础。完整示例代码发布在 GitHub（https://github.com/alexcheng1982/happyride）上并提供更新。

### 学习目标

通过这样一个完整的过程，可以细致而且系统地掌握微服务云原生应用开发的全貌与细节，把各种散碎的知识与概念串联起来；通过贴近实际场景的应用示例，了解真实业务的开发过程、最佳实践，真正将想法变成可运行的业务代码。

## 小结

理论知识与实际的产品开发之间不可避免地存在一些差异，原因在于抽象的理论知识需要与具体的实践相结合，才能转化为实际的开发经验。

要真正了解微服务架构和云原生应用，最好的做法就是实际完成一个项目的开发：把遇到的问题都解决一遍，把可能踩的坑都踩一遍。第一个项目的开发过程是痛苦的——一开始认为正确的做法，可能被实践证明是不合理的，会有反复验证的过程。但只有在不断试错的过程中，才能积累到真实经验，并用于指导以后的开发。

做完第二个、第三个项目时，就会有得心应手的感觉：已有一整套从架构、设计、实现、测试到部署的成熟完整流程，可以快速复制。即使遇到本体系未覆盖的内容，也可以按照同样的方式实践，积累属于自己的经验。

微服务架构的云原生应用开发是一个巨大的挑战，同时也带来机遇。可以预期的是，在未来的三到五年内，会有越来越多的公司迁移到微服务架构和云平台。这个趋势已经在国内外的大公司中得到验证，中小企业也会逐步跟上。学会微服务和云原生相关技术，可以确保跟上这一波技术热潮。

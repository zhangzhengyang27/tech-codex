# 数据观测：数据追踪的基石从哪里来？

## 背景与问题

日常开发过程中，程序无时无刻不在与数据打交道，要让程序运行得稳定顺畅，就必须实时对数据进行观测。而数据观测的前提，是弄清观测数据从哪里来：从用户端发起请求，到服务端真正完成查询，整个链路中的每一层都会产生可供观测的数据。

## 监控数据来源

一般所说的数据观测，观测的是从请求发起、到真正完成查询这一过程中的数据。按请求流转路径，可以从数据请求发起的用户端到数据查询响应的服务端逐层划分来源。

### 端上访问

端上访问是用户侧的数据来源，也是最直观的一层。互联网发展早期，通过 PC 浏览网页属于端上访问；随着移动互联网的发展，打开各种 App，或访问 App 内的小程序/H5 页面，都属于端上访问的范畴。用户通过端上访问最直观地感受到程序的响应速度，因此端上访问的数据十分重要。

获取端上访问数据的常见方式有以下几种：

- **用户体验监控**：Web 页面中的白屏时间、DOM 元素/资源加载耗时、文档网络耗时；App 的卡顿率、崩溃率、热启动加载时长等。
- **日志**：Web 页面出现脚本错误时，需要将相应的异常信息通过日志的方式上报服务器；App 也有相应的日志输出，但移动端更关注系统崩溃或出现异常时的日志信息。
- **端到端**：指用户端（Web/App）到后端服务器的请求情况，比如访问量、成功率、响应时间等。做端到端观测时，还需要了解端上所处的地区、网络环境、响应状态码等信息，才能掌握用户真实的使用情况。
- **可用率**：运营商和地区的不同会导致访问端上时存在差异，比如访问是否可用、响应耗时长短等。这与 CDN、DNS 等公共资源有莫大的关系。

### 应用程序

端上发起请求后，一般会到达应用程序。这里是代码运行、处理用户请求的地方，通常会集成各种第三方组件，比如常见的 Kafka、Redis、MySQL。应用程序的执行效率最终会通过端上响应情况反映出来，直接影响用户的使用体验。要提升程序的响应速度，需要关注以下几个指标：

- **执行情况**：响应时间、QPS 等都可以反映应用程序的执行情况。针对端上的请求或定时任务，执行情况十分关键；执行情况越差，用户的直观体验也越差。组件级别上，MySQL 中的慢查询监控、Kafka 中的 Lag 监控等，也可以反映应用程序的执行情况。
- **资源消耗**：应用程序部署后会消耗一定的资源，例如内存级别的 Redis 会消耗大量的内存，Kafka 因为要进行磁盘写入所以会要求较好的 I/O。应用程序区分 I/O 密集型和 CPU 密集型，二者对应的资源消耗不同。
- **VM 指标监控**：指 JVM 监控，比如 GC 时间、线程数、FGC/YGC 耗时等信息；其他语言也有各自独特的统计指标信息。
- **容量**：指单个系统可最大承受的容量。当应用访问量到达阈值时，一般会对该应用的访问容量进行扩缩容。
- **服务关系**：随着分布式系统架构的流行，在监控单体应用的基础上，还必须考虑应用之间的调用关系和调用速度，比如是否存在两个服务之间的相互循环引用、下游服务出现问题是否会干扰整个流程的执行，以及服务之间的响应时长、上下游服务的依赖程度等。
- **应用日志**：应用程序会记录自身的日志，第三方组件也有相应的日志，比如 MySQL 的进程日志、慢查询日志等。充分利用应用日志，可以大幅提高排错能力。
- **健康情况**：当前服务是否存活、服务运行是否稳定等。例如在 ES 中可以看到服务的状态（RED、YELLOW、GREEN）。

### 业务监控

让应用程序稳定运行还远远不够，可观测系统还需要对具体业务产生的数据进行监控：网站系统会关注 PV、UV 等参数；支付系统则会关注创建订单量、成单量等。

业务指标能很好地体现系统是否稳定。任何系统出现问题时，最先受到影响的肯定是业务指标；反之，如果影响不是特别大，就说明对这个指标进行监控的意义也不大。

业务指标还可以衡量上线后的成效。需要通过 A/B Test 了解用户更偏好哪一种模式时，可以分别观察两种模式下的业务指标来比对用户喜好；也可以依据业务指标得出的结论，在上线前进行一些改进（例如选择用户更偏好的模式）来提高成单率。

核心业务指标的设定因具体的业务和场景而异，因此开发人员需要对业务和代码都有一定的了解。

### 基础设施

应用程序/组件一般运行在云主机、操作系统之上，如果基础设施出现了严重问题，会影响到云主机和操作系统，进而牵连应用程序/组件的正常运行。为避免这种情况，需要对基础设施进行监控，保证其良好运行。

基础设施监控一般从两个方向展开：

- **资源利用**：I/O 使用率、CPU 利用率、内存使用率、磁盘使用率、网络使用率、负载等都属于资源利用的范畴。
- **通信情况**：指主机与主机之间的网络情况。通信是互联网中最重要的基石之一，如果两台主机之间出现网络延迟时间大、丢包率高等问题，会导致业务受阻。

## 可观测性核心概念

基于上述几个层次的数据来源，为了全面观测系统状态，通常会通过几个关键维度来观测数据，即可观测性中比较关键的三个概念：**日志**、**统计指标**和**链路追踪**。

### 日志（Logging）

**日志**是系统中的常见功能，上述数据来源的各个部分都有可能产生日志。日志的一般定义是：在特定时间发生的事件，被以结构化的形式记录并产生的文本数据。

日志可以展现系统在任意时间的运行状态；又因为它是结构化的文本，很容易通过某种格式进行检索，例如检索 7 月 24 日用户支付下单操作的记录。

日志是三类数据中最容易生成的，大量输出会占据比较大的存储空间，进而影响整个应用程序的性能。例如 Java 中的 logback 日志框架，就算使用了异步线程来执行，也会对磁盘和 I/O 的使用率造成影响。

也有部分系统反向利用日志可追溯、结构化的特点来实现相关功能，最典型的是 WAL（Write-Ahead Logging，预写日志）：在操作之前先进行日志写入，再执行操作；如果操作没有执行完成，下次启动时就可以通过日志中结构化的、有时间标记的信息恢复操作。MySQL 中的 Redo log 就是其中的典型。

### 统计指标（Metrics）

**统计指标**是一种可累加的聚合的数值结果，具有原子性，可以通过各种数学计算方式来获取一段时间内的数值。

统计指标针对数据的存储、处理、压缩和检索进行了优化，所以一般可以长期存储并以很简单的方式（聚合）查询；但由于涉及数据的处理（数学计算方式）和压缩，它也会占用一定的 CPU 资源。

统计指标是压缩后的数值，因此指标出现异常时，很难得知是什么原因导致的异常。此外，如果使用了一个高基数的指标作为统计维度，统计很容易给机器带来较高的性能损耗：例如基于用户 ID 的维度去做数据统计时，因为统计需要一段时间范围，数据过多就必然会造成内存上的占用。

后端经常说的 QPS、TPS、SLA 都是计算后得到的指标；基础设施中的 CPU 使用率、负载情况也可以认为是指标。

### 链路追踪（Tracing）

**链路追踪**是一个相对较新的概念。“全链路压测”中的“链路”与链路追踪中的“链路”概念一致，区别在于链路追踪将链路的完整行为信息进行记录，然后通过可视化的形式展现出来。

以一个例子说明：程序中的一个接口总共有 4 个服务参与，调用关系分别是 A->B->C->D，其中 B 服务还与 Redis 这种第三方应用产生了调用/请求关系。这一完整过程就可以在链路追踪中以调用关系图的形式展示；在实际场景中，链路追踪展示的图会比这个例子更加清晰。

链路是支持跨应用的，常见的 RPC 请求就可以说是链路中的一部分。

与日志一样，链路追踪也会造成一定的性能损耗，因为任何形式的观测都需要存储一定的数据和时间信息，这必然会占用一定的 CPU 和内存资源。资源占用的问题一般可以通过采样的方式解决。

### 三者之间关系

数据来源一般可以分为 2 个级别：

- **请求级别**：数据来源于真实的请求，比如一次 HTTP 调用、RPC 调用；
- **聚合级别**：真实请求的指标，或是系统的一些参数数据聚合，比如 QPS、CPU 数值。

对照这两个级别可以对三个概念加以细化：**链路追踪**属于请求级别，因为它和每个请求都挂钩；**日志**和**统计指标**既可以是请求级别，也可以是聚合级别，因为它们可能来自真实的请求，也可能来自系统对自身诊断时记录的信息。

三者两两组合之后形成如下关系：

- **链路追踪+统计指标**（Request-scoped metrics），请求级别的统计：在链路追踪的基础上，与相关的统计数据结合，从而得知数据与数据、应用与应用之间的关系。
- **链路追踪+日志**（Request-scoped events），请求级别的事件：这是链路中一个比较常见的组合模式。日志本身是每一条单独存在的，将链路追踪收集到的信息集成在日志中，可以让日志之间具备关联性，使其具有除了事件维度以外的一个新维度——上下文信息。
- **日志+统计指标**（Aggregatable events），聚合级别的事件：这是日志中比较常见的组合。通过解析这部分具有统计指标的信息，可以获取相关的指标数据。
- **三者结合**（Request-scoped, aggregatable events）：可以理解为**请求级别+聚合级别的事件**，由此形成一个丰富的、全局的观测体系。

从最终输出的**数据量（Volume）**看：**统计指标**是数值的形式，同时又可以压缩，所以它所需的存储量是最小的；**日志**的输出量最大，但相对的，它也有比较全的内容记录；**链路追踪**则正好处于二者之间，它不会像日志一样大量地输出，也不像统计指标一样节省存储。

## 实践要点

- 端上访问数据直接反映用户真实体验，采集时需同时覆盖体验指标、日志、端到端请求与可用率四类信息。
- 应用程序层的观测需要“执行情况 + 资源消耗 + VM 指标 + 容量 + 服务关系 + 应用日志 + 健康情况”多线并行，缺一不可。
- 业务指标是系统出问题时最先受影响的信号，核心指标的定义必须与具体业务和场景对齐。
- 三类观测数据都有代价：日志大量输出影响磁盘与 I/O，指标计算与压缩消耗 CPU 且须警惕高基数维度，链路追踪占用 CPU 与内存——采样是控制链路追踪开销的通用手段。

## 小结

数据观测的对象贯穿“用户端 → 应用程序 → 业务 → 基础设施”四个层次；日志、统计指标、链路追踪三大概念各有特性、开销与适用场景，三者按请求级别与聚合级别组合，构成完整的观测体系。

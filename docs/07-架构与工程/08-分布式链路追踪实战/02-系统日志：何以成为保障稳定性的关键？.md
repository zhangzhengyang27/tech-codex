# 系统日志：何以成为保障稳定性的关键？

## 背景与问题

日志是可观测性三个核心概念中最基础的一个。在应用程序、端上和传输系统中，日志无处不在。一个请求在分布式系统中往往跨越多层组件，故障发生时，日志通常是最先被查看的数据来源：它可以记录系统中硬件、软件和系统的信息，同时观测系统中发生的事件，据此检查错误发生的原因。

日志之所以是保障系统稳定性的关键，源于它的两个特性——**全面性**与**完整性**：它存在于系统的任何地方，同时又事无巨细地记录下每一件细小的事情。要把日志用好，需要回答三个问题：日志有哪些功能、级别如何正确使用、日志从哪些地方产生。

## 日志的六大功能

- **便于调试**：应用开发阶段的测试或本地环境中，添加日志可以感知程序进入了某个函数、执行了某些行为，甚至进入了代码层级，记录代码判断后的行为。这类日志一般设置为调试级别，或在上线前统一删除。

- **快速定位问题**：依据对业务的理解，在程序中增加相应的日志记录。程序出现问题时，第一时间通过日志查看当时用户进行了什么操作、有没有出现程序报错等，这是定位问题原因的关键。进行业务数据埋点时，也会使用日志来查看更详细的业务数据信息。

- **高度定制化**：日志是结构化的，同时可以在代码的任意位置编写。无论应用是在执行业务请求，还是在执行定时任务，只要是在程序可执行的代码位置都可以编写日志。

- **信息埋点**：业务信息可以以日志的形式保存下来。例如用户在 21:22 进行了准备支付操作，在 21:23 进行了支付结束操作，这一行为就可以完整记录。

- **追踪数据变化**：日志可以将数据实时记录下来，比一般统计系统更详细——统计系统通常只记录某个时间段的信息，而日志可以精确到某个时间点。读取这部分数据，可以更好地了解系统运行时的状态。

- **数据分析**：基于信息埋点，将收集到的信息统一写入一个文件，数据分析系统定期解析这些日志文件，得出每个用户的具体操作。例如大数据分析师可以利用这些数据分析用户行为，指引下一步的整体战略。

## 日志级别

日志级别是一个为人熟知的概念，但在实际使用中经常出现误用。以下按从低到高的顺序介绍其中比较关键的 4 个日志等级，并给出各级别的正确用法。

- **debug（调试级别）**：通常记录调试内容，例如程序进入方法或函数时的参数信息。debug 级别的日志会极大地影响 CPU 和磁盘 I/O 写入的性能，一般只在测试或本机环境中使用。除自己编写的日志外，一些常见的第三方框架也会输出调试日志；这种日志量在生产环境中很难抓到重点，会浪费大量时间在日志检索上，因此不建议在生产环境中使用。

- **info（信息级别）**：开发人员最常用的日志等级，信息埋点、追踪数据变化、数据分析等功能一般都通过这个级别完成。常见的误用是把 info 级别当作 debug 级别，输出大量没必要的日志内容，导致线上环境产生大量垃圾和重复信息，不便于日志检索。

- **warning 与 error 的常见误用**：许多人会使用 error 级别来记录 warning 级别的内容，这使得不太关键的信息也会在查看故障日志时被筛选出来，导致对故障原因产生误判，浪费大量排查时间。

  - **warning（警告级别）**：用来记录虽然出现了错误、但并不会真正对程序执行构成影响的内容。判断标准是：如果想使用 error 级别，但感觉这个错误并不会影响程序往后执行或业务逻辑不会产生错误，就应改用 warning 级别。

  - **error（错误级别）**：只有当整个接口、方法调用都产生了不可避免的问题，对业务的主流程造成影响时才采用。

## 日志的常见来源

排查问题的原因时，如果一时找不到，可以按照一定的顺序对日志逐一排查。找问题原因的过程是一个不断否定、不断排除的过程——排除了所有的不可能，剩下的就是真相。为此需要了解日志的常见来源，建立分层检索的整体视角。

与监控数据的来源类似，日志的来源也可以按照用户端到服务端来划分，共分为五层：终端层、网关层、应用层、组件层、基础层。

### 终端层

终端层指网页、App、小程序这样的形式。这一层的所有日志信息都不在服务端，而在用户的电脑、手机中，收集时一般通过打点的形式上传到后端服务再记录下来。

终端层更偏向用户的真实操作行为和一些异常信息的记录，例如用户当前的网络环境、系统状态、手机型号等。通过观察这部分数据，可以看出是哪一类用户在操作时容易产生问题，方便后端和终端的研发人员定位问题。

### 网关层

网关层可以理解为请求被接收之后最先经过的地方，就像水龙头流出的水会先经过过滤器。最常见的网关层组件是 Nginx、Kong，以及 Spring 体系中的 Zuul 和 Spring Cloud Gateway。网关层通常产生如下 2 个日志文件：

- **访问日志**：服务请求到达网关层后生成一条日志，记录这个请求从开始接收到最终反向代理的整个流程信息，其中不仅包括请求中的基本信息（如请求 IP、请求 UA），还包含与下游服务相关的 IP 地址、响应时长信息等。这个文件支持高度定制化：以 Nginx 为例，有相当多的环境变量可供选择，这些变量基本覆盖了一个请求生命周期中绝大部分的数据信息。

- **错误日志**：记录网关服务在执行过程中出现的问题。除非使用了第三方框架，网关层一般不会出现问题。

### 应用层

应用层一般指业务程序代码的执行位置。应用程序分为**基于容器托管的应用程序**和**普通的应用程序**两类。

- 基于容器托管的应用程序，例如 Java 开发中常见的 Tomcat，有 2 个相对关键的日志文件：

  - **容器启动日志**：以 Tomcat 为例，容器的 logs 目录中经常会有"catalina.日期.log"，这是 Tomcat 启动时的日志，通常会随着控制台日志一同被打印出来。有时候某些程序异常没有被记录，会在这里显示。当程序启动时莫名挂掉、无法启动，但应用程序日志中又找不到输出信息时，可以到这个日志里查看。

  - **请求访问日志**：与网关层的访问日志类似，记录与上游相关的访问时间、访问地址等信息；这类日志信息与网关层的日志一一对应。

- 普通应用程序：其日志文件通常通过框架编写，写法相对多样和自由。

### 组件层

MySQL、Redis 这类常用组件产生的日志属于组件层。这一层级比较常见的日志有：

- **应用运行时产生的日志**：第三方应用运行时会输出程序执行时的日志内容。当业务程序与组件通信出问题时，可以尝试通过这个日志定位，看应用当时是否出现了某些数值的波动或其他异常。

- **慢查询日志**：一般的数据库类型应用中都有这种日志，用于记录业务系统在进行数据库查询时出现的"查询速度慢"现象。如果某个系统中突然出现大量"慢查询"，就需要监控这个问题，获取更完整的数据库查询语句和来源信息，以便更好地解决问题。

- **审计日志**：同样适用于数据库，主要作用是在进行相关操作的时候将操作行为记录下来，例如一次数据库查询、一次数据插入。这类日志输出量比较大，对应用性能有一定损耗，大多数情况下并不会开启；但在金融行业等有特殊审计需求的场景中，审计日志必不可少。

### 基础层

基础层中的日志更偏向运维，功能倾向于日志审计与系统问题记录。比较常见的日志有：

- **系统日志**：一般指 Linux 平台中的"/var/log/messages"，记录系统中比较关键的日志。系统启动了某个程序，或某个程序因为内存过高引发了系统级别的 kill，都会记录在这个文件中。

- **操作日志**：Linux 的日志通常通过环境变量定制。通过这个日志，可以查询到哪个人在哪个时间点进行了哪些操作；系统出现异常问题时，也可以据此查看是谁、因为什么操作而导致的。

## 实践要点

- **级别纪律**：debug 只留在测试或本机环境；info 只记录有价值的业务信息，避免当作 debug 输出垃圾信息；warning 与 error 严格按"是否影响主流程"区分，防止故障排查时被不关键信息干扰。
- **分层排查**：无法定位原因时，按"终端层 → 网关层 → 应用层 → 组件层 → 基础层"的顺序逐层检索日志，每层都有明确的排查对象。
- **终端层补充打点**：服务端日志覆盖不到用户侧的真实操作行为与设备环境，需要通过打点上传来补齐。
- **利用容器启动日志兜底**：应用日志中没有异常输出但程序无法启动时，检查容器启动日志（如 Tomcat 的 catalina.日期.log）。
- **审计日志按需开启**：审计日志输出量大、有性能损耗，仅在金融等有强制审计需求的场景开启。

## 小结

日志具有**全面性**和**完整性**的特点：它存在于系统的任何地方，同时又事无巨细地记录下每一件细小的事情。掌握日志的六大功能、四个级别的正确用法与五层来源划分，就构成了通过日志保障系统稳定性的完整知识框架——前者决定日志"能做什么"，中者决定日志"该怎么写"，后者决定日志"去哪里找"。

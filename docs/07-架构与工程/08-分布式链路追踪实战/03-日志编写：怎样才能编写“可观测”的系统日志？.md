# 日志编写：怎样才能编写“可观测”的系统日志？

系统日志是保障系统稳定性的关键手段之一，日志的价值最终取决于日志内容本身的质量。日志编写涉及三个环节：选用的日志工具、编写日志的方式、日志编写完成后的管理，三者共同决定日志能否真正具备“可观测性”。

## 日志框架

编写日志前，首先需要了解支撑日志编写的框架体系。

::: warning 避免使用控制台输出
如果代码中仍在使用 System.out.println、Exception.printStackTrace 或类似的控制台输出方式记录日志，应改用第三方日志框架。从源码可以看到，这类控制台输出是线程同步的，同一时间只允许一个线程执行，大量使用会对程序性能造成严重影响。
:::

日志框架在系统中一般分为 2 种类型：日志实现框架和日志接口框架。

### 日志实现框架

日志实现框架提供具体的日志管理与写入方式。Java 生态中的日志实现框架并不统一，以下以认知度最高的 3 个项目说明。

- **log4j 1.x**：2001 年发布，后来成为 Apache 基金会的顶级项目，曾一度是几乎所有项目都在使用的日志实现框架，至今仍有不少项目在使用。log4j 1.x 使用方便，但 1.x 版本在高并发场景下存在比较严重的锁竞争，性能难以充分发挥。

- **logback**：log4j 1.x 创始人的另一个项目，提供更高效的写入性能——据官方说明是 log4j 1.x 的 10 倍——以及更多功能，例如异步日志。

- **log4j 2.x**：logback 流行后，log4j 1.x 的开发人员推出的新一代框架，号称比 logback 更快。log4j 2.x 借鉴了 logback 的许多想法和功能，并解决了 log4j 1.x 架构上存在的一些问题（注：log4j 1.x 已于 2015 年起停止维护；log4j 2.x 曾于 2021 年底曝出 Log4Shell 严重漏洞（CVE-2021-44228），生产环境应保持 2.17.1 及以上版本）。同时，log4j 2.x 采用 Disruptor 实现异步日志，相比 Java 自带的队列提供了更高效、更完整的队列实现方案。

三种框架目前市面上都有使用，但主流是 logback 和 log4j 2.x。虽然两者的异步日志效率相差无几，log4j 2.x 仍略有优势。

### 日志接口框架

多种日志实现框架并存会带来两个问题：

- **多框架协作**：业务系统中往往集成了许多第三方框架，如分布式协调用到 ZooKeeper、Curator，RPC 通信用到 Dubbo、Thrift。这些第三方框架各自依赖不同的日志框架输出日志，而排查问题需要借助日志了解各框架之间的协作状态。如果直接使用 logback、log4j 这类实现框架，业务系统就得同时接入每一种日志框架。

- **不同框架竞争**：引入多个日志框架时，还要处理各框架的输出位置。多个日志框架同时写入一个日志文件会产生竞争问题，导致性能无法发挥。

面向接口的日志框架因此出现。它提供统一的 API，开发人员在编写代码时统一面向接口，业务项目接入时只需选定一个实现框架，即可统一整个系统的日志实现。

目前使用最广泛的日志接口框架是 SLF4J，同样出自 logback 的开发者，基本已形成事实规范。SLF4J 提供动态占位符功能，无须再手动拼接参数字符串，显著提升程序性能。

默认情况下程序运行在 info 级别，使用字符串拼接输出 debug 日志的写法如下：

```java
logger.debug("用户" + userId + "开始下单:" + orderNo + ",请求信息:" + Gson.toJson(req));

```

这种写法的问题在于：如果系统中存在大量类似代码，而日志只输出 info 及以上级别，那么执行 debug 日志语句时字符串仍会被不停拼接却不会真正输出，白白浪费系统性能。使用 SLF4J 的占位符写法则可以避免这一点：

```java
logger.debug("用户{}开始下单:{},请求信息:{}", userId, orderNo, Gson.toJson(req));

```

SLF4J 会根据日志等级判断，只对符合输出要求的日志进行数据拼接和打印。

有些日志输出需要数值计算或 JSON 转换等计算任务。方法调用即使被当作参数传递也一样会被执行，因此 Java 8 中的 SLF4J 还支持通过 Supplier 延迟传参：

```java
logger.debug("用户{}开始下单:{},请求信息:{}", userId, orderNo, () -> Gson.toJson(req))

```

SLF4J 不仅提供了一套面向接口的开发方式，也明确了如何有效地编写日志，这是它被广泛采用的原因。

## 日志编写要点

“可观测”的日志如何编写，可以归纳为 8 个要点：日志编写位置、写入性能、占位符、可读性、关键信息隐蔽、减少代码位置信息的输出、文件分类、日志 review。这 8 个要点分成 2 个方向：

- 日志开发时（前 5 项）：如何写出更有效率的日志。

- 日志完成后（后 3 项）：上线前后有哪些需要注意的事项。

### 日志编写位置

日志编写位置是重中之重，好的日志位置既能帮助排查问题，也能加深对代码运行情况的了解。以下是几个比较重要的编写位置：

- **系统/应用启动和参数变更**：系统启动时打印相关参数信息，出现问题时可以更准确地查询原因。参数信息可能并不存储在本地，而是通过配置中心获取；参数发生变更时，也需要将变更后的内容输出到日志。

- **关键操作节点**：最典型的做法是在关键位置添加日志，记录用户进行的某个操作，出现问题时可通过该位置的日志还原用户行为。系统自身执行某些操作时同样适合记录，例如准备启动某个线程池进行数据处理时加上日志，便于以后分析问题。

- **大型任务进度上报**：系统处理较大的任务时，可在过程中增加日志表明任务处理进度，防止程序长时间运行却无法得知执行状态。例如文件下载时，可以按百分比定时/定次地上报数据。

- **异常**：程序出现异常时，通常通过 try-catch 记录当时情况，再以日志形式表现。使用 try-catch 时需要注意日志编写位置：如果异常会向本层之外继续抛出，本层就不需要记录日志，否则会出现日志重复；除异常之外还需要记录其他内容时，可以通过定制异常信息来实现。

### 写入性能

日志的写入性能受以下 5 个因素影响：

- **日志编写位置**：日志位置在程序中十分重要。在 for 循环中编写日志，由于循环会执行很多次，会产生大量日志记录，此时需要评估这条日志是否有必要。

- **日志数量**：大量编写日志必然降低日志质量，海量日志让问题排查变得困难，反而成为一种负担；高访问量时，过多的日志还会影响程序执行效率。

- **日志编写等级**：日志等级很容易被滥用，不正确的等级会拉长问题排查时间。

- **日志输出级别**：指配置中日志输出级别的选择。线上环境不建议使用 debug 级别——线上请求持续不断，debug 级别会输出大量基础和请求信息，极其浪费资源，建议开启 info 或以上级别。

- **无用输出参数**：不对大字段、无用字段输出，否则会同时影响程序执行效率和日志内容。一个真实案例：开发人员在线上打印了一个完整的 HTML 内容，导致当日部分日志错乱、部分日志无法检索——原因是 HTML 的多行内容导致日志无法解析；开发人员到服务器上查看时，日志文件大小已经扩大到原来的 3 倍。

好的日志一定便于排查问题。编写每一条日志时都应思考：这条日志能帮助排查什么。

### 占位符

编写日志时应尽可能选择基于占位符的方式，原因有三：

- **节约性能**：生成较高级别日志时，低级别日志若使用字符串拼接会不停叠加字符串，占用过多内存和 CPU 资源。

- **便于编写**：先确认日志要表达的内容，再确认需要编写的参数，写日志时目的更明确。

- **便于查看**：代码 review 时更容易看清日志想表达的意思，不会被参数打乱。

### 可读性

可读性是日志编写的关键之一。好的日志像一篇好的文章，能让人快速抓住关键信息。实践中大量日志是无意义的，根本无法定位问题根源，例如：

```java
boolean success = doSomeThing();
if (success) {
    logger.info("数据保存成功！");
}

```

这段代码乍看没有问题，但运行后系统会大量输出“数据保存成功！”，这类输出和没有输出一样，起不到任何作用。

日志中容易遗漏的关键信息包括：

- **会话标识**：当前操作的用户及与当前请求相关的信息，类似 Session。出现问题或查看行为时，可以根据该值快速定位相关日志。

- **请求标识**：每个请求拥有唯一标识，排查问题时只需查看这一个请求下的所有日志。请求标识一般配合链路追踪系统使用，后者可实现跨应用的日志追踪，过滤掉不相关的信息。

- **参数信息**：日志中带上参数信息能还原问题产生的上下文，便于复现问题和辨别错误原因。

- **发生数据的结果**：与参数信息相互对应——一个在执行前，一个在执行后。执行结果帮助了解程序运行的产出，出错时也是重要参考。

### 关键信息隐蔽

关键信息应不显示或掩码显示，避免信息被盗取后出现数据内容泄漏。推特在 2018 年曾将用户密码打印在日志中，这一行为泄露了 3.3 亿人的密码。

### 减少代码位置信息的输出

非必要情况下，不要在日志格式中输出日志所在的代码行和方法名称。logback、log4j 的这一能力通过获取当前线程堆栈快照实现，会极大影响程序执行效率。log4j 文档中有这样一段话：使用同步方式获取位置信息会慢 1.3 到 5 倍；使用异步日志时，因为涉及跨线程获取位置信息，会慢 30 到 100 倍。

关闭代码位置信息的输出可以节省系统资源，提升性能。

### 文件分类

文件分类可以提高检索日志的效率。将不同业务逻辑按不同日志文件分类，可以保证看到的信息都与该功能相关，不被其他日志干扰，这是大型系统常用的手段。例如某招聘网站的单点登录系统，将极验验证功能和登录验证功能拆成两个独立的日志文件，出现问题时可以根据相关功能的日志快速筛查，减少筛选时间。

### 日志 review

每次功能上线后，除了对业务功能回归，还要对日志进行观察，确认日志内容的输出情况——内容是否符合预期，有没有不合适的地方。

好的日志无法一次写好，必须像代码一样持续迭代，才能越来越便于处理问题、越来越具有可读性。

## 日志管理

编写完日志，管理工作同样重要。好的日志管理方式可以显著提高阅读日志的效率，这需要开发人员和运维人员共同协作。

### 日志格式

日志的格式布局影响运维人员收集与管理日志的效率。编写者和管理者协商规定出一套完整的日志格式后，排查问题可以事半功倍。以下是几点注意事项：

- **系统之间格式保持一致**：各应用在日志格式上尽量统一，运维人员收集日志时就能采用统一的日志模板收集和格式化内容，减少双方沟通成本。

- **不编写多行的日志内容**：除异常堆栈信息外，不对日志内容做多行输出。多行内容非常不利于数据解析，可能出现一条日志被拆成多条的情况。

- **不要使用日志中的常见内容来分割**：用日志中常见的内容做分割符会在格式解析时出问题，例如用户 ID 中的空格就是比较常见的内容。

### 日志归档

日志归档很重要。所有日志都写入同一个文件会让日志文件越来越冗余，不利于收集和查看。

一般做法是按日期归档，每天生成一个日志文件，备份和恢复时可以按日期进行。如果天级别的日志文件仍然过大，可以按小时细分。

## 小结

日志编写涵盖工具选型、编写要点和管理方式三个环节：实现框架中 logback 与 log4j 2.x 是主流，接口层面统一使用 SLF4J 并配合占位符与 Supplier 延迟传参；编写时关注位置、性能、可读性、信息隐蔽等 8 个要点；上线后通过日志 review、格式约定与按日期归档保证日志长期可用。整个流程需要从项目一开始就纳入规范。

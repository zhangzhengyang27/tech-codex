# 统计指标：“五个九”对系统稳定的真正意义

## 概念说明

统计指标和日志一样无处不在。**统计指标**记录系统在一段时间内某个维度的数值，因此能最直观地体现系统是否出现了问题。每一个统计指标都可以被量化为一个数值，这一高度可量化的特点使其能够支撑以下两类工作：

- **业务分析**：产品团队通过业务型指标了解产品上线之后的真实效果，从而优化下一步的产品决策。业务型指标包括成单率、用户留存等。
- **系统运行状态**：通过在系统中埋点或统计已有数据——例如最常见的 CPU 使用率、访问 QPS、响应耗时——开发人员可以快速了解系统的运行状态。

借助统计指标，能够对整个系统的运行情况形成感性认识。出现问题后，各个指标数据会首先出现波动，这些波动反映出系统在哪些方面出现了问题，可以由此排查原因。

一个典型案例：使用 HttpClient 框架发送 HTTP 请求时总是卡死，且堆栈始终卡死在发送请求上；最终查询句柄的指标数据，才发现是句柄被占满、无法执行导致的卡死。

## 指标类型

统计指标有多种类型，各自的作用不同。

### 计数器（Counter）

计数器是一个数值单调递增的指标，值一般为 Double 或者 Long 类型。常见的有 Java 中的 AtomicLong、DoubleAdder，它们的值就是单调递增的。QPS 的值也是通过计数器的形式，配合一些函数计算得出的。

### 仪表盘（Gauge）

仪表盘和计数器都可以查询某个时间点的固定内容的数值，但与计数器不同，仪表盘的值可以随意变化，可以增加也可以减少。例如 Java 线程池中活跃的线程数可以通过 ThreadPoolExecutor 的 getActiveCount 获取；比较常见的 CPU 使用率和内存占用量也可以通过仪表盘获取。

### 直方图（Histogram）

直方图相对复杂一些，它是将多个数值聚合在一起的数据结构，可以表示数据的分布情况。

直方图将数据分成多个**桶（Bucket）**，每个桶代表一个范围区间（图下横向数），比如第 1 个桶代表 0~10，第二个桶就代表 10~15，以此类推，最后一个桶代表 100 到正无穷。每个桶之间的数字大小可以不同，并没有规定要有规律。每个桶和一个数字挂钩（图左纵向数），代表了这个桶的数值。

以最常见的响应耗时举例：将 0~100 毫秒这一“比较快”的范围作为一个桶，然后是 100~150 毫秒，以此类推。通过这样的形式，可以直观地看到一个时间段内的请求耗时分布图，有助于理解耗时情况的分布。

### 摘要（Summary）

摘要与直方图类似，同样表示一段时间内的数据结果，但反映的内容不太一样。摘要一般用于标识分位值，分位值就是常说的 TP90、TP99 等。

分位值的含义：假设有 100 个耗时数值，将所有数值从低到高排列，取第 90% 的位置，这个位置的值就是 TP90 的值；假设这个位置的值是 80ms，那么就代表小于等于 90% 位置的请求都 ≤80ms。

一张比较典型的分位值图中有 6 个桶，分别是 50、75、80、90、95、99，桶的值就是相对应的耗时情况。通过分位值图，可以看到最小值和最大值以外的一些数据，这些数据在系统调优时有重要参考价值。

这里补充一个知识点，叫作**长尾效应**：少部分类数据在一个数据模型中占了大多数样本，在数据模型中呈现出长长的尾巴的现象。TP99 相当于分位值图中最上面的尾巴，可以看到，1% 用户访问的耗时比其他 5 个桶加起来的都要长。此时若只通过指标查看某个接口的平均响应时间，意义不大，因为这 1% 的用户访问已经超出平均响应时间，平均响应时间已经无法反映数据的真实情况了。这时用户会出现严重的量级分化，而量级分级正是系统调优时需要着重关注的。

这种情况一般很难通过拨测、自行访问来复现，但通过观测这一部分内容、借助链路追踪的方式可以定位到问题的根源。

## 常见指标

以下列举工作中常见的指标，通过这些指标可以了解系统运行的情况。

### QPS

Query Per Second，每秒查询的数量。QPS 在系统中很常见，如今已不再单单与“查询”这个特殊条件绑定，也与请求量挂钩，可以通过这个值查看某个接口的请求量：假设 1 秒内进行了 1 次接口调用，就可以认为在这 1 秒内 QPS 增加了 1。如果系统进行过压测，也可以估算出 QPS 的峰值，从而预估系统的容量。

### SLA

Service Level Agreement，服务等级协议。SLA 是服务商和用户之间的协定，规定了服务的性能和可用性。根据这种可量化的协定，双方可以更详细地制定细则，比如没有达到一定可用性时的赔偿方案。阿里云之前就规定了短信发送的 SLA 方案，并制定了详细的赔偿明细，具体细节可查看： https://help.aliyun.com/document_detail/63935.html?spm=5176.13910061.sslink.1.64b922b2xSbOT9。

最常见的可用性指标类似于“四个九”“五个九”：四个九指的是 99.99%，五个九就是 99.999%，以此类推。SLA 并不是一个固定的数值，“四个九”“五个九”只是代表系统可以保持稳定的时间；SLA 会因为成功数与请求数的不同而变化，可能是 95%，也可能是 80%，需要实际计算。

计算某个接口的 SLA 时，指定一段时间区间，然后依据以下公式计算：

```text
总计成功数 / 总计请求数 = 百分比(%)

```

总计成功数由判定标准得来。例如 HTTP 请求，状态码 200 就可以算是成功，此时成功数 +1；Dubbo 不出现异常时成功数 +1。这也不是一定的，根据公司内部的 HTTP 响应状态码等内容还可以更细粒度地规定，例如将响应结果中 json 的 code 值为 1 定为成功，满足条件时成功数同样 +1。

SLA 算出来之后与系统稳定性工作直接相关。例如要求保证某个服务 1 年的 SLA 是“五个九”，以 1 年为时间单位，即可算出服务不可用的时间：

```text
1 年 = 365 天 = 8760 小时
三个九 = 8760 * (1 - 99.9%) = 8.76 小时
四个九 = 8760 * (1 - 99.99%) = 0.876 小时 = 0.876 * 60 = 52.6 分钟
五个九 = 8760 * (1 - 99.999%) = 0.0876 小时 = 0.0876 * 60 = 5.26 分钟

```

1 年内，该服务不可用的时间为 5.26 分钟。

由此可见，想要保证越多的“九”，就要保证服务稳定、缩短服务错误的时间，因此 SLA 对系统稳定有重要的意义，“九”也成了公认的标准。

### Apdex

Application Performance Index，应用性能指数。Apdex 会用响应耗时判断用户对应用性能的满意度，并通过可量化的形式展现出来。通过这个量化的值，可以快速感知用户的满意程度。这也是首次和用户的使用体验相结合的一个指标。

Apdex 分为 3 个区间：

- 满意（Satisfactory）：对于这样的响应时间十分满意，感觉十分流畅。
- 容忍（Tolerating）：稍微慢了一点，但是可以接受。
- 失望（Frustrating）：实在太慢，快要放弃了。

有了这样的指标信息，无论是否参与了这个服务的开发、是否懂技术，都可以了解这个服务是否令人满意。

衡量用户是否满意的值需要一个时间单位 T，表示当小于或等于多少秒的时候用户的感觉非常好。映射到 3 个区间内，Apdex 规定：符合满意程度的是 1T，符合容忍程度的是 1T~4T，失望则大于 4T。由此即可得知当前请求属于哪个区间。

计算某个时间段内的 Apdex 值使用以下公式：

```text
(满意数量 + (容忍数量 / 2)) / 总数 = Apdex 值

```

通过这个公式可以得出服务整体的 Apdex 值，这个值在 0~1 的范围内，值越接近 1 代表用户满意度越高。通过这种可自定义阈值的计算方式，衡量业务的满意度也有了一个可量化的标准。

## 实践要点

- 指标波动是排查问题的第一信号：问题出现后各指标数据先于其他可观测信号出现波动，据此可以圈定问题方向（如句柄占满导致 HTTP 请求卡死的案例）。
- 平均值在长尾分化场景下会失真，系统调优时应重点关注 TP90/TP99 等分位值以及量级分化情况。
- 长尾问题难以通过拨测、自行访问复现，需借助链路追踪定位问题根源。
- 利用压测结果估算 QPS 峰值，进而预估系统容量。
- SLA 的“成功”判定标准可结合公司内部的响应状态码、业务 code 等细化，并据此精确计算可用性预算（如“五个九”对应 1 年内不可用时间不超过 5.26 分钟）。

## 小结

统计指标高度可量化，既支撑业务分析，也反映系统运行状态。其核心类型为计数器、仪表盘、直方图与摘要（分位值），其中摘要与长尾效应揭示了平均值之外的关键信息；常见指标包括 QPS、SLA 与 Apdex，SLA 以“几个九”作为可用性的公认标准，Apdex 则将用户满意度量化为 0~1 的指数。

# 监控指标：如何通过分析数据快速定位系统隐患？（上）

## 问题场景

系统的隐患往往先体现在数据上，而不是故障现场。监控指标就是把这些数据系统化采集的方式：按照数据来源自用户侧到服务器侧的顺序，监控指标依次分为**端上访问**、**应用程序**、**组件**和**机器信息**四类。本篇覆盖前两类（端上访问与应用程序），组件与机器信息两类见下篇。

## 端上访问指标

端上访问一般可细分为 App 和网页两类。二者虽然都属于端上，但侧重点不一样，主要区别有以下 4 点：

- **访问方式**：App 需要在应用市场下载使用，下载会花费一定的时间；网页只需要输入一个地址或直接利用搜索引擎即可访问。

- **兼容性**：从使用者的角度来讲，兼容性十分关键。App 一般具有很好的兼容性，虽然 Android 厂商相对较多、每个厂家可能有一些细微差别，但整体兼容性不会有太大问题；网页需要考虑各种不同的浏览器厂商，有些差别还比较大，例如最常见的 IE8 相对而言就比较难做兼容。

- **内容变更**：显示的内容需要变更时，App 往往需要很长的周期，因为要进行发版、应用审核、上架，最后才到用户更新，所以为了方便，在 App 内嵌入 H5 是很常见的做法；网页则是实时的，开发人员将更改后的内容上线后，用户访问时即为最新内容。

- **使用体验**：从用户使用体验角度来讲，App 往往体验更好，作为手机上的应用，在使用、消息推送等方面都有更好的支持；网页相对差一些，更多承担展示信息的功能，因为其属于浏览器应用中的内容，可获取的权限相对较少。

### App 指标

App 是目前更受用户青睐的形态，其常见监控指标如下：

- **崩溃率**：崩溃指应用在运行过程中出现强制关闭的现象。崩溃会打断用户操作的体验，造成业务中断；崩溃率过高还会导致用户留存率下降、品牌口碑变差等问题。

- **卡顿率**：App 中的卡顿率指 UI 刷新时出现卡顿的情况。卡顿率过高会让用户感觉 App 运行很慢，降低使用体验。

- **卸载率**：卸载说明用户很难适应产品，卸载率可以说是最能检验用户是否满意一款产品的指标。卸载率的升高可能由多方面因素导致，例如推送过多打扰用户、严重 bug 影响使用体验等。

### 网页指标

网页更关注显示体验，其中一般包含这样一些指标：

- **白屏时间**：用户访问页面时，从输入地址栏之后到首次出现内容的时间，也叫首次渲染时间。白屏时间的长短直接影响使用体验，白屏时间长会让用户认为网站比较慢；若出现较长时间的空白，可能是服务器响应慢或网络波动等原因造成的。

- **首屏时间**：用户输入地址栏之后到首个屏幕渲染完成（页面内容完全显示）的时间。首屏时间受资源下载速度影响，首屏渲染速度越快，用户的使用体验越好。

### 通用网络指标

端上的资源请求一般会经历以下步骤：DNS 寻址、与服务器建立连接、发送请求、请求响应。这些步骤均可被监控，很多主流拨测软件也提供此类统计功能——拨测软件利用分布在各个不同地方的机器发起请求，来测试网络情况。

App 和网页在发送请求和获取数据内容的过程中，除上述指标外，还有以下指标需要关注：

- **DNS 响应时间**：访问地址向 DNS 服务器发起请求，到 DNS 返回服务器 IP 地址信息的耗时。

- **建立连接时间**：客户端通过 TCP 与服务器建立连接的时间。

- **SSL 握手时间**：SSL 握手指与 HTTPS 服务器端建立连接的整个过程，其耗时即 SSL 握手时间。

- **首字节时间**：从客户端发送请求到接收服务器首个字节的时间，因此它包含了服务器响应耗时信息。

- **下载内容时间**：接收到内容后，内容被完整下载完成的时间。

通用指标并不限于 App 或网页，通过它们可以完整掌握客户端从请求发起到接收完整内容的耗时情况。前三项（DNS 响应时间、建立连接时间、SSL 握手时间）属于基础功能，优化时更偏向运维层面；首字节时间和下载内容时间，则更多由后端开发人员优化。

## 应用程序指标

应用程序需要监控的指标更多，可分为请求、数据处理、组件协作资源、业务指标、VM 监控五个部分。其中**业务指标**偏向于开发人员编写代码时自定义控制的指标内容，详见《指标编写：如何编写出更加了解系统的指标？》。

### 请求

请求指端上通过 HTTP 等方式发起的请求，与请求相关的指标有以下几类：

- **QPS**：代表请求数量，是了解系统使用情况最快的指标。

- **状态码**：针对 HTTP(S) 的请求，一般会细化响应状态码的数量指标：

  - 2xx：响应被正常处理。一般系统会使用 JSON 返回数据，而 JSON 可能带有不同的业务状态码，监控时可依据具体情况定制。

  - 3xx：请求被重定向。出现大量重定向，一般表明该网页存在一定的问题，且存在降低用户使用体验的风险。

  - 4xx：无法访问，常见的如 403 无权限、404 未找到。4xx 说明业务边界存在问题，可能导致身份信息出现问题或页面访问异常。

  - 5xx：后端比较常见，服务器内部出现错误时，通常伴随访问出错。

- **请求时间**：从服务器发起请求到返回数据内容的总计时间，一般也叫响应耗时。响应耗时可用于了解具体某个接口或页面的执行情况；通过直方图和分位值图等形式展示响应耗时，能更直观地了解耗时的整体分布情况。

- **SLA**：在 HTTP 请求层面，SLA 一般可以通过总请求数与 5xx 请求数之间的运算获得。

- **独立用户数**：指总共有多少个用户访问。用户数越多，说明产品使用人数越多、用户基数越大。通过独立用户数还可以发现一些问题，例如爬虫在抓取数据时，可能出现 QPS 偏高而用户数很少的情况。

### 数据处理

数据处理多与第三方框架交互，请求数据处理时会涉及很多内容，其中比较关键的指标类型如下：

- **RPC**：应用程序普遍采用微服务架构，系统之间必然存在 RPC 调用，调用会涉及消费者和提供者两类角色，可分别记录两者的调用次数、成功率、耗时等信息。之所以要分别记录，以成功率为例：消费者一般设有超时时间，假设超时设置为 2 秒，提供者第 3 秒才返回数据，提供者认为自己调用成功，但消费者可能早已将其认定为超时。因此消费者的成功率更能体现真实执行情况，提供者的数据则更多作为参考。

- **熔断限流降级**：熔断、限流、降级是高流量场景下必不可少的内容，例如阿里的 Sentinel、Netflix 的 Hystrix。通常基于 RPC 或其他资源的使用情况设置相应阈值进行限流或熔断。熔断/限流/降级的次数与阈值本身也是很好的观测指标，通过它们可以更清楚地了解阈值设置是否正确、触发后的处理是否正确等。

- **数据源**：系统会涉及各种各样的第三方数据源，例如最常使用的 MySQL、ElasticSearch、MongoDB。应重点关注与这些系统交互时的执行耗时、调用频次。与数据库交互出现较高耗时，通常代表业务逻辑也出现了问题。

- **自定义业务指标**：以上固有指标早已不能满足对系统的观测需求，因此经常会自定义业务指标，以便更细化地了解系统。

### 组件协作资源

应用程序会与各种第三方框架进行资源利用，资源利用效率很大程度上决定了应用的执行效率。资源可分为五大类：RPC、数据库、队列、缓存和请求。

- **RPC**：与数据处理中提到的 RPC 类似，组件协作资源中的 RPC 同样涉及资源利用。以国内使用最多的 Dubbo 为例，其每一次发送请求和接收请求都利用线程池完成。使用 Dubbo 时，可以通过监控线程池资源信息掌握系统运行状态，相关指标包括总计的**线程数**、**活跃线程数**等。生产环境中曾出现过这样的情况：一个 Dubbo 接口耗时较长，且线程池没有做到良好隔离，导致当前服务的资源完全处于等待状态，无线程可以处理其他业务请求，最终造成线上故障。

- **数据库**：业务系统与数据库之间的交互一般由专门的 TCP 链接资源保持并处理，每个数据库都有各自的数据协议。通常将链接池化以提高资源使用效率、避免浪费，并监控**活跃数**、**闲置数**和**总共的资源数**。资源缺少时，需要注意是否为配置不足导致的资源减少。

- **队列**：针对**异步**和**大量需要处理的任务**，通常会使用队列以起到**削峰**的作用。因此需要监控任务的**发送量**、**处理量**、**Lag 值**、**处理耗时**，确保不会出现大面积延迟进而影响业务处理的情况。

- **缓存**：缓存框架在系统中经常使用，正确使用它可以减少部分数据库查询的压力，从而提升接口的响应性能，例如部分教育平台经常使用 Redis 作为部分数据的查询缓存。缓存中通常更关注命中率、内存使用率、数据量等指标，尤其是命中率——命中率越高表明接口性能越高，而接口性能越高则响应耗时越短。

- **请求**：系统经常依赖其他需要进行 HTTP 请求等方式通信的第三方服务，例如微信创建订单需要通过 HTTP 请求，创建订单后再返回数据。这里同样要监控其请求数、耗时情况等指标。虽然这是常见现象，但与第三方服务通信时一定要做好熔断降级策略，最好不要因为第三方服务的不稳定导致自身业务主流程受到阻碍。

### VM 监控

Java 程序一般运行在 JVM 上，JVM 上有很多指标，其中以下几个需要重点关注：

- **GC**：通常收集 GC 的次数、每次 GC 时收集的内存空间大小等数据。

- **内存**：内存可分为年轻代、老年代、堆外、Meta 区四个部分。如果老年代长期占有率较高，则有可能存在内存泄漏问题。可分别观测这四个部分的当前值和最大值，来了解内存的使用量。

- **CPU 占用率**：指进程启动时的 CPU 占用率，通过该值可以看出应用是否频繁使用 CPU。出现问题时，如果 CPU 占用率居高不下，它可能并不是问题的根源，而仅仅是任务处理不过来的表现。

- **类加载**：程序启动后一定会进行类的加载和卸载，监控当前总共的类加载和类卸载数量也是观察问题的良好方式。如果持续出现大量类被加载的情况，有可能是使用动态代码生成框架时出现了问题；大量类被加载会不停占用 Meta 区，最终导致元空间溢出（OutOfMemoryError: Metaspace）。

- **线程**：线程数据也是必不可少的观察指标之一。程序代码都运行在线程上，如果当前活跃线程数过多，会使 CPU 资源过高，最终因资源占用问题导致任务执行缓慢。一般监控线程中的活跃线程数、总计线程数、等待线程数等指标。

## 关键要点与实践建议

- 端上指标以用户体验为核心：App 关注崩溃率、卡顿率、卸载率，网页关注白屏时间与首屏时间；通用网络指标（DNS、建连、SSL 握手、首字节、下载内容）则构成请求全链路耗时分解。

- 指标优化分层明确：DNS 响应时间、建立连接时间、SSL 握手时间偏向运维层面优化；首字节时间、下载内容时间、请求耗时、数据源耗时偏向后端开发优化。

- RPC 成功率统计必须区分消费者与提供者两个视角，以消费者视角（含超时判定）的数据为准，提供者数据作为参考。

- 需要重点警惕的异常信号：大量 3xx/4xx 状态码、数据库交互耗时偏高、线程池无线程可用、队列出现大面积延迟、缓存命中率下降、老年代长期高占用、类加载量持续增长、活跃线程数过多。

## 小结

端上访问与应用程序两类指标构成了从用户体验到服务运行状态的观测面：端上侧关注崩溃、卡顿、卸载与渲染耗时等体验类指标，应用程序侧围绕请求、数据处理、组件协作资源和 JVM 运行状态展开。结合组件与机器信息两类指标（见下篇），即可形成完整的监控指标体系，通过指标数据分析定位系统隐患。

# 监控指标：如何通过分析数据快速定位系统隐患？（下）

## 概念说明

监控指标体系通常划分为四个层面：**端上访问**、**应用程序**、**组件**与**机器信息**。端上访问指从网页或 App 中发起的访问，应用程序指接收到端上请求后的业务处理程序；**组件**既是数据最终存储的位置，也是数据中转的地方，**机器信息**则是服务赖以运行的基础资源。组件的好坏很大程度决定了应用程序的好坏，机器的处理性能不够好也会直接影响服务的运行情况。

组件协作资源中常见的类型包括数据库、队列、缓存，此外还有处于请求链路入口的**网关层**。本文对这 4 类资源的运行指标以及机器统计信息逐一说明。

## 组件监控指标

### 数据库

数据库的种类很多，既有传统的关系型数据库，也有当下常用的 NoSQL，各自实现方式不同，需要监控的指标也不同。以下 7 项指标在各类数据库中具有共通性，且一旦出现问题会极大影响接口性能，可以帮助初步认定问题的原因。

- **QPS**：每秒查询次数。几乎每个数据库都会涉及查询请求。通过观测该指标，可以快速了解系统对数据库的查询量，以及是否需要优化查询语句。

- **查询耗时**：用于判断系统的查询效率是否处于正常区间。如果出现"**慢查询**"现象需要及时处理，例如 MySQL 中可以通过增加索引解决部分查询效率问题；ElasticSearch 则需要筛选出查询慢的语句再逐个优化。

- **TPS**：每秒事务数，一般指对数据的添加/删除/修改操作的处理速度。TPS 不同于 QPS，它涉及修改数据。由于大多数数据库在设计时的初衷以查询为主，TPS 在处理时会花费更多的时间。

- **主从延迟数**：主从架构是很多数据库都会采用的集群方式，其中许多实现方式基于**从机器**向**主机器**同步数据来完成，例如 MySQL。因此同步时的主从延迟数是一个十分关键的指标：延迟数高时，业务系统读取数据如果恰好命中延迟较高的数据节点，系统就有可能出现错误。

- **连接数**：业务系统与数据库的连接达到一定数量后，可能造成数据库处理缓慢。该指标通常与数据库的最大连接数做对比，通过对比可以体现数据库的资源分配是否均衡。

- **数据量**：单个表的数据量超过某个数值后同样会出现性能问题。例如阿里巴巴《Java 开发手册》规定，单表超过 500 万条数据后就要做分库分表处理。数据量过大会影响查询与插入效率，这一规定同样适用于当下的很多数据库。

- **VM 监控**：某些组件基于特定语言开发，因此还存在与开发语言对应的指标监控。例如 ElasticSearch 基于 Java 开发，还需要监控 JVM 的信息。

除以上指标外，每类数据库因其实现方式还会细化出更多具有独特性的统计指标，可按需补充。

### 队列

队列通常用来处理异步和大量的任务，需要监控的通用指标一般有以下 4 个：

- **Lag**：目前待消费的数据量大小。如果该值持续增长且过大，说明消费能力已无法满足生产速度。此时的处理思路一般包括：减少生产者生产的内容、加快消费者速度，条件允许时增加机器运行消费者也是有效的选择。

- **发送数量**：生产者生产数据的内容大小。该值增长越快，代表生成内容的数量越多。如果该值突然飙升得比较高，也应注意是否存在无用内容的发送。

- **消费数量**：消费端消费生产者内容的数量。一般队列中间件中都有分区的概念，通过消费数量可以清楚看到每个分区的消费情况。如果某个分区的消费数量明显不足，则需要针对该分区的消费实例做特殊观察。

- **分区数**：通常在 1 个 topic 中会将数据分区以提高并行消费速度，分区的数量即分区数。分区数同样是一个很关键的概念：一个 topic 的分区数较少，意味着可以交给消费者消费的线程数也不多。

### 缓存

正确使用缓存可以减少部分数据库查询的压力，从而提升接口的响应性能。缓存中有以下关键指标：

- **响应时间**：该指标的值通常很低，因为缓存大多数时候存储在内存中。如果该值偏高，说明使用方或缓存出现了问题，此时需要从更细的维度跟踪问题原因。

- **缓存命中率**：即请求中**查询到数据的请求**除以**请求总数**得到的百分比。百分比越高说明命中率越高，程序也会有更好的性能；如果命中率相对较低，则要考虑是否写法出现问题，或者该内容是否适合使用缓存。如果不适合，可以考虑不引入缓存——新增一个组件会增加运维和开发的成本。

- **网络延迟时间**：缓存的调用频率通常不低，交互中出现较高延迟会影响业务系统与接口性能，因此保证网络延迟低是一个很关键的因素。

- **已使用内存**：缓存一般存储在内存中，对内存使用量有严格要求。未满足要求时，缓存系统会执行淘汰策略（例如 LRU），执行后可能导致缓存命中率下降；而内存使用过高时，缓存系统会被操作系统 kill。

- **资源链接**：业务系统除与数据库建立连接外，还会与缓存系统建立连接，因此同样需要监控连接情况。常用的缓存 Redis 本质上也是一种 KV 类型的 NoSQL 数据库。

- **缓存数量**：数据库中已有的缓存数量也是一个很好的指标。当内存使用达到配置阈值时，缓存会按一定算法淘汰数据，通过缓存数量可以清楚看到系统中新增缓存与被移除缓存的数量对比，进而判断系统是否一直在有效利用缓存提升性能。

### 网关层

请求从客户端过来，一般会先经过网关层，由网关层统一接收管理所有请求。网关层可监控的指标包括：

- **请求相关**：网关层同样需要关注 QPS、状态码、请求耗时等信息，其中往往会记录请求整体的执行情况，这里的数据是最全、最准的。

- **错误数**：网关层高于应用层，应用层的请求一般由网关层转发。当网关层出现错误数飙升的问题时，请求信息可能根本不会进入应用层，因此在应用层可能无法定位问题的原因。

- **请求处理**：网关层有相关的请求处理机制，监控请求处理相关的数据也十分关键，例如总请求数、正处于"读"状态的请求数、正处于"写"状态的请求数、正在排队的请求数。如果出现大量排队现象，说明网关层已经处理不过来了，一般可以通过增加网关机器解决。

## 机器信息监控指标

机器的处理性能不够好会直接影响服务的运行情况，因此机器统计信息也是监控体系的重要组成部分。机器信息的指标可以按照组成部分分为以下几类：

- **CPU**：CPU 的运行情况是应用程序中最重要的指标之一。一般重点关注 **CPU 的整体使用率**，再细分为**系统侧**、**用户侧**的使用率；同时关注系统的 **Load 情况**——Load 值越高，说明系统承受的处理任务越多，执行也会更缓慢。

- **内存**：内存大小影响程序可使用的内存空间，对**重内存使用**的程序尤其明显。内存层面需要关注**整体使用率**以及 **swap 区的使用率**。一般不建议使用 swap 区，因为它会利用磁盘空间代替内存，可能影响程序性能。如果 swap 区使用率较高，可以考虑将其关闭，通过升级内存提高程序性能。

- **磁盘**：一般应用程序中，磁盘更多用于**日志记录**和**临时缓存文件记录**。与 CPU 和内存一样，关注磁盘使用率即可。

- **网络**：网络情况是应用中的重中之重，无论是连接组件还是微服务间的 RPC，到处都有服务器之间的通信。一般重点关注**出/入流量**：到达网卡限制的大小后，通常只能通过扩容服务解决，因为网卡本身的提升是有限的。此外还应监控**网络丢包率**、**连接错误数**等信息，用于在网络出现问题时判断是否为网卡原因。

- **I/O**：在 Linux 平台中，任何网络请求、消息或其他内容都基于文件构成，因此 I/O 在 Linux 中无处不在。重点关注 I/O 的**文件读取/写入速度**、**耗时**、**次数**等最能直观体现读写能力的信息；同时关注**使用率（util）**——磁盘使用率过高说明应用对磁盘的使用量很大，很有可能因磁盘问题导致应用程序故障。

- **句柄**：随着 I/O 的使用，还需要关注句柄的**使用量**。程序中出现资源流未关闭的情况时，可能导致句柄数激增，最终句柄耗尽、影响程序执行。实践中曾出现因 HTTP 流未关闭使句柄耗尽、程序无法再次发起 HTTP 请求的案例。

## 实践要点

- 指标是保证系统稳定不可或缺的一环。它同日志一样，在每个层面都有大量的指标数据，需要分层建立完整的指标体系。
- 组件指标的共通性是排查问题的起点：先通过 QPS、耗时、命中率等通用指标初步认定问题原因，再深入到组件特有的细化指标。
- 机器指标与组件指标应结合观测：接口性能异常时，既可能源于数据库慢查询、缓存命中率低，也可能源于 CPU、内存、网络或磁盘 I/O 的瓶颈。
- 主从延迟、句柄数量等指标往往对应"隐性故障"：读到延迟数据、句柄耗尽等问题在代码层面不易察觉，只能通过监控提前发现。

## 小结

监控指标体系覆盖端上访问、应用程序、组件与机器信息四个层面。组件层面关注数据库的 QPS/查询耗时/TPS/主从延迟/连接数/数据量/VM 指标、队列的 Lag/发送数量/消费数量/分区数、缓存的响应时间/命中率/网络延迟/内存/连接/缓存数量，以及网关层的请求、错误数与请求处理状态；机器层面关注 CPU、内存、磁盘、网络、I/O 与句柄。掌握这些指标的含义与异常表现，是快速定位系统隐患的基础。

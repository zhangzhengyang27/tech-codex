# 链路监控：为什么对于系统而言必不可少？

## 背景与问题

在日志、统计指标之外，可观测性还有一个重要环节：链路追踪。它记录一个请求在系统内部流转的完整过程，回答“这个请求到底经过了哪些服务、每一步花了多久、哪里出了问题”。本篇从服务之间的依赖关系入手，逐步拆解 Span 与链路图的概念，并归纳链路追踪的实际作用。

## 什么是链路追踪

### 服务之间的依赖

数据来源分为很多层（端上访问、应用层、数据库层等），这些层恰好对应一个请求完整执行链路中的各个节点。以一个“获取系列信息”的请求为例，各节点的角色如下：

- **A 代表端上访问**。比如网站发起的一个 Ajax 请求——以某教育平台为例，在系列详情页中获取系列信息就是一个 Ajax 异步数据获取请求。
- **B 可以理解为应用层**，比如 Tomcat。应用层接收从 A 过来的请求信息，进行最简单的、类似判断用户身份信息的操作。B 操作了 Redis：如果做 Session 共享，此时就可以把 Redis 作为存储方案。
- **C 同样可以理解为应用层**。就目前微服务化的基础架构来讲，**一般也会将接口层和业务逻辑层分开，之间通过 RPC 的方式通信**。这样做的好处在于**耦合度降低**：接口层只需要专注和各种端上的交互，业务逻辑层只需要专注业务处理，无须关心上层是哪里调用过来的，同时可以很好地进行代码复用。以某教育平台为例，这一部分就可以理解为 B 通过 Dubbo 框架调用业务逻辑层，获取系列信息数据。
- **D 为数据库层**。数据基本都采用数据库的方式存储，D 就可以理解为通过 ID 获取系列的详细数据后返回。

通过这样一张依赖关系图，可以清晰地了解一个请求完整的执行链路：**从端上开始，到应用层后，通过各种组件的访问最终获取到数据**。真实的业务会比这个示例更复杂，但原理是相通的。

### 调用流程

把上述链路的执行流程按时间轴展开，并对每一步标注消耗的时间（**这个时间不是固定的**，会依据场景和性能的不同而变化），就得到了调用流程图：从左到右代表时间，**字母**和对应的“**字母'**”代表每个阶段的开始和结束。

图中各段耗时的含义如下：

- A 到 A' 代表请求从开始到结束的整体时间。
- A 发起请求到 B 接收到数据总共花费了 50ms，B 在计算时总共花费了 250ms，最终 B 将数据聚合返回给 A，这个过程花费了 20ms。因为这一步会涉及内外网的数据传输，所以会有一定的时间损耗；真实环境中的耗时会比这个低，这里只是举例说明。
- B 在接收请求后，分别去请求了 Redis 和 C 应用（Redis 在这里用 R 代表），请求时分别花费了 10ms 和 20ms。Redis 和 C 应用在接收请求后，又分别使用了 10ms 和 210ms 来处理业务逻辑并返回数据。
- C 与上面类似，通过 10ms 来进行 D 的调用和处理，这个流程总共花费了 210ms。

从这张图中可以清楚地看到每一个应用和其他应用交互时的总耗时与自身耗时，进而了解它们之间通信和自身处理的耗时、流程和数据走向。剩下的问题是：**怎样将这张图以数字化的形式展现出来，并通过这种形式定位问题**？解决方式就是“**链路图**”。在理解链路图之前，需要先了解 Span 的构成。

### Span 的构成

Span 对应调用流程图中的**字母**和对应的“**字母'**”，代表一个操作行为。Span 一般由以下几个部分构成：

- **开始时间**：代表这个操作从什么时候开始的时间戳。
- **结束时间**：同样是时间戳，代表操作执行完成的时间。通过**开始时间**和**结束时间**这两个时间戳，可以计算出这个操作的耗时时长。
- **ID**：主键。在一个链路中这个 ID 是唯一的，概念上与 MySQL 中的主键类似。
- **父级 ID**：一个 Span 中有自己的 ID 和父级 ID，可以理解为树形的概念——父级 ID 是树干，ID 则是枝叶。通过树状图可以更方便地绘制图片和查询操作之间的依赖关系。
- **操作名称**：用于指明操作的内容名称，可以快速了解是在进行什么操作。比如 Dubbo 这类 RPC 调用可以使用方法签名，HTTP 访问可以使用访问路径。名称还会用在其他地方，例如聚合数据时，就可以将同一名称的数据聚合在一起。
- **操作类型**：用于指定当前操作的类型，一般分为下面 3 类，基本囊括了各种操作类型：
  - **入口**：**别的请求到达系统时，就可以认为是入口操作**。比如 Tomcat 接收到外部的 HTTP 接口请求。
  - **出口**：**系统向别的系统发出了请求，通常是获取数据等通信操作**。比如通过 RPC 调用了其他系统，或者向数据库发起了一次查询，都可以认为是出口操作。
  - **本地**：**本地进行了某些操作，不涉及任何需要远程通信的组件，是业务系统调用的本地处理**。比如通过 EhCache 查询了本地缓存，或是本地进行了一次文件操作。

### Span 之间关系

链路在大多数情况下是一个树形结构。日常开发过程中，一个入口下面一般会有多个出口操作，比如通过 Kafka 发送消息、Redis 写入缓存、MySQL 查询数据。

那么会不会有多个父节点的情况？其实是有的。比如 Kafka 在消费的时候，可能会一次性消费一个 Topic 下面的多个链路信息，由此就可以将这个消费的链路理解为一个“森林”：它同时拥有多个父节点，并且每个父节点对应着具体的某个链路。

### 链路图

在讲解了 Span 的基本属性后，接下来看链路图。链路图中的每一行代表一个操作的基本单元，也就是**Span（跨度）**，**链路由一个 Span 的集合构成**。每个 Span（图中为一行长方形）包含 4 个信息，从左到右依次是：**SpanID**、**父级 SpanID**、**当前开始时间**（从 0 开始）和**当前 Span 的耗时**。

对链路图中流程的解读如下：

- 假设第一行的 Span 代表在网页中发出请求，可以认定为出口请求，所以 A 的 Span 是出口类型的操作。SpanID 从 1 开始，没有父级 Span，所以 parentID 认定为 0；开始时间是 0ms，当前 Span 的总共耗时是 320ms。在真实的场景中，**当前开始时间是系统当前的时间戳**，**耗时也会根据场景和性能的不同而变化**，这里使用 0ms 和 320ms 只是为了说明。
- 在第二行中，B 接收到 A 传递来的请求，所以是入口类型的操作。由于网络损耗导致 B 在 50ms 时才接收到请求，所以当前操作的开始时间是 50ms。根据层级可以得知 B 是 A 的子节点，所以 B 的父级 ID 对应 A 的 ID，因此 B 的 parentID 是 1；ID 是自增的，所以 B 的 ID 为 2。
- 在第三行中，因为 B 进行了一次 Redis 操作，而 Redis 需要连接别的数据源，所以这里的 Span 算为出口类型的操作。网络耗时和 Redis 处理各花了 10ms，所以总共的耗时是 20ms。当然，**如果再细一步的话，同样可以在当前行的下面画出 Redis 中的入口 Span，这取决于链路追踪系统的能力，是否可以细粒度到 Redis 组件内部**。
- 第四行则代表 B 向 C 应用发出了一个请求，所以同样是出口操作类型。需要注意的是，第三行和第四行的父级 SpanID 是一致的，这代表它们的父级应用是一样的，都是 B 入口下面的操作；又由于它们开始的时间相同，所以代表它们分别启动了两个线程来进行操作。

为什么不是同步执行的？**如果是同步执行，这张图就需要改变为先完成 Redis 操作，在 Redis 结束后，才会开始第四行的操作**。

## 链路追踪的作用

链路追踪是可观测性中不可缺少的一环，因为它会监控服务运行中的每一步，可以通过它快速了解程序真实的执行状态。具体作用如下：

- **链路查询**：即使接手一个全新、一无所知的项目，也可以**通过某个入口查看链路，快速了解当前程序的运行情况**，并且可以通过很直观的图来展现：到底是哪里比较耗时、出现错误时是哪个操作导致的，等等。
- **性能分析**：通过聚合链路中的数据，结合操作名称，**快速得知系统的运行容量、耗时情况等**。
- **拓扑图**：通过对链路信息的**聚合分析**，将分析得到的数据形成拓扑图，**直观地了解整个系统的构成**。
- **依赖关系**：同样是链路的聚合分析，还可以了解到操作之间的依赖关系，从而快速感知操作之间的重要等级。将依赖关系与限流熔断技术相结合，可以帮助更快地构建一个企业级的链路保护措施。
- **跨应用/语言**：链路追踪的各个内容都是**不限制语言**的，每个语言都有它自己的实现。在一个大型的企业中，几乎不可能保证所有的系统都使用同样的语言，利用链路追踪不限语言的特点，可以将不同语言的代码串联到一起。

### 采样率

监控这么大的数据量，会很消耗系统资源吗？答案是肯定的。所以现在已有的大量链路追踪系统中，都存在**采样率**的设定，其作用就是**只采集一部分的链路信息，从而提升程序性能**。

在真正的环境中，没有必要采集 100% 的链路信息：很多时候大量的链路信息是相同的，需要关注的只是其中**相对耗时较高**或者**出错次数较多**的部分。当然，有些时候也会为了防止漏抓错误而进行全量的链路追踪。**是否需要进行全面的链路追踪，取决于在观察成本和性能之间的权衡**。

## 小结

链路追踪以树形（极端情况下为森林）结构组织 Span，每个 Span 记录开始/结束时间、ID、父级 ID、操作名称与操作类型，据此还原请求的完整执行链路。它的价值覆盖链路查询、性能分析、拓扑图、依赖关系与跨语言串联五个方面；工程上通过采样率在观察成本与性能之间取得平衡。

# 性能剖析：如何补足分布式追踪短板？

## 背景与问题

链路追踪是可观测性中必不可少的一环，但它的最小单位是 Span，每一个 Span 代表一个操作——这个粒度仍然太粗。当程序执行缓慢或不稳定时，链路追踪常常无法给出代码级别的答案。性能剖析（Profile）正是补足这一短板的手段。

## 链路追踪的短板

要解决 Span 粒度太粗的问题，链路追踪的实现中一般有 2 种方式：

- **代码埋点**：在代码中预埋点，通过侵入式的方式记录链路数据。

- **字节码增强**：在字节码生成之后，再对其进行修改，从而为其添加功能。比如像 Java 这类语言，就可以通过字节码增强，而不是人工侵入式的方式记录链路数据。

这两点的区别在于**是否是侵入式的**：埋点的方式虽然灵活，但依赖性较高；字节码增强的形式不需要代码层介入，但仅能支持一部分应用框架。这两种方式能够实现链路追踪，并且可以大面积使用，因为框架都是通用的。

**但通用的链路监控方案的实现方式都逃不过面向切面编程，因为它们只能做到框架级别**。这又会导致程序执行缓慢或者不稳定时，可能无法查询到原因。一个典型的场景是：在链路监控时发现某个接口内部有很长的一段时间没有 Span 信息，虽然知道了这个情况，却仍然无能为力。

这时一般只能通过**在业务中手动增加埋点**的方式进行更细粒度的 Span 开发，但这种方法有几个缺点：

- **增加埋点成本高，很难全面覆盖**。这种方式只适用于具体的业务场景，如果其他的业务场景也存在类似的问题，就需要在其他的业务场景中再次埋点。如果一次没有把需要埋点的位置加全，还可能涉及多次上线，降低系统的稳定性。

- **大量埋点占用 CPU 和内存资源**。虽然每个埋点的性能损耗都不高，但随着项目不停地迭代，埋点数量会越来越多，性能损耗也会越来越大，长期下来对系统性能造成持续影响。而且埋点后还需要开发人员定期移除不需要的埋点信息，极其浪费人员和时间成本。

- **动态增加埋点技术不可靠**。既然人工难处理，便有了动态增加埋点技术：在某个特定的包下，对每个方法的执行都增加埋点，无须手动修改代码。但问题也很明显——因为会给所有地方都增加埋点，性能损耗可能比人工方式更为严重，甚至因埋点过多导致内存增长，最终造成系统崩溃，影响线上程序运行。

- **无法深入 JDK 层面**。即使通过十分合理的方式解决了上面两个问题，也只能在业务级别做埋点，没有办法深入 JDK 中的某个场景——因为对 JDK 中的某个方法做埋点可能造成巨大的延迟风险；对于 JDK 中的底层工具类，处理不当还会出现很多不可预料的错误，那时就不光是影响程序效率这么简单了。

## 性能剖析的原理

要解决上述 3 个问题，可以换一个角度思考，不被链路追踪中 Span 的思想框架限制。关键在于两个事实：

- **在编程语言中，基本所有的代码都是运行在线程中的，并且在大多数情况下，一个请求是由单个线程处理的**。比如 HTTP 或者 RPC 等框架接收到请求之后都会交给单独的线程去处理。

- **大多数的编程模型是基于线程这一个概念去实现很多功能的**。无论是现成的框架，还是底层的 JDK，例如 Dubbo 中的 RPCContext、Java 中线程安全的随机数生成器 ThreadLocalRandom。

既然都基于线程，而线程中基本会伴随着方法栈——每进入一个方法都会通过压入一个方法栈帧来保存——那么**定期查看方法栈的情况就可以确认问题**。例如常用的 jstack，其实就是实时地对所有线程的堆栈进行快照操作，来查看当前线程的执行情况。

结合这两点事实与链路中的上下文信息，就得到了性能剖析的做法：**周期性地对执行中的线程进行快照操作，并聚合所有的快照，获得应用线程在生命周期中的执行情况，从而估算代码的执行速度，查看出具体的原因**。这样的处理方式就叫作**性能剖析**（Profile）。

其原理可以从两个维度理解：

- **第一行代表线程进行快照的周期情况**：每一个周期都可以认为是一段时间，比如 10ms、100ms。周期的时间长短决定了对程序性能影响的大小，因为在进行线程快照时程序会暂停，当快照完成后才会继续进行操作。

- **第二行代表需要观测的方法的执行时间**：线程快照只能做到周期性的快照获取，虽然可能并不能完全匹配方法的真实执行时间，但通过这种方式，相对来说已经很精准了。

### 与埋点相比的优势

- **整个过程中不涉及任何埋点，性能损耗相对稳定可控**，不用担心因埋点过多导致的业务系统压力和性能风险；同时因为不涉及埋点，不再需要重复增加或删除埋点，大大节省人力开发和上线时间。

- **无须区分底层 JDK、框架还是业务代码**，在运行时它们都是代码，不需要对它们进行区分。

- 结合当前链路中的上下文信息，**只需要对指定链路的执行时间之内进行性能剖析**，而不用对每个线程定时进行线程快照操作，因此减少了程序性能的损耗。

- 通过**精准到代码行级别**的方式定位执行缓慢的原因，减少研发定位问题的时间。

- **只在需要的时候才使用**，平时不会用到这样的功能，因此性能损耗是稳定的。

## 性能剖析的展现方式

利用性能剖析工具获取到链路中的线程快照列表之后，一般可以通过 2 种方式查看线程聚合的结果信息：**火焰图**和**树形图**。

### 火焰图

火焰图是在 Linux 环境中比较常见的一种性能剖析展现方式，展现形式有很多种，最常用的是 CPU 火焰图。

CPU 火焰图的解读方式如下：

- 每一个方格代表一个方法栈帧，方格的长度代表它的执行时间，方格越长说明该栈帧执行的时间越长。
- 在某一个方格中增高一层，说明这个方法栈帧中又调用了某个方法的栈帧。
- 最顶层的函数是叶子函数，叶子函数的方格越宽，说明这个方法在这里的执行耗时越长。

以一张简化的图为例：a 方法是执行的方法，其中 g 方法是执行时间相对较长的。

无论是完整的 CPU 火焰图还是简化图，它们都通过图形的方式快速定位到执行缓慢的原因，但也存在一些问题：

- **不方便查看函数名称等信息**。虽然可以做一些交互上的处理（比如浮动时展示），但在进行栈帧跟踪时，查询还是不方便。

- **很难发现非叶子节点的问题**。在简化图中可以发现，d 方法除了 e 和 f 方法的调用以外，其实还有一段时间是自己消耗的，并且没有被处理掉；这一问题在完整的火焰图中会更加明显。

### 树形图

为了解决上述 2 个问题，就有了另外一种展现方式——**树形图**。树形图将方法的调用堆栈通过树形图的形式展现出来，对开发人员来说相对直观，可以通过树形图快速查看整体的调用情况。针对火焰图中的问题，树形图有很好的解决方法：

- 使用这样的形式，栈帧很容易识别，并且之间的调用关系也很容易理解。

- 对于非叶子节点的耗时，可以直接查看到自身耗时的数据。

但树形图也有一些自己的问题：

- **内容显示相对较长**，在方法栈相对复杂的情况下，这一问题会更为突出。

- **栈帧深度较多时，容易显示不全信息**。

所以在使用树形图时一般会配合前端的展示优化，比如只显示 topN 中耗时较高的内容，或者支持搜索功能。

### 两种方式的侧重

火焰图和树形图没有绝对的好坏之分，只是相对应的侧重点不同：

- **火焰图更擅长快速展现问题所在**，能够最快速地找到影响最大的问题的原因。

- **树形图则更倾向于具体展示栈的执行流程**，通过执行流程和耗时统计指标来定位问题的原因。

## 实践要点

- **默认方案不追求业务级细粒度埋点**：代码埋点、字节码增强、动态埋点各有覆盖与成本问题，细粒度需求优先交给性能剖析。
- **剖析范围绑定链路上下文**：只对指定链路执行时间内的线程做快照聚合，避免全量定时快照的性能开销。
- **周期设置权衡精度与暂停成本**：快照周期越短结果越精细，但程序暂停越频繁；10ms、100ms 是常见量级。
- **两种展现方式配合使用**：先用火焰图快速锁定影响最大的热点，再用树形图核对栈执行流程与非叶子节点的自身耗时；树形图配合 topN 过滤与搜索功能使用。

## 小结

链路追踪的短板在于 Span 粒度太粗，而三种埋点补足方式（业务手动埋点、动态埋点、深入 JDK 埋点）分别受制于成本覆盖、可靠性、延迟风险。性能剖析以"请求由线程处理、方法执行伴随方法栈"为前提，通过周期性线程快照加聚合，实现无埋点、无语言/框架区分、可精确到代码行级别的耗时分析。火焰图适合快速锁定热点，树形图适合细看执行流程，两者互补构成性能剖析的完整展现体系。

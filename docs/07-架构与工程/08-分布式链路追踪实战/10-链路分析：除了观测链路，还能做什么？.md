# 链路分析：除了观测链路，还能做什么？

链路追踪的核心是跟踪应用中的请求数据，而链路分析把这些数据的使用范围从“观测单条链路”扩展到三个方向：指标聚合、绘制拓扑图和数据定制化。性能剖析解决了链路追踪中的短板，链路分析则回答“还能从链路数据中获得什么”。

## 指标聚合

链路追踪会跟踪应用中的请求数据，将这些数据聚合即可获得统计指标——这是链路分析除观测链路之外的第一个功能。通过分析链路，部分指标无须再通过手动埋点统计，相比手动埋点具有 3 点优势。

- **更精准**：链路追踪中的数据面向框架内部，相比在业务代码中编写的计时逻辑，覆盖面更广，计时也更精准。

- **更动态**：传统方式要求对每个功能都进行埋点，功能迭代时难免遗漏。链路分析由程序自动解析链路中的数据信息，无须手动埋点，实现动态化。

- **更通用**：链路追踪的概念是统一的，所有需要分析的链路都可以基于同一套数据内容处理，生成多种相同的指标信息。无论代码在哪个层面、使用哪个框架、哪种语言，都不会被这些烦琐内容局限。

在指标体系中，数据一般分为 3 个维度。

- **服务**：指具有一段相同代码、相同行为的服务。通常一个项目认定为一个服务，但多个服务之间可能存在组合的数据关系。

- **实例**：指服务在多进程、多机器部署时的运行实例。在微服务时代，为了提高服务的吞吐率和灰度上线时的稳定性，服务一般不单独部署，而是采用集群形式。因此一个服务往往对应两个或更多的实例。

- **端点**：是与实例平级的概念，一个服务下会有多个端点。端点可以理解为 span 中定义的操作名称，每个操作的操作名称就是一个端点，大多数时候端点都是入口操作。

当然，通过链路来分析统计指标存在局限：**这些指标来源于链路数据，所以只能观测到通用的数据信息，无法对指标进行定制化统计**。定制化的指标仍需要开发人员在代码层通过埋点统计。链路分析提供通用数据信息，代码埋点收集定制化的指标数据，两种方式合理搭配才能让可观测的维度最大化，丰富分析数据、查看问题时的内容参考。

### 链路分析可获取的 8 类指标

链路分析可获取的数据共有 8 类：QPS、SLA、耗时、Apdex、Percentile、Histogram、延迟和 topN。它们在链路追踪中的具体用法如下。

- **QPS**：链路分析中最常用，可以清楚地记录每个服务、实例、端点之间的请求量。通过某个服务或端点中实例之间的请求量，可以查看负载是否均匀。

- **SLA**：根据 QPS 和具体端点的错误次数，可以统计出服务、实例或者接口的 SLA 情况，能够统计到某个组件具体到服务的 SLA 执行情况。SLA 还会提供来源信息，在评估问题影响时起到关键作用。

- **耗时**：Span 中的数据包含开始时间和结束时间，因此可以计算出耗时情况。针对某个接口，可以统计出接口中每个 Span 在整体耗时中的占比，让性能优化聚焦在相对耗时较高的 Span 上。

- **Apdex**：有耗时数据就有对应的 Apdex 值。通常在分析之前预定义不同类型服务的耗时基准时间单位，然后采用统一标准设定。

- **Percentile**：基于耗时信息可以计算出相应的百分位值。一般依据长尾效应，根据 P95 或 P99 中的耗时情况做针对性优化。

- **Histogram**：通过直方图可以根据耗时信息指定多个耗时区间，辅助查看耗时分布范围。

- **延迟**：Span 有出口和入口的理念，可以据此了解网络通信情况。例如 Dubbo 调用时，消费者发起请求的时间是 A，提供者接收到请求的时间是 B，通过 B-A 即可获取网络延迟时间。延迟较大时可能是网络通信问题，会影响整体服务效率；也可能是机器之间时钟不同步导致，不过一般服务器之间的时间差别很小，部分数据可以忽略。

- **topN**：根据上述几部分数据，可以分别绘制出相对缓慢的服务、实例或端点，优先优化相对缓慢的部分，提高整体效率。

## 绘制拓扑图

链路分析的第二个功能，是根据从链路中分析出的数据关系绘制拓扑图。拓扑图可以呈现服务之间的关系与数据走向，通过链路分析绘制出的拓扑图具有**可视化**、**数据化**、**动态性** 3 个优点。

- **可视化**：通过可视化的形式，开发者能以全局视角审视整个系统，更好地分析数据之间的依赖关系和数据走向——哪些点可以优化、系统瓶颈可能在哪里，都可以从拓扑图中得到线索。

- **数据化**：将拓扑图中的数据与统计指标结合，两类数据可以放在同一位置展示。例如通过 QPS 可以看出哪些服务产生的请求更多、请求来自哪里；出现问题时，通过 SLA 可以看出受影响服务的范围有多大。通过服务、实例、端点之间的相互引用，可以快速分析出相应的依赖占比——依据一个接口的依赖占比识别强依赖与弱依赖，进而更好地进行熔断降级。

- **动态性**：功能迭代时，拓扑图会基于链路数据动态分析，始终与实际架构保持一致。这一特性也支持通过时间维度查看系统的演进过程。

与指标一样，拓扑图中的数据也分为服务、实例和操作 3 个维度。每个维度显示的内容不同，作用也各有侧重。

- **服务**：通过服务关系拓扑图可以了解整个系统的架构、服务与服务之间的依赖，还可以借助全局数据内容提供“下钻点”，从大范围的一个点切入，直到发现问题的根源。借助拓扑图还能以全局视角优先优化相对依赖度高、耗时更高且更为重要的服务。

- **实例**：当两个服务之间存在依赖关系时，可以继续下钻，查看具体的进程与进程之间的依赖关系。在实例之间加上统计指标数据，还可以看到两者相互通信时的具体关系。通过实例之间的拓扑图，可以确认各实例是否都在正常工作，出现问题时快速定位到可能异常的实例。例如 Dubbo 请求调用时，可以通过依赖和指标数据查看负载均衡器是否正常工作。

- **操作**：操作与端点是同一概念，与实例处于同一级别。通过拓扑图可以了解操作之间的业务逻辑依赖，并结合统计指标了解延迟和依赖程度。依据这部分数据可以看到某个接口在业务逻辑上依赖了多少个下游操作——依赖越多，程序出现错误的概率越大。

## 定制链路与数据

链路追踪的最后一个功能，是链路与数据的定制化。链路与程序代码息息相关，让链路携带业务中的数据可以更好地辅助理解链路。

链路中最基本的数据单位是 Span。一个 Span 中记录的可能是接收到的某个请求，也可能是与其他第三方组件的一次通信，比如 Tomcat、Dubbo。但 Span 往往只知道操作名称，不知道来源 IP 地址、访问 UA 信息之类的细节。此时可以给 Span 增加自定义数据，丰富链路数据。可添加的数据内容分为 3 类。

- **通信数据**：通过框架中的相关数据内容，可以了解业务在通信时产生的数据，例如 MySQL 中可以存储相关的 SQL 语句，Redis 处理时可以记录相关的命令。这部分数据能还原与组件交互时发送了哪些请求——出现“慢查询”时，可以通过通信数据获取请求的 SQL,进而对“慢查询”进行优化。

- **业务数据**：将自己业务中的数据保存到链路中，例如操作时的用户 ID、操作目的等。这部分数据帮助理解链路内容，并可以根据这些内容模拟出对应的真实场景，更好地定位问题产生的原因。

- **日志+异常信息**：链路在真实代码中执行，可以将当时的日志框架与链路数据相结合，看到当时的执行日志；出现异常时，也可以在链路中结合异常堆栈信息快速定位问题。以某教育平台为例，获取系列信息时出现接口访问错误(如查询 MySQL 数据库超时)，通过观察出错时的具体链路数据，结合出错 Span 的堆栈信息，即可快速得知错误原因。

通过增加这些数据内容，可以更容易地了解代码的真实执行情况，包括其中的参数数据。链路收集到这部分数据后，有两种处理方式。

- **数据展示**：在链路信息展示时展示定制化的数据，定位问题时更加得心应手。

- **数据检索**：通过业务数据和通信数据检索链路信息。最常见的场景是通过用户 ID 检索，查询出该用户的请求链路——有客服反馈问题时，可以根据用户 ID 快速检索出包含指定业务和通信数据的数据链路。

## 小结

链路分析在链路追踪之外提供三项能力：一是将链路数据聚合为 QPS、SLA、耗时、Apdex、Percentile、Histogram、延迟、topN 共 8 类指标，覆盖服务、实例、端点三个维度，比手动埋点更精准、更动态、更通用；二是基于链路数据绘制可视化、数据化、动态的拓扑图，支撑依赖分析与熔断降级决策；三是为 Span 定制通信数据、业务数据、日志与异常信息，并通过数据展示和数据检索两种方式消费。通用指标靠链路分析，定制指标靠代码埋点，两者结合才能让可观测维度最大化。

# 黑白盒监控：系统功能与结构稳定的根基

## 概念说明

**黑盒监控指的是监控外部用户可见的系统行为**，**白盒监控指的是监控内部暴露出来的指标信息**。二者一个对外，一个对内，在功能上有 2 点区别。

- **监控角度不同**：黑盒更偏向于外侧，通过某个功能或者具体的某个接口来观察，它并不清楚内部是如何实现的；白盒则更倾向于从内侧监控，它是代码层面的，从内部的视角来解读整个系统。

- **面向对象不同**：黑盒更倾向于看到问题的现象，比如某个端口挂掉了无法再提供服务，它面向的是当下所发生的故障；白盒则更加倾向于面向产生问题的原因，比如在日志中可以通过堆栈信息分析出故障的根源。

需要注意：**白盒监控有时面向问题，有时面向问题的原因，它的监控对象会根据监控的内容改变**。假设白盒在接口层反映接口耗时比较长，此时可以认定白盒面向的是“耗时长”这一问题；但同时，白盒监控也会监控到与这个接口相关联的数据库出现了严重的慢查询，慢查询是接口耗时较长的原因，这时候就可以认定白盒是面向原因的。

## 监控数据

### 黑盒监控

黑盒中的监控一般可以细分为如下 4 类内容。

- **端口状态**：**通过程序检测具体业务的端口是否存活**，可以简单确定程序是否在提供服务。如果端口都无法连接，那么肯定是系统出现了问题。通常会结合进程检测使用：如果进程存活，但是端口不存在，则说明程序可能存在某些问题，没有将服务暴露出来。

- **证书检测**：**通过检测证书是否有效，确认用户是否可以正常访问**。现在的网站服务基本都是使用 HTTPS，如果证书出现了问题，则可能是浏览器认定为不安全，阻止了用户访问。

- **探活**：**通过心跳检测来判定服务是否存活**，比如定期通过具体的某个接口检测服务是否运行正常。如果在这里出现异常，则说明系统存在问题。Dubbo 中就有心跳机制来保证双方的链接，这也算是一种探活。

- **端到端功能检测**：相对复杂一些。**通常是通过定期进行端到端的测试，结合业务流程感知业务是否在正常执行**，例如通过 UI 或者接口自动化测试工具，确认页面中返回的数据是否正确。

黑盒监控更偏向确认功能是否可用，理解门槛相对较低，即便是从来没参与过项目的开发人员，也可以对这些数据进行验证、确认。

### 白盒监控

日志、指标、链路追踪这 3 类数据源正是白盒监控中重要的数据维度：

- **日志**：通过日志记录可以了解程序的运行状态，以及程序中是否存在异常。

- **指标**：数值形式的指标可以帮助了解系统中的数据走向、流量情况等。

- **链路追踪**：可以细粒度到程序的代码行级别将链路可视化，帮助了解程序的执行流程。

系统中会大量运用白盒监控来查看问题或分析问题产生的原因。但黑盒并非没有价值：黑盒所监控的内容更偏向用户。当系统出现问题时，通过白盒可以查看到问题的原因，但并不一定知道这个问题在用户那里是如何表现的——凭想象推测可能与真实情况有一定出入，此时黑盒就可以展现出用户端的真实表现形式。黑盒和白盒之间没有优劣对比，各自有各自偏向的重点，将两者结合起来使用才是监控中最有效的方式。

## 黄金指标

***Google SRE*** 中提出了一个概念：**黄金指标**。**黄金指标是 Google 针对大量分布式监控的经验总结，可以在服务级别帮助衡量终端用户体验、服务中断、业务影响等层面的问题**，包含 4 类指标信息：**错误**、**延迟**、**流量**和**饱和度**。无论监控的数据再复杂、再令人眼花缭乱，都可以套用在这 4 类上。

每类指标都可以按照**基础监控**和**业务监控**这两个维度落地：

- **基础监控**：多指监控云主机、进程等机器信息，一般不代表服务的真实运行状况。比如在以集群方式部署的服务中，某台服务器中出现了一些问题，基础监控会报告这一台服务器的故障，但仅一台服务器的故障并不代表这个服务无法运行。

- **业务监控**：指监控业务系统内部的执行状态。通过业务监控可以更多地了解程序内部或者组件内部的执行情况。通常将基础和业务结合起来看，才能更全面地了解系统执行情况。

### 错误

**错误指的是当前系统所有发生过的错误请求**，可以通过错误请求个数计算出相应的错误率。只要是程序运行，就肯定会因为某些原因而产生错误——可能是其他系统的组件导致的，也可能是程序代码自身的问题。

以 HTTP 接口为例，有 3 种比较常见的错误类型：

- **显示错误**：指**可以立即看出来的错误**。比如在 HTTP 请求中，响应状态码出现 500，即可认定为显示错误。

- **隐式错误**：指**表面上显示完全正确，但是在数据中已经出现异常的错误**。响应状态码为 200 通常可认定为成功，但如果业务在返回的数据结构中被认定为错误，那这个错误就是隐式的。

- **策略导致错误**：与第二种类似，都是**在表面上显示正确，但是可能因为某种策略被认定为错误**。比如某个接口在 1s 时返回，因为已经接收到了数据，所以被认定为成功；但策略限制 500ms 内才算完成，因此这个数据会被记录为错误。在 RPC 的提供者消费者模式中这个情况也很常见。

从基础和业务两个维度监控错误的方式：**在基础层中**，可以把系统宕机、进程或者端口挂掉、网络丢包这样的情况认定为故障；**在业务层中**，监控的内容相对较多，比如 Dubbo 调用出错、日志中出现的错误，都可以被认定为“错误”的指标。

### 延迟

**延迟指的是服务在处理请求时花费的时间**，常说的接口耗时、响应时长指的就是延迟。这里需要注意一点：**一般在统计延迟时，并不会把成功或者错误的信息分开统计**。这样的统计方式会更难了解到真实的情况，所以在统计时常常需要把它们区分开。以一个 HTTP 接口为例，响应状态码正确的（200）和错误的（500）请求耗时一定会有差别，因为正确的请求走完了全流程，而错误的可能只进行了某一部分流程，所以需要把这两类请求的耗时在统计时分别记录。

**在基础层中**，可以监控 I/O 等待、网络延迟等信息；**在业务层中**，则可以监控接口调用的耗时、MySQL 查询的耗时等信息。

延迟在系统中是一个十分关键的指标：很多时候服务并不会产生错误，但很可能会有延迟。延迟在 HTTP 层会影响用户体验，在数据库中出现高延迟会导致请求错误，这是需要着重关注的。

### 流量

**流量是表现系统负载情况的数据**，比如常见的 QPS、UV。通过这个指标可以确切了解服务当前承受了多大的压力、请求量和处理量有多大。**常说的容量规划，其实是流量规划**。通过流量，可以得知当前系统运行的状况，是否到达了它的负荷上限。

**在基础层中**，常见的监控指标有磁盘的读写速度、网络 I/O 情况等；**在业务层中**则有请求量、MySQL 查询次数等。

通过观察流量相关的指标，可以了解到是否存在突增突降的情况，从而判断是否遭受到了攻击或者是否在进行某些活动。

### 饱和度

**饱和度通常是指某个资源的使用率**，一般通过容量的最大值和现在的使用量，来判断这个容量是否“满”了。某些程序如果资源饱和度过高，可能会导致执行缓慢，甚至无法使用。比如 CPU 使用率达到 100% 时会出现执行缓慢；Dubbo 进行 RPC 调用时，如果线程池没有可用的线程数，则会使业务受到阻碍。

**饱和度一般也会配合其他指标一起使用**。比如在使用网络 I/O 时，网卡都有流量上限，通过流量上限值和当前网络 I/O 的使用情况，可以得知相应的饱和度。**饱和度是衡量系统是否到达瓶颈的关键**。饱和度过高时，就需要考虑扩容、减少数据量或其他降低饱和度的操作。

**在基础层中**，需要监控的指标有 CPU 使用率、I/O 使用率、句柄使用情况等；**在业务层中**则有线程池的线程使用数、JVM 中的堆内存使用率等信息。

## 实践要点

- 黑盒面向现象、面向用户，白盒面向原因、面向内部，二者没有优劣之分，必须结合使用。
- 白盒监控的对象会随监控内容变化：既可能呈现“问题”（接口耗时长），也可能呈现“原因”（数据库慢查询）。
- 错误类型要区分显示错误、隐式错误与策略导致错误，仅看状态码会漏掉隐式错误。
- 统计延迟时必须将成功请求与错误请求分开统计，否则无法反映真实情况。
- 容量规划的本质是流量规划，观察流量的突增突降还可辅助判断攻击或活动。
- 饱和度需要结合容量上限（如网卡流量上限）来计算，并作为扩容、降量等操作的触发依据。

## 小结

黑盒监控面向外部用户可见的系统行为，白盒监控面向内部暴露的指标信息，二者共同构成系统功能与结构稳定的根基。Google SRE 的四大黄金指标——错误、延迟、流量、饱和度——为服务级别的监控提供了统一框架，且每一类都需要在基础监控与业务监控两个维度上分别落地，再结合使用才能全面掌握系统执行情况。

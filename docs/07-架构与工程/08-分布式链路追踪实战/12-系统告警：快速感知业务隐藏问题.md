# 系统告警：快速感知业务隐藏问题

## 问题场景

在没有告警时，通常依靠人工定期查看相关指标或链路数据，再到程序上确认。虽然人工也能监控，但有时难以判定是否真的出现了问题——某一个单独指标的上升或下降并不代表系统出现了错误；即便确认了问题，没有完善的处理流程，也很难规定问题具体该如何处理，例如针对某个具体问题应该做什么、出现问题后运维人员如何通知开发人员去寻找原因。除此之外，人工监控还有 2 个无法避免的难题：

- **无法保证 24 小时都有人监控**。涉及人工，就不可能全天候有人盯着指标，会存在有事情走开或忘记查看的情况。
- **人工成本高**。项目上线后，让开发人员定时定点观看业务指标数据并不现实，因为开发人员还承担着其他业务的开发工作。

告警是针对上述问题的有效解决方案：它可以早于用户发现且及时地定位、反馈问题，再通过告警的规则和流程规范进行有效处理。

## 方案与原理：告警的作用

告警的主要作用体现在以下 4 点：

- **通过监控数据，早于用户发现问题**。告警系统通过对数据进行监控，可以在出现问题时第一时间告知相关项目的开发人员。开发人员可以在用户反馈之前，通过告警查看问题原因并解决，从而极大提升用户使用体验、降低用户流失风险。

- **通过聚合相关指标快速定位问题**。运维人员发现问题后，可以通过告警将指标等相关内容聚合显示给开发人员，让开发人员快速定位问题产生的根本原因，而不是在海量数据中盲目翻找。

- **制定个性化的告警规则**。通过告警系统，业务开发人员和运维人员都可以根据数据来源制定自己的告警规则，而不仅是参考现有数据。开发人员可以自定义指标和内容进行告警，让告警与真正的实际业务结合起来；运维人员也可以更好地管理和制定符合公司的服务指标监控。

- **制定告警规范**。告警的流程和规范由运维和开发人员在告警之后共同协定完成，例如告警后的处理流程如何规范化、如何查看历史错误情况以避免问题再次发生。数据确实产生告警后，运维和开发人员只需遵循这样的规范，问题处理就会快捷高效。

## 方案与原理：告警数据来源

告警中的数据一般源于监控系统：对数据统一聚合计算、分析，到达一定阈值后告警自动触发。数据来源可以按照黑/白盒监控的划分来分类（黑/白盒的完整定义见《黑/白盒监控：系统功能与结构稳定的根基》）。

### 黑盒

在黑盒监控中，偏向于以系统使用者或对系统完全未知的状态观察整个系统，告警来源可以从**端口状态**、**证书检测**、**服务探活**、**拨测**、**端到端功能检测**几方面入手：

- **端口状态**：通过观测端口的运行情况快速感知程序是否在真实运行。出现这类问题一般第一时间告警——业务场景中系统无时无刻不在和其他系统进行通信操作，端口出现问题会造成很严重的后果。

- **证书检测**：通过检测证书快速感知证书服务是否可用。HTTPS 技术已十分成熟，能对数据起到很好的保护作用，可以说是一个网站的根基；现在的请求一般都基于 HTTPS，证书出现问题时应及时处理，否则各端都无法发送和处理请求。

- **服务探活**：保证业务系统或第三方组件处在可用状态。不可用可能是端口存在但服务一直处在"假死"状态，这一般是在与第三方组件交互时出现问题导致的。

- **拨测**：目前互联网中普遍存在的服务质量检测工具，通过多个不同地区的节点打开网站，获取不同地区对网站的访问速度，其中就包含端上访问的通用指标（见《监控指标：如何通过分析数据快速定位系统隐患？（上）》）。假如拨测发现某些地区访问网站会出现拦截、禁止访问等状态，就需要运维人员与相关地区的服务商联系，排查问题所在。

- **端到端功能检测**：通过场景、流程化的方式调用业务，检测业务是否处在可用状态。它基于业务功能的检测机制，一般由专门的测试开发团队完成。如果端到端功能检测显示某个操作有问题，说明用户在业务场景中执行该操作时会出现问题；通过端到端检测，开发人员可以快速定位问题的具体操作流程，甚至深入到接口级别，再结合白盒数据快速定位问题产生原因。

黑盒告警大部分由运维人员接触较多，也有像端到端检测这类需要业务人员接入的方案。出现黑盒类型告警时一定要第一时间恢复，因为它们与真实业务关联最为紧密；这类告警一般数量不多，但一旦出现往往都是比较严重的问题，例如端口问题会导致整个服务不可用，拨测告警则证明某些地区存在无法访问的问题。

### 白盒

白盒监控是业务系统中最常用的。其数据来源相对较多，但基本都涵盖可观测体系的 3 个组成部分：日志、指标、链路追踪。通过这 3 个部分，可以全面且完整地了解告警内容和问题产生原因。排查问题时，通常将白盒作为查看问题和指出错误原因的重要方式。

#### 日志

日志是开发人员在发生故障后第一个想到的内容。日志中通常记录当时的异常堆栈信息，开发人员一般也会在异常时记录相关参数信息或数据流转的关键数据。发生错误时，可以将链路追踪中的数据内容和每个应用节点中的日志内容结合起来查看。

在真实场景中，一般会将日志文件收集到统一的日志平台，并提供便捷的查询能力，例如通过日志内容和关键词搜索。通过收集过程中筛选或收集后检索，可以对符合条件的日志内容进行告警。

#### 统计指标

统计指标是监控告警中的重中之重，告警的大部分数据都源于统计指标，例如 MySQL 调用耗时的增加会对数据查询造成影响。通过统计指标可以清晰看到当前实时的运行情况，接口耗时、流量情况等可参考黄金指标（见《黑/白盒监控：系统功能与结构稳定的根基》）。

在真实场景中，一般将统计指标聚合到一个系统中，设定一定的阈值规则来告警，例如把"接口的 HTTP 请求时间超过 1s"认定为一条规则，请求时间超过 1s 时系统自动告警。实际操作会比这更复杂，阈值规则的设计直接影响告警质量。

#### 链路追踪

链路追踪是可观测系统三大支柱的最后一个，可以在分析问题时从全局角度审视整个链路，确认具体是哪个环节出现问题、具体的产生原因是什么。

在白盒中，链路追踪可以分析出服务、实例、端点 3 个维度的指标（同《链路分析：除了观测链路，还能做什么？》），可能基于操作名称，也可能基于某个 tag 值，可通过这些方式进行检索。

在真实场景中，一般采取与统计指标相同的策略，即设定阈值：对符合阈值的数据查询出相关链路数据，再告知具体业务开发人员进行优化。例如某个 HTTP 接口出现大量 500 错误，此时需检索出该接口中出现 500 错误的链路数据，统一告警告知业务开发人员处理。

## 方案与原理：故障分类

告警出现后，将故障分类可以帮助运维人员和开发人员根据不同故障类型选择不同处理方案，也可以根据不同类型制定更有针对性的告警阈值。一般来说，故障可分为**错误**、**延迟**、**流量**、**资源** 4 个类别：

- **错误类**：某个组件、服务或接口出现执行错误。这类错误比较直观，一般日志中都有对应的错误详情。但需注意，错误类故障有时只代表表象，并不能代表真正发生的原因——例如接口执行超时，此时就需要更细致地观察执行链路里下游的延迟原因。

- **延迟类**：服务之间的通信耗时，或服务本身的耗时。这类故障一般需结合具体内容来看，例如 MySQL 出现慢 SQL 时，需要定位具体的 SQL 再进行优化。突然出现类似告警通常是系统出现问题的前兆，要多加注意。

- **流量类**：服务本身所承担的访问压力。这类故障更多反映当前产生的现象，通过它们可以看到当前服务的请求情况，例如 QPS 突然大幅下跌或上涨、服务调用量突然掉到 0。

- **资源类**：组件或基础服务中的资源使用情况。通过这部分数据可以看出哪些资源出现了问题，再寻找问题原因，例如机器中 CPU 使用率突然升高可去 CPU 层面寻找；Dubbo 中执行线程数突然增多可查看是否有请求堆积。

## 关键要点

- 这 4 类故障通常不会单独出现，很多时候会彼此组合发生：表象上某个接口出现高延迟，底层原因可能是某个系统的资源数使用不足，划分故障类型时需注意追查根因。

- 四类故障与黄金指标（错误、延迟、流量、饱和度）高度对应，告警实践也是基于这几类指标展开的。

- 黑盒告警与真实业务关联最紧密，出现后必须第一时间恢复；白盒告警则承担定位根因的职责，排查时以日志 + 链路追踪结合查看为标准动作。

- 告警规则由数据来源决定：黑盒面向"系统对外是否可用"，白盒面向"系统内部哪里异常"，两者互补构成完整的告警覆盖面。

## 小结

系统告警解决了人工监控"判定难、处理流程缺失、无法 24 小时值守、人工成本高"四个问题，其价值体现在早于用户发现问题、聚合指标快速定位、个性化告警规则与统一告警规范四个方面。告警数据来源按黑/白盒划分：黑盒包含端口状态、证书检测、服务探活、拨测与端到端功能检测；白盒包含日志、统计指标与链路追踪。告警触达后的故障可分为错误、延迟、流量、资源四类，且常组合发生。在此基础上进一步设计合理的告警规则与阈值，是保证告警质量的关键。

# 指标体系：Prometheus 如何更完美地显示指标体系？

## 背景与问题

统计指标可以了解系统当前的执行情况，并通过可视化的形式展现出来；它还可以和告警相结合，在出现异常时及时反馈。对于监控系统而言，指标体系是其中不可缺少的一环。Prometheus 是这一领域的事实标准，理解指标体系的通用原理，是掌握 Prometheus 用法的前提。

## 指标在监控系统中的作用

在一个比较完整的监控系统中，指标主要发挥以下作用：

- **通过查看指标数据了解指标的走向，从而更好地优化系统、流量等内容**。以流量为例，假如有人在爬取数据，此时请求量指标可能会出现有规律的突增突降，这时可以结合访问日志分析出对方爬取的方式，然后结合具体的业务场景来处理。

- **通过导出或者查询已有数据，将一段时间内的数据以 dashboard 的形式进行展示**。这也是目前主流的一个使用场景，比如"双十一"淘宝的销售额。

- **基于预先配置好的告警规则，定时检测数据是否符合规则，并对其进行告警处理**。这是指标监控中最为重要的一个目的。

## 指标体系的原理

目前大多数的监控系统底层基本都分为 4 个步骤：**数据收集**、**指标存储（聚合）**、**指标查询**、**规则告警**。

### 数据收集

监控系统从服务器或者服务中获取数据，并将其统一收集到监控系统中。

由于统计指标是变化的，并且变化的频率较高，实时发送数据是不现实的，一般会将数据内容缓存在组件中，定期收集数据。目前主流的数据收集方式有两种：

- **push，推送模式**：定期主动将数据内容发送给收集器端。

- **pull，拉取模式**：业务系统主动暴露相关的数据指标信息，收集器端利用服务发现能力感知所有可能的服务列表，并定期通过发送请求的方式获取数据内容。

两者没有好坏之分，可以从以下 5 个方面对它们做出区分，作为不同场景下的选型依据：

- **数据采集**：推送模式下，业务系统一旦启动，便会定期主动将数据信息上报；拉取模式则是暴露指标，由收集器决定是否获取数据。

- **可扩展性**：推送模式可以随时扩展新的节点信息，实现线性增长；拉取模式的工作负载由业务系统的数量决定，如果业务系统数量不断增加，收集器系统也只需要动态增加机器。

- **安全性**：推送模式本身就是安全的，业务系统可以防止遭受到远程攻击；拉取模式一般采用轮询协议，可能有潜在的访问攻击。

- **灵活性**：推送模式相对不灵活，因为它只能定期发送数据；拉取模式则可以随时获取数据。

- **系统耦合**：推送模式对于系统耦合性相对较高，因为它需要获取到收集器列表，并对其进行发送数据处理，如果收集系统出现问题，数据可能会丢失；拉取模式的耦合性则相对较低。

### 指标聚合

收集指标数据之后，收集器就可以对已有的数据内容聚合，然后保存。

指标聚合是将数据按照主体部分，以时间维度按照秒或者分钟级别来聚合，然后根据不同的数据类型计算相应的数值——比如仪表盘类型的数据只保存最近一次的值。最后将得到的数据存储到数据库中（通常为时序数据库）。

### 指标查询

数据存储到对应的数据库之后，就可以通过界面或者类似 SQL 的形式查询数据。

通常在查询时还会涉及时间范围和指标计算的工作。一个指标监控系统中最为重要的，是其**数据查询的灵活度**和**支持聚合函数的种类**，比如常见的分位值、最大值、平均值等方式的数值计算。

把这些数值与图表结合，可以定义自己的 dashboard，从而更快了解系统当前的运行情况。

### 规则告警

监控系统可以通过统一的配置来进行告警，其中包含以下几个维度的数据信息：

- **检测时间**：多长时间检测一次告警内容，时间越短说明检测的周期越密集。通常可以指定为 1 分钟，如果业务系统对数据比较敏感，则可以适当降低时间，比如 30 秒。

- **告警规则**：进行告警规则的配置，通常会包含统计指标的名称、查询方式和阈值构成。检测的时候会判断当前指标查询出的结果值是否符合告警规则，如果符合则说明达到了告警条件。

- **通知方式**：符合告警规则后会进行相关的告警操作。比如通过 HTTP 的回调方式告知业务系统，或者通过钉钉、企业微信这类信息推送的方式告知业务研发人员。

通过收集数据，将数据指标聚合存储后制定相关规则；告警系统查询相关指标，判断是否符合告警条件，符合则进行告警。能完成这样一个流程，就算是一个相对完整的指标监控系统。

## Prometheus

Prometheus 是一个开源的服务监控系统和时间序列数据库，它是一款基于统计指标的服务监控系统，可以很方便地进行统计指标的存储、查询与告警。下面按照上述四步原理（数据收集、指标聚合、指标查询、规则告警）说明 Prometheus 的系统架构，再讲解其中的常见功能。

### 系统架构

Prometheus 的架构图可以从数据收集、指标聚合、指标查询和规则告警 4 个步骤来理解：

- **数据收集**：Prometheus 主要采取拉取模式获取数据，它提供了完善的服务发现机制，结合 K8s 的 API 可以动态感知服务的创建与销毁，通过可配置的方式定期拉取服务列表的数据。对于一些短期存在的任务，Prometheus 同样提供了 PushGateway，让业务程序能够推送数据，再由收集系统来收集。

- **指标聚合**：Prometheus 服务器接收到数据之后，会通过 TSDB 存储引擎聚合数据，然后存储到磁盘上。TSDB 中的数据结构即时序数据库的结构。

- **指标查询**：Prometheus 提供了一套完整的查询语言 PromQL，通过 HTTP 服务的形式对外提供查询接口和基础的展示界面。通过接口，可以将数据与 Grafana 界面相结合。Grafana 是一个强大的可视化监控指标展示工具，可以自定义页面中所需要展示的内容，定制属于自己业务的关键指标的 Dashboard。

- **规则告警**：基于 Prometheus 中的配置方式管理所有的告警内容。符合条件时，会通过 Alertmanager 推送相应的告警内容给业务系统，比如 Email、PagerDuty 等；也可以通过 HTTP 的方式发送给业务系统，让业务系统自行处理告警信息。

### 业务数据收集

将业务系统中的相关指标接入 Prometheus，一般会选择 Micrometer 作为首选 SDK。Micrometer 类似日志系统中的 slf4j：它通过一套统一的 API 集成多种指标系统，比如 Prometheus、Elastic、Datadog 等。

如果项目是基于 Java 语言和 Spring Boot 系统开发的，通过声明 spring-boot-starter-actuator 和 micrometer-registry-prometheus 这两个依赖，引入后会自动加入一些基础的指标内容，比如 HTTP 层调用次数、本机的 CPU、内存等资源的使用情况。

完成配置后，系统就可以对外暴露统计指标信息。其中 Spring 的 actuator 是一个完整的监控组件，除了收集的统计指标信息，还可以上传服务相关的信息。合理利用这两部分信息，可以让系统更具可观测性。

对外暴露统计指标信息后，可以在代码中声明 **MeterRegistry** 对象，使用它声明自定义的统计指标，然后发送到 Prometheus 中统计。下面这段代码展现了比较常见的 4 种统计指标（计数器、仪表盘、摘要、直方图）的声明方式：

```java
// 创建计数器，并且增加 1
meterRegistry.counter("counter").increment();
// 创建仪表盘，监控线程池的活跃线程数
ThreadPoolExecutor threadPool = new ThreadPoolExecutor(0, 10, 0, TimeUnit.MILLISECONDS, new LinkedBlockingDeque<>());
meterRegistry.gauge("thread_pool_active", threadPool, (pool) -> (double) threadPool.getActiveCount());
// 创建摘要和直方图
final DistributionSummary summary = DistributionSummary.builder("summary")
   // 规定 bucket 列表
   .serviceLevelObjectives(0, 10, 100)
   // 规定分位值
   .publishPercentiles(0.90, 0.95)
   .register(meterRegistry);
summary.record(10);

```

Spring 也提供了一些注解和第三方框架的适配来辅助创建自定义指标内容，比如 Timed 注解。

### PromQL

PromQL 是在 Prometheus 查询指标数据中最重要的内容，通过它提供的数据内容可以更方便地进行表格绘制、内容告警。

```java
http_error_requests{job="apiserver"}[5m]

```

这段代码可以查询出 http_error_requests 这个统计指标中，主体中 job 值等于 apiserver 的所有数据在最近 5 分钟内的值，它代表了 HTTP 请求错误的次数。可以通过这样的数据内容绘制柱状图或折线图。

PromQL 还支持很多指标函数，比如下面代码表示的是 http_error_requests 这个统计指标的当前值，与前 5 分钟相比较的增速值：

```java
rate(http_error_requests[5m])

```

PromQL 支持更多的计算函数，可以参考官网教程进行更细致的学习。

### 告警规则

**告警规则就是定期执行 PromQL 中的语句，当符合条件时进行告警**。下面的代码创建了一个告警规则：当 HTTP 请求错误数据的错误数超过 20 个，并且持续了一分钟，就会告警。

```yaml
- alert: RequestErrorAlert
  # 表达式，代表触发什么样子的条件，这里代表了请求错误次数超过了 20 个
  expr: http_error_requests{job="apiserver"} > 20
  # 持续时间。表示持续一分钟都出现请求错误数超过 20 个，则触发报警。
  for: 1m
  # 当符合条件时进行告警通知信息
  annotations:
    # 摘要，支持通过模板的形式定制当前统计指标中的信息
    summary: "Instance {{ $labels.instance }} 请求错误数过高"
    description: "{{ $labels.instance }} 实例中的请求错误数超过 20 个(当前值：{{ $value }})"

```

声明告警规则之后，就可以通过 Alertmanager 组件进行更详细的通知方式配置，这部分可以参考官方文档学习。

### Grafana

Grafana 是**一个通过可视化的形式查看指标数据的展示系统**，通过它可以快速构建出 dashboard。其数据源依赖 Prometheus，通过 PromQL 的查询实现；官方提供的 Demo 可以在线体验其展示内容。

Grafana 是依赖于 Prometheus 提供的数据搭建而成的，其界面结构如下：

- **最上面一行分别展示当前的展示模板和对应查询时间范围**，这与 Kibana 十分类似。

- **下方的每一个模块展示的是通过 PromQL 所查询出数据的结果**，这个部分可以选择不同的展示方式，例如柱状图、折线图、列表等。

Grafana 还支持导入和导出展示模板，可以直接下载一些已经很成熟的模板来使用。

## 实践要点

- **采集模式选型看场景**：需要业务系统自主上报、对安全性要求高时选 push；需要随时查询、配合服务发现动态扩缩时选 pull；Prometheus 以 pull 为主、PushGateway 补足短期任务。
- **检测周期与业务敏感度匹配**：常规 1 分钟，数据敏感业务可缩短到 30 秒。
- **优先复用自动指标**：Spring Boot 场景下 actuator + micrometer-registry-prometheus 开箱即得 HTTP 调用次数、CPU、内存等基础指标，再按需用 MeterRegistry 声明业务自定义指标。
- **dashboard 从成熟模板起步**：Grafana 支持导入导出模板，先用成熟模板再定制业务关键指标。
- **告警通知交给 Alertmanager**：规则只负责"何时触发"，通知渠道、模板等细节由 Alertmanager 统一配置。

## 小结

指标体系的价值在于了解系统走向、dashboard 展示与规则告警三大作用，其底层由数据收集、指标聚合、指标查询、规则告警四步构成。Prometheus 是这套原理的典型实现：pull 为主 + PushGateway 兜底的采集、TSDB 存储、PromQL 查询、Alertmanager 告警，再配合 Grafana 完成可视化，配合 Micrometer SDK 即可将业务指标低成本接入，构成业务中统计指标时必不可少的完整系统。

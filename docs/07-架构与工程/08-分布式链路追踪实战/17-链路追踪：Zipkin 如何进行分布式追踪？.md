# 链路追踪：Zipkin 如何进行分布式追踪？

链路追踪是可观测性体系中的最后一个环节。它呈现系统执行时的链路情况，通过图形化的形式描述程序的执行流程。一个比较好的链路追踪系统能够完成以下事情：

- **全链路记录**：将系统中的**业务系统**、**组件**纳入链路追踪工具观测，当发生请求或执行定时任务时，记录下完整的链路信息并以可视化形式展示。

- **快速检索**：快速检索指定入口、执行路径中的链路数据，提高优化链路流程或性能时的效率。

- **快速定位**：当线上请求处理出现问题或数据异常时，快速定位到出现异常的链路，提高开发人员定位问题的效率。

- **便于沟通**：排查问题时经常涉及多个组的开发人员。全链路的信息可视化追踪展示出链路中所有涉及的项目，可以直接询问问题项目的开发人员，快速还原问题发生时的执行情况，省去挨个询问的时间成本。

## 原理

常见的链路追踪实现原理可以拆解成 3 个部分：**链路采集**、**数据收集**、**数据查看**。链路采集是实现原理的基础，没有它后续步骤无从谈起；数据收集是中间的衔接环节，负责存储采集到的数据；数据查看是最终目的，支持快速查看链路数据信息并分析问题。

### 链路采集

**链路采集是指从业务系统或者组件中采集实时的流量数据，将这些数据汇聚成统一的格式，然后发送到链路收集服务中**。

实现链路采集的主流方式有 2 种：**埋点**和**字节码增强**(在“性能剖析：如何补足分布式追踪短板？”中已有简单介绍)。可以从以下几个维度对比两者在采集器应用中的区别。

- **性能损耗**：采集器对服务的影响应尽可能小。在高并发、高流量的场景中，即使只有一点性能损耗也可能带来比较大的影响，甚至导致服务关停链路采集工作。埋点和字节码增强都存在一定的性能损耗，单就节省性能而言，埋点略优于字节码增强；具体选择仍要依据使用场景判断。

- **代码侵入**：接入链路追踪时，接入方式越简单越好，且与业务代码相关度越低越好，这样更容易解耦。埋点可能存在一定的代码级侵入性，但通常不需要处处埋点，一般会结合过滤器、注解等技术实现接入方式的通用化，降低侵入性。字节码增强的依赖性更低，通常业务程序启动时无须太多配置即可生效，例如 Java 中可以通过 JavaAgent 的方式接入。

- **开发难易程度**：两者实现方式不同，开发难度也不同。埋点需要各框架提供类似 AOP 的扩展功能支持，开发相对简单；由于它基于框架内部功能的扩展，进行链路追踪时相对不便。字节码增强在代码级别拦截方法调用，基于代码的执行流程做链路追踪，需要了解相关组件的实现原理才能开发，开发难度相对较高，但也更灵活。

- **可扩展性**：优秀的链路追踪系统在链路采集层面一定具有良好的扩展性，而不是仅适用于单独的一个业务或框架，因此需要支持更多的框架，同时尽量不对系统性能造成过高影响。字节码增强因其实现方式的原因，可扩展性相对埋点更高；实际选择仍应依据具体实现方式和框架判断。

两种链路采集方案没有绝对的好坏之分，关键看项目的具体使用场景。选用开源或商业方案时，还要考虑其与整个链路追踪系统的集成程度、支持的组件等。

### 数据收集

采集到数据后，需要对这些数据进行解析、分析等工作，并最终存储到相应的存储引擎中，常见引擎有 Elasticsearch、HBase、MySQL 等。

此时数据通常分为两类：统计数据和链路数据。统计数据用于了解数据的走向，链路数据则可以清晰地呈现链路中的每一个细节。

**统计数据**通常指通过链路分析得到的数据，与时间维度相关，类似于 Prometheus 所处理的指标，存储到时序数据库上更为合适。

**链路数据**通常指采集后解析成指定格式、用于链路展示的数据，通常采用唯一的数据 ID 存储。检索时需要采用链路 ID 或相关链路数据信息的方式，因此可以考虑使用支持全文检索的存储引擎。

### 数据查看

数据存储到数据库后，就可以进行数据查询、基于数据的告警以及其他操作。

链路追踪更强调数据的可观测性，它可以通过图形化的形式展现问题，对可观测性有重要意义，这也决定了链路追踪的数据展示是重 UI 的。

不同类型数据的展示方式各有侧重。统计数据通常用于展示一段时间内的数值变化曲线、热力图、topN 样本数据等，需要使用图表、列表等形式，前端的 ECharts 是目前比较常见的选择之一。

链路数据基于请求链路，数据与数据之间存在依赖关系，通常有树形图和拓扑图 2 种展现形式。

- **树形图**：链路中每一个 Span 都至少有 ID 和对应的父级 ID 信息，通过树形图可以直观地看到一个链路的执行过程，以及服务与服务、接口与接口之间的调用关系。

- **拓扑图**：拓扑图可以展现不同维度之间的依赖关系，包括服务、实例、接口之间的依赖。依据拓扑图可以快速梳理出链路依赖了哪些服务，排查问题时用于辅助判断问题的影响范围。

通过链路采集数据，对数据解析、分析后存储到数据库中，再通过可视化的形式查看数据，就构建了一个相对完整的链路追踪系统。下面以 Zipkin 说明实际应用中链路追踪系统的运作方式。

## Zipkin

Zipkin 是一款开源的链路追踪系统，基于前文提到的 ***Dapper*** 论文设计，由 Twitter 公司开发贡献。

### 系统架构

Zipkin 的整体工作流程与上文原理中链路采集、数据收集、数据查看三个步骤一一对应：

- **链路采集**：业务系统和组件是被观测对象，以一个典型的 RPC 请求为例，client 为请求发起方，分别请求两个服务端。被观测的客户端和服务端会在启动的实例中增加数据上报功能，将本实例观测到的链路数据一并上报到 Zipkin,常见的传输工具有 Kafka 或 HTTP 请求。

- **数据收集**：数据传输到 Zipkin 的收集器后，会经过 Zipkin 的存储模块存储到数据库中。目前支持的数据库有 MySQL、Elasticsearch、Cassandra 几种类型，具体选择可以根据公司内部运维的能力评估出最适合的。

- **数据查看**：Zipkin 提供一套完整的 UI 界面进行查询，这套 UI 界面依赖于一整套完整的 API 来处理请求。

### 链路采集

Zipkin 提供多语言支持，官方版本支持目前比较主流的语言，例如 C#、Go、Java、JavaScript、Scala 等，同时支持社区提供的其他语言，具体可参考官网说明。

在链路采集上，**Zipkin 使用数据埋点的方式来进行观测**。

Java 项目一般都会集成 Spring,写作时可以通过 spring-cloud-starter-zipkin 快速集成，经过简单的项目配置即可让项目拥有 Zipkin 的基础能力(注：spring-cloud-starter-zipkin 与 Spring Cloud Sleuth 均已停止维护，Spring Boot 3.x 起推荐使用 Micrometer Tracing 对接 Zipkin)。

埋点一般通过拦截器、注解等方式注入链路观测能力，从而实现链路追踪。例如项目使用了 OkHttp 框架，想将其接入 Zipkin 进行管理，就可以通过增加拦截器的方式埋点，观测执行链路：

```java
@Bean
public OkHttpClient buildOkHttpClient(HttpTracing tracing) {
    return new OkHttpClient.Builder()
        .dispatcher(new Dispatcher(
            tracing.tracing().currentTraceContext()
                .executorService(new Dispatcher().executorService())
        ))
        .addNetworkInterceptor(TracingInterceptor.create(tracing))
        .build();
}

```

上述代码通过分发器和代理器分别对请求的发送过程进行拦截，在准备发送请求时将链路上下文信息传递出去。

### 消息传递

**消息传递是在链路追踪中保持上下游服务相同链路的关键，一般通过消息透传的方式实现**。例如上下游通过 HTTP 的方式进行数据交换，上游在准备发送时于 HTTP 请求头中增加链路的上下文信息；下游接收到请求后，解析对应的 HTTP 请求头数据，确认是否存在链路上下文信息。

如果存在链路上下文信息，则继续传递链路信息，认定为相同链路，从而实现链路追踪；如果没有，则认定为一条全新的链路。

以 OkHttp 框架发送请求为例，通过 Wireshark 等工具观测数据内容可以看到：请求头中除了基础的 Header 信息以外，还会有很多以“X-B3”开头的内容，比如 TraceId、SpanId 等关键信息，这些就是由 Zipkin 产生的链路上下文信息。

### 数据展示

Zipkin 的链路数据展示界面以 client 端发送请求、server 端接收请求的链路逻辑为例：

- 左侧部分展示 client 端接收到上游请求后，交由 server 获取数据内容的链路信息。

- 右侧上半部分分别显示客户端发送、服务端接收、服务端处理结束、客户端获取到数据等每一个节点的时间关系。

- 右侧下半部分展示当前选中 Span 的标签信息。这与“链路分析”中所讲的自定义数据十分相似，可以通过自定义属性信息完成信息的定制化。

## 小结

链路追踪通过全链路记录、快速检索、快速定位和便于沟通四项能力，补齐可观测体系的最后一环。其实现原理拆解为链路采集、数据收集、数据查看三段：采集层在埋点与字节码增强之间权衡性能损耗、代码侵入、开发难度与可扩展性；收集层将统计数据(存入时序数据库)与链路数据(存入支持全文检索的引擎，以链路 ID 组织)分别处理；查看层以重 UI 的形式提供树形图与拓扑图。Zipkin 作为基于 Dapper 论文的开源实现，通过埋点接入、X-B3 请求头透传链路上下文，并依赖 UI + API 完成数据展示，是理解链路追踪系统运作的典型样本。

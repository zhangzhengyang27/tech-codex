# 观测分析：SkyWalking 如何把观测和分析结合起来？

## 概念说明

依据链路数据可以进行更细维度的数据分析，其中包含指标聚合和拓扑图两个主要内容。SkyWalking 就是这样的链路分析系统，它提供链路追踪、链路分析、性能剖析、告警等一系列功能，帮助定位问题。

### 与 Zipkin 的定位差异

Zipkin 是一个链路追踪系统，提供链路数据的基本查询和展示功能。Zipkin 项目的定位主要在于链路追踪：从官网提供的支持列表可以看出，它支持很多第三方组件内部的链路追踪，比如 HBase、Kafka，甚至可以把它理解为一个带全局链路 ID 的日志系统。从它的消息传递协议中可以看出，它并没有传递过多的数据信息。

SkyWalking 则是一个完整的 APM（Application Performance Management）系统，链路追踪只是其中的一部分。

两者定位不同，决定了它们不是相同类型的产品。**SkyWalking 中提供的组件更加偏向业务应用层面**，并没有涉及过多的组件级别的观测；**Zipkin 提供了更多组件级别的链路观测**，但并没有提供太多的链路分析能力。选型时可以依据两者的侧重点选择合适的产品。

## 系统架构

SkyWalking 的系统架构可以从三个方向理解：

- **Receiver Cluster（接收器集群）**：整个后端服务的接入入口，专门用来收集各个指标、链路信息，相当于链路收集器。

- **Aggregator Cluster（聚合集群）**：汇总接收器集群收集到的所有数据，并且最终存储至数据库，并进行对应的告警通知。SkyWalking 支持多种不同的存储方式，比如常见的 ElasticSearch、MySQL，可以根据需要选择。

- **CLI 与 GUI**：位于架构左上方，通过 HTTP 的形式向集群服务器发送请求来读取数据。

架构下方是数据接收的来源，分为 3 种：

- Metrics System：统计系统。目前支持从 Prometheus 中拉取数据到 SkyWalking，也支持程序通过 micrometer 推送数据。

- Agents：业务探针。指在各个业务系统中集成探针服务来进行链路追踪，也就是链路追踪中的链路采集部分。SkyWalking 支持 Java、Go、.Net、PHP、NodeJS、Python、Nginx LUA 语言的探针，是目前市面上支持探针语言比较全的系统。同时，它还支持通过 gRPC 或者 HTTP 的方式来传递数据。

- Service Mesh：SkyWalking 还支持目前比较新的 Service Mesh 监控技术，通过观测这部分数据同样可以实现链路数据的观测。

## 链路分析实践与原理

统计指标和拓扑图是链路分析在 SkyWalking 中的两大应用。

### 统计指标

**SkyWalking 定义了一套观测解析语言，叫作 OAL（Observability Analysis Language），它通过这套语言来实现统计指标的定义和统计。**

以下通过一个例子说明如何通过 OAL 语言定义一个统计指标：

```java
service_resp_time = from(Service.latency).longAvg();

```

右侧的 **from 代表数据从哪里来**。在这个示例中，数据来自 Service.latency，代表服务的响应耗时。**longAvg 函数会对服务中的所有响应时长求平均值，最后赋值给左侧的 service_resp_time 字段**，这个字段也就是最终生成的统计名称。

通过这样简单的方式即可定义一个统计指标，在系统运行时，SkyWalking 会根据定义生成数据。

#### 数据源与计算

每一个 Trace 数据中，都有 3 个维度的实体，分别是**服务、实例、端点**。

链路分析时，不仅可以通过这 3 个实体计算得出数据，比如基于响应时间计算平均响应耗时、基于调用次数计算 QPS；还可以依据三者之间的依赖，统计数据与数据之间的关系，比如基于端点和端点之间的调用次数，统计两者的调用频次。

计算得出数据之后，可以对同一个实体中的数据进行聚合，聚合之后由 SkyWalking 按照实体将数据分组。

以平均响应耗时为例，SkyWalking 把每一次链路中该服务的响应时间按照服务的名称分组。为了分担每一台机器的压力，就需要用到 SkyWalking 中的聚合服务器集群：按照服务名称做路由，把相同的服务名称路由到相同的聚合服务器中进行数据统计。通过这样的方式可以充分利用集群的优势来进行数据计算，数据计算完成后便会存储到数据库中。

在上述过程中，由于实时计算涉及数据存储的问题，如果每计算一次就存储一次，会耗费大量的存储系统资源。因此，SkyWalking 采用的是时间窗口的模型，将一段时间内的数据统一放置在内存中进行汇总和计算，并通过定时器的形式将数据批量地查询与写入，从而减少对数据库的读取和写入压力。

最后，基于 OAL 语言自定义的统计指标可以运用在自定义的 UI 展示和告警中，将动态统计指标的优势最大化，从而实现一套高度可定制化的观测平台。

### 拓扑图

除了统计指标之外，链路分析中的另一个关键点就是拓扑。拓扑图可以展示服务、端点、实例之间的引用关系，将引用关系与统计指标相结合后，能够更快地了解系统整体的运行情况，以及流量主要分布在哪里。

以 SkyWalking 的典型拓扑展示为例：从左到右代表服务从接入流量到服务处理中的完整拓扑信息。用户发起访问，首先经由 ProjectA 服务，然后引入 ProjectB、ProjectC 和其他的云服务，ProjectB、ProjectC 又分别调用了其余的组件和服务。服务依赖之间使用线进行连接，可以清楚地描绘出彼此的关系。

#### 传统拓扑检测的问题

传统的拓扑检测通常利用时间窗口来推断服务之间的依赖关系。比如 RPC 中消费者发送请求给提供者，提供者会先完成请求，再将链路数据发送到链路收集器端。此时，由于收集器端并不清楚是谁调用了提供者，所以会将数据保留一段时间到内存中；消费者完成请求处理后，将链路信息再发送到链路收集器中，此时再进行数据匹配，才能得知提供者的消费者是哪一个。得知消费者之后，保存在内存中的数据就会被删掉。

在分布式系统中，RPC 的请求数量可能非常巨大，如果使用传统的拓扑检测，虽然也能完成，但是会导致高延迟和高内存使用。同时由于是基于时间窗口模式，如果提供者的数据上报事件超过了时间窗口规定的时间，就会出现无法匹配的问题。

#### STAM：流式拓扑分析

SkyWalking 为了解决上述延迟和内存问题，引入了一个新的分析方式来进行拓扑检测，这种方式叫作 STAM（Streaming Topology Analysis Method）。

**STAM 通过在消息传递的内容中注入更多的链路上下文信息，解决了传统拓扑检测中高延迟和高内存的问题。**

Zipkin 和 SkyWalking 在 OkHttp 框架的消息传递时，都会将链路信息放置在请求头中。**无论它们的采集器是如何实现的，在进行消息传递时，都会通过某种方式将链路信息设置到请求中**。

请求头中有三个以“sw8”开头的 header 内容，“sw8”是 SkyWalking 在进行链路上下文传递中的关键信息。这些内容经过了转码处理，通过阅读官方对跨线程消息透传协议的介绍可以了解其传递的信息，其中比较关键的部分如下：

- Trace Id：用于记录全局的链路 Id。

- Parent segment Id：记录上一个服务消费者中的链路数据 Id。每个线程在链路记录时，会使用 Segment 来区分不同的线程。

- Parent span Id：记录消费者在发送请求时产生的 Span id。

- Parent service：消费者的服务名称。

- Parent service instance：消费者的实例名称。

- Parent endpoint：消费者中 Span 所指定的端点名称。

- Peer network address：指定消费者在进行数据发送时，发送到的目标地址，这里指的就是提供者的网络地址，由 IP 加端口组成。

这些内容中除了全局的链路信息以外，还有很多数据内容，比如消费者的服务名称、实例名称。通过这些数据信息，可以很快定位到当前服务的上游信息，而无须再等待上游请求完成后通过匹配的方式完成拓扑图的记录。

利用 Peer network address 构建下游服务和实例的别名，可以快速定位到相关的实例和服务信息，SkyWalking 也可以在很低的延迟下分析出对应的拓扑信息。由于不再依赖消费者的链路数据信息，也不会有过多的内存消耗。虽然存在一定的传输损耗，但整体的链路请求过程中占用的空间会比较小。

## 实践要点

- 选型依据侧重：需要组件级链路观测可考虑 Zipkin；需要业务应用层面的完整 APM（含链路分析、性能剖析、告警）可考虑 SkyWalking。
- 存储选型按需选择 ElasticSearch、MySQL 等后端；数据来源可同时接入 Prometheus/micrometer、多语言探针与 Service Mesh。
- 利用 OAL 语言自定义统计指标，并接入自定义 UI 与告警，构建高度可定制化的观测平台。
- 聚合集群按服务名称路由数据，配合时间窗口批量读写，降低存储系统压力。
- STAM 依赖请求头 sw8 上下文透传实现低延迟、低内存的拓扑分析；上游服务名称、实例名称、Peer network address 等字段是定位上游的关键。

## 小结

SkyWalking 是完整的 APM 系统，链路追踪只是其中一部分，其架构由接收器集群、聚合集群与 CLI/GUI 组成，数据来源覆盖统计系统、业务探针与 Service Mesh。链路分析围绕统计指标与拓扑图展开：统计指标通过 OAL 语言定义并借助时间窗口批量计算；拓扑图则通过 STAM 注入 sw8 链路上下文，解决了传统基于时间窗口匹配的拓扑检测高延迟、高内存且可能无法匹配的问题。

# 运维集成：内部的 OSS 系统如何与观测相结合？

## 概念说明

很多公司内部都有一套属于自己的 OSS（Operations Support System），即运营支持系统。它管理着系统内部的众多系统，例如 CMDB 系统、运营人员的业务后台系统，同时负责内部各种数据的收集汇总和管理控制。将观测系统与 OSS 运维体系相结合，核心在于**如何收集数据内容、配置告警规则、完成最终的告警全流程**。

## OSS 的作用

OSS 系统主要帮助公司做到 2 件事情。

- **统一入口**：统一所有子系统的全局访问入口，让寻找相关项目变得简单，方便研发和运维人员查看、管理相关的系统数据；同时使用统一的一套 UI 和用户系统，统一用户身份和展现方式，让使用体验更好。

- **系统集成**：子系统集成时提供统一的 API 接口，例如通过全局的 API 接口获取用户名称、组织架构等；需要对用户进行信息通知时，也可以通过 OSS 提供的接口进行更方便的处理。通过 OSS，系统之间的集成更加简单、便捷。

## 常见集成功能

以下几类系统通常会被集成到 OSS 中。

- **CMDB 系统**：主要负责存储服务、实例、机器配置等信息。研发人员进行服务申请、机器资源扩容或缩容时，可以在这个平台中申请，并交由审批处理。

- **运营平台**：主要用于处理技术运营中的常见功能，例如 on-call 值班就在这里进行管理。研发需要创建数据库、在 Git 上进行项目操作或执行其他行为时，也可以通过运营平台完成相关操作。

- **上线系统**：主要供研发将系统上线时使用。通过上线系统，研发可以很方便地将程序逐步发布到线上环境，简化并统一上线流程，减少与运维的沟通成本。

- **观测系统**：即与可观测性三大支柱——日志、统计指标、链路追踪——相关的系统，例如 Kibana、Grafana、SkyWalking。除了外部可见的实现方式，有些公司内部还会有自己的、将可观测性内容相互结合展示的实现方式。

- **告警系统**：收集所有观测的数据，通过在告警平台中配置相关告警规则实现告警，并结合统一告警处理流程、界面化的形式查询等能力。

## 观测与告警集成实践

### 数据收集

**数据收集指将各种观测到的数据内容，通过内容解析，然后进行聚合，最终组装成统计指标数据并进行存储**，以便后续进行告警处理。这里从链路追踪和日志两个方面说明；由于各类数据最终都存储到统计指标系统中，统计指标本身无需额外收集。

- **日志**：日志中可能需要统计各个系统中 error 或 warning 级别日志的次数，例如 error 级别的数据一段时间内超过 5 次就进行告警。以 ELK 体系为例，可以利用 Kafka 集群启动一套新的 Consumer 集群和 Topic 来消费日志队列中的数据，解析日志中的日志等级信息、机器信息等数据，将其以服务或实例的维度存储，以此对指定的服务或实例进行精确内容的告警。也可以在 Logstash 日志解析的后续环节做日志内容消费，这样可以减少日志内容解析的成本。

- **链路追踪**：通过解析链路数据，可以获取链路中的访问量、耗时、依赖关系等数据。将这部分数据同步至统计指标系统，即可对指定的服务、实例进行告警操作。对于开源中并不支持链路分析的组件，如 Zipkin，可以考虑通过 Kafka、gRPC 等中间件手段收集其链路数据并进行解析，不过这种操作难度相对较高。

日志、链路追踪，以及存储数据的统计指标，以这 3 个维度中的数据为基础就可以进行告警等操作。数据是告警处理的基础，也是后续告警的数据源。

### 按端配置告警规则

监控指标分为 4 个端：**端上访问**、**应用程序**、**组件**和**机器信息**。并非所有指标都适合在 OSS 系统中配置告警规则，不同端有不同的配置侧重点。

**端上访问**

端上访问指通过 App 或者浏览器进行的访问操作，这个层面的告警比较关注用户的使用体验。App 的统计指标内容更多是"查看"，因为浏览器更易于迭代更新，所以一般会更多针对浏览器进行告警配置。浏览器的告警配置主要关注两个方面：

- **页面元素**：页面中的资源加载和页面的访问情况，例如常见的 JS 脚本错误数、资源错误数等。通过对页面元素的监控，可以快速感知页面出错的可能性——大面积的脚本错误就可能导致用户无法与页面完成正常的交互操作。

- **接口访问**：与后端服务的接口访问交互情况，例如调用耗时时长、请求错误数。通过接口访问可以感知用户操作时的体验，调用耗时较长则会出现等待现象。

**应用程序**

应用程序指请求流量到达服务器后端后，应用进行请求处理时的操作。这个层面比较关注服务之间调用的情况、服务本身耗时情况、是否有异常产生等问题，通常关注以下 4 点。

- **服务调用**：服务之间的 RPC 调用在微服务架构中最常见，因此监控调用关系至关重要。通常监控**调用次数**、**出现错误次数**、**响应耗时**等信息，并通过生产者与消费者之间的关联关系，聚焦到具体的调用依赖上。如果响应耗时持续出现错误，说明服务处理时出现了超时或业务异常等问题，要根据模块的重要程度及时反馈。

- **数据库操作**：数据最终都会存储至数据库中，常见的如 MySQL、Redis、ElasticSearch 等，对数据库操作进行监控是有必要的。一般监控**调用次数**、**执行耗时**。如果执行耗时相对较长，可能出现接口响应缓慢甚至接口出错的问题。

- **JVM**：在 Java 语言中，代码都运行在 JVM 平台上，JVM 性能的好坏决定着程序的运行效率。Java 程序在出现 Full GC 时会先进行内存回收再恢复业务线程执行，因此会造成业务程序停顿。所以一般监控**堆空间使用占比**、**GC 次数**、**GC 耗时**。当堆空间内存使用占比达到 90% 甚至更高时，需要多加关注，防止情况向不好的方向发展。

- **限流熔断**：当系统请求量到达一定阶段后，限流熔断可以对应用程序起到很好的保护作用，但仍需对限流熔断的次数进行监控。如果大量请求都触发了限流熔断的保护措施，用户的使用体验就会受到影响。此时可以统计**触发限流或熔断的次数与占比**，例如占比超过 10% 时，研发人员可以通过告警确认是否要限流或调整熔断规则；如果是程序引发的错误，则需要根据具体的业务场景查询问题原因。

**组件**

组件指经常使用到的中间件，例如 Nginx、Kafka、Redis。这里的监控更偏向于运维层面，通过监控这部分数据可以快速了解组件的整体运行情况。配置告警时，一般按照**网关层**、**数据库**、**队列**、**缓存** 4 个类型进行配置。

- 网关层中有常见的 Nginx 等，这个组件中更加关注**请求的耗时与响应时的状态**。当某个具体接口出现超时时要进行告警，告知接口存在缓慢情况并及时优化，减少对用户使用体验的伤害；如果响应状态码出现大面积的 500，这一问题的重要级别就会很高，因为这代表有很多用户在使用程序时都出现了严重的问题。

- 数据库比较常见的有 MySQL、MongoDB。除响应耗时等信息外，在组件层面会更加关注**其他服务与本服务的连接情况**、**本身所产生的慢查询情况**，以及**常见主从架构中的主从延迟数**。主从延迟数较高时，业务方的数据查询可能受到影响。

- 队列中常见的有 Kafka、RocketMQ。队列监控更关注**生产者与消费者之间的待消费数量**，从而获取数据的堆积情况。长时间堆积可能导致业务受阻，严重时会影响用户的使用体验。

- 缓存中有常见的 Redis。缓存一般将数据存储至内存中以加速读取效率，因此**内存的使用情况是缓存中关注的重点**。通过监控内存的使用占比，可以快速得知内存使用量，确定对缓存是否足够使用。此外还要关注**缓存的命中率**：长期命中率不高时，要告知业务方确认是否存在缓存穿透的问题。

**机器信息**

机器是应用程序和组件的运行基础。通过对机器信息进行深度告警配置，可以感知业务系统是否会出现错误。配置告警时，一般关注 **CPU**、**内存**、**磁盘**和**网络** 4 个方向。

- **CPU**：CPU 是数据计算的关键，CPU 使用率较高可能导致业务程序执行缓慢，进而影响业务的处理。

- **内存**：内存代表程序可以操作的内存空间，更加关注**内存的使用占比**。出现较高的内存占比且保持持续增速时，需要进行告警通知，防止系统检测到内存占用过高而关闭进程。

- **磁盘**：磁盘在日志写入、业务临时文件使用时十分关键，关注**磁盘的剩余空间**、**磁盘写入负载**等。磁盘写入负载到达一定占比时，可能会堵塞程序运行。

- **网络**：系统之间的 RPC 或对接第三方通常使用网络通信，此时可以监控**网卡流入和流出的数据量**。超过一定占比且持续增长，可能会导致网络传输堵塞、影响程序执行。

### 告警流程

将监控指标应用到 OSS 系统并配置完告警规则后，判定到达告警阈值时就可以进入告警流程处理，并将其与 OSS 内部系统能力相互结合，主要包含以下 3 个部分。

- **将告警处理与内部的 OSS 相互结合**。集成到 OSS 中的多个系统都适合承担告警流程中的角色：

  - **CMDB 系统**：从中可以快速获取指定服务相关的负责人信息，通过负责人信息快速找到通知对象。
  - **上线系统**：可以快速查询指定服务最近是否有上线单。如果最近有上线单，可以同样提供给通知对象，用于判定问题是否与上线相关。
  - **观测系统**：可以了解到相关告警的数据信息，让处理人更快地查询数据内容。

- **通过获取系统中组织架构的数据了解研发人员及其 TL**。出现问题时，可以快速找到与项目相关的研发人员。

- **对接协同软件的 API**。很多公司内部都使用协同软件作为同事之间交流的平台，常见的有钉钉、企业微信、飞书等。通过对接协同软件的 API，可以在出现问题时快速联系到相关的同事，共同协作处理问题。

## 实践要点

- OSS 是运维体系的枢纽：统一入口降低查找与管理成本，统一 API 降低系统集成与通知成本。
- 数据收集是告警的前提：日志按等级与维度聚合成指标，链路数据解析后同步至统计指标系统，最终统一在指标层做告警。
- 告警规则按端配置、各有侧重：端上看体验、应用程序看调用与 JVM、组件看运维视角的运行状态、机器看资源水位。
- 告警流程依赖内部系统协同：CMDB 提供负责人、上线系统提供变更线索、观测系统提供数据上下文、协同软件提供触达通道。

## 小结

观测系统与 OSS 系统的结合方式可以概括为：OSS 作为统一入口与系统集成枢纽，将 CMDB、运营平台、上线系统、观测系统、告警系统等纳入统一管理；在数据层通过日志与链路追踪的解析聚合形成统计指标，在规则层按端上访问、应用程序、组件、机器信息四个端配置各有侧重的告警，在流程层借助 CMDB 负责人信息、上线单、组织架构与协同软件 API 完成告警的快速触达与协作处理。可观测体系的价值最终体现在落地到业务开发中，让告警出现时有清晰的流程可依。

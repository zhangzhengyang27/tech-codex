# 中高级研发面试，逃不开架构设计这一环

面试中的一个共性问题值得注意：**很多研发工程师在基础问题上答得不错，却往往栽在架构设计问题上**——要么回答得不够有深度，要么考虑得不够全面，或者干脆把网上看到的方案抄过来，连哪里有坑都不知道。

## 为什么架构设计是必考环节

这一问题与候选人的认知有很大关系。很多候选人认为，“架构设计”是应聘架构师或成为技术大牛后才会被问到的问题，觉得考察架构设计能力超出了岗位职责要求，并不重视。

实际情况是，**考察架构设计，是面试中高级研发工程师逃不开的一环。** 绝大多数面试官会看重候选人的架构设计能力，以此衡量候选人的技术深度和对技术的驾驭能力，挖掘技术亮点。**如果候选人能在“如何设计系统架构”上回答得有条理、体现出自己的思考，很容易得到认可，甚至可以掩盖个别技术问题上回答的不足。**

即使面试初级研发岗位，很多面试官也会站在候选人能力上一层继续提问。以“Redis 是否可以作为分布式锁？”为例，面试官会站在中高级研发角度考察技术能力：用 Redis 实现分布式锁会存在哪些问题？为什么 Redis 会采用 AP 模型？

应聘中高级研发时，面试官则会站在架构师的角度，将问题扩展到分布式缓存系统的数据分布、复制，以及共识算法，还要考察候选人在实际业务场景中应用分布式缓存的技术判断力。这些都是为了挖掘候选人的能力边界，看看天花板有多高，未来能在团队中发挥多大价值。

## 候选人的三类常见问题

以下三类问题在候选人中非常普遍：

- 没有设计经验，不了解面试前需要准备哪些架构设计问题；

- 没有大厂经历，不知道如何回答面试官提出的架构设计问题；

- 没有技术认知，不知道如何回答架构设计问题能让面试官满意。

针对第一类问题，切忌直接在网上搜索高性能高可用的架构设计方案来背：没有实际踩过坑，就很难分辨哪些设计仅仅是为了公关、很难落地，在面试中也容易被面试官识破，进而怀疑技术能力的真实性。

针对第三类问题，有些研发同学明明技术能力可以满足应聘部门的岗位要求，却面不到想要的职位。这不是技术能力不足，而是对技术的认知不够，达不到高级研发或架构师应有的技术思维层次——面试大厂时很难讲出自己的技术价值与亮点，导致竞争力不足。面试官更关注考察解决问题的思维过程，如何阐述解决问题的思维能证明能力，存在可学习的方法(如回答问题的视角应如何选择)，本系列会结合具体案例举例说明。

## 面试形式与六大知识模块

面试官在面试候选人时，常见的形式是：假设一种场景，让候选人根据场景做技术设计；或者直接让候选人画出自己做过的最复杂系统的架构图，再提具体设计问题。**这其中，100% 会涉及架构原理、分布式技术、中间件、数据库、缓存、业务系统架构 6 个方面，对应本系列的 6 个模块。**

本系列**主要面向想准备面试的中高级后端研发，以及想提前掌握架构设计知识、从而在面试中增加亮点的初级研发**，目标是摆脱面试中的架构设计误区，识别技术陷阱，掌握面试中关于架构设计问题的知识体系。

| 模块 | 主题 | 核心内容 |
|---|---|---|
| 模块一 | 架构原理与技术认知 | 以架构师视角解析遇到系统设计问题时，应具备怎样的技术认知和解题思路。架构设计的底层思维逻辑是架构设计能否立足的根本，决定了从什么角度回答提问才更有价值，是学习后续模块的理论基础 |
| 模块二 | 分布式技术原理与设计 | 通过亿级商品的数据存储问题，解析分布式系统技术架构中面对热点问题的回答思路，例如用 etcd 如何解决数据共识问题；深入原理并结合落地经验，抓住面试官的提问思路，给出被认可的答案 |
| 模块三 | 中间件常用组件的原理和设计问题 | 结合大厂关注的考察点，讲解 RPC 远程调用和 MQ(消息队列)的技术原理和实践，比如如何实现一个 RPC 框架？MQ 如何实现消息的不丢失、不重复消费，以及积压等问题 |
| 模块四 | 数据库原理与设计问题 | MySQL 的知识点很零散，本模块整理出一套架构设计面试中必考的 MySQL 知识体系，并可根据应聘职级针对性学习 |
| 模块五 | 分布式缓存原理与设计问题 | 仅能熟练使用 Redis 还不够，面试官还要求候选人深入理解底层实现原理，并具备解决常见问题的能力(尤其是高并发场景下的缓存解决方案)；结合分布式缓存原理与电商场景下 Redis 的设计案例，解锁经典面试问题 |
| 模块六 | 互联网高性能高可用设计问题 | 针对系统遭遇百万并发时的技术瓶颈与优化思路，剖析大厂招聘必问的高性能、高可用问题背后的原理，比如如何判断一个系统是高可用的；最终通过电商平台案例，解析面试中的高频架构设计问题 |

总的来看，在面试中，互联网公司会把技术层层设卡，通过架构设计上的各类知识点将研发工程师进行分层。每个人的工作经历有限，很多人遇不到好的平台和机会，平时工作中只做 CRUD 的工作——这个问题对中小型企业的研发工程师尤为明显，导致其应聘大厂的竞争力偏弱。本系列从具体的面试场景入手，按案例背景、案例分析、原理剖析、解答方法等层面展开，由浅入深；吃透一个案例后，可以灵活运用到其他案例中。

## 备考建议

考虑到不同候选人对架构设计的掌握程度不同，备考时有几点建议：

- **夯实基础**：无论基础如何，都建议先完整地系统学习一遍架构设计面试知识，对每个常见问题的考查方式建立全新认知，对涉及的知识点查缺补漏，夯实技术基础。

- **以教促学**：备考最直接的目的是通过面试考核，可以把所学内容用自己的话术和风格讲出来，让别人听懂——这离不开“从学习到分享再到学习”的迭代过程。

- **高屋建瓴**：有了一定的实践经验后，建议重新学习对应章节，结合实际经验思考是否有更好的回答方式。

## 小结

架构设计是中高级研发面试逃不开的一环：初级岗位会被越级考察(如 Redis 分布式锁的缺陷与 AP 模型)，中高级岗位会延伸到分布式系统的原理与业务判断力，以挖掘候选人的能力边界。备考的关键不是背诵网络方案，而是建立架构设计知识体系(六大模块：架构原理、分布式技术、中间件、数据库、分布式缓存、高性能高可用设计)，并通过案例学习掌握阐述解决问题思维过程的方法。作为技术人，即使代码写得再好，做的也是执行层面的工作，存在收入的天花板；想要突破它，就要突破做事的边界，让自己成为一个架构师或技术负责人——这些认知越早建立越好。

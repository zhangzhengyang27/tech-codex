# 大厂都在用哪些敏捷方法

## 核心命题

大厂做项目也没有什么特别的，无非就是工程中常见的"分而治之"的策略：**大项目拆成小项目，大服务拆成小服务，大团队拆成小团队。**

服务之间通过商定好的标准协议进行通信，架构上将大的服务拆分隔离成微服务，大团队按照业务或者服务拆分成小组，按照一定的流程规范保障协作。最终，各个小组要负责的内容其实就不多了。

> 就像淘宝这种网站，不需要一个庞大的项目组，通过逐级分拆，一个小组可能就只需要负责一个页面中的一个小模块。

---

## 1. 流程规范一：工作任务围绕 Ticket 开展

早些年的项目开发都是围绕项目计划开展的：把甘特图打印贴在墙上，方便团队成员看项目进展到什么地步。敏捷化之后，这种方式变成了看板；物理看板又逐渐变成电子看板，通过各种项目管理软件来管理跟踪任务，即时贴也变成了 Ticket。逐渐地，所有与开发相关的任务都和 Ticket 挂钩：报一个 Bug、提一条需求、要重构一下代码，都需要提交一个 Ticket。

> 每天上班第一件事就是打开看板，看看当前 Sprint 还有哪些 Ticket 没有完成，哪些已经完成，哪些正在进行中，非常直观。

这套机制对项目成员和项目经理的价值在于：

- **项目成员**：做完手头的事情不用再问项目经理该干什么，直接从 To Do 栏选一条 Ticket 做就是了。
- **项目经理**：看看 To Do 栏还有多少没被选取，就知道还剩多少 Ticket 没完成；看看 In Progress 栏就知道哪些 Ticket 正在进行中。
- **风险预警**：如果有 Ticket 在某一栏待太久，或者某一栏 Ticket 太多，可能就有风险，可以及时介入。

## 2. 流程规范二：基于 Git 和 CI 的开发流程

### 2.1 瀑布模型的两大烦恼

如果团队应用瀑布模型来开发，大概会有两大烦恼：**代码不稳定和部署太麻烦。**

- **代码不稳定**：早些年虽然也用源代码管理，但大家都在 master（主干）上开发，所以 master 的代码特别不稳定，一不小心就可能被签入不稳定的代码。于是上线前有一段时间叫"代码冻结期"——这期间除非紧急修复，否则谁都不能往上面提交代码。
- **部署太麻烦**：测试环境的部署是老大难问题，尤其服务较多时，编译要注意各种依赖和环境的配置，更新测试环境是个大工程。据宝玉介绍，当年他在飞信时，专门有人负责部署测试环境。

"代码冻结"和"专人部署"这两个方案一点都不敏捷。团队想要敏捷起来，一定要解决代码不稳定和部署太麻烦这两大问题。而基于 Git 的开发流程结合 CI 的自动测试部署，很完美地解决了这两大问题。

### 2.2 Git 分支 + 代码审查 + 自动化测试

Git 本来只是源代码管理工具，但其强大的分支管理和灵活的权限控制，结合一定的开发流程，可以帮助团队很好地控制代码质量。

基本假设是：master 的代码是稳定的。那么怎么保证新加入的代码也稳定？答案就是**代码审查（Code Review）和自动化测试**——如果代码有严格的审查，并且所有自动化测试代码都能测试通过，那么可以认为代码质量是可靠的；前提是自动化测试代码要有一定的覆盖比率。对大厂来说这不是问题：正规的项目组对代码审查和自动测试代码的覆盖率都有严格的要求。

剩下的问题是：如何在合并到 master 之前把代码审查和自动化测试做好？做法是：每次要往 master 添加内容，不是直接提交代码到 master，而是先基于当前稳定的 master 克隆一个 branch（分支）出来，基于 branch 开发，开发完成后提交一个 PR（Pull Request，合并请求）。

- PR 提交后，可以清楚地看出代码做了哪些改动，其他人可以针对每一行代码写评论提出修改意见；确认代码没问题了，就算通过代码审查。
- 自动化测试则由 CI（持续集成）完成。CI 可以想象成一个机器人：每次提交一个 PR（严格来说是 Commit，这里略作简化）到源代码服务器，这个机器人马上就知道了；然后它创建一个干净的运行环境，把提交的代码下载下来，再下载安装所有依赖项，运行所有测试代码，运行完后把测试结果报告出来。测试结果直观地反馈在 PR 上，绿色表示通过，红色表示不通过。

> 延伸阅读：阮一峰的《[Git 工作流程](http://www.ruanyifeng.com/blog/2015/12/git-workflow.html)》与《[持续集成是什么？](http://www.ruanyifeng.com/blog/2015/09/continuous-integration.html)》可先行阅读了解。

至此，代码审查和自动测试的问题都解决了：当一个 PR 代码审查通过、CI 通过所有自动化测试，就可以合并到 master，而且可以认为合并到 master 后的代码也是稳定的。

至于自动部署测试环境，反倒简单：CI 这个机器人在代码合并到 master 的时候，再次运行自动化测试代码，测试通过后直接运行自动部署的脚本，把 master 代码部署到开发环境或测试环境上。

### 2.3 一个开发任务的基本流程

以一个开发任务为例，应用敏捷开发方法的基本流程如下：

- 把要开发的 Ticket 从"To Do"栏移动到"In Progress"栏；
- 从主干（master）创建一个分支（branch），基于分支去开发功能或修复 Bug；
- 编写实现代码和测试代码（单元测试和集成测试），是否测试驱动不重要，看个人偏好或团队要求；
- 持续提交代码更新到分支，直到完成；
- 创建 PR（Pull Request，合并请求），邀请其他人帮忙 Review 代码，根据 Review 的结果，可能还需要更新几次；
- CI 在每一次提交代码到代码库后都会自动运行，运行后主要做这些工作：检查代码格式是不是符合规范、运行单元测试代码、运行集成测试；
- 最终这些检查都完成后，CI 会把执行结果显示在 PR 上，通常绿色表示通过，红色表示失败；
- PR 能合并需要满足两个条件：CI 变绿 + 代码 Review 通过；
- PR 合并后，CI 会自动构建 Docker Image，将 Image 部署到开发环境；
- 将相应的 Ticket 从看板上的"In Progress"栏移动到"Done"栏。

正常来讲需要严格遵守开发流程，但偶尔肯定也有紧急任务，来不及写测试代码——这种情况下，一定要再创建一条 Ticket 跟踪，以确保后续完成测试代码。

## 3. 流程规范三：部署上线流程

部署方式的演进经历了三个阶段：

| 阶段 | 做法 | 问题/特点 |
|------|------|----------|
| **程序员自管服务器** | 最早的方式，程序员自己管服务器 | 过于随意，导致很多问题出现 |
| **运维手动部署** | 专门运维团队：开发好的程序编译好、数据生成脚本写好、写成部署文档，交给运维手动部署 | 过程无比繁琐、无比慎重，通常几周才部署一次，遇上打补丁才隔几天部署 |
| **DevOps 自动化部署** | 随容器化、微服务、DevOps 兴起：DevOps 写自动化部署工具，开发人员自己去部署生产环境 | 部署越来越高效，大厂已在部署流程上融合这些理念 |

现在大厂的部署都已实现自动化，但流程上仍有一些控制：

- 首先，部署的不再是程序代码，而是 Docker 的 Image；每次代码合并后 CI 都会自动生成新的 Image，测试也是基于 Image 测试。
- 部署生产环境之前，先在内部的测试环境充分测试。
- 部署生产环境前，需要审批确认，有 Ticket 跟踪。
- 部署时，先部署一部分，监测正常后再全量部署。
- 整个过程都有监控报警，出现问题及时回滚。

如果一切顺利的话，整个生产环境的服务部署过程通常几分钟就完成了——这在以前简直是不敢想象的事。

## 4. 流程规范四：每日站立会议

在敏捷开发中，每日站会非常有名。在大厂，但凡实施敏捷开发的小组，上班第一件事就是一起开一个站会，沟通项目的基本情况——这也导致会议室越发紧张起来。

**时间与形式**：站立会议什么时间开都可以，但早上无疑是最好的时机——一天工作的开始，开完会全身心去干活。是不是站着开会其实不重要，**重点是要高效沟通反馈**；开会时间控制在半小时以内，半小时内不能完成的应该另外组织会议。

**主持人**：在敏捷的 Scrum 中，有一个角色叫 Scrum Master（敏捷教练、敏捷大师），主要任务就是保证各种敏捷流程。所以通常由 Scrum Master 主持会议，也可以采用轮班制，每个星期换一名团队成员主持。负责主持会议的人，主要职责是组织会议、一个一个环节开展、控制好会议节奏。

会议主要有三个话题：

**1. 成员轮流发言**

每个人轮流介绍：昨天干了什么事情，今天计划做什么事情，工作上有没有障碍无法推进。

> 一个成员的发言可能是这样的："昨天我实现了用户登录模块的前端输入框，今天打算完成后端 API 调用，在实现后端的时候需要 API 组的支持，昨天发现他们文档有问题，不知道该找谁。"

这过程中很容易偏离主题，比如突然有人提了一句"好久没团建了，是不是该出去玩了"，很可能大家就 high 地讨论起来了。这时会议主持者要及时打断，记录到"问题停车场"，让下一个人继续，先保证高效完成这一环节。

> 问题停车场（Parking lot question）：把需要进一步讨论的问题暂时放到这里，一会儿再讨论。

通过这样的形式，项目成员可以相互了解任务进展，有困难可以互相支援，及时发现问题和风险。还有一个重要因素：每个人对于自己提出的目标会信守承诺，努力完成。

**2. 检查最新的 Ticket**

所有日常工作都是基于 Ticket 来开展的，这些 Ticket 可能是测试报出的 Bug，也可能是产品经理提交的需求。所以每天例会都需要检查一下新增的 Ticket，甄别优先级，然后决定放到当前 Sprint，还是放到 Backlog（任务清单）。

这个阶段同样要注意不能发散，不要针对 Ticket 的细节展开过多讨论；有需要讨论的，同样可以先收集到"问题停车场"，由会议组织者做好控制。

**3. 停车场问题**

在这个环节，大家可以针对之前来不及讨论的问题进行讨论：能在会议时间内解决的马上解决，不能解决的会后再私下讨论或者再组织会议。

当然，大厂的流程规范还有很多，这里仅列出与敏捷相关的主要开发流程。

## 5. 案例剖析：一个应用敏捷开发的小组日常（宝玉）

宝玉以一个每周一个 Sprint 的小项目组为例，说明敏捷开发的日常应用——这回应了"如果每周一个 Sprint，怎么保证每周都有交付，还能保证产品质量"这个问题。

### 5.1 团队构成与分工

这个小组做网站开发，基于微服务负责网站的某一个小模块，标准配置 7 人左右，主要负责网站某模块的日常维护：

| 角色 | 人数 | 职责 |
|------|------|------|
| 程序员 | 4（至少一名资深，有架构能力） | 每天从看板上按照优先级从高到低领取 Ticket，完成日常开发任务 |
| 产品经理 | 1（Scrum 里叫 Product Owner） | 写需求设计文档，将需求整理成 Ticket，随时和项目成员沟通确认需求 |
| 测试 | 1 | 测试已经部署到测试环境的程序，如果发现 Bug，提交 Ticket |
| 项目经理 | 1（Scrum 里叫 Scrum Master） | 保障日常工作流程正常执行，让团队成员可以专注工作，提供必要的帮助，解决问题 |

在敏捷开发框架下，已形成一些很好的敏捷实践：这个小组基于 Scrum 方法做过程管理，基于极限编程做工程实践，用看板做可视化，每周一个 Sprint。

- **如何完成需求和修复 Bug**：日常工作围绕 Ticket 开展——所有的需求、Bug、任务都作为 Ticket 提交到项目的 Backlog，每个 Sprint 的任务以看板的形式展现出来。每个人手头事情忙完后，就去看来板上的"To Do"栏，按照优先级从高到低选取新的 Ticket，选取后移动到"In Progress"栏。

### 5.2 每周一：部署生产环境

没有人愿意星期五部署——那意味着如果部署后发现故障，可能周末都没法好好休息。所以即使程序早已测试好，除非特别紧急，否则都会留在下一周再部署；部署放在上半周，这样后面遇到问题还有足够的时间应对。

部署本身很简单：按照流程执行几个命令就可以完成生产环境部署。部署完成后，需要对线上监控的图表进行观察，有问题需要及时甄别，必要的话对部署进行回滚操作。**但轻易不会打补丁马上重新上线，因为仓促之间的修复可能会导致更大的问题。**

一周一个 Sprint 的好处之一：即使这一周的部署回滚了，下周再一起部署也不会有太大影响。

### 5.3 每周二：迭代回顾会议（Sprint Retrospective）

每周二早上，小组一般预留一个小时：常规站会完成后，还有一个**迭代回顾会议（Sprint Retrospective）**，目的是回顾在迭代中团队有哪些做得好的地方、有哪些做得不好的地方。对于需要后续改进的，创建相应的 Ticket 加入 Backlog，在后续迭代中改进完善。

> **案例**：某次会议上，测试人员反馈——上一个 Sprint，开发人员上线前几个小时还往预部署的分支里更新代码，导致测试需要重新做回归测试；因为时间不够，没来得及测试完整，上线后不稳定。建议以后不要随意在上线前、在部署分支更新代码。

对于这样的问题，可能不止一次发生，说明流程上存在漏洞。所以最后大家商定：以后如果不是紧急的修复，就不要在预部署的分支上更新；确实要加，需要和测试先确认。

如果会议中要形成涉及项目的决策，最好通过集体表决的方式，尽可能避免独裁式决策——因为敏捷的原则之一是要**善于激励项目人员，给他们以所需要的环境和支持，并相信他们能够完成任务**。

### 5.4 每周四：迭代规划会（Sprint Planning Meeting）

每周四早上也需要一个小时：常规站会完成后，还有一个**迭代规划会（Sprint Planning Meeting）**，大家一起讨论下一个 Sprint 的内容。开会之前，产品经理和项目经理会商量好 Ticket 的优先级；会议上，大家一起按优先级从高到低的顺序，从 Backlog 中选出下个 Sprint 的内容。

团队每个成员都要对候选的下个 Sprint Backlog 中的 Ticket 从 1-5 分进行打分：1 分表示容易、1 天以内可以完成的工作量；2 分表示 2 天内可以完成的工作；5 分表示非常复杂、需要 5 天以上的工作量。**注意：打分时要大家一起亮分，而不是挨个表态，不然结果很容易被前面亮分的人影响。**

**评估每条 Ticket 工作量的流程**：

1. 会议组织者阅读一条 Ticket（可能是用户故事、Bug 或优化任务），同时询问大家对内容有没有疑问。
2. 大家一起讨论这个 Ticket，确保充分理解。
3. 每个团队成员在心中对 Ticket 进行工作量估算。
4. 会议组织者确认大家是否都已确定估算结果；确认后开始倒数"3、2、1"，大家一起伸出一只手，亮出代表分数的手指头。
5. 如果估算结果存在分歧，出分最高的和最低的各自说明理由，讨论后达成一致。

这种估算工作量的方法叫**估算扑克**（Planning Poker），因亮分时用扑克牌亮分而得名，但并非一定要用扑克牌。

**这种评估方式的三点好处**：

1. **大家积极参与，详细了解需求。** 相比之下，以前可能只有当某个功能模块分配到自己头上时，才会去详细了解那部分需求，其他开发人员可能都不了解。
2. **工作量由实际参与开发的成员评估，往往更准确也更容易被接受。** 以前项目经理代为估算的模式，很容易不准确，或者让开发人员抵触。
3. **促进成员的交流和经验分享。** 一般经验浅的新手估算工作量会偏乐观，经验丰富的老手则更准确；通过这种方式，新手可以向老手学到很多工作量估算甚至技术实现的经验。

经过几个 Sprint 的磨合后，一般一个团队在每个 Sprint 的产出是比较稳定的——例如这样一个 7 人小团队，一个 Sprint 预计可以完成 20-30 分的 Ticket。

### 5.5 每周五：分支切割（Branch Cut）

周五标志着一周工作的结束，所以下班之前（4 点左右）要做 branch cut（分支切割），也就是把当前主干上的代码克隆到一个分支（branch）上。

**为什么要做分支切割？** 经过一周的开发，master（主干）已经合并了不少新的 PR，但直接把 master 的代码部署到生产环境肯定不放心——自动化测试还是不能完全代替专业测试人员的测试。所以需要把 master 上的代码部署到测试环境进行测试，并对测试出来的 Bug 进行修复，直到稳定为止。由于 master 还需要一直合并新的功能，最好的方式就是每次 Sprint 结束，从 master 创建一个分支版本出来，基于这个分支部署和修复 Bug。

流程效果：基于主干做 branch cut 创建一个预部署的分支，将预部署分支的代码部署到测试环境；下周测试人员测试新版本；测试验收通过后，预部署分支的代码部署到生产环境。

### 5.6 每周轮值

小组里除了日常开发工作，还有不少琐碎的事情：每周部署生产环境、每天部署测试环境、每周的 branch cut、回答其他小组的问题、主持每日会议（不一定需要项目经理）。这些事如果都是一个人做，难免枯燥。

在敏捷开发中鼓励发挥每个成员的主动性，所以每周轮值是一个不错的方式：让每个人都有机会体验、帮助团队完成这些事情，更有集体荣誉感和责任感。

## 6. 常见问题解答

### 6.1 基于这种敏捷开发的方式加班多吗？

加不加班，绝大部分时候和是不是敏捷开发没关系，还是看项目组的情况。通常来说，基于敏捷开发一个 Sprint、一个 Sprint 迭代，节奏比较稳定：这个 Sprint 做不完的任务可以顺延到下个 Sprint，不影响发布。不像瀑布模型那样前松后紧，后期加班可能性大一些。

### 6.2 一周一个迭代怎么保证质量？

宝玉介绍，自己以前使用迭代模型开发时，一般是 4 周左右的迭代周期，2 周就是极限；所以最开始看到敏捷开发用 1 周的迭代周期也有疑惑——1 周时间又要开发又要测试，怎么保证质量？实际实践下来，发现 1 周一个 Sprint 确实可行，而且质量可以有保障，关键因素有三个：

- （a）有足够比例的自动化测试代码，可以很好地保证质量：当用户的主要功能都通过自动化测试覆盖时，基本可以保证主要功能流程不会出问题。
- （b）一个 Sprint 开发完成后，并不马上部署生产环境，而是先部署到测试环境，会有 1 周时间测试。
- （c）有专业的测试人员进行测试，并非完全依赖自动化测试；有时候一些大的功能更新，甚至会组织全组成员一起测试，以弥补测试人员不足。

也就是说，虽然是 1 周的 Sprint，但其实还有 1 周的时间进行测试；每个 Sprint 不仅开发新功能，还要同步修复以前版本的 Bug。这样基本上可以保证有好的质量。而且 1 周的迭代可以保持每周都有内容更新，每周更新的内容不多，出现问题很容易定位到是什么地方导致的。

### 6.3 基于敏捷开发如何做计划？

大厂通常会在上一年底确定第二年整年的大的开发计划，并确定上线的时间范围，每个季度再根据情况做一些调整。这些大计划最终会变成具体的开发任务：一个大的开发任务会分拆到各个部门，各部门再将任务分拆到各个项目组。基于敏捷开发的话，主要就是看把这些开发任务放到哪几个 Sprint 去做，并确保在规定的时间范围内完成。至于工期的估算，迭代规划会上会对每个 Ticket 进行打分，根据分数可以预估有多少工作量、要花多少时间。

### 6.4 如何沟通协作？

组和组之间的沟通协作，主要通过邮件、会议、内部沟通工具，最终任务会以 Ticket 的形式体现。团队内部因为都在一起，沟通起来很方便，每天站立会议就是很好的沟通方式。

在敏捷开发中，有一种实践叫结对编程：两个程序员在一台电脑上一起工作。这个实践一直争议比较大，但如果用来两人一起排查一些问题，或者是资深程序员带新手程序员，则是一种非常好的协作方式。

### 6.5 案例中的实践和标准 Scrum 有什么不同？

案例中的做法确实和标准的 Scrum 有不少不一样的地方：

- **角色名称不一样**：Scrum 里分 Product Owner、Scrum Master 和 Team 三种角色；案例中是产品经理、项目经理和团队成员，但只是叫法不一样。
- **项目经理的定位**：传统的项目经理是偏控制型角色；Scrum Master 则更多是一种服务型角色，主要职责是保障敏捷流程的执行、提供必要的帮助，很多团队的决策采用集体决策的方式。
- **会议类型**：Scrum 有四种会议——每日站会（Daily Scrum）、Sprint 计划会（Sprint Planning）、Sprint 回顾会议（Sprint Retrospective），以及 Sprint 评审会（Sprint Review）。评审会的作用是让客户审查 Sprint 的完成结果；案例小组并没有直接的客户（都是完成产品经理提交的需求，且沟通紧密），所以没有安排专门会议。
- **站立会议的差异**：Scrum 的站立会议通常只有 15 分钟，并且只有轮流发言环节；案例小组增加了每天审查 Ticket 的环节，主要是为了将优先级高的 Bug 修复之类的 Ticket 放到当前 Sprint，及时响应、及时处理。有的项目组没有这个环节，由测试人员或 Scrum Master 直接将 Ticket 放到看板。
- **需求方式**：这个小组没有使用用户故事来开发需求，而是由产品经理事先写好需求文档。Scrum 推荐用户故事的方式——分拆需求、减少繁重的需求文档、在实现过程中再沟通确认——这是高效的方式，但并不代表是唯一的方式：如果有产品经理，可以提前几个 Sprint 就将需求文档写详细，一样可以达到高效理解需求的效果。

**那么这样还算敏捷开发吗？** 宝玉在 [《敏捷开发到底是想解决什么问题？》](http://time.geekbang.org/column/article/84351) 中讲过：是不是敏捷开发，核心并不是应用了哪个方法，而是应用的时候，是否遵循了敏捷开发的价值观和原则。比如非标准的站立会议效率更优，那么就应该采用非标准的站立会议；如果有专业产品经理事先做好需求分析、可以达到解释清楚需求的效果，就没必要一定要用用户故事来理解需求。

## 7. 小结

- **质量保障**：要保障质量，离不开充分的测试——不仅要有自动化测试，还要辅助一定量的人工测试。敏捷开发虽然求快，但不代表应该牺牲质量。
- **敏捷的真相**：大厂的敏捷实践并不神秘，关键是分而治之——最终团队小、项目小，所以才可以敏捷起来。大厂注重流程和工具的应用：通过 Ticket 的方式管理和跟踪开发任务，通过自动化的方式部署。
- **实践组合**：大厂的敏捷实践一般基于 Scrum、极限编程和看板，针对各自项目组的特点有所侧重、有所调整，在遵循敏捷的价值观和原则的前提下做到高效使用。
- **模式选择**：没有万能的开发模式，只有适合项目的开发模式；最重要的是摸索出一套适合自己项目特色的开发模式。
- 限于篇幅，Scrum、极限编程和看板未展开细讲，需辅助阅读书籍。宝玉在 [《怎样学好软件工程？》](http://time.geekbang.org/column/article/82697) 和 [《敏捷开发到底是想解决什么问题？》](http://time.geekbang.org/column/article/84351) 中列了一些参考书籍；另可阅读《天下武功，唯快不破——新时代敏捷项目管理之道》，对敏捷开发也有很不错的讲解。

# 服务可用性探针：如何判断你的服务是否可用

## 一、什么是健康度检查

在 K8s 的默认机制下，当 `Pod` 的状态为 `Running` 时，该 `Pod` 就可以被分配流量（可以访问到）。**但是这种检查方式对一部分 Pod 来说是不靠谱的。**

一个后端容器启动成功，不一定代表服务启动成功：后端容器启动后，部分 MySQL、消息队列、配置文件等其他服务的连接还在初始化，但容器的外部状态却已经是启动成功。在这种情况下直接访问 Pod 必然会有问题。

要自行控制流量分配的标准，就需要用到服务探针。

## 二、三种探针类型

探针一词与古代银针试毒的概念类似——将银针放入水中，银针变黑则代表有毒，没有变黑则代表正常。在 `kubernetes` 中，探针用来检测 `Pod` 的可用情况，共有三种探针可以使用：

### 1. 存活探针 LivenessProbe

存活探针对运行中的容器进行检测。需要检测服务在运行中有没有发生崩溃、服务有没有中途退出或无响应时，可以使用这个探针。

如果探针探测到错误，`Kubernetes` 就会杀掉探针所在的容器并按重启策略重启；否则不会进行处理。如果默认没有配置这个探针，容器不会被重启。

### 2. 可用探针 ReadinessProbe

可用探针用来检测 Pod 是否允许被访问到（是否准备好接收流量）。如果服务需要加载很多数据，或者有其他需求要求在特定情况下不被分配到流量，可以使用这个探针。

如果探针检测失败，流量就不会分配给该 Pod。在没有配置该探针的情况下，流量会一直分配给 Pod。**探针检测失败，Pod 不会被杀死。**

### 3. 启动探针 StartupProbe

启动探针用来检测 Pod 是否已经启动成功。如果服务启动需要一些加载时长（例如初始化日志、等待其他调用的服务启动成功）才代表服务启动成功，可以使用这个探针。

如果探针检测失败，该容器就会被杀死重启。在没有配置该探针的情况下，默认不会杀死容器。在启动探针运行时，其他所有的探针检测都会失效。

### 探针对比

`Kubernetes` 内置的三种健康度探针可以分别在启动时和运行时为 Pod 做检测：

| 探针名称 | 在哪个环节触发 | 作用 | 检测失败对Pod的反应 |
| --- | --- | --- | --- |
| 存活探针 | Pod 运行时 | 检测服务是否崩溃，是否需要重启服务 | 杀死容器并重启 |
| 可用探针 | Pod 运行时 | 检测服务是不是允许被访问到。 | 停止Pod的访问调度，不会被杀死重启 |
| 启动探针 | Pod 运行时 | 检测服务是否启动成功 | 杀死容器并重启 |

配置方式：在 `containers.livenessProbe/readinessProbe/startupProbe` 下配置即可。

## 三、三种探测方式

探针类型不同、触发的阶段不同，但探测方式都是一样的，检测的 API 也一样。共有以下三种检测方式：

### 1. ExecAction

这种方式是在 Pod 的容器内执行预定的 Shell 脚本命令。执行的命令没有报错退出（返回值为 0）代表容器状态健康，否则就是有问题的。

以下是一个创建 Pod 的配置文件模版，配置了一个存活探针 LivenessProbe + ExecAction 命令检测。其中，`livenessProbe.exec` 代表去执行一段命令，`command` 是要执行的探针命令，`livenessProbe` 代表声明一个存活探针：

```yaml
apiVersion: v1
kind: Pod
metadata:
  labels:
    test: liveness
  name: liveness-exec
spec:
  containers:
  - name: liveness
    image: registry.aliyuncs.com/google_containers/busybox
    args:
    - /bin/sh
    - -c
    - touch /tmp/healthy; sleep 30; rm -rf /tmp/healthy; sleep 600
    livenessProbe:
      exec:
        command:
        - cat
        - /tmp/healthy
      initialDelaySeconds: 5
      periodSeconds: 5
```

Pod 启动成功时会自动执行下面的命令：新建一个 `/tmp/healthy` 文件 => 睡眠 30 秒 => 删除 `/tmp/healthy` 文件 => 睡眠 600 秒。

```shell
touch /tmp/healthy; sleep 30; rm -rf /tmp/healthy; sleep 600
```

探针检测在第一次探测等待 5 秒后，会尝试访问 `/tmp/healthy` 文件来判断检测结果。只有在 `Pod` 运行的前 30 秒这个文件才存在；第 30 秒后文件被删除，探针访问不到这个文件，于是按照失败规则重启 `Pod`。

创建这个 `Pod` 并观察效果：

```shell
vim ./liveness-exec.yaml
kubectl apply -f ./liveness-exec.yaml && date && kubectl get pods | grep liveness-exec
```

等待 30 秒后，通过 `kubectl describe` 命令查看 Pod 的运行全览状态：

```shell
kubectl describe pods liveness-exec
```

可以看到，在运行一段时间后，探针被检测失败，Pod 被迫重启，接着创建了新的 Pod。

### 2. TCPSocketAction

这种方式使用 TCP 套接字检测。Kubernetes 会尝试在 Pod 内与指定的端口进行连接：能建立连接（Pod 的端口打开了）就代表容器是健康的，不能建立连接则代表这个 Pod 有问题。

下面这个 Pod 配置文件定义了一个可用探针 + 存活探针，检测方式为 TCP 检测。探针会在容器启动成功 5 秒后开始检测，每 10 秒检测一次，每次尝试访问 Pod 的 8080 端口：

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: tcp-socket-action
  labels:
    app: tcp-socket-action
spec:
  containers:
  - name: tcp-socket-action
    image: registry.cn-hangzhou.aliyuncs.com/janlay/goproxy:0.1
    ports:
    - containerPort: 8080
    readinessProbe:
      tcpSocket:
        port: 8080
      initialDelaySeconds: 5
      periodSeconds: 10
    livenessProbe:
      tcpSocket:
        port: 8080
      initialDelaySeconds: 15
      periodSeconds: 20
```

### 3. HTTPGetAction

这种方式使用 HTTP GET 请求。Kubernetes 会尝试访问 Pod 内指定的 API 路径：返回 200 代表容器是健康的，否则代表这个 Pod 有问题。

这里配置了一个存活探针。探针将会在容器启动成功后 3 秒钟开始检测，每隔 3 秒检测一次，每次携带 `httpHeaders` 内填写的请求头，并尝试访问 `8080` 端口下的 `/healthz` 地址：

```yaml
apiVersion: v1
kind: Pod
metadata:
  labels:
    test: liveness
  name: liveness-http
spec:
  containers:
  - name: liveness
    image: registry.cn-hangzhou.aliyuncs.com/janlay/liveness
    args:
    - /server
    livenessProbe:
      httpGet:
        path: /healthz
        port: 8080
        httpHeaders:
        - name: Custom-Header
          value: Awesome
      initialDelaySeconds: 3
      periodSeconds: 3
```

容器内 `/healthz` 地址的编写规则是：容器启动 `10` 秒钟内返回 `200` 请求码，之后统一返回 `500` 状态码：

```go
http.HandleFunc("/healthz", func(w http.ResponseWriter, r *http.Request) {
    duration := time.Now().Sub(started)
    if duration.Seconds() > 10 {
        w.WriteHeader(500)
        w.Write([]byte(fmt.Sprintf("error: %v", duration.Seconds())))
    } else {
        w.WriteHeader(200)
        w.Write([]byte("ok"))
    }
})
```

保存配置文件，等 10-20 秒钟后查看结果：

```shell
vim ./liveness-http.yaml
kubectl apply -f ./liveness-http.yaml
kubectl describe pods liveness-http # 等10-20秒后再执行
```

可以看到，Pod 启动一段时间后，探针检测到返回值 500，标记检测失败，并回收了 Pod 重新创建。

## 四、控制探针检测行为的参数

`Kubernetes` 提供了以下参数定义探针的检测行为：

- initialDelaySeconds：容器初始化等待多少秒后才会触发探针。默认为0秒。
- periodSeconds：执行探测的时间间隔。默认10秒，最少1秒。
- timeoutSeconds：探测超时时间。默认1秒，最少1秒。
- successThreshold：探测失败后的最小连续成功数量。默认是1。
- failureThreshold：探测失败后的重试次数。默认是3次，最小是1次。

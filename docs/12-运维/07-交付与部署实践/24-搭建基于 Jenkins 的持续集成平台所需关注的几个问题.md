# 搭建基于 Jenkins 的持续集成平台所需关注的几个问题

本文讲解基于 Jenkins 的持续集成架构及常见问题。

## 基础概念

### Jenkins 简介

Jenkins 是一个用于搭建持续集成平台的开源工具，它的官网地址是：https://jenkins.io/。持续集成是近些年来企业管理、软件开发、软件上线过程中的一个概念，其核心主要强调的是：

- 开发人员在提交了新的代码以后，立即进行构建、（单元）测试等相关流程；

- 自动化部署。

### 持续集成和 Devops 的差异

持续集成与近些年新产生的 Devops 概念有何差异？可参考下图：

![](/ops-course-images/09-搭建基于_Jenkins_的持续集成平台所需关注的几个问题__CgpOIF5wY7yAJJsMAAJRRuQVMKw843.png)

图中最外圈的方框代表的是 Devops 一层，其里面包含了持续集成的流程部分；里面的小方框是持续集成覆盖的范围，包含三个部分：开发、测试和部署。这三个环节对企业开发来说是必备的，是必须要经过的流程，持续集成做到了把三个过程很好地相互串联起来。

所以持续集成覆盖的主要是开发、测试和部署三个环节，但是持续集成忽略了一个重要的步骤，就是上线以后的运维环节。运维的成本对于企业来说也是消耗比较大的，而 Devops 就集成了整个持续集成环节，并且重点融入了运维环节来考虑。

总结下，持续集成和 Devops 共同的技术要求是：

- 自动化：做到部署自动化、测试自动化等。

- 各项流程需要无缝打通，如开发到测试，测试到部署，这些都要求无缝地把各个管理环节和流程打通。

- 交给统一平台进行可视化管理。

这就是持续集成和 Devops 所具备的共性要求。

## 基于 Jenkins 的持续集成方案

基于 Jenkins 的持续集成有以下三种典型架构。

### 小型集成架构

第一种是小型的持续集成架构，整体结构如下图：

![](/ops-course-images/09-搭建基于_Jenkins_的持续集成平台所需关注的几个问题__Cgq2xl5wY76ASQwBAAUQzeQk2NQ579.png)

整体上 Jenkins 把整套流程进行了串通，从研发上传到代码仓库，通过代码仓库自动触发代码的下载、代码的编译及构建，然后做代码的测试，并且完成工程的打包，最后进行代码的部署。

代码的部署可以通过 Shell 脚本来实现，自动发布到预上线环境和上线等环境，多套环境的打通也是在 Jenkins 中完成的。

这个架构包含这几个部分：

- 版本库管理，用 SVN 或者 Git 来做代码版本的管理，Git 和 SVN 的区别是，Git 是一个多分支的代码管理系统，通常现在大部分的企业已将 SVN 改为 Git 来做代码管理。

- Jenkins 调用的代码构建工具，如果是 Java 的相关服务，就需要调用到 maven 或者 ant 等工具来实现 Java 代码的编译和构建。

- 私服系统，企业会搭建一个自己的私服，可以代理远程仓库和部署自己或第三方构件。

- JUnit 和 TestLink 通常可以用来做单元测试。

- Shell 脚本逻辑主要为了串联发布流程各个步骤，把测试好的代码工程包通过执行 Shell 脚本发布到各个部署环境。

### 微服务集成架构

![](/ops-course-images/09-搭建基于_Jenkins_的持续集成平台所需关注的几个问题__CgpOIF5wY76AB1SaAAZNIemKRrY433.png)

微服务是当前的一个主流架构，Jenkins 很好地支持企业微服务部署环节。K8s 完美地解决了调度，负载均衡，集群管理、有状态数据的管理等微服务面临的问题，成为企业微服务容器化的首选解决方案。Jenkins 支持打包部署通过 Docker 来承载应用：把应用封装进镜像，然后通过 Jenkins 打包一个完整的镜像并上传到镜像仓库。

另外，小型集成方案里的 Shell 是有局限性的：管理海量的服务系统时，不如 Ansible 或者自动化执行的管理模块方便，自动化运维能力也没有那么强大。这个时候可以用 Ansible 来做自动化任务。

镜像仓库在这套环境的代码发布管理流程中至关重要：需要把每一个镜像，按照它的版本号和发布时间和主题描述来进行版本的管理，方便于发布记录及回滚，所以仓库管理也成了微服务集成架构里面非常重要的一个组件。

Jenkins 在微服务的集成架构里面起着一个核心的持续集成环境平台的作用。

### Devops 集成架构

第三种是 Devops 集成架构：

![](/ops-course-images/09-搭建基于_Jenkins_的持续集成平台所需关注的几个问题__Cgq2xl5wY7-ANUjVAAdwdd2Q2To107.png)

这个 Devops 平台不仅处理代码发布和自动化持续测试，更多的把运维的相关工作融入到 Devops 平台中。比如企业的资产管理、配置管理、监控等相关的运维任务平台都融合到整体的一个叫 Devops 的平台。

这样 Devops 优势会更加好体现到持续集成，如：它要发布的应用名称、主机信息等，都可以通过 Devops 平台直接获取，又如：持续集成平台需要调用指令也可以封装到 Devops 中。

## 关注重点问题

介绍完 Jenkins、Devops、持续集成的相关概念，下面梳理搭建基于 Jenkins 的持续集成平台需要关注的几个问题。

### 问题一、推荐快速搭建方式

第一个问题，就是 Jenkins 本身怎么来搭建。这里先介绍一套通用的搭建方案，其要点有两点：第一点就是尽可能的把 Jenkins 相关的组件来做容器化；第二点就是相关自动化的任务执行尽量交给 Ansible 来处理。这是一个比较通用的结构。

如何来快速搭建这样的一套结构呢？下面列出主要用到的命令，具体细节可查阅相关文章：

![](/ops-course-images/09-搭建基于_Jenkins_的持续集成平台所需关注的几个问题__CgpOIF5wY7-AFSPOAAVFUJDaFAI724.png)

首先，Jenkins 整个通用的部署架构里面，GitLab 和 Jenkins 是两个开源的平台：Jenkins 是一个持续集成平台，而 GitLab 是一个基于 Git 的管理项目，它在 Git 管理工具的基础上，来做 Web 的平台化的代码管理。另外，GitLab 建议用容器的搭建方式，且已有一些通用的镜像可以供下载。所以，Jenkins 和 GitLab 都可以通过官方的相关镜像来直接生成容器。

部署时，需要先安装 Docker 的环境（可参考官网的方式安装 Docker 相关环境并启用 Docker 服务），而 Jenkins 和 GitLab 通过下载相应的镜像，把镜像生成为对应的容器，从而启动服务。

另外，在 Jenkins 启动正常以后，就可以通过控制台来进行插件下载/管理并对工作流进行配置——这就是搭建一个通用平台的步骤。

### 问题二、Jenkins 日志文件体积过大问题

第二个需要关注的问题，是 Jenkins 产生的日志体积过大。

Jenkins 会默认将自己的运行日志都输出到 jenkins.log 中，尤其是在非容器的部署模式下，常常由于日志输出过多、工作流任务过多，导致磁盘出现膨胀问题；磁盘空间被占满也会导致任务流无法稳定运行。虽然可以到服务器上进行日志删除，但会遇到两个痛点：

- 第一个痛点：产生的日志集中，且没有一个可切割的工具，会导致磁盘占用率过高；需要有一个定时清理的方式，运维人员不可能频繁地去机器上做日志清理。

- 第二个痛点：如果通过 rm 命令删除日志会遇到一个问题——Jenkins 本身占用着这个文件，删除日志文件以后，因为进程依然处于运行状态，空间并不会马上释放，需要重启 Jenkins 进程。

**Jenkins 日志文件体积过大问题 - 解决方式**

解决方式是使用日志切割工具 logrotate 来做 Jenkins 的日志切割。logrotate 是 Linux 平台下的日志管理工具，用于分割日志，也就是删除旧的日志文件并且创建新的日志文件，可以起到一个日志轮转的作用。

配置 logrotate 需要按照配置文件规范来进行操作。以 jenkins.log 文件为例，logrotate 的配置文件示例如下：

```text
/var/log/jenkins/jenkins.log {
    hourly         # 日志切割频率
    copytruncate   # 输出的日志拷贝(copy)一份出来，再清空(truncate)原来的日志
    missingok      # 包容文件没有找到的错误
    rotate 8       # 轮转次数及保留的文件数
    compress       # 是否通过 gzip 压缩转储以后的日志文件
    delaycompress  # 延迟压缩
    size 5G        # 目标文件需要满足大于指定大小（最高优先）
}
```

在配置文件里面，第一项配置的 hourly，表示切割的频率，按小时来进行切割。第二个配置（copytruncate）就是输出日志拷贝，再清空原有日志——即先把原来的日志拷贝出来一份，然后再清空这个日志文件，这样的好处是不会直接删除日志，相当于先做一个备份。

另外一个配置 missingok，可以包容文件找不到的错误：如果日志文件不存在，它也不会因为错误而导致中断。rotate 8 表示保留的文件份数，也就是底下会切割多少份副本做保留。后面的 compress 就是进行 gzip 压缩，可以把日志通过压缩的方式减少磁盘的空间占用。

后面的 delaycompress 是延迟压缩，避免 CPU 性能损耗过大。size 5G 是另外一条切割的规则：即使还没有到一个小时，只要目标文件已经大于 5 个 G，就优先满足这条规则来进行切割。

在配置好配置文件以后，就可以在控制台执行 logrotate --force /etc/logrotate.d/jenkins 命令；通常可以把 logrotate 加入到定时任务里面去执行这条命令，这样就可以做到定时的日志轮转。

### 问题三、持续集成规范性标准定义

最后一个需要关注的问题，是优先定义持续集成规范。自动化实现的基础就是建立规范性，尽可能地在标准的基础上来做持续集成。Jenkins 在持续集成中需要定义的规范性如下：

1、应用名称：{应用类型}-{端口}-{应用名称} or {类型}-{应用名称}

例如：api-8080-gateway,api-gateway

第一项是单个应用的名称，推荐按照 `{应用类型}-{端口}-{应用名称}` 或 `{类型}-{应用名称}` 的格式来定义每一个应用的名称。

2、主机名称：{地区}-{机房}-{开发语言}-{项目名称}-{应用类型}-{序列号}

例如：bj-yz-{java}-imoocc-api-01

第二项是本地所需要管理的主机资源的名称（主机名）。主机名的管理非常重要，建议使用 `{地区}-{机房}-{开发语言}-{项目名称}-{应用类型}-{序列号}` 的格式来定义主机，如上例。

3、日志路径：/opt/logs/{应用类型}/{应用名称}-{端口}

例如：/opt/logs/web/gateway-8080

第三项是日志的路径。日志路径管理也非常重要，查看相关日志需要定义好规范性：统一放到 /opt/logs/ 目录下，按 {应用类型} 分门别类，再以 {应用名称}-{端口} 作为下一级目录。应用日志这一级的路径可参考此规范定义。

4、代码路径：/opt/apps/{应用名称}

例如：/opt/apps/api-8080-gateway

第四项是代码的路径。代码的存放也要遵循整体的规范性定义：所有应用都放到 /opt/apps/ 目录下，按 {应用名称} 为每个应用进行归纳。

5、tomcat 实例路径：/opt/tomcats/{应用名称}

若使用 Java 语言并以 tomcat 作为 servlet/JSP 容器，主机上有多个 tomcat 时，需要定义好实例名称及路径，推荐按 `/opt/tomcats/{应用名称}` 的方式定义。

6、Jenkins job命名: {环境}_{项目名称}_{应用名称}

如：TEST_IMOOCC1_api-8080-gateway

第六项是 Jenkins job 命名。同样需要定义好统一的名称以便管理，推荐采用 `{环境}_{项目名称}_{应用名称}` 的格式。

这样定义好以后，会使持续集成的整套开发过程和管理过程更加清晰。标准的定义是整套持续集成中至关重要的一环。

## 小结

- **概念边界**：持续集成覆盖开发、测试、部署三环节并自动化串联；Devops 在此基础上融入运维环节，形成组织级平台。
- **架构选型**：小型集成架构（SVN/Git + Maven + JUnit + Shell 脚本）适合简单项目；微服务集成架构引入 Docker 镜像、镜像仓库与 Ansible，配合 K8s 承载微服务；Devops 集成架构进一步融合资产、配置、监控等运维平台。
- **快速搭建**：Jenkins 与 GitLab 均容器化部署（官方镜像生成容器），自动化任务交由 Ansible 执行。
- **日志治理**：jenkins.log 过大时用 logrotate 做日志轮转（hourly/copytruncate/rotate/compress/size 规则），避免 rm 删除后空间不释放、需重启进程的问题。
- **规范先行**：自动化之前先定义应用名称、主机名称、日志路径、代码路径、tomcat 实例路径、Jenkins job 命名六项规范。

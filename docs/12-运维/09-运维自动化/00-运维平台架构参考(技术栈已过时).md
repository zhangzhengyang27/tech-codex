# 运维平台架构参考(技术栈已过时)

::: danger 技术栈已过时

## 平台全景：三块拼图

原文三套系统构成一条完整的「运维平台化」链路，这套分层思路至今仍然成立：

- **定时任务管理系统（Jcrontab）**：解决周期任务散落在各机器 crontab 中——只能命令行管理、无界面、单机执行、无通知——的痛点；
- **CMDB 资产管理平台（Imoocc）**：解决资产靠表格手工维护的痛点，是自动化体系的底座；
- **自动化任务平台**：解决 Ansible 命令行操作难沉淀、难授权、难审计的痛点。

三者的协作关系：**CMDB 管资产 → 自动化任务平台消费资产执行变更 → 定时任务系统把例行变更周期化**。这也是 DevOps 平台建设中「资产 → 执行 → 调度」的标准分层范式。

## 一、定时任务管理系统（Jcrontab）

### 系统组成

工程分为三个子系统：

- **前端任务系统**：记录单个任务的执行情况（执行时间、执行结果），可对单个任务启动、停止或修改任务周期；
- **后台管理系统**：基于 Xadmin 框架搭建，用于编辑、添加、删除任务；
- **脚本录入系统**：基于 Python 开发的脚本，方便运维人员在控制台快速录入任务。

![Jcrontab 框架结构](/ops-course-images/07-基于_Django_crontab_Xadmin_做一套定时任务管理系统__Cgq2xl5nIHyAM5EnAAb-zfht2e4708.png)

工程遵循 Django MVT 框架：URL 层做请求路径路由（`/xadmin` 交给 Xadmin 处理），Views 层实现视图逻辑并调用核心方法，models 层负责数据库模型读写。数据模型主要用两张表：**Demandorder 表**（任务主表）与 **Demandorder_log 表**（外键表，记录每次任务执行的结果与时间）。

### 值得保留的两个设计点

**1. 动态加载 crontab**：Django_crontab 的标准用法要求任务写死在 settings 的 CRONTAB 全局变量中，无法动态变更。Jcrontab 的改造思路是把该变量改写为调用 `todo()` 方法——每次加载时从数据库模型读取任务属性，按 crontab 模块要求生成任务列表，实现「任务模型化 + 动态生成 crontab」。

**2. 前后台动态联动**：前台点击催单或恢复按钮时，Django 内调用 Shell 脚本，先把现有 crontab 任务 remove，再执行加载把改动后的任务加入，相当于前端按钮触发 reload 任务。配合企业微信通知接口，任务执行结果（含命令输出）直接回推到群消息，形成「配置 → 执行 → 通知 → 催单」的闭环。

## 二、CMDB 资产管理平台（Imoocc）

### 资产的三种类型

- **物理资产**：机房、机柜、网络设备、硬件服务器等看得到的硬件；
- **虚拟资产**：KVM、VMware、Docker 等虚拟化出来的个体；
- **信息资产**：服务器上的系统、运行的服务、IP 与登录信息等标示与属性。

CMDB 是 DevOps 设计里最基础的环节：监控、配置管理、资产弹性、自动化任务等功能大多依赖资产管理。

![资产管理在 DevOps 中的位置](/ops-course-images/10-基于_Python_Ansible_Django_搭建_CMDB_平台__Cgq2xl5zJpGAMNBTAAF2XF3qyck100.png)

### 主动探测 vs 被动收集

传统 CMDB 多靠手动录入；加 agent 的被动探测又因 agent 的安装与维护成本而变得复杂。Imoocc 选择**服务端主动探测**：用 ICMP 扫描局域网内存活设备、用 ssh 协议登录获取主机信息——通用协议的好处是开发与运维实现简单、通用。

### 探测器三阶段逻辑

`main.py` 依次执行三个阶段：

1. **存活探测**：扫描局域网内存活 IP 列表；
2. **主机探测**：对开放 ssh 端口的 Linux 主机，模拟密码/key 两种登录方式，获取 sn 号、系统版本、MAC、主机名等资产信息；
3. **主机关系探测**：识别宿主机与虚拟子机（KVM/Docker/ESXi）的映射关系。

![探测器三阶段逻辑](/ops-course-images/10-基于_Python_Ansible_Django_搭建_CMDB_平台__CgpOIF5zJpWAcd3dAAFKPqRX0rA372.png)

收集的资产信息包括：服务器 IP、品牌、主机名、系统版本、sn 号、MAC 地址、宿主机类型，以及 ssh 登录信息（用户名、密码/(key)、端口）。**有了登录连接信息，就为自动化任务执行奠定了信息基础**——这是 CMDB 与自动化平台衔接的关键。展示层则按「左侧功能菜单 → 中间按资源类型全局统计 → 类型间关系关联（宿主机↔子机）」组织。

## 三、自动化任务平台（Django 融合 Ansible）

### Ansible 的三种使用方式

| 方式 | 特点 | 适用场景 |
|------|------|---------|
| adhoc（命令模式） | 以模块方式直接运行任务 | 简单、临时任务 |
| playbook（剧本模式） | 按 yml 剧本文件执行任务序列 | 场景丰富、运维管理方便 |
| roles（角色模式） | 基于 playbook 的工程化目录结构 | 大型工程化运维项目 |

三种方式虽能提升效率，但仍有局限：hosts/groups 配置难以与已有 CMDB 融合、终端方式管理烦琐、定制场景受限——因此需要自建可视化任务平台。

### 三层架构与三库存储

![自动化任务平台架构](/ops-course-images/11-基于_Python_Ansible_Django_搭建自动化任务平台__Ciqah155wHCARtpTAAHVwx-gTak127.png)

主体工程分三层：

- **API 接口层**：接收用户请求并调用核心逻辑；
- **逻辑层**：用 Django 开发，把 Ansible 作为 Python 模块封装融合；
- **执行层**：从 MySQL 获取主机资产信息，对目标机器执行自动化任务。

存储层用三个数据库各司其职：

- **MySQL**：存放主机资产信息等关系型数据；
- **Redis**：作任务锁，防止同一任务重复执行或重复调用；
- **Mongo**：记录执行日志，便于出问题时按日志溯源定位。

### 核心类封装（ansible_api.py）

对 Ansible 模块默认内核方法重新封装为四个类：

| 类 | 作用 |
|------|------|
| MyInventory() | 定义主机和主机组的相关关系 |
| ModelResultsCollector(CallbackBase) | adhoc 回调类，修改任务显示与返回内容，回执成功/失败状态 |
| PlayBookResultsCollector(CallbackBase) | playbook 回调类，返回相关任务执行状态 |
| ANSRunner(object) | 任务执行类，对外暴露执行方法，视图层调用它执行具体任务 |

执行流程：`/adhocdo` 接口（POST）提交 taskid、模块类型、执行命令与 **sn_key**（从资产系统提取的主机唯一标识）→ 服务端关联任务与资产并执行 → 返回执行日志 → 目标机器上验证结果。**sn_key 关联 CMDB 资产**正是平台化与散装脚本的本质区别：任务对象化、资产可寻址、执行可审计。

## 现代化替代方向（简要）

| 原方案 | 已过时组件 | 现代替代思路 |
|--------|-----------|-------------|
| Jcrontab 定时任务 | Django_crontab（单机、需 hack 动态加载） | APScheduler / Celery Beat（分布式调度），任务状态持久化到数据库 |
| Xadmin 后台 | Xadmin（多年未维护） | Django Admin（官方维护）或 Vue 系开源后台框架 |
| Imoocc 式自研 CMDB | Django 1.8 + Python 2.7/3.6 | NetBox、蓝鲸 CMDB 等活跃开源 CMDB，配合自动发现 |
| Django 融合 Ansible | Ansible 2.4 旧内核封装 | ansible-runner（官方执行运行时）+ AWX（Tower 开源版）做可视化 |

## 小结

这套合并后的参考材料的精华不在具体代码，而在三条平台化设计原则：

1. **任务模型化**：把 crontab/playbook 从「写死的配置文件」变成数据库对象，才有动态变更、界面管理与审计；
2. **资产先行**：CMDB 收集的资产与登录信息是自动化执行的地址簿，主动探测比手工录入和 agent 维护更轻；
3. **分层与隔离**：API 层 / 逻辑层 / 执行层分离，MySQL 管状态、Redis 管并发锁、Mongo 管日志，各组件职责单一。

「CMDB 管资产 + Ansible 管执行 + Django 管界面」的三层结构，与「资产 → 执行 → 调度」的平台链路，是运维平台化建设长期有效的参考范式；实现层面请按上表选用现代技术栈。

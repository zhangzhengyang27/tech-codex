# 19 数据契约与示例集
> 项目：PEXELS 壁纸应用 ｜ 版本：v1.2 ｜ 生成日期：2026-10-06 ｜ 依据：源码分析

## 0. 本篇定位与阅读约定

《15-接口全量参考》已经用"字段 → 归一化去向 → 消费点"的表格形式给出了全部端点的静态契约，本篇补上它的另一半：**完整的请求与响应实例**。每个端点给出可复制执行的 curl、原始响应 JSON（结构与 `src/utils/pexels.ts` 中对应的 `Pexels*` 接口逐字段对齐）、归一化与门面出口的关键差异，以及无 Key 降级时同一调用的假数据形态。目标是让读者不启动应用、不发真实请求，就能在纸面上完成"这个接口长什么样、我的代码会拿到什么"的推演。

三条阅读约定需要先立住。**其一，示意值标注**：以下所有 JSON 中的 id、URL、摄影师姓名、统计数字均为按真实数据形态构造的示意值（如照片 id 358457、宽高 4592×3056），仅字段类型与取值范围可信，具体值不可作为断言依据；Pexels 官方若调整字段，以运行时响应为准 ⚠️ 待确认（本篇未做真实请求采样，结构依据源码类型声明与官方文档公开形状）。**其二，敏感值占位**：所有示例中的鉴权头一律写作 `<VITE_PEXELS_API_KEY>`，绝不出现任何真实 Key 值；代理模式下该头不存在。**其三，消费视角**：响应 JSON 中"本应用未消费"的字段会保留在示例里（它们是真实响应的一部分，也是《15》第 2 节"未消费字段同样入表"原则的实例化），并用注释标明状态，避免读者误以为响应里没有这些字段。

## 1. 公共请求约定

全部请求共用一组基础设施参数，先一次性交代，后续端点不重复。基础地址 `https://api.pexels.com/v1`（`src/utils/pexels.ts` 的 `PEXELS_API_BASE`）；鉴权头 `Authorization: <VITE_PEXELS_API_KEY>`——**无 Bearer 前缀**（文件头注释强调，照搬主流模板加 Bearer 会 401）；走代理模式（baseUrl 非官方地址）时不发该头，Key 由服务端注入。分页参数 `page`（下限 1）与 `per_page`（钳制 [1,80]）在协议层与门面层各钳一次；`buildParams` 会剔除 undefined 与空串，因此"全部分类"不会产生 `query=all` 这类脏参数。响应只认两态：`res.ok` 为真则 `res.json()` 解析，否则按状态码构造 `PexelsApiError` 抛出——401 文案「API Key 无效，请重新设置」、429 文案「Pexels 请求过于频繁，请稍后再试」、其余「API 请求失败: {status} {statusText}」。**错误响应体从不被解析**：前端对 4xx/5xx 的全部认知来自状态码本身，这意味着无论 Pexels 的错误体长什么样（HTML 错误页、JSON、空体），行为都一致——这是"信任契约 + 状态码驱动"设计的一个直接推论。

一个通用的 curl 模板（以照片搜索为例，替换路径与参数即可用于全部端点）：

````
curl -sS -D - \
  -H "Authorization: <VITE_PEXELS_API_KEY>" \
  "https://api.pexels.com/v1/search?query=nature&page=1&per_page=20"
````

`-D -` 把响应头一并打到标准输出，方便确认 `X-Ratelimit-Remaining` 一类限流头 ⚠️ 待确认（Pexels 是否返回该头以其文档为准，前端代码不消费它）。开发环境等价请求走同源代理：把地址换成 `http://localhost:5173/api/pexels/search?...`，不带鉴权头，由 Vite 转发（`vite.config.ts` 的 `server.proxy`）。

````
curl -H "Authorization: <VITE_PEXELS_API_KEY>" \
  "https://api.pexels.com/v1/curated?page=1&per_page=20"
````

响应结构与 `/search` 完全同构（`PexelsSearchResponse`），仅无 `query` 语义、`total_results` 通常是官方精选池的实际规模（示意值 8431）。协议层 `normalizeSearchResponse` 对两者共用，页面层因此可以用同一个无限滚动容器承载两种数据源而不写任何分支（《03-接口设计》2.1 节"照片组复用度最高"的出处）。需要特别记录一个行为差异：`/curated` 不支持 `orientation`/`color` 筛选参数（官方端点无此能力），SOP-C 暴露筛选 UI 时"全部"分类下筛选控件需禁用（《11-扩展开发指南》第 3 节）。

## 3. 端点二：GET /v1/photos/:id（单图详情）

**消费链**：`PexelsClient.getById` → 门面 `getPexelsFromId`（`/pins/:id` 详情直达页）。响应是单个 `PexelsPhoto` 对象（非数组、无分页字段），形状即端点一 `photos[]` 的单元素：

````
curl -H "Authorization: <VITE_PEXELS_API_KEY>" \
  "https://api.pexels.com/v1/photos/358457"
````

归一化走同一条 `normalizePhoto` 路径，产出单个 `NormalizedWallpaper`，门面包一层 `toWallpaperItem` 直接返回卡片模型。这个端点的特殊性在错误语义：404（id 不存在）与 401/429 一样走"上抛不降级"路径——`getPexelsFromId` 有 Key 时没有 catch，分享出去的失效链接会以错误提示 + 白底呈现（13 篇 D-11 的已知留白）。它与列表端的另一差异是无 Key 降级形态：返回 `generateFallbackWallpaper()`（固定 id=1 的单张占位）而非列表。

## 5. 端点四：GET /v1/videos/popular（热门视频）

**消费链**：`PexelsClient.videosPopular` → 门面 `getPopularVideos`（视频页无关键词时的默认流）。响应与端点三同构（`PexelsVideoSearchResponse`），差异在参数面：支持 `min_width/min_height/min_duration/max_duration` 四个过滤参数（均未暴露 UI）：

````
curl -H "Authorization: <VITE_PEXELS_API_KEY>" \
  "https://api.pexels.com/v1/videos/popular?page=1&per_page=18"
````

它与 `/videos/search` 的响应无任何结构差异，归一化共用 `normalizeVideoResponse`，因此视频列表组件以 `mode`（popular/search）分流请求、以完全同一套渲染逻辑消费（《02-页面设计》3.2 节）。示意图值 `total_results: 76120`。

## 6. 端点五：GET /v1/videos/videos/:id（视频详情，双段路径）

**消费链**：`PexelsClient.videoById` → 门面 `getVideoById`（`/videos/:id` 详情直达页）。**路径是全 API 集成里最容易写错的一处**：官方视频详情挂在 `/videos/videos/:id`（双段 `videos`），源码第 310 行注释专门标注"注意官方路径是 /v1/videos/videos/:id"：

````
curl -H "Authorization: <VITE_PEXELS_API_KEY>" \
  "https://api.pexels.com/v1/videos/videos/2499611"
````

响应为单个 `PexelsVideo`（端点四 `videos[]` 的单元素，示意 id 2499611）。归一化后门面直接返回 `NormalizedVideo`（此门面函数不做 WallpaperItem 式的再适配，弹层数据由 `toViewerItem` 在消费侧转换）。错误语义与端点二同档：有 Key 时失败一律上抛，无 Key 返回 BigBuckBunny 示例视频保证可播（《03-接口设计》3.2 矩阵）。

**消费链**：`PexelsClient.collectionsFeatured` → 门面 `getFeaturedCollections`（合集列表"特色"Tab + 合集详情页元信息翻页匹配）。

````
# 响应（示意值）

  "per_page": 12,

  "next_page": "https://api.pexels.com/v1/collections/featured?page=2&per_page=12",
  "collections": [
    {
      "id": "nhxxxQ",
      "title": "晨雾与远山",
      "description": "精选 32 张高海拔山地的晨雾摄影",
      "private": false,

````

**这条响应定义了本篇最重要的一条"否定性契约"：响应中没有封面字段。** 合集卡片的封面必须对每个 id 再发一次端点八（`per_page=1` 取首图），N+1 由此而来——`src/utils/pexels-collection-cache.ts` 的整个调度器都是对这个缺口的补偿（ADR-004）。归一化把 snake_case 驼峰化（`media_count → mediaCount` 等）、数值兜底 0、`private` 强制布尔；`cover` 字段在协议层永远不赋值，由卡片局部状态回填。它的第二个消费场景是元信息匹配：合集详情页为查标题最多翻 3 页 × 80 条逐页 `find(id)`（`src/views/collection/index.vue` 的 `loadCollectionMeta`），命中即写 `metaCache`——Pexels 无"按 id 查合集元信息"的端点是官方形状缺口，本端点是唯一的替代路径。

## 8. 端点七：GET /v1/collections（我的合集，需用户登录态）

**消费链**：`PexelsClient.myCollections` → 门面 `getMyCollections`（"我的合集"Tab）。参数与端点七相同（`page/per_page`），响应同构。但它有一条独特的行为契约：

````
curl -H "Authorization: <VITE_PEXELS_API_KEY>" \
  "https://api.pexels.com/v1/collections?page=1&per_page=12"

# 前端直连场景下的典型实际结果：401 Unauthorized（浏览器未持有 Pexels 登录态）
# 门面层对它的处理：catch 全部错误 → 返回 { items: [], total: 0, totalPages: 0 }
````

需要讲清的是"为什么大多数用户拿不到数据"：该端点鉴权依赖的是 **Pexels 账号的用户级登录态**（浏览器 Cookie），而非 API Key 本身——配 Key 只证明"应用被允许调 API"，不证明"某个用户登录了 Pexels"。前端直连架构下没有获取用户登录态的路径，于是门面层把无 Key、请求失败、401 三种情形统一归一化为空数组（注释："返回空数组比兜底占位更准确，避免误导用户"），UI 呈现为空 Tab + 提示文案。这是官方端点里唯一被前端"主动放弃"的一个，也是 ADR-001（无账号架构）在数据契约上的直接投影（13 篇 D-10）。

它是全站唯一的混合类型数据源：`media[]` 每项靠 `type: 'Photo' | 'Video'` 判别字段分派，`normalizeCollectionMediaResponse` 按大写 type 归一化后打上小写 `type: 'photo'|'video'` 标签，产出联合类型 `NormalizedCollectionMediaItem`——`media-item.vue` 的卡片分支与 `toViewerItem` 的鸭子测试都以此为基础。这条端点有两个消费身份：详情页媒体流（每页 18）与封面调度器的单发探测（每页 1，取 `media[0]`：视频用 `image`、照片用 `url`）。错误语义是全矩阵最严的一格：有 Key 时任何失败一律抛出，注释理由是"媒体与封面会被写进缓存并当作真实数据展示，绝不静默换成 picsum 占位"——缓存污染防护（18 篇第 1.4 节同源原则）。

## 10. 降级响应示例集：同一调用的假数据形态

## 11. 本地存储与内存缓存结构示例

接口契约的另一半是"数据的另一半存放地"——浏览器侧。先给唯一的持久化条目（经 `pinia-plugin-persistedstate` 写入，业务代码 0 处直接调 localStorage）：

````
// localStorage
key:   "theme"
value: {"themeType":"dark"}        // "light" | "dark" | "system" 三选一
````

值是整个 state 的 JSON 序列化（store id 即 key），`src/utils/theme.ts` 启动时 `watch(themeType, changeTheme, { immediate: true })` 立即消费。若值被手动改坏（如 `{"themeType":"blue"}`），`changeTheme` 的 switch 落空、html class 不动——"非法主题等于维持现状"（12 篇 FAQ-8）。除此之外**没有任何持久化键**：无收藏、无历史、无缓存落地，这是 ADR-009 隐私边界的实物形态。

两处内存缓存的结构示例（模块级单例，刷新即失）：

````
// src/utils/pexels-collection-cache.ts（会话内存）
coverCache: Map<string, string>       // "nhxxxQ" => "https://images.pexels.com/videos/2499611/free-video-2499611.jpg"
metaCache:  Map<string, unknown>      // "nhxxxQ" => { id:"nhxxxQ", title:"晨雾与远山", mediaCount:32, ... }
waiters:    Map<string, Set<cb>>      // "nhxxxQ" => Set{ fn1, fn2 }（同封面多订阅者）
queue:      string[]                  // ["x9aaaB", "k2cccD"]（待拉取，FIFO）
enqueued:   Set<string>               // 与 queue 一致，防重复入队
// 熔断标量：rateLimited=false, rateLimitUntil=0, rateLimitNotified=false, draining=false

// src/directives/modules/lazy.ts（会话内存）
loadedCache: Set<string>              // "https://images.pexels.com/photos/358457/...h=350" （load 成功才登记）
stateMap:    WeakMap<HTMLImageElement, { src: string; stop: () => void }>
````

写入门槛与生命周期在《15》第 5 节已成表，这里只补结构示例揭示的两个事实：其一，`coverCache` 的值可能是视频封面帧地址（首图是视频时取 `image`），消费方 `collection-item.vue` 无须知道这一点——它只把字符串塞进 `<img :src>`，Pexels 的视频封面帧恰好是可作 `<img>` 源的静态图；其二，`stateMap` 用 WeakMap 以 DOM 元素为键，元素被虚拟滚动回收后条目随之可回收，无泄漏之忧——与 `loadedCache`（按 URL 索引、跨 DOM 生命周期共享）形成"元素态"与"资源态"两种缓存粒度的对照。

## 12. 收束：契约的三张面孔

把全篇合上，这个项目的数据契约以三张面孔存在：**Pexels 的原始面孔**（snake_case、八档 src、混排 type 判别、无封面字段、双段视频详情路径），它由官方定义、本应用只能适应；**归一化的中间面孔**（`Normalized*` 三兄弟 + `WallpaperItem`/`ViewerItem` 两个适配层），它由 `src/utils/pexels.ts` 与 `src/utils/viewer.ts` 定义、是本应用对契约的"翻译声明"；**门面的行为面孔**（降级矩阵、total 截断、错误分级），它由 `src/api/pexels.ts` 定义、决定"拿不到时给什么"。本篇的示例集覆盖第一张面孔的实例与第三张面孔的假数据形态，第二张面孔的字段级映射见《15》第 2 节的表格。当怀疑"数据没显示"时，排查顺序始终是：先看 Network 里的原始响应（第一张面孔是否变了）→ 再对照归一化输出（翻译是否丢失字段）→ 最后查门面行为（是否处于降级/熔断态）——三步分别对应三张面孔，与本篇的章节顺序一致。

## 1. 术语表

### 1.1 核心术语（六条，逐段展开）

**瀑布流（m-waterfall）**。指 `src/libs/waterfall/index.vue` 实现的"绝对定位多列布局"：每张卡片被放置到"当前最矮的列"顶部，列高随放置累加，最终形成参差错落的多列墙。区别于 CSS `columns` 方案（内容按列纵向填充、顺序不可预知），这里的布局算法自己计算每个 item 的 `left/top`，因此"第 N 项在哪、多高"完全可预知——这是虚拟裁剪得以实现的数学前提。组件是全站最复杂的单件（544 行 + utils.ts 29 行），三个列表页各自传入列数梯度（首页四档 2→5 列，其余三档 2→4 列）。机制详解见《07-模块详解》6.2，性能视角见《10-性能设计与优化》第 2 节，逐段走读见《18-代码走读实录》第 2 节，选型考古见《16-决策记录ADR》ADR-005。

**虚拟裁剪（虚拟滚动）**。只把"视口上下各 400px 缓冲（`VISIBLE_BUFFER = 400`）内的 item"渲染进 DOM 的技术，其余 item 只存在于数据数组与定位结果 `itemStyles` 中。三个不变量值得背下来：DOM 数量只与视口面积相关、与数据总量无关（理论上限 8000 条）；未定位的 item 始终保留渲染（否则永远测不到高度，布局自锁）；渲染集合与上一帧完全相同时不触发响应式更新（滚动大多数帧零渲染）。与它咬合的两个搭档：`v-lazy` 的 `loadedCache`（DOM 销毁重建时不重复请求图片）与 `useScrollRestore`（keep-alive 页面的滚动恢复）。术语在全集中的口径一致："虚拟裁剪"强调动作（updateVisible 的区间筛选），"虚拟滚动"强调能力整体，同义。出处：《07》6.2、《10》第 2 节、《18》2.4。

**熔断（429 熔断）**。`src/utils/pexels-collection-cache.ts` 的限流自保机制：当封面请求命中 429（配额耗尽），调度器置 `rateLimited = true` 并记录 `rateLimitUntil = now + 5分钟`；冷却期内所有封面请求直接回调空串（卡片显示占位色块）、排队项被整体释放；冷却到期后由 `isRateLimited()` 的惰性判断自动复位（无定时器）。配套的"每冷却期只提示一次"由 `rateLimitNotified` 标志保证。注意口径：**熔断只覆盖合集封面这一条静默失败路径**；列表类请求遇到 429 是"抛错 + 可重试"，不走熔断（错误分级见降级门面条目）。出处：《07》5.2、《03》第 4 节、《12》FAQ-3/FAQ-12、《18》3.3~3.4。

**降级门面**。`src/api/pexels.ts` 的整体角色：全部 8 个接口函数的"降级决策"收敛在这一个文件，页面层永远面对 `{ list, total }` 这类规整形状，不感知数据真假。两条铁律构成它的行为核心：其一，401/403/429 必须上抛不降级（否则熔断与配额提示成为死分支）；其二，按"数据可信度要求"分档——列表可降级、指向性详情（getPexelsFromId/getVideoById/getCollectionMedia）有 Key 时失败必须抛出、getMyCollections 一律空数组。完整行为矩阵见《15》第 3 节，决策考古见《16》ADR-002，逐段走读见《18》第 1 节。口语里的"降级"若不加限定词，通常指"Picsum 占位降级"这一分支。

**媒体查看器（media-viewer）**。`src/components/media-viewer/index.vue`（398 行），图片与视频共用的详情弹层：gsap 从卡片中心点放大进场、左右切换（按钮/方向键/触屏滑动）、清晰度胶囊、下载与"原页"外链、地址栏同步。它有两种运行形态——`embedded=true`（列表内弹层，pushState 写地址、popstate 关闭）与 `embedded=false`（直达页复用，地址已是详情路由、关闭时 router.back 或 push exitPath）。弹层的数据入口永远是 `ViewerItem[]`（`viewerItems` 与列表同序，切换零网络请求）。机制状态机见《05》第 2 节，走读清单见《07》10.1，地址同步的取舍见《16》ADR-006。

**双端分支（isMobileTerminal）**。`src/utils/helpers.ts` 导出的响应式布尔值，全站双端差异的唯一开关：移动端 UA 正则 ∨（有触摸能力 ∧ 视口宽 <1024），三条件叠加规避 iPadOS 13+ UA 伪装 Mac 的盲区。分支发生在组件层而非路由层（单路由表双端复用，ADR-008），典型应用：tabbar 的整体渲染裁剪、hover 下载浮层仅 PC、导航组件两端两套模板。已知边界：触屏笔记本与 iPad 横屏会走 PC 分支。出处：《00》3.1、《07》第 9 节、《12》FAQ-10。

## 3. 按任务阅读路径

四条路径都标注了"预计精读量"（以节计），并遵循同一条元规则：**先读约定与契约，再读机制，最后动手**——《11-扩展开发指南》第 0 节的三条公共约定是所有任务的前置。

### 路径一：加一个新页面（预计精读 6 节 + 动手 4 文件）

读《11》SOP-B（两条走法：轻量静态页 vs 复用列表骨架）→《02》第 1 节（路由表与 keep-alive 机制）→ 若进 `CACHE_NAMES`：读《16》ADR-007 与《02》第 6 节（三个配套：name 一致、滚动恢复、失活挂起）→ 若含列表：读《04》第 4 节（列表状态机四不变量）与《18》1.3（requestSequence 用法）→ 动手文件：`src/router/index.ts`、新页面目录、（可选）`src/views/layout/components/main-tabs.ts`。收尾走《11》第 7 节统一收尾（type-check、构建告警、手工验收、注释归档）。

### 路径二：适配一个新的外部 API（预计精读 7 节 + 动手 3 文件）

读《11》SOP-D（来源并存或整体替换的四步）→《16》ADR-002 与《03》3.2 节（降级矩阵必须原样继承：新家也要 401/403/429 上抛）→《04》3.2 节（三个归一化模型是返回形状的硬契约）→《15》第 3 节（门面行为矩阵，改完逐格验收）→ 若涉及视频清晰度：《04》3.2 的 pickVideoFile 规则 → 动手文件：`src/utils/`（新协议文件或改造 pexels.ts）、`src/api/pexels.ts`（通道选择）、`src/utils/pexels.ts` 的归一化函数。验证三件事：无 Key 降级形态、401/429 行为一致、`pnpm type-check` 全绿（归一化字段遗漏会被 strict 拦截）。

### 路径三：排查 429（预计精读 5 节，按现象分叉）

### 路径四：上线检查（预计精读 8 节 + 一张清单）

# XSearch 数据契约与示例集

> 项目：XSearch ｜ 版本：v1.2 ｜ 生成日期：2026-10-06 ｜ 依据：源码分析

## 导读：本篇与《03》《15》的分工

《03-接口设计》讲契约的设计意图与鉴权时序，《15-接口全量参考》讲全量 29 条路由的参数边界与错误码。本篇做第三件事：**给出可以直接复制执行的真实请求/响应示例**——每条核心接口配 curl 命令、成功响应 JSON、错误响应 JSON，字段形状严格按 `XSearch/search/api_views.py` 的视图实现与 `frontend/src/api.ts` 的 interface 构造，最后附一个真实的 ES 查询 DSL。选入的 9 组接口覆盖系统全部主干：搜索（#1/#2）、热搜与概览（#3）、要闻（#4）、榜单与新闻列表（#5）、详情（#6）、登录与 token（#7）、采集任务管理（#8）、数据管理（#9）。

**示意值约定**：所有示例中的具体取值——`id` 的 MD5 串、时间戳、token、数字统计——均为示意，仅字段名与结构与源码逐一对齐；`id` 字段是 ES 文档 `_id`（本项目中为 `md5(url)` 或站点原生 id，如 `aihot_8f2b…`、`douyin_hot_1`）。开发态直连后端用 `localhost:8000`；生产态经前端 nginx 反代同源（`https://你的域名`）。管理接口统一携带 `X-Admin-Token` 请求头。错误响应的完整枚举（401/429/409/413/503 等）见《15-接口全量参考》第九节总表，本篇只在每组接口旁列出该接口特有的错误形态。

**示例的构造方法**值得先交代一句，因为它决定了本篇可以放心当作联调参照：每条响应示例不是凭记忆写的，而是把 `search/api_views.py` 对应视图函数的返回字典逐键抄录、再把可选字段按实际分支补齐（比如搜索响应里 `did_you_mean/corrected/fuzzy/suggestions` 四个纠错字段恒在、恒为对应类型）；条目形状则对照 `frontend/src/api.ts` 的 `DocItem`/`SearchResult` 等 interface 双向核对——两端一致的字段才是契约，只在单侧出现的（如后端 `ServiceInfo` 的 endpoints 列表）会特别注明。反过来，`⚠️ 待确认` 的位置也用同一方法确定：任何一处后端字段与前端 interface 形状有出入的地方（如 `DbPurgeResult` 里前端多声明的 `source` 可选键），都按后端实现为准并在文中标注。

## 〇、通用约定速览（所有接口共享）

在逐条看示例之前，有四组横切约定需要先立住，它们决定了任何一个接口在异常时刻的行为，也是对接新客户端时最先要实现的分支。**第一是鉴权**：全站只有一层管理员 token，公开读接口（搜索、补全、概览、要闻、榜单、详情、图片代理、SEO）完全无鉴权；管理接口统一经 `require_admin` 装饰器校验 `X-Admin-Token` 头，失败一律 401 加 `code: "auth_required"`，不存在"部分保护"的中间态。**第二是错误体形状**：统一为 `{"error": "<中文可直接展示的文案>", "code": "<机器码，可选>"}`——文案给前端直接渲染，机器码给程序分支用，且机器码全集只有三个（`auth_required`/`not_found`/`too_many_login_attempts`），新增错误场景时优先复用既有状态码语义而非发明新码。**第三是依赖降级**：ES 不可用时读接口返回结构化 503（`_es_error()` 统一产出），唯 suggest 与 stats 两个接口降级为 200（前者返回空数组、后者置 `es_ok:false`）；Redis 不可用时所有接口静默跳过缓存与统计照常出数据——对接方收到 2xx 仍应检查业务降级字段。**第四是参数夹取**：`p` 非法回退 1、`hours` 夹 1-168、`pages` 夹 1-20、`limit` 夹 1-200，越界不报错而是收敛到合法区间，这是"宽容入口"的一致风格（白名单类参数除外——`sort/days/source/spider` 走严格白名单，不合法直接拒绝）。

## 二、搜索框补全：GET /api/suggest/

```bash
curl "http://localhost:8000/api/suggest/?s=%E4%BA%BA%E5%B7%A5"
```

成功响应（200，JSON 数组）：

```json
["人工智能芯片格局生变", "人工智能通识课进校园", "AI 与人工智能安全治理"]
```

契约要点：返回的是**标题字符串数组**而非对象数组（`JsonResponse(titles, safe=False)`），来源为 ES `suggest` completion 字段（input 来自 title 与 author）+ fuzziness 2 容错，保序去重且已排除榜单来源。两条降级约定：`s` 为空返回 `[]`；ES 故障也**静默降级**为 200 `[]`（补全是最不该报错的接口）。前端 250ms 防抖 + `suggestSeq` 竞态序号消费（《02-页面设计》4.2）。

## 七、管理员登录与 token：POST /api/auth/login/ 与 logout

```bash
curl -X POST "http://localhost:8000/api/auth/login/" \
  -H "Content-Type: application/json" \
  -d '{"username": "admin", "password": "correct-password"}'
```

成功响应（200）：

```json
{
  "ok": true,
  "token": "8f14e45fceea167a5a36dedd4bea2543c2b1e9a7d5f3c1b9e7a5d3f1c9b7e5a3",
  "username": "admin",
  "expires_in": 43200
}
```

错误响应（四种，状态码即语义）：

```json
{"error": "用户名或密码错误"}
```

```json
{"error": "失败次数过多，请 812 秒后重试", "code": "too_many_login_attempts"}
```

```json
{"error": "管理员账号未配置：请创建 XSearch/local_settings.py（参考 local_settings.py.example）"}
```

契约要点：token 为 64 位十六进制（`secrets.token_hex(32)`，256 bit 熵），此后所有管理接口以 `X-Admin-Token` 头携带；`expires_in: 43200`（12 小时）且**每次成功请求滑动续期**；锁定分支（429）带 `Retry-After` 头（秒数，直接可 `setTimeout`），且**先于密码比较执行**——密码正确也照样 429，自动化脚本不要把 429 当"密码错误"做字典尝试；账号未配置返回 503 而非 500（配置缺失不是程序崩溃，测试固化）。登出 `POST /api/auth/logout/`（携带要吊销的 token）幂等返回 `{"ok": true}`。token 存进程内字典：后端重启全部失效需重登（单 worker 架构的既定代价，见 ADR-04 与《16-决策记录ADR》）。

把 token 的完整生命周期按"四问"过一遍，对接方就能覆盖全部边界。**它存在哪**：后端进程内字典 `_admin_tokens`（token 到过期时间戳），不落盘、不入库、不进任何响应体之外的地方——因此没有"查所有 token"的管理接口，丢了只能等过期或重启。**它什么时候失效**：三种路径——超时（12 小时无请求）、登出（从字典弹出）、进程重启（字典清空）；服务端在校验失败路径上还会顺带清理全部过期 token，长期运行不积累。**它怎么续期**：每次成功的管理请求都把过期时间重置为"当前时刻加 12 小时"，所以"12 小时"指的是最后 activity 而非首次登录；前端无需刷新逻辑，只有 401 才需要重新登录。**它在传输中怎么保护**：走 HTTPS（VPS Nginx 终结）、以请求头而非 Cookie 携带（天然免疫 CSRF，这也是写接口豁免 CSRF 校验的前提——token 永不落入 Cookie）。

## 八、采集任务管理：start / status / history / stats

### 8.1 启动采集 POST /api/crawl/start/

```bash
curl -X POST "http://localhost:8000/api/crawl/start/" \
  -H "Content-Type: application/json" \
  -H "X-Admin-Token: 8f14e45fceea167a5a36dedd4bea2543..." \
  -d '{"spider": "news_rss", "pages": 2, "js": false}'
```

成功响应（202，任务已异步启动）：

```json
{
  "started": true,
  "pid": 41237,
  "started_at": "2026-10-06T09:30:00",
  "spider": "news_rss",
  "label": "新闻RSS(3源)",
  "job_dir": "news_rss_1788987390",
  "resumed": false
}
```

冲突响应（409，已有任务在运行——这是**正常业务态**，监控不应计入错误率）：

```json
{
  "started": false,
  "reason": "已有采集任务在运行",
  "pid": 41201,
  "started_at": "2026-10-06T09:28:11"
}
```

契约要点：`spider` 必须在白名单 `SPIDERS`（douyin_hot/aihot_hot/aihot_news/news_rss/news_backfill，可用 `GET /api/crawl/spiders/` 查询），未知爬虫同样 409（`reason: "未知爬虫: …"`）；`pages` 夹 1-20 默认 2；带 `resume_job` 时为 JOBDIR 目录名（经 `JOB_NAME_RE` 三重校验，见《18-代码走读实录》3.2），非法返回 409 `"非法的任务名称"`。启动是异步的：202 只表示子进程已拉起，终态由盯梢线程回写（无轮询依赖）。

异步模型值得对接方多理解一层，因为它决定了客户端该怎么消费这个接口。调用方拿到 202 后**不需要也不应该**长轮询等待终态——采集是分钟级的长任务，正确的消费姿势是按需查询两个只读端点：`/api/crawl/status/` 给"现在正跑着谁、日志尾部长什么样"，`/api/crawl/history/` 给"过去的每一轮跑成了什么样"。前端采集管理页的做法可以照抄：运行中每 2 秒查一次 status，空闲时降到 8 秒，页面卸载清掉定时器。409 冲突响应里附带的 `pid` 与 `started_at` 不是装饰——前端用它展示"正在运行的那个任务是谁"，对接方做并发控制时也应利用这两个字段判断"是不是同一个任务还在跑"。此外全系统同时最多一个采集任务，第二个请求无论指向哪个爬虫都会得到 409，这是互斥锁的语义而不是竞态缺陷。

### 8.2 状态与历史 GET /api/crawl/status/、GET /api/crawl/history/


## 十、附录：/api/search/ 实际发出的 ES 查询 DSL

以下是 `api_search` 在请求 `q=人工智能&source=news_ithome&days=30&sort=time` 时实际发送到 ES `quotes` 索引的查询体（对照 `api_views.py` 的 `_run_search`/`_HIGHLIGHT`/`_FACET_AGGS`/`_SORTS`，值示意）。读懂这个 DSL 等于读懂搜索接口的全部行为：

```json
{
  "query": {
    "bool": {
      "must": {
        "multi_match": {
          "query": "人工智能",
          "fields": ["title^3", "tags^2", "author", "content"],
          "minimum_should_match": "2<80%"
        }
      },
      "must_not": [
        {"terms": {"source": ["douyin_hot", "aihot_hot"]}}
      ]
    }
  },
  "post_filter": {
    "bool": {
      "must": [
        {"term": {"source": "news_ithome"}},
        {"range": {"create_date": {"gte": "now-30d"}}}
      ]
    }
  },
  "from": 0,
  "size": 10,
  "sort": [
    {"create_date": {"order": "desc", "missing": "_last"}},
    "_score"
  ],
  "highlight": {
    "pre_tags": ["<span class=\"kw\">"],
    "post_tags": ["</span>"],
    "fields": {"title": {}, "content": {}}
  },
  "aggs": {
    "facet_sources": {"terms": {"field": "source", "size": 20}},
    "facet_days": {
      "date_range": {
        "field": "create_date",
        "ranges": [
          {"key": "7", "from": "now-7d"},
          {"key": "30", "from": "now-30d"},
          {"key": "90", "from": "now-90d"}
        ]
      }
    }
  }
}
```

三层语义再复述一遍：`must` 的 multi_match 决定相关性与召回（title 三倍权重；超 2 词元要求 80% 命中）；`must_not` 永久排除榜单来源（它们没有发布时间语义，ADR-07）；`source/days` 筛选放 `post_filter`——聚合桶统计的是 post_filter **之前**的命中集，分面计数才能保持"其他筛选条件下"的口径。`sort` 里 `_score` 作次序兜底、`missing: "_last"` 让无日期文档沉底。若首查询 0 结果，还会追加两次补救查询：phrase suggester（`{"suggest": {"text": "…", "title_phrase": {"phrase": {"field": "title", "size": 1}}}}`）与模糊重搜（multi_match 加 `"fuzziness": "AUTO"`、`minimum_should_match` 放宽为 `"2<50%"`）。

## 十一、对接速查：十条契约红线

1. 高亮片段（`<span class="kw">`）是唯一携带 HTML 的内容，渲染前必须整体转义再还原；
2. `id`（ES `_id`）是详情与单文档管理的唯一寻址键，列表类接口必带；
3. 2xx 里混着降级：`stats` 的 `es_ok:false`、`suggest` 的 `[]`——收到 200 仍需检查业务降级字段；
4. `code` 字段只有三个值（`auth_required`/`not_found`/`too_many_login_attempts`），机器判断读它，文案展示读 `error`；
5. 429 的 `Retry-After` 是秒数；409 是正常业务态；
6. `rankings` 两种分支响应形状不同，按 `source` 区分；
7. AI 三源条目才有站内详情语义，新闻条目 `url` 是源站外链；
8. 管理接口一律先 `401` 检查（token 过期/缺失），token 进程内存储、重启即失效；
9. `view_nums` 语义随 `source` 变化（热度值/信源数），不要假设同一含义；
10. 契约演进规则是"只增不改"：删字段或改语义必须连同前端同批发布（《15-接口全量参考》第八节）。

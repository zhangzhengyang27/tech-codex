# XSearch 术语表与文档索引

> 项目：XSearch ｜ 版本：v1.3 ｜ 生成日期：2026-10-06 ｜ 依据：源码分析

## 导读：本篇的三个用途

这套文档共 21 篇，本篇是收尾的"地图与词典"，有三个用途。**用途一，术语表**：XSearch 的词汇来自三个世界（爬虫工程、Elasticsearch 检索、Django/Vue Web 开发），本篇把其中约五十个高频术语按"这个项目里它具体指什么"定义，并给出源码锚点——同一个词在不同项目里含义有差异（比如"采集任务"在这里有精确的五态机），以本篇的定义为准。**用途二，源码文件与篇目的反向索引**：拿着一个文件名，立刻查到哪些篇目讲过它、各讲到什么深度，避免在 21 篇里逐篇翻找。**用途三，按任务的阅读路径**：四个高频任务场景（加新爬虫站点、修搜索无结果、上线检查、排查爬虫被封）各给一条"按序读哪些篇、按序动哪些文件"的路线。三个用途共同的前提是：本套文档的所有结论都来自源码分析，路径引用相对 `XSearch/` 仓库根（`frontend/` 与 `XSearch/XSearch/` 是仓库内的前后端两个工程）。

## 一、术语表

### 1.1 采集侧（Scrapy 与爬虫工程）

这一组的术语有两条互相缠绕的主线：一条是**框架机制线**（spider → 中间件 → item → pipeline 的数据通道），一条是**治理线**（合规白名单、robots、限速、五态任务机）。读表时建议两条线分开走：先把"一个请求从发出到入库经过谁"顺着框架线走一遍，再回头理解每个环节上挂着什么治理约束——你会发现治理几乎全部作用在框架的**配置点**上（settings 与 custom_settings），而不是业务代码里，这正是这个爬虫子系统"业务文件里找不到一行反爬逻辑"的原因。另一个值得提前建立的认知是：本组的"采集任务"是 Web 层概念（CrawlManager 管理的一次子进程运行），与"spider"（一段可执行的采集代码）不是同义词——一次任务运行一个 spider，但 spider 也可以完全脱离任务机用命令行跑。

### 1.2 检索侧（Elasticsearch）

检索侧的术语围绕三个中心组织。第一个中心是 **mapping**：索引字段与分词器在 `QuoteDocument` 一处声明，"双分析器"（建索 `ik_max_word`、检索 `ik_smart`+停用词）是其中最需要理解的决策——它同时决定了召回质量与检索噪音水平，且改任何一个都要重建索引才对存量生效。第二个中心是**查询语义**：must/must_not/post_filter 三层的分工（打分召回 / 无条件排除 / 不影响聚合的过滤）与纠错链（phrase suggester → fuzziness → 热搜词引导）共同构成搜索接口的行为边界。第三个中心是**数据契约**：`_id` 幂等、`source` 维度、aware UTC 时区约定——这三个词没有一个是"检索功能"，但没有它们，去重、分面、时间筛选全会静默失真。读这组术语时手边最好开着《04-数据模型》与《18-代码走读实录》第二章对照。

|---|---|---|
| quotes 索引 | 业务文档唯一权威存储（历史遗留命名，可经 `ES_INDEX` 覆盖）；mapping 由爬虫侧维护，Django 无业务模型 | `crawler/pipelines.py` 的 `QuoteDocument.Index`；`search/models.py` |
| mapping | 索引字段与类型的声明（21 字段 + suggest）；`QuoteDocument.init()` 只在索引不存在时创建，已存在不更新 | `crawler/pipelines.py` 59-89 行；《11-扩展开发指南》SOP-2 |
| IK 分词 | 中文分词插件（`analysis-ik`），ES 必须用自建镜像 `xsearch-es-ik:8.15.3`；双分析器：建索 `ik_max_word` 细粒度、检索 `ik_smart` 粗分 | `deploy/es-ik.Dockerfile`；`crawler/pipelines.py` 67-69 行 |

### 1.3 服务与前端（Django / Redis / Vue）

这一组的术语有一个统一的母题：**单进程架构下的可靠性补丁**。单 worker（token、互斥、调度器全在进程内）是这个系统的地基，围绕它长出了一系列补偿机制——盯梢线程让任务状态不依赖消费者、原子写让状态文件经得起 kill 与 bind mount、冷却告警让"悄悄停更"变成一封邮件、降级语义让依赖故障不升级为页面故障。另一个母题在**前端**：既然没有状态管理库、没有单测框架、没有 UI 上的复杂路由库，那么"URL 即状态"、"类型契约"、"体积守门"就是补位的三大支柱——它们各自替代了一个"本可以引入的依赖"。读这组术语时留意每个词条的源码锚点：几乎每一条都对应一段记录了事故成因的注释，那是这些术语最好的扩展阅读。

| 术语 | 本项目中的定义 | 源码锚点 |
|---|---|---|
| 热搜词 | Redis zset `search_keywords_set`：每次搜索 `zincrby` 计数、裁剪前 100；stats 读 Top8、空结果/首页读 Top6 引导 | `api_views.py` 的 `_record_search_keyword`；`api_stats` |
| Redis 纯加速层 | Redis 挂掉只损失缓存与热搜词、绝不阻塞主流程；所有访问 try-except 包裹，3 秒双超时 | `api_views.py` 60-61 行；ADR-06（《16-决策记录ADR》） |

## 三、按任务的阅读路径

### 3.4 任务四：排查爬虫被封

**路线**：《12-FAQ与故障排查》第三节决策树（failed/empty/running 三分支分诊）→《16-决策记录ADR》ADR-08（合规白名单的设计与张力）→《08-安全与权限设计》第四节（爬虫合规四件套）→《10-性能设计与优化》第三节（限速参数全景）。

**动线**：先看采集历史状态与日志尾部——`failed` 看退出码与 Traceback；`empty`（正常退出 0 条）按爬虫分诊：news_rss 看每源"feed 解析出 N 条"是否为 0（源站改版），aihot 看日志 `aihot/ratelimited`（限流，等冷却再试，**不要退避重试加重压力**），douyin 看 `/tmp/douyin_hot_debug.png` 截图（页面改版对比）。风控类症状（444/412/403）：444 是抖音对"不像浏览器"请求的主动拒绝——确认 `FINGERPRINT_HOSTS` 白名单、browserforge 可用性、chromium 已装；412 的历史成因是指纹头没盖住内置 UA（已修）；403 常提示需要登录态——**项目不采集登录后数据，这是预期边界而非可修复故障**。处置纪律：不关 `ROBOTSTXT_OBEY`、不给白名单加站（除非完成合规预检并同步更新 `CrawlerComplianceTests`）、不提高限速（1.5-2 秒间隔是对源站的礼貌承诺）。若某源长期被封，两条正路：与站方沟通按 UA 放行，或按《16》ADR-08 的思路下线该源。

**完成标志**：分清"被封"与"没被封"——`empty` 不等于封禁（feed 改版、0 条解析失败同样产生 empty），444/412/403 也不全等于风控（403 的最常见解释恰恰是项目主动不做的登录态）。这个路径最重要的产出是一份结论：该源在当前合规立场下还能不能采、以什么方式采；结论写进 PR 描述，延续 2026-09-27 那次逐源核对留下的格式。

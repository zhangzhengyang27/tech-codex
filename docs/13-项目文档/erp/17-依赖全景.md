# 17-依赖全景

> 项目：ERP-CRM ｜ 版本：v1.3 ｜ 生成日期：2026-10-06 ｜ 依据：源码分析（v1.3：2026-10-06 一致性回刷——oshi"可能无消费者"经回源 grep 确认为"无消费者"）

本篇是两端依赖的**逐个解析手册**：后端以 `erp-crm/pom.xml`（297 行）为唯一清单，前端以 `erpcrm-ui/package.json`（v4.0.0）为唯一清单，每个依赖给出版本、用途、实际使用位置、选型理由、替代方案与升级风险。重点依赖（ORM、工作流引擎、Excel 导出、权限框架）单独立段展开。技术栈的宏观描述见《00-项目总览》第 3 节，构建与运行配置见《14-配置与环境详解》，本篇不重复选型结论之外的内容。版本号一律以两份清单文件为准（本篇写作时点的实际值），引用处标注文件与依赖坐标。

## 1. 后端依赖全景（erp-crm/pom.xml）

后端构建基座为 `spring-boot-starter-parent 3.5.16`（parent 继承，Java 17），因此凡未显式写版本的依赖均由 BOM 管理版本。仓库配置为阿里云 nexus 镜像（`pom.xml` 第 271-294 行），打包由 `spring-boot-maven-plugin` 完成（`repackage`，mainClass `com.ec.ErpCrmApplication`，`<finalName>erpcrm</finalName>`，devtools 在 repackage 时被排除）。

### 1.2 重点依赖展开：ORM 三件套（MyBatis + PageHelper + Druid）

这三个依赖共同构成数据访问层，选型是"手写 SQL 优先"路线。**MyBatis 3.0.3（starter）**：全部 SQL 以 XML 手写/生成（`erp-crm/src/main/resources/mapper/{sys,crm,erp,saas}/*.xml` 共 43 个映射文件），typeAliasesPackage `com.ec.**.domain`，mapperLocations `classpath*:mapper/**/*Mapper.xml`（`application.yml` mybatis 段）——新增 XML 放对目录即被扫描，无需登记。选 MyBatis 而非 MyBatis-Plus 的理由有三：其一，项目继承 RuoYi 的 XML 写法存量（含 `restrictOwner` 这类条件 SQL 谓词、`${params.dataScope}` 切面片段），换框架等于全量重写；其二，多租户动态数据源架构下需要完全掌控 SQL 形态，Query Wrapper 反而隔了一层；其三，生成器 `gen_business_modules.py` 的模板产出就是 RuoYi 风格 XML（见《18-代码走读实录》第二走读），工具链已闭环。升级风险：mybatis-spring-boot 3.0.x 对 Spring Boot 3.5 的兼容性经过 CI 验证，2.x→3.x 的 `SqlSessionFactory` 配置迁移已完成，再升级主要是跟随 Spring 官方节奏。

**PageHelper 2.1.0**：物理分页拦截器，`supportMethodsArguments: true` 使其能从请求参数自动取 `pageNum/pageSize`——这是 `PageUtils.startPage()` 能生效的前提；配套做了两条项目级加固（git 提交 `afaa542`）：pageSize 钳制上限 500 防恶意大分页、`PageClearInterceptor` 每请求结束清理分页 ThreadLocal 防容器线程复用串页（AGENTS.md 后端约定）。替代方案是手写 LIMIT 或 MyBatis-Plus 的 IPage，前者侵入每个 SQL、后者绑定框架，都不如独立分页插件正交。升级风险集中在"startPage 后必须立即执行查询"这条纪律被破坏时，分页会染到下一条 SQL——这是使用纪律问题而非版本问题。

**Druid 1.2.25**：本项目最"非标准"的依赖用法——不用 starter，纯依赖 + 编程式装配。理由在《01-系统架构》第 4 节已展开：多租户"每租户一池"需要运行时动态创建数据源（`DynamicRoutingDataSource.addDataSource`），`DruidProperties.dataSource()/tenantDataSource()` 两个方法定义主库/租户两档规格（租户池 1/1/10 的连接数账见《10-性能设计与优化》1.1）。HikariCP 虽是 Spring 默认且性能更优，但当时需要 Druid 的三件东西：可编程建池的成熟 API、内置慢 SQL 统计与防火墙（`application-druid.yml` 的 stat/wall 配置）、以及运维熟悉的监控控制台（dev 环境开启、账号走 `EC_DRUID_*`）。升级风险：Druid 与新 JDK 的兼容性历史上偶有滞后（1.2.x 线目前良好）；另一处隐性风险是 `DruidMonitorConfig` 把控制台账号接到 `EC_DRUID_*` 三个环境变量，升级 starter 化会丢失这套自定义装配。

### 1.3 重点依赖展开：Flowable 7.0.1

Flowable 是后端最重的单一依赖（引入十余个传递依赖与 40+ 张 ACT_* 引擎表）。使用面却刻意收得很窄：全库只有 `crm/service/impl/CrmApprovalServiceImpl.java` 一个文件 import `org.flowable`，仅用 `RuntimeService/TaskService/HistoryService` 三个 API 与一个 BPMN 流程定义（`erp-crm/src/main/resources/processes/contract-approval.bpmn20.xml`，key=`contractApproval`）。配置三板斧（`application.yml` 第 148-151 行）：`database-schema-update: true`（引擎表启动自动建在主库）、`async-executor-activate: false`（关闭异步执行器，审批全同步执行——这是 `taskService.complete` 同步语义的前提，若打开会改变补偿式一致性的失败窗口）、`check-process-definitions: true`（启动校验流程定义与引擎版本匹配）。选 Flowable 而非 Camunda 7 的理由：课程原码生态与中文资料更丰富、BPMN 2.0 规范实现完整、Spring Boot 3 starter 官方维护；而非自研审批单的理由是"轻量审批单"已被试用过并放弃（git 提交 `b0f2684` → `9f51b23` 的替换史，见《16-决策记录ADR》ADR-003）。升级风险：Flowable 大版本升级伴随引擎表结构变更与历史数据迁移脚本，当前 `database-schema-update: true` 只处理新建不处理跨大版本迁移，升级前必须备份主库；7.0.x 对 SB 3.5 的兼容良好，跨 7→8 的风险 ⚠️ 待确认届时评估。另一个值得记录的边界：引擎表落主库意味着 Flowable 的启动建表动作会写主库——首次启动前主库账号需要 DDL 权限，部署时容易踩（compose 栈的 db-init 已考虑）。

### 1.4 重点依赖展开：安全与序列化（Spring Security + jjwt + fastjson2）

**Spring Security 6.x**：安全链完全按 6.x 新版 Lambda DSL 配置（`auth/config/SecurityConfig.java`），`@EnableMethodSecurity` 开启方法级 `@PreAuthorize("@ss.hasPermi(...)")`，自定义 `PermissionService` 以 `@ss` bean 名暴露。会话策略 `STATELESS`、CSRF 关闭、匿名白名单与 401 的"HTTP 200 + body 401"协议见《08-安全与权限设计》第 3 节。升级风险主要是 6.x 内部持续的小重构（如 `SecurityFilterChain` bean 式配置取代 `WebSecurityConfigurerAdapter` 已完成迁移）。

**jjwt 0.12.7**：三件套拆分（api/impl/jackson）按官方推荐；0.12 的新 parser/builder API 与"HS512 密钥必须 ≥64 字节"的硬约束都已在 `TokenService.getSecretKey()` 落实（`EcProdConfigVerifier` 亦有校验）。升级风险低，但注意 0.12 是 API 大改版本（旧 `Jwts.parser().setSigningKey` 写法失效），从课程原码迁移时已踩平。

**fastjson2 2.0.64**：承担两类职责——Redis 值序列化（`FastJson2JsonRedisSerializer`，含白名单 autotype 配置，git 提交 `e0d8874`"Redis 序列化白名单"是加固痕迹）与部分工具类内的 JSON 转换。注意 Spring MVC 的 HTTP JSON 消息转换并未换成 fastjson2，仍走 Jackson 默认——即"Redis 用 fastjson2、HTTP 用 Jackson"的双栈现状，两套日期/空值序列化语义略有差异，排查"Redis 里存的和返回的字段不一致"类问题时先想到这里。替代方案是统一 Jackson（可减少一个依赖），但 RuoYi 栈的存量写法依赖 fastjson2 特性，迁移收益低风险高。fastjson2 与历史声名狼藉的 fastjson 1.x 不同，安全模型重写，版本保持跟随即可。

### 1.5 重点依赖展开：Excel 导出（POI 5.3.0 + @Excel 注解体系）

Excel 是业务系统的高频刚需（每个列表页都有导出按钮），项目自建了一套轻量注解体系：`common/annotation/Excel.java` 定义列头/类型，`common/utils/poi/ExcelUtil.java`（继承自 RuoYi）在导出时反射读取 `@Excel(name="中文列头")` 注解生成 xlsx。使用密度很高：`CrmCustomer.java` 有 10 个导出字段、生成器 `gen_business_modules.py` 的 `gen_domain` 函数为每个非主键非 remark 列自动加 `@Excel` 注解（见《18-代码走读实录》第二走读）。两种导出形态并存（CRM 系统管理用 POST + HttpServletResponse 直写流、ERP 主数据用 GET + AjaxResult 包裹）的差异已在《15-接口全量参考》第 7 节说明。选 POI 而非 EasyExcel（阿里）：EasyExcel 在大数据量流式写出上更优，但 `@Excel` 注解体系与存量代码深度绑定，且本项目导出量级（分页钳制 ≤500 的同源查询全量导出）未到 EasyExcel 的收益区间 ⚠️ 待确认未来导出量级。升级风险：POI 5.x 需要 JDK 8+ 且 5.3.0 与 log4j-api 传递依赖的版本对齐要注意；Excel 导入（用户导入 `importData`）同走 ExcelUtil，格式兼容性回归时两个方向都要测。

### 1.6 后端依赖的三个历史决策点

通读 pom 时有三处"看似奇怪、实则有意"的写法值得专门解释，它们都是加固期留下的决策痕迹。第一处是 **Redis starter 的 lettuce 排除再显式引入**（第 84-102 行）：`spring-boot-starter-data-redis` 里把 `lettuce-core` 排除，紧跟着单独声明 `lettuce-core` 与 `commons-pool2`——效果上等价于默认行为，但把"连接池依赖 commons-pool2"从隐式传递变成显式声明，防止上游 starter 未来调整传递依赖时 lettuce 池静默失效（lettuce 无 pool2 时会退化为单连接，表现为并发下 Redis 排队）。第二处是 **devtools 的 optional 与 repackage 排除双保险**：`<optional>true</optional>` 保证它不传递，`spring-boot-maven-plugin` 的 excludes 保证打出的生产 jar 不含它——devtools 的重启类加载器若混进生产包会引发诡异的类转换异常，双保险是 RuoYi 社区踩坑后的标准写法。第三处是 **ec-quartz 的注释块**（第 230-236 行）：课程原码带 quartz 定时任务模块，合并单模块后项目改用 Spring `@Scheduled`（`TenantExpirationJob`、`IdleDataSourceEvictor` 都是），quartz 依赖被注释保留而非删除——它本身就是一个"决策化石"，提醒后来者"定时任务框架曾经存在、已被有意放弃"，清理建议见第 3.1 节。这三个点合起来说明：这个 pom 里的每一行非标准写法都能在 git 提交或 AGENTS.md 里找到解释依据，读 pom 与读代码同等重要。

### 1.7 版本属性的维护口径

`pom.xml` 的 `<properties>` 段（第 21-40 行）集中管理全部显式版本号（druid/mybatis/pagehelper/fastjson2/oshi/jna/commons 系/poi/jwt/springdoc 共 11 个属性）。维护口径有两条：一是**凡 BOM 管得到的绝不写版本号**（web/security/redis/mysql/actuator 全部裸引用），保证升级 parent 时整组联动；二是**显式写版本的都是 BOM 不管或需要偏离的**（flowable 不在 BOM、druid 有意用纯依赖）。检查一个依赖"该不该升级"的最快方法就是看它出现在 properties 还是裸引用：前者按自己的节奏升级并跑全量测试，后者跟随 parent 升级即可。这个口径没有文档化在仓库内（pom 无注释说明），本节即其事实记录，升级操作前建议先读《09-测试与质量保障》第 4 节确认两端门禁基线。

## 3. 依赖健康度评估

总体判断：后端 20 个直接依赖全部有明确用途，密度健康（无依赖地狱）；前端 36 个运行时依赖中约 6 个存在"低引用或零业务价值"的冗余，属于底座迁移的沉淀物而非决策失误。两端均无已知高危漏洞版本（fastjson2/poi/jjwt 均为修复后的大版本线 ⚠️ 待确认定期跑 `mvn dependency-check` 或 `pnpm audit` 复核）。

### 3.3 升级风险总览

按"动不得 → 小心动 → 随便可动"排序：**动不得**——rolldown 1.2.5 钉版（升级需连带迁移 codeSplitting API 并验证构建，D15）、axios 精确锁版、fastjson2 与 Redis 白名单的配套；**小心动**——Spring Boot/parent 升级（牵动 security 6 API、druid 兼容、flowable 引擎表）、MyBatis starter 大版本、Element Plus 大版本（86 页回归）、Flowable 跨大版本（引擎表迁移脚本）；**随便动**——commons-io、file-saver、mitt 等无深度耦合的工具件。整体节奏建议：跟随 spring-boot-starter-parent 的 3.5.x 补丁线（安全补丁优先），前端跟随 pure-admin 模板的上游节奏，两者都每季度复核一次；任何升级前先跑两端质量门禁（`mvn test` 47 例基线 + `pnpm lint/typecheck/test`），绿灯基线是升级的唯一安全网（命令见《09-测试与质量保障》第 4 节）。

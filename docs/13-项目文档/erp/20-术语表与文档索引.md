本篇是文档集（00-20）的**收口篇**，解决三个检索问题：一是术语对齐——业务与技术术语在 17 篇文档中反复出现，本篇给每个术语一个"本文档集内的标准定义 + 权威出处"；二是反向索引——知道文件名（或表名、类名）却不知道在哪篇讲过时，按"源码文件 → 篇目"反查；三是任务路径——带着一个具体任务（修 bug/加模块/加租户/上线）来的人，按最短路径读对应的篇目组合。术语的深入解释一律指向对应篇目，本篇只给"一句话定义 + 锚点"。

## 1. 业务术语表

业务术语的边界先说清楚：本表的"标准定义"是**本项目语境下的操作定义**（哪个表、哪个字段、哪个枚举值），不是教科书式的行业定义。这样做的理由有两个：其一，同一术语在通用 CRM 语境里可有多种实现（比如"公海"有的产品是独立表、有的是状态位），本文档集统一到本项目唯一的实现口径上，读者拿着定义就能直接定位代码；其二，术语与字段的绑定关系是排查业务 bug 的最快入口——"这个客户为什么在公海列表里"这个问题，按术语表查到 `status='2'`，再查 `customerToPoolByIds` 的 SQL 谓词即可收敛到答案。每个术语的"出处/锚点"列给出最权威的一到两篇文档，深入机制一律跳转，本表不重复。

## 2. 技术术语表

技术术语与业务术语的分层逻辑不同：业务术语对应"产品功能如何落到数据"，技术术语对应"架构决策如何落到代码"。两者叠加才是完整的认知——比如读懂"客户公海"要同时知道单表三态（技术）与公海业务规则（业务）。技术术语表特别收录了那些**在本项目里有专属含义**的词：像"CAS 认领""补偿式一致性""sweepOnce 模式"这类词在通用语境里各有解释，但在本项目里它们指向特定的实现文件与既定纪律，读者在代码评审或提交信息里遇到时应按本表口径理解。两条使用纪律：术语首次出现于 commit message 或注释时，优先引用本表的锚点篇目而非重新解释；新增术语（尤其是新 SOP 引入的模式名）应同步登记进本表，保持"一个概念一个名字"。

## 3. 高频混淆点：术语辨析

术语检索之外，有五组概念在实际沟通中最容易混用，单独立段辨析。

**"CRM 订单"与"ERP 销售订单"**是两套完全独立的数据：`crm_order`（order_no 唯一键、带审核状态 0/1/2、归属 CRM 域 `com.ec.crm`）与 `erp_order`（关联 `erp_client`/`erp_tax_info`、无审核端点、归属 `com.ec.erp`）没有任何外键或代码级关联，首页"订单趋势"统计的是 CRM 订单（`CrmStatisticServiceImpl.dashboardStats` 查 `ICrmOrderService`）。汇报口径与报表需求提小时必须先问清是哪一个。

**"主库表"与"租户库表"**：同名表可能两库都有而语义不同——`crm_approval` 主库那份是预留的"审批中心整体迁主库"结构（当前不被写入），租户库那份才是实际留痕；`sys_oper_log` 恰好相反（`@Log` 写当前租户库）；`sys_logininfor` 只有主库一份（全局链路）。判断一张表落在哪，先查《04-数据模型》第 2/3 节，再看 service 层有没有 `@DataSource(MASTER)`。

**"租户名"与"租户库名"**：请求头 `tenant` 传的是租户名（如 `tenant1`），不是库名；库名（如 `ryt_nelub7xr`）只存在于 `master_tenant.database_name` 列与 MySQL 侧。手工建测试租户时最常见的错误就是把库名填进请求头——拦截器按租户名查登记表，查不到即拒绝。

**"审批任务 ID"与"审批留痕 ID"**：`GET /crm/approval/{id}` 收 Flowable 任务 ID（UUID），`crm_approval.id` 是自增主键——两者都在审批页出现过，误传得到空对象而非报错（坑的完整分析见《07-模块详解》2.2）。

**"连接池淘汰"与"数据删除"**：`IdleDataSourceEvictor` 关闭的是缓存里的 JDBC 连接池，租户库本身原封不动，下次访问自动重建；把日志里"淘汰租户数据源"理解成"清了租户数据"是纯粹的误读（《01-系统架构》第 5 节）。

## 5. 按任务阅读路径

四条路径的编排逻辑说明一下：每条路径都遵循"先建立心智模型 → 再进源码定位 → 最后按纪律收尾"的三段式，避免新人直接扎进代码丢失全局。路径里引用的篇目均已在前文出现，遇到"篇目与源码不一致"时按第 6 节的权威性排序处置。若你的任务不在四条之列（例如"给看板加一张图""接一个新的导出格式"），最接近的做法是取 5.1（改既有行为）或 5.2（新增能力）的骨架，再把《10-性能设计与优化》《17-依赖全景》对应章节补进前置阅读。

### 5.1 修一个审批流 bug

最短路径：先读《18-代码走读实录》走读一（逐段行为模型：库切换纪律、两阶段顺序、补偿回退点、崩溃窗口语义）→ 带着模型进 `CrmApprovalServiceImpl.java` 对照现象定位 → 复现与验证读《09-测试与质量保障》3.4 与 `CrmApprovalFlowIntegrationTest`（fixture 直接插合同行、`deleteHistoryQuietly` 清理手法）→ 若涉及"taskId 传错/列表查不到/重复提交"类现象，查《12-FAQ》已知坑与《07-模块详解》2.2 的使用提醒（`{id}` 是任务 ID）。改码红线：两库操作不得包进同一事务、`useMaster()/useTenant()` 必须成对、补偿 SQL（`CrmApprovalMapper.xml` 的 revert*）不可改动语义。

### 5.2 新增一个业务模块

按《11-扩展开发指南》SOP-1/SOP-2 全程操作（九步链或生成器路径），前置阅读两篇：《01-系统架构》第 4 节（十条设计决策，尤其事务陷阱与业务域不横向 import）、《18-代码走读实录》走读二（生成器模板逻辑——用 SOP-2 前必须懂它会生成什么、不生成什么）。数据层三处同步规则查《04-数据模型》5.3 与 SOP-5；权限串与菜单 SQL 范本查《08-安全与权限设计》4.2 与 `db-backup/upgrade_business_modules.sql`；归属校验照抄走读三的 restrictOwner 范式（勿复刻生成器产物的无守卫形态，D03）。收尾验收：`mvn test` + 两端门禁 + 菜单/权限/导出五端点冒烟（SOP 通用收尾清单）。

### 5.3 新增一个租户

优先走产品化路径（注册页自助建库，零手工），操作规程见《11-扩展开发指南》SOP-3，流程细节见《05-核心流程》流程一（建库→模板→登记的完整时序与失败回滚）。手工路径（测试租户）的口令列写法是唯一坑点：配了 `EC_TENANT_PASSWORD_KEY` 时必须写密文或留明文等启动迁移器改写（密文格式错误表现为 JDBC Access denied，《08-安全与权限设计》7.1）。新增后验收三件事：`SHOW TABLES` 对照模板 40 表、登录验证菜单/字典/角色种子就位、`/system/tenant/quota` 返回配额。若新租户缺表，回查 SOP-1 第 1 步是否漏改租户模板（最高频翻车点）。批量租户的备份/迁移视角查《14-配置与环境详解》6.2（backup.sh 逐库枚举可改造为迁移游标）。

### 5.4 上线检查（Release Checklist）

按顺序过五关。第一关配置：`config/application-prod.yml.example` 落地、`EcProdConfigVerifier` 必配密钥清单逐项核对（`EC_TOKEN_SECRET` ≥64 字节、`EC_TENANT_PASSWORD_KEY` 必配、Druid 控制台与 springdoc 已关）、《14-配置与环境详解》5 与 8 的排障三经验。第二关数据：主库+模板 SQL 初始化正确（`sql/erp-crm-master.sql` 口令列为 ROTATED 占位、真实凭据只走 .env）、存量租户库 upgrade 补齐且幂等性人工确认（裸 ALTER 不重跑）、《04-数据模型》5.3 执行规程。第三关安全：CORS/nginx TLS 由部署层确认 ⚠️ 待确认、`/profile/**` 匿名直出与验证码缺失两项已知风险按《13-技术债务与演进建议》D01/D02 决策是否带病上线、备份 crontab 接入并演练一次恢复（`ops/backup.sh` 恢复命令在脚本头部注释）。第四关可观测性：9091 指标端口可达、`ops/prometheus` 抓取配置接入、Grafana 面板导入。第五关冒烟：登录→客户 CRUD→提交审批→审批→采购入库→调拨六步全通（各步请求契约照抄《19-数据契约与示例集》）；Docker 栈部署则先读《06-部署运行》4.2 并注意 compose 未实测的告警（D14）。上线后首周每日巡检 `erp.login.total`、`erp.datasource.pools.active`、`erp.approval.total{result=rolled_back}` 三个指标（ rolled_back 频发即审批链路异常信号）。

> 项目：html5-examples ｜ 版本：v1.0 ｜ 生成日期：2026-10-06 ｜ 依据：源码分析

---

## 1. 接口体系总览

项目的"接口"分三个层面，阅读源码时务必区分：

1. **后端 REST API**：`server/src/modules/*/**.controller.ts` 暴露的 `/api/*` 端点（NestJS），前端经 `src/api/client.ts` 调用，开发期走 Vite 代理 `/api → localhost:3000`。
2. **示例-框架契约**：`CodeExample` 等数据结构与 `src/utils/sandbox.ts`、`src/api/examples.ts` 之间的格式约定——示例正文虽已本地化，契约不变。
3. **前端内部接口**：`src/api/*.ts` 暴露给页面的函数签名（与后端结构同构）、composable 的 props/事件契约。

鉴权模型：全局 `JwtAuthGuard`（`app.module.ts` 的 `APP_GUARD`）默认拦截一切请求，控制器用 `@Public()` 装饰器（`modules/auth/decorators/public.decorator.ts`）显式放行公开端点；写操作叠加 `AdminGuard`（`modules/auth/guards/admin.guard.ts`）。访问令牌以 `Authorization: Bearer <accessToken>` 携带（`client.ts` 的 `authTokenProvider` 注入），cookie 会话作为无 token 时的回退通道（`credentials: 'include'` + CORS `credentials: true`）。

这套鉴权设计有一个值得称道的取向：**默认拒绝、显式放行**。与其让每个接口自己声明"要不要鉴权"（容易漏），不如全局先拦死，再用 `@Public()` 一个装饰器把公开接口白纸黑字地列出来——审查一个控制器的安全性时，只需要数一数 `@Public()` 的个数。同理，管理类写操作在"已登录"之上再叠一层 `AdminGuard` 角色检查，形成"公开 < 登录 < 管理员"的三级访问漏斗。前端与之配套的是 Bearer 优先、cookie 兜底的双通道：正常用户走无感刷新的 token 对，残存的 cookie 会话保证老版本前端不至于突然全员掉线。理解这个漏斗后再看端点表，每个接口该挂在哪一级就不再需要记忆，而是可以推导。

## 2. 后端 REST API 端点总表

以下逐条来自对控制器源码的 grep 实证。**标注 [公开] 的为 `@Public()` 放行端点；标注 [Admin] 的挂 `AdminGuard`；未标注的需登录。**

阅读这些端点表时建议带着三个视角。**视角一：消费方是谁**——topics/categories/examples 的 GET 全部公开，因为它们支撑的是无登录的内容浏览；favorites 与 auth 未标注的端点全部要登录，因为它们操作的就是"当前用户"；写操作几乎清一色 [Admin]，对应"内容由维护者经管理后台或脚本治理"的运营模式。**视角二：参数形状**——列表端点统一接受 `page/limit` 分页对加若干业务过滤字段，详情端点统一以路径参数收 id 或 slug，写端点统一收 DTO（class-validator 校验）；三个"统一"让新端点的接入几乎没有学习成本。**视角三：活跃度**——标有"历史板块"的端点（visual-demos、chart-examples）与 examples 的部分端点属于冻结资产（见 01 篇 §3.4），调用它们之前先确认前端是否还有消费方。

### 3.2 沙箱契约（`src/utils/sandbox.ts`）

`buildSrcDoc(example, snippet?)` 对示例源码的隐含约定：

1. `html` 是**片段**：框架负责包上 `<!DOCTYPE html>`、charset、viewport、`<base href="{origin}/">`（使 `/shared-assets/`、`/static-sites/` 绝对路径可用）与统一 reset CSS；
2. `topicSlug === 'html5'` 时自动包 `.example-stage` 舞台容器（宽高 100vh、flex 居中），补偿导入时被清洗掉的 body 布局样式——**html5 主题示例的 css 中的 body 选择器应在导入期改写为 `.example-stage`**（AGENTS.md 8.7 第 6 步）；
3. `snippet` 参数（`{ label, css?, html?, js? }`）：css/js **追加**到示例对应段之后，html **整体替换**——这是详情页「变体」切换的实现基础（`DemoSnippet.label` 为变体名）；
4. `js` 中的 `</script` 会被转义为 `<\/script` 防止提前闭合；重复拼接的两段完全一致 JS 会被 `deduplicateRepeatedJs()` 去重；
5. 需要加载同源资源的示例会被 `needsSameOrigin()` 正则检出，sandbox 属性追加 `allow-same-origin`。

这份契约的价值在于它同时服务了三方而没有任何一方需要妥协。内容生产者只需要产出"干净的片段"——不用关心文档结构、编码声明、样式重置；预览框架因此获得完全的渲染控制权——统一字体基线、统一 reset、按主题注入舞台容器，还能在拼装层做安全处理（script 标签闭合转义）；而示例本身保持了"复制出去也能跑"的完整性——源码面板展示的仍是片段原文，用户复制三段到本地 HTML 里稍加包装即可独立运行。变更这份契约前必须同时评估三个方向的影响面：新增"框架自动注入的全局能力"（如默认字体）会不会改变存量示例的渲染？收紧"源码清洗规则"会不会让旧示例在下次加载时行为漂移？放宽"变体合并语义"会不会让 snippets 的追加顺序产生覆盖歧义？

## 4. 前端 HTTP 客户端约定（`src/api/client.ts`，397 行）

所有后端请求的统一行为：

先说这个文件在架构中的位置。`client.ts` 是全站唯一允许出现裸 `fetch` 的地方，397 行代码完成了通常由 axios 之类库承担的全部职责——正因如此，它没有引入任何运行时依赖，行为完全透明可测（配套 `client.test.ts` 对重试与错误归一有专门用例）。它对调用方暴露的是五个谓词函数（get/post/put/patch/del）加两个注入点（token provider 与 401 处理器），对下则把传输细节（超时、重试、缓存穿透、卸载期 keepalive）全部封装。阅读它的推荐顺序是：先看 `request()` 主循环（重试编排），再看 `doRequest()`（单次请求与错误折叠），最后看 `toApiError()`（异常归一），三个函数吃透，全站的网络行为就尽在掌握。

| 特性 | 约定 | 源码位置 |
|------|------|---------|
| baseURL | `import.meta.env.VITE_API_BASE_URL ?? '/api'` | `defaultConfig` |
| 超时 | 10s（`AbortController` + `linkSignals` 合并外部 signal，兼容无 `AbortSignal.any` 环境） | `request()` |
| 重试 | 仅 GET 且网络错误(0)/5xx，默认 2 次，指数退避 `min(500*2^(n-1), 2000)ms` | `shouldRetry()/backoffDelay()` |
| 401 | 触发 `authFailureHandler`（authStore 注册：清会话 → `/login?redirect=`）；403 不触发 | `request()` catch 分支 |
| 鉴权头 | `authTokenProvider()` 返回值非空则附 `Authorization: Bearer` | `doRequest()` |
| 空响应 | 2xx 且空 body 返回 `null as T`（调用方应声明 `T \| null`） | `doRequest()` |
| 缓存 | `disableCache=true` 时 GET 附 `_t` 时间戳 | `get()` |
| 卸载期请求 | `fireAndForgetKeepalive()`：`keepalive:true`、不重试不抛错、不读响应（64KB body 上限），用于 beforeunload 快照保存 | 独立导出 |
| 查询串 | `buildQueryString` 过滤 undefined、全值字符串化 | 私有函数 |

**错误处理约定**：错误统一为 `ApiError`（`status/statusText/url/body`）；`getApiErrorMessage(error, fallback)` 是全站唯一的错误文案提取器——优先取后端 `body.message`（NestJS `string | string[]`，数组以「；」连接），否则回退 `error.message` 或 fallback 文案。AbortError 归一为 `ApiError(408)`；网络异常归一为 `ApiError(0)`。

后端侧约定（`server/src/main.ts`）：全局 `ValidationPipe{ whitelist, forbidNonWhitelisted, transform }`——DTO 未声明字段直接 400 并返回字段级 message 数组，与前端 `getApiErrorMessage` 的数组拼接逻辑互为配套。

错误处理的整体哲学是"**语义在异常对象上，展示在最后一公里**"。`client.ts` 不弹 toast、不跳页面，它只负责把五花八门的失败（网络断、超时、4xx、5xx、JSON 解析失败）折叠成携带状态码与后端原文的 `ApiError`；真正决定用户体验的展示逻辑放在两层——全局层处理"会话失效"这种横切事件（401 → 清会话跳登录），页面层处理业务性失败（`useResourceFetch` 的 error 分支渲染 `EmptyState` 重试按钮，或 `toast.error(getApiErrorMessage(e))` 轻提示）。这个分工避免了两类常见事故：错误提示在 client 与页面各弹一次；以及页面各自为政地解释 401 导致行为不一致。编写新的 api 模块时，请继续保持"只抛不弹"的纪律。

## 5. 新增一条 API 的标准契约清单

若要给后端新增资源模块（对照既有模块的固定四件套）：

1. `modules/<name>/entities/<name>.entity.ts`：TypeORM 实体（可参考 `bigint.transformer.ts`、`id.util.ts`）；
2. `modules/<name>/<name>.service.ts`：业务逻辑，分页用 `clampPage/clampLimit` 归一化；
3. `modules/<name>/<name>.controller.ts`：`@Controller('api/<name>')` + 公开端点标 `@Public()` + 写端点挂 `AdminGuard`；
4. `modules/<name>/<name>.module.ts`：`TypeOrmModule.forFeature([Entity])` 并注册进 `app.module.ts`（实体同步登记 entities 数组）；
5. 前端在 `src/api/<name>.ts` 用 `get/post/patch/del` 封装同名签名，经 `src/api/index.ts` 再导出。

> 结构变更需生成迁移：`cd server && pnpm migration:generate && pnpm migration:run`（`data-source.ts` 提供连接配置）。

## 6. 前端 api 模块编写惯例

`src/api/` 下每个资源文件的结构高度一致，新增模块时照抄惯例即可通过 review：

1. **导入三件套**：从 `./client` 导入需要的谓词函数（`get/post/patch/del`），从 `@/types` 导入领域类型，必要时从 `./examples` 复用 `PaginatedResponse`（它是全站分页响应的规范类型，即便该模块数据来自后端也复用同一形状）。
2. **函数即端点**：一个函数对应一个端点，函数名即动宾短语（`getTopics`、`getTopicBySlug`、`createTopic`），参数用可选对象展开为 query，路径参数经 `encodeURIComponent` 包裹。
3. **只声明不实现**：模块内不出现业务逻辑、不缓存、不弹提示；缓存语义属于 `api/examples.ts` 的特例（内容本地化），一般后端资源模块保持"薄封装"。
4. **经桶导出**：新模块在 `src/api/index.ts` 再导出，页面统一从 `@/api` 引入，便于未来调整文件组织而不动调用方。
5. **类型先行**：响应类型与 `src/types/**` 的实体保持同构；不便进全局类型文件的场景（如分页包装、分组结构）在模块内就近声明并导出（如 `categories.ts` 的 `CategoryGroup/GroupedCategoriesResponse`）。

对照 `src/api/topics.ts`（43 行）可以五分钟掌握全部惯例——它是所有模块里最短的一个，却完整覆盖了 CRUD 五个端点的标准写法。

## 7. 分页与列表数据约定

全站列表数据遵循同一套分页契约，前后端两侧的实现互为镜像：

**响应形状**：`{ data: T[], pagination: { total, page, limit, totalPages } }`。`total` 是过滤后的总数，`totalPages` 至少为 1（空结果也返回一页），前端据此渲染分页器与"共 N 个"文案。

**参数钳制**：后端 `pagination.util.ts` 把 `page` 钳到 ≥1 的整数、`limit` 钳到 [1, 100]（默认 20），非法输入静默回退而非报错——列表接口"永远给出可用结果"是刻意选择，避免一个越界参数让整页白屏。全量拉取场景（分类目录、静态站点）用放宽上限的 `clampLimit(value, 1000)`。

**前端镜像**：`api/examples.ts` 的本地实现逐条复刻了这些语义——`Math.max(1, limit)`、`Math.ceil(total/limit)`、页码钳制到 `[1, totalPages]`——这是"接口签名向后兼容"承诺的落地细节：调用方无论拿到的是后端响应还是本地响应，边界行为完全一致。

**越界语义**：请求页超出范围时服务端返回空 `data` 但保留正确 `total`；前端 `ExamplesLibraryPage` 通过"筛选变化即重置 `page=1`"的 watcher 顺序约定（见 02 篇 §2.2）保证用户几乎不会触达该状态。

## 8. 兼容性与演进策略

接口层面的历史包袱处理，项目沉淀了三条可复用的策略：

**策略一：签名兼容，实现替换**。示例数据从 PostgreSQL 迁到本地 JSON 是一次伤筋动骨的实现替换，但 `getExamples/getExampleById` 的函数签名、分页响应结构、404 异常语义原样保留， eleven 个页面消费方零改动。这说明该项目的数据访问层设计成功地隔离了"数据在哪"与"数据长什么样"两件事，日后若需反向迁移（内容重新入库）或接入 CMS，同样只需替换 `api/examples.ts` 内部实现。

**策略二：旧路径重定向，而非断链**。接口与路由的每一次迁移都伴随 redirect 或保留端点：路由层有九条兼容重定向，后端保留了已无人调用的 examples CRUD。代价是代码库存在"死代码"，收益是外部书签、搜索引擎收录、用户肌肉记忆全部无损。清理死代码应当是一个显式的、带着消费方审计的任务（见 01 篇 §3.4），而不是顺手行为。

**策略三：双通道过渡**。认证的 Bearer/cookie 双通道是典型的灰度手法：新前端优先 Bearer，检测不到时回退 cookie。任何"传输凭证方式升级""响应包裹结构调整"类的改动，都可以借鉴这种"新通道先行、旧通道兜底、观察期后收口"的三步节奏。

## 0. 本篇定位与统计口径

本篇把根 `package.json`（前端）与 `server/package.json`（后端）的全部直接依赖逐个过一遍，每条回答四个问题：它被谁用、为什么选它、换掉它要付什么代价、升级它会踩什么坑。《00-项目总览》§3 的技术栈表回答"有什么"，本篇回答"为什么与怎么样"；两者冲突时以本篇的实测为准（本篇基于 2026-10-06 的 package.json 实文）。

统计口径有三条约定。第一，"使用位置"给的是**代表性消费点**而非穷举——像 `dayjs` 这类散布全站的工具只列入口级位置；第二，"替代方案"评估的是**当年做选型时真实存在的对手**，不做上帝视角的翻案；第三，`^` 语义意味着实际安装版本可能高于声明值，本文版本号全部抄自 package.json 声明，锁定版本以 `pnpm-lock.yaml` 为准（未逐条核对实际解析版本，`⚠️ 待确认`）。

读依赖表之前先建立一个总体判断：这个项目的依赖结构是"**前端重、后端轻、两侧都不虚胖**"。前端 32 个运行时依赖里约半数服务于"Canvas 九库 + 动效四板块 + 编辑器高亮"这些内容板块的硬需求；后端 22 个运行时依赖是标准的 NestJS 全家桶及其配套（express/reflect-metadata/rxjs/class-validator/class-transformer）加四个领域特需（ali-oss/mysql2/nanoid/dotenv）。真正的冗余集中在两处——前端为已拆分板块保留的图表库残余，以及后端冻结模块挂着的特需依赖——第 7 节健康度评估会分别点名。

## 2. 前端重点依赖逐段展开

### 2.1 Vue 生态（vue / vue-router / pinia / @vueuse / @vue/compiler-sfc / xiaoye-ui）

Vue 生态四件套的选型几乎没有悬念，真正值得记录的是三个使用纪律。第一，**Pinia 被刻意限制在 2 个 store**（exampleStore、authStore）：全局状态只收"跨页面共享且需要响应式"的两样东西——示例目录与认证会话，页面级筛选状态一律走 URL query（ADR 的"URL 即状态"，《01-系统架构》§5 模式四）。这使 store 不是状态垃圾场而是精心圈养的会话中枢。第二，**@vueuse/core 是本项目"隐形的基础设施"**：300ms 防抖（watchDebounced）、localStorage 响应式（useStorage）、剪贴板（useClipboard）都出自它，而这些恰恰是最容易写出自研 bug 的原语；项目在 `src/utils/debounce.ts` 另有一份自研防抖（带单测），两者并存说明选型纪律是"组合式函数场景用 @vueuse，纯函数场景自研可测"。第三，**@vue/compiler-sfc 与 vue 严格同版本**（都声明 ^3.5.x）：浏览器内 SFC 运行时（`sfcRuntime.ts`）编译产物直接跑在同页面的 vue runtime 上，两者版本错位会出现编译产物引用不存在的内部 API——升级 vue 时这是必须成对检查的依赖对，manualChunks 也把 compiler-sfc 与 esbuild 单独拆成 `sfc-compiler` chunk 隔离加载时机（`vite.config.ts` 63-70 行）。xiaoye-ui 作为团队自有库被 `optimizeDeps.exclude` 保持源码形态（`vite.config.ts` 146 行），避免预构建版本漂移——这是"自己的库自己编译"的明确表态。

### 2.2 Monaco 双件套与 Shiki 的分工

编辑器链路是两条技术路线的并轨：**Monaco 管编辑，Shiki 管展示**。Monaco（monaco-editor + @guolao/vue-monaco-editor）只在 SourcePane 进入编辑态时挂载（`MonacoCodeEditor.vue` 仅编辑态渲染），配合 `monaco-vendor` 独立 chunk，"打开详情页只读"永远不下载 Monaco 的数百 KB（《10-性能设计》§3.2 样板一）；封装层 @guolao 的价值是把 Monaco 的 AMD loader、worker 配置、生命周期销毁这些臭名昭著的脏活包成 Vue 组件。Shiki 则反着来：只读高亮必须**廉价且处处可用**，所以走 `highlighter.ts` 的单例 + 14 种语言内联注册 + 2 主题的极简配置（ADR-5），它比 Monaco 轻两个数量级但精度足够。两者的分界线是"可编辑性"而非"语言支持"。升级风险上，Shiki v1 到 v3 的 API 已发生结构性变化（createHighlighter 转向 bundle 函数族），当前锁 ^1.0.0 是务实选择，升级等于重写 `highlighter.ts`，应单独立项；Monaco 的月度发版风格则要求 @guolao 封装层确认兼容后再动。

### 2.3 可视化四件套：拆分战略的"活化石"

echarts / echarts-gl / vue-echarts / @antv/g2plot 是三个已拆分姊妹项目留下的残余依赖：图表内容主体已迁往 html5-dataviz，本项目仅剩 SFC 运行时演示与个别页面还在引用（`src/utils/sfc-modules.ts` 的可用模块表、`echarts-setup.ts` 的按需初始化）。项目没有急于卸载它们，而是用两道机制把影响锁死：manualChunks 三级拆分（echarts-gl-vendor / echarts-stat-vendor / echarts-vendor）保证"不进首屏"，`echarts-setup.ts` 的文件头注释记录了从"main.ts 全量导入（~1.1MB 进入口）"改为"路由级加载"的优化史（《10-性能设计》§3.2）。健康度视角（第 7 节）：这组依赖处于"低频使用、中额体积、低风险"的灰色地带，清理收益主要是安装体积与认知负担，而非运行时性能；若 SFC 演示对图表的需求可以收敛，卸载 @antv/g2plot 是最安全的第一刀。

### 2.4 Canvas 九库与动画族：内容板块的硬成本

九个 Canvas 库加三个动画族（GSAP/animejs/animate.css）合计 13 个依赖，全部服务于具体的演示内容——这是"内容型站点"依赖结构的典型样态：依赖数量由**内容清单**而非技术架构决定。项目为此付出的工程代价集中在构建治理：19 组 manualChunks 里约 10 组在为它们划界，注释里"每个示例只引入自己的库"一句就是这套拆包的设计总纲（`vite.config.ts` 108 行）。其中 gsap 的治理成本最高——`resolve.dedupe` + optimizeDeps 全列插件入口是双保险，注释记录的事故（MotionPathPlugin 跨实例污染抛 "Indexed property setter"）说明这类"一个库被拆成多个物理 chunk"的策略与"库内全局单例"的假设天然冲突，未来给 pixi/fabric 等库新增插件子路径时也应预防同类问题。升级风险上最需要盯的是 pixi.js v8 的异步初始化与 fabric v7 的 ESM 化——两者都曾以破坏性重构著称，升级时应只动一个库并全量回归对应板块演示。

## 5. 后端重点依赖展开：Nest 系与 TypeORM 的组合逻辑

后端选型的核心判断只有一个：**用 NestJS 的"约定密度"换团队规模的"纪律密度"**。一人维护的后端最容易退化成"一个 routes 文件里塞全部逻辑"，Nest 的模块四件套（controller/service/entity/module）+ 全局管道 + 全局守卫把结构约定自动化了——本项目的 controllers 高度一致（`@Controller('api/<name>')` + `@Public()` 显式放行 + 写端点 AdminGuard），正是框架约定的红利（《03-接口设计》§2 的三个"统一"）。TypeORM 的选择则与 Nest 生态绑定（@nestjs/typeorm 官方集成），它的QueryBuilder 参数化满足了注入防护基线（《08-安全与权限设计》§4），迁移体系支撑了 11 个结构演进节点（《04-数据模型》§4.3）；代价是 0.3.x 的 API 面较大且部分行为（如 `save` 的级联语义）需要经验，团队以"实体三惯例"（《04-数据模型》§4.3 末段）对冲。认证栈（passport + passport-jwt + @nestjs/jwt）在 2026 年看略显繁琐——JWT 中间件手写不过百行——但它换来的是"宽容模式守卫、策略可替换"的弹性，`jwt.strategy.ts` 的 Bearer 优先/cookie 兜底双提取器（《08-安全与权限设计》§2.1）就是站在 passport 抽象上实现的。整体升级策略建议：Nest 系 10.x 全家保持同一节奏升到 v11（单次集中迁移优于逐包漂移），TypeORM 与 pg 在迁移测试（up/down 幂等）护航下跟进。

## 6. 后端无消费方模块关联依赖（单列清单）

《13-技术债务》第 2 条的消费方审计结论是：`examples`、`chart-examples`、`visual-demos`（列表端点）、`knowledge`（7 子模块）、`oss`、`run` 六处后端资产当前没有前端消费方。它们拖住的特需依赖如下，**在这些模块去留决策落地前，以下依赖不应单独升级也不应卸载**（捆绑纪律）：

| 依赖 | 服务模块 | 模块状态 | 处置建议 |
|------|---------|---------|---------|
| ali-oss + @types/ali-oss | knowledge 域配套 oss 模块（`/api/knowledge/oss`） | 前端、三姊妹项目与 `/admin` 静态页均无引用（2026-10-06 复核） | 随 knowledge 域去留一并决策；保留期间跟随安全通告 |
| mysql2 | run 模块 MySQL 查询通道 | devtools 调用方在现源码找不到（2026-10-06 复核 devtools/dataviz/games 与 `/admin` 均无 `/api/run` 调用，`⚠️ 待确认` 仅剩未开源分支） | run 通道 fail-closed 守卫在，保留成本低；若确认弃用连依赖一起删 |
| nanoid | `common/utils/id.util.ts`（generateId） | **活跃**（auth 的 refresh token id、captcha 均用） | 不在本清单删除范围，列出仅为澄清：它是公共工具而非冻结模块专属 |

需要澄清：examples/chart-examples/visual-demos/knowledge 四个模块本身**没有**引入额外依赖（复用 Nest 系全家桶），所以"冻结模块的依赖成本"实际上只有 ali-oss 与 mysql2 两项——这也是为什么第 7 节把它们标记为"低危冗余"而非"健康问题"。

## 7. 依赖健康度评估

**总体评级：B+（健康，有三处可预期的清理项与两处高危关注点）。** 分项如下。

**前端运行时（A-）**：32 项依赖无一冗余于首屏——manualChunks 与按需加载把体量责任精确分摊到消费板块，这是同体量项目里少见的纪律。扣分项一：@antv/g2plot 与 echarts-gl 的"活化石"属性（§2.3），属于战略性遗留而非技术失误；扣分项二：puppeteer/playwright 并存与 pg/@types/d3-geo 等 devDependencies 沉积（《13-技术债务》第 8 条），建议随专项一清理，预计可减 200MB 级安装体积（`⚠️ 待确认` 实测值）。

**后端运行时（B）**：Nest 系 + TypeORM 的组合对当前规模略重但约定收益真实存在；ali-oss/mysql2 是唯一"功能面大于消费面"的依赖对（§6），处置捆绑在模块去留决策上。真正需要盯的升级风险集中在两处——**TypeORM 0.3.x 的下一个大版本**（迁移体系若有破坏性变更，11 个迁移的可重放性需要重新验证）与 **Shiki v1 锁定**（安全通告若停止覆盖 v1 线，被迫升级时 highlighter.ts 要重写，建议提前立项）。bcryptjs v3 属于纯 JS 实现的小众版本线，注意与 @types/bcryptjs ^3.0.0 的配套。

**版本纪律（A）**：全项目仅 3 处精确锁版（dayjs、vuedraggable、以及 echarts-stat 相关拆包规则隐含的稳定性假设），其余全部 `^`——这与"pnpm-lock.yaml 冻结 + CI --frozen-lockfile"的组合是合理的双层结构：日常靠锁文件保证可重现，升级靠显式改 package.json 走评审。唯一建议补充的机制是 **pnpm outdated 的季度例行化**（或 Renovate 类工具），因为当前依赖面（尤其 Canvas 九库）的升级窗口完全依赖人工记忆，而 gsap 事故注释证明这个项目的依赖升级从来不"顺手"。

**一条总建议**：本项目依赖表的复杂度主要来自"内容清单驱动依赖"这一领域事实，任何"减依赖"的冲动都应先问"对应的演示内容是否还保留"——依赖是内容的影子，清理影子之前先清理本体。

# 00 项目总览

> 项目：xyMall ｜ 版本：v1.0 ｜ 生成日期：2026-10-05 ｜ 依据：源码分析

## 1. 项目定位与目标用户

xyMall 是一个**前后端分离的全品类电商系统**（对标京东购物范式），仓库内含四个可独立构建的子项目：一个 Spring Boot 3 多模块后端（`xy-mall/`）与三个前端应用——PC 响应式商城（`xy-mall-web/`）、Element Plus 管理后台（`xy-mall-admin/`）、Vant 4 移动端 H5（`xy-mall-h5/`）。

根据 `xy-mall/AGENTS.md` 的定位描述，该系统是**单实例部署的教学/演示级高完成度商城**：一台服务器 + MySQL 8 + Redis（可选，Redis 挂掉自动降级纯 DB 路径，不阻断交易）。它刻意覆盖了电商领域的完整业务面——商品/SKU、购物车、订单状态机、四层优惠（券/满减/PLUS/积分）、支付（模拟支付、余额、支付宝沙箱）、秒杀（Redis Lua 预扣 + DB 权威扣减）、拼团、预售、售后退款、库存流水、RBAC 权限、操作审计、站内 IM 客服——并在关键链路上按大厂标准实现生产化能力（条件更新防超卖、幂等、延迟双删、对账纠偏、限流、分布式锁、可观测性）。因此它同时适合两类读者：

- **学习者/面试者**：把每一个业务模块当作"小而完整"的参考实现来读，代码内有大量中文注释解释"为什么这样做"；
- **接手维护者**：可直接部署运行，按第 06 篇的步骤本地起服务后，前后端均能开发调试。

服务对象角色分为三类：**消费者**（商城 Web / H5 端的用户，可注册登录、浏览下单）、**运营/管理员**（管理后台的用户，管理商品、订单、营销与用户）、**客服**（后台 IM 控制台的使用者，通过 WebSocket 与消费者实时会话）。

从项目规模看，这是一套"麻雀虽小、五脏俱全"的系统：后端 `xy-mall-server` 含 30 个业务模块、50 余个 Controller，MySQL 侧由 Flyway `V1~V8` 迁移脚本定义了 40 张表（覆盖商品、订单、营销、秒杀、拼团、售后、IM 等完整业务面），配套 32 个单元/集成测试（7 个测试类，含 framework-core 的 CsvUtilTest）、`xy-mall/scripts/load-seckill.py` 秒杀压测脚本与前端 e2e GUI 冒烟脚本。仓库 `mall/docs/` 目录还保留了完整的演进档案：`HANDOVER.md` 记录了十轮迭代交接，`BIG-TECH-READINESS-ASSESSMENT.md` 是对照大厂标准逐项打分的生产化自评，`MICROSERVICE-SHARDING-PLAN.md` 则是"未来若要拆微服务"的评估底稿（只评估、未实施）。这些档案与源码互相印证，是理解"代码为什么长这样"的第一手线索。

选择"电商"作为业务载体并非偶然：电商域天然覆盖了后端工程的大多数经典难题——库存并发正确性（超卖）、支付一致性（幂等与补偿）、营销规则的叠加计算（优惠分摊）、流量脉冲（秒杀）、缓存一致性（商品详情高读低写），且每个难题都有肉眼可判的对错标准（订单金额对不对、库存会不会为负）。把它做成一个可运行、可压测、可观测的小型系统，比抽象地讲概念更能暴露设计取舍。

对这张表做一点阅读上的展开。**交易主线**（上半部分从用户账户到物流售后的连续各行）串起了一个消费者从注册到售后的完整购物旅程：注册即领券赠余额的"新人礼包"把新用户第一时间导入营销体系；商品中心以三级分类、品牌与 SKU 规格组织货品，搜索/联想/热卖榜/"看完又看"四种发现路径分别服务"目标明确、模糊意图、从众心理、兴趣延伸"四类购物心智；结算时四层优惠按"券→满减→积分→PLUS"固定顺序叠加计算，支付后订单进入状态机管理，超时未付由三重兜底关单并回补库存；确认收货后还能评价、追评、收藏，形成交易闭环。这条主线的端到端代码走读见《05-核心流程》。

**支撑线**（认证安全、消息与 IM、管理后台、基础设施）则回答"一个商城要稳稳跑起来还需要什么"：JWT + 会话版本 + token 黑名单构成可随时吊销的登录态；站内消息覆盖订单、物流、系统三类事件通知；管理后台用 RBAC 把"谁能干什么"收敛为权限码并辅以操作审计留痕；基础设施层把限流、分布式锁、幂等、对账、可观测这些生产化能力做成 framework 通用件，业务模块按需取用而不必各自造轮子。各功能域的表结构与字段语义见《04-数据模型》，三端页面与组件组织见《02-页面设计》。

### 3.2 前端三端（均为 Vue 3 + Vite + TypeScript）

| 维度 | xy-mall-web（商城 PC） | xy-mall-admin（管理后台） | xy-mall-h5（移动端） |
| --- | --- | --- | --- |
| UI 库 | Element Plus 2.9（响应式适配手机） | Element Plus 2.9 | Vant 4.9 |
| 图表/富文本 | - | ECharts 6、wangEditor 5 | - |
| 状态管理 | Pinia 2.3 | Pinia 2.3 | Pinia 3.0 |
| 路由 | Vue Router 4.5（history 模式） | 同左 | 同左 |
| HTTP | axios 1.7（`/api` baseURL + 拦截器） | 同左（blob 导出放宽超时） | 同左 |
| dev 端口 | 5177 | 5176 | 5188 |
| 特殊依赖 | element-china-area-data（省市区） | - | - |
| 包管理 | pnpm 11（`packageManager` 字段锁定） | pnpm 11 | pnpm 11 |

选型理由：三端共用同一套 Vue 3 技术心智与同一种 axios 封装（`src/api/request.ts` 几乎同构），后端统一响应 `R{code,message,data}` 使三端能以同一种方式解包数据；Element Plus 承担后台密集的表格/表单场景，Vant 4 则为移动端提供触摸友好的组件；ECharts 按需注册（`DashboardView.vue` 中 `echarts.use([...])`）控制产物体积。

几处值得注意的**选型权衡**：其一，后端坚持"单体内多模块"而非微服务——30 个模块同进程部署，换来极低的运维成本与事务内一致性（下单扣库存、核销券、扣积分在同一事务内完成），代价是登录失败计数、幂等键、sys_config 进程缓存等进程内状态无法直接横向扩容，《MICROSERVICE-SHARDING-PLAN.md》评估过拆分路径但刻意不实施；其二，Redis 被定位为"可丢的增强层"而非硬依赖——缓存、预扣库存、延迟队列、分布式锁全部 try/catch 降级，最坏情况系统退化为纯 DB 路径，牺牲吞吐但不牺牲正确性，这使教学环境"不装 Redis 也能跑通全部业务"；其三，框架层五个 Maven 模块刻意做到可独立复用（framework-core 甚至零 Spring Web 依赖），为将来抽取公共脚手架留了口子；其四，金额一律以"分"（INT）存储、schema 变更只走 Flyway，分别消除了浮点精度与"库结构漂移"两类高频事故源。

## 5. 快速上手（最短路径）

以下命令即可在本机把后端与 PC 商城跑起来（完整细节见第 06 篇）：

```bash
# 1. 初始化数据库（需本地 MySQL，root/root1234 供集成测试使用）
mysql -u root -p < xy-mall/server/src/main/resources/db/migration/V1__init.sql
#    —— 或直接空库启动：Flyway baseline-on-migrate=true 会自动建表

# 2. 注入必填 JWT 密钥（无默认值，缺失时启动直接失败）
cd xy-mall
export XY_MALL_JWT_SECRET=$(openssl rand -base64 36)
export MYSQL_USERNAME=root MYSQL_PASSWORD=你的密码

# 3. 编译并启动后端（必须以 xy-mall/ 为工作目录，/upload/** 静态映射是相对路径）
mvn clean install -DskipTests
mvn -pl server spring-boot:run
#    健康检查：curl http://localhost:8081/api/health
#    接口文档：http://localhost:8081/doc.html

# 4. 启动 PC 商城（另开终端）
cd xy-mall-web && pnpm install && ./node_modules/.bin/vite   # http://localhost:5177

# 5. 启动管理后台 / H5
cd xy-mall-admin && ./node_modules/.bin/vite                 # http://localhost:5176
cd xy-mall-h5   && ./node_modules/.bin/vite                  # http://localhost:5188
```

关键开发约定（源自 `xy-mall/README.md` 与 `AGENTS.md`，全文档集将反复引用）：

- 后端包结构 `com.xiaoye.mall.server.modules.{module}.{layer}`，复杂入参聚合为 `XxxContext`，VO 转换按 README/AGENTS 约定"交给 MapStruct converter"——但当前源码零 converter 实现，实际用 `BeanUtils.copyProperties`（见《17-依赖全景》§5.2）；
- 业务失败统一抛 `BizException`，由 `framework-web` 的 `GlobalExceptionHandler` 转为 `R{code,message}`；
- 用户端接口 `/api/**`，管理端 `/api/admin/**`；请求头 `Authorization: Bearer <token>`；
- 金额一律以"分"（INT）存储；schema 变更只走 Flyway，严禁手改库结构；
- 所有 Redis 访问点必须 try/catch 降级，不允许 Redis 故障阻断交易；
- 本地验证码旁路：以 `--mall.captcha.allow-bypass=true` 启动后验证码填 `0000`。

另有两个新手高频踩坑点提前提示：一是前端 dev 需以 `./node_modules/.bin/vite` 直跑（pnpm 11 的构建脚本拦截所致），且前端默认仅监听 IPv6，请用 `localhost` 而非 `127.0.0.1` 访问；二是后端必须以 `xy-mall/` 为工作目录启动，否则 `/upload/**` 相对路径映射丢失、商品图全部 404。生产环境变量清单与 Docker/nginx 编排见第 06 篇。

## 6. 文档集阅读指引

本套文档共 7 篇，建议按 00 → 01 → 04 → 03 → 02 → 05 → 06 的顺序阅读：先建立全局认知（00/01），再理解数据底座（04）与对外契约（03），随后深入三端页面（02）与端到端业务流程（05），最后按 06 部署运行。每篇均引用真实源码相对路径（相对 `mall/` 目录），读者可随时对照源码验证。

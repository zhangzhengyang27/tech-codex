## 1. 项目定位

`my-ts-axios`（npm 包名 `ts-axios-zhangzhengyang`，`package.json` 中 `version: 0.2.1`）是一个**使用 TypeScript 从零实现的 axios 学习版 HTTP 客户端库**。它不是对官方 axios 源码的复制，而是围绕 axios 的公开行为规范，逐个特性独立重写了一套可构建、可测试、可发布的完整库工程：浏览器端基于 `XMLHttpRequest`，Node.js 端基于原生 `http` / `https` 模块，另附一个基于全局 `fetch` 的适配器用于 Service Worker / Cloudflare Workers 等无 XHR、无 Node http 的运行时。

项目的核心学习价值在于：它把 axios 这类"看似简单"的 HTTP 库背后真正的工程难点完整展开——

- **同构（isomorphic）设计**：一份源码同时服务浏览器与 Node.js，通过适配器抽象隔离环境差异，通过 Rollup 的别名 + shim 技巧让浏览器产物"零 external"；
- **Promise 链编排**：拦截器、`dispatchRequest`、响应转换全部挂在一条动态拼装的 Promise 链上，这是理解 axios 行为（如"请求拦截器后注册先执行"、"响应拦截器 rejected 能捕获适配器错误"）的关键；
- **类型体系设计**：`AxiosRequestConfig` / `AxiosResponse` / `AxiosError` / `AxiosStatic` 等接口构成对外契约，兼有"混合对象"（既是函数又挂载属性/方法）的类型表达；
- **测试与质量工程**：Jest + jsdom + jasmine-ajax 兼容层、90% 行覆盖率门槛、ESLint flat config、husky + lint-staged + commitlint 的提交链路、发布前 dist 产物冒烟检查。

按 README 的描述与源码验证，这是一个**库项目**而非应用项目：没有页面路由与业务界面，`examples/` 下的 Vite + Vue 3 多页面站点仅作为库的手工验证沙盒。因此本套文档的重心是**模块设计与请求链路**，而非页面设计。

### 1.2 特性覆盖的判定口径

## 3. 技术栈速览

| 维度 | 选型 | 出处 |
| --- | --- | --- |
| 语言 | TypeScript 5.9（`strict: true`，target ES2017，lib ES2019 + DOM） | `tsconfig.json` |
| 构建产物 | Rollup 4：CJS（Node 主入口）+ ESM + UMD（浏览器）+ `tsc` 独立输出类型声明 | `rollup.config.mjs`、`package.json` scripts |
| Node 端运行时依赖 | 仅 Node 内置模块 `http`/`https`/`zlib`/`stream`；`form-data` 为 optionalDependencies（未安装时降级） | `src/core/adapters/http.ts`、`package.json` |
| 示例工程 | Vite 8 + Vue 3.5 + Express 4（mock API 内嵌进 Vite dev server） | `examples/vite.config.ts`、`examples/plugins/mock-api.ts` |
| 测试 | Jest 29 + ts-jest + jsdom 环境 + jasmine-ajax（带自建兼容引导层） | `package.json` jest 段、`test/boot.ts` |
| 代码质量 | ESLint 9 flat config + typescript-eslint + prettier；husky + lint-staged；commitlint + commitizen | `eslint.config.mjs`、`package.json` |
| Node 版本 | 库运行时要求 `>=14.0.0`（engines）；开发/构建建议 Node 20+（Vite 8 要求） | `package.json`、`README.md` |

值得注意的一个工程选型：**浏览器构建把 Node 内置模块与 `form-data` 通过 `@rollup/plugin-alias` 全部映射到 `src/shims/node-builtins.ts` 占位实现**（调用即抛错），因此 UMD 产物没有任何 external 依赖，`<script>` 标签可直接引入；而 http 适配器代码随包携带，只在真正被调用时才会触发占位实现抛错。这解决了"一份源码、双端产物、浏览器包零依赖"的矛盾。

构建工具的双轨分工也体现了同样的思路：**Rollup 只负责库产物**（cjs/esm/umd 三形态 + sourcemap + 类型声明），因为它对多格式输出、tree-shaking 与 external 控制更精细；**Vite 只负责示例工程**（dev server、HMR、多页面扫描），因为它对开发体验更友好。两者通过 `examples/vite.config.ts` 里的 `resolve.alias`（把 `stream/http/https/url/zlib` 指到 `examples/shared/node-stub.ts`）衔接，使示例页可以直接 `import` 库源码入口而不必先跑库构建。测试则选择 Jest + jsdom 而非 Vitest，主要动因是 `jasmine-ajax` 这套成熟的 XHR mock 生态仍挂在 jasmine 全局上（`test/boot.ts` 为此写了专门的兼容引导层）。

对上表再做一轮"按职责归组"的文字导览，便于建立空间感。`src/` 下的代码分为四组：**入口组**（`index.ts`、`axios.ts`、`defaults.ts`）回答"库长什么样、默认行为是什么"；**链路组**（`core/` 除 adapters 外）回答"一次请求如何被编排与加工"；**端点组**（`core/adapters/`）回答"具体怎么把字节发出去、怎么把字节收回来"；**支撑组**（`helpers/`、`cancel/`、`types/`、`shims/`）提供无状态的纯函数、取消原语、类型契约与构建占位。组间依赖是单向的：端点组与链路组都依赖支撑组，入口组依赖链路组，任何反向依赖都不存在。

`test/` 的组织与 `src/` 形成镜像：根级 spec 按"用户可见行为"划分（实例、默认值、转换、取消、进度……），`test/core/` 按链路内部构件划分（拦截器、settle、适配器解析、三个适配器各自的专项），`test/helpers/` 按纯函数划分。这意味着回归定位有一条清晰的路径——先从根级 spec 复现行为异常，再下钻到 core/helpers 的单元级 spec 找根因。`examples/` 则是"人工验收层"：`routes/*.js` 的八组 Express 路由与各示例页一一对应，`npm run dev` 一次启动即可覆盖拦截器、取消、上传、跨域（8088 的 server2）等真实浏览器场景。

`scripts/smoke-dist.cjs` 是发布前的最后一道闸：它不以"构建成功"为满足，而是把三种产物逐一加载、逐项断言导出面（含 `VERSION` 与 `package.json` 的同步），从消费端视角验证包的可用性。这个"以消费者身份检查自己"的习惯贯穿了整个工程——rollup 配置里关于 CJS `exports: 'default'` 的长注释、`util.ts` 里关于 extend 沿原型链遍历的修复，都是同一思路的体现。

```bash
npm run test:watch    # 监听模式
npm run test:prod     # lint + 无缓存测试（发布前组合）

# 4) 跑示例：启动 Vite dev server（http://localhost:5173），
#    mock-api 插件会同时挂载 Express mock 路由并拉起 8088 跨域服务器
npm run dev

# 5) 示例构建（多页面输出到 examples/__dist__/）
npm run examples:build

# 6) 代码检查 / 监听构建
npm run lint          # eslint .
npm run start         # rollup -w 监听模式

node scripts/smoke-dist.cjs
```

消费构建产物（`package.json` 的 `exports` 映射）：Node `require` 走 `dist/node/axios.cjs`，打包器 `import` 走 `dist/index.esm.js`，浏览器 `<script>` 走 `dist/browser/axios.umd.js`（全局 `window.axios`），类型统一读 `dist/types/index.d.ts`。

几条命令背后的流水线值得展开说明，以免"只会敲不会改"。`npm run build` 实际是三段式的：npm 的 `prebuild` 生命周期钩子先执行 `rimraf dist` 保证产物目录干净；随后 `build:types` 用 `tsc --declaration --emitDeclarationOnly` 只产出声明文件到 `dist/types/`；最后 `rollup -c` 按 `rollup.config.mjs` 的两个构建任务产出 cjs/esm/umd 三种 JS 产物。`npm test` 固定带 `--coverage`，且 `package.json` 的 `coverageThreshold` 设了硬门槛（branches 80% / functions 85% / lines 90% / statements 90%），覆盖率不达标即判定失败——这是该仓库"测试即门禁"的核心机制。`npm run dev` 启动的不只是静态服务器：`examples/plugins/mock-api.ts` 会在 Vite 的 `configureServer` 钩子里挂载一组 Express 中间件（含 `XSRF-TOKEN-D` cookie 种植、`connect-multiparty` 文件上传解析与八组示例路由），并尝试拉起 8088 端口的跨域服务器 `examples/server2.js`，所以示例页里连跨域、cookie、上传这类需要真实服务端配合的场景都能离线跑通。

首次上手建议的验证顺序：先 `npm test` 确认环境健康（全绿且覆盖率达标），再 `npm run build` 确认构建链路可用，最后 `npm run dev` 打开 `http://localhost:5173` 在示例页里实际发起一次请求。三步都通过，即可开始阅读源码。

## 6. 源码阅读路线建议

若目标是通读实现，推荐按"由外向内、先编排后端点"的顺序：第一步读 `src/axios.ts`（80 行以内，看清混合对象如何拼装、静态 API 如何挂载）；第二步读 `src/core/Axios.ts` 的 `request` 方法（Promise 链编排是全库的灵魂）；第三步读 `src/core/dispatchRequest.ts` 与 `src/core/mergeConfig.ts`（配置合并与加工的三步曲）；第四步按需深入 `src/core/adapters/` 三兄弟（xhr 最短、适合先读；http 最长、涵盖重定向/代理/流）；最后把 `src/helpers/` 当作工具书按需查阅。`src/types/index.ts` 建议在第二步之前先速览一遍，带着类型读实现事半功倍。

# 07-模块详解
> 项目：my-ts-axios ｜ 版本：v1.1 ｜ 生成日期：2026-10-06 ｜ 依据：源码分析

## 1. 本篇定位与阅读方法

第 02 篇《模块设计》回答的是"模块怎么划分、为什么这样划分"；本篇则下沉一层，对 `src/` 下的每一个源文件做逐文件深读：文件职责、导出清单、逐函数机制走读与文件间依赖关系。阅读本篇时建议同时打开对应源文件，行号引用以当前版本（`package.json` version 0.2.1）为准，重构后请以函数名为锚重新定位。

全篇按第 00 篇确立的四组划分组织：**入口组**（`src/index.ts`、`src/axios.ts`、`src/defaults.ts`）、**编排组**（`src/core/` 除 `adapters/` 外）、**端点组**（`src/core/adapters/` 三适配器）、**支撑组**（`src/helpers/`、`src/cancel/`、`src/shims/`、`src/types/`）。每个文件给出三样东西：一句话职责、导出清单表格、逐函数机制说明。行数统计来自当前源码，用于建立"该文件有多重"的直觉。

一个贯穿全篇的阅读原则：这个库的函数几乎都是"无状态纯函数 + 一个大闭包（适配器）"的形态，理解任何一个文件只需要回答三个问题——输入是什么、输出是什么、修改了谁的引用。第 04 篇已经证明"全程只有一个 config 对象被就地修改"，本篇会在每个函数的走读中反复标注"这里改的是引用还是副本"，这是排查该库行为问题时最重要的单一线索。

## 2. 入口组

### 2.1 src/index.ts（5 行）

库的唯一出口。`import axios from './axios'` 后执行两条导出：`export * from './types'`（全部公共类型，编译后消失，不占运行时体积）与 `export default axios`（默认导出的混合对象实例）。导出设计的三条原则已在第 03 篇第 1 节展开，此处不重复。该文件没有任何逻辑，存在的意义是给 `rollup.config.mjs` 两个构建任务提供统一的 `input: 'src/index.ts'`。

### 2.2 src/axios.ts（55 行）

**职责**：实例工厂与静态 API 挂载——把 `Axios` 类"拍平"为既是函数、又带全套方法与静态成员的混合对象。

**导出清单**：

| 导出 | 形态 | 说明 |
| --- | --- | --- |
| `default` | `axios`（`AxiosStatic`） | `createInstance(defaults)` 的产物 + 12 项静态挂载 |

**逐成员走读**：

- `VERSION`（第 15 行）：字符串常量 `'0.2.1'`，手工维护，与 `package.json` 的同步由 `scripts/smoke-dist.cjs` 在发布前断言（见《06-部署运行》第 4 节）。
- `createInstance(config)`（第 18~23 行）：三步——`new Axios(config)` 得到完整实例 `context`；`Axios.prototype.request.bind(context)` 得到绑定 `this` 的裸函数（这就是"函数即实例"的函数本体）；`extend(instance, context)` 把实例属性与原型方法全部拷到函数上。注意绑定的**只是 `request`**：实例上的 `get`/`post` 等方法是靠 `extend` 拷贝上去的属性，而非绑定方法。这意味着拷贝的方法内部 `this` 指向——`extend` 拷的是函数引用，调用 `axios.get(...)` 时 `this` 是 `axios` 函数对象本身，而该对象上存在 `defaults` 与 `interceptors`（都是拷来的），所以 `request` 内部 `this.defaults` 依然能取到正确值。这是一个依赖"拷贝的完整性"的隐式契约：若未来 `extend` 漏拷了 `defaults`，所有方法族都会静默失效。
- `axios.create`（第 28~30 行）：`createInstance(mergeConfig(defaults, config))`——**总是以全局 defaults 为底**再叠加传入配置，因此 `axios.create()` 不传参也拿到完整默认配置的独立实例。
- 第 31~53 行：依次挂载 `CancelToken`、`Cancel`、`isCancel`、`all`（即 `Promise.all`）、`spread`（数组展开回调）、`Axios`（类本身）、`AxiosHeaders`、`VERSION`、`HttpStatusCode`、`mergeConfig`、`getAdapter`、`isAxiosError`、`CanceledError`、`AxiosError`、`toFormData`、`formToJSON`。这 16 项与 `smoke-dist.cjs` 的导出断言一一对应。

**依赖**：`./types`（仅类型）、`./core/Axios`、`./helpers/util`（`extend`）、`./defaults`、`./core/mergeConfig`、`./cancel/CancelToken`、`./cancel/Cancel`、`./core/AxiosHeaders`、`./cancel/CanceledError`、`./core/getAdapter`、`./helpers/HttpStatusCode`、`./helpers/error`、`./helpers/formData`。它是全库唯一同时接触这些模块的文件，处于依赖图的顶端。

### 2.3 src/defaults.ts（89 行）

**职责**：库级默认配置与默认转换器。模块级单例，所有未显式 `create` 的请求共享它；`axios.create` 通过 `mergeConfig` 深合并产出副本而非引用，因此修改实例 defaults 不会污染全局单例（`deepMergeStrat` 的深拷贝语义，见第 02 篇第 2 节）。

**导出清单**：

| 导出 | 形态 | 说明 |
| --- | --- | --- |
| `default` | `defaults`（`AxiosRequestConfig`） | 含 `transformRequest`/`transformResponse` 两个默认转换器数组与 `transitional` 三项 |
| （模块内私有） | `getContentType(headers)` | 大小写不敏感读取 Content-Type |

**逐函数走读**：

- `getContentType`（第 8~14 行）：`Object.keys(headers).find(k => k.toLowerCase() === 'content-type')`。存在的原因是默认转换器必须在**拍平前的分层 headers** 上判断 multipart 意图，此时键名大小写不受控（用户可能写 `content-type` 小写顶层键）。
- `transformRequest[0]`（第 37~55 行）：默认请求转换器。判定序：①`getContentType(headers)` 含 `multipart/form-data` 且 data 是普通对象且存在可用的 FormData 构造器 → `toFormData(data, new EnvFormData())` 直接转 FormData（注意第二个参数传的是**新建的实例**而非 undefined，构造器优先取 `defaults.env.FormData`，回退全局 `FormData`）；②否则走 `processHeaders(headers, data)` 补 `Content-Type: application/json;charset=utf-8`（仅普通对象且缺失时）再调 `helpers/data.ts` 的 `transformRequest`（流直通 → 普通对象 JSON 序列化 → 其余原样）。
- `transformResponse[0]`（第 58~62 行）：薄包装，直接转调 `helpers/data.ts` 的 `transformResponse`（字符串尝试 `JSON.parse`，失败静默保持字符串）。
- `validateStatus`（第 64~66 行）：`status >= 200 && status < 300`，被 `core/settle.ts` 消费。
- 第 76~87 行：为 7 个 HTTP 方法补默认 headers——`delete/get/head/options` 空对象，`post/put/patch` 预置 `Content-Type: application/x-www-form-urlencoded`。这个"保守默认值 + 转换器按需补 JSON 头"的两段式设计在《02-模块设计》第 10 节有完整论证。

**依赖**：`./types`、`./helpers/headers`（`processHeaders`）、`./helpers/data`、`./helpers/formData`（`toFormData`）、`./helpers/util`（`isPlainObject`）。

## 3. 编排组（src/core/）

### 3.1 src/core/Axios.ts（198 行）

**职责**：请求编排。`request` 方法拼装动态 Promise 链，方法族是 `request` 的参数折算糖衣。

**导出清单**：

| 导出 | 形态 | 说明 |
| --- | --- | --- |
| `default` | `class Axios` | 数据属性仅 `defaults`、`interceptors`；方法 `request`、`get`、`delete`、`head`、`options`、`post`、`put`、`patch`、`postForm`、`putForm`、`patchForm`、`getUri`，私有 `_requestMethodWithoutData`、`_requestMethodWithData`、`_requestForm` |
| （模块内） | `interface Interceptors`、`interface PromiseChain<T>` | 链环形状 |

**逐函数走读**：

- `constructor(initConfig)`（第 29~35 行）：存储 defaults，创建请求/响应两个 `InterceptorManager`。每个实例的拦截器容器相互独立，这是 `axios.create` 隔离语义的物理基础。
- `request(url, config?)`（第 41~105 行）：五个阶段。①**双签名归一**（第 42~49 行）：字符串走"合并 config 并写 url"，否则 config 直接取第一个参数——注意 `config.url = url` 是对调用方对象的就地写入。②**合并归一**（第 51~52 行）：`mergeConfig(this.defaults, config)` 产出无原型对象，随后 `config.method.toLowerCase()`（这里没有判空，依赖 defaults 保证 `method: 'get'` 存在——若用户以 `mergeConfig` 产物之外的方式传入无 method 的配置会抛 TypeError）。③**拦截器收集**（第 54~68 行）：请求拦截器先过 `runWhen(config)` 过滤（返回 false 连链都不进），响应拦截器原样收集。④**链构造**（第 70~97 行）：`syncRequest = requestInterceptors.every(i => i.options?.synchronous === true)`——全真时走同步快路径（倒序逐个调用 `resolved(conf)`，最后一次 `Promise.resolve(conf).then(dispatchRequest)`）；否则构造 `chain` 数组（中坚 `dispatchRequest` 居中，请求拦截器逐个 `unshift`），`while (chain.length)` 依次 `promise.then(resolved, rejected)`。请求链环的 `rejected` 位是 `undefined`，因此请求拦截器阶段的错误会跳过 `dispatchRequest` 直达响应拦截器的 rejected 钩子。⑤**响应拦截器追加**（第 100~102 行）：按注册序 `then`，返回最终 promise。
- 方法族（第 107~145 行）：`get/delete/head/options` 委托 `_requestMethodWithoutData`，`post/put/patch` 委托 `_requestMethodWithData`，二者都是 `Object.assign(config || {}, {...})` 折算后转调 `request`——**会就地改写调用方传入的 config 对象**（写 method/url/data）。`postForm/putForm/patchForm` 委托 `_requestForm`。
- `_requestForm`（第 182~196 行）：在折算之外做两件事：`Object.assign({ 'Content-Type': 'multipart/form-data' }, config && config.headers)` 前置 multipart 头（用户显式传入的同名头优先级更高）；`toFormData(data, undefined, config && config.formSerializer)` 预转换请求体。注意第二参传 `undefined`，`helpers/formData.ts` 内部回退 `new FormData()` 全局构造器——**没有走 `defaults.env.FormData`**，与默认转换器（`defaults.ts` 第 42~44 行优先取 `env.FormData`）的路径不一致，已在第 03 篇标注 ⚠️ 待确认是否有意。
- `getUri`（第 147~150 行）：只执行 `mergeConfig` + `transformURL`，不触发 data/headers 加工，用于预览最终地址。
- 第 37~39 行被注释掉的第一版 `request`（直接 `return dispatchRequest(config)`）是刻意保留的演进线索。

**依赖**：`../types`、`./dispatchRequest`（含具名 `transformURL`）、`./InterceptorManager`、`./mergeConfig`、`../helpers/formData`。

### 3.2 src/core/dispatchRequest.ts（58 行）

**职责**：Promise 链的中心环节——取消预检、配置三连加工、调适配器、响应转换。它是"横切关注点收敛到链路中层"这一架构决策（第 01 篇第 2 节）的物化。

**导出清单**：

| 导出 | 形态 | 说明 |
| --- | --- | --- |
| `default` | `dispatchRequest(config)` | 链中坚环节 |
| `processConfig` | 具名导出 | url/data/headers 三连加工 |
| `transformURL` | 具名导出 | baseURL 拼接 + params 序列化（被 `Axios.getUri` 复用） |
| （模块内私有） | `transformResponseData`、`throwIfCancellationRequested` | 响应转换与取消预检 |

**逐函数走读**：

- `dispatchRequest(config)`（第 8~22 行）：先 `throwIfCancellationRequested(config)`（第 50~58 行：`cancelToken.throwIfRequested()` 同步抛 `Cancel` 实例；`signal.aborted` 则抛 `new CanceledError('canceled', config)`——覆盖"取消发生在发请求之前"的时序），再 `processConfig(config)`，最后 `getAdapter(config)(config).then(成功转换, 失败转换)`。失败分支对携带 `response` 的错误先 `transformResponseData(e.response)` 再继续 reject，保证 4xx/5xx 时 `error.response.data` 已解析。
- `processConfig`（第 24~28 行）：顺序刻意为 url → data → headers。url 必须最先（默认转换器不关心 url）；data 在 headers 拍平**之前**转换，因为默认请求转换器要按原始分层 headers 判断 Content-Type 并补写头；headers 拍平必须最后。
- `transformURL`（第 30~37 行）：`baseURL` 存在且（`allowAbsoluteUrls === undefined || allowAbsoluteUrls`）且 url 非绝对地址时 `combineURL`，随后 `buildURL` 序列化 params。
- `transformResponseData`（第 39~48 行）：`transitional.forcedJSONParsing === false` 时传给 `transform` 的转换器数组为 `undefined`，`core/transform.ts` 对空 fns 原样返回——这是 `transitional` 三项中第二个被消费的项（第一个是 `clarifyTimeoutError`）。

**依赖**：`../types`、`./getAdapter`、`../helpers/url`、`../helpers/headers`、`./transform`、`../cancel/CanceledError`。

### 3.3 src/core/mergeConfig.ts（73 行）

**职责**：策略模式的字段级配置合并。机制与策略表已在《02-模块设计》第 2 节完整展开，此处只补本篇视角的三点实现细节：其一，策略表用 `Object.create(null)` 创建（第 4 行），查找 `strats[key] || defaultStrat` 时不会误命中 `Object.prototype` 上的键；其二，结果对象同样无原型（第 53 行），因此调用方无法通过配置对象的 `constructor` 等原型键做任何原型链把戏；其三，第二轮遍历（第 60~64 行）只合并 `config2` 中**值为 undefined** 的键——注释强调"已显式给出（含 falsy 值）的字段不再重复合并"，即 `config2.timeout = 0` 会阻止 defaults 的 `timeout` 参与，但 `fromVal2Strat` 下 `config2.data = null` 会以 `null` 为准而非继承，两类策略对 falsy 的语义都是"显式即生效"。

**导出清单**：`default mergeConfig(config1, config2?)`；模块内私有 `defaultStrat`、`fromVal2Strat`、`deepMergeStrat` 与三个策略键数组。

**依赖**：`../types`、`../helpers/util`（`deepMerge`、`isPlainObject`）。

### 3.4 src/core/InterceptorManager.ts（47 行）

**职责**：拦截器的有序存取容器（稀疏数组）。`use` push 后返回下标；`eject` 把槽位置 `null` 而非 splice（id 永不错位）；`forEach` 跳过空槽。`synchronous`/`runWhen` 选项接口 `InterceptorOptions<T>` 定义在此文件（第 3~6 行）并导出，但未进入 `src/types/index.ts` 的公共类型面（第 03 篇差异清单第 3.4 节）。泛型参数 T 使同一个类同时服务请求侧（`AxiosRequestConfig`）与响应侧（`AxiosResponse`）。

**导出清单**：`default class InterceptorManager<T>`（方法 `use`/`forEach`/`eject`）；具名 `interface InterceptorOptions<T>`。

**依赖**：仅 `../types`（`ResolvedFn`/`RejectedFn`）。

### 3.5 src/core/transform.ts（18 行）

全库最小的模块。`transform(data, headers, fns?)`：fns 为空原样返回；单函数包装成数组；`forEach` 串行执行 `data = fn(data, headers)`。它是"转换器按数组顺序串行管道执行"语义的唯一实现点，`dispatchRequest` 的请求侧与响应侧共用。无状态、无依赖（除类型），18 行里没有任何环境探测。

### 3.6 src/core/getAdapter.ts（53 行）

**职责**：适配器注册表与解析。

**逐函数走读**：模块顶部的 `knownAdapters`（第 10~14 行）在**模块加载时**求值：`xhr: typeof XMLHttpRequest !== 'undefined' ? xhrAdapter : null`——浏览器/jsdom 里注册 xhr 适配器函数，其他环境注册 `null`；`http` 无条件注册 httpAdapter（其内部对 Node 内置模块的依赖由 rollup 的 external/shim 机制处理）；`fetch` 无条件注册 fetchAdapter（运行时无全局 fetch 时以 `ERR_NOT_SUPPORT` 拒绝，`fetch.ts` 第 46~55 行）。`getAdapter(config)`（第 16~53 行）把 `config.adapter` 归一为数组：null → 默认 `['xhr', 'http', 'fetch']`；字符串/函数/其他非数组 → 单元素数组；随后线性扫描——函数直接返回，字符串查表，查不到（或表值为 null）静默尝试下一个；全部失败抛普通 `Error`（注意**不是 AxiosError**），错误消息里用 `knownAdapters[k]` 过滤后列出当前环境真正可用的适配器名。

**依赖**：`../types`、`./adapters/xhr`、`./adapters/http`、`./adapters/fetch`。它是三适配器唯一的汇聚点。

### 3.7 src/core/settle.ts（33 行）

三适配器共享的最终裁判，机制见第 02 篇第 5 节。本篇补充判定式的精确语义：`if (!response.status || !validateStatus || validateStatus(response.status))`——三个放行条件分别是"状态码为 0"（xhr 跨域失败等场景不会走到这里，因为 xhr 适配器已把 status 0 静默忽略；此条件主要服务 Node 端自定义 transport 的边缘形态）、"未配置 validateStatus"（任意状态码都算成功）、"validateStatus 放行"。拒绝分支的错误码以 500 为界（`>= 500 → ERR_BAD_RESPONSE`，否则 `ERR_BAD_REQUEST`），并通过 `createError` 的第 6 参把数值状态写入 `error.status`。`test/core/settle.spec.ts` 的注释记录了一次历史回归——"http 适配器此前反转"过 4xx/5xx 错误码，这正是把判定收敛到一份实现的价值：修一处即修三端。

**依赖**：`../types`、`../helpers/error`。

### 3.8 src/core/AxiosHeaders.ts（139 行）

**职责**：以规范化（小写）键名存储首部的容器类。机制与官方方法子集的取舍见《02-模块设计》第 7 节。本篇补充实现要点：类本体就是存储容器（索引签名 `[key: string]: any`），没有独立的内部 Map；构造器三分支（普通对象逐键 `set`、AxiosHeaders 实例先 `toJSON` 再逐键、原始报文按 `\n` 行切首个 `:`）；`set` 的 `rewrite` 参数默认 true，值为 `undefined/null` 等价删除；`has` 是"存在即真"（`typeof !== 'undefined'`），空字符串也算有；`merge` 对已有数组值做 concat 而非覆盖；`normalize` 把所有非小写键重写为小写。静态方法 `from`（等价 new）与 `concat`（多源合并）。请求链路中它只在两个位置出现：`flattenHeaders` 兼容用户传入实例（先 `toJSON`），以及用户在拦截器里可以选择用它操作 headers；库内部流转仍以普通对象为主。

**依赖**：无 import（自包含，连 `util.ts` 的 `isPlainObject` 都在文件内重新实现了一份）——这是一个刻意的解耦决定，使 `AxiosHeaders` 可以被单独抽取使用。

## 4. 端点组（src/core/adapters/）

三个适配器共用签名 `(config: AxiosRequestConfig) => AxiosPromise`，共同出口是 `settle`。横切对照表（取消/超时/进度/headers/认证/XSRF/特有配置）见《02-模块设计》第 5 节，本篇按文件展开内部函数。

### 4.1 src/core/adapters/xhr.ts（205 行）

**职责**：浏览器/jsdom 的 XMLHttpRequest 适配器，全库最短的适配器，适合作为"适配器如何写"的范本。

**结构**：单个导出函数包裹一个大 Promise，executor 内先解构 config（第 12~27 行，`headers = {}`、`data = null`、`method = 'get'` 均有默认值兜底），随后按固定装配序执行 `request.open → configureRequest → addEvents → processHeaders → processCancel → processSignal → request.send(data)`（第 41~49 行）。

**逐函数走读**：

导出 `getProxyForUrl(targetUrl)`。内部三段：`getEnv`（大小写兼容读 `process.env`，无 process 时安全返回 undefined）；`splitHostPort`（IPv6 方括号/多冒号兼容的 NO_PROXY 条目拆分）；`isNoProxy`（`*` 全排除、`.后缀` 匹配、精确主机、带端口条目）。主函数解析目标 URL，按协议取 `https_proxy || all_proxy` 或 `http_proxy || all_proxy`，解析代理 URL 得到 `AxiosProxyConfig`（host 剥 IPv6 方括号、port 缺省按协议 443/80、auth 从 URL 的 username/password decode）。注释明确"对齐官方 axios（proxy-from-env）的行为"。**依赖**：`../types`。

### 6.10 src/helpers/HttpStatusCode.ts（70 行)

状态码常量表（1xx~5xx 全量 63 项），`default` 导出对象、具名导出同值类型。唯一的"纯数据"文件，被挂到 `axios.HttpStatusCode`。

## 7. 构建支撑（src/shims/node-builtins.ts，15 行）

`unavailable(module)` 工厂产出"调用即抛中文错误"的占位函数，具名导出 `request`（http）、`createGunzip`/`createInflate`/`createBrotliDecompress`（zlib）、`Readable`/`Transform`（stream），default 导出（form-data）。浏览器构建时 `rollup.config.mjs` 的 alias 把这五个模块名全部映射到本文件，UMD 产物因此零 external。维护契约：http 适配器若引入新的内置 API，本文件必须同步补齐导出，否则浏览器构建要到**运行时**才暴露缺符号（第 01 篇 3.7 节）。jest 覆盖率统计显式排除本目录（占位代码无可测分支）。

## 8. 类型组（src/types/index.ts，307 行）

全库唯一"只有声明没有实现"的文件。文件顶部用 `import type` 引入五个实现模块的类型（AxiosHeaders、CanceledError、getAdapter、mergeConfig、HttpStatusCode、isAxiosError/AxiosErrorClass）——全部是 type-only，保证类型面无运行时代价。结构分七段：`Method` 与 `AxiosRequestConfig`（第 8~86 行，末尾宽松索引签名）、辅助配置接口（ProgressEvent/ParamsSerializer/FormSerializer/Transitional/ProxyConfig，第 90~147 行）、响应三件套（AxiosResponse/AxiosPromise/AxiosAdapter，第 150~163 行）、错误 interface（第 166~173 行）、实例四层类型（Axios/AxiosInstance/AxiosClassStatic/AxiosStatic，第 175~250 行）、拦截器三类型（第 252~268 行）、取消七类型与凭据（第 270~307 行）。取舍细节（interface/class 双轨、AxiosPromise 空接口、四层静态类型拆分、宽松索引签名的代价）见《02-模块设计》第 11 节；全字段速查表见《15-接口全量参考》。

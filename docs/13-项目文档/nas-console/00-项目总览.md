# 00 项目总览
> 项目：nas-console ｜ 版本：v1.0 ｜ 生成日期：2026-10-05 ｜ 依据：源码分析


## 1. 项目定位

nas-console 是一个部署在家庭 NAS 上的**服务管理台**，对外呈现为「个人主页 + 运维控制台」的双重形态。它把站长散落在 NAS 与 VPS 上的十几个自托管服务（后台管理系统、云盘、商城、文档站、数据库中间件等）收拢到一个入口，解决三个核心痛点：

1. **状态不可见**：服务是否在线、延迟多少、TLS 证书还剩几天，过去只能逐个打开确认。nas-console 通过服务端探针 7×24 巡检，把所有服务的健康状态收敛到一个面板；
2. **访问数据分散**：全站访问统计托管在 Umami，但原生面板无法与自有服务清单结合。nas-console 在管理区内置访问分析页，浏览器直连 Umami API 拉取 PV/UV/来源/设备等维度数据；
3. **个人主页缺乏真实感**：首页不是静态简历，而是实时读取探针脱敏快照的「活的门口」——访客无需登录即可看到精选项目的真实在线状态、30/45 天可用率条与项目档案（故事/亮点/时间线/截图）。

项目单体仓库内同时包含**前端**（`src/`，React + Vite + TypeScript）与**后端探针**（`server/`，Node.js 原生 http + SQLite），构建产物 `dist/` 由探针进程同端口静态托管，最终以**单容器单端口（5950）**形态部署。整个项目面向的用户只有两类：

- **站长（唯一管理员）**：登录 `/console/*` 管理区，使用总览、访问分析、服务管理、设置四个页面，并负责维护探针侧的 `config.json`；
- **访客（任何人）**：访问公开首页 `/`、项目详情 `/projects/:id` 与全屏状态页 `/status`，只读脱敏快照，不接触任何内部信息。

## 3. 技术栈速览

| 层 | 技术 | 版本 | 选型理由（源码/注释可证） |
|---|---|---|---|
| 前端框架 | React | ^19.1.1 | antd v6 原生支持 React 19；`vite.config.ts` 以 `resolve.dedupe` 统一 React 实例避免双份 |
| UI 组件库 | antd | ^6.0.0 | React 19 原生兼容；`ConfigProvider` 统一主色 `#4c6ef5` 与深浅色算法（`src/App.tsx`） |
| 路由 | react-router-dom | ^7.14.2 | `BrowserRouter` + 嵌套路由实现公开/管理区分区与 `RequireAuth` 登录门 |
| 图表 | recharts（内置封装） | ^3.0.0 | 项目自带 `src/charts/` 封装层（Area/Bar/Line/Donut/Sparkline），配色为本地扁平色板，Sparkline 为手写 SVG 零依赖 |
| 图标 | react-icons / @ant-design/icons | ^5.4.0 | `ServiceIcon` 以 14 个 lu 系列图标映射服务类型 |
| 工具库 | dayjs | ^1.11.11 | 日期格式化与按天聚合分桶，前后端同构使用 |
| 构建 | Vite + TypeScript | ^5.4.0 / 5.5.2 strict | `npm run build = tsc --noEmit -p tsconfig.build.json && vite build`，类型检查前置于打包 |
| 后端运行时 | Node.js（原生 `node:http`） | 22（bookworm-slim） | **零 Web 框架**：路由/静态托管/JSON 解析/SSE 全部手写（`server/src/server.ts`），部署面最小、同源免 CORS |
| 存储 | better-sqlite3 | ^11.10.0 | 同步 API 对单实例个人规模「绰绰有余」（`server/src/store.ts` 注释）；WAL 模式；bookworm(glibc) 可命中预编译二进制，免现场编译 |
| 容器 | Docker / docker compose | — | 两个 Dockerfile（全量构建 vs NAS 轻量构建）+ 两份 compose（桥接 vs host 网络）覆盖两种部署路径 |
| 鉴权 | 自研 HMAC 签名 Cookie | — | 「无需额外依赖」（README 0.3.1 节）：`node:crypto` HMAC-SHA256 + HttpOnly Cookie，会话密钥落盘 `data/session-secret` |

技术栈整体取向非常明确：**能不引依赖就不引**。前端没有 Redux/Zustand/React Query（用 Context + localStorage + `useSyncExternalStore` 模块级 store 替代），后端没有 Express/Fastify/Koa（原生 http 手写路由表），存储没有 MySQL/Redis（SQLite 单文件 WAL）。这与其「单 NAS、单用户、个人规模」的定位完全匹配，也让整个系统在 NAS 这种低功耗设备上足够轻。

选型理由值得逐项展开说明。其一，antd v6 而非 Mantine：从 `src/theme/feedback.tsx` 的注释（「必须挂在 antd `<App>` 内：把上下文实例绑定给静态桥，等价原 notifications/modals 包」）与 `src/components/Field.tsx` 的注释（「替代 Mantine 风格输入组件的 label 属性」）可以还原出一段演进史——项目早期使用 Mantine，后来整体迁移到 antd v6，迁移层被刻意保留成很薄的兼容桥，新代码可以直接使用 antd 原生 API。其二，recharts v3 而非 ECharts：图表需求只有面积/柱/折线/环形/迷你走势五种，`src/charts/` 以不到千行封装出统一主题（`chart-theme.ts` 的扁平色板 + 深浅色轴/提示框配色），其中 Sparkline 完全手写 SVG（`sparkline-path.ts` 实现 Fritsch–Carlson 单调三次插值，避免平滑过冲），零运行时依赖。其三，better-sqlite3 而无 ORM：同步 API 在单进程低并发下反而省去异步开销，建表/迁移直接写在 `Store` 构造函数里，个人规模完全够用且排障直观（一个 `probe.db` 文件即全部状态）。

## 5. 快速上手

本地开发按「先后端、后前端」顺序（摘自 README「开发」节，均为源码可验证的命令）：

```bash
# 1) 前端依赖
npm install

# 2) 构建并启动探针（dev 约定端口 5951，vite 已配置 /api、/sse 代理）
cd server && npm install && npm run build
PORT=5951 node dist/index.js
cd ..

# 3) 前端开发服务器（探针在线则页面进入探针模式，否则自动降级浏览器巡检）
npm run dev        # http://127.0.0.1:5173

# 4) 生产构建（tsc 类型检查 + vite 打包 → dist/）
npm run build
```

首次启动前需要准备探针配置：`cp config.example.json config.json`（样例含空的 `services`/`alerts`/`auth` 三段）。若需启用登录鉴权，用 `cd server && read -s P && node scripts/hash-password.mjs admin "$P"` 生成 `auth` 段（输出 JSON 直接合并进 config.json 后重启），避免密码进入 shell 历史。启动后打开控制台，前端会把「内置+自定义」清单经 `PUT /api/services` upsert 给探针并落盘 `config.json`；手工调优探测参数（tcp 端口、关键词、tlsSkipVerify、intervalSec）则直接编辑 config.json 后重启进程。

Docker 部署有两条路径（详见 `06-部署运行.md`）：全量构建用 `Dockerfile` + `compose.yml`（构建上下文须为上级 PROJECT 目录）；NAS 常规更新用 `Dockerfile.nas` + `docker-compose.nas.yml`（本机构建好 dist 上传后 `docker compose up -d --build`，host 网络直连本机 1Panel）。

上手过程中有三个容易踩的点需要提前知晓。第一，**dev 与生产的端口约定不同**：本地探针跑在 5951（与 vite 代理对齐），容器内固定 5950（与 frp 链路对齐），混淆会导致页面进入浏览器降级模式而非探针模式。第二，**前端身份文案是编译期常量**：`src/config/identity.ts` 头注释明确「⚠️ 以下为占位示例，部署前替换为真实信息」，且「修改=改代码发版」——它不走任何运行时配置。第三，**健康检查的模式在页面加载时锁定**：`use-health.ts` 只在挂载时探测一次探针可达性，运行期不自动切换，因此先启动页面再启动探针时，需要刷新页面才能进入探针模式。

## 5.1 模块协作鸟瞰

从模块协作的角度看，前端九个 `src/api/` 文件恰好构成一张「外部系统 → 客户端」的映射表：探针（`probe.ts`）、登录会话（`auth.ts`）、Umami（`umami.ts`）、1Panel 代理（`host.ts`）、公开快照（`public-status.ts`），外加三块自有领域逻辑——浏览器降级探测（`health.ts`）、历史存储（`health-history.ts`）与两个组合 Hook（`use-health.ts`、`use-probe-sync.ts`）。后端十个 `server/src/` 文件则按「入口 → 门卫 → 领域」排布：`index.ts` 装配、`server.ts` 分发、`auth.ts` 守门，`probe.ts`/`store.ts`/`sse.ts`/`alerts.ts` 四件套构成监控领域核，`config.ts` 与 `1panel.ts` 分别对内管理配置、对外对接面板。两侧仅通过 HTTP/SSE 一条通道通信，没有共享代码包，契约靠 `server/src/types.ts` 与前端 `src/api/*.ts` 里的镜像类型手工对齐（这一取舍及其风险在 04 篇第 6 节讨论）。

## 5.2 阅读路径建议

不同角色的接手者可以按需取用本套文档：想快速跑起来，读本节加 `06-部署运行.md` 第 2–3 节即可；想改页面或加功能，按 `02-页面设计.md` 的组件树定位文件，再查 `03-接口设计.md` 确认数据从哪来；想理解「为什么这样设计」，`01-系统架构.md` 第 5 节的五个架构决策与 `docs/v03-probe-design.md` 原始设计稿对照阅读最有价值；排查数据问题时，`04-数据模型.md` 的三处持久化与 `05-核心流程.md` 的五张时序/流程图给出了从浏览器事件到 SQLite 落盘的完整链路。

## 6. 版本演进脉络（来自 docs/ 与代码内注释）

项目经历了三个可辨识的阶段，理解它有助于读懂代码中的「双模式」设计：

- **v0.2 纯前端**：健康检查跑在浏览器里（no-cors fetch），历史靠 localStorage 逐日积累，只在页面打开时工作——没有 7×24 巡检、没有告警（`docs/v03-probe-design.md` 第 1 节）。这条路径今天仍完整保留为**降级模式**（`src/api/health.ts`、`src/api/health-history.ts`），而非被删除——这是本项目「演进不拆迁」风格的最好例证。
- **v0.3 探针 sidecar**：常驻探针接管巡检/历史/告警/SSE，并**替代**原 nginx 静态容器，实现单容器单端口（`docs/v03-probe-design.md` 第 2 节的「关键决策」）。设计稿同时圈定了边界（第 9 节「不做的」）：不做多实例高可用、不接 Prometheus/InfluxDB、不做分布式探针——这些「不做」同样是架构信息。
- **0.3.1+ 门户化**：加入单用户登录、公开脱敏快照与白名单分组、`/status` 状态页、TLS 证书监控、1Panel 集成与项目档案上传（README 各节与 `server/src/server.ts` 对应端点）。项目从「给自己用的监控台」长成了「对外的个人门户 + 对内的运维台」双形态，公开面与鉴权面的字段级隔离（01 篇决策五）正是这一阶段的核心命题。

从 git 历史之外的证据也能看到这种演进的痕迹：`package.json` 描述写的是「服务健康监控 + Umami 访问分析」，而实际功能已远超此描述；`Dockerfile` 顶部关于 react-ui 的注释对应更早的工具链形态（当前 `package.json` 已无 react-ui 依赖，该 COPY 步骤疑似历史遗留，见 06 篇）；`charts/`、`theme/` 里的若干「替代原 XX 包」注释记录了 Mantine → antd 的整体迁移。接手者阅读代码时遇到「为什么有两套做同样事情的路径」，几乎都可以在「v0.2 保留为降级」或「迁移兼容层」这两个答案中找到解释。

最后说明本篇与其余六篇的分工。本篇回答「这是什么、用什么造的、东西在哪」；`01-系统架构.md` 回答「整体如何组织、为什么这样组织」；`02-页面设计.md` 与 `03-接口设计.md` 分别是前端与接口的详细图纸；`04-数据模型.md` 盘点所有持久化与运行时数据的形状；`05-核心流程.md` 把最重要的五条端到端链路拆成时序图与分步说明；`06-部署运行.md` 覆盖从本地开发到两种容器部署与日常运维的全部操作面。七篇之间通过篇名互相引用，结论一律标注源码依据，无法从源码确认的事项统一以「⚠️ 待确认」标记而非臆测。

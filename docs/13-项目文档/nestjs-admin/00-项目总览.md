# 00 项目总览

> 项目：nestjs-admin ｜ 版本：v1.0 ｜ 生成日期：2026-10-06 ｜ 依据：源码分析

## 1. 项目定位与目标用户

nestjs-admin 是一套**前后端完全分离的企业级后台管理系统**（若依/RuoYi 风格），由两个子项目组成，同仓维护于 `nestjs-admin/` 目录下：

- **`nestjs-microservice-app/`**：基于 NestJS 12 的微服务后端。它不是一个单体应用，而是一个 pnpm workspace 多包仓库（monorepo），内含 1 个 HTTP 网关（gateway）、2 个 gRPC 业务微服务（user、system）、1 个健康检查聚合服务（health）、1 个共享契约包（proto-pkg）和 1 个新服务脚手架（template）。服务注册与发现基于 Consul（本仓库 `bin/consul` 附带 v2.0.3 darwin-arm64 二进制），服务间通信走 gRPC（可选 TLS，自签证书随 `proto-pkg/certs` 分发）。
- **`vue-admin/`**：基于 **vue-pure-admin 完整版**深度改造的 Vue 3 管理端（`package.json` 中 `name` 仍为 `vue-element-plus-admin`，`version 7.0.0`）。登录、动态菜单、按钮权限码、用户/角色/菜单/部门/字典/日志/通知等管理页面全部对接真实网关接口，模板中的 mock 体系与假数据已被清除。

按 `nestjs-microservice-app/HANDOFF.md` 的定位，这是一个"教学/演示级、但按生产思路实现"的项目：它完整落地了微服务拆分、注册中心容灾、双 token 鉴权、CASL 动态权限、操作/登录/系统三级日志、对象存储上传、Docker 化部署等工程实践，并且**已实际部署到公网**（HANDOFF §4.5：`https://admin-vue.zhangzhengyang.com`，NAS 多容器 + frp + VPS nginx 反代链路）。

目标用户与适用场景：

| 读者 | 用途 |
|---|---|
| 后端接手者 | 理解微服务拓扑、Consul 发现、gRPC 契约、权限模型，独立维护/扩展服务 |
| 前端接手者 | 理解 pure-admin 改造点、动态路由与权限码映射、API 封装约定 |
| 运维/部署者 | 本地一键起栈（dev-start.sh）、Docker 编排、生产反代链路 |
| 教学/二开者 | 以 `template/` 为脚手架复制出新微服务，套用既有注册/发现/鉴权模式 |

演示账号（来自 HANDOFF 与登录页 `vue-admin/src/views/login/index.vue` 中写死的 `TEST_ACCOUNT`）：`p1user / secret123`（主演示账号，已授权全部菜单；且后端 `user/src/app.controller.ts` 中对该账号写死"测试账号不可以修改密码"保护）、`p0user / secret123`、生产管理员 `prodadmin`（HANDOFF §4.5）。

## 1.1 项目由来与演进脉络

从 `nestjs-microservice-app/HANDOFF.md` 记录的里程碑可以还原出这个项目的完整成长史，理解这条演进线索对接手者非常有价值——今天代码里的很多"为什么"都藏在这段历史里。项目最初是一个 NestJS 单体教学工程（user 服务的前身），随后经历了一次大规模依赖升级：NestJS 10 升 12、Prisma 5 升 7、Node 18 升 22/24，同时做了一批 P0 到 P4 级别的安全与质量修复——包括密码从明文改为 argon2 哈希、全局参数校验管道、JWT 认证闭环、统一异常过滤器、strict 类型检查全开、带 traceId 的日志体系，以及 TLS 加密与 CI 流水线。官方 `consul` npm 包在此期间被官方弃用，于是有了 `proto-pkg` 里那个基于 Node 内置 fetch 的 `ConsulHttpClient` 自研薄封装。

之后的功能迭代按里程碑推进：M1 引入 system 微服务与菜单管理全链路，并把动态权限码合并进 CASL 能力体系；M2 加入部门管理、数据字典与操作/登录日志（由网关中间件自动采集）；M3 完成双端 gRPC TLS 实测、Swagger 与容器编排；M5/M6 补齐用户管理完整 CRUD 与个人中心（资料读写、头像上传、改密码、登出、在线用户强退、字典改删）；M7 做了文件上传迁移到 MinIO 对象存储、菜单 iframe/外链支持、在线强退真实化（后又于 2026-09-10 把 Redis 图形验证码整体移除，Redis 依赖随之删除）；M7.5 把"假 refresh"做成真实的双 token 体系；M8/M9 依据前端交接清单补齐了管理员重置密码、改他人头像、日志删除清空、通知消息待办、仪表盘统计、日志多维筛选、偏好设置与密保信息等一批缺口。2026-09-11 是一个密集的缺陷修复日，连续五排排查修复了"7 天免登录实为 24 小时"、"登录日志管理页因取值错误恒为空表"、"系统日志页无菜单入口也无数据源"、"全局菜单搜索弹窗图标渲染成 412×412 撑爆布局"等一批真实缺陷，并把登录/操作日志改造为服务端真分页、路由切换为 history 模式、接入 Umami 访问统计，最终完成公网生产发布。理解这些背景后你会发现：代码里大量防御性注释、try/catch 兜底与"特性化"的限流配置，都是这一路踩坑的沉淀。

## 1.2 一套代码覆盖三套关注点

值得强调的是，这个仓库实际上同时承载了三类读者的关注点，并且刻意让它们互不污染。第一类是**业务功能**：用户/角色/菜单/部门/字典五大管理域与日志/通知/仪表盘三个辅助域，全部走"前端页面 → 网关路由 → gRPC 微服务 → Prisma → PostgreSQL"的标准链路，任何新功能都建议沿用这条路径。第二类是**平台能力**：注册发现、健康检查、鉴权授权、限流、日志采集、异常映射、对象存储，这些能力集中在网关与 proto-pkg 中，业务服务基本不感知——比如 user 服务完全不知道自己会被 CASL 消费，它只负责按 proto 契约应答。第三类是**工程示范**：`template/` 脚手架展示了"如何新增一个微服务"，`vue-admin` 中保留的 pure-admin 演示页展示了"组件怎么用"，二者与业务代码物理隔离（template 不参与生产构建，演示页不接业务接口）。接手者的改动几乎总落在第一类；改第二类时要跑全量单测与全链路冒烟；第三类可以随意删除而不影响业务。

逐行读这张功能表可以发现几个贯穿性的设计事实。第一，所有写操作都是"权限码先行"的：前端按权限码决定按钮显隐，网关按同一个权限码做服务端兜底，而权限码本身是 system 库菜单表里的一条 type=2 记录、经角色授权动态生效——这意味着"加一个按钮"是纯数据操作（插菜单记录加授权），不需要改网关代码。第二，日志是零侵入的：业务代码里没有任何一行"记日志"的调用，操作日志由网关中间件在响应结束后统一采集，登录日志按路径规则采集，系统日志由异常过滤器采集，三者都遵循"尽力而为、失败不影响业务"的旁路原则。第三，跨域聚合只发生在网关：仪表盘的七项统计来自 user、system 两个 gRPC 调用与网关自身的内存会话计数，`dashboard.controller.ts` 负责拼装；两业务服务之间从不互相调用，这让它们的依赖图始终是一棵以网关为根的树，排障时拓扑清晰。第四，功能演进高度依赖 proto 契约的向后兼容：从 M6 到 M9 的每一次加功能，动作序列都是"改 proto → 重生成产物 → 服务端补 RPC → 网关透传 → 前端接线 → seed 补权限码"，这个固定节奏在 03 篇还有详细展开。

### 3.3 工程化

- **包管理**：两端均为 pnpm workspace（根 `pnpm-workspace.yaml`）；后端 `package.json` 用 `pnpm.onlyBuiltDependencies` 显式放行 argon2/swc/esbuild/grpc-tools/prisma 等原生构建包；前端 `preinstall` 钩子强制 `only-allow pnpm`。
- **CI**：`nestjs-microservice-app/.github/workflows/ci.yml` —— 起 Consul 1.21 + Postgres 16 容器，跑 `pnpm -r build`（strict 类型检查）、`prisma migrate deploy`、gateway 单测、health 启动后跑 e2e。
- **部署工件**：后端单镜像 `Dockerfile`（node:22-bookworm-slim，4 服务共用，compose `command` 决定跑谁）与参数化 `Dockerfile.service`（node:24-alpine，`--build-arg SERVICE=`）；`docker-compose.full.yml` 一键编排 consul+postgres+4 服务；前端 `vue-admin/Dockerfile` 与生产反代配置 `admin-vue-deploy/nginx-admin.conf`。

关于技术栈选型还有几点值得展开的"为什么"。微服务通信选 gRPC 而非 HTTP/REST 内部调用，除了性能与强类型契约之外，还有一个很实际的原因：NestJS 的 `@nestjs/microservices` 对 gRPC 提供了一等公民支持——`@GrpcMethod` 装饰器让业务服务的代码形态与 HTTP 控制器几乎一致，迁移成本极低；而 proto 文件天然就是接口文档，`proto-pkg` 把契约、加载工具、Consul 客户端、TLS 证书打包成一个 workspace 内共享包，两端永远引用同一份产物，从机制上杜绝了"接口文档与实现不一致"这一微服务最常见的老大难问题。选 Prisma 7 的新 `prisma-client` generator，是因为项目紧跟 Prisma 7 的驱动适配器架构（`PrismaPg`），这带来两个直接好处：连接串不再写死在 schema 里（由 `prisma.config.ts` 与运行时代码分别注入，便于 CLI 迁移与运行时指向不同环境），且生成物落在本地目录 `src/generated/prisma-client`，模型类型与客户端同仓可见、IDE 跳转友好。前端坚持完整版 pure-admin 而不是精简版或自研脚手架，看重的是它开箱即用的布局体系（三种侧边栏形态、多标签页、全局搜索、设置抽屉）、`PureTableBar` 加 hook 的页面组织模式与成熟的动态路由方案——本项目所有业务页都复用了这套骨架，业务代码只写"数据怎么来、操作怎么发"，交互细节零成本。至于两端都用 pnpm，除了速度与磁盘节省，后端还依赖 workspace 协议（`"@toimc/proto-pkg": "workspace:*"`）实现包内联引用，前端则靠 `preinstall` 钩子把包管理器锁死，避免贡献者混用 npm/yaml 导致锁文件漂移。

## 5. 快速上手

### 5.1 前置条件（来自 HANDOFF §2/§3 与脚本实文）

- Node.js（后端日常 v22.15.0，跑单测需 v24.9+；前端 `engines.node >=22.22.1`）、pnpm 10.x、PostgreSQL（15/16 均可，需建 `user_db`/`system_db` 两库）、Consul 二进制（默认找 `$HOME/work/bin/consul`，可用 `CONSUL_BIN` 覆盖）。
- 数据库初始化：分别在 `user/`、`system/` 目录 `npx prisma migrate deploy`（Prisma 7 经 `prisma.config.ts` 读 `DATABASE_URL`/`SYSTEM_DATABASE_URL`），再 `psql -f prisma/seed.sql` 灌权限码/菜单种子（HANDOFF 陷阱 31：漏 seed 会导致菜单/权限 403）。

### 5.2 启动后端（`dev-start.sh` 已固化全部顺序）

```sh
cd nestjs-microservice-app
bash dev-start.sh
# 脚本动作：导出 DATABASE_URL/SYSTEM_DATABASE_URL/JWT_SECRET/GRPC_TLS 等默认值
# → source dev-secrets.env（MinIO 凭据，可选）
# → [1/6] consul agent -dev ×2（8500/8501，第二个全套端口偏移）
# → [2/6] health :3030 → [3/6] user :40001 → [4/6] system :40010
# → [5/6] 轮询 Consul /v1/health/service?passing=true 等 user/system 转绿
# → [6/6] gateway :3040；日志在 /tmp/svc-*.log 与 /tmp/consul{1,2}.log
```

首次运行前需先构建产物：`pnpm install && pnpm -r build`（脚本执行的是各服务 `dist/main.js`）。

### 5.3 启动前端

```sh
cd vue-admin
pnpm install
pnpm dev        # :5173，vite 把 /api 与 /uploads 反代到 http://localhost:3040
```

浏览器访问 `http://localhost:5173`，登录页已预填 `p1user/secret123`，也可点"一键测试登录"。冒烟验证可跑仓库根 `node smoke_fullchain.js`（HANDOFF §3，注意 signin 限流 10/min，多轮需间隔 60s）。

### 5.4 常用验证命令

- 网关健康：`curl http://127.0.0.1:3040/api`
- gRPC 健康聚合：`curl "http://127.0.0.1:3030/api/v1/health?service=user_grpc"`
- Swagger：浏览器打开 `http://localhost:3040/api/docs`（NODE_ENV=production 时不挂载，可用 `SWAGGER_ENABLED=true` 显式打开）
- 单测：`cd gateway && pnpm test`（Node 24）、`cd system && pnpm test`；e2e：`cd gateway && pnpm run test:e2e`
- 前端门禁：`pnpm typecheck && pnpm build`

## 6. 阅读路线建议

新接手者建议按本文 → `01-系统架构.md`（微服务拓扑与发现机制）→ `03-接口设计.md`（网关路由与鉴权约定）→ `04-数据模型.md`（两库实体）→ `05-核心流程.md`（登录/CRUD/注册发现/健康检查端到端时序）→ `02-页面设计.md`（前端页面与状态）→ `06-部署运行.md`（环境变量与部署链路）的顺序阅读。阅读源码时始终以 `proto-pkg/proto/*.proto` 为接口契约锚点、以各服务 `prisma/schema.prisma` 为数据锚点；`HANDOFF.md` 的 32 条陷阱清单是排障时的第一参考。

补几条实践层面的阅读心法。读网关代码时建议从 `app.module.ts` 入手建立全局观——它集中声明了两个 Consul 实例、限流配额与请求日志中间件，是理解"每个请求会经历什么"的地图；然后按一个具体请求（比如打开用户列表页）沿"中间件 → 守卫 → 控制器 → 客户端服务 → gRPC"的路径走一遍，五分钟就能建立完整的数据流心智模型。读前端代码时则要从 `router/index.ts` 的全局守卫和 `api/routes.ts` 的菜单适配函数开始，因为 pure-admin 的动态路由机制是这套前端最"绕"的部分，理解了"后端菜单如何变成路由与权限码"，其余页面代码都只是这个机制的消费者。阅读过程中遇到任何看似奇怪的设计（比如 refresh 换发后旧 access 立即失效、登录日志把每次写接口的删除也记一条），先查 05 篇的核心流程与本文功能清单里的注释说明——绝大多数"怪异"都是被真实事故教育出来的有意设计，HANDOFF 陷阱清单里几乎每一条都对应一次踩坑实录，贸然"修复"它们往往会把坑重新挖开。

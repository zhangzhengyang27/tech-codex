# 09 测试与质量保障

> 项目：nestjs-admin ｜ 版本：v1.1 ｜ 生成日期：2026-10-06 ｜ 依据：源码分析

## 2. 代表性用例走读（三个最值得学的测试）

### 2.1 竞速与恢复广播（`consul.service.spec.ts`）

这组测试的价值在于它锁定了三个"手工极难验证、回归极伤"的时序行为。其一，`retryGetServiceInfo` 的容灾竞速：consul1 空列表、consul2 命中时，结果必须来自 consul2——测试用 `jest.useFakeTimers()` + `advanceTimersByTimeAsync` 驱动 rxjs 的 timer，这是测 retry/退避逻辑的标准姿势。其二，恢复广播：两个 Consul 各持一条 `nestjs-service` 客户端条目，订阅挂在"落选"条目（consul2）上，consul1 的 `updateGrpcClient` 恢复后断言 consul2 上的订阅者也收到了非空客户端——这正是 `updateGrpcClient` 里 `filter(c => c.serviceName === serviceName)` 全量广播语义的回归锚点，改回"只更新自己"这条测试立刻红。其三，错误卫生：发现失败时构造器内的 5 秒重试链不能产生未处理 Promise 拒绝（Node 会因此崩进程），测试推进 40 秒虚拟时间断言不抛。mock 组织上有个精巧设计：`ConsulHttpClient` 构造函数同步消费"预置健康结果队列"（`mockHealthQueue`），使每个 ConsulService 实例在构造期就拿到各自的发现结果——这是被"构造器内 initClients 立即发起首次发现"的现实逼出来的 mock 形态。

### 2.2 空对象判定（`auth.service.spec.ts`）

`用户不存在时抛出 403 而不是对空对象做校验` 这条用例锁定了 gRPC 边界的一个隐形契约：user 服务 FindOne 未命中返回 `{}` 而非 null，网关必须以 `user.id` 判存在性——若误写成 `if (!user)`，空对象为真值，后续 `argon2.verify(undefined, ...)` 会产生难以理解的错误。同文件的 `gRPC 调用失败时触发客户端重建回调` 锁定自愈机制：构造 `details='No connection established'`、`message='connect ECONNREFUSED'` 的错误（与 `GrpcExceptionInterceptor.checkIfConnectionIssue` 的判定字段精确对齐），断言 `updateGrpcClient` 被以正确服务名调用。注释还提醒了一个测试写法陷阱：必须持有 promisify 包装**前**的原始 jest.fn 引用，否则断言打在包装函数上永远不命中。

### 2.3 日志分页与筛选语义（`system/src/app.controller.spec.ts`）

七条用例完整钉死了日志查询的边界约定：无分页参数时保持历史行为（skip 0/take 100、orderBy id desc）；`page=2&pageSize=5` 换算 `skip=5,take=5` 且返回过滤后总数；`status=1` 映射"成功"（登录日志 `success:true`；操作日志 `statusCode 2xx`）、`status=0` 映射"非成功"（操作日志走 OR 分支：`<200 或 >=300`）、`-1` 不加筛选（proto3 默认值 0 与"未传"区分是 M9 修过的坑）；username 模糊（contains）与时间范围（gte/lte）组合进同一 where。这组测试的存在理由写在 HANDOFF 里：登录日志页曾因同类逻辑缺陷"空表运行了数个里程碑"，此后这类条件组合被认定为高回归风险区。

## 3. 质量门禁体系

门禁分四道，按"提交前必跑 → CI 自动 → 发布前人工"分级：

```mermaid
flowchart LR
    A[本地提交前] --> B["pnpm -r build<br/>(strict tsc 全量类型检查)"]
    B --> C["gateway/system 单测<br/>Node 24.9+ + ESM flag"]
    C --> D[前端 typecheck + build<br/>vue-tsc + eslint 零警告]
    D --> E{CI 触发 push/PR}
    E --> F["服务容器: consul 1.21 + postgres 16"]
    F --> G["pnpm install --frozen-lockfile"]
    G --> H[proto-pkg 构建 + prisma generate]
    H --> I["pnpm -r build"]
    I --> J["prisma migrate deploy"]
    J --> K[网关单测]
    K --> L[起 health 服务]
    L --> M["e2e 4 例 (supertest)"]
    M --> N{发布前}
    N --> O["全链路冒烟 smoke_fullchain.js<br/>ALL GREEN"]
    O --> P["浏览器人工实测<br/>登录/各页/深链接/暗色"]
```

三处细节值得展开。**CI 与本地的差异**：`.github/workflows/ci.yml` 起了 Consul 与 Postgres 服务容器，因此 e2e 能真实装配 AppModule（发现链路会去查 Consul），而本地跑 e2e 前提是 dev-start.sh 的两个 consul dev agent 在线；CI 只对 user 库跑了 migrate deploy（system 库未跑，因 e2e 不触达 system_db）。**前端门禁的严格度**：`vue-admin/package.json` 的 lint 是 `eslint --max-warnings 0`（一个警告都不过）+ prettier 全量检查，typecheck 是 `vue-tsc --noEmit --skipLibCheck`，build 用 8GB heap + rolldown 分包——HANDOFF 各里程碑的验收标准都是"后端 build+单测、前端 typecheck+build"成对出现。**人工验收基线**：全链路冒烟脚本的四步断言（登录/菜单/仪表盘/验证码下线）加浏览器人工过一遍核心页面，是每次发版的固定动作；历史上一轮 M7 冒烟 21 项、M8 冒烟 25 项的一次性脚本（`/tmp/smoke_m7.py`、`smoke_a1a7.py`）已被系统清理，仅存 HANDOFF 记录，其断言思路（按"目标 id 消失"而非数量归零断言日志删除）值得在重建冒烟套件时继承。

## 4. 缺口分析与补测建议

按"回归概率 × 爆炸半径"排序，当前体系有七个明确缺口：

1. **user 服务零测试**（26 个 RPC 无一覆盖）。它是认证数据与全部用户域写路径的落点，`CreateUser` 的事务/角色校验/P2002 映射、`DeleteDept` 的双前置校验都是纯逻辑密集区，参照 `system/src/app.controller.spec.ts` 的 mock-Prisma 模式补齐成本很低，建议最先补 CreateUser/UpdateUserRoles/DeleteDept 三条。
2. **system 服务的通知与字典域无测试**。日志域有 7 条，字典唯一冲突（P2002→"字典编码已存在"）与通知已读（单条/按类全量）同样是条件分支密集区。
3. **网关中间件与异常过滤器无测试**。`request-logging.middleware.ts` 的路径分流规则（signin/signup→登录日志、写方法→操作日志、module 取 URL 前两段）与 `all-exceptions.filter.ts` 的 gRPC→HTTP 映射表都是"改一行影响全站观测"的集中点，且都是纯函数式逻辑，非常适合单测。`GrpcExceptionInterceptor` 的连接失败判定（`No connection established` + `ECONNREFUSED` 双条件）同理。
4. **e2e 不覆盖多 Consul 与多实例拓扑**。竞速逻辑有单测，但"真起两个 consul + 两个 user 实例"的场景只有 dev:user1/dev:user2 手工验证路径，CI 无此编排。建议在 CI 加一个可选 job 用 compose 起 2 consul + 2 user 跑发现相关断言。
5. **前端零自动化**。优先级建议：先给 `utils/http/index.ts` 的刷新队列写 vitest 单测（时序复杂、401 全局登出的兜底行为值得锁定），再给 `api/routes.ts` 的 toRoute/buildTree 写纯函数测试（出错影响全站导航但输入输出确定），页面级 E2E（Playwright）最后考虑——pure-admin 演示页多、选择器不稳定，投入产出比低。
6. **权限变更生效窗口无断言**。"改授权后 ≤60s 生效"横跨三个服务，没有任何自动化覆盖；可在 e2e 里用假时钟或直接调 `AuthorizationService` 的缓存失效行为补一条。
7. **上传链路（multipart→MinIO→回读）无自动化**。历史上靠 M7 冒烟脚本覆盖过一次后即失传；MinIO 依赖可用 testcontainers 起一次性实例，或先退而求其次锁住 fileFilter/大小限制的单元行为。

## 5. 给接手者的质量守则

三条从现有体系提炼出的工作纪律。第一，**改三类代码必须跑对应测试**：动 `gateway/src/consul/**` 跑 consul.service.spec，动日志查询跑 system 的 app.controller.spec，动 auth 链路跑 auth/authorization/policies 三份 spec——它们锁定的都是"曾经真实坏过"的行为，绿了再提交。第二，**新增接口的最小测试义务**是给网关控制器补一条权限码守卫断言（policies.guard.spec 的 makeContext 模式可直接复用），给业务服务补一条成功路径 + 一条约束冲突路径（P2002/前置条件），这两类正是线上事故的高发区。第三，**把"冒烟 ALL GREEN + 人工过页"当作不可省略的发布门禁**，尤其在改过 proto、seed、迁移或会话层之后——现有单测的覆盖重心在网关与查询构建，业务读路径的最终保证仍来自全栈实跑，这在教学/演示规模下是有意为之的分级策略，不要误以为"测试全绿 = 可以直接发"。

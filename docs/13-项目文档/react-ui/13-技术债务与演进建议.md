# 13 技术债务与演进建议（台账与路线图）
> 项目：react-ui ｜ 版本：v1.1 ｜ 生成日期：2026-10-06 ｜ 依据：源码分析

本篇把散落在源码注释、文档口径与既往篇目里的 ⚠️ 项汇总成一张台账：每一项给「位置 / 证据 / 影响 / 建议」四要素，全部经本轮回源码核实（不沿用传闻）。之后给出与台账对应的演进路线图。仓库自己的债务政策（CONTRIBUTING「债务政策」：棘轮只许调低、豁免必须留注释、争议写「待裁决」）与本篇的立场一致——**债务必须可见、可定位、有处置意见，但不必全部立刻清偿**。两轮全量审计的档案在 `archive/audit/`（12 条逐文件审查清单在 `archive/audit/AUDIT-2026-09-17/CHECKLIST.md`），本篇是它们之后的第三轮汇总。

## 1. 台账

### D1：apps/nas-console 仅有 dist 构建产物，源码未随仓库检出

- **位置**：`apps/nas-console/`（本检出仅含 `dist/` 与 `node_modules/`）。
- **证据**：目录列举可见无源码文件；《06-部署运行》第 10 节已标注「源码未随仓库检出 ⚠️ 待确认其源码管理位置」。
- **影响**：三方面——无法审计该示例的真实行为（截图 e2e 托管的是 `apps/docs/dist`，暂不涉及它，但 ADMIN-ROADMAP 的管理端示例叙事依赖它）；文档站迁移指南若引用其实现，读者无源可查；dist 产物会随时间与依赖漂移，变成无法重建的黑盒。
- **建议**：要么把源码入库（推荐，单人仓成本最低），要么从仓库移除并归档 dist，README 注明去向。禁止第三种状态（既留着又不管）。

### D2：`@xiaoye-react/charts` 在路线图中标记「✅ 可用」但仓库内不存在

- **位置**：`ADMIN-ROADMAP.md` 第 26 行（「仪表盘 | `@xiaoye-react/charts`（recharts 封装）：Bar/Line/Area/Pie/Donut/Radar 等 | ✅ 可用」）；`packages/` 与 `packages/@xiaoye-react/` 下均无 charts 目录；全仓源码检索无 recharts 依赖。
- **证据**：本轮 grep 复核，上述三处互相矛盾。
- **影响**：路线图是管理端能力的对外承诺，标记「可用」会让读者按存在去引用；若包在别处发布（独立仓库/未随检出），monorepo 的 `check:exports` 与 peer 校验对它完全失明。属「文档承诺与仓库事实漂移」类债务，性质比代码 bug 更伤信任。
- **建议**：三选一并落档——把 charts 包迁入 `packages/@xiaoye-react/charts`；或把路线图该行改为「计划中/外部仓库」；或在 README 声明 charts 的真实位置。⚠️ 待确认该包是否存在于独立仓库。

### D3：37 个组件目录无同目录单测（覆盖缺口）

- **位置**：`packages/ui/src/components/` 下 129 个目录中的 37 个（完整清单见《09-测试与质量保障》第 2 节；既往文档口径「91/130 有单测」与本批初稿的「90/129」均为目录计数与测试文件归类的口径差，2026-10-06 回源复核统一为实测 92/129）。
- **证据**：find 核对每个目录是否存在 `*.test.tsx`。
- **影响**：按风险分层——复杂交互型（Tree、TreeSelect、ComboboxPopover、ModalBase、Modals、Menubar）是状态机密度最高、回归代价最大的组件；输入外壳族（Input、InputBase、PillsInput）承载 a11y 关联契约；基建型（Button、Transition、Group、Stack、Text、Title、Input 系）目前靠上层组件测试间接兜底。Button 作为工厂模式范本无本目录测试是最醒目的一个点（其行为由 e2e 与消费方测试兜底）。
- **建议**：按《09-测试与质量保障》第 7 节的优先级清单消化：先补 6 个复杂交互组件的状态语义测试（ModalBase 的 modal-stack 纯函数可低成本直测），再用 `@xiaoye-react/tests` 的 axe 工具补输入外壳的无障碍断言；基建型与纯视觉型的优先级最低。配套动作：在 docs 或 CONTRIBUTING 里把「同目录必须有测试」从惯例升格为可检查的清单（甚至可加一个简单的缺测告警脚本入 docs:lint 旁路，⚠️ 待确认是否值得为它加脚本）。

### D4：hooks 包 README 与包描述的口径是「60+」，实际 83 个

- **位置**：`packages/hooks/package.json` 的 `description` 字段、`packages/hooks/README.md` 第 7 行；实测 `packages/hooks/src/` 下 83 个 `use-*` 目录。
- **证据**：本轮 grep 与目录列举。
- **影响**：对外口径低估了包的真实规模（反向漂移，比夸大无害但同样不严谨）；镜像地，`packages/hooks/vite.config.ts` 注释里的「87 个 hook」是另一个口径——三个数字（60+/83/87）并存说明没有单一事实源。
- **建议**：以 `packages/hooks/src/index.ts` 的导出为唯一事实源，README 与 description 改为实测数字；更彻底的做法是让 docgen 脚本顺带产出 hook 清单（`apps/docs/scripts/docgen.ts` 已具备类型扫描能力）。《15-接口全量参考》已按 83 目录口径建表，可作为对账基准。

### D5：Menubar 与 Tree 被整体排除在 ESLint 之外

- **位置**：`eslint.config.mjs` 的 ignores 数组（`packages/ui/src/components/Menubar/**/*`、`packages/ui/src/components/Tree/**/*`）。
- **证据**：配置文件原文；这两个目录恰好也无同目录单测（与 D3 重叠，风险叠加）。
- **影响**：react-hooks 规则与未使用变量在这两个目录完全失察；与 D3 的「复杂交互型无测试」叠加后，Menubar/Tree 成为质量洼地。
- **建议**：先按 hooks 规则修复（eslint 注释记录了同类修复的既有路径：145 → 78 → 57 三轮治理），再移出 ignores；若确有无法短期修复的告警，按债务政策留注释定向豁免而非整目录排除。

### D6：ESLint 类型安全规则大范围关闭

- **位置**：`eslint.config.mjs` rules 段：`no-explicit-any`、`no-unsafe-function-type`、`no-empty-object-type`、`ban-types`、`no-unused-vars`、`no-unused-expressions`、`no-namespace` 均 off。
- **证据**：配置原文（部分关闭有明确理由——OOM 限制了 type-aware 规则的使用，见 ignores 注释）。
- **影响**：`any` 的入库无门禁（实例见第 08 篇第 6 节的 adapter ctx）；`no-unused-vars` 关闭意味着死代码不被提示。
- **建议**：至少对 `packages/*/src` 开启 `no-explicit-any` 为 warn 并并入棘轮总量（不追求清零，只防增长——与 exhaustive-deps 台账同一模式）；`no-unused-vars` 可用 tsc 的 noUnusedLocals 折中评估（2026-10-06 回源复核：根与各包 tsconfig 均未启用 noUnusedLocals，启用属纯新增、与现有 typecheck 配置无冲突；代价是存量未用变量会新增一批报错，需按棘轮模式消化）。

### D7：截图 e2e 不在 CI

- **位置**：`playwright.config.ts` 与 `.github/workflows/ci.yml` 注释（「基线跨平台不通用」）。
- **证据**：CI 只跑交互 e2e 独立 job。
- **影响**：视觉回归完全依赖本地自觉，docs 站样式回退可能带病入库。
- **建议**：按 linux 单平台建基线入 CI（`actions/cache` 缓存基线产物），本地与 CI 各自维护平台基线目录；若维护成本实测过高再退回现状并记录裁决（⚠️ 待确认基线维护成本）。

### D8：包级 prepublishOnly 不含测试

- **位置**：`packages/*/package.json` 的 `prepublishOnly`（仅 build；ui 另跑 check:exports）。
- **证据**：`scripts/release.mjs` 头注释明言「包级 prepublishOnly 只有 build，不含测试」并因此显式执行 `runPackageTests`。
- **影响**：走 `release.mjs` 或根 `publish:*` 脚本时测试必跑（两处都补了），缺口只在绕过脚本直接 `pnpm --filter <包> publish` 的手工路径。
- **建议**：维持现状可接受（release.mjs 是唯一受支持的发布入口）；若要收紧，把 test 加进包级 prepublishOnly 并同步更新 release.mjs 的重复执行说明。

### D9：hooks 单测覆盖 30/83

- **位置**：`packages/hooks/src/` 30 个测试文件 vs 83 个 hook 目录（清单见《09-测试与质量保障》第 2 节）。
- **证据**：find 统计。
- **影响**：未覆盖清单里风险最高的是 `use-uncontrolled`（全库状态模型法定实现，语义目前靠 ui 侧测试间接固化）、`use-media-query`（其 `attachMediaListener` 导出是 ui peer 下限所系）、`use-focus-trap`、`use-id`。
- **建议**：优先补上述四个；`use-uncontrolled` 的「双 onChange 陷阱」与受控判定语义应像 `merge-ui-theme.test.ts` 一样固化为契约测试。

### D10：遗留的口径与注释漂移（轻项合并）

- 组件数口径：`packages/ui/package.json` description 写「130+ 组件」、目录实测 129——「130+」作为约数可接受，但在《15-接口全量参考》建表后建议统一引用实测值；
- `commitlint.config.cjs` 尾部有大段注释掉的汉化配置（约 80 行死配置），建议删除或启用；
- `CodeHighlight` 同步高亮阻塞主线程的已知边界（`CodeHighlight.tsx` 注释自述），长期方案是异步/Worker adapter（见《10-性能设计与优化》第 6 节）；
- 文档站构建链的 mako 保留决策（ADMIN-ROADMAP 记录的 21 分钟实测）与 rspress/vitepress 迁移备选——属路线图事项而非债务，并入第 3 节。

## 3. 演进路线图

把台账与既有路线图（`ADMIN-ROADMAP.md`）对齐，给出三个阶段的演进建议。每个阶段的立项都遵循同一条排期原则：**先清「文档性债务」（零代码风险、立刻建立信任），再清「覆盖性债务」（补测试补 lint，风险低但耗工时），最后才动「结构性演进」（新包、换构建链、换实现）**——这个顺序本身就是路线图的裁决逻辑，任何跳级（比如先做图表包再补覆盖缺口）都意味着在已知风险未消化时引入新面。

## 3.1 度量与节奏**第一阶段（卫生，1～2 个批次）**：清 D1/D2/D4/D10——全是文档与档案动作，不动代码；顺手把「同目录测试清单」挂进 docs:lint 旁路。**第二阶段（加固，按批次滚动）**：D5 → D6 → D9 的顺序推进 lint 覆盖与契约测试（先让 Menubar/Tree 回到规则之下，再开 no-explicit-any warn，最后补四个基建 hook 测试）；D3 按《09》的优先级分三批消化（复杂交互 → 输入外壳 a11y → 基建兜底）；D7 做 linux 单平台试点，裁决后固化。**第三阶段（演进，按需立项）**：四个方向值得评估——其一，图表域：若 D2 裁决为「迁入」，charts 包按 pro 的「peer 不造件」模式建包（recharts 封装 + `@xiaoye-react/tests` 复用）；其二，文档站构建链迁移（rspress/vitepress 备选，dumi patch 与 mako 的长期维护是隐性成本，ADMIN-ROADMAP 已列为长期可选项）；其三，高亮链路异步化（CodeHighlight adapter 的 loadContext 已预留异步形态）；其四，React 官方 Activity API 稳定后替换 `core/utils/Activity` 的 fallback 实现（源码注释已预告这一步）。第三阶段项目因为动了结构，每项都需要独立的立项记录（实测数据、替代方案对比、回滚方案）——ADMIN-ROADMAP 里 mako 保留决策的记录方式就是范本：两个候选方案的实测数字、落选原因、复评触发条件全部在案。

节奏上没有理由快：这是单人维护仓，路线图的执行者与受益者是同一个人，真正的约束不是进度而是**每次改动都必须全绿**——门禁清单本身就是最稳的节拍器。若多个阶段并行，唯一需要串行的点是发布：结构演进产出的新包（charts 等）要走《06-部署运行》的发布序列，与第二阶段的补测批次错开发布窗口即可。每一步都应延续本仓的纪律：先写注释记录实测数据，再动代码——债务治理与性能优化一样，起点是「可见」。

## 4. 台账的维护机制

这份台账本身也需要一个「不腐化」的机制，建议与仓库既有的治理设施对齐：**每项债务一个锚点**——D 系列编号写进对应位置的注释（如 D5 写进 `eslint.config.mjs` 的 ignores 注释、D8 写进 release.mjs 头注释），让「债务存在」这件事在源码里可见，而不是只活在文档里；**清偿动作走正常门禁**——补测试、修 lint、移出 ignores 都随常规提交走 `pnpm commit`，不设专门的「还债分支」，避免债务分支与主干漂移出第三种状态；**新债务的入口**——按 CONTRIBUTING 的裁决原则，发现即记录（位置/证据/影响三要素齐全才入台账，「感觉不好」不算证据），争议项标「待裁决」挂起而不是强行定性；**定期复核**——台账与 `archive/audit/` 的审计节奏对齐（两轮全量审计先例），每轮复核标记已消解项与新增项，路线图的阶段划分随之滚动。这套机制没有新增任何工具——它复用的全部是仓库已验证有效的设施（注释档案、棘轮、测试裁决），这正是对这个治理体系最好的信任投票：债务管理的答案不在更多流程里，而在把既有纪律延伸到「未修的东西」上。

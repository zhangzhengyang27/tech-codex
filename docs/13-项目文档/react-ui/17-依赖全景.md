# 17 依赖全景（逐包逐个解析与健康度评估）
> 项目：react-ui ｜ 版本：v1.2 ｜ 生成日期：2026-10-06 ｜ 依据：源码分析

## 1. 盘点范围与方法

依赖是一个组件库最诚实的「资产负债表」：`package.json` 里的每一个条目都对应一份维护承诺与一次下游升级风险。本篇把 monorepo 四层依赖面逐个走完——根 `package.json`（工程底座）、`packages/hooks`（应然的最小面）、`packages/ui`（真正的运行时主面）、`packages/@xiaoye-react/pro`（刻意的零依赖）与 `apps/docs`（文档站生态）——每条给出版本、用途、使用位置、选型理由、替代方案与升级风险。结尾单列 `patches/` 补丁依赖并给出整体健康度评估。选型理由一律以源码注释、README、ADMIN-ROADMAP 或包描述为据；属本篇分析的推断处会显式说明。机制与版本发布面的既有结论（外部化策略、peer 下限案例、发布顺序）以「见《0X-xxx》」引用，不再展开。

一个先给的结论：这张表总体是「小而克制」的——三个发布包的运行时依赖合计 20 条且全部有明确消费点（除一条例外，见第 9 节 klona 条目），没有任何「顺手装上」的全家桶式依赖。

根依赖里最值得注意的一条纪律是：**TypeScript 版本四手对齐**（根、hooks、ui、pro 的 devDeps 都是 5.5.2）——组件库的类型产物对 TS 编译器版本敏感（`vite-plugin-dts` 的发射与 `check:published-types` 的复检都吃这个版本），版本错位会产生「本机能过、发布产物类型报错」的幽灵问题。

## 3. packages/hooks：应然的最小面

`packages/hooks/package.json` 没有任何 `dependencies` 字段——83 个 hook 全部是纯 React 原语。devDeps 只有测试与构建两族（vitest 1.6 系、testing-library 系、jsdom、vite 5.4 系、vite-plugin-dts 4.3 系、typescript 5.5.2），peer 仅 `react`/`react-dom`（`^18.0.0 || ^19.0.0`）加 `sideEffects: false`。这是全仓健康度最高的一张依赖表：**运行时依赖为零意味着它对任何宿主项目都是零成本的**，也正是 ADR-001（《16-决策记录》）能成立的物质基础。升级风险面几乎不存在——唯一要守的是「不引入任何带副作用的模块」，否则 `sideEffects: false` 的承诺变成谎言，下游摇树会删掉真实需要的代码。

### 4.2 devDependencies 的三个观察

ui 的 devDeps 里混着三类东西：测试资产（vitest 1.6 系、@testing-library 三件套、jsdom）、构建资产（vite 5.4 系、vite-plugin-dts 4.3 系、@vitejs/plugin-react、postcss-nested）、以及三个值得单独说明的条目——`@xiaoye-react/hooks` 与 `@xiaoye-react/tests`（`workspace:*` 引用内部资产，前者同时是 peer，开发时经 devDeps 短路到源码仓）、`zod ^4.4.3`（schema-resolver 的测试演示依赖，恰好在 devDeps 而非 dependencies，说明「校验库永远属于消费者」的立场）、`@phosphor-icons/react` 与 `lodash`（story 与测试用，不进产物）。`vite-plugin-dts` 的两个行为补丁（afterDiagnostic 强制失败、beforeWriteFile 修 `__` 前缀重命名 bug）见《14-配置与环境详解》第 3 节，是 devDeps 中行为风险最高的一个——它的上游 bug 修复节奏直接决定 ui 的 dts 发射质量。

## 5. packages/@xiaoye-react/pro：刻意的零依赖

pro 包的 `package.json` 没有依赖条目——三个页面模式（PageContainer/SearchFilter/ProTable）全部由 peer（ui、hooks、react/react-dom）组装而成，连工具函数都没有自带。这是 ADMIN-ROADMAP「总体策略：分层放置，复用优先，不重写已有组件」的依赖面表达：模式层若有自己的运行时依赖，就会在消费者应用里出现「pro 的 dayjs 与 ui 的 dayjs」这类双实例问题。风险点同样清晰：pro 对 ui 的耦合是深度的（ProTable 直接内嵌 DataTable + SearchFilter），ui 的大版本升级天然要求 pro 跟进，peer 的 `workspace:^` 在发布时重写为 `^3.0.1` 一类的区间，区间内 ui 的破坏性 minor（若发生）不会被 peer 拦截——依赖 pro 的项目应把 ui 与 pro 视为一个联动升级单元（见《03-接口设计》第 7 节）。

## 6. apps/docs：文档站生态概览

文档站依赖面显著宽于任何发布包（约 40 条），可归五族：**dumi 内核族**（dumi ^2.4.30、dumi-plugin-color-chunk，构建链绑定 webpack/mako，patch 见第 8 节）；**演示与代码展示族**（@codesandbox/sandpack-react、@stackblitz/sdk、prismjs、highlight.js、vanilla-jsoneditor、mermaid）；**交互演示素材族**（@dnd-kit 三件套、motion、react-virtuoso、embla-carousel-autoplay、swr）；**图标族**（@phosphor-icons/react、react-icons——正是启动性能优化中「barrel 退出编译图」事件的当事依赖，438 文件改写、入口包 20.6→13.7MB，见 ADMIN-ROADMAP 进度节）；**工程脚本族**（ts-morph 驱动 docgen、tsx、glob、semver）。文档站依赖不需要发布面的严苛纪律，但有两点仍然要紧：其一，`@xiaoye-react/ui|hooks|pro` 走 `workspace:*`，本地源码即所见；其二，文档站是「文档即测试」机制的载体（docgen 与 `docs:lint` 三脚本），所以 ts-morph 的版本升级会直接影响 API 表核对能力。

## 7. 重点依赖深读

### 7.1 @floating-ui/react：浮层族的单一定位引擎

全库浮层（Tooltip/Popover/HoverCard/Menu/Spotlight/Combobox 及其上的 Select 家族、日期输入族）统一构建在 @floating-ui/react 之上，没有第二个定位实现。这个「单引擎」决策的收益在《02-组件设计》第 2.5/2.9 节已经展开（浮层基建复用图）；从依赖视角补充两点：其一，floating-ui 的中间件配置（flip/shift/arrow/size）在各组件的 use-tooltip/use-popover 等文件中各自组装，依赖升级时这些是回归排查点；其二，floating-ui/react 0.x 系列版本号意味着「次版本也可能带行为修正」，锁 `^0.27.19` 是当前测试面（浮层族全量单测 + modal/slider 等 e2e）能兜住的范围，升 1.x 应视为结构演进立项（按《13-技术债务》第三阶段的立项标准走）。

### 7.2 @tanstack/react-virtual：与 DataTable 的深度咬合

这是全库与业务代码咬合最深的一条依赖：DataTable 的虚拟行渲染、`measureElement` 引用直传、展开行双行高度合成上报（`resizeItem`），全部使用 tanstack v3 的内部语义（见《05-核心实现流程》主题二）。ADMIN-ROADMAP 决策 2（2026-09-09）明确拍板「`@tanstack/react-virtual` 进 ui 包 dependencies，DataTable 直接内置虚拟滚动」，理由是「demo 已验证过，先例充分」。升级风险因此不是「能不能跑」而是「测量语义会不会变」——v3 的动态测量与 resize 观测行为若有调整，展开行高度修正、固定列对齐这类精细逻辑需要重验。仓储里 `apps/docs` 也依赖 react-virtuoso 做文档站自身的长列表，但那是文档站自用，与组件库依赖面无关，不能混为一谈。

### 7.3 Emotion 五包：一个「可选通道」的依赖形态学

Emotion 在 ui 的 dependencies 里占五席（cache/react/serialize/utils 四个运行时包，加上根部的 postcss-styled-syntax 协助 lint），但主路径（CSS Modules）一个都不 import——它们只被 `src/emotion/` 的可选通道消费：`UIEmotionProvider` + `create-styles` + `emotion-transform`（以 stylesTransform 注入 UIProvider）+ `use-css`/`merge-sx` + `ssr.tsx`（html-react-parser 抽取服务端关键样式）。这个依赖形态值得学习：**「可选能力」以 dependencies 而非 peerDependencies 存在**——消费者不装任何东西也能用主路径，装了 ui 就天然具备 emotion 通道，代价是所有消费者都背着这四个包的安装体积（虽然不 import 就不进产物）。设计谱系上，这条通道与 Mantine v6→v7 的演进轨迹同构（v6 的 create-styles 基于 emotion，v7 转向 CSS Modules + CSS 变量并保留兼容层）——本库内核（factory/StylesApi/varsResolver/useProps/CSS 变量主题）与 Mantine 的同构性是结构事实，但仓库内没有任何文字声明这一谱系 ⚠️ 待确认（作者意图层面）。从依赖治理看，若未来确认 emotion 通道无真实消费者，五包合计是最大的一条可裁剪面。

### 7.4 dayjs 与 rrule：日期域的双内核

dates 模块 33 个组件全部基于 dayjs（`dates/utils/` 封装层），schedule 模块的重复事件基于 rrule（`schedule/utils/expand-recurring-events/`）。两条依赖的性格完全不同：dayjs 是「基础设施型」——版本范围声明为 `>=1.0.0`（极宽），真正的约束不在版本号而在**单实例纪律**（插件 extend 与 locale 注册是全局副作用，这正是 vite.config 外部化注释点名它的原因）；rrule 是「功能型」——`^2.8.1` 锁区间，但它是 README 发布坑清单里唯一的第三方包案例（CJS/ESM 双入口，`main` 与 `module` 指向不同构建，消费代码要「命名空间优先、计算键 default」），这意味着 rrule 的每一次升级都必须走消费者侧 ESM 复验，不能只看单测绿。

### 7.5 Playwright：双配置的测试基建

根 `playwright.config.ts`（截图 e2e，托管 `apps/docs/dist`，10 条基线）与 `playwright.interactions.config.ts`（交互 e2e，Vite harness 端口 4175，24 条用例）共用 `playwright ^1.61.1` 与 `@playwright/test ^1.61.1` 双 devDeps。选型理由在《09-测试与质量保障》第 3 节已展开；依赖视角的风险集中在截图基线：内核渲染随版本漂移会让基线批量失真，而基线「跨平台不通用」导致 CI 不跑截图（D7）——升级 playwright 版本时，截图套件实际上是在本地以「人工对差异」方式复验的，这是当前依赖面里最依赖人的一个环节。

### 7.6 dumi：被打了补丁的文档内核

文档站选择 dumi 2 的理由（markdown 长文 + demo + API 表三合一、可被脚本核对）见《00-项目总览》第 9 节；代价是绑定 webpack/mako 构建链（ADMIN-ROADMAP 实测：mako 无持久化缓存、webpack fs cache 冷 21min/热 146s 均不划算，保留 mako 并把图标 barrel 移出编译图）。dumi 在 `pnpm.overrides.patchedDependencies` 里被登记为 `dumi@2.4.47: patches/dumi@2.4.47.patch`——补丁内容见第 8 节。升级风险：dumi 2.x 内部（dist 产物）被直接 patch，任何上游升级都会使补丁失配，需要重新定位对应产物并重做 diff；这也是 ADMIN-ROADMAP 把「迁移 rspress/vitepress」列为长期可选项的根本原因——框架级依赖的不可控性只能用「可迁移性」对冲。

## 8. patches/ 补丁依赖单列

`patches/` 目录当前只有一个补丁：`patches/dumi@2.4.47.patch`（19 行），在根 `package.json` 的 `pnpm.patchedDependencies` 登记。补丁内容是删除 dumi 产物中 `DumiDemo` 组件的 `React.memo` 包装——原实现用「JSON.stringify 前后长度相等」作为 props 判等，补丁注释记载了故障与根因：「demo 数据异步就位后，Suspense 重试渲染会被该 memo 的 props 判等命中而 bailout，骨架屏永久停留（schedule 视图页 100% 复现）」。

这个补丁是全仓依赖治理的一个标本，有三条纪律值得记录：其一，**补丁必须带故障复现描述**（「schedule 视图页 100% 复现」让未来的维护者能验证补丁是否仍必要）；其二，**补丁对象是构建产物而非源码**（diff 的目标文件是 `dist/client/theme-api/DumiDemo/index.js`），因此 dumi 小版本升级即失配——依赖声明里的 `^2.4.30` 区间实际上被 patchedDependencies 收窄为「2.4.47 可用」；其三，补丁是债务不是资产，第 9 节的健康度评估将其计为维护面而非功能面。《08-安全与权限设计》第 2.2 节已从供应链视角讨论过 patches 的作用与纪律，本节不重复。

## 9. 健康度评估

综合四层依赖面，给出六个维度的评估：

**1. 依赖数量与密度：优。** 三个发布包运行时依赖合计 20 条（ui 20、hooks 0、pro 0），无传递性大件（无 UI 框架、无状态管理库、无路由），除 klona 一条死依赖（见下条）外每条都有可指认的消费文件。对照同类组件库（普遍 30-60 条），这是刻意的「最小面」结果（ADMIN-ROADMAP 总体策略、《08-安全与权限设计》第 2.3 节「运行时依赖的最小面」）。

**2. 死依赖：一处。** `klona ^2.0.6` 声明于 ui 的 dependencies，但全 src 检索无任何 import——唯一的痕迹是 `form/paths/set-path.ts` 第 3-4 行注释：「此前每次 setPath 都对整表值做 O(整表) 深克隆(klona)，大表单高频键入时是稳定热点；实际上只有路径上的祖先链需要克隆」——即 klona 已被 copy-on-write 浅克隆优化取代，依赖声明却留了下来。这是本篇回源码的新发现，建议在下一批卫生清理（《13-技术债务》第一阶段）中移除并过一次全量单测。

**3. 版本声明纪律：良，有两类例外。** 绝大多数依赖用 `^` 区间，符合生态惯例；例外是 `type-fest 4.41.0` 与 `react-dropzone 15.0.0` 的精确锁定（前者是类型库版本敏感的合理防御，后者精确锁定的理由仓库内未见说明 ⚠️ 待确认），以及 `dayjs >=1.0.0`、`chroma-js >=2.4.2` 的下限式宽松声明（实质靠 lockfile 与单实例纪律兜底）。TypeScript 四处 5.5.2 对齐是这套纪律里执行得最好的一条。

**4. 补丁面：小而可控。** 仅 1 个补丁、19 行、带复现描述，且登记在 `pnpm.patchedDependencies` 由 pnpm 统一应用——没有散落的 postinstall 改写。维护成本集中在 dumi 升级时重建补丁。

**5. 双入口与互操作风险：聚焦于一点。** 全仓唯一已知的 CJS/ESM 双入口第三方依赖是 rrule，且已有成文的消费模式与消费者侧复验流程兜底（README 第 4 步 + release.mjs 显式执行）。这个风险模型是健康的：风险被识别、被文档化、被流程化。

**6. 升级风险的分布：冷热分明。** 热区三处——@floating-ui/react（0.x、浮层族全覆盖）、@tanstack/react-virtual（与 DataTable 测量语义咬合）、dumi（patch 失配）；温区若干（vite-plugin-dts 的上游 bug 行为、playwright 截图基线）；其余基本是「升了大概率没事」的冷区。给后续维护者的操作建议：热区升级一律按《13-技术债务》第三阶段的结构演进标准立项（实测数据、替代方案对比、回滚方案），温区升级走正常门禁全绿，冷区随例行手动升级节奏即可（2026-10-06 回刷核实：全仓无 dependabot/renovate 配置，`.github/` 下仅 `workflows/ci.yml`，依赖更新为手动节奏）。

一句话收束：这张依赖表的治理水平高于「单人仓」的平均线——最小面是有意识的结果而非运气不足，唯一的不对称在于：热区风险已有成文流程，而像 klona 这样的「尾巴」靠本轮回源码才现形。建议把「依赖消费点检索」纳入《09-测试与质量保障》式的周期审计清单，让死依赖无处存活。

## 1. 走读一：polymorphic-factory.tsx——多态工厂的运行时层

文件位于 `packages/ui/src/core/factory/polymorphic-factory.tsx`。它的类型层搭档 `create-polymorphic-component.ts`（61 行）负责「component prop 的类型分发」，见《03-接口设计》第 2 节；本篇聚焦运行时层——工厂如何把一个普通 forwardRef 渲染函数变成「可多态、可封装、带静态件」的组件。

### 1.1 载荷扩展与 withProps 的类型签名

````ts
export interface PolymorphicFactoryPayload extends FactoryPayload {
    defaultComponent: any
    defaultRef: any
}

export type PolymorphicComponentWithProps<Payload extends PolymorphicFactoryPayload> = {
    withProps: <C = Payload['defaultComponent']>(
        fixedProps: PolymorphicComponentProps<C, Payload['props']>
    ) => <L = C>(props: PolymorphicComponentProps<L, Payload['props']>) => React.ReactElement
}
````

**逐段解读**：第一段定义多态工厂的载荷——在基础 `FactoryPayload`（《05-核心实现流程》与 `factory.tsx` 中定义，含 props/ctx/ref/stylesNames/vars/variant/staticComponents/compound 九个槽位）之上，要求组件必须声明 `defaultComponent` 与 `defaultRef`。这两个 `any` 类型的槽位是整个多态类型系统的锚点：后续所有泛型的默认值都从它们取（`<C = Payload['defaultComponent']>`），所以 Button 声明 `defaultComponent: 'button'`、`defaultRef: HTMLButtonElement`（见 `components/Button/Button.tsx` 第 88-99 行）之后，消费者写 `<Button>` 时 TS 自动推断 C 为 'button'，继承全部 button 原生属性；写 `<Button component="a" href="...">` 时 C 变成 'a'，href 合法而 type="button" 报错——多态的类型分发不需要用户手写任何泛型。

第二段是 `withProps` 的类型签名，读法是「双函数柯里化」：第一层接收固定 props（类型按 C 推断，C 默认取 defaultComponent），返回的函数本身还带一个泛型 `<L>`——意思是 `Button.withProps({ variant: 'light' })` 的产物**依然是多态的**，用的时候还能再换 `component`。如果签名写成返回一个单态组件，`ButtonLink = Button.withProps(...)` 之后再传 `component={Link}` 就会丢类型。

**这段代码教会我们什么**：泛型默认值可以承载「默认形态」的语义——把最常用的情况设为类型参数默认值，用户在常用路径上完全感知不到泛型存在，只有在偏离默认时才需要（或自动地）切换类型参数。多态组件 API 的易用性，一半是运行时给的，另一半是这种「默认泛型」设计给的。

### 1.2 主体类型：五路交叉的静态件装配

````ts
export function polymorphicFactory<Payload extends PolymorphicFactoryPayload>(
    ui: React.ForwardRefRenderFunction<Payload['defaultRef'], Payload['props']>
) {
    type ComponentProps<C> = PolymorphicComponentProps<C, Payload['props']>

    type _PolymorphicComponent = <C = Payload['defaultComponent']>(props: ComponentProps<C>) => React.ReactElement

    type ComponentProperties = Omit<React.FunctionComponent<ComponentProps<any>>, never>

    type PolymorphicComponent = _PolymorphicComponent &
        ComponentProperties &
        ThemeExtend<Payload> &
        ComponentClasses<Payload> &
        PolymorphicComponentWithProps<Payload> &
        StaticComponents<Payload['staticComponents']> & {
            varsResolver?: VarsResolver<Payload>
        }
````

**逐段解读**：工厂函数签名只接受一个参数——forwardRef 渲染函数本身（`ui`），也就是说组件作者的全部实现责任被压进一个 `(props, ref) => JSX` 的纯函数。主体类型 `PolymorphicComponent` 是六路交叉：

- `_PolymorphicComponent`：带泛型的调用签名，这是「多态」本体的类型表达；
- `ComponentProperties`：从 `React.FunctionComponent` 挖来的函数组件基础能力（displayName、propTypes 等）——注意它用的是 `ComponentProps<any>`，否则 displayName 等成员的类型会跟具体 C 绑死；
- `ThemeExtend<Payload>`：`extend(input: ExtendComponent<Payload>) => UIThemeComponent`，即 UIProvider 主题 `theme.components` 定制口的类型面（`factory.tsx` 第 92-94 行）；
- `ComponentClasses<Payload>`：`classes: Record<string, string>` 静态成员，供消费者探测组件内部类名（如 `Paper.classes.root`）；
- `PolymorphicComponentWithProps<Payload>`：上面 1.1 讲的 withProps；
- `StaticComponents<Payload['staticComponents']>`：把 `Button.Group`、`Tabs.List` 这类静态子组件并入组件自身类型——泛型别名 `StaticComponents<Input>` 在 `factory.tsx` 第 84 行有个精妙的防御性注释：「回退必须是 `{}`（交叉类型的单位元），不能用 `Record<string, never>`。因为 `StaticComponents` 会被交叉（`&`）进 `UIComponentStaticProperties`，`[key: string]: never` 索引签名会把 extend/withProps/classes 及具体子组件赋值全部坍缩为 `never`」。

最后挂一个可选的 `varsResolver` 静态成员，类型来自 `../styles-api`。

**设计意图**：这个交叉结构把「一个组件是什么」定义成了函数能力与静态能力的并集——它首先是个可调用的渲染函数（带泛型调用签名），同时是一组可编程的静态件（extend/withProps/classes/varsResolver），还可以是子组件的命名空间（staticComponents）。全库 129 个组件共享这一形状，这正是《02-组件设计》第 1 节「统一出生流程」铁律的类型层兑现。

**这段代码教会我们什么**：交叉类型（`&`）是给「组件 + 静态 API」建模的正解，但交叉是有陷阱的——索引签名与交叉相遇会把整个类型坍缩。`StaticComponents` 回退到 `{}` 的注释值得每个写组件库类型的人抄进自己的笔记：**交叉类型的每个参与者都必须是「可交叉」的，一个带索引签名的成员会污染整个交集**。

### 1.3 forwardRef 包装：双参守卫与「类型断言的边界」

````ts
    // 包装 render 函数，确保 React 19 forwardRef 始终接收 (props, ref) 双参数
    const Component = forwardRef((props: Payload['props'], ref: React.Ref<Payload['defaultRef']>) =>
        ui(props, ref)
    ) as unknown as PolymorphicComponent
````

**逐段解读**：这段代码乍看是多余的——`forwardRef(ui)` 直接传 `ui` 不就行了？但工厂选择再包一层箭头函数并显式传 `(props, ref)` 双参。原因写在注释与 `factory.tsx` 第 217-219 行的同款注释里：「避免部分组件只声明 _props 单参数时触发运行时警告/SSR 组件类型错误」——`forwardRef` 的语义是给渲染函数传双参，若组件作者偷懒只写 `(props) => ...`，第二参虽不会被读到，但 React 的开发态校验与某些类型推导路径会出问题。工厂层统一兜住这个纪律，组件作者犯不了这个错。

然后是 `as unknown as PolymorphicComponent`——**双重断言**。运行时对象实际上只是 forwardRef 的产物（带后续手工挂上的静态件），类型系统里它要被当作六路交叉的复合体。为什么 TS 需要先 `unknown` 中转？因为 forwardRef 的返回类型与 `PolymorphicComponent` 差异太大，直接断言会被 TS 拒绝（两者没有明显的重叠子类型）。这里的边界意识很清楚：类型断言集中在一处、紧跟在创建点之后、以类型定义为准绳——而不是让 `any` 扩散到组件实现里。

**这段代码教会我们什么**：基建层的职责之一是「把纪律做进 API 形状里」，让调用方无法犯错（双参守卫）；而类型断言不等于类型作弊——把 `as unknown as` 圈定在工厂的最后一个表达式，用一个精心设计的复合类型作为唯一的「出栈口」，整库其余代码拿到的都是强类型。断言的毒性取决于它的扩散面。

**这段代码（与 1.2 合并）教会我们什么**：所谓工厂，本质是把「重复的样板（forwardRef 包装、静态件挂载、displayName 规范）」从 129 个组件里抽走，同时把「容易做错的判断（双参、静态件透传）」从人肉纪律变成结构保证。

### 1.4 withProps 运行时实现：静态件透传的兼容性修正

````ts
    Component.withProps = (fixedProps: any) => {
        const Extended = forwardRef((props, ref) => <Component {...fixedProps} {...props} ref={ref as any} />) as any
        Extended.extend = Component.extend
        Extended.displayName = `WithProps(${Component.displayName})`
        // 与非 polymorphic 版 factory 的 withProps 对齐：classes/varsResolver 是
        // 组件的静态属性（如 Paper.classes），依赖它做样式探测的消费者在 withProps
        // 产物上不应失效
        Extended.classes = Component.classes
        Extended.varsResolver = Component.varsResolver
        return Extended
    }

    Component.extend = identity as any

    return Component as PolymorphicComponent
}
````

**逐段解读**：withProps 的运行时实现是个四行的 forwardRef 包装：展开顺序 `{...fixedProps} {...props}` 保证**传入 props 优先于固定 props**——`Button.withProps({ variant: 'light' })` 产出的组件仍可被调用方覆盖成 `variant="outline"`，固定值是「默认」而非「锁定」。这是一个容易写反的细节：如果顺序反了，withProps 就变成「劫持」而非「预置」。

随后的四行静态件透传里藏着一段**事后修正的考古痕迹**。注释明确说这是「与非 polymorphic 版 factory 的 withProps 对齐」——对照 `factory.tsx` 第 222-229 行的非多态版 `factory().withProps`，它从一开始就透传 `extend/classes/varsResolver` 三件，而多态版最初只透传了 extend。注释里给出的理由句式（「依赖它做样式探测的消费者在 withProps 产物上不应失效」）表明这是一次由消费者兼容性驱动的补课：`Paper.classes` 这类静态属性一旦被第三方代码拿去做样式探测，withProps 产出的变体组件如果不带同样的静态件，消费方代码就静默失效。displayName 的 `WithProps(原displayName)` 包装则是调试约定——React DevTools 里能一眼认出变体的出身。

最后一行 `Component.extend = identity as any` 把恒等函数（`factory.tsx` 第 174-176 行）挂为 extend 的实现。运行时它什么都不做，意义全在类型层：`ExtendComponent<Payload>` 定义了「主题里能对一个组件配置什么」，`extend` 的存在让 `theme.components.Button` 的类型收窄入口成立——传什么进去、原样返回，但类型从宽松收窄到精确（见《01-系统架构》第 3.4 节 create-theme 同款手法）。

**这段代码教会我们什么**：其一，HOC 展开顺序即语义（预置 vs 劫持），这种顺序必须像 API 契约一样对待；其二，静态成员是组件公共面的一部分——高阶封装「丢静态件」是组件库生态里最隐蔽的一类破坏（类型不报错、运行时才炸），修复方式不是改消费者而是让封装层的静态面与本体严格一致；其三，注释里那句「对齐」是优秀的工程沟通：它告诉读者这不是随手写的四行，而是与另一个实现保持契约一致的有意行为。

## 2. 走读二：use-props.ts——默认值三级合并与快路径

文件位于 `packages/ui/src/core/UIProvider/use-props/use-props.ts`，全文件 45 行，是 core 里最短却被每个组件调用的函数之一。它解决的问题是：组件默认值、主题层默认值（`theme.components.Button.defaultProps`）、调用方传入 props，三者如何按稳定优先级合并且不破坏引用稳定。

### 2.1 签名：复合组件的名称数组与「必填化」返回类型

````ts
export function useProps<T extends Record<string, any>, U extends Partial<T> | null = {}>(
    component: string | string[],
    defaultProps: U,
    props: T
): T &
    (U extends null | undefined
        ? {}
        : {
              [Key in Extract<keyof T, keyof U>]-?: U[Key] | NonNullable<T[Key]>
          }) {
````

**逐段解读**：三个参数对应三级合并的三个来源——但顺序是「组件名、组件默认值、传入 props」，主题默认值不在参数里，因为它是运行时从 context 读的。`component` 接受字符串**或字符串数组**，注释只有一句：「复合组件可传名称数组（依次读取各层主题默认属性）」——复合组件（如 Modal 由 Root/Header/Body 组成）可以让每层都在 `theme.components` 上有自己的 defaultProps，useProps 逐一读取后叠加。返回类型是本函数最精巧的部分：`U`（组件默认值类型）非空时，对「既是 props 的键又是默认值的键」做 `-?` 修饰——**去掉可选性**。含义是：如果组件声明了 `defaultProps = { size: 'sm' }`，那么经过 useProps 之后 `size` 就保证有值，类型从 `size?: ...` 变成 `size: ...`。下游代码（如 Button 的 varsResolver 里 `getSize(size, 'button-height')`）因此不需要写 `size ?? 'sm'` 这类防御。`U extends null | undefined ? {}` 分支则对应 Button 那样的用法（`useProps('Button', null, _props)`，见 `Button.tsx` 第 143 行）——不传组件默认值时返回类型就保持原样，不产生虚假的「必填化」。

**这段代码教会我们什么**：类型系统可以编码「运行时保证」——defaultProps 的存在意味着「合并后必有值」，这个事实用 mapped type 的 `-?` 写进返回类型，运行时合并与类型收窄互为印证。好的泛型签名让调用方的下游代码少写一整层防御。

### 2.2 快路径：引用稳定是性能契约

````ts
    const theme = useUITheme()
    // component 支持传单个名称或名称数组（复合组件依次读取各层主题默认属性）
    const names = Array.isArray(component) ? component : [component]

    // 快路径：组件无 defaultProps 且主题也没有为该组件配置 defaultProps 时，
    // 原样返回 props。此前这里每次都新建 5~6 个对象，既白花时间又破坏 props 引用身份，
    // 让下游所有 useMemo/React.memo 判定永远命中不了。
    const hasOwnDefaults = defaultProps != null && Object.keys(defaultProps).length > 0
    if (!hasOwnDefaults && !names.some(name => theme.components[name]?.defaultProps)) {
        return props as any
    }
````

**逐段解读**：先看判断条件的精确性：快路径要求**两边都没有默认值**——组件自身的 defaultProps 为空（`Object.keys(...).length > 0` 同时排除了 null 与空对象）且主题上没有任何一层（names 数组里任意一个名字）配置了 defaultProps。只有此时才走 `return props` 原样返回。注释里的话是这次优化的历史证词：「此前这里每次都新建 5~6 个对象」——旧实现无条件走展开合并，即使三路全空也要产出新对象，后果不只是分配开销：**props 对象的引用身份每帧都变，下游一切以 props 为依赖的 useMemo/React.memo 全部失效**。这与《10-性能设计与优化》第 3 节「引用稳定优先」的纪律直接对应，与 `useUncontrolled` 的稳定 setter、`useStyles` 的按选择器缓存是同一族设计。

值得注意的还有 `theme.components[name]?.defaultProps` 的可选链：主题上没有配置过的组件名直接得 undefined，不抛错——主题层对任意组件的 defaultProps 配置是「可以有」而非「必须有」。

**这段代码教会我们什么**：合并函数的性能问题从来不是「慢」，而是「破坏引用身份」——对象展开是引用变的、内容不变，缓存层完全无法识别。给热路径函数设计「零分配快路径」时，判断条件必须覆盖所有「有实质合并」的情形（这里漏判主题 defaultProps 就会导致主题配置静默失效——条件是两处 OR 的否定，一处都不能少）。

### 2.3 主题归约：函数型 payload 的延迟解析

````ts
    const contextProps = names.reduce<Record<string, unknown>>((acc, name) => {
        const payload = theme.components[name]?.defaultProps
        const resolved = typeof payload === 'function' ? payload(theme) : payload
        return { ...acc, ...resolved }
    }, {})

    return { ...defaultProps, ...contextProps, ...filterProps(props) } as T &
        (U extends null | undefined
            ? {}
            : { [Key in Extract<keyof T, keyof U>]-?: U[Key] | NonNullable<T[Key]> })
}
````

**逐段解读**：归约循环按 names 顺序叠加各层主题默认值，展开顺序决定了后者覆盖前者——复合组件传 `['ModalRoot', 'Modal']` 时，更具体的层放前面还是后面由调用方语义决定。中间那行 `typeof payload === 'function' ? payload(theme) : payload` 是容易一眼扫过却大有文章的分支：主题 defaultProps 允许是**函数**，参数是最终合并后的 theme。这让「依赖其他主题配置的默认值」成为可能——比如默认值想跟随 `theme.defaultRadius` 或某个色彩派生值，写成函数就能在主题合并完成后再解析，而不是在主题对象字面量里静态写死。`filterProps(props)` 来自 `core/utils/filter-props`，作用是把 undefined 值的键从 props 里剔除——调用方写 `<Button size={cond ? 'lg' : undefined}>` 时，undefined 的 size 不应盖掉默认值，剔除后展开合并才能落在正确的优先级上。

最终返回的展开顺序 `{...defaultProps, ...contextProps, ...filterProps(props)}` 就是文档反复承诺的优先级：**传入 props > 主题 defaultProps > 组件 defaultProps**（`use-props.ts` 顶部 JSDoc 的 @returns 注释原文）。

**这段代码教会我们什么**：三级合并看似只是三个展开运算符，但两个分支决定了它的正确性——函数型 payload（延迟解析，让默认值能引用主题上下文）与 filterProps（undefined 不抢位）。优先级声明写在 JSDoc、实现写在展开顺序、验证写在单测，三处一致才是契约。

## 3. 走读三：use-styles.ts——样式中枢与按选择器缓存

文件位于 `packages/ui/src/core/styles-api/use-styles/use-styles.ts`（145 行）。它是 StylesApi 体系（《01-系统架构》第 3.3 节）的运行时总装线：所有组件在实现里调用它一次，得到一个 `getStyles(selector, options?)` 函数，此后每个内部节点用选择器取类名与内联样式。

### 3.1 输入接口：一个组件要交出什么才能获得样式能力

````ts
export interface UseStylesInput<Payload extends FactoryPayload> {
    name: string | (string | undefined)[]
    classes: Payload['stylesNames'] extends string ? Record<string, string> : never
    props: Payload['props']
    stylesCtx?: Payload['ctx']
    className?: string
    style?: UIStyleProp
    rootSelector?: Payload['stylesNames']
    unstyled?: boolean
    classNames?: ClassNames<Payload> | ClassNamesArray<Payload>
    styles?: Styles<Payload>
    vars?: PartialVarsResolver<Payload>
    varsResolver?: VarsResolver<Payload>
    attributes?: Attributes<Payload>
}
````

**逐段解读**：输入十三项，可以分四组读。**身份组**：`name`（组件名或名称数组——与 useProps 的复合组件机制同构，主题层按名字找该组件的 classNames/styles/vars 配置）、`classes`（CSS Modules 对象，类型约束为「当 Payload 声明了 stylesNames 才有」——没有选择器的组件根本不需要 useStyles）。**实例覆盖组**：`classNames/styles/vars/attributes` 四件套即 StylesApiProps 消费者传入的部分，加上组件自带的 `varsResolver` 静态件。**环境组**：`unstyled`（关样式）、`rootSelector`（默认 'root'，决定「根类名」以哪个选择器为准）。**直通组**：`className/style`（消费者直接传的字符串类名与样式对象，不走选择器）。`stylesCtx?: Payload['ctx']` 是复合组件的槽位——子件通过 context 拿到根件的 ctx 传入，让主题层能对「特定上下文里的子件」做样式配置。这个接口本身就是一份「组件作者接入 StylesApi 的清单」：漏传任何一件，对应通道就静默失灵（排查方法见《12-FAQ与故障排查》）。

**这段代码教会我们什么**：API 的复杂度要花在「类型分组清晰」而不是「条目少」上——十三项输入按四组阅读毫不费力，因为命名与类型把每一项的来源（消费者传/组件静态/Provider 环境）标得清清楚楚。

### 3.2 环境读取与 themeName 规整

````ts
    const theme = useUITheme()
    const classNamesPrefix = useUIClassNamesPrefix()
    const withStaticClasses = useUIWithStaticClasses()
    const headless = useUIIsHeadless()
    const themeName = useMemo(() => (Array.isArray(name) ? name : [name]).filter(n => n) as string[], [name])
    const { withStylesTransform, getTransformedStyles } = useStylesTransform({
        props,
        stylesCtx,
        themeName
    })
````

**逐段解读**：五连读。前四个都是从 UIProvider 的细粒度消费 hook 取环境（《04-数据模型》第 5 节的 10 个细粒度 hook 机制）——注意取的是 `useUITheme()`（无 Provider 时回落 DEFAULT_THEME）而非 `useUIContext` 全量对象，消费面越窄，未来 context 拆分的兼容缝越宽。第五行把 name 规整为数组并过滤空值（`filter(n => n)` 处理复合组件传入的 `[undefined, 'Modal']` 这类形态——子件可能不知道自己该挂哪个主题名）。最后一行接入 `useStylesTransform`：这是 stylesTransform 通道（Emotion 可选层，《01-系统架构》第 4 节）的入口，返回两个东西——是否需要走转换（`withStylesTransform`）与转换函数（`getTransformedStyles`）。注意它是**无条件调用**的，内部再根据 Provider 是否配置了 stylesTransform 决定行为——与 DataTable「useVirtualizer 始终调用」是同一条 hooks 纪律：条件调用 hook 会破坏调用顺序一致性。

**这段代码教会我们什么**：环境依赖要在函数顶部一次性收拢，且「按需消费」（细粒度 hook）与「无条件调用」（hooks 顺序）两条纪律在这里同时兑现。规整动作（数组化、过滤）发生在 useMemo 里而非每次计算时，为后面每帧多次的解析铺平了输入。

### 3.3 缓存 Map 与 computeStyles：性能设计的完整注脚

````ts
    // 同一次渲染内按选择器缓存解析结果：getStyles 每次都重跑 varsResolver / 主题 vars /
    // filterProps 与 8 个 className 辅助函数，而 DataTable 这类组件每行每格都会重复请求
    // 同一批选择器（tr、td……），虚拟滚动下等于每帧重复解析上百次。
    // 仅对不带 options 的调用生效——带 options 时结果依赖 options，不适合按选择器复用。
    const resolvedOncePerSelector = new Map<string, ReturnType<typeof computeStyles>>()

    function computeStyles(selector: string, options?: GetStylesApiOptions) {
        return {
            className: getClassName({
                theme,
                options,
                themeName,
                selector,
                classNamesPrefix,
                classNames,
                classes,
                unstyled,
                className,
                rootSelector,
                props,
                stylesCtx,
                withStaticClasses,
                headless,
                transformedStyles: getTransformedStyles([options?.styles, styles])
            }),

            style: getStyle({
                theme,
                themeName,
                selector,
                options,
                props,
                stylesCtx,
                rootSelector,
                styles,
                style,
                vars,
                varsResolver,
                headless,
                withStylesTransform
            }),

            ...attributes?.[selector as keyof typeof attributes]
        }
    }
````

**逐段解读**：缓存 Map 的注释是全仓性能注释里信息密度最高的一段，四句话分别交代了**为什么缓存**（解析成本：varsResolver + 主题 vars + filterProps + 8 个类名辅助函数）、**谁触发重复**（DataTable 每行每格重复请求同批选择器）、**多严重**（虚拟滚动下每帧上百次重复解析）、**边界在哪**（仅缓存不带 options 的调用）。最后一句是这条缓存的正确性关键：`getStyles('tab', { active: true })` 这种带 options 的调用，结果随 options 变化，按 selector 做键会缓存出错误结果——所以带 options 直接走 computeStyles 不进缓存。

`computeStyles` 的结构是「两路合成 + 属性展开」：className 交给 `getClassName`（位于 `get-class-name/get-class-name.ts`，内部串联全局类名、主题类名、变体类名、静态类名、选择器类名、根类名、options 类名、resolved 类名八级辅助——《07-模块详解》第 3.3 节），style 交给 `getStyle`（`get-style/get-style.ts`，合并 styles 对象、vars、varsResolver 产物与主题 vars）。两路都吃同一份环境与 props，最后 `...attributes?.[selector]` 把该选择器上的附加属性（data-* 之类）摊进返回对象——调用方拿到的是 `{ className, style, ...attributes }` 一体货，直接展开到 DOM 节点上。

**这段代码教会我们什么**：注释 caching 决策时，把「成本模型（为什么值得）、触发模式（谁在重复）、量级（多严重）、失效边界（什么时候不能缓存）」四件事写全，后人才能安全地维护它。而缓存键的设计必须严格对应结果的依赖集——「按 selector 缓存」之所以正确，是因为不带 options 的结果只依赖 selector 与本次渲染的输入快照。

### 3.4 返回的选择器函数：三条路径一个出口

````ts
    return (selector: string, options?: GetStylesApiOptions) => {
        if (options) {
            return computeStyles(selector, options)
        }

        const cached = resolvedOncePerSelector.get(selector)
        if (cached) {
            return cached
        }

        const computed = computeStyles(selector)
        resolvedOncePerSelector.set(selector, computed)
        return computed
    }
}
````

**逐段解读**：出口只有 14 行，三条路径清晰分流：带 options → 每次现算；不带 options 且缓存命中 → 直接返回；否则现算并写入缓存。三个值得点破的细节：其一，缓存的生命周期是「函数实例」——`resolvedOncePerSelector` 在 useStyles 的每次调用（即组件每次渲染）时新建，所以这是**渲染内缓存**而非跨渲染缓存，天然没有失效问题（新渲染新 Map），代价是每渲染重建一个空 Map（一次分配，换来百次级解析的豁免，稳赚）；其二，返回的 `getStyles` 本身不是 useCallback 的——它每帧重建，但它被组件实现里直接展开消费（`{...getStyles('root')}`），不进任何依赖数组，所以稳定与否无关紧要，真正的稳定承诺在 varsResolver、setter 这类「会被下游 memo」的引用上；其三，不带 options 的调用在组件实现里占绝大多数（Button 五个节点全部是 `getStyles('xxx')` 形态），带 options 的少数（如 `getStyles('root', { active: ... })`）恰恰是状态相关的，两条路径的流量分布与缓存策略严丝合缝。

**这段代码教会我们什么**：缓存的正确位置有时不是「全局记忆」而是「本次计算会话」——识别出重复发生在「单次渲染内」而不是「跨渲染」，缓存的生命周期与失效问题就一起消失了。对照常见错误（把缓存挂到模块级或 useMemo 跨渲染持有），这里的方案以一次空 Map 分配的代价买走了全部正确性负担。

## 4. 走读总结：三个文件共享的工程基因

把三段走读合上，能提炼出这个内核反复出现的四个基因。**基因一：纪律结构化**——双参守卫（1.3）、undefined 剔除（2.3）、hooks 无条件调用（3.2）都是「把容易犯的错变成结构里不可能犯的错」。**基因二：引用稳定是一等契约**——useProps 的快路径、useUncontrolled 的稳定 setter、getStyles 渲染内缓存，全部在防「每帧新对象击穿 memo 链」，对应《10-性能设计与优化》第 3 节。**基因三：注释即档案**——三份源码的注释分别保存了消费者兼容性修正的动机、快路径优化的历史（「此前每次都新建 5~6 个对象」）、缓存决策的完整成本模型；本篇的许多结论若无这些注释，只能靠猜。**基因四：类型与运行时互为印证**——useProps 返回类型的 `-?` 收窄与运行时合并、PolymorphicComponent 交叉类型与静态件挂载、StylesApi 泛型与 classes 静态件，类型描述的正是运行时保证的事实。对想深读源码的读者，建议按本篇顺序（工厂 → props → 样式）读完后，对照《05-核心实现流程》的五个主题与《07-模块详解》第 9 节的递进路径，把 Button 或 Tabs 当作验证场——三个内核文件学到的每一个机制，都能在那两个组件里找到原样落地的身影。

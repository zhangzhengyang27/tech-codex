# 19 数据契约与示例集

> 项目：vitest-playground ｜ 版本：v1.2 ｜ 生成日期：2026-10-06 ｜ 依据：源码分析

本篇是三份"契约类"文档中的示例集：《03-接口设计》讲契约的设计哲学与字段语义（为什么三字段、错误四象限怎么划分），《15-接口全量参考》给全字段速查表与 16 章 56 课时索引（查字段、查课时用），本篇则提供**可以直接复制重放的完整实例**——每一个请求/响应对都对应真实课时与真实处理路径，每一份 Lesson 示例都取自 `src/pages/vitest-learn/data.ts` 的原文。读完 03/15 再读本篇，效果是"契约从定义变成手感"。示例的组织顺序遵循一条请求的生命：先看黄金路径（成功与断言失败），再看错误形态（429/超时/启动失败/400 家族），然后翻到数据侧看四种课时形态的完整 Lesson 实例与其装配产物对照，最后给一份"全字段拉满"的 RunResult 综合样例。

先立三条贯穿全篇的契约公理（出处见《05-核心流程》跨流程不变量，本篇不重复论证）：其一，请求体只有 `chapterKey / lessonKey / code` 三个字符串字段，其余一切执行要素由服务端按课时数据推导；其二，"运行了但失败"一律 HTTP 200 + `success:false`，"根本没运行"才动用 4xx/5xx，且所有 JSON 错误体仍是 `RunResult` 形态（`failResult` 构造：`{success:false, output, passed:0, failed:1}`）；其三，`success` 的唯一判据是"没有失败用例"，pending/skipped 不影响通关。

## 1. 黄金路径：一次成功的普通课时运行

以 `basics/first-test`（1.1 第一个测试用例）为例，用户把初始代码的三个注释任务补全后点击运行。请求：

````json
POST /api/run-vitest HTTP/1.1
Content-Type: application/json

{
  "chapterKey": "basics",
  "lessonKey": "first-test",
  "code": "function add(a, b) {\n  return a + b;\n}\n\ntest('add function should return correct sum', () => {\n  expect(add(1, 2)).toBe(3);\n});\n\ntest('add(0, 0) equals 0', () => {\n  expect(add(0, 0)).toBe(0);\n});\n\ntest('add(-1, 1) equals 0', () => {\n  expect(add(-1, 1)).toBe(0);\n});\n"
}
````

服务端处理序：字段校验通过 → `findLesson('basics','first-test')` 命中 → `limiter.acquire()` 获得槽位 → `buildLessonFiles` 产出 `{'lesson.spec.ts': code}`（无 grader，走普通分支）→ `resolveRunOptions` 得 `{coverage:true, benchmark:false}` → 沙箱写入 `vitest.config.js`（coverage enabled）+ `setup.ts` + `lesson.spec.ts` → spawn `node node_modules/vitest/vitest.mjs run --root <runDir> --reporter=json --outputFile.json=result.json --coverage` → 读 `result.json` 与 `coverage/coverage-summary.json` → `finally` 删除沙箱目录。响应（HTTP 200，字段按 `parseVitestJson` 的组装规则还原）：

````json
{
  "success": true,
  "output": "Test Results\n============\n\n📄 lesson.spec.ts\n  ✓ add function should return correct sum (2ms)\n  ✓ add(0, 0) equals 0 (1ms)\n  ✓ add(-1, 1) equals 0 (1ms)\n\n通过: 3  失败: 0  跳过: 0",
  "passed": 3,
  "failed": 0,
  "pending": 0,
  "tests": [
    { "name": "add function should return correct sum", "status": "passed", "duration": 2, "file": "lesson.spec.ts" },
    { "name": "add(0, 0) equals 0", "status": "passed", "duration": 1, "file": "lesson.spec.ts" },
    { "name": "add(-1, 1) equals 0", "status": "passed", "duration": 1, "file": "lesson.spec.ts" }
  ],
  "markers": [],
  "coverage": {
    "total": { "lines": 100, "statements": 100, "branches": 100, "functions": 100 },
    "files": [
      { "file": "lesson.spec.ts", "lines": 100, "statements": 100, "branches": 100, "functions": 100 }
    ]
  }
}
````

三个字段细节值得指出：`output` 的图标与耗时格式（`✓ 名称 (Nms)`）来自 `parseVitestJson` 第 171-181 行的映射规则，耗时四舍五入取整；`tests[].duration` 是未取整的毫秒原值，与 output 里的取整值可能相差 1ms，这不是 bug 而是两个消费者的精度需求不同；`markers` 成功时恒为空数组（不是 undefined）——因为 `parseVitestJson` 无条件返回该字段，前端 markers effect 拿到空数组正好走"显式复位"分支（见《18-代码走读实录》§3.3）。

## 2. 断言失败：passed/failed 断言明细与 markers 的生成

同一课时，用户把第二个用例写错（`expect(add(0, 0)).toBe(1)`）。响应骨架不变，关键差异在失败明细：

````json
{
  "success": false,
  "output": "Test Results\n============\n\n📄 lesson.spec.ts\n  ✓ add function should return correct sum (2ms)\n  ✗ add(0, 0) equals 0 (1ms)\n    AssertionError: expected 0 to be 1 // Object.is equality\n\n  ✓ add(-1, 1) equals 0 (1ms)\n\n通过: 2  失败: 1  跳过: 0",
  "passed": 2,
  "failed": 1,
  "pending": 0,
  "tests": [
    { "name": "add function should return correct sum", "status": "passed", "duration": 2, "file": "lesson.spec.ts" },
    { "name": "add(0, 0) equals 0", "status": "failed", "duration": 1, "file": "lesson.spec.ts", "line": 9 },
    { "name": "add(-1, 1) equals 0", "status": "passed", "duration": 1, "file": "lesson.spec.ts" }
  ],
  "markers": [
    { "line": 9, "message": "AssertionError: expected 0 to be 1 // Object.is equality" }
  ]
}
````

生成规则对照：`markers[].line` 取 vitest 报告的 `location.line`（缺失时兜底为 1）；`markers[].message` 取 `failureMessages[0]` 的**首行**且截断至 200 字符（`parseVitestJson` 第 196-199 行）；失败用例在 `output` 里缩进附带 `failureMessages[0]` 的**前 6 行**（第 189-195 行）——所以 output 里的失败详情最多 6 行，而 marker 只有一行，两者信息量不同。普通课时（非 TDD）下前端把 markers 下发给 Monaco，形成第 9 行的红色波浪线；此课时带 `coverage`（普通课时默认开），此处省略其值（结构与 §1 相同）。

## 3. 错误形态全集

### 3.1 429：排队已满

并发 2 满且排队 8 满时，`limiter.acquire()` 抛 `RUNNER_BUSY`，HTTP 层转 429：

````json
HTTP/1.1 429 Too Many Requests

{ "success": false, "output": "运行排队已满，请稍后再试", "passed": 0, "failed": 1 }
````

两个容易混淆的 429 来源要区分：本例是**应用内信号量**（`createRunLimiter(2,8)`）；另一个来源是 **nginx 限流**（每 IP 10r/m + burst 3，`limit_req_status 429`），其响应体是 nginx 的默认 HTML 而非 JSON——前端 `runVitest` 对非 2xx 统一合成 `服务端返回 429` 的失败结果，所以用户看到的文案相同，但排障时要分清是哪一层（《12-FAQ与故障排查》§3.3 的区分方法：应用内 429 只在排队真满时出现，nginx 429 在低频请求下也会触发）。

### 3.2 超时：60s 进程组击杀（HTTP 200 + success:false）

用户写了个死循环用例。60 秒后 `killGroup()` 以 SIGKILL 整杀进程组，超时分支构造失败结果：

````json
HTTP/1.1 200 OK

{
  "success": false,
  "output": "Vitest 运行超时（60s，可能有用例陷入死循环）:\nRUN v4.1.8 /Users/xx/vitest-playground/.vitest-runs/run-XXXX\n\n❯ lesson.spec.ts (0 test) [Run killed]\n...\n（此处为子进程输出尾部 2000 字符）",
  "passed": 0,
  "failed": 1
}
````

注意三点：状态码是 200——超时属于"运行了但没通过"；output 附带子进程输出**尾部** 2000 字符（`out.slice(-2000)`）供排障；`timeoutMs` 参数即便被调用方注入也被 `Math.min(timeoutMs, RUN_TIMEOUT)` 钳制在 60s，HTTP 协议层不暴露该参数。该形态有专门集成用例（`timeoutMs:2000` 缩短验证）锁定"输出含超时 + 目录零残留"两个断言。

### 3.3 启动失败与解析失败（同为 200 + success:false）

vitest 二进制不存在（未 `pnpm install`）时走 `child.on('error')` 分支：

````json
{ "success": false, "output": "启动 Vitest 失败: spawn node ENOENT\n（请确认项目已安装 vitest：pnpm install）", "passed": 0, "failed": 1 }
````

result.json 缺失且 stdout 截不出 JSON 时（罕见，多为环境异常）：

````json
{ "success": false, "output": "无法从输出解析测试结果，Vitest 输出:\n（尾部 2000 字符）", "passed": 0, "failed": 1 }
````

result.json 存在但内容损坏时：`测试结果解析失败，原始输出:\n` + 前 2000 字符。这三条与超时共同构成《15-接口全量参考》§3 表的序 8-12"运行了但失败"家族。

### 3.4 400 家族：非法 JSON、缺字段、旧契约、未知课时

四个变体共用 400 状态码，output 文案区分了具体环节：

````json
HTTP/1.1 400 Bad Request

{ "success": false, "output": "请求无效: 请求体不是合法 JSON", "passed": 0, "failed": 1 }
````

````json
{ "success": false, "output": "请求无效: 需要 chapterKey / lessonKey / code 三个字符串字段", "passed": 0, "failed": 1 }
````

````json
{ "success": false, "output": "未知课时: basics/not-exist", "passed": 0, "failed": 1 }
````

触发方式依次是：body 不是合法 JSON；body 为 `{}`、`null`、`[]` 或任一字段非字符串（含旧契约 `{files: {...}}` 形态——它没有三字段，被同一条件拦下，有专门测试锁定）；课时 key 在 `data.ts` 中寻址不到。这条链的全部检查发生在触碰文件系统与并发槽位之前（快速失败链语义见《18-代码走读实录》§1.3）。

### 3.5 非法文件名：当前源码实际走 500 出口

这是一个值得单独澄清的形态。文件名由服务端 `buildLessonFiles` 生成，正常情况下不存在"用户提交非法文件名"的入口；唯一可能触发 `sanitizeEntryName` 抛错的是课时数据被改出非法 `extraFiles` 名。按当前源码（`vitestServerRunner.ts` 第 302 行校验发生在 `handleRunVitest` 第 477 行 `runInSandbox` 调用**内部**，异常被第 479-481 行 catch 接住），其实际响应是：

````json
HTTP/1.1 500 Internal Server Error

{ "success": false, "output": "服务端错误: 非法文件名: ../evil.ts", "passed": 0, "failed": 1 }
````

即 **500 而非 400**——与《15》§3 表序 7（"runInSandbox 装配/执行抛意外异常 → 500 服务端错误: {message}"）一致；但《12-FAQ与故障排查》§3.6 曾将其表述为"三个 400 变体"之一，属文档间口径漂移，以源码行为为准（《12》§3.6 已于 2026-10-06 回刷修订为 500 口径，同源表述《01》§3.5、《04》§9、《07》§1.1、《08》§3-L3、《18》走读二亦已订正）。若未来把文件名校验提前到 handleRunVitest 的 try 之外，它才会变成 400——那是行为变更，需同步《15》表与测试。

### 3.6 bench 课时：Benchmark Results 模板

`coverage-advanced/benchmark` 课时的响应走 `parseBenchTable` 路径（无 JSON reporter，解析 vitest bench 默认表格）：

````json
{
  "success": true,
  "output": "Benchmark Results\n================\n\n  • 累加 1000: 0.002ms (345678 ops/s)\n  • 累加 100000: 0.089ms (11234 ops/s)\n",
  "passed": 2,
  "failed": 0,
  "tests": [
    { "name": "累加 1000", "status": "passed", "duration": 0.002 },
    { "name": "累加 100000", "status": "passed", "duration": 0.089 }
  ]
}
````

三个特征：output 以 `Benchmark Results` 开头（与 test 模板区分）；无 `coverage` 字段（bench 课时 `resolveRunOptions` 关闭 coverage）；`tests[].duration` 是 bench 表格的 mean 值——注意其单位语义存在已立项的混乱（前端按毫秒渲染，实际为亚毫秒小数，《13-技术债务与演进建议》问题 12，⚠️ 待确认 vitest 4.1.8 bench mean 列的精确单位）。bench 用例抛错时默认 reporter 不打印表格行，解析得 0 行即返回失败（`无法从输出解析基准结果`），该行为有测试锁定。

## 4. Lesson 数据对象：四种形态的真实实例

以下五份示例全部取自 `src/pages/vitest-learn/data.ts`（行号随文标注），是"数据侧契约"的完整样本。理解它们的钥匙是 ADR-007：形态由字段组合推导，没有显式 mode 字段。每份示例的建议读法是三步：先看字段组合推出了什么形态（`grader` 有无、`environment` 值、`benchmark` 值），再看装配产物对照（哪些文件会出现在沙箱目录里、各自的内容来源是谁），最后回到 §1-§3 想象这个课时点击运行后响应会长什么样——三步走完，"数据结构 → 装配行为 → 响应形态"这条因果链就在同一个课时上闭合了。这也是调试课程数据时最可复用的推理顺序：课时表现不符合预期时，先确认形态推导是否如你所想，再确认装配产物是否符合形态，最后才怀疑执行与解析环节。

### 4.2 TDD 模式：tdd-practice/tdd-fizzbuzz（第 4161-4246 行）

### 4.3 jsdom + TDD 叠加：react-testing/rt-greeting（第 4542-4598 行）

## 6. 示例的重放方法

所有请求示例都可以用 curl 重放，这是核对文档与源码是否漂移的最快手段。黄金路径的重放命令（本地 `pnpm dev` 或 `pnpm preview` 均可，端口 8000）：

````bash
curl -s -X POST http://localhost:8000/api/run-vitest \
  -H 'Content-Type: application/json' \
  -d '{"chapterKey":"basics","lessonKey":"first-test","code":"test(\"ok\", () => { expect(1 + 1).toBe(2); });"}' | python3 -m json.tool
````

把 body 换成 §3 各例的形态即可重放错误路径（429 需并发占满两个槽位再发 11 个请求，建议用 `for i in $(seq 1 11); do curl ... & done` 观察；nginx 429 的重放需在生产域名上 6 连发，见 `docs/deploy/runbook.md` 的验证命令）。响应示例的核对基线是 `tests/runner-security.test.ts` 的全链路用例与《15》§3 的错误码表——当三者（文档示例、测试断言、实际响应）出现不一致时，以测试断言为准并修订文档，这正是本套文档"与测试同源"的维护约定（《13》结尾的文档债务条款）。

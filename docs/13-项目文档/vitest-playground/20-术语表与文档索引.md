两个特别容易混淆的对照组值得在正文里点破。**第一组："运行器"与"runner.ts"**。`vitestServerRunner.ts` 是服务端运行器（Node 侧，真正执行测试）；`src/pages/vitest-learn/runner.ts` 是浏览器侧的请求客户端（fetch 封装 + Hook）。两个文件名共享 "runner" 一词纯属历史巧合，读到"运行器"三个字时默认指前者。**第二组：`.vitest-runs` 与 `.vitest-sandbox`**。前者是现行运行时目录根（RUNS_ROOT），后者是早期共享沙箱方案的遗留样例（已 gitignore、非运行时依赖）——《13》问题 3 建议本地删除它，接手者若看到两个目录并存，不要把后者当参考实现。另有三组"近义不同义"：`grader`（可见测试）与 `hiddenGrader`（隐藏测试）的区别在于是否进入 HTTP 响应；`environment: 'jsdom'`（字段名）与 happy-dom（实际执行的模拟 DOM 实现）是"声明类别"与"执行实现"的错位；`RunResult`（接口契约）与 `TestResult`（页面状态）的分界在于 status 字段的归属。

使用这张术语表还有一个正确姿势：不要把它当字典逐条背，而是当"歧义探测器"用。读其它篇目或源码注释时，凡是遇到一个词与你的理解有微妙不符（最常见的是"装配"到底包含不含配置写入、"判题器"到底是不是一个模块），先回到这里对一次口径，再决定是否继续往下读——本项目的多数术语都有一条"定义 → 源码锚点 → 详述篇目"的三级追溯链，任何一处存疑都可以在两分钟内落到具体代码行。反过来，如果你在源码注释里发现了一个本表未收录的行话（例如某次新提交引入的新概念），按第 4 节的维护约定把它补录进来，注明出处与首次出现的位置，让后来者不必重走你的理解弯路。

维护这张索引时有三条操作规则。其一，**新增文件即登记**：任何新提交引入的源文件（或被删除的文件）都应在这张表里增删对应行，引用篇目写"实际讲过它的篇目"而非"理论上应该讲的篇目"——空挂的引用比没有引用更误导。其二，**篇目号是稳定标识**：文件可以改名，篇目编号不回收复用；若某篇被拆分或合并，在原编号位置留一行指向新篇目的说明。其三，**重叠度是健康信号**：枢纽文件被多篇覆盖是正常的（多视角才能覆盖多职责），反而要警惕的是某个源文件在右列完全消失——那通常意味着文档集出现了盲区，应该在下次修订时补写或并入邻近篇目，而不是放任"代码先行、文档永久滞后"。

## 3. 按任务阅读路径

路径的设计原则是"最短闭环"：每个任务给出首读篇（建立正确心智）、操作篇（动手时对照）、验收篇（收尾门禁），以及一条"别踩"的提醒。所有路径的公共前置是《00-项目总览》——它足够短，且术语与本篇对齐。

### 路径 A：加一个课时（普通或 TDD）

首读《11-扩展开发指南》SOP-1/SOP-2（操作步骤与 grader 编写约定）与《04-数据模型》§1.2（Lesson 字段语义）；动手时对照《19-数据契约与示例集》§4——四种形态各有一份真实课时实例，新课时照着最近形态的实例抄字段结构最不容易漏；收尾跑 `pnpm check:lessons`（solution 必须实测通过）与 `pnpm test`（lessons.test.ts 校验 key 唯一性与 code||grader 非空）。两个提醒：其一，纯空白 grader 等于没有 grader（trim 守卫），不要用空白字符串"占位"；其二，extraFiles 文件名过白名单，扁平名以外一律被拒。若要加的是**新形态**（而非新课时），升级为先读《16》ADR-007 理解形态推导哲学，再走《11》SOP-4 的扩展三道门。

### 路径 B：调判题规则（改既有课时的 grader/hiddenGrader）

首读《07-模块详解》§4（判题器三角色协作）与《05-核心流程》流程二（TDD 批改时序，理解 hidden 失败事实会出现在 output 但源码不会泄露）；操作时对照《19》§4.2 的 tdd-fizzbuzz 范本——hiddenGrader 的写法范式（全量遍历防查表、边界补充用例）都在这个实例里；收尾四绿门禁，特别注意 `pnpm check:lessons` 会用新 grader 实测原 solution，若把规则调严到 solution 都过不了，CI 会替你拦下。提醒：TDD 课时改判题不影响前端（markers 本就被丢弃），但会改变结果面板逐用例列表的行数——有 UI 截图类验收（gui-test-screenshots）时需同步。

### 路径 C：排查一次运行失败

## 4. 文档集的维护约定

21 篇文档自身也需要防漂移，以下约定沿袭《13》结尾的条款并扩展到新五篇。第一，**版本与日期**：每篇头部元信息的版本号与生成日期表示"该篇最后一次对源码核实的时间"，源码行为变更时必须修订对应篇目并更新版本——历史上已发生过一次口径漂移（《12》§3.6 曾称非法文件名为 400 变体，源码实为 500 出口，已于 2026-10-06 按《19》§3.5 的源码口径回刷修正），这类不一致一经发现应立即在两处同时修正。第二，**测试是最高事实源**：文档、测试断言、实际行为三者冲突时，以测试为准修订文档，并以测试名为引用锚点（如"「旧 files 形态请求被 400 拒绝」用例"）。第三，**重复内容用引用不用复制**：跨篇的机制描述只在一篇展开（如并发语义只在 07 §1.6、防篡改只在 08 §3-L2），其余篇目用"见《0X》"——新五篇严格遵循了这一分工（16 只写"为什么"、17 只写"依赖评估"、18 只写"逐行走读"、19 只写"实例"、20 只写"索引"）。第四，**无法确认的事实标注 ⚠️ 待确认**，禁止用推测填充（现有标注集中在 bench 单位、TS6 行为、antd 主题接入等处），接手者处理完一条就应删除对应标注。最后，本篇作为索引，其阅读路径与术语条目应随篇目增删同步维护——当第 22 篇出现时，先来这里登记，再动笔写正文。

# 03 - 接口设计

> 项目：运营搭建平台（vue3-course） ｜ 版本：v1.0 ｜ 生成日期：2026-10-05 ｜ 依据：源码分析

## 1. 接口组织与命名约定

两个服务端各自持有一份集中式路由表：`packages/work-server/src/router.ts`（565 行，约 60 个端点）与 `packages/portal-server/src/router.ts`（63 行，9 个端点）。命名约定严格二分：

- `/api/post/*` —— 一切**写操作与动作**（create/update/delete/publish/revert/query 等虽是读语义的查询也归 post，因为带请求体）；
- `/api/get/*` —— 一切**读操作**（列表、详情、状态）。

portal 侧则是 `/api/portal/*`（访客可触达）与 `/api/log/push`（前端日志）。每个端点在路由表里就地挂中间件链，典型形态是 `限流 → 认证 → 权限码 → 控制器`。所有业务响应统一 `{ data, success, message }`（`packages/work-server/src/types.ts` 的 `MyAPIResult`），HTTP 状态码只表达传输层事实：401 未登录、403 无权限/无令牌、404 资源不存在、429 限流、503 服务不可用。

## 4. 认证、鉴权与访问控制的三层模型

接口安全的完整链路是三层叠加，各自独立失效即各自兜底：

1. **认证（你是谁）**：登录成功签发 JWT（HS256，`JWT_SECRET`，TTL 1h，`config.ts`），写入 HttpOnly + SameSite=Lax cookie `online-status`。`slidingSessionRenewal` 中间件在剩余寿命不足一半时重签全时长 token（活跃用户不被强踢）；`JWT_SECRET` 生产缺失直接拒绝启动。`parseOnlineUserData`（`packages/work-server/src/controller/user.ts`）是所有认证读口的统一入口。
2. **权限码（你能干什么）**：`requirePermission(code)`（`packages/work-server/src/middleware/rbac.ts`）查 `checkUserPermission`（user → user_role → role_permission → permission 四表联查，`packages/work-server/src/service/rbac.ts`），无码 403。权限码按"资源:动作"命名（如 `dashboard:publish`），种子见 `packages/init-database/src/sql/insert_role_permission_*.sql`（admin 全量、editor 19 项、viewer 只读）。
3. **资产级访问控制（这条数据你能不能碰）**：读走 `visibility.ts` 的 `isVisibleTo`/`visibilityWhere`（本人/租内公开/同部门/无主），写走各 service 的 `check*Ownership`（仅 owner，无主首写认领）。访客侧则完全不同：portal 的令牌门 `access-gate.ts` 校验 cookie 或表单令牌，取数通道的最终裁决是 prod schema 冻结的 `publishedDataSources` 白名单——**匿名访客的数据能力与数据源可见性无关**，只与发布白名单有关。

另有两层横切：CSRF 的 `sameSiteGuard()`（状态变更请求同源校验，跨域白名单 `CSRF_ALLOWED_ORIGINS`）与两级限流——IP 桶（sign-in/sign-up/token-verify/portal-query/front-log，`packages/server-kit/src/http-security.ts` 的 `rateLimit`）与用户桶（AI/codegen 的 `rateLimit` + `dailyQuota` 双档，`packages/work-server/src/middleware/quota.ts`），计数后端可切 MySQL（`RATE_LIMIT_STORE=mysql`，两进程共享 `rate_limit_bucket` 表）。

## 5. 错误处理约定

服务层错误不抛出到传输层，而是被 `packages/work-server/src/util/error-message.ts` 的 `internalFailure(err, module)` 收敛为用户可读文案并打服务端日志（原始错误不外泄——报错常含主机/账号，出码快照失败时只落布尔标记也是同一原则）。可预期的业务失败以 `success:false + message` 返回 200；不可预期异常（如库层故障）在 portal 侧渲染友好 503 页（`packages/portal-server/src/controller/dashboard.ts` 37-46 行），绝不裸 500。限流返回 429 并带 `Retry-After`。所有"fail-fast"场景（密钥缺失、REQUIRE_DB 探活失败）集中在启动期，不在请求期。

## 6. 核心接口示例

### 6.1 发布到生产：`POST /api/post/dashboard/stage/push`

请求：

```json
POST /api/post/dashboard/stage/push
Content-Type: application/json
Cookie: online-status=<JWT>

{ "uuid": "9f1c...", "stage": "prod" }
```

处理链（`packages/work-server/src/service/dashboard-stage.ts` 的 `pushDashboardStage`）：① `checkDashboardOwnership` 确认仅所有者；② stage=prod 时取 pre 快照（prod 复制的就是 pre），`findPageMethodsGateViolation` 校验"公开 + 含页面方法"则拒绝（提示改用令牌访问）；③ 注入实时 `accessMode`（令牌不进产物）；④ `runTransaction` 内 `nextProdVersion` 行锁自增版本、`upsertStageInfo('prod', ...)`、自动打 `source='publish'` 快照。

响应：

```json
{ "data": { "stage": "prod", "uuid": "9f1c...", "currentVersion": 3 },
  "success": true, "message": "成功发布到环境prod（v3）" }
```

### 6.2 访客取数：`POST /api/portal/dashboard/query`

```json
POST /api/portal/dashboard/query
{ "uuid": "9f1c...", "dataSourceId": "ds-88..." }
```

处理链：portal 侧先过令牌门（token 模式无有效 cookie 即 403 `{message:"缺少或无效的访问令牌"}`）→ 携 `x-internal-token` 转发 work-server → `queryPortalDashboardData`：读 prod 行不存在则"看板不存在或未发布"；`getProdDataSourceWhitelist` 校验数据源在发布白名单内（不在则"数据源不在该看板发布白名单内"）→ `queryPublishedDataSource` 以 `queryParams` 固定空对象防参数注入 → 统一查询引擎解密配置、按 type 分派查询、`normalizeData` 归一化后返回 `{ data: [...rows], success: true }`。整个链路对访客只暴露 `uuid + dataSourceId`，主机、口令、SQL 全部留在服务端。

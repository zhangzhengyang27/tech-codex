# 19 - 数据契约与示例集

> 项目：运营搭建平台（vue3-course） ｜ 版本：v1.2 ｜ 生成日期：2026-10-06 ｜ 依据：源码分析

本篇给出 10 个核心接口的完整请求/响应示例，覆盖登录、看板草稿的保存与读取、三阶段发布、数据源查询代理、数据库连接等高频契约。示例 JSON 依据类型定义（`packages/shared/src/schema/index.ts`、`packages/work-server/src/types.ts`）与 controller/service 的实际字段构造，**凡非真实值一律为示意**，标注方式：字段语义说明写在注解里，值本身可读出示意的（如 uuid 片段、时间戳）不再逐一打标。通用约定先复述一遍（详见《03-接口设计》第 1 节与《15-接口全量参考》第 0 节）：写与动作走 `/api/post/*`、读走 `/api/get/*`；响应统一 `{ data, success, message }`（`packages/work-server/src/types.ts` 的 `MyAPIResult`）；可预期业务失败一律 HTTP 200 + `success:false`，401/403/404/429 只表达传输层事实；登录态是 HttpOnly cookie `online-status`（curl 场景用 `-c`/`-b` 维持 cookie jar）。示例统一假设管理端在 `http://127.0.0.1:8001`、门户在 `http://127.0.0.1:6001`。

## 0. 读示例前先懂的五个契约常识

**响应包络是统一的**。两个服务端的所有业务接口都返回 `{ data, success, message }` 三键结构，类型定义在 `packages/work-server/src/types.ts` 的 `MyAPIResult`。这意味着调用方的错误处理可以完全模板化：先判 HTTP 状态码（只可能是 200/401/403/404/429/503 六种），再判 `success` 布尔，最后把 `message` 直接展示给用户——它被 `internalFailure` 收敛过，永远是用户可读文案而非技术细节。`data` 在失败时通常是 `null`（查询类接口给空数组），调用方不要依赖"失败时 data 的部分字段"这种约定，它不存在。

**字段命名是"库下划线、接口驼峰"**。数据库列是 `modify_time`/`create_time`/`owner_uuid`/`schema_json`（下划线蛇形），接口层统一下发驼峰 `modifyTime`/`createTime`/`ownerUuid`/`schemaJson`——转换发生在 controller/service 层，不是序列化库的自动行为，所以个别历史接口可能存在漏改（`⚠️ 待确认`：以 15 篇逐端点表格为准）。写请求同理：前端传 `schemaJson`，落库进 `schema_json` 列。

**认证是 cookie 而非 header**。除 portal 的取数通道外，全部接口的登录态是 HttpOnly cookie `online-status`，没有任何 Bearer token 或自定义鉴权头的入口。这决定了两件事：跨域部署必须解决 cookie 的 SameSite/secure 问题（而不是改用 header 令牌）；服务间调用（portal → work-server）不共享登录态，靠的是独立的 `x-internal-token` 共享密钥——它的语义是"我是内网通道"而不是"我是某个用户"，终点裁决完全依赖 prod 白名单。

**时间与软删是隐式契约**。所有主表都有 `create_time`（DEFAULT CURRENT_TIMESTAMP）与 `modify_time`（ON UPDATE 自动更新），接口层只读不可写；删除一律是软删（status=0），回收站恢复把 status 置回 1——发布状态不随恢复回滚（restore 只动草稿行）。写用例或脚本时不要假设 DELETE 之后行不存在，它只是不可见。

**分页与列表是固定形状**。列表端点统一接受 `pageNum`/`pageSize`（默认 10，`packages/work-server/src/util/pagination.ts` 的 `clampPage` 钳制非法值与上限，四条线共用同一个上限），响应统一为 `{ list, total, pageNum, pageSize, keyword? }`；看板列表另有 `visibility` 过滤与 `scope=all|mine`（"全部可见 | 我拥有的"切换）。分页是兜底而非优化——列表行可能带大字段（schema 全文），见 10 篇第 3 节的量级警告。

## 1. 登录：POST /api/post/account/sign-in

请求（IP 桶限流 20 次/10 分钟，`packages/work-server/src/router.ts` 153 行注册点）：

````sh
curl -s -c /tmp/cookies.txt -X POST http://127.0.0.1:8001/api/post/account/sign-in \
  -H 'Content-Type: application/json' \
  -H 'Origin: http://127.0.0.1:8001' \
  -d '{"username":"admin001","password":"88888888"}'
````

成功响应：

````json
{
  "data": { "username": "admin001", "uuid": "u-1001 ※ 示意" },
  "success": true,
  "message": "登录成功"
}
````

同时 Set-Cookie 下发 `online-status`（HS256 JWT，HttpOnly + SameSite=Lax，TTL 1 小时；curl 已由 `-c /tmp/cookies.txt` 接住）。失败响应（HTTP 仍 200）：

````json
{ "data": null, "success": false, "message": "登录失败，用户名称或密码错误" }
````

要点：① 本项目带 cookie 的 POST 必须带同源 `Origin`（或 `Sec-Fetch-Site`），否则被 `sameSiteGuard` 以 403「跨站请求已被拒绝」拦截——curl 加 `-H 'Origin: ...'` 即可通过（08 篇第 8 节）；② 失败文案已回源核实（`packages/work-server/src/service/user.ts` 45/58 行）：无此用户与密码错误统一返回「登录失败，用户名称或密码错误」，参数缺任一项也是同文案——这是防用户枚举的常规做法；③ 401 只出现在未登录访问受保护端点时，登录接口本身不返回 401。

成功响应：

````json
{
  "data": { "stage": "prod", "uuid": "9f1c2a34-5b6d-4e7f-8a9b-0c1d2e3f4a5b", "currentVersion": 3 },
  "success": true,
  "message": "成功发布到环境prod（v3）"
}
````

三个典型失败响应（HTTP 200，文案即原因）：

````json
{ "data": null, "success": false, "message": "请先发布到预发环境" }
{ "data": null, "success": false, "message": "该看板含 2 个页面方法（refresh、track），页面方法会以脚本形式在访客浏览器执行，在独立沙箱上线前不允许公开访问；请改为「令牌访问」，或先移除方法体。" }
{ "data": null, "success": false, "message": "发布到环境prod失败" }
````

要点：① test 阶段从组件 `dataBinding` 收集数据源 id 冻结白名单 `{id,name,type}` 进 `publishedDataSources`，config 永不进产物（`packages/work-server/src/service/dashboard-stage.ts` 42-52 行）；② pre 复制 test、prod 复制 pre，跳阶段被拒；③ prod 在事务内行锁自增版本并自动打 `发布 v{n}` 快照，重复点击产生连续版本不重号；④ 发布后又给看板绑了新数据源的，必须重走 test → pre → prod 才会进白名单（12 篇第 5 节高频条目）。公开闸门文案已回源核实（`packages/work-server/src/util/page-methods-guard.ts` 71-76 行）：方法名列举最多 5 个（超出加"等"），上文第二条中的"2 个/refresh、track"为示意值。配套查询：`GET /api/get/dashboard/stage/status?uuid=…` 返回 `{ data: { test: {currentVersion, modifyTime}, pre: null, prod: {currentVersion, modifyTime} }, success: true }`（未发布的阶段为 null）。

## 8. 访客取数通道：POST /api/portal/dashboard/query

匿名可达（限流 300 次/min/IP + 令牌门）。这是 portal 转发 work-server 的访客取数入口：

````sh
curl -s -X POST http://127.0.0.1:6001/api/portal/dashboard/query \
  -H 'Content-Type: application/json' \
  -d '{"uuid":"9f1c2a34-5b6d-4e7f-8a9b-0c1d2e3f4a5b","dataSourceId":"ds-88a1"}'
````

成功响应（结构同第 7 节，但**参数不可传**——queryParams 在终点写死空对象）：

````json
{ "data": [ { "date": "2026-10-01", "pv": 12000, "uv": 4500 } ], "success": true, "message": "查询成功" }
````

失败响应（按拦截层排列）：

````json
{ "data": null, "success": false, "message": "缺少或无效的访问令牌" }
{ "data": null, "success": false, "message": "数据源不在该看板发布白名单内" }
{ "data": null, "success": false, "message": "数据查询通道未配置（INTERNAL_TOKEN）" }
{ "data": null, "success": false, "message": "数据查询暂不可用，请稍后重试" }
````

要点：① 令牌模式下 cookie（`portal_access_<uuid>`）或 URL `?t=` 任一通道通过即放行（`packages/portal-server/src/util/access-gate.ts`，curl 可加 `-d` 后再带 `?t=<token>` 验证免 cookie 通道）；② 四条失败文案分别对应令牌门、双层白名单校验、通道未配置（fail-closed）、work-server 库层故障（该文案刻意中性——响应要出公网，18 篇 2.3 节）；③ 访客对数据源的全部能力就是"uuid + dataSourceId"两个参数，其余一切（连接、SQL、参数）都在服务端固化。

## 10. 物料/页面线配套的两个高频契约（速览）

**CSV 上传** `POST /api/post/datasource/upload`（multipart，权限码 `datasource:create`）：`curl -b /tmp/cookies.txt -F "file=@data.csv" http://127.0.0.1:8001/api/post/datasource/upload`，响应 `{ "data": { "fileId": "… ※ 示意" }, "success": true }`，fileId 随后填进 CSV 数据源的 config（04 篇 4.2 节）。**出码下载** `POST /api/post/codegen`（登录 + 用户桶配额 30/min + 100/日）：请求 `{ "uuid": "…" }`，响应是 zip 二进制（`Content-Disposition` 附件），curl 加 `-o dashboard.zip` 接住；数据源只带 500 行内快照（`resolveCodegenSnapshot`），失败回落 mockData 并只落布尔标记。

## 12. 错误响应的分层语义（汇总）

把本篇各接口出现过的错误响应归拢成一张心智图，排查时先按文案归层再往下查——这与 12 篇第 3 节的决策树一致，但这里是契约视角。第一层是**认证层**（401）：`requirePermission` 与 `filterLoginStatus` 在登录态缺失/过期时返回「暂无权限，请先登录」，cookie 存在仍 401 通常是服务器时间漂移或 JWT_SECRET 变更。第二层是**横切层**（403）：`sameSiteGuard` 的「跨站请求已被拒绝（同源校验未通过）」与限流的 429（带 `Retry-After` 头）——它们与权限无关，任何端点都可能命中。第三层是**权限码层**（403）：「缺少权限: {code}」的 message 会回显具体权限码，直接对照种子矩阵查角色绑定。第四层是**资产层**（HTTP 200 + success:false）：归属（「只有所有者可以…」）与可见性（「暂无权限访问该看板」）两层文案刻意不同——前者说明资源对你存在但不归你写，后者连存在性都不泄露（08 篇第 5 节）。第五层是**业务规则层**（HTTP 200 + success:false）：三阶段的「请先发布到…」、白名单的「数据源不在该看板发布白名单内」、公开闸门的方法体提示——文案即规则本身。第六层是**服务与网络层**（404/503/200+中性文案）：portal 的 404 友好页、库层故障的 503 页、转发链路的「数据查询暂不可用」——这一层刻意模糊，因为响应可能出公网。联调时遇到"系统繁忙"级别的文案，正确的下一步永远是查服务端 stdout 的模块前缀日志，而不是重试。

## 13. 联调检查单

拿本篇示例联调时按序自检：① cookie jar 是否带上（401 先查 `online-status`）；② POST 是否带同源 `Origin`（403 跨站文案即此）；③ 权限码是否与角色匹配（403「缺少权限： xxx」——自助注册默认 viewer，只读）；④ 写操作是否是所有者（403「只有所有者可以…」）；⑤ 访客链路三道门顺序——令牌门 → prod 白名单 → queryParams 固定空，任何一道失败文案见第 8 节；⑥ 时间字段以服务端 `modify_time`（ON UPDATE 自动维护）为准，接口层驼峰下发。更多端点的参数级速查见《15-接口全量参考》，鉴权模型见《08-安全与权限设计》。

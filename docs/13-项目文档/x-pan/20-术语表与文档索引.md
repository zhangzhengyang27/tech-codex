## 0. 本文定位

本文是全文档集（00-20 共 21 篇）的收官件，承担三个检索职能：**术语表**把散落在各篇的项目特有词汇收进一处（每个术语给定义、源码落点与深读篇目）；**反向索引**回答"我手上有一个源码文件，该读哪几篇"——它与各篇目录的"篇目 → 内容"正向阅读互为补集；**任务阅读路径**回答"我要做某件事，最少读哪几篇、按什么顺序"。使用本文的正确姿势是按需跳转而非通读：术语表在首次遇到陌生词时查，反向索引在读码迷路时查，任务路径在开工前查。三条路径的写法刻意保持"篇目引用 + 具体动作"的密度差——动作是可以立刻执行的（打开某文件第几行、跑某条命令），篇目引用是纵深材料（理解为什么这样动），先动作后纵深能保证路径在最短时间内产生第一次有效进展。全文档集以源码为唯一事实来源，本文标注的篇目引用在源码演进后可能滞后，发现冲突以代码为准并回改对应篇目。

术语使用中的三个易混点值得单独澄清。**"物理文件"不等于"文件内容"**——它是 `x_pan_file` 表里的一行元数据，字节本体在 MinIO/本地盘，所以"删物理文件"通常是删记录 + 删对象两步且后者受引用计数保护。**"clientId"不是设备序列号**——它由客户端自行生成并长期稳定，同一台设备重装 App 可能变化（移动端持久化在 Keychain/Keystore，Web 清 Cookie 即变化），"设备管理"页面的记录以登录时上报为准。**"断点续传"与"秒传"是两个正交机制**——前者解决"传了一半怎么办"，后者解决"别人传过没有"，一个 5GB 文件完全可能"秒传命中"而从未触发分片，也可能"秒传未命中 + 断点续传"组合出现。另有一个高频误读需要预防：把"回收站"理解为独立存储位置。回收站不是另一块存储——文件进入回收站只是 `x_pan_user_file` 上 `del_flag` 与 `delete_time` 两个字段的变化，物理对象原地未动，配额照计；所谓"彻底删除后释放空间"释放的是"不再被任何逻辑记录引用的物理对象"，若同一物理文件仍被秒传复用，空间不会减少。理解了这一点，"删除后马上上传大文件提示配额不足"就不是 bug 而是设计的必然结果。

## 3. 按任务阅读路径

### 3.1 修复上传类 bug

最少五步：先读《05-核心流程》流程一建立"先问、再传、后合"的分段心智模型，用任务面板状态把 bug 定位到段（解析中/上传中/合并中）；再查《12-FAQ与故障排查》第 4 节上传表与第 5 节决策树——413、锁竞争繁忙、断点续传不跳片、99% 卡住四个高频现象都有现成根因；涉及服务端行为读《18-代码走读实录》走读一（分片锁与合并判定）与走读二（composeObject 与慢路径），涉及客户端读《10-性能设计与优化》第 1 节（5MB 强制、并发 3、函数式 headers 的理由）；改代码前过《11-扩展开发指南》"动代码前五问"（identifier 是否进存储路径、是否绕过唯一键幂等）；最后按《09-测试与质量保障》第 2 节的 `uploadWithChunkTest` 范式补回归用例——注意独立线程与测试事务可见性的坑。定位阶段还有两个实用抓手：服务端日志按 `X-Pan-Trace-Id` 一次 grep 到位（《12》第 1 节的排障走查），浏览器 Network 面板看最后失败的请求落在 sec-upload/chunk-upload/merge 哪一段。修 bug 时最容易踩的两条红线：不要给分片接口加"方法级 synchronized"（会把不同文件的并发压成串行，正确做法沿走读一的键粒度锁扩展），不要把 `uploadedChunks` 的判定改成"客户端本地计数"（服务端连续性校验是防坏文件的最后防线）。若 bug 指向"多实例部署后才出现"，直接跳《13-技术债务与演进建议》D12，那是三处 JVM 锁的已知边界。

### 3.2 接入新的存储介质

按《11-扩展开发指南》SOP-5 为主线：OSS/FastDFS 是"解注释 + 补配置"的接线活，自研介质（SFTP/Azure Blob 等）走"新模块 → 实现 `StorageEngine` 六操作 + 继承模板 → `@ConditionalOnProperty` 装配"的完整流程。动工前必读三篇打底：《16-决策记录ADR》ADR-003 理解抽象的收益与代价（接口是按文件网盘形状设计的，不支持服务端合并的介质要自行降级）；《04-数据模型》1.2 理解 realPath 与桶规划（存量对象迁移是切换的真实前置）；《10-性能设计与优化》第 3 节理解下载路径的 50MB 路由与预签名语义（`replaceEndpoint` 的签名绑定陷阱在《18》走读二有行级说明）。落码时记住两条硬约束：MinIO 与 Local 双实现必须同时落（CI 与本地模式走 Local 引擎，`application-ci.yaml` 强制关闭 MinIO，单实现等于让一半环境坏死）；熔断要对照 `MinIOStorageEngine.doStore` 的 `@CircuitBreaker + @Retry` 给新引擎等价保护（ADR-009）。配置面遵循《14》的"三份同源"原则（运行时 yaml/打包模板/CI yaml 同步改）。完成后必做：存量迁移工具验证（《13》D11 的 `StorageMigrationRunner` ⚠️ 待确认完成度，实测前不得用于生产），以及《10》第 7 节预留的预签名 PUT 直传评估——若新介质支持服务端合并与预签名，把这两个能力接进 `FileController` 的可选注入路径，业务侧才能享受与 MinIO 同级的性能形态。

### 3.3 上线前检查

以《06-部署运行》第 8 节清单为骨架（数据库脚本、七个密钥、MinIO 三桶、Nginx 两 location、健康探针、CI 绿、雪花 workerId），补三篇的专属视角：《14-配置与环境详解》第 4 节三环境差异矩阵逐行核对（profile、密钥来源、中间件寻址、文档开关），并用三个"探针"自检环境纯度（`/doc.html` 应关、yaml 无明文地址、错误响应不泄堆栈）；《08-安全与权限设计》第 7 节密钥治理（`.env` 权限收紧、`run-local.sh` 不落生产机、AES 密钥视同不可逆资产）；《12-FAQ与故障排查》第 2 节启动失败三段判别法（静态块/数据源/compose 编排对应三个责任边界）。有几项容易被清单遗漏的核对点在此强调：`pan.storage.minio.public-endpoint` 必须是浏览器可达的公网入口（302 直链下发给的就是它）；Prometheus 的五条 MinIO 告警规则加载后应在 Grafana 面板确认可见（没有告警的熔断等于没有熔断）；限流四 scope 阈值若按业务调整过，确认打包模板同步（《14》第 5 节的变更规程）。上线后四步验证：health、登录、上传小文件、打开分享链接——分别验证密钥、会话链路、存储链路、`XPAN_SHARE_HOST`。

### 3.4 排查分享越权/泄露类问题

先立威胁模型再查代码：《08-安全与权限设计》第 3、4 节给出分享域的全部防线位置（归属校验、保险箱隔离、Share-Token 与登录 token 隔离、防爆破），第 5 节给失效三态语义；对照《05-核心流程》流程三确认"创建 → 提取码 → 浏览/转存/下载"每一步的校验点。具体疑点按越权面大小排序排查：保险箱文件是否可经分享流出（`checkShareFileOwnership` 在创建时拒绝 parentId=-2，核对 `ShareServiceImpl` 现状）；匿名下载是否绕过登录（`/share/file/download` 设计为免登录 + Share-Token，核对 `@NeedShareCode` 注解在位，同时确认 Controller 未被移出 `controller/` 子包——包结构即鉴权边界，见 ADR-001）；ptoken 是否可跨文件复用（`previewStream` 比对 token 内 fileId 与请求 fileId 一致）；转存是否校验了目标配额（`ShareSavePO` 路径走 `saveUserFile` 的配额校验）；移动端 shareToken 存储是否按分享隔离（《13》D16 ⚠️ 待确认项，后端 `ShareIdUtil` 与归属校验会兜底拒绝错配 token，风险主要是体验而非越权）。真实报文对照《15-接口全量参考》第 4 节与《19-数据契约与示例集》第 8-9 节。定性结论回到《16-决策记录ADR》ADR-006 理解凭证设计边界——分享域的一切"看似过严"的拒绝都是 ADR 代价侧的刻意选择，排查的终点往往是确认"这是防线在工作"而不是"这里有漏洞"。

## 4. 结语：文档集的使用契约

21 篇文档各自的最佳打开方式已在《00-项目总览》第 6 节按角色给出，本文最后补一条**维护契约**：本套文档的生命力取决于三件事的同步纪律——源码变更时先改对应篇目再合码（尤其"四大件"与 `db.sql`）；发现漂移时在涉及篇目加 ⚠️ 标注并回溯根因（本套新增的五篇已示范两处修正：《19》对 sec-upload 入参与响应语义的校准、《16》对 WebDAV 能力边界的收窄）；新增决策按《16》的五段结构落 ADR 并同步 `DEV_GUIDELINES.md` 红线。术语表会随业务膨胀、索引会随重构漂移，但"以源码为准、标注待确认、代价写明处"这三条原则不变——它们也是这套代码库本身写给维护者的三条承诺。

# 00 项目总览

> 项目：xiaoye-admin-react ｜ 版本：v1.0 ｜ 生成日期：2026-10-06 ｜ 依据：源码分析

## 1. 项目定位与目标用户

xiaoye-admin-react 是一个基于 **Vite + React 19 + Tailwind CSS v4 + Ant Design 6** 的企业级后台管理系统脚手架（`package.json` 中描述为 "Xiaoye Admin React - Vite + React + Tailwind CSS + Ant Design 后台管理框架"）。它不是某个具体业务系统的残片，而是一套**面向二次开发的后台框架**：内置了登录鉴权、动态路由与菜单权限、按钮级权限、多套布局、主题定制、国际化、请求层封装、MSW 本地 Mock、OpenAPI 代码生成以及一整套演示业务页面。开发者拿到代码后，替换掉 Mock 数据、接上真实后端，即可在其上快速搭建自己的管理系统。

项目由原 `Hooks-Admin-Pro-master`（Xiaoye-Admin）全量移植而来（见 `README.md` 第七节），原项目使用自研组件库 `@xiaoye-react/ui`，本项目统一改为 **Ant Design 6 + Tailwind CSS**，并且**全程不使用 Less**——所有样式文件均为原生 `.css`，原子化样式由 Tailwind CSS v4 承担，组件样式由 antd 的 CSS-in-JS 运行时承担（`README.md` 开篇明确声明，`vite.config.ts` 末尾注释再次强调）。

**目标用户**分为三类：

1. **前端开发者**：以本框架为起点开发中后台系统，关注请求层、路由权限、组件封装等基建能力；
2. **技术负责人**：评估技术选型与工程化方案（无 Less 的样式体系、Tailwind 与 antd 共存、OpenAPI 契约先行、MSW 契约级 Mock）；
3. **运维/部署人员**：关注 `nas-deploy/` 提供的 NAS + VPS + frp 内网穿透部署链路，以及 history 路由、PWA 的服务器配置要求。

**演示形态**：项目以 `pnpm build:mock` 构建的"演示构建"（production + MSW 浏览器端 Mock）部署于 `admin-react.zhangzhengyang.com`（`nas-deploy/README.md`），无需真实后端即可完整演示登录（admin / 123456）、权限、CRUD 等全部页面。

### 1.1 技术组合的工程含义

这套"React 19 + antd 6 + Tailwind 4 + Vite 8"的组合并非流行词拼盘，每一项都服务于"脚手架"这一定位。React 19 提供 `lazy/Suspense` 的成熟语义与 `useSyncExternalStore` 等底层能力（后者被 `OfflineBanner` 用于订阅网络状态）；antd 6 以 CSS-in-JS 运行时承担组件样式，配合 `@ant-design/cssinjs` 的 `layer` 能力解决了与原子化 CSS 的优先级冲突，使两套样式体系可以无 `!important` 共存；Tailwind v4 的 CSS-first 配置（`@theme` 设计令牌 + 官方 Vite 插件）消灭了传统 v3 的 `tailwind.config.js` 与 PostCSS 链，让"设计令牌"直接写在 `src/styles/global.css` 里并被工具类自动消费；Vite 8 则通过 `import.meta.glob`、`define` 注入、插件开关体系支撑了动态路由、构建信息注入与环境分化这三个框架级特性。选择 pnpm 除了速度与磁盘收益，更因其严格的 node_modules 结构形成了"依赖必须显式声明"的纪律（`@ant-design/cssinjs` 因此出现在 dependencies 中，尽管它也是 antd 的传递依赖）。理解这些"为什么"比记住"是什么"更重要：替换任何一项技术栈时，都要重新评估它对样式分层、动态路由与 Mock 体系的影响。

### 3.3 关键选型决策

- **无 Less 原则**：不安装 `less`，Vite 机制上无法处理 `.less`。布局/原子样式归 Tailwind，组件样式归 antd CSS-in-JS，变量用原生 CSS 自定义属性与 `@theme` 设计令牌，三者覆盖 Less 全部场景（`README.md` 第四节）。
- **Tailwind 与 antd 优先级调和**：全局 CSS 顶部声明 `@layer theme, base, antd, components, utilities;`，配合 `StyleProvider layer`，使 Preflight 不破坏 antd、工具类无需 `!important` 即可覆盖 antd（详见 `docs/tailwind-antd-style-conflict.md` 与 `src/styles/global.css`）。
- **pnpm**：严格 node_modules 结构，因此 `@ant-design/cssinjs` 虽是 antd 的传递依赖，也必须显式声明才能直接 `import`。
- **MSW 而非在线 Mock 平台**：开发态与演示构建共用同一套 handler，接口契约与 `src/api/modules/` 一一对应，且演示站可脱离后端独立运行。
- **环境要求**：Node >= 20.19.0（`package.json` engines），包管理器 pnpm >= 9。

### 3.4 代码规范与工程化约定

工程规范层面有三组约定需要二次开发者知悉。第一组是 **ESLint Flat Config 的顺序敏感性**（`eslint.config.js`）：导出数组的排列依次为忽略目录（`dist/node_modules/coverage` 与生成物 `src/services/**`）、`js.configs.recommended`、`typescript-eslint` 推荐集、项目自定义 TS/TSX 规则、Node 脚本全局变量补充、纯类型文件的 `no-explicit-any` 豁免，最后一项必须是 `eslint-config-prettier`，用于关闭一切与格式化冲突的检查规则——这个"最后一项"是硬约束，插队会导致格式类误报。项目还有几个刻意的规则取舍（源码注释写明理由）：TS 文件关闭 `no-undef`（TypeScript 自身已做未定义检查，重复检查产生误报）；React Hooks 与 React Refresh 规则手动声明而非引用插件预设对象（插件预设的导出结构在大版本间会变，手动声明更稳）；`no-console` 仅放行 `warn` 与 `error`。

第二组是 **Prettier 与编辑器约定**：`.prettierrc.json` 核心项为 `printWidth: 120`、双引号、带分号、`trailingComma: "none"`、`arrowParens: "avoid"`；`.prettierignore` 排除生成物；`.editorconfig` 与 `.vscode/` 提供基础编辑器对齐。

第三组是 **TypeScript 工程结构**：采用 project references 三文件结构——`tsconfig.json` 仅做引用聚合不含编译配置，`tsconfig.app.json` 管业务源码 `src/`（配置 `@` 别名、`strict`、`noUnusedLocals`、`noUnusedParameters`、`verbatimModuleSyntax`），`tsconfig.node.json` 管构建脚本 `vite.config.ts`（需要 `"types": ["node"]`）。`verbatimModuleSyntax: true` 与 ESLint 的 `consistent-type-imports` 规则配合，确保类型导入在编译后被完全擦除，这是业务代码中大量 `import type` 写法的来源。

## 5. 快速上手

### 5.1 环境准备与启动

```bash
node -v    # 需 >= 20.19.0
pnpm -v    # 需 >= 9
pnpm install
pnpm dev   # 启动开发服务器（端口取 .env 的 VITE_PORT=5173，自动打开浏览器）
```

开发态有两个刻意设计（`src/main.tsx`）：

1. **自动预置登录态**：非生产构建时写入 `xiaoye-user`（dev-token + 演示账号）并跳过登录页；`.env.development` 中 `VITE_DEV_AUTO_LOGIN=false` 可关闭，以便完整测试登录/退出/redirect 回跳。
2. **MSW 启动**：`enableMocking()` 在渲染前 `await`，带 5 秒超时兜底与"SW 未接管页面自动整页刷新一次"的时序缺口修复。

开发态菜单直接使用 `src/assets/json/authMenuList.json`（`usePermissions` 短路后端请求），按钮权限仍走 MSW 接口并带 5 秒重试窗口。

### 5.3 二次开发指引（新增一个页面）

1. **建视图**：在 `src/views/<your-module>/index.tsx` 创建组件（目录约定为 `index.tsx`，因为动态路由按 `/src/views + element + .tsx` 解析，见 `src/routers/helper/ConvertRouter.tsx`）。
2. **登记菜单**：开发态把 `{ path, element, meta }` 节点加入 `src/assets/json/authMenuList.json`；接入真实后端后由菜单接口（`GET /api/hooks/menu/list`，mock 见 `src/mocks/modules/auth.ts`）下发。`meta.key` 用于菜单/标签/按钮权限的 i18n 与权限码定位。
3. **定义接口**：手写方式在 `src/api/modules/<domain>.ts` 增加函数并在 `src/api/interface/index.ts` 补类型；契约优先方式则更新 `openapi/oneapi.json` 后执行 `pnpm openapi` 重新生成（生成物 `src/services/api` 禁止手改，见 `src/services/README.md`）。
4. **补 Mock**：在 `src/mocks/modules/` 对应域文件中用 MSW `http.get/post` 注册 handler（与真实接口路径 `/api/hooks/...` 一致）。
5. **补词条**：菜单标题等 UI 文案在 `src/languages/modules/zh.ts` 与 `en.ts` 中按命名空间补充。
6. **验证**：`pnpm typecheck && pnpm lint && pnpm test`，再 `pnpm dev` 目测。生产构建后刷新深链不 404 依赖服务器 `try_files ... /index.html` 回退（`README.md` 部署注意一节）。

### 5.4 接真实后端的改造点

- `.env.development` 的 `VITE_PROXY` 配置 `[["/api", "http://your-backend"]]`（`build/proxy.ts` 会 rewrite 掉 `/api` 前缀并支持 https/ws）；
- 生产 `.env.production` 的 `VITE_API_URL` 保持 `/api` 由 Nginx 反代（当前默认值即是）；
- 将 `openapi/oneapi.json` 替换为后端导出的 swagger/oneapi 文档并重新生成 services；
- 生产环境菜单/按钮权限完全以后端接口为准，接口失败会清空登录态跳登录页、**绝不回退静态全量菜单**（`src/hooks/usePermissions.ts` 注释明确这是防权限绕过的安全设计）。

## 6. 开发态与生产态的行为差异（务必理解）

这套框架里"开发态"与"生产态"的差异不止于接口地址，还涉及权限、Mock 与登录三条主线，二次开发时若不清楚差异会误判问题。

**权限主线**：`usePermissions` 用 `import.meta.env.PROD` 取反判断开发态（而不是 `DEV`，源码注释解释：以 `--mode development/test` 构建部署时 `DEV` 仍为 true，会误判为开发态）。开发态菜单直接取 `src/assets/json/authMenuList.json` 静态数据、零网络等待，仅按钮权限仍请求 MSW 接口（带 5 秒重试窗口）以保证按钮权限演示页有数据；生产态两个权限接口并行请求，菜单失败即清登录态跳登录，空菜单视为合法结果。因此"开发态看得到、生产态看不到的菜单"几乎都是后端菜单数据未下发所致，而不是前端路由注册问题。

**Mock 主线**：开发态恒定启动 MSW；演示构建（`pnpm build:mock`）靠 `VITE_ENABLE_MOCK=true` 在生产产物中保留 MSW；常规生产构建通过动态 `import("@/mocks/browser")` 让 MSW 代码不进入产物。MSW 启动有三重防护（5 秒超时、未接管请求告警、SW 接管缺口自愈刷新），任何一重触发失败都不会阻塞渲染。

**登录主线**：开发态默认预置 `dev-token` 与演示账号直接进主界面，想测完整登录流需把 `.env.development` 的 `VITE_DEV_AUTO_LOGIN` 改为 `false` 并重启 dev server；生产态永远从真实登录开始。另外开发态 `usePermissions` 不会触发菜单接口，意味着"菜单接口超时 30 秒挂起"这类问题只会在生产形态出现——这也是该短路设计诞生的原因（源码注释：避免 mock 不可达时请求挂起）。

## 7. 常见问题排错指引

以下条目均对应源码中真实存在的机制。其一，**页面刷新后深链 404**：history 路由要求服务器把未知路径回退 `index.html`（Nginx `try_files $uri $uri/ /index.html;`），dev server 与 `pnpm preview` 已内置，自建静态服务器必须补齐。其二，**控制台出现"你所访问的资源不存在"**：典型的 MSW 未接管，首装 SW 的时序缺口已由 `main.tsx` 的自动刷新自愈，若仍出现检查 `public/mockServiceWorker.js` 是否与 msw 版本匹配。其三，**切页白屏且控制台报 chunk 加载失败**：发版后旧 chunk 已删除，`ErrorBoundary` 会给出"重试"按钮，恢复联网时自动整页刷新；开发中遇到多半是构建缓存问题。其四，**登录后跳回登录页**：检查菜单接口是否返回成功——生产态菜单失败会清 token，`RouterGuard` 随即拦截跳转，这是设计行为而非 Bug。其五，**整页按钮全部消失**：按钮权限接口最终失败会按"无权限"处理（`usePermissions` 的兜底分支），检查 `/api/hooks/auth/buttons` 的可达性，开发态该接口有 5 秒重试窗口仍失败才会触发。其六，**构建警告 `INEFFECTIVE_DYNAMIC_IMPORT` 与 vendor-antd 超 1.5MB**：均为已知且无害（`README.md` "已知构建提示"），前者源于 login 页被静态与动态双路导入，后者源于 antd 全量引入。

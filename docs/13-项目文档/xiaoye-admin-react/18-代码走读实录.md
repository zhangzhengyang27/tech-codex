## 一、ConvertRouter.tsx：菜单变成路由的五十三行

文件路径 `src/routers/helper/ConvertRouter.tsx`，全文件 65 行，是"菜单即路由"（ADR-01）的执行者。

### 1.1 顶部的 glob 声明与两条注释

````tsx
// Import all view files in the views directory
// Note: import.meta.glob does not support path aliases, so a real path is required here.
// The pattern MUST start with "/" (project root). Only then does Vite return keys as
// root-absolute paths (e.g. "/src/views/home/index.tsx"), which is what the lookup below expects.
// A relative pattern like "../../views/**/*.tsx" would instead yield keys relative to this module
// (e.g. "../../views/home/index.tsx"), making every lookup miss and fall back to "Page Not Found".
const modules = import.meta.glob("/src/views/**/*.tsx") as Record<string, Parameters<typeof lazy>[number]>;
````

这一行是整个动态路由体系的物理基础。`import.meta.glob` 在构建期把 `/src/views/**` 下全部 tsx 文件替换为"路径 → 动态 import 函数"的映射表，注意它返回的是 loader 而非组件——真正的组件代码在路由匹配时才通过网络加载（代码分割由此自动成立）。类型标注 `Record<string, Parameters<typeof lazy>[number]>` 用 `Parameters<typeof lazy>[number]` 取 `lazy()` 的入参类型，比手写 `() => Promise<any>` 更能跟随 React 类型演进。

注释密度在此处是刻意的：六行英文注释守护两个硬约束——glob 不支持路径别名（必须写真实路径）、模式必须以 `/` 开头（否则键是相对本模块的 `../../views/...`，与下方查找键 `"/src/views" + element + ".tsx"` 永远对不上，所有页面静默降级为 Page Not Found 而不报错）。注释甚至给出了正确与错误两种键形态的具体样例，这是"给未来排查者写注释"的范本。

**这段代码教会我们什么**：字符串寻址体系的键格式约定，必须在产生键与消费键的两处代码附近用注释钉死。glob 匹配失败不抛错（构建期只是"没有这批动态导入"），所以这个体系的所有错误都是运行期静默的——凡是静默失败的地方，注释就是唯一的报警器。

### 1.2 转换函数：扁平列表到路由数组的四步翻译

````tsx
export const convertToDynamicRouterFormat = (authMenuList: RouteObjectType[], flatMenuList?: RouteObjectType[]) => {
  // Flat Routing (reuse pre-computed list when available)
  const menuList = flatMenuList ?? getFlatMenuList(authMenuList);

  // Convert Routing (immutable: never mutate input/cloned items directly)
  const handleMenuList: RouteObjectType[] = menuList.map(item => {
    let element = item.element;

    // Set redirection component
    if (item.redirect) element = <Navigate to={item.redirect} />;

    // Convert element string to lazy component
    if (element && typeof element == "string") {
      const loader = modules["/src/views" + element + ".tsx"];
      const Component = LazyComponent(
        loader ? lazy(loader) : lazy(async () => ({ default: () => <div>Page Not Found: {element}</div> }))
      );
      // 注入路由自身 meta：页面（含 KeepAlive 缓存页）从 Context 读取身份，
      // 不依赖全局 URL 反查——缓存页隐藏期间重渲染时全局 URL 可能属于其他页面
      element = (
        <RouteMetaContext.Provider value={item.meta}>
          <RouterGuard>{Component}</RouterGuard>
        </RouteMetaContext.Provider>
      );
    }
````

函数签名先读参数设计：`flatMenuList?` 是可选的预扁平列表。扁平化（`getFlatMenuList`，`src/utils/menu.ts`，递归剥掉 children）在 `useAuthStore.setAuthMenuList` 派生三视图时已经算过一次，这里优先复用避免重复计算——同一个数据在内存态只展平一次，是全项目"派生一次、多处消费"风格的缩影。

主体是 `map` 里的四步翻译。第一步 `redirect` 转 `<Navigate>`：菜单里的目录节点不渲染页面，只负责把浏览器推到第一个子菜单。第二步是核心的键拼接查找：`modules["/src/views" + element + ".tsx"]` 拿到 loader 后包 `lazy()`；未命中时不抛错、不中断整表构建，而是造一个渲染 Page Not Found 的兜底组件——一条坏数据只毁掉一个页面，路由表其余部分照常工作。第三步（兜底分支的构造方式）值得细看：`lazy(async () => ({ default: () => <div>Page Not Found: {element}</div> }))` 把"错误页"也伪装成合法的懒加载组件，让两条分支在类型与结构上完全同构，下游无须写任何 if。第四步是双层包裹：`RouteMetaContext.Provider` 注入该路由自己的 meta（注释解释了为什么不能用全局 URL 反查——KeepAlive 缓存页隐藏期间重渲染时，全局 URL 可能属于别的页面），`RouterGuard` 再包一层守卫。组件链最终形态是 Provider → Guard → Suspense(lazy) 三层，每层各管一件事。

**这段代码教会我们什么**：其一，"降级而非崩溃"要落在数据条目粒度——坏一条数据毁一个页面可接受，坏一条数据毁掉整个路由表不可接受。其二，用同构兜底消除分支：把异常路径也包装成正常类型，下游代码就不需要防御分支，这是消除 if 的正统方式。其三，Context 注入的是"页面自己的身份"而不是"当前 URL 的身份"，凡是有缓存/延迟渲染的地方，身份判定都不能依赖全局易变态。

### 1.3 loader 与不可变收尾：meta 下发与 isFull 分流

````tsx
    // Set loader
    const loader = () => {
      return { ...item.meta, redirect: !!item.redirect };
    };

    // Return a new object without children (avoid delete side-effect)
    const { children: _children, ...rest } = item;
    return { ...rest, element, loader };
  });

  const layoutRoutes = handleMenuList.filter(item => !item.meta?.isFull);
  const fullScreenRoutes = handleMenuList.filter(item => item.meta?.isFull);

  return [{ element: <LayoutIndex />, children: layoutRoutes }, ...fullScreenRoutes] as RouteObjectType[];
};
````

`loader` 把 meta（附带 `redirect: !!item.redirect` 布尔化标记）下发给 react-router 的 `useLoaderData`——路由元信息的官方通道，标签栏与面包屑由此拿到当前页的 key/title。收尾两行是 JavaScript 解构的教科书用法：`const { children: _children, ...rest } = item` 用"取出来扔掉"的方式剥离 children，`_` 前缀恰好命中 ESLint 的 `no-unused-vars` 豁免规则（`eslint.config.js` 的 `^_` 豁免），注释点明动机是 "avoid delete side-effect"——不 mutate 输入是这条链路能被 `useMemo` 安全缓存的前提（ADR-01 的"路由表不可原地修改"规约同源）。

最后按 `meta.isFull` 一刀分两半：普通路由全部塞进一个**无 path** 的 `<LayoutIndex />` 的 children，全屏路由平铺在顶层。这个"无 path 布局路由"是整套设计的结构支点——它让所有页面共享布局又不产生路径前缀，也让顶层 path 列表在菜单加载前后完全相同（这正是《01-系统架构》4.1 说的"路径指纹永远不变"陷阱的结构性成因）。

**这段代码教会我们什么**：其一，不可变不是教条而是缓存正确性的前提——`useMemo` 依赖数组里的东西，必须是纯派生的。其二，用结构（无 path 父路由）表达"共享外壳"，比在每个页面里重复引入布局干净一个量级。其三，函数式收尾（filter 分流）比命令式循环拼两个数组更难写错，因为每个数组的来源一目了然。

### 1.4 与 routers/index.tsx 的交接：引用相等性作为重建信号

`ConvertRouter` 的返回值被 `src/routers/index.tsx` 的 `useMemo` 消费：

````tsx
const router = useMemo(() => {
  const createRouter = mode === "history" ? createBrowserRouter : createHashRouter;
  // Menu not loaded yet: keep the static router so "*" renders <Loading /> instead of 404.
  if (!authMenuList.length) {
    return createRouter(wrappedStaticRouter as RouteObject[], { future: { v7_relativeSplatPath: true } });
  }
  const dynamicRouter = convertToDynamicRouterFormat(authMenuList, flatMenuList);
  // Use immutable map to avoid mutating the wrappedStaticRouter module-level constant.
  const finalRouter = [...wrappedStaticRouter, ...dynamicRouter].map(item =>
    item.path === "*" ? { ...item, element: <NotFound /> } : item
  );
  return createRouter(finalRouter as RouteObject[], { future: { v7_relativeSplatPath: true } });
}, [authMenuList, flatMenuList]);
````

三个细节收束这个文件群。其一，菜单未就绪时返回纯静态路由，`*` 渲染 `<Loading />`——刷新页面时权限接口未返回的窗口期里，用户看到骨架而非误报 404（两段式兜底，见《02-页面设计》第 2 节）。其二，`*` 路由的元素替换用 `.map` 生成**新数组**，注释明确不能原地改 `wrappedStaticRouter` 这个模块级常量——改了会影响下一次重建的起点，属于典型的"全局可变状态泄漏"。其三，依赖数组是 `[authMenuList, flatMenuList]` 两个**引用**，源码上方的大段注释解释了为什么不能用"路径指纹"：所有动态路由都嵌在同一个无 path 布局路由下，顶层 path 列表永远相同，指纹永不变化，路由器会停在空菜单版本。以数组引用为信号，既保持菜单不变时 router 实例稳定（不重建），又保证菜单内容变化时必定重建。

**这段代码教会我们什么**：当"状态变没变"无法用内容指纹廉价判定时，引用相等性（配合不可变更新纪律）是 React 官方认可的正确信号。前提是全链路守纪律——任何一处原地修改都会让引用信号失灵，这就是为什么上游 ConvertRouter 用解构而非 delete。

## 二、api/index.ts：113 行裁决全站错误语义

文件路径 `src/api/index.ts`，全文件 113 行。机制全景见《03-接口设计》1.2-1.4，这里带码走读。

### 2.1 配置与自定义配置类型

````ts
export interface CustomAxiosRequestConfig extends InternalAxiosRequestConfig {
  loading?: boolean;
  /**
   * 逃生口：跳过全局错误提示（业务码 / HTTP 状态码的统一处理），由页面自行 catch 处理。
   * 注意业务 401 仍会清登录态并跳转登录页，只是不弹提示。
   */
  skipErrorHandler?: boolean;
}

const config = {
  baseURL: import.meta.env.VITE_API_URL as string,
  timeout: ResultEnum.TIMEOUT as number,
  withCredentials: false
};
````

三个环境无关的全局决策在此定档：`baseURL` 全部走环境变量（各环境均为 `/api`，由 Nginx 反代，见《14-配置与环境详解》3）；`timeout` 引用枚举 `ResultEnum.TIMEOUT`（30000）而非裸数字——魔法数字收口到 `src/enums/httpEnum.ts`，改超时只动一处；`withCredentials: false` 是无 Cookie 鉴权（ADR-11）的落点。`skipErrorHandler` 的 JSDoc 是全文件最重要的一条注释：它把语义写成"逃生口而非豁免口"——页面可以接管**提示**，但接管不了**登录态清理**。这半句话决定了后面 401 分支的代码顺序。

**这段代码教会我们什么**：给扩展开关写文档的最好位置是类型定义上方的 JSDoc，IDE 悬停即见。开关语义要拆成"哪些行为可跳过、哪些不可跳过"两半说清楚，含糊的"跳过错误处理"会让使用者误以为连登出都不发生。

### 2.2 请求拦截器：两件事与一个兼容检查

````ts
this.service.interceptors.request.use(
  (config: CustomAxiosRequestConfig) => {
    if (config.loading) showFullScreenLoading();
    if (config.headers && typeof config.headers.set === "function") {
      config.headers.set("x-access-token", useUserStore.getState().token);
    }
    return config;
  },
  (error: AxiosError) => Promise.reject(error)
);
````

拦截器只做两件事：按需全屏 loading（`showFullScreenLoading` 内部计数器管理并发，"第一个开、最后一个关"）、注入 `x-access-token`。两个细节都是防御性的。第一，token 是**每次请求时**从 store 现读的（`useUserStore.getState().token`），不是实例化时闭包缓存——登录、登出、切换账号后不需要任何"刷新 token 缓存"的操作，store 是唯一事实源。zustand 允许在 React 之外调用 `getState()`，这让拦截器保持纯函数形态。第二，`typeof config.headers.set === "function"` 的检查是给 axios 1.x 的 `AxiosHeaders` 兼容留的：headers 可能是普通对象（没有 set 方法），直接调用会在某些请求形态下抛错。

**这段代码教会我们什么**：请求层的"全局状态"（token）应该在每个使用点现读现用，而不是启动时快照——前者天然跟随状态变化，后者制造出一类"改了却不生效"的玄学 Bug。兼容性检查的价值在 prevent：一行 `typeof` 换掉的是升级 axios 时的整批用户报障。

### 2.3 响应拦截器成功回调：分支顺序即语义

````ts
(response: AxiosResponse) => {
  tryHideFullScreenLoading();
  // Blob/stream responses (file download) should bypass code-check logic
  if (response.config.responseType === "blob") return response.data;
  const { data } = response;
  const { skipErrorHandler } = response.config as CustomAxiosRequestConfig;
  // login failure（业务 401）：无论是否 skip 都必须清登录态并跳登录页，skip 只影响是否弹提示
  if (data.code == ResultEnum.OVERDUE) {
    useUserStore.getState().setToken("");
    // 同时清空菜单 / 按钮权限，避免下一个账号继承上一个账号的权限
    useAuthStore.getState().resetAuth();
    if (!skipErrorHandler) showBizError(data);
    navigateTo(buildLoginUrlWithRedirect());
    return Promise.reject(data);
  }
  if (data.code && data.code !== ResultEnum.SUCCESS) {
    if (!skipErrorHandler) showBizError(data);
    return Promise.reject(data);
  }
  return data;
}
````

分支顺序本身就是一份协议文档，逐条读。第一行 `tryHideFullScreenLoading()` 与请求侧的计数器配对，放在最前保证任何后续分支（包括 return）都不漏减计数。Blob 直通分支必须先于信封检查：二进制流被当 JSON 读 `code` 会得到 undefined，直通返回原始数据是唯一正确处理。业务 401 分支是全文件的语义核心，四步顺序经过刻意编排：**先清 token、再清权限、然后按需提示、最后跳转**——清理在前保证无论后面哪一步抛异常，登录态已经干净；`resetAuth()` 单独调用（而非依赖 setToken 连带清理）是为了把"权限串号"的教训（bug-audit P1-4：只清 token 不清菜单，下一个账号看到上一个账号的菜单）显式写进代码；跳转用 `buildLoginUrlWithRedirect()` 把当前地址编码进 `?redirect=`（安全校验见 `src/utils/safeRedirect.ts`，防 Open Redirect）；最后 `Promise.reject(data)` reject 的是**信封对象**而非 AxiosError，页面 catch 里直接 `err.msg` 可用。普通业务错误分支对称地短：按 showType 分流提示、reject 信封。成功分支返回整个信封 `data`，调用方以 `const { data } = await api()` 解构。

`data.code == ResultEnum.OVERDUE` 用宽松相等是刻意的：后端可能返回字符串 `"401"`，`==` 吞掉类型差异；而下一个分支用 `data.code && data.code !== ResultEnum.SUCCESS` 两段判断，第一段挡住 `code` 缺失的响应（blob 之外的非标准响应不被误判为错误）。

**这段代码教会我们什么**：其一，分支顺序是 API——先做不可跳过的（清理）、再做可跳过的（提示）、最后做流程性的（跳转、reject），这个顺序让"逃生口"天然只能逃过提示。其二，reject 值的形态要全项目统一并写进文档，页面代码的可读性一半取决于 catch 到的东西长什么样。其三，把历史 Bug（权限串号）固化成显式调用 + 注释，比相信"以后不会有人合并那行删掉"可靠得多。

### 2.4 错误回调与 RequestHttp 封装

````ts
async (error: AxiosError) => {
  tryHideFullScreenLoading();
  const { skipErrorHandler } = (error.config ?? {}) as CustomAxiosRequestConfig;
  if (!skipErrorHandler) showHttpError(error);
  return Promise.reject(error);
}
````

HTTP 层异常（网络错误、超时、非 2xx）的回调极短：减计数、按需 `showHttpError`（内部依次识别超时文案、断网文案、checkStatus 状态码映射，断网时跳 `/500`）、原样 reject AxiosError。`error.config ?? {}` 的空值合并挡住"请求根本没发出去"（config 为 undefined）的场景。注意这里 reject 的是 AxiosError 本身——与成功回调 reject 信封对象形成两种形态并存，登录页的 `getLoginErrMsg` 演示了兼容两者的写法（见《12-FAQ与故障排查》3.3）。

类壳 `RequestHttp` 对外暴露 `get/post/put/delete/download` 五个泛型方法，`download` 强制 `responseType: "blob"` 并返回 `BlobPart`——下载语义在类型层与信封体系隔离。文件以 `export default new RequestHttp(config)` 收尾：**单例**是这套管线成立的前提，全站所有请求（含 openapi 生成代码经 `src/api/openapiRequest.ts` 的桥接）共享同一组拦截器行为。

**这段代码教会我们什么**：错误处理要分层定价——业务错误（有信封）与传输错误（无信封）是两类东西，reject 值形态不同、处理策略不同，混在一层会让页面永远猜不准 catch 到什么。而单例不是偷懒，是让"全局语义只写一遍"的结构手段。

## 三、双自愈机制：main.tsx 的 MSW 接管与 ErrorBoundary 的 ChunkLoadError

### 3.1 enableMocking：三重有界等待

文件路径 `src/main.tsx` 第 37-71 行（完整机制见《10-性能设计与优化》4）：

````tsx
async function enableMocking(): Promise<boolean> {
  if (import.meta.env.PROD && import.meta.env.VITE_ENABLE_MOCK !== "true") return true;
  const { worker } = await import("@/mocks/browser");
  await Promise.race([
    worker.start({
      onUnhandledRequest: "warn",
      serviceWorker: { url: "/mockServiceWorker.js" }
    }),
    new Promise((_, reject) => setTimeout(() => reject(new Error("启动超时（5s）")), 5000))
  ]);

  const RELOAD_FLAG = "xiaoye-msw-claim-reload";
  if (!navigator.serviceWorker.controller) {
    await new Promise(resolve => setTimeout(resolve, 300));
    if (!navigator.serviceWorker.controller) {
      if (sessionStorage.getItem(RELOAD_FLAG)) return true;
      sessionStorage.setItem(RELOAD_FLAG, "1");
      window.location.reload();
      return false;
    }
  }
  sessionStorage.removeItem(RELOAD_FLAG);
  return true;
}
````

三重防护读起来是三个递进的"如果坏了怎么办"。第一重，构建期短路：PROD 且未开 `VITE_ENABLE_MOCK` 直接 return true——动态 `import("@/mocks/browser")` 也就从未执行，MSW 代码被 tree-shake 出常规生产产物（演示构建三态见 ADR-06）。第二重，5 秒竞速：Service Worker 注册在隐私模式、禁 SW、部分无头环境会无限挂起，`Promise.race` 把等待变成有界——超时的代价只是接口不可用，渲染照常（`bootstrap` 的 catch 会打 `[msw] 启动失败` warn 后继续渲染）。第三重，接管缺口自愈：SW 首次安装存在 `clients.claim()` 的时序缺口——worker 已激活但当前页面未被纳入控制（`navigator.serviceWorker.controller` 为 null），页面请求全部穿透到真实网络，表现为"你所访问的资源不存在"；处理是等 300ms 复查一次（claim 异步生效），仍未接管就整页刷新一次（第二次加载时 SW 从导航起就接管，必然生效），`sessionStorage` 键 `xiaoye-msw-claim-reload` 防异常环境无限刷新循环。函数返回 `false`（触发过刷新）时 `bootstrap` 不渲染——渲染权让给刷新后的那次启动。

**这段代码教会我们什么**：其一，每一层等待都要有上界，"宁可功能缺失、不可整站不可用"要翻译成具体的竞速代码而不是口头原则。其二，环境问题的自愈要用"状态标记 + 一次性动作"防住复发（无限刷新比 mock 失效更糟）。其三，注释里写清故障的现象学（"表现为各页面报『你所访问的资源不存在』"）——下一个遇到该现象的人会先搜报错文案，注释是给他们准备的入口。

### 3.2 ErrorBoundary：识别、重试、自动刷新三段式

文件路径 `src/components/ErrorBoundary/index.tsx`。先看识别函数：

````tsx
function isChunkLoadError(error: Error): boolean {
  return (
    error.name === "ChunkLoadError" ||
    /(?:loading|failed to load) (?:css )?chunk/i.test(error.message) ||
    /Failed to fetch dynamically imported module/i.test(error.message)
  );
}
````

chunk 加载失败没有标准错误类型——webpack 系叫 `ChunkLoadError`，Vite/Rollup 系报 "Failed to fetch dynamically imported module"，浏览器还可能报 "loading chunk failed"。识别函数用"名字 + 两条消息正则"三路并判把方言归一。发版场景里这是高频路径：服务器删除旧 hash chunk 后，停留在旧页面的用户一切路由就命中它。

````tsx
handleRetry = () => {
  // 自增 retryCount 改变 Fragment 的 key，强制 React 卸载重挂载全部 lazy 组件
  this.setState(prev => ({ hasError: false, error: null, retryCount: prev.retryCount + 1 }));
};

handleOnline = () => {
  this.setState({ isOnline: true });
  // chunk 加载失败且已恢复联网：几乎可以断定是发版导致的资源失效，直接整页刷新
  if (this.state.hasError && this.state.error && isChunkLoadError(this.state.error)) {
    window.location.reload();
  }
};

render() {
  if (!this.state.hasError || !this.state.error) {
    return <React.Fragment key={this.state.retryCount}>{this.props.children}</React.Fragment>;
  }
  // ... 兜底 UI：按 isChunkError 与 isOnline 组合出四态文案，chunk 态额外提供"重试"按钮
}
````

重试的实现是整个文件最反直觉也最有教育意义的一处：`hasError` 置回 false 并不奏效——源码注释解释了原因，React.lazy 会**缓存已 reject 的 promise**，再渲染同一个 lazy 组件仍会抛出同一个错误。因此"重试"的真实机制是自增 `retryCount` 并把它挂到 `render` 顶层 Fragment 的 `key` 上：key 变化强制 React 卸载整个子树重挂载，所有 lazy 组件重新执行 `import()`，此时用户浏览器拿到的是服务器上的**新** index.html 引用的**新** chunk，问题根治。自动刷新则是第二个自愈出口：组件监听 `online` 事件，处于 chunk 错误态时恢复联网几乎可以断定是发版失效（旧 chunk 404 常伴随网络报错），直接 `window.location.reload()` 拉取新版资源，用户甚至不需要点重试。

**这段代码教会我们什么**：其一，框架层的"重试"按钮，语义必须是"让失败的那个动作真的重做一遍"，而不是把错误状态变量清零——区分这两者是前端容错设计的分水岭。其二，React 的缓存行为（lazy promise 缓存、memo、Suspense 复用）意味着"重新渲染"不等于"重新执行"，改 key 强制重挂载是应对前者唯一可靠的杠杆。其三，把两个自愈出口（手动重试、联网自动刷新）叠在同一种错误上，覆盖"用户在场"与"用户挂机"两种场景——可用性设计的完整性体现在兜底出口的数量上。

### 3.3 双自愈的合流：同一哲学的两次落笔

把 `enableMocking` 与 ErrorBoundary 并排看，能看到同一套哲学的两次落笔：**故障被分类、每类故障配有界的恢复动作、恢复动作不可自我循环**。MSW 启动失败（有界等待后放弃）与 chunk 失效（有界重试 + 自动刷新）都没有"无限重试"或"阻塞用户"的分支；两者的异常环境（SW 缺失、断网）都有降级形态（无 mock 照常渲染、断网提示文案）；两者都留下了排查锚点（`[msw]` 日志前缀、`xiaoye-msw-claim-reload` 标记、`[ErrorBoundary]` 组件栈日志——完整清单见《12-FAQ与故障排查》第 4 节）。复刻这类机制时，按"分类 → 有界恢复 → 防循环 → 留锚点"四件套检查，通常不会漏。

## 结语：三个文件，三种可迁移的能力

三个文件的公共气质可以概括为：**在类型与注释里写协议，在分支顺序里写策略，在 key 与引用里写缓存正确性**。ConvertRouter 用 65 行完成了别的框架数百行路由配置做的事，靠的是"数据（菜单）即配置"的勇气与降级兜底的谨慎；api/index.ts 用 113 行统一全站错误语义，靠的是分支顺序的纪律与对历史 Bug 的显式固化；双自愈机制总共不到百行，却覆盖了演示与生产环境的两大可用性杀手。走读的终点不是记住这些代码，而是带走它们的方法：静默失败处留注释、扩展开关写清可跳过与不可跳过、重试必须真的重做失败动作、每层等待设上界。把这四条带回自己的代码，本次走读就完成了它的任务。
